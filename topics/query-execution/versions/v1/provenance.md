## Sources

- [PostgreSQL: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) — accessed 2026-07-29 — supports: `EXPLAIN (ANALYZE, BUFFERS)` semantics — the cost-estimate-versus-actual-time distinction, buffer hit/read accounting, and the plan-node reading discipline the piece applies to every transcript on the page.
- [PostgreSQL: ANALYZE](https://www.postgresql.org/docs/current/sql-analyze.html) — accessed 2026-07-29 — supports: `ANALYZE` as the statement that resamples table statistics into `pg_statistic`, distinct from the `ANALYZE` option inside `EXPLAIN`, and the fact that stale statistics persist — `n_mod_since_analyze` climbing, `last_autoanalyze` empty — until it runs.
- [PostgreSQL: Statistics Used by the Planner](https://www.postgresql.org/docs/current/planner-stats.html) — accessed 2026-07-29 — supports: `pg_stats`' stored per-column frequencies, the row-estimate arithmetic (a stored frequency times the row count) the piece verifies by hand against the planner's own `rows=` figures, and most-common-value-list-driven selectivity generally.
- [PostgreSQL: Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html) — accessed 2026-07-29 — supports: index-only scans requiring the visibility map to skip the heap, the `INCLUDE` clause building a covering index, and `Heap Fetches` as the count of heap accesses an index-only scan needed anyway.
- [PostgreSQL: The Cumulative Statistics System](https://www.postgresql.org/docs/current/monitoring-stats.html) — accessed 2026-07-29 — supports: `pg_stat_user_indexes` and its `idx_scan` counter as the record of how often an index was actually used, which is what the piece reads to answer "did anything use it."

## Synthesis

- MEASURED FOR THIS CUT (v1). The article's worked figures come from two labs run on 2026-07-29, both PostgreSQL 16.14 (`postgres:16-alpine`, image `sha256:e013e867e712fec275706a6c51c966f0bb0c93cfa8f51000f85a15f9865a28cb`) in Docker on an arm64 Mac laptop. The full harness — setup scripts, driver scripts, environment records, and immutable raw logs — is published beside this article at `topics/query-execution/evidence/`; every measured figure in the article traces to a named raw file there.
- Measured — the selectivity flip (`evidence/selectivity/raw/02-selectivity-flip.log`): the same indexed `status` column produces `Index Scan using orders_status_idx` at 1.012% selectivity (`cancelled`, cost=0.43..9105.51, actual rows=20241, Buffers shared hit=11764, Execution Time 5.467 ms) and `Seq Scan on orders` at 94.987% selectivity (`shipped`, cost=0.00..41667.00, actual rows=1899747, Buffers shared hit=14661 read=2006 written=32, Execution Time 156.691 ms) — the planner pricing the same column differently by row-count share, not refusing or favoring the index on principle.
- Measured — the covering-index refusal until `VACUUM` (`evidence/selectivity/raw/03-covering-index.log`): after `CREATE INDEX orders_status_covering_idx ON orders (status) INCLUDE (customer_id, total)` but before `VACUUM` (`relallvisible` still 0), the planner keeps using the 13 MB plain index — same cost 14082.32, same ~16,607 buffers, three runs running. After `VACUUM` sets `relallvisible` to 16667/16667, the same query flips to `Index Only Scan using orders_status_covering_idx`, `Heap Fetches: 0`, cost 2974.60, Buffers 398 — 41.7x fewer pages than the pre-VACUUM plan.
- Measured — stale statistics, `rows=1` against an actual 500,000 (`evidence/selectivity/raw/04-stale-stats.log`): 500,000 rows inserted under a never-before-seen `status` value with no `ANALYZE` run; the planner estimates `rows=1` (actual 500000), `cost=0.43..8.45`, Execution Time 55.917 / 50.636 / 50.920 ms. After `ANALYZE orders`, the estimate moves to `rows=506417` and the plan flips to a `Bitmap Heap Scan`, Execution Time 37.953 / 37.642 / 37.305 ms — a 13–18 ms difference in this run, priced cheaply here because the misestimated node feeds nothing downstream.
- Measured — the join fix arc (`evidence/slow-query/raw/03-explain-before.log`, `05-after-fix-1.log`, `07-after-fix-2.log`, `08-close.log`): the unindexed join reads 26,933 buffers (11,983 hit + 14,950 read); adding `order_items(order_id)` drops it to 9,413 buffers; adding `orders(user_id, created_at)` drops it to 1,800 buffers (1,800 hit + 0 read, nothing outside shared memory). Timed runs fall from 180.537 / 149.901 / 138.042 ms with no join indexes to 4.516 / 1.824 / 1.227 ms with both.
- Measured — the counters close (`evidence/slow-query/raw/08-close.log`): `pg_stat_user_indexes` shows `order_items_order_id_idx` at `idx_scan=2080` and `orders_user_id_created_at_idx` at `idx_scan=12` — the two indexes added this lab — against `order_items_pkey` at 0 and `orders_pkey` at 24, closing the "did anything use it" question the article poses at the end.
- Claims explicitly NOT measured, and not claimed in the article: the write-path cost of the two new indexes on the join table (build time and size are logged; ongoing write overhead was not tested); `CREATE INDEX CONCURRENTLY`, which the article names as untested here; production-scale behavior — both labs ran on a single laptop container with sibling containers sharing the Docker VM, so absolute millisecond timings are directional and plan shapes, row counts, and buffer counts carry the argument; and any cross-engine claim — every measurement in this cut is PostgreSQL 16.14-specific, and the article makes no claim about any other database engine's planner or statistics behavior.
- The stance itself: read the plan, not the schema — an index is a suggestion the planner prices and is free to refuse, and `EXPLAIN ANALYZE` is how you find out what your query actually did.

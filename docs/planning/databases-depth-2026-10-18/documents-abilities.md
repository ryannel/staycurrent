# Document databases: abilities before pages

18 October 2026. Independent derivation for the depth commission. This file was saved before assigning teaching homes or page boundaries. It does not use an existing collection inventory, outline or coverage map. The `staycurrent-planning` and `staycurrent-style` skills and the authoring depth reference guide the derivation. The commission's restrictions take precedence over their usual instruction to inspect existing collections.

## Audience and destination

An application engineer understands records, APIs, basic queries and deployment. They may arrive with a flexible product catalogue, an array query returning the wrong result, an overloaded tenant or an acknowledged update that appears to have disappeared. Relational expertise is not an entry requirement.

An expert practitioner can defend the boundary of a document, preserve an application's invariants while that boundary changes, predict the cost and meaning of nested queries, select a product contract, and operate one representative implementation through failure and recovery. Knowing the names of embedding, multikey indexing and sharding is insufficient. The reader must explain why a design fails when an array grows, two writers race, a large tenant dominates, an index falls behind or recovery discards a later valid change.

The family includes document-oriented persistence with identity, nested values and queryable fields. JSON as an interchange format is insufficient. A relational JSON column, an opaque key-value blob and a search index can solve overlapping problems without becoming equivalent database contracts. Those boundaries need a decision, not a taxonomy lecture.

## Expert tasks decomposed into teachable units

Each row follows task → required understanding → unit. IDs are fresh and stable for this derivation. The proposed form is the least demanding evidence that would teach the ability; it is not yet a page assignment. Units describe general reasoning where possible. Implementation units are explicitly marked.

## Representative implementation abilities

MongoDB is the proposed initial implementation, not the definition of a document database. These units require actual commands, limits and mechanism explanations that cannot be taught honestly as universal family behaviour. They are deliberately decomposed before grouping.

## Running material, evidence and exclusions

Use a configurable equipment catalogue. Product `p104` belongs to tenant `t7`; variants contain colour, size and availability. Supplier `s9` owns mutable contact data. Orders preserve the purchased variant and price. Stock reservations are separate when their independent write rate requires it. A product's bounded activity preview points to complete event records. This gives one familiar dataset without asserting that all of these records belong in one database or one document. A later reporting query is allowed to argue for a different store.

No browser library is assumed to execute MongoDB. Inspectable array/index/routing models can run locally in the page but must be labelled models. BSON semantics, query plans, transactions, elections, streams and restore work require a pinned native implementation. A single process cannot establish replica-set or sharded behaviour. No experiments have been run for this derivation.

Primary-source scope checks made before grouping:

- [MongoDB embedding](https://www.mongodb.com/docs/manual/data-modeling/embedding/) grounds the need to teach growth and document boundaries; the documented 16 MiB limit is product-specific, not a family property.
- [MongoDB multikey indexes](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-multikey/) makes same-element query reasoning and array-entry constraints consequential. Constraint details need rechecking against the article's pinned version.
- [WiredTiger](https://www.mongodb.com/docs/manual/core/wiredtiger/) distinguishes cache, history, checkpoints and journal. It warrants real storage depth rather than an introductory storage paragraph.
- [Read isolation, consistency and recency](https://www.mongodb.com/docs/manual/core/read-isolation-consistency-recency/) distinguishes concerns and causal sessions. It rules out one generic claim that MongoDB is simply consistent or eventually consistent.
- [Shard-key choice](https://www.mongodb.com/docs/v8.3/core/sharding-choose-a-shard-key/) and [troubleshooting](https://www.mongodb.com/docs/manual/core/sharding-troubleshooting-shard-keys/) distinguish cardinality, skew, monotonic growth and routing. Exact current tooling needs later version verification.
- [Change streams](https://www.mongodb.com/docs/manual/changestreams/) makes resumable history a bounded operational resource. A stream is not a permanent recovery archive.
- [Couchbase Query Service](https://docs.couchbase.com/server/current/learn/services-and-indexes/services/query-service.html) and [SDK query consistency](https://docs.couchbase.com/cxx-sdk/current/concept-docs/n1ql-query.html) show an alternative where document querying and index visibility have a different implementation contract.
- [Firestore indexing](https://firebase.google.com/docs/firestore/query-data/indexing), [offline access](https://firebase.google.com/docs/firestore/manage-data/enable-offline) and [billing](https://firebase.google.com/docs/firestore/pricing) justify considering client synchronisation, query/index requirements and charging. Firestore now distinguishes operation families/editions in its documentation; claims must name the selected edition and operations.

These are planning evidence, not a verified article source set. Server versions, editions, defaults, commands and limits remain article-verification work. Shared distributed-systems teaching stays parked; these units teach only the replica and placement behaviour needed for the database decision. Search ranking, analytical engine internals, legal retention policy, broad cloud infrastructure and every SDK language are outside the collection. Their boundaries must leave sufficient local context to make the document-database decision.

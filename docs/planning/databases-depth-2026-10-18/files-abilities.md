## Reader and destination

The reader builds or operates services that store files, run databases on volumes, or share directories between machines. They can run a programme and inspect a server but need no filesystem implementation background. Expertise here means choosing the right interface, predicting its important failure behaviour, measuring the work, changing storage safely and recovering useful application data. It does not mean implementing an allocator, SSD firmware, a distributed filesystem or a cluster manager.

A single running workload can connect the work: an image-processing service stores uploads under `/srv/media`, publishes a manifest, runs two worker processes, keeps a small application database on a separate volume, and later serves a second machine. The manifest names generation `g17`; replacing it with `g18` changes which immutable output files readers use. The database has useful writes after a bad manifest publication, so recovery must preserve or reconcile those later writes. Names and data are illustrative, not a claim that this layout is suitable for every service.

The units below are the smallest useful teaching commitments, not headings or promises of one page each. “Native” means a disposable Linux VM or other specified real environment. A browser model exposes chosen states; it cannot establish kernel, device or provider behaviour.

## Derive the work into units

| Select a storage interface and identify who owns each promise | An application addresses names and byte ranges; a filesystem maps names to objects and storage; a block device exposes addressable blocks; remote services add their own contract | **FS-U01** Match mutable files, shared trees, embedded/database storage and opaque objects to interfaces using concrete operations, not a binary/blob feature checklist. Worked choice cases. **FS-U02** Trace process → runtime buffer → kernel cache → filesystem → volume/device → provider, and assign visibility, ordering, durability and access promises to the layer that supplies them. Inspectable diagram. **FS-U03** Separate host loss, volume loss, zone loss, account/key loss and accidental deletion; persistent, replicated and backed up answer different failures. Failure-domain table. |
| Predict what a path operation changes | A path is a lookup through a namespace, whereas an open descriptor refers to an opened object | **FS-U04** Resolve names, mount points, links and descriptors; demonstrate open-then-unlink and an overmounted directory. Native inspection. **FS-U05** Predict create, rename, replacement and deletion with existing readers, including same-filesystem atomic name changes and cross-filesystem copy boundaries. Two-reader trace. **FS-U06** Check enumeration, case, Unicode, path and metadata assumptions when moving between systems; directory listing is not an application transaction. Small portability cases, with native-platform references rather than a universal POSIX promise. |
| Read and change bytes correctly | System calls can complete partly; offsets and caches are state separate from the bytes eventually stored | **FS-U07** Handle short reads/writes, offsets, append, interruption and checked errors; a successful close is not an application commit protocol. Native small programmes and traces. **FS-U08** Choose buffered I/O, direct I/O or memory mapping from caching, alignment, visibility and error consequences; direct does not mean durable and mapping does not mean transaction. Paired access traces, plus a native mmap/truncate failure. |
| Define what “saved” means across a crash | Acknowledgement, visibility and persistence are different events, and names need persistence as well as contents | **FS-U09** Choose a synchronisation boundary and account for fsync/fdatasync, checked failure and the application's own buffering. Ordered timeline. **FS-U10** Build a durable single-file replacement protocol, including file contents, rename and directory synchronisation, under a stated OS/filesystem contract. Crash-point model and later native verification. **FS-U11** Recognise that sectors, individual writes and multi-file updates need different atomicity guarantees; use checksums, generation manifests or an application log where needed. Torn-record and two-file counterexamples. **FS-U12** Follow flush/FUA through device/virtualisation layers and distinguish documented power-loss protection from the OS requesting persistence. Mechanism figure and contract-reading exercise. **FS-U13** Explain how journalling or copy-on-write makes filesystem structures recoverable without implying that arbitrary application state is committed. Before/after crash model. **FS-U14** Treat deferred writeback errors and ambiguous outcomes as application/recovery events; do not blindly retry an append or call another fsync and declare the previous failure repaired. Failure trace with explicit unknown state. |
| Coordinate multiple writers and long-lived readers | Namespace atomicity, write atomicity and application invariants have different scopes; locks work only under the appropriate contract | **FS-U15** Expose read-modify-write loss, lock scope/lifetime, advisory cooperation and lock-file replacement hazards. Two-process worksheet. **FS-U16** Design append, rotation and reader handover with descriptors that survive rename; do not infer a portable record-append guarantee from a local demonstration. Trace. **FS-U17** Publish a coherent generation of several files, manage old generations and bound reader/reclaimer races. Manifest model that first mixes generations and then fixes them. |
| Confine access and retain the ability to recover | Path traversal, process identity, filesystem policy and key ownership operate at different boundaries | **FS-U18** Avoid check-then-open races, unexpected symlinks and untrusted relative paths; distinguish a directory handle strategy from a complete sandbox. Native adversarial case. **FS-U19** Evaluate owner/group/mode, directory search permission, ACLs and inherited policy; explain how a container identity or remote user mapping changes the result. Permission worksheet. **FS-U20** Choose encryption scope and key custody; distinguish access revocation, file unlink, discard and sanitisation across retained copies, snapshots and keys. Threat and recovery cases; no compliance certification or cryptographic algorithm curriculum. |
| Share files across machines without inventing local guarantees | Network clients cache data and names; servers arbitrate state; interruption can leave operations outstanding | **FS-U21** Distinguish a network filesystem, a synchronised copy and a multiply attached block device. Choose the actual sharing contract. **FS-U22** Predict cache revalidation, close-to-open behaviour, locking and concurrent mutation under a stated protocol/version; a local POSIX example is insufficient. Two-client state model. **FS-U23** Handle stalled calls, retry/timeout choices, server restart and lease/state recovery; availability tuning can change correctness. Failure timeline. **FS-U24** Explain why shared blocks need coordinated filesystem ownership and fencing; retrying an old writer after failover can corrupt a volume. Small fencing model, with cluster implementation external. |
| Provision and change storage without damaging the wrong thing | Device names, partitions, mapping layers and filesystems have independent sizes, identities and lifecycles | **FS-U25** Identify a device end to end using stable identities and inspect partitions, volume mappings, mounts and ownership before a change. Native inventory. **FS-U26** Plan initialise/mount/persist, grow, migrate or shrink as ordered operations with supported rollback; resizing the provider volume does not resize every layer. Native disposable-volume worksheet. **FS-U27** Select mirror/stripe/parity arrangements using usable capacity, failure tolerance, write behaviour and degraded rebuild exposure; redundancy is not a backup. Worked loss and rebuild cases, not a RAID implementation course. **FS-U28** Account for logical/physical sectors, alignment, SSD erase/write amplification, endurance and discard propagation sufficiently to interpret provisioning and latency; do not tune opaque firmware from a cartoon. Diagrams and vendor/device evidence reading. |
| Keep capacity available while the application runs | Logical size, allocated blocks, live names, retained versions and physical pool use can diverge | **FS-U29** Diagnose free-byte, inode/metadata, quota, deleted-open-file and sparse/preallocated-space differences. Contrasting counters and native cases. **FS-U30** Budget thin pools and snapshot/COW growth, including metadata capacity; apparent free space inside a guest cannot protect an exhausted pool. Space ledger. **FS-U31** Set headroom, growth alarms, quotas and retention against change rate and response time; include capacity/cost of recovery copies and a full-volume incident. Worked forecast and operational response. |
| Find the bottleneck and decide whether a storage change helps | Byte rate, request rate, latency distribution and outstanding work constrain different workloads | **FS-U32** Relate request size, IOPS, throughput, concurrency and tail latency; latency limits a serial sync workload even if bandwidth is spare. Worked numbers and queue model. **FS-U33** Separate application cache, kernel cache, filesystem work, device queues and remote/network work; show how metadata-heavy or mixed workloads change the limit. Path traces. **FS-U34** Diagnose with application timings, kernel/device counters, filesystem evidence and provider metrics; high utilisation or average latency alone cannot identify the cause. Correlated incident record. **FS-U35** Design a meaningful workload measurement: data size, warm/cold state, direct/buffered mode, sync policy, size distribution, queue depth, read/write mix, runtime, working set and interference. Native fio/profile worksheet, explicitly not a browser benchmark. **FS-U36** Measure the price of a required durability boundary and choose batching or workload separation without silently weakening that boundary. Matched sync profiles and percentile interpretation. |
| Capture a recoverable state and prove restoration | A snapshot records a layer's state; recovery must reconstruct a consistent application and may depend on external state | **FS-U37** Explain block and filesystem snapshots, shared-block retention, failure domains and independent copies; a snapshot on the failed pool cannot supply it. State/space model. **FS-U38** Coordinate application checkpoints/quiescence, filesystem freeze and multi-volume capture; crash consistency and application consistency differ, and freeze alone does not flush application buffers. Timeline including database, manifest and queued work. **FS-U39** Define backup scope, retention, independent access and restore objectives; include metadata, keys, manifests and application logs where required. Restore plan rather than a list of backup features. **FS-U40** Distinguish checksums, metadata checking, data scrubbing, redundancy-based repair and application validation; a repair tool cannot recreate bytes with no good copy. Corruption tree. **FS-U41** Copy or migrate files while preserving required metadata, sparse layout and generation boundaries; verify contents and final deltas before cutover. Native rehearsal. **FS-U42** Triage failure without destroying evidence, restore into isolation, verify the application and reconcile valid post-target work before cutover. Incident run with failed restore variation. |
| Operate a real Linux filesystem rather than only its abstract model | Implementation choices make allocation, log pressure, feature compatibility and repair observably different | **FS-U43** Read XFS geometry, allocation groups, extents and delayed allocation sufficiently to explain allocation behaviour and metadata work. Native tools plus mechanism model, stopping before B-tree implementation. **FS-U44** Follow XFS metadata transactions, delayed logging and replay; relate fsync and log pressure to the observed write path without claiming a user-data journal. Source-backed trace. **FS-U45** Use XFS reflink/shared extents and explain COW write cost, retained space and metadata-only integrity protection. Copy-then-overwrite worksheet. **FS-U46** Provision and grow XFS with selected feature flags, project quotas and compatibility checks; resize/shrink eligibility and moving to an older system depend on kernel, tools, geometry and distribution support. Native lifecycle worksheet. **FS-U47** Choose XFS health checks, supported scrub/repair and restore from evidence; a dirty log, unavailable device or damaged data requires different treatment. Disposable-image recovery practice, version gated. |
| Operate Linux volume mapping without confusing it with a filesystem | LVM owns allocation and snapshots beneath the filesystem; encrypted mappings add key dependencies | **FS-U48** Build and inspect PV/VG/LV mappings, resize in order and plan removal or migration with copies and headroom. Native worksheet with wrong-layer counterexample. **FS-U49** Operate LVM thin data/metadata capacity, snapshot retention and monitoring; recover a full-pool situation according to supported procedure. Native small-pool worksheet plus failure model. **FS-U50** Place dm-crypt/LUKS in the stack, preserve unlock/header/key recovery and account for cloning and discard policy. Native recovery checklist, bounded to storage operation. |
| Operate a hosted block volume and its recovery path | The guest OS sees a block device but the provider owns attachment, location, service limits, lifecycle and snapshot plumbing | **FS-U51** Choose EBS volume class and provisioned performance against instance limits, request size and actual workload; include storage and retained-copy cost without fixing price tables in durable prose. Contract and metric exercise. **FS-U52** Manage EBS identity, attachment, availability-zone scope, termination settings and replacement ownership; Multi-Attach does not make XFS cluster-safe. Account worksheet and failure timeline. **FS-U53** Capture EBS single/multi-volume snapshots with a defined consistency boundary, restore to new volumes and verify readiness/performance after initialisation. | Run a network filesystem with two real clients | A chosen client, server, export and security configuration determine the protocol's practical contract | **FS-U54** Configure a bounded Linux NFSv4.1 export/client pair, identity mapping and export/security policy; distinguish root squashing from authentication and transport protection. ## Depth boundaries before page decisions

The initial representative implementation is a Linux service stack with XFS, LVM2 and optional LUKS. EBS supplies one concrete hosted block environment. Linux NFSv4.1 supplies a real network-sharing branch. These are connected operational paths, not claims that one filesystem, one provider or one sharing protocol represents every mechanism.

Ext4 is an important alternative for journalling/layout/resize contrasts. OpenZFS is a credible contrast for integrated pools, data checksums, snapshots and repair from redundancy. SMB/Windows is a material interface contrast for sharing, locking and namespace assumptions. These alternatives require primary evidence before article claims; this derivation does not promise their own full operational branches. The absence of a Windows/SMB production route is a real audience limit, not a sentence that teaches Windows operation.

General RAID and device work stops when the operator can select an arrangement, understand degraded risk and locate evidence. NVMe submission queues, FTL algorithms, parity algorithms, firmware tuning, filesystem source implementation and forensic data recovery stay external. Cluster filesystem deployment, Ceph internals, multipath SAN administration and full Kubernetes CSI operations also stay external; local context must explain attachment/mount ownership and failure boundaries wherever these appear. Shared distributed-systems teaching stays parked.

Application log recovery, database-specific checkpoint protocols, object-storage APIs and identity-provider administration have their own homes elsewhere. This collection must still show why they change a file/volume recovery decision. It cannot delegate its crash-consistency lesson to a database collection or label a storage snapshot application-consistent without evidence.

## Fresh primary evidence used to challenge scope

Checked 18 October 2026. These are planning sources: they establish why a mechanism or boundary needs teaching. Article writing must recheck exact versions, commands, defaults and claims and preserve its own evidence. No benchmark or failure outcome was observed here.

- [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html), [open](https://man7.org/linux/man-pages/man2/open.2.html) and [rename](https://man7.org/linux/man-pages/man2/rename.2.html): file versus directory persistence, object lifetime and name replacement make separate abilities necessary. Linux documentation is not a universal platform guarantee.
- [Linux fcntl locks](https://man7.org/linux/man-pages/man2/fcntl_locking.2.html): lock ownership and lifetime need practical explanation, rather than a generic “use locking” recommendation.
- [Linux cache flush/FUA](https://docs.kernel.org/block/writeback_cache_control.html): the request path and device acknowledgement must be taught apart from runtime and page-cache buffering.
- [Ext4 journal](https://docs.kernel.org/filesystems/ext4/journal.html) and [XFS logging](https://docs.kernel.org/filesystems/xfs/index.html): filesystem structural recovery is a different job from application recovery; different implementations warrant explicit treatment.
- [XFS grow](https://man7.org/linux/man-pages/man8/xfs_growfs.8.html) and [repair](https://man7.org/linux/man-pages/man8/xfs_repair.8.html): online growth, dirty logs, destructive repair options and support levels affect the operational curriculum. Pin distribution/kernel/xfsprogs before worksheets.
- [LVM thin provisioning](https://man7.org/linux/man-pages/man7/lvmthin.7.html): physical pool data and metadata make capacity a layered problem; thin snapshots deserve more than a backup paragraph.
- [Linux NFS mount/consistency/security](https://man7.org/linux/man-pages/man5/nfs.5.html): cache coherence, client recovery and security choices are separate from local file semantics. Protocol support and defaults vary with client and server.
- [OpenZFS scrub](https://openzfs.github.io/openzfs-docs/man/master/8/zpool-scrub.8.html): detecting damage and repairing it with redundancy are different promises. The master manual is a planning pointer, not a pinned release claim.
- [fio documentation](https://fio.readthedocs.io/en/latest/fio_doc.html): access mode, sync policy and workload state belong in a reproducible storage measurement. Its version must be recorded for practice.
- [dm-crypt](https://docs.kernel.org/admin-guide/device-mapper/dm-crypt.html): encryption is a mapping-layer concern whose configuration changes operating and recovery dependencies; LUKS procedure needs cryptsetup evidence at authoring.
- [EBS I/O characteristics](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-io-characteristics.html), [Multi-Attach](https://docs.aws.amazon.com/en_en/ebs/latest/userguide/ebs-volumes-multi.html) and [snapshot creation](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-creating-snapshot.html): provider performance accounting, shared-block safety and snapshot consistency cannot be inferred from a guest's filesystem. Avoid hard-coded quotas or regional availability until verified for the worksheet.

A consequential check changed a common assumption: the current upstream XFS grow manual documents limited shrinking of the final allocation group. The plan must teach version-, geometry- and distribution-specific resize eligibility rather than repeat “XFS cannot shrink”. Upstream capability is not evidence that a selected distribution supports it.

Joins and the meaning of a result row
Deep dive
About 8 minutes
AI-generated

A join returns a row for each matching pair of input rows. That small rule explains both its usefulness and its most expensive mistakes. Adding a customer name to each order may leave the row count unchanged. Adding payments to order lines may multiply it. Both queries can be valid SQL, and both can return plausible amounts.

The first question is therefore what one result row should mean. A receipt wants one row per order line. A list of orders wants one per order. A list of customers who have ordered wants one per customer, however many orders they have. Keep that meaning in view while choosing the matches.

This article builds the shop’s still-due report: the value of each order, its recorded payments and the difference. It uses PostgreSQL 18 and the same three orders as the introduction. The figures illustrate result construction; the downloadable SQL checks the results on PostgreSQL 18.6.

One row for each match

Begin with orders and customers. Each order carries a customer_id, and the customer primary key makes that value unique on the other side.

SELECT o.order_id, c.name
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
ORDER BY o.order_id;
One result row per order
Order	Customer
101	Mina Shah
102	Tariq Aziz
103	Mina Shah

Order 101 finds Mina, order 102 finds Tariq, and order 103 finds Mina again. Mina appears twice because she has two orders. These are different order rows carrying the same customer fact, rather than duplicate customers in the source table.

The key tells us that each order finds at most one customer. The non-missing foreign key tells us that the customer exists, so in this schema every order finds exactly one. A join condition alone promises neither. Joining on a non-unique name could find several people, and joining to an optional relation could find none.

Now join orders to their lines instead. Order 101 has two matching lines, 102 has one and 103 has two. The result has five rows. One row now means one order line, identified by (order_id, line_no). The order’s date and customer ID repeat on each of its lines because they describe the order to which those lines belong.

This meaning is often called the result’s grain. Write it as “one row per …” before adding a sum or another join. It gives you a concrete check: if one row should mean an order, why does order 101 appear twice?

Two independent collections

Order 101 has two lines, worth 4.50 and 35.00, and two payments, 30.00 and 9.50. The line numbers identify what was bought. The payment IDs identify payments towards the order; no payment belongs to a particular line.

Joining these collections on order_id therefore matches every line with every payment for that order. Read the four pairs in the drawing, then choose Total each side first.

The matches as text

The detailed join has four rows: two lines times two payments. With three lines and four payments, it would have twelve. The match is a pair of facts about the same order, not evidence that one payment paid for that particular line.

SELECT i.order_id,
       SUM(i.quantity * i.unit_price) AS order_total,
       SUM(p.amount) AS paid
FROM order_items AS i
JOIN payments AS p ON p.order_id = i.order_id
GROUP BY i.order_id
ORDER BY i.order_id;

For 101 this reports 79.00 for the order and 79.00 paid. Subtracting gives zero, the correct balance for the wrong reason. Order 102 also looks correct because it has one line and one payment. Order 103 disappears because it has no payment. Testing only a single-line paid order would miss both defects.

GROUP BY does not undo the multiplication. It adds the values on the rows it receives, including every repeated contribution. Nor does SUM(DISTINCT amount) repair it. That removes repeated values, so two legitimate payments of the same amount would be counted once. The identities are different even when their amounts agree.

SELECT DISTINCT removes identical projected result rows. It is useful when that is the requested answer, but it cannot decide which line or payment each amount belongs to. Keep the right identities through the calculation instead of asking a duplicate-removal step to reconstruct them.

Total before combining

The report wants one row per order, so first make each collection have that grain. Total the lines by order_id, and separately total payments by order_id. Each derived result then has at most one row for any order. Combining them cannot multiply an order’s amounts.

WITH lets us name these intermediate query results. Such a name is a common table expression, or CTE. It is available to this statement, rather than being a stored report table.

WITH line_totals AS (
  SELECT order_id, SUM(quantity * unit_price) AS order_total
  FROM order_items
  GROUP BY order_id
), payment_totals AS (
  SELECT order_id, SUM(amount) AS paid
  FROM payments
  GROUP BY order_id
)
SELECT o.order_id, c.name, l.order_total,
       COALESCE(p.paid, 0::numeric) AS paid,
       l.order_total - COALESCE(p.paid, 0::numeric) AS due
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
LEFT JOIN line_totals AS l ON l.order_id = o.order_id
LEFT JOIN payment_totals AS p ON p.order_id = o.order_id
ORDER BY o.order_id;
The still-due report, using recorded line prices and payments
Order	Order total	Paid	Due
101	39.50	39.50	0.00
102	40.00	40.00	0.00
103	29.00	0.00	29.00

Order 101 now combines one line-total row with one payment-total row. Order 103 has a line total but no payment-total row. A LEFT JOIN retains its order row and supplies NULL for the missing payment columns. COALESCE turns that missing total into zero: no recorded payments contributed to it.

We do not apply the same substitution to a missing line total. This schema does not enforce that every order has a line. An order with no lines would remain in this report with a missing total and balance, signalling that its value has not been established. Treating it as a free order would be a different business rule. The three core orders all have lines.

The calculation uses the agreed unit_price on each line. Joining today’s product price into the sum would change old receipts when the catalogue changed. Likewise, the status text is not a substitute for summing payments. Here 101 and 102 are paid, but a status field does not prove that recorded amounts equal what is owed.

The CTEs make the reasoning readable. They do not require PostgreSQL to execute the clauses as a series of stored temporary tables. The planner may combine work while preserving the result. Keeping unmatched rows

An ordinary JOIN, also called an inner join, retains matches only. A left join additionally keeps each left-side row with no match, filling the right side with missing values. It does not add one missing row alongside existing matches. If an order has two matching payments, it still produces two result rows.

That preservation happens at the join. A later WHERE can discard the preserved row again. Suppose we want every order alongside its card payments, if any. Compare the position of the card condition in the next figure.

Both answers as text
SELECT o.order_id, p.payment_id, p.amount
FROM orders AS o
LEFT JOIN payments AS p
  ON p.order_id = o.order_id AND p.method = 'card'
ORDER BY o.order_id, p.payment_id;

In ON, the condition defines a match. Order 103 has no card payment, so the left join keeps it with missing payment columns. Move p.method = 'card' to WHERE, and it tests the joined rows instead. The condition on 103 is unknown, and WHERE retains only true, so 103 disappears.

Adding OR p.payment_id IS NULL in WHERE is not generally equivalent to putting the card restriction in ON. An order with only non-card payments already found matches at the join, so no missing placeholder row was created. The later filter would remove every one of those matches and lose the order. Make the join’s matching rule express the optional fact you want.

A condition on the preserved side can still belong in WHERE. For example, WHERE o.customer_id = 1 deliberately selects Mina’s orders while retaining missing payments on them. Decide whether each condition chooses the parent rows, defines an optional match or filters the final result.

A right join preserves the right input instead. A full join preserves unmatched rows from both sides, useful for comparing two independently supplied lists. Neither changes the pairing rule. Choosing a different outer join will not make two many-sided collections safe to sum together.

Whether a match exists

Sometimes we need no columns from the other side. “Which customers have ordered?” asks whether an order exists for each customer. Joining customers to orders would return Mina twice. EXISTS tests for at least one matching row without adding a result row for every match.

SELECT c.customer_id, c.name
FROM customers AS c
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.customer_id = c.customer_id
)
ORDER BY c.customer_id;

The answer is Mina and Tariq, one row each. The inner query refers to c.customer_id from the outer query; this makes it a correlated subquery. SELECT 1 is conventional because only the existence of a result matters. It does not count orders or choose a particular one.

Reverse the test with NOT EXISTS to find customers without orders: Edda. For orders without any payment, change the outer table and the matching condition:

SELECT o.order_id
FROM orders AS o
WHERE NOT EXISTS (
  SELECT 1
  FROM payments AS p
  WHERE p.order_id = o.order_id
)
ORDER BY o.order_id;

This returns 103. It asks a different question from “which orders still have an amount due?” A partly paid order has a payment, so it fails this absence test while still owing money. To find positive balances, name the completed report as another CTE and filter its due > 0. In the core snapshot both questions happen to select 103.

The matching condition is essential. Without p.order_id = o.order_id, the query asks whether the entire payments table is empty. Since payment 501 exists, every order would fail NOT EXISTS, including 103.

A left join followed by WHERE p.payment_id IS NULL can express the same absence test. Test a right-side column guaranteed non-missing in a real match, such as its primary key. A nullable note or reference could be missing on a real payment and would give a false absence.

NOT IN needs more care. If its right-hand result contains a NULL, an otherwise unmatched value can produce unknown rather than true. The shop’s payments.order_id is non-missing, but a later union or optional relation could change that guarantee. NOT EXISTS keeps “no matching row” explicit; Values, missing data and equality follows the three-valued comparisons.

Checking the question

Check a query with rows that separate its possible meanings: a parent with no children, one with one child and one with several children on both joined sides. The shop deliberately contains all three payment shapes. Compare identities as well as totals; a plausible balance can hide doubled contributions.

At each join, identify the key of each input and how many matches a row can find. Before each sum, say what one input row means and whether the same fact has already repeated. Before each absence test, say exactly which match must not exist. These checks continue to work as queries grow, because they follow the meaning of the rows rather than the length of the SQL.

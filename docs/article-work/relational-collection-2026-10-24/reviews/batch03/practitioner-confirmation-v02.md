### r04 practitioner-1 / r08 practitioner-1 · medium · downloadable runners and repeat instructions

Shared canonical issue: **the filtered child environment does not sanitise in-process Psycopg connections**. Each piece retains its own label for traceability.

Problem: `run-history.py:11,22` and `run-imports.py:11,71` create a PG-free dictionary for `subprocess.run`, then connect through Psycopg in the original Python process. The displayed command has no environment-clearing prerequisite. An inherited `PGOPTIONS` therefore still affects the new private connection. The current mechanical statement that the scripts strip all PG-prefixed settings is too broad: invalid PGHOST/PGPORT/PGUSER/PGDATABASE happen to be overridden by explicit conninfo.

Effect: a reader following the stated setup can fail before any teaching drill runs, and must diagnose an option unrelated to the newly owned server. This is a reproducibility/prerequisite defect. The successful recorded baseline remains real; it does not cover this environment case.

Suggestion: make the intended connection-environment contract apply to every actual connection, including worker connections, or explicitly require and verify an adequately clean invocation. Update the mechanical scope and test a non-conninfo option as well as endpoint defaults.

Evidence: exact scripts were run without editing with all ambient PG-prefixed variables removed, then the single deliberate input `PGOPTIONS=-c default_transaction_read_only=on`. This altered only their owned session settings, not any global configuration. PostgreSQL [libpq environment variables](https://www.postgresql.org/docs/18/libpq-envars.html) documents PGOPTIONS as a connection default; [Psycopg Connection.connect](https://www.psycopg.org/psycopg3/docs/api/connections.html#psycopg.Connection.connect) links the environment parameters affecting a connection.

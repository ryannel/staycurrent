Outboxes and database-backed jobs
 Deep diveAbout 12 minutes AI-generated 
An outbox records work to do in the same transaction as the change that requires it. When the shop creates order 103, it can also record “send this order’s confirmation”. Either both records commit or neither does. A worker performs the external work later, after the purchase request has finished.
That closes one failure gap: a committed order whose process stopped before recording its confirmation work. It leaves another. A worker can send the confirmation and stop before recording that it succeeded. Recovering the job may send it again. The database can make the intention atomic with the order; the receiver must help make a repeated effect safe.
We continue from Retries when a commit reply is missing and Locks, contention and deadlocks. Order 103 is Mina’s pending purchase of one mug and two packs of tea, worth 29.00. This article adds an outbox event, order-103-created, as an explicitly separate record of intended work. It does not add a payment or claim that an email has been delivered.

Commit the intention
Sending an email inside the purchase transaction does not extend that transaction into the email provider. If the provider accepts the email and the database later rolls back, the email can still leave. Sending after commit reverses the gap: the order can commit, then the process can stop before calling the provider.
Put the intention inside the database boundary instead. The purchase transaction reserves stock, records the order and its two lines, and inserts an outbox row. The worker sees only committed work.

The enclosing box is a database transaction. The receiver is outside it. No arrow promises delivery time or end-user receipt.
Give each event a stable identity and a defined payload. Here one event means “order 103 was created”, with a payload naming order 103. A real event may need immutable receipt facts or a schema version so that a delayed consumer can interpret it. Decide whether it carries facts as they were at the event or asks a worker to read current state; those are different contracts.
The request key purchase-mina-103 still identifies the logical purchase across request retries. The outbox event ID identifies one event produced by that purchase. Replaying a resolved purchase must return its outcome without creating another event. If one purchase emits several events, give each its own stable identity and meaning.
-- Inside the purchase transaction, after creating order 103:
INSERT INTO outbox (event_id, order_id, payload)
VALUES (
 'order-103-created', 103,
 '{"order_id":103}'::jsonb
);
-- Commit this with stock, order, lines and request outcome.
The event’s primary key prevents two copies of this identity. It cannot tell whether a programmer invented a second identity for the same intended effect. Nor does ON CONFLICT DO NOTHING justify ignoring a changed payload under an existing event ID. Preserve immutable events and reject a conflicting duplicate.
In a disposable PostgreSQL 18.6 experiment, committing the order before inserting its event left one order and no outbox row when the next write was omitted. Terminating a client while the combined transaction remained open left neither. Committing the combined transaction left both. This scratch fixture isolates that boundary; it does not re-enact the complete stock purchase.
Claim work briefly
A background worker polls for available work. Several workers may poll together, so a plain select followed by an unguarded update lets both choose the same event. Claim the row under a database lock and commit the claim before making a network call.
The example’s outbox table has event_id as its primary key, a required order_id reference and required payload. Scheduling and ownership add five columns:
 Fields used by this worker protocol
FieldMeaning
available_atEarliest database time to attempt this work
lease_untilDeadline of the current claim; missing means unclaimed
claim_tokenIncreasing generation for claims of this event, initially 0
attemptsNumber of successful claims, initially 0
completed_atWhen this event’s delivery contract was confirmed; missing means unfinished 
The deadlines and completion time use timestamptz. Claim token and attempts are required integers; the download uses bigint for the token. A lease gives a claim a deadline, after which unfinished work becomes eligible for recovery. It survives the short transaction which acquired it, allowing the row lock to be released while the worker calls the receiver. Expiry makes recovery possible; it cannot stop a paused process from resuming.
BEGIN ISOLATION LEVEL READ COMMITTED;
WITH candidate AS (
 SELECT event_id FROM outbox
 WHERE completed_at IS NULL
 AND available_at <= clock_timestamp()
 AND (lease_until IS NULL
 OR lease_until <= clock_timestamp())
 ORDER BY available_at, event_id
 FOR UPDATE SKIP LOCKED
 LIMIT 1
)
UPDATE outbox AS o
SET lease_until = clock_timestamp() + interval '5 minutes',
 claim_token = o.claim_token + 1,
 attempts = o.attempts + 1
FROM candidate AS c
WHERE o.event_id = c.event_id
RETURNING o.event_id, o.payload, o.claim_token;
COMMIT;
The candidate query locks the row it selects; the update gives that claim a deadline and a generation. The returned token is provisional until the worker receives a successful commit reply. If that reply is missing, this protocol abandons the claim: discard its token and never use it to call the receiver, renew the lease or record completion. Dispose of the broken connection and finish its cleanup. Resume polling through the normal claim query, accepting a claim only when its commit succeeds. If the uncertain claim did commit, its lease keeps the event unavailable until expiry; this deliberately trades some recovery time for a simpler ownership contract.
A matching token in a later lookup cannot recover that ownership. A can receive token 1 before commit, then disconnect and have its update rolled back. B can then commit a claim with token 1. Locking the row now reveals B’s current lease, even though its number matches A’s discarded token. The increment orders committed claims of this event; it does not identify every attempted claim.
SKIP LOCKED lets another worker omit a row already being claimed and seek other work. With only this event, an empty claim can mean it is locked, leased, scheduled for later or already complete. It does not prove the queue is empty. This incomplete view suits independent jobs; it was unsuitable for the class capacity decision.
Five minutes is an illustrative lease, not an execution measurement. Choose the duration against expected work and recovery needs. Use the database’s clock consistently for granting, checking and renewing it. PostgreSQL’s now() stays at transaction start; clock_timestamp() reads current wall time, which is why this protocol uses it explicitly. Keep claim transactions short rather than using a long transaction as a clock.
If a job needs more time, renew only a claim whose commit was acknowledged. For renewal, completion and release, first lock the event row in a short Read Committed transaction, then test the token and deadline in a separate update. An ordinary update can test its time condition before waiting for a row lock; a lock holder that changes no data need not make it test again. Taking the lock first puts that wait before the expiry check.
The subsequent update authorises the change when its condition finds the current generation unexpired. Keep the lock until commit so another worker cannot replace that generation between the test and the change. Commit and its reply may arrive after the deadline: this is a check under a lock, not a promise to finish before a wall-clock instant. Wait for renewal’s successful commit reply before continuing; if it changes no row or its outcome becomes uncertain, abandon the claim and stop starting work under it. Neither a renewal reply nor local abandonment can recall a network request already sent.
Finish only your claim
The worker calls the receiver after its claim’s commit was acknowledged. On a confirmed receiver success, it records completion with the event ID and that claim’s token:
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT event_id FROM outbox
WHERE event_id = $1
FOR UPDATE;
-- A separate statement, after acquiring the row lock:
UPDATE outbox
SET completed_at = clock_timestamp(),
 lease_until = NULL
WHERE event_id = $1
 AND claim_token = $2
 AND lease_until > clock_timestamp()
 AND completed_at IS NULL
RETURNING event_id;
COMMIT;
A row returned by the update and a successful commit reply confirm completion. No updated row means the claim was expired at the post-lock check, was replaced or was already completed. Do not turn it into an unconditional update. The token prevents an old worker from marking a later worker’s claim complete. If completion’s reply is missing, retire the claim as well: do no further work under it. A committed completion removes the event from polling; otherwise the unfinished event becomes claimable after expiry and release of any transaction lock.
A worker that dies before calling the receiver leaves the event unfinished. Once its lease expires, another worker can claim it. A worker that dies after the receiver acts leaves the same unfinished event. Those two failures look alike to the outbox, just as the two commit histories looked alike to the purchase caller.

A chosen failure schedule. Claim tokens 1 and 2 are generations of one event; the external effect identity stays the same.
The native experiment held an uncommitted claim while another worker polled: the second skipped the locked row. After the claim committed, its active lease excluded the event. The test then explicitly moved the deadline into the past to model expiry. B obtained token 2; A’s completion with token 1 changed zero rows, while B’s completion changed one. For renewal, completion and release, a further test held an unchanged row lock across a short deadline. A direct guarded update began before expiry, waited and still changed the row afterwards. With the separate locking statement, the later update changed zero rows. When a competing worker instead committed a newer generation, the old token also changed zero rows. These are controlled schedules, not measurements of the five-minute lease.
The experiment also reproduced A’s rolled-back token 1 matching B’s committed token 1. The worker discarded A’s uncertain claim in that history and in a second history where A’s commit succeeded but its reply was withheld; neither authorised a receiver call, renewal or completion. Normal polling recovered the unfinished event.
Make the receiver recognise a repeat
Use a stable effect identity at the receiver. For this one confirmation, the example uses order-103-created:confirmation. It identifies the same intended effect whether A or B sends it. A new claim token must not become a new effect identity, or every recovery would ask for a different effect.
The receiver needs a real contract: record that identity with the effect atomically, compare the meaningful payload, and return the recorded result on a replay. The sender must know how long that record is retained and how to query an uncertain result. If a provider forgets an identity before the outbox can replay it, repetition may act again.
A provider’s “accepted” reply also needs interpretation. Acceptance into its queue is not the same as an email reaching Mina. Choose what completed_at means: perhaps the provider has durably accepted responsibility, while delivery reports are a separate workflow. An HTTP success code alone does not define that contract.
The native test uses a receiver stand-in in a second database on the same local PostgreSQL server. Two deliveries with one stable effect ID left one keyed effect. A deliberately unprotected receiver log accumulated two effects from the same two attempts. This checks the duplicate boundary under controlled application logic; it does not establish any email or payment provider’s behaviour, or independent machine failure.
A consumer with its own database
A consumer that changes its own database can implement that contract with an inbox. Its key is the pair (consumer, event_id), so two different consumers may each process the event once. Store the normalised payload alongside that key. Inside the consumer’s Read Committed transaction, insert the receipt; if newly inserted, apply the local effect; commit both. On a duplicate, read the stored payload in a separate subsequent statement and compare it: a matching replay can skip the effect, while changed input under the same identity must be rejected. The separate statement sees a receipt that an overlapping insertion may have waited for, just as the purchase request protocol did.
BEGIN ISOLATION LEVEL READ COMMITTED;
INSERT INTO inbox (consumer, event_id, payload)
VALUES ('confirmation-projection', 'order-103-created', $1)
ON CONFLICT DO NOTHING
RETURNING event_id;
-- Only if the receipt was newly inserted:
-- apply this consumer's local database change here.
-- Otherwise: read the stored payload in a new statement,
-- compare it and reject a conflicting replay.
COMMIT;
Committing the receipt first creates a lost-work gap: a crash before the effect leaves a receipt that makes the replay skip unfinished work. Applying the effect first creates a duplicate gap: a crash before the receipt allows the effect again. The receipt and effect must be within one authority’s transaction.
The experiment checks those boundaries with a scratch counter. Rolling back the combined receipt and increment left neither. Committing both, then replaying the receipt, left one increment. A deliberately separate receipt commit left one receipt and zero increments when its effect was omitted. Calling an external provider inside the consumer transaction would reopen the same boundary; another outbox may be needed.
What fencing adds
A token can do more than guard the outbox’s completion update, but only if the authority performing the effect checks it. A fence rejects work from an older owner. For a protected resource, the receiver remembers the highest generation it has accepted and refuses lower ones. After seeing generation 2, it rejects A’s delayed generation 1.
This needs a generation ordered across every contender for that resource, enforced atomically at the resource. Our per-event claim_token orders claims of one event. It is not automatically a resource-wide fence for several different events updating one account or file. Each event could independently have token 1. Choose the token authority and scope to match the resource being protected.
Fencing also does not deduplicate the logical effect. Generation 1 can legitimately act before generation 2, so both may be accepted in order. A stable effect identity prevents repeating one intention; an ordered token rejects an obsolete owner. A receiver may need both. If an email provider accepts neither a stable identity nor a fence, the database cannot manufacture those guarantees around it.
For an external operation with an uncertain result and no reliable replay contract, keep it unresolved and reconcile with the receiver’s records or a human workflow. Marking it complete before sending risks loss; retrying forever risks duplicates. The application must choose and expose that trade rather than calling the outbox “exactly once”.
Keep the work recoverable
Retry temporary failures with bounded backoff and jitter, carrying the same event and effect identities. To set available_at for a later attempt and release the lease, use the same lock-first transaction as completion: lock the event, then update only if the acknowledged token still matches and the lease is unexpired at that post-lock check. Commit before discarding the claim. If no row changes or the outcome becomes uncertain, abandon it; normal polling follows the state that actually committed. Retain the attempt count and useful error information. Stop retrying a permanently invalid payload as though elapsed time will repair it.
A failed-work state or dead-letter queue gives operators somewhere to inspect work that cannot proceed. It must preserve the payload, identity and failure reason. Moving a row there is not successful delivery. Alert on the age of the oldest eligible unfinished work, repeated failures and expired leases; a low queue length can hide one important stranded event.
The claim query needs an access path suited to unfinished eligible work. As completed rows accumulate, consider a partial index over the unfinished set and an explicit retention policy. Many workers polling the same small head can compete for database resources even with skipped row locks. Bound batch size and worker admissions against actual receiver and database capacity.
Claims do not establish business ordering. ORDER BY available_at, event_id chooses eligible rows for this query, but skipped locks, leases and retries let later work finish first. If one order’s events must be applied in sequence, give that order a sequence contract and enforce it at the consumer, or serialise its processing. Do not infer commit order from opaque event IDs or a timestamp alone.
Keep unfinished events and receiver deduplication records for compatible replay windows. Archive completed history deliberately, and preserve a way to distinguish an old replay from new work. A restore may bring back an outbox event whose external effect survived; reconciliation needs the stable effect identity at that external authority. A restored queue flag is not evidence that the provider never acted.
Repeat the boundaries
Download the outbox experiment and run python3 run-outbox.py --bindir /path/to/postgresql/bin. The standard-library script starts an owned disposable PostgreSQL cluster with a private socket, checks its identity and removes it afterwards. The second database is explicitly a local receiver stand-in.
The recorded PostgreSQL 18.6 run checks the separate-write gap, combined commit and rollback, locked-row skipping, active leases, abandoned uncertain claims, expiry across unchanged row-lock waits, injected expiry, newer claims, stale completion, duplicate effects, receiver fencing and atomic consumer receipts. It terminates an owned client before commit and withholds selected successful replies from a simulated worker. These are controlled fault injections, alongside deliberately held row locks, short deadlines, modelled worker pauses and omitted follow-up writes. They do not measure a network failure, lease duration, production throughput, broker delivery or a provider’s service contract.

Relational databases
 IntroductionAbout 15 minutes AI-generated 
A relational database keeps data in tables and lets you ask questions that combine them. The data outlives the application request that stored it. A shop can store its customers, products, orders and payments separately, then ask which customer placed an order, what the order contains and how much remains to be paid. The relationships are values in the rows: an order carries the ID of its customer, and an order line carries the ID of its product.
The database also controls changes to that shared data. A purchase might need to reduce stock, create an order and record its lines. Those changes belong together. If the application stops halfway through, the database can discard the unfinished work. If two buyers want the last mug, it can make them take turns at the stock row, provided the application asks for the right protection.
Those two jobs, answering questions across related facts and keeping related changes correct, explain much of the appeal. They also explain what you have to learn. You choose what each table means, state the rules the database should enforce, and write queries and transactions that preserve that meaning.
Every example here follows a small shop selling tea and tea things. Mina Shah and Tariq Aziz have placed orders; Edda Berg is a customer who has not. The SQL examples use PostgreSQL. The tables and drawings are small enough to follow by eye, and the interactive steps illustrate their meaning rather than a measured run.

Tables and keys
A table is a named collection of rows. Each row records one instance of the same kind of thing, with a value in each named column. In customers, one row is one customer, and its columns are customer_id and name. In orders, one row is one order. Each column has a type: an integer for a customer ID, text for a name, a timestamp for when an order was placed.
The arrangement looks like a spreadsheet, but the row number on the screen has no lasting meaning. Sorting the display does not change which customer a row represents. The shop gives each customer an ID and declares it to be the table’s primary key: the column, or combination of columns, whose value identifies one row. The database refuses a missing primary key or a second row with the same key.
Mina’s customer ID is 1. Her two orders carry that same value in their customer_id column. Follow it across the next drawing, then choose Tariq and Edda.

Three customers and three orders. Matching ID values connect the rows; their positions on the page do not. Choose Edda to see that a customer can exist without an order.
Orders 101 and 103 both point to customer 1. That makes this a one-to-many relationship: one customer can have many orders, while each of these orders has one customer. Edda’s row also matters. A customer can have zero orders, so the absence of an order is not a reason to lose the customer.
The customer_id on an order is a foreign key when it is declared to refer to the customers table. It requires the referenced customer to exist. An order for customer 99 would be refused while there is no customer 99. Repeating the value 1 across Mina’s orders is allowed: uniqueness belongs to customers.customer_id, where 1 identifies Mina, and to orders.order_id, where 101 and 103 identify different orders.
These keys do different work. The primary key answers “which row is this?” The foreign key answers “which row over there does it belong to?” A name would do those jobs poorly. Two customers can have the same name, and a customer can change theirs. With the ID, changing Mina’s name changes one customer row; her orders continue to refer to her.
The table definitions, types and rules together form the database’s schema. Here is enough SQL to define the first table:
CREATE TABLE customers (
 customer_id integer PRIMARY KEY,
 name text NOT NULL
);
CREATE TABLE names the table. Inside the parentheses, each line names a column and its type, followed by any rules. NOT NULL requires a value for the name. Without it, SQL can represent a missing name with NULL, a marker for absence rather than the text “NULL” or an empty string. Missing values need care in comparisons and totals; Values, missing data and equality develops those rules.
The word relational comes from relation, the mathematical idea behind a table. It does not mean every table must have a foreign key. The useful consequence is that data has a regular form you can combine and transform: rows and named columns go into a query, and rows and named columns come out.
What an order contains
An order can contain several products, and a product can appear in many orders. Putting a single product_id on the order would allow only one product. Adding product_1, product_2 and product_3 would make three an arbitrary limit, and every question about products would have to inspect three columns.
The shop uses another table, order_items. Each row is an order line: one product, its quantity and its unit price on one order. Mina’s order 103 has two lines:

The first line says that order 103 includes one P7 at 20.00. The second says it includes two P3s at 4.50 each. The products table tells us that P7 is a blue mug and P3 is green tea, 50 g.
Neither order_id nor line_no identifies a line by itself. Order 103 appears twice, and line 1 can occur on every order. The pair (order_id, line_no) is the primary key. This is a composite key, one made from more than one column. The two foreign keys have simpler jobs: order_id refers to an order and product_id refers to a product.
This table expresses the many-to-many relationship between orders and products. One order reaches many products through its lines; one product reaches many orders through the same table. Quantity belongs on the line because it describes that particular purchase, rather than the product in general.
The two prices deserve the same thought. products.price is the current catalogue price. order_items.unit_price is what the customer agreed to pay on that line. Both happen to be 20.00 for the mug here. If its catalogue price changes later, the old line should still say 20.00. These columns record different facts about different moments.
Separating facts this way is part of data modelling: deciding what one row means, which values identify it and which facts belong with it. Normalisation is the discipline of using those dependencies to avoid storing the same fact in several places where the copies can disagree. Relations, keys and normalisation works through those choices, including when a deliberate copy is useful.
Asking a question
A query asks the database for an answer from its data. Most relational databases use SQL, short for Structured Query Language. You describe the answer you want: which tables supply it, which rows qualify and which columns to return. The database chooses how to find those rows.
With PostgreSQL, an application opens a connection to the database server and sends SQL through a client library, often called a driver. The server does the work and returns result rows or an error. Several application processes can have connections open at once, all working with the same stored tables.
Start with a question confined to one table: which of Mina’s orders are still pending?
SELECT order_id, status
FROM orders
WHERE customer_id = 1 AND status = 'pending'
ORDER BY order_id;
FROM identifies the input table. WHERE keeps rows for customer 1 whose status is pending. SELECT names the columns returned, so the answer is one row: 103, pending. ORDER BY requests a display order. Tables have no guaranteed row order, and a query without ORDER BY can return the same answer in a different sequence.

Here is that question in SQL:
SELECT p.name, i.quantity, i.unit_price,
 i.quantity * i.unit_price AS line_total
FROM order_items AS i
JOIN products AS p ON p.product_id = i.product_id
WHERE i.order_id = 103
ORDER BY i.line_no;
AS i gives order_items a short name for this query, and AS p does the same for products. So i.quantity means the quantity on the order line, while p.name means the product’s name. JOIN … ON supplies the matching condition. In the first line, AS line_total names a calculated result column rather than a table.
This query reads the inputs and produces a result; it does not store the receipt as a new table or change the existing rows. The drawing filters first to make the matching easy to follow. An actual database can use a different route to produce the same answer, perhaps looking up the relevant lines through an index. Understanding the result and understanding the work it takes are separate questions. Query execution and bad plans follows the latter.
From lines to totals
A receipt has two lines, but a list of orders usually wants one total per order. Aggregation combines several input rows into one result. SUM adds values; COUNT counts rows. GROUP BY says which rows should be combined.
SELECT order_id,
 SUM(quantity * unit_price) AS order_total
FROM order_items
GROUP BY order_id
ORDER BY order_id;
For order 103, the group contains its two lines. Their contributions are 1 × 20.00 and 2 × 4.50, which add to 29.00. The same calculation gives 39.50 for order 101 and 40.00 for order 102.
The meaning of a result row has changed: it now represents an order, where the receipt query returned an order line. Keep asking what one row means, especially when adding another join. A join can multiply rows before a sum sees them.
Payments show why. Order 101 has two lines and two payments, 30.00 and 9.50. Joining its lines directly to its payments on order_id would make four pairs: each line with each payment. A sum over those pairs would count every line twice and every payment twice. To find what is still due, first total the lines per order and the payments per order, then combine those totals. An order with no payments must stay in the answer, with paid amount treated as zero.

Rules at the table
Storing a row means more than finding room for its values. The shop wants to refuse duplicate customer IDs, order lines for nonexistent products and quantities of zero. A constraint is a rule declared in the schema that the database checks when data changes.
We have already used primary keys, foreign keys and NOT NULL. A CHECK constraint adds a condition on the row, such as quantity > 0 or stock >= 0. A UNIQUE constraint can forbid repeated values without making the column the table’s primary key; missing values have separate rules.
Putting a rule in the database gives every writer the same boundary. The checkout application, an import job and an administrator’s SQL session can all write orders. A check in the checkout form alone cannot protect the other two paths. With a foreign key, all three must name a customer that exists.
The application still checks inputs so it can give a useful explanation before sending a write. The database check covers the data that actually arrives, including writes that overlap. A friendly validation message and an enforced rule solve different parts of the problem.
The schema cannot infer all of the shop’s meaning. A positive payment amount does not prove that a card provider charged the customer. A foreign key from payments to orders does not prove that the payments add to the order total. And a non-negative stock value does not, by itself, prove the shop sold only the stock it had. That last gap is small enough to draw, after we have a way to group changes.
Constraints and tenant boundaries explains which rules can be enforced directly and how to express them. The first design question is which states must be impossible, then which combination of constraints and transaction logic makes them impossible.
A purchase as one change
So far we have read a shop with order 103 already present. Now rewind to just before Mina places it. There is one blue mug left and twelve packs of tea. She wants the mug and two packs. Recording the purchase needs changes to three tables: reduce stock in products, add a row to orders, and add two rows to order_items.
Suppose the application reduces the stock, then its process stops before it records the order. The stock has disappeared without any order explaining where it went. Reversing the order of the writes only changes the failure: the shop could have an order whose stock was never taken.
A transaction groups the changes into one unit. In PostgreSQL, BEGIN starts an explicit transaction, COMMIT finishes it successfully, and ROLLBACK discards its changes. The application can read its own unfinished work, but another connection cannot read those uncommitted changes.

The changes and both endings, as text
Before BEGIN: one blue mug and twelve packs of tea are available. Order 103 has not been stored.
BEGIN starts the transaction. The application has not changed any rows yet.
The transaction reduces mug stock to 0 and tea stock to 10. These changes are still private. Another connection’s ordinary read still sees the committed stock.
It adds pending order 103 and two order lines. The transaction now has the complete purchase, still uncommitted.
COMMIT makes the stock changes, order and lines visible together. No observer reads a committed state with only half of this transaction.
If the transaction stops before committing, rollback discards its changes: stock remains 1 and 12, and order 103 and its lines are absent.
With a commit, the order, its lines and the reduced stock become visible together. With a rollback, none of them takes effect. This property is atomicity: the grouped change is all or nothing. If a connection ends with the transaction still open, PostgreSQL aborts that unfinished transaction.
Order 103’s status is still pending. Recording the purchase and taking its stock do not mean payment has arrived. A later transaction can record a payment and make the appropriate change to the order’s status. The business chooses these boundaries; the database carries them out.
Acknowledging a commit also carries a promise about crashes. With PostgreSQL’s normal durability settings and storage that honours flush requests, a successful commit survives a database crash. PostgreSQL records changes in a write-ahead log on durable storage; after a crash it can replay that log to recover changes whose table pages were still in memory. Write-ahead logs and crash recovery follows the writes and the settings that change this promise.
That promise has a boundary. A database transaction does not reach into a card provider and roll its charge back, or pull back an email that has been sent. Work across those boundaries needs its own protocol. Outboxes and database-backed jobs shows how to commit a record of work alongside the change that requires it.
Nor does a dropped connection tell the application whether a commit succeeded. The server may have committed just before the reply was lost. Sending the purchase again could create a duplicate unless the application can recognise the same request. Retries when a commit reply is missing develops that case. It is a different uncertainty from a transaction known to have rolled back.
Two buyers, one mug
Atomicity prevents a half-written purchase, but two complete purchases can still disagree. Mina and Tariq each try to buy the last blue mug. Their applications both read stock 1 and both decide a sale is possible. Each calculates a new stock value of 0.
Mina writes 0 and commits order 103. Tariq then writes his saved value, also 0, and commits order 104. Both transactions are complete, and stock is non-negative, but the shop has sold two mugs from one. Tariq’s write failed to account for the sale that happened since his read.
The database needs to keep the decision and the change together. One way for this particular rule is a conditional update:
UPDATE products
SET stock = stock - 1
WHERE product_id = 'P7' AND stock > 0
RETURNING stock;
SET calculates the new stock from the row being updated. WHERE requires that row to have stock available. RETURNING gives the application the updated value if a row changed. No returned row means no mug was taken, and the application must stop that purchase and roll its transaction back. The update and the order writes belong to the same transaction.
In PostgreSQL’s default isolation level, Read Committed, two updates of this same product row cannot pass each other. The second waits for the first transaction. If the first commits, the second rechecks its condition against the updated row. Stock 0 no longer satisfies stock > 0, so Tariq’s update changes no row.

Tariq: His UPDATE checks stock > 0 again, against the updated row. Stock is 0. No row matches; the UPDATE returns no row.
Tariq: The application rolls back his transaction. Order 104 does not commit. Only Mina bought the last mug.
The row lock makes Tariq wait, and the condition decides what he may do afterwards. Waiting alone would not rescue the first version: writing a saved 0 after waiting still writes 0. Nor would putting the separate read and write inside BEGIN and COMMIT; the unsafe drawing already does that.
Isolation describes what one transaction can see and do while others run. A stronger level, Serializable, promises that successful transactions have an effect consistent with some order of running them one at a time. The database may reject a transaction to preserve that promise, so the application has to retry it. Other rules need different protection: the last mug lives in one row, while a limit spread across several rows can be harder.
This is the division of work to remember. Constraints reject forbidden data states. Atomicity groups the changes that belong together. Isolation, locks and correctly written updates govern how transactions interact. They help you implement a business rule; they need a business rule and a transaction design to implement. Where relational databases fit
The shop has several good reasons to use a relational database. Its facts have identities and relationships. It needs questions that cross those relationships, including questions it did not anticipate when the data was first stored. And several writers must preserve rules about the same orders, payments and stock.
These needs recur in booking systems, billing, accounts, project management and many other applications. A relational database is a useful first choice when the hard part is keeping shared facts consistent while finding several useful views of them. The tables do not have to resemble the screens: the shop’s receipt is assembled from several tables, while each table keeps a particular fact in one place.
The cost starts with making those meanings explicit. Schema changes need planning as applications and data grow. Queries can ask for more work than you intended, and transactions can hold locks long enough to delay other users. Storing the data is also an ongoing responsibility: someone must manage access, capacity and a way to recover from mistakes or lost storage.
Relational describes the data model, rather than a deployment size. SQLite puts a relational engine inside an application and can keep its database in one local file. PostgreSQL and MySQL commonly run as servers that applications connect to; the server manages the shared files and coordinates their work. Distributed SQL systems extend the design across machines, adding questions about where data lives, what a commit waits for and what happens when machines cannot communicate. Having SQL in common does not make those operational choices interchangeable.
A different store can be a better centre for a different job. Large images and video often suit an object store’s handling of whole files. Reports that repeatedly scan a few columns across billions of records can benefit from a column store’s layout. Search systems provide ways to retrieve and rank text. An application can use a relational database for its orders while placing those other workloads elsewhere. Choose from the access patterns and correctness requirements, rather than from the shape of a single sample record.

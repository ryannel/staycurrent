Pagination and consistent exports
 Deep diveAbout 9 minutes AI-generated 
A large result usually arrives in pieces. An order list asks for the next page when someone scrolls. An export reads batches until it has written every matching row. Both need an order in which to continue, but they need not make the same promise about changes during the read.
A live list can follow rows after a saved position in the current data. An export may need every value from one consistent view, even while writers continue. A cursor that remembers a position solves the first problem. A snapshot that fixes which versions are visible solves the second.
The examples use PostgreSQL 18 and the shop’s order headers. Extend the three core orders with later orders 105 for Mina and 106 for Edda, both placed at 2026-10-21 12:00:00Z. Both later headers begin with status pending. No lines, payments or stock effects are assigned to those two orders here. The changing-list histories below are separate illustrations and do not amend the core still-due report.

A position in a result
LIMIT caps how many rows a query returns. OFFSET skips that many result rows first. For a page size of two, the first request uses offset zero and the second offset two.
SELECT order_id, placed_at
FROM orders
WHERE status <> 'cancelled'
ORDER BY placed_at, order_id
LIMIT 2 OFFSET 2;
With the five unchanged orders, page one is 101 and 102; page two is 103 and 105. The final order_id breaks the time tie between 105 and 106. Without it, the database can put either noon order first, even without a concurrent change. A total order gives every row a distinct position in this result.
The offset counts positions in the result of this particular query. It has no memory of the previous response. In the next figure, page one has already returned 101 and 102. Cancel 101 between requests, then compare OFFSET 2 with After the saved key.

With no change, both methods return 103 and 105. After 101 is cancelled, OFFSET 2 returns 105 and 106, skipping 103; the saved key returns 103 and 105. If 103’s time moves to 13 October 12:00 UTC, the list becomes 101, 103, 102, 105, 106. OFFSET 2 repeats 102 and returns 105. The saved key returns 105 and 106, but misses the moved 103. These are independent illustrative histories, with cancelled orders excluded from the list.
After 101 leaves the eligible list, its first two rows are 102 and 103. Skipping two now skips 103 before it has ever been delivered. In a different history, moving 103 before 102 shifts 102 into the second page, so the client receives 102 twice and misses 103. The SQL is correctly applying an offset to a changed result.
Offset pagination can still be a sensible contract for a small, stable result or a screen that accepts movement between numbered pages. It also allows a direct request for page 40 without having visited page 39. Say what stability the application offers; an ordered query alone does not preserve the rows between requests.
Continue after a key
Keyset pagination saves the last row’s ordering values and asks for rows after them. It is also called seek pagination. The cursor is the saved boundary, rather than the number of rows that used to precede it.
Use the pair (placed_at, order_id), the same pair as the ORDER BY. Suppose a larger first page ends at order 105. Its boundary is noon on 21 October and ID 105. This request continues after it:
SELECT order_id, placed_at
FROM orders
WHERE status <> 'cancelled'
 AND (placed_at, order_id) >
 (timestamptz '2026-10-21 12:00:00Z', 105)
ORDER BY placed_at, order_id
LIMIT 2;
The answer is 106. PostgreSQL compares the pair from left to right. A later time qualifies; at the same time, a larger order ID qualifies. In expanded form, the condition is placed_at > saved_time OR (placed_at = saved_time AND order_id > saved_id).
Saving only the timestamp would lose 106: its time is equal, not greater. Changing the test to >= would instead repeat 105 and could keep returning the same first row of a large tie. The unique pair makes strict continuation possible.
Build the cursor from the last row actually returned. On the first request, omit the boundary condition. To indicate that another page exists, an application can request one extra row, return only the page’s requested size and use the last returned row for its cursor. Saving the look-ahead row would skip that row on the next request.
For ORDER BY placed_at DESC, order_id DESC, continuing towards older rows uses < on the pair. Mixed directions need the equivalent explicit branches, with each comparison following its own direction. For a previous page, reverse the comparisons and fetch direction, then reverse the fetched rows for display. Test ties at both boundaries.
The simple pair assumes non-missing keys, as the shop schema supplies. With a nullable sort field, NULLS LAST places missing values but does not make a tuple comparison with NULL true. Define separate continuation branches for the missing-value region, or choose a non-missing order. Text ordering must use the same collation on every request.
What the cursor carries
An API cursor usually packages the boundary into an opaque token. Its contents need to preserve the exact values and the query they belong to: ordering, direction, filters and any shop scope. A timestamp rounded from database microseconds to a coarser application format may move the boundary. Serialise enough precision to compare the same instant again.
Pass decoded values as query parameters, just as for other application inputs. Validate the cursor’s format and version, cap the page size, and reject a cursor supplied for a different filter or order. A signature can detect altered tokens. It does not grant permission to read another shop: apply authorisation and shop restrictions to every query independently.
The token need not point to a row that still exists. Its saved values still define a boundary after that row is cancelled or deleted. This is why cancelling 101 in Figure 1 does not disturb continuation after 102.
A numeric ID alone is a valid boundary only for a list ordered by that ID. An increasing sequence is not proof of commit order: one transaction can allocate a lower number and commit after another. Likewise, a placed_at supplied by an application need not reflect when the database made the row visible.
The work behind a page
An offset also costs work. The server still has to produce the skipped rows. With OFFSET 10000 LIMIT 2, even an index supplying the right order must pass over 10,000 rows before returning the next two. A matching keyset condition can begin at the boundary instead.
On a separate scratch table of 20,000 numbered rows, the experiment’s PostgreSQL index-only scan produced 10,002 rows for that offset query. The equivalent WHERE n > 10000 LIMIT 2 scan produced two. Those are observed row counts on a deliberately simple indexed fixture, not timings or a guarantee that every keyset query reads exactly one page.
The shop list can use an index on (placed_at, order_id). A list restricted to one customer may instead benefit from (customer_id, placed_at, order_id), putting the fixed equality first. Other filters can force the scan to inspect and reject many entries before it finds a full page. Joins, sorting, row visibility and the cost of returned columns still matter. Indexes and access paths develops that match, and Query execution and bad plans checks the work with EXPLAIN.
Keysets trade arbitrary page numbers for efficient continuation. Finding page 40’s boundary still requires a previous boundary, an additional index of saved boundaries or another way to locate it. An exact total count is a separate query over the matching set; the next-page token does not provide it for free.
A boundary is not a snapshot
Return to 103 moves before 102 in Figure 1. Keyset continuation does not repeat 102, but it also cannot find 103 once that row has moved behind the saved boundary. A delivered row moved forwards can appear again. If membership changes, an as-yet unread order can cease to qualify altogether.
Immutable ordering values remove movement of the key, but not all changes to the set. A newly committed row can carry a key behind the boundary. A row can change status before the reader reaches it. Values on already-delivered rows can be changed after they were read. Each request can be internally consistent while the concatenated responses describe no single database view.
For a live browsing list, that may be exactly the intended contract: continue through what currently qualifies, with refresh available to see earlier changes. Deduplicating IDs in the client can suppress repeats but cannot recover omissions. Do not describe this as an exact export of the starting set.
A saved upper time or maximum ID limits how far a traversal goes; it does not freeze it. Late commits can appear below that upper bound, existing rows can change and deletions can remove them. An upper bound works as a complete export boundary only with additional guarantees about how the data is admitted and retained.
One view for an export
An export that promises one consistent view needs to keep that view across batches. PostgreSQL’s ordinary Read Committed queries take a new statement snapshot each time. A read-only Repeatable Read transaction keeps the snapshot established by its first query for later reads.

First, the reader gets 101 and 102. A separate writer then cancels 103 and commits. A new statement snapshot sees only 101, 102, 105 and 106; continuing after 102 returns 105 and 106. With one fixed snapshot established before that commit, the reader still sees all five original rows; continuing after 102 returns 103 and 105. The writer’s change committed in either case. This illustration concerns ordinary reads, without row locks.
The fixed view still includes 103, because it qualified before the writer’s commit. The writer is free to commit; the report’s view remains older. This is the snapshot promise developed in Transactions and isolation, applied to an entire result rather than a repeated stock read.
Keep the export transaction on one database connection. It can issue successive keyset queries, or declare a database cursor and fetch from that one query in batches:
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT COUNT(*) FROM orders WHERE status <> 'cancelled';
DECLARE export_orders NO SCROLL CURSOR FOR
 SELECT order_id, customer_id, placed_at, status
 FROM orders
 WHERE status <> 'cancelled'
 ORDER BY placed_at, order_id;
FETCH FORWARD 2 FROM export_orders;
-- Repeat FETCH until it returns no rows.
CLOSE export_orders;
COMMIT;
This database cursor is a server-side query position, distinct from an API token carrying key values. Its batches continue the same query. A plain non-locking PostgreSQL cursor already keeps its query’s view across fetches; Repeatable Read here also makes the separate count and any related report queries share that view. Starting independent Read Committed queries would not.
The cursor closes at the end of this transaction. A lost connection ends the transaction and its cursor; reopening a new transaction with the last key gets a new snapshot. It can resume a live traversal, but cannot honestly continue the same exact export without another mechanism retaining the original result.
What a long view costs
Old versions visible to an open snapshot cannot yet be removed by PostgreSQL’s normal cleanup. A slow export can therefore retain dead row versions while writers continue, increasing storage pressure and the work cleanup must do later. A cursor limits the rows delivered to the client at once; it does not automatically bound the database’s sorting, retained versions or total work.
Do not leave this transaction open while a person decides whether to click “next”. For a bounded export, read promptly into an output file or other controlled destination, close the transaction, then let the user download that finished result. Limit duration, batch size and concurrency, and handle cancellation by closing the cursor and ending the transaction. Connections, overload and capacity follows the resource budgets.
A durable export job can materialise the required rows from one snapshot, then serve or retry delivery from that stored result. Freeze the actual fields promised by the export. Saving only IDs and later joining them to current orders preserves a membership list, but lets field values change underneath it. Record the export’s query, schema/version and snapshot description alongside the output so its meaning remains clear.
PostgreSQL also offers WITH HOLD cursors that survive a successful commit within the same session. It copies their result into memory or temporary storage. That exchanges snapshot retention for materialisation cost; it is still lost with the session, so it is not a durable background-job record.
Choose the contract before choosing the batching mechanism. A scrolling list usually needs a clear continuation order and honest behaviour under movement. An exact report needs a fixed view, a bounded way to read it and a durable finished output if delivery must survive a retry. Neither “cursor” nor “page size” by itself states all three.
Repeat the experiments
Download the pagination experiment. It uses Python 3’s standard library and an installed PostgreSQL binary directory: python3 run-pagination.py --bindir /path/to/postgresql/bin. The directory needs initdb, pg_ctl, postgres and psql. The script creates and verifies its own temporary cluster on a private local socket, runs the checks, then stops and removes it. It never connects to an existing database.
The experiment contains only the five order headers needed here. Each change resets that input, so cancelling 101, moving 103’s time and cancelling 103 are separate histories. It checks the missing tied row with a timestamp-only boundary, both continuation methods, new and fixed snapshots, cursor fetches and the separate 20,000-row plan comparison. PostgreSQL 18.6 produced the stated outcomes. No throughput, network or distributed-snapshot result is claimed.

History, correction and deletion
 Deep diveAbout 11 minutes AI-generated 
Today’s value is not always the fact a reader needs. The catalogue can say that a blue mug costs 24.00 while Mina’s order correctly says she agreed to pay 20.00. A report can also need to explain why the catalogue said 25.00 yesterday, before somebody recorded a correction.
Keeping those answers requires deciding which past to preserve. The time when a price applies and the time when the shop records it are separate facts. Cancellation, retirement and deletion need the same care: an action that removes something from a current screen may leave its agreements, references and copies elsewhere.
The examples use PostgreSQL 18 and the shop’s fixed rows. After order 103, P7’s catalogue price changes to 25.00 effective at 09:00 UTC on 21 October 2026. At 14:00 UTC on 22 October, staff record that the intended price from the earlier instant was 24.00. We use that later history without changing the order’s agreement. Retirement and cancellation are separate policy drills, not further events in that history.

Keep the agreement with the order
Order 103’s mug line records one P7 at 20.00. Its tea line records two P3s at 4.50 each. The total remains 29.00 after the catalogue changes, because these are prices agreed on the order lines:
 Order 103’s agreement, before and after the catalogue correction

P7120.0020.00
P324.509.00 
Recalculating the old mug line from the corrected catalogue would make it 24.00 and change the order’s total to 33.00. That would answer what those products cost under another price, not what Mina agreed to pay. The original line price is a separate fact with its own owner.
Choose which other facts need the same treatment. A product reference can identify what was bought, but joining it to the current product name shows the name today. An issued document that must retain its original wording needs that wording retained as part of the issued document. Copying a fact deliberately at the moment of agreement is different from accidentally storing several editable copies of one current fact.
Changing an issued agreement is then another operation. A correction, adjustment or replacement document should say what it changes and why, while preserving the earlier version when the application must explain it. A direct update that silently substitutes today’s values cannot supply that explanation later.
When a price applies
A current products.price answers a current catalogue lookup. To ask which catalogue price applied at an earlier instant, store periods of applicability. This is often called valid time or effective time: the time in the world described by the data.
Before the correction is known, the price history says 20.00 before 21 October at 09:00 and 25.00 from that instant onwards. Use half-open periods: include the start, exclude the end. At exactly 09:00, the new period applies and the old one no longer does.
SELECT price
FROM price_history
WHERE product_id = 'P7'
 AND effective_from <= timestamptz '2026-10-21 12:00Z'
 AND (effective_to IS NULL
 OR timestamptz '2026-10-21 12:00Z' < effective_to);
Here price_history denotes a one-time-axis design with those named columns. A missing end means “continues until further notice”, not that somebody has predicted the price for every future date. A scheduled future change can be recorded in advance; its effective start need not be the moment the row is inserted.
The periods need rules. For one product and one view of history, two prices should not cover the same instant. A non-overlap constraint can enforce that. Whether gaps are permitted is a different question: non-overlap does not require every instant to have a price. Decide whether an absent period means unavailable, unknown or invalid history before choosing a fallback.
When the correction became known
The correction creates two reasonable answers to “what was P7’s catalogue price at noon on 21 October?” Using the corrected history today, it was 24.00. Using the information the shop had recorded at noon that day, it was 25.00.
Changing the effective-time row from 25.00 to 24.00 preserves the first answer and destroys the second. To keep both, record another time dimension: when each assertion became part of the recorded account, and when it was replaced. We call this recorded time. A design retaining both effective and recorded time is bitemporal.

All times are UTC in 2026. Each cell is a query answer, not one physical stored row. The baseline starts the example’s recorded history at order 103’s instant; it makes no claim about earlier recording. Before a change is recorded, this model’s open-ended assertion continues the last known price.
The later column changes from 25.00 to 24.00 when the recorded account changes. The earlier column remains 20.00. This is not a contradiction: each answer states both which effective instant and which recorded view it uses. Order 103’s agreement is another fact again, retained directly on the line rather than reconstructed from either catalogue answer.
These axes also explain late-arriving information. A correction recorded today can apply to last week. A price schedule recorded today can apply next week. Sorting changes by their database arrival time alone cannot reconstruct the effective price in either case. Conversely, sorting only by effective date cannot say what the application knew before a correction arrived.
Store the assertions
The downloadable example stores price_assertions. Each row says “during this recorded period, this was our asserted price for this effective period”. PostgreSQL’s tstzrange holds a range of instants, so the two periods have the same type but different meanings.
CREATE EXTENSION btree_gist;
CREATE TABLE price_assertions (
 assertion_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 product_id text NOT NULL REFERENCES products,
 price numeric(8,2) NOT NULL
 CHECK (price >= 0 AND price <= 999999.99),
 effective_period tstzrange NOT NULL
 CHECK (NOT isempty(effective_period)),
 recorded_period tstzrange NOT NULL
 CHECK (NOT isempty(recorded_period)),
 EXCLUDE USING gist (
 product_id WITH =,
 effective_period WITH &&,
 recorded_period WITH &&
 )
);
&& tests whether two ranges overlap. The exclusion constraint forbids a pair of rows for the same product whose effective periods and recorded periods both overlap. Such a pair could give two answers to the same two-time lookup. The supplied btree_gist extension provides the equality support for the text product ID beside the range operators.
The example constructs bounded ends as [start,end). An unbounded end is represented by a range with no upper bound. These range bounds are not SQL NULL prices; the price itself remains required. The declaration rejects empty ranges and overlapping assertions. The write protocol still owns the intended coverage, the meaning of the endpoints and which staff operation may change them.

The first row preserves the initial account before any future change was recorded. The example starts that recorded account at 20 October 10:15, the existing instant of order 103, purely as its baseline. It asserts no earlier recording history. The second row keeps the unchanged effective past. The last two rows give different recorded accounts of the same later effective period.
SELECT price
FROM price_assertions
WHERE product_id = 'P7'
 AND effective_period @> timestamptz '2026-10-21 12:00Z'
 AND recorded_period @> timestamptz '2026-10-21 12:00Z';
-- 25.00
@> means “contains”. Keep the effective argument unchanged and move the recorded argument to 2026-10-22 15:00Z; the answer becomes 24.00. At the correction boundary itself, the 25.00 assertion has ended and the 24.00 assertion has begun, so there is still one answer.
Record a correction as one change
Replacing an assertion requires several writes: close its recorded period, insert the corrected assertion and update the current catalogue if it derives from this history. Keep those writes in one transaction so a stopped application cannot leave the old account closed with no replacement. The example also records a correction identity and reason in that transaction.
Its deliberately narrow correction operation takes a lock on P7’s product row before changing the history. Every writer of this history must use the same coordination point and choose recorded boundaries in their intended order. A correction spanning several effective periods would need to split and replace the affected portions carefully. The supplied experiment implements this one displayed correction; it is not a general temporal editing library.
The recorded boundaries here are explicit application-maintained labels for the historical example. They are not captured PostgreSQL commit timestamps. PostgreSQL’s current_timestamp is the start time of the transaction, so naming a column recorded_at and defaulting it to that function does not turn it into a commit-order record. A system needing exact transaction-time history must choose a supported timestamping and concurrency scheme for that promise.
Nor are the old physical row versions kept for isolation a substitute for this table. Those versions are eventually cleaned up and do not carry the application’s effective-time meaning. A retained history is ordinary application data with its own constraints, write authority and retention policy.
On PostgreSQL 18.6, interrupting the correction after closing the old assertion rolled that close back. The earlier account remained queryable. Inserting an overlapping assertion was refused with 23P01; the same insert into an unconstrained copy produced two answers. Those checks establish the displayed mechanism. They do not establish that every possible historical edit preserves gap-free coverage.
Retire a product without losing a purchase
Suppose a separate policy drill retires P7 from sale. Deleting the product row would leave old lines referring to a missing product, so the core foreign key refuses it. That refusal gives the shop a useful question: should retiring a catalogue item also erase what customers bought?
A retired_at column is one possible extension. Current catalogue queries exclude retired products; old receipt queries continue to follow their references. The row remains the identity of the thing that was bought.
SELECT product_id, name, price
FROM products
WHERE retired_at IS NULL
ORDER BY product_id;
Do not add that active-product condition indiscriminately. In the retirement drill, joining order 103’s lines to products still gives its mug and tea. Adding retired_at IS NULL to the receipt query removes the mug line and silently changes the displayed order. A filter appropriate for buying today is wrong for explaining an earlier purchase.
A soft-deletion marker is similar: the row stays, while application policy treats it as removed. This can support undo and preserve references. Every relevant read path, uniqueness rule and restore path must agree on what counts as active. A foreign key normally sees the retained row; it does not make an inactive parent unavailable to new children.
Uniqueness may need a separate active-row policy. A partial unique index can permit reuse of a value while an older row is marked deleted. Restoring that older row can then conflict with its replacement. The application must resolve that collision; clearing the marker is not automatically a valid undo.
Retaining a row also retains its contents. A hidden customer name remains stored and can still be present in privileged queries, exports and historical copies. If a policy requires removing a particular field, a visibility flag alone does not perform that removal. Decide which facts must remain, which may be transformed and which must be removed before choosing the schema action.
Cancellation keeps a record of what happened
Now start a separate drill from the core snapshot: order 103 is pending, it has no payment, and its purchase has left P7 stock 0 and P3 stock 10. Choose a cancellation policy that returns the reserved stock and retains the order and lines as the explanation.
Deleting the order would not, by itself, return that stock. Changing its status would not either. The policy needs both the status transition and the compensating stock changes, together. Make the transition conditional so a repeated cancellation cannot return the same units twice.
UPDATE orders
SET status = 'cancelled'
WHERE order_id = 103 AND status = 'pending'
RETURNING order_id;
Run this inside a transaction. If it returns order 103, add its reserved quantities back to the products in the same transaction and commit the group. If it returns no row, do not add any stock. The downloadable implementation groups the lines by product before applying those additions. All other operations that can change this order’s status or reservation must follow a compatible protocol.
The native drill accepted the first cancellation and refused the repeated transition. The final stock was P7 1, P3 12 and P9 4, while the two lines remained. This is a chosen alternative history, not a change to the collection’s core still-due report.
An already-paid order needs another policy. Its recorded payments must not disappear merely because a status changes, and a card refund is an action at the provider. A database transaction can record that a refund is required; it cannot make the provider undo a charge by rolling back SQL. The lack of a payment on order 103 makes this particular drill a reservation cancellation, with no claimed external refund.
Follow a deletion to its copies
A physical DELETE removes rows from the database’s logical state. References decide what else must happen inside that database. With ON DELETE CASCADE, deleting a parent also deletes its referencing children. With the core default action, a referenced parent deletion is refused. Neither action is a general instruction to every system that has copied the data.

No foreign-key action reaches these copies. Each needs its own removal, expiry or suppression policy.
The worksheet uses an independent local table to show this boundary: the cascading lines disappear while an unreferenced receipt copy remains. It does not execute a cache, search service or backup deletion.
Before removing a record, follow the relationships in both directions. Which parents would remain? Which children would be removed, refused or detached? Which history or audit rows carry the same information? A cascade from a catalogue product to its old order lines would erase purchase evidence as a side effect of catalogue upkeep.
Then follow copies outside those declared references. A cache may outlive the row; a search document may remain searchable; an export may already be elsewhere. Record the required downstream work durably with the deletion, give that work a stable identity and check its completion. Outboxes and database-backed jobs develops the delivery protocol.
Backups and replicas need different treatment. A replica can carry a deletion onward, but an older backup preserves an earlier state by design. A restore can therefore reintroduce data previously removed. Keep whatever suppression or reconciliation record the restoration process needs outside the state being rolled back, and apply the chosen policy before the restored system becomes authoritative. Backup, restore and reconciliation owns that recovery procedure.
A deletion policy is complete when its scope and acceptance checks are clear. “No longer appears on the account page”, “cannot be used for a new purchase”, “removed from the current operational tables” and “removed from every managed copy after its retention period” are different promises. State the one the application can carry out and verify.
Repeat the history and policy drills
The experiment targets macOS or Linux with Python 3, a PostgreSQL 18 installation that includes btree_gist, and a writable /tmp directory. Run it as an ordinary user: PostgreSQL’s initdb refuses to run as root.
Download the experiment, the shop data and the history labels into one directory. In a disposable Python environment install psycopg[binary]==3.2.12, then run python run-history.py --bindir /path/to/postgresql/bin, replacing the path with the directory containing initdb and pg_ctl. It creates a private temporary cluster under /tmp, verifies the connected server’s data directory, installs btree_gist only there and removes its cluster afterwards. It clears inherited environment variables whose names begin with PG from its own process and child tools, including the defaults used by later driver connections.
The macOS run used PostgreSQL 18.6, Python 3.14.5 and Psycopg 3.2.12; Linux execution has not been checked. It verifies the six price answers in Figure 1, both half-open boundaries, rollback of an interrupted correction and rejection of overlapping assertions. It also checks the retained agreement, the retirement-filter counterexample, the repeated cancellation and the cascade boundary. The latter drills are independent policies on disposable state. No external erasure, provider action, backup restore or retention interval is claimed by these local checks.

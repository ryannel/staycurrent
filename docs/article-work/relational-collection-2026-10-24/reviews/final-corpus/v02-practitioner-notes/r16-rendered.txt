Retries when a commit reply is missing
 Deep diveAbout 8 minutes AI-generated 
A missing commit reply leaves a question that another connection cannot answer merely by being healthy: did the purchase happen? The database may have rolled the transaction back when the connection ended. It may instead have committed just before its reply was lost. Sending the purchase again has to be safe in both histories.
This differs from a transaction the database has explicitly rejected. A serialization failure says this attempt did not succeed and its whole decision must run again. A broken connection during commit says the application does not yet know the outcome. Treating both as “try the SQL again” loses that distinction.
We follow Mina’s order 103, rewinding to before it exists. There is 1 blue mug and twelve packs of tea. She wants the mug and two packs, with agreed unit prices 20.00 and 4.50. The purchase must record its order and two lines while taking stock to P7 0 and P3 10. It remains pending payment. PostgreSQL 18 supplies the concrete protocol; the same uncertainty appears wherever a reply can go missing.

Two histories, one missing reply
A transaction can commit before the application hears that it committed. The change and the message reporting it are separate events. The gap can be small and still matter.

Chosen histories, not a timing measurement. What the database did differs; what the caller received does not.
In the second history a blind stock reservation now finds no mug. Reporting “out of stock” would lose Mina’s successful purchase even if a primary key prevented a duplicate order. With replenished stock, a new order ID and no request identity, another attempt could instead become a second purchase. A guard against negative stock is not a record of which logical request used it.
Nor does a timeout establish the first history. It says a deadline expired. The server may still be working, and a cancellation can race with completion. Dispose of a broken connection, let the owner finish its cancellation and cleanup, and resolve the purchase separately. Replacing a connection repairs transport capacity; it does not resolve the old operation.
Name the logical request before attempting it
Give this purchase a stable opaque request key, purchase-mina-103. Create it before the first attempt, retain it through a dropped reply and reuse it on every retry of that purchase. A second attempt must not generate a second key. The example’s readable spelling is for us; an actual key need not contain an order number.
The key identifies an intention across attempts. A database transaction ID identifies one attempt inside a database. Order ID 103 identifies a stored order. A payment provider’s effect ID identifies work at that provider. They have different authorities and lifetimes. Retrying the same purchase should retain its request key even when it needs a fresh connection and a fresh database transaction.
A key alone is insufficient. Suppose the caller reuses it while changing the quantity of tea. The application must reject that conflicting reuse, rather than return the old order as though it matched the new request. Store a fingerprint of every meaningful input alongside the key.
Here the fingerprint is a normalised JSON value containing Mina’s customer ID, both product IDs, quantities and agreed unit prices. The application first establishes the customer’s authority, validates quantities and obtains prices from an authorised quote. It orders lines consistently and represents exact prices consistently. Comparing arbitrary request JSON would make incidental formatting or omitted fields decide whether two intentions match.
The experiment stores that normalised value itself as jsonb and compares it for equality. A compact hash is another representation, but then canonicalisation, the hash algorithm and collision handling belong to the contract. Do not leave the meaning of “same payload” to whichever serialiser happens to run.
Commit the identity with the purchase
Add a purchase_requests table to record successful purchases. One row means “this logical purchase committed, with this payload and this resulting order”. For this example the successful result is the order ID. It does not claim that payment arrived or that the order’s later status will never change.
CREATE TABLE purchase_requests (
 request_key text PRIMARY KEY,
 payload jsonb NOT NULL,
 order_id integer NOT NULL
 REFERENCES orders (order_id)
 DEFERRABLE INITIALLY DEFERRED
);
The primary key is immediate, so two simultaneous attempts cannot both claim the same request key. The order reference is deferred: the transaction can claim the request before it inserts the order, but the order must exist at commit. The request, stock deductions, order and lines all belong to that one transaction.
Claim the identity before doing purchase work. These placeholders represent bound values in application code:
BEGIN ISOLATION LEVEL READ COMMITTED;
INSERT INTO purchase_requests
 (request_key, payload, order_id)
VALUES ($1, $2, $3)
ON CONFLICT (request_key) DO NOTHING
RETURNING request_key;
A returned key means this transaction inserted it. Reserve the products in a consistent order, using conditional stock updates; insert order 103 and its two lines; commit. If any product is unavailable or another operation fails, roll back the whole transaction, including the new request record. Report success only after commit succeeds.
No returned key means another attempt owns or has recorded it. PostgreSQL’s uniqueness check can wait for an overlapping transaction to finish. If that transaction aborts, this insertion can proceed. If it commits, this insertion does nothing. Start a separate subsequent statement to read the stored result:
SELECT payload, order_id
FROM purchase_requests
WHERE request_key = $1;
-- Same normalised payload: return that order_id.
-- Different payload: reject conflicting key reuse.
-- Do not run the stock updates on this branch.
End the replay transaction before returning its recorded result. The separate statement matters at Read Committed: it gets a fresh snapshot after a possibly waiting insertion. A single statement combining “insert if absent” with a fallback lookup can have an earlier snapshot that cannot see the conflicting row which made the insert do nothing. An unexpectedly missing result requires bounded resolution, not permission to run an unowned purchase.
This protocol assumes request records are not concurrently deleted or rewritten. The authoritative lookup goes to the write authority, not a replica that may be behind. An earlier absence query is never the claim: the original attempt could still be in progress and commit afterwards. The unique insertion coordinates those overlapping attempts.

Resolution as text
If the first attempt committed, the retry’s insertion of the same request key finds the existing record. A subsequent Read Committed statement compares the payload and returns order 103 without taking stock again. If the first attempt aborted, no request record or purchase effect remains. The retry claims the same key and performs the purchase, committing the record, stock, order and lines together. An overlapping first attempt can make that key insertion wait; absence in an earlier lookup alone does not grant ownership.
The disposable PostgreSQL 18.6 experiment deliberately withheld a real successful commit’s acknowledgement from a simulated caller. Replaying the same key and payload returned 103 with stock and row counts unchanged. Without that resolution branch, another conditional mug reservation returned no row, reproducing the misleading refusal. A separate client termination before commit left no request or purchase effects, so the same key could perform the purchase on a fresh attempt.
The experiment also overlapped two key insertions. The second waited for the first transaction and then read its committed order in a new statement. A changed payload was rejected before any stock work. The reply withholding is an explicit fault injection at the caller boundary; it is not a measured network partition, power failure or driver’s automatic retry behaviour.
Choose the retry from the outcome
The application needs an error policy that preserves what it actually knows. PostgreSQL SQLSTATEs are stable identities for database errors; a transport exception is a different kind of evidence.

ResultMeaningNext action
Successful commit replyPurchase committed under the configured durability promiseReturn its recorded outcome

40P01, deadlock victimThis attempt was selected to break a deadlockRoll back; bounded whole-operation retry where appropriate; fix recurring ordering
Insufficient stockAn application precondition failedRoll back this new purchase and return a refusal
Connection loss while commit is in flightCommit outcome unknownReconnect and resolve with the same request identity
Different payload under the same keyConflicting request reuseReject; do not reinterpret it as the old purchase 
Rerunning a transaction includes its application decisions. A new snapshot may show that the class is full or the stock is gone. Reusing a value calculated from an earlier attempt defeats the reason for retrying. Keep network calls and other irreversible effects outside the retrying transaction; an aborted database attempt cannot recall an email already sent.
Do not retry every constraint violation. A duplicate request key is handled by the protocol above; another duplicate key may indicate invalid input or a bug. A check violation does not become valid because the application waits. Classify the relevant object and SQLSTATE, and keep unexpected errors visible.
Use a bounded retry budget with backoff and jitter, so competing clients do not all immediately collide again. Bound total elapsed time as well as attempt count, and include connection acquisition, lock waits and cleanup. Exhausting that budget while the outcome is uncertain must remain an unresolved purchase. Retain the key and offer a status lookup or later reconciliation; do not translate exhaustion into “the purchase did not happen”.
The record has a lifetime
Keeping the request key only in process memory would lose it on the next process restart. The caller or its durable workflow must retain it for as long as it may need to repeat the intention. If the browser creates a fresh key on every submit, a double-click can still become two logical requests. The interface must decide when the user is resuming a purchase and when they are starting another.
The server must retain the outcome too. Deleting a request record while an old retry is still possible makes that retry look new. Choose retention from the maximum replay and reconciliation window, and keep a durable rejection of expired identities if deletion would otherwise reopen them. Authorise status lookups; knowing an opaque key alone should not grant access to someone else’s order.
This deliberately small relation records successful purchases. An insufficient-stock attempt rolls back its key, so a later retry can try the purchase again against later stock. If the product contract promises to remember refusals permanently, model those terminal outcomes explicitly and commit them under the same identity. That is a different contract from assuming every failed attempt has been remembered.
A database record also has the database’s durability and recovery limits. Restoring a backup that excludes a previously acknowledged request can remove its deduplication record along with its order. Reconcile valid later requests and any external effects before reopening an old history; a key cannot recognise a record that recovery discarded.
Repeat the protocol
Download the retry experiment and its fixed shop data into the same directory. Run python3 run-retries.py --bindir /path/to/postgresql/bin. It uses the Python standard library and PostgreSQL client, checks an owned disposable cluster through a private socket and removes it afterwards.
The scratch schema keeps the purchase’s identity, stock, order and lines; historical orders and payments are outside this fixture. Checks compare the complete resulting stock vector and row counts. No provider charge is attempted. Outboxes and database-backed jobs carries this identity reasoning across a boundary that the database transaction cannot commit for itself.

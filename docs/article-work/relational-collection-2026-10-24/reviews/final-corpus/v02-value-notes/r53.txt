H1 Moving a SQL application to CockroachDB

Deep diveAbout 7 minutes AI-generated   

A PostgreSQL driver can connect to CockroachDB and still send a command with a different meaning. A complete copy can contain every expected row and still be unsafe to serve. Moving an application therefore has two linked jobs: preserve the contract its callers rely on, then transfer authority over a closed, accounted-for history.

We will use an explicitly separate migration rehearsal, rewound to before Mina's order 103. Historical orders 101 and 102 and their payments exist; P7 has one blue mug and P3 has twelve packs of tea. PostgreSQL 18.6 starts as the only write authority. After a consistent copy to CockroachDB 25.4.17, Mina's request purchase-mina-103 creates order 103 there. A return to PostgreSQL must preserve that purchase, including stock P7 0 and P3 10. It cannot just reconnect the old application to its old rows.

H2 Test meaning before copying

CockroachDB supports PostgreSQL's wire protocol and much of its SQL syntax. That makes drivers and familiar tooling useful starting points. It does not make PostgreSQL's complete behaviour the target contract. Inventory what the application actually uses: schema definitions, generated SQL, stored code, extensions, transaction settings, result types and error handling. Check those against the pinned target release and test the important paths.

A small arithmetic probe exposes a difference without any copying:

SELECT n / 2 FROM division_probe;
-- n is an integer with value 5.
-- PostgreSQL 18.6: 2
-- CockroachDB 25.4.17: 2.5

The native fixture observes those answers. If the caller means a fraction, use an explicit decimal expression on both engines and retain the driver's exact decimal value. If it means a count of complete pairs, choose and test the rounding rule. CockroachDB's // supplies floor division, but replacing operators without considering negative inputs would not establish equivalence to every PostgreSQL expression.

Type names need the same scrutiny. PostgreSQL's ordinary integer is 32-bit; CockroachDB's default INT is 64-bit. The rehearsal explicitly uses INT4 for the source's 32-bit contract. Test boundary values, returned driver types and serialisation, rather than deciding compatibility from these small IDs. Prices remain exact two-decimal values; timestamps are compared as UTC instants.

Check transaction behaviour separately. PostgreSQL normally defaults to Read Committed; CockroachDB normally defaults to Serializable and can require whole-transaction retries with SQLSTATE 40001. Choose the target isolation deliberately and preserve the business rule under that protocol. A transport failure during commit still leaves an uncertain outcome, not an instruction to invent another purchase key. Retries when a commit reply is missing develops that distinction.

H2 Port the purchase contract

A concrete incompatibility appears in that earlier PostgreSQL purchase. It claims a unique request key before taking stock, with a non-null order reference checked at commit through a deferred foreign key. The native CockroachDB 25.4.17 probe rejects that deferred definition. Removing the reference silently would lose part of the source's protection; keeping the original SQL in an untested migration file would not preserve it either.

This fixture chooses an application-owned bridge. Its immediate foreign key remains, but the outcome may be null while the transaction owns a new claim:

CREATE TABLE purchase_requests (
request_key TEXT PRIMARY KEY,
payload JSONB NOT NULL,
order_id INT4 REFERENCES orders (order_id)
);

The transaction claims the key with the normalised payload and a null outcome, using INSERT ... ON CONFLICT DO NOTHING RETURNING. If it owns the claim, it conditionally reserves both products, inserts the order and lines, then fills order_id = 103. The application refuses to commit an incomplete claim. An exception rolls back the claim and all purchase effects together. The immediate reference checks the completed outcome against an order that now exists.

This changes the enforcement boundary. A nullable foreign key permits a committed null; it does not recreate PostgreSQL's non-null deferred reference. The procedure relies on trusted writers that all run the completion check, with access preventing bypass. The fixture tests that application contract and audits zero incomplete committed claims. If arbitrary writers must be prevented by the database alone, this bridge is insufficient: choose another schema or enforced procedure and verify it before moving the application.

If another attempt already claimed the key, the operation reads its payload and completed outcome. Matching payload returns 103 without taking stock; different payload is refused. An incomplete committed outcome is an error to resolve, never permission for another purchase. A retryable failure restarts the whole decision with the same identity and a bounded retry budget.

In the native run, two overlapping identical requests return 103 with one order and one stock effect. A deliberately raised exception after the tea deduction leaves neither a claim nor a deduction. Withholding an actual successful purchase's acknowledgement from the simulated caller, then repeating its identity, returns the stored outcome unchanged. This tests the application boundary; it is not a claim that a network partition occurred. No provider or message sender is called.

H2 Choose a copy whose end is knowable

For this small rehearsal, accept a write pause. Stop new source admissions, finish or cancel admitted work, resolve uncertain requests and fence every old write path. Keep PostgreSQL fenced while taking the final copy and validating it. The pause includes copy and acceptance, so its duration must fit the service's maintenance budget.

The fixture makes admission visible through one gate row. Every application purchase updates it only while it is open, holding the transaction's conflict through the purchase. Closing the same row serialises with those admissions. Both engines are tested with a closing transaction held open and another purchase racing it: the request waits and is refused after the fence commits, with complete retries where needed. Only then is the closed history enumerated.

This cooperative gate covers its declared participants. A production application also has importers, privileged scripts, workers and old sessions. They must obey an effective fence too. Changing a web deployment or a connection address does not stop an already-running writer.

The final PostgreSQL export reads all intended tables in one Repeatable Read, read-only transaction after the fence. The target stays closed to application writes while related rows are loaded. Schema creation and indexes are separate controlled work; the example keeps ordinary foreign keys active and loads parents before children.

A larger migration can bulk-copy while the source remains active and then apply captured changes. That adds a precise join between the copy's snapshot and the stream, dependency ordering, deletes, retries and a final applied position after source fencing. A low lag estimate does not prove that every transaction before the fence arrived. This paused-write run does not execute MOLT, CDC or a zero-downtime migration; those are different procedures to rehearse.

H2 Compare facts and effects

Define equality before comparing two engines. The fixture orders rows by their complete keys, normalises exact decimals and UTC instants, and compares every selected value in customers, products, orders, order lines, payments and request outcomes. Control rows and each instance's ownership marker are checked separately; they are not copied business identities.

Counts find obvious omissions. They do not establish equality. In a scratch target branch, changing the teapot line in order 101 from 35.00 to 34.00 keeps every table's count unchanged. The complete value comparison detects the mismatch; restoring the agreed 35.00 makes it pass. Copying both data and a mistaken aggregate from the same faulty query would not provide an independent check.

Add acceptance that gives those rows meaning. The native run checks the core receipts and still-due report, the complete stock vector, foreign-key refusal and request replay. After Mina's accepted purchase, order 103 totals 29.00, has no payment and is due 29.00. Orders 101 and 102 remain fully paid. Existing payments are historical rows, not evidence of a new provider action.

Re-establish and test roles, ownership, runtime grants, policies, TLS identities and connection routes in the target deployment too. A successful copy run as administrator cannot prove that the application can use its rows or that an unrelated caller cannot. Operating and securing a CockroachDB cluster develops those checks.

H2 Transfer one authority

Open CockroachDB only after the closed copy and application checks pass, while PostgreSQL remains fenced. Record the routing and credentials that make the new authority effective. A gradually changing client population must still obey that authority; independently directing purchases to each database creates two histories that a later row copy cannot safely merge.

The player follows the purchase through both handovers. Watch its request identity and both stock values when the old database becomes the candidate for a return.

H2 Reconcile the return before reopening it

Close CockroachDB's admissions and settle in-flight work first. Enumerate the accepted history while it remains closed. Here the new operation is Mina's stable request key, normalised payload and order outcome. PostgreSQL has stayed fenced since the first handover, so there is no competing source history to merge.

Controlled reconciliation on PostgreSQL applies the complete operation in one transaction: request claim, both stock deductions, order 103, its two lines and completed outcome. The fixture checks the expected starting rows before replay; a conflict stops reconciliation instead of overwriting it. Repeating the same operation returns 103 without another deduction; changing its payload is refused. The fixture then compares the entire closed business state on both databases and runs the receipts again.

Only after acceptance does PostgreSQL reopen. CockroachDB stays fenced. A later retry of Mina's key on the returned authority still resolves to 103, with P7 0 and P3 10. This is a reconciled return, not a route change followed by a hope that stock will converge.

The fixture creates no provider payments, messages or emails. A real return must reconcile those authorities too: a missing outbox row on PostgreSQL cannot prove that CockroachDB's worker never sent its event. Preserve effect identities and consult the provider or consumer's record before repeating external work. CockroachDB backup and recovery develops the same problem when replacement history comes from a restore.

H2 Accept the service that will run

Passing these tiny functional checks establishes the declared copy, purchase and return mechanics. It does not establish production latency, contention, connection-pool capacity or placement. Test representative generated SQL, realistic key distributions and mixed caller versions, including retry exhaustion, prepared commands and actual reconnection routes. Keep operational acceptance separate from a correct row comparison.

The native run uses one private PostgreSQL cluster and one private CockroachDB process on a single host, then removes both. It records exact binaries, driver and actual licence setting; temporary feature execution is not production entitlement. There is no independent-host failure, live replication, elapsed-time objective or external-effect result. Keep those limits visible when choosing the migration and its return window.

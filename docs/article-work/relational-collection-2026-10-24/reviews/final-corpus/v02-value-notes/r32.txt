H1 PostgreSQL vacuum and transaction age

Deep diveAbout 7 minutes AI-generated   

A table can need vacuum even when it has spare disk space and almost no deleted rows. PostgreSQL must reclaim obsolete versions, maintain information that lets reads avoid heap visits and keep old transaction identifiers safe to interpret. Those jobs share a maintenance mechanism, but their warning signs differ.

That matters when deciding what to change. More aggressive workers cannot remove a version that an old snapshot still needs. Rebuilding a bloated file does not explain why the same backlog will return. A recent vacuum timestamp does not establish that transaction-age risk has been resolved.

Start with the scratch mug update from the architecture article: a read-only Repeatable Read report sees P7 at 20.00, another backend commits 25.00, and a fresh reader sees the replacement. This is an independent storage experiment. It changes neither order 103’s agreed price nor the collection’s dated catalogue history.

H2 The version that cannot go

The report’s snapshot is a promise that PostgreSQL must continue to honour. Removing its 20.00 tuple would break that promise. Vacuum therefore needs a safe horizon: a boundary before which obsolete versions are no longer required. Commit makes a replacement visible to eligible readers; it does not, by itself, make its predecessor removable.

Follow the two vacuums in Figure 1. The first does run, but cannot reclaim the version the report still needs. The second has a different horizon because the report has finished.

On an owned PostgreSQL 18.6 instance, the first vacuum left one current tuple and one dead tuple according to pgstattuple. The open report still returned 20.00 afterwards. Once it committed, another vacuum removed the dead tuple. The visible table had one product throughout.

This is a counterexample to “vacuum ran, so all dead rows are gone”. It also separates a cleanup delay from a worker that never started. Repeatedly vacuuming behind the same retained horizon spends work without changing what is eligible for removal.

A long query can retain a snapshot. A session left idle inside a transaction can retain one too, depending on the transaction’s work and isolation level. An idle connection outside a transaction is different. Inspect what the backend retains rather than treating every old connection as a blocker.

H2 Space, visibility and statistics

After removal, the space is normally reusable inside the existing heap. Ordinary vacuum does not pack all survivors together. It may truncate entirely empty end pages, but scattered gaps usually remain in the file. That can be a healthy steady state for a table that will fill them again.

Bloat describes an excess of allocated space over what the useful data and expected working slack need. A large file alone does not quantify that excess. Separate the heap, its indexes and TOAST storage; distinguish live data, versions still required, removable tuples and space already free for reuse. Each points to different work.

Visibility has another representation. Every heap page has two bits in the visibility map. An all-visible bit says the page’s tuples are known to be visible to all relevant readers. An index-only scan can use it to avoid inspecting the heap. An all-frozen bit additionally says that the page needs no further tuple freezing. The second implies the first, but the first does not imply the second.

The test discouraged sequential scans explicitly to inspect this index-only route on one row; it is not a natural plan-choice benchmark. Two heap fetches in the first state reflect physical index entries, rather than two logical products. The second state lets the same query avoid the heap. A later change to the page can clear visibility-map information again.

The standalone ANALYZE command has a separate job: sampling data to update the planner’s statistics. VACUUM (ANALYZE) combines cleanup and statistics collection. Plain vacuum is not a substitute for collecting fresh distributions when data changes, and plain analyze does not remove obsolete tuples.

H2 Why old transaction IDs matter

Tuple visibility uses transaction identifiers, whose normal on-disk form has 32 bits. Their counter eventually wraps. Comparisons work within a moving window, so PostgreSQL cannot keep interpreting an arbitrarily old committed insertion as an ordinary recent ID forever.

Freezing records that an eligible old insertion is permanently in the committed past. It changes how visibility treats that tuple; it does not freeze its business values against future updates. Modern PostgreSQL can preserve the original xmin value while setting the relevant flag, so looking for a special number in xmin is not a reliable freeze check. The fixture’s second vacuum requested freezing as well as cleanup, and its page became both all-visible and all-frozen.

For each relation, relfrozenxid tracks a conservative boundary for unfrozen transaction IDs. Its age counts transaction-ID distance from the current point, not days since the table was edited. A quiet catalogue table ages as transactions elsewhere consume IDs. A young dead-tuple estimate therefore cannot establish that an old table is safe.

SELECT c.oid::regclass AS relation,
age(c.relfrozenxid) AS xid_age,
mxid_age(c.relminmxid) AS multixact_age
FROM pg_class AS c
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY age(c.relfrozenxid) DESC;

SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;

The first query includes ordinary tables, materialised views and TOAST tables in the current database. The second compares database boundaries across the cluster. Inspect all databases, including those an application rarely uses. System catalogues matter too; a maintenance role that skips them cannot establish database-wide completion.

Multixact IDs are another finite identifier space, used when row-lock information describes multiple transactions. Their age and retention have related but distinct maintenance rules. Monitor mxid_age(relminmxid) alongside transaction age rather than assuming that a low XID age covers both.

H2 Find the retained horizon

Start with evidence about sessions. The age of backend_xmin shows how far back a backend’s snapshot horizon reaches; backend_xid identifies a transaction ID it has acquired. Some fields can be null and visibility into other sessions depends on the monitoring role.

SELECT pid, usename, state, xact_start,
backend_xid, age(backend_xid) AS xid_age,
backend_xmin, age(backend_xmin) AS snapshot_age,
wait_event_type, wait_event
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL OR backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC NULLS LAST;

A session is not the only possible holder. Prepared transactions can remain after their client disconnects. Replication slots can retain an xmin for ordinary rows or catalog_xmin for catalogue rows. A standby using hot-standby feedback can also hold cleanup back on the primary. Identify the owner and the purpose of each retained boundary.

SELECT gid, prepared, owner, database,
age(transaction) AS xid_age
FROM pg_prepared_xacts;

SELECT slot_name, slot_type, active,
xmin, age(xmin) AS row_age,
catalog_xmin, age(catalog_xmin) AS catalog_age,
restart_lsn
FROM pg_replication_slots;

restart_lsn concerns retained WAL. It is not another measure of tuple age. A slot can create log-retention and row-cleanup problems with different boundaries. Dropping a needed slot can force its consumer to rebuild; resolving a prepared transaction requires knowing the transaction’s intended outcome. These are ownership decisions, not automatic consequences of sorting an age column.

H2 Can maintenance keep up?

Once retention is understood, inspect maintenance itself. pg_stat_user_tables reports estimated live and dead tuples, vacuum and analyze timestamps and activity counts. Estimates can lag. A counter gives useful trends, but does not replace physical inspection when deciding whether a large rewrite is justified.

pg_stat_progress_vacuum shows a running vacuum’s phase and progress. Logs can reveal repeated lock conflicts, skipped work, index cleanup and the horizon used. A long interval since completion means something different from a worker repeatedly completing but being unable to remove recently dead versions.

Autovacuum scheduling uses change counts, table size and configured thresholds, with separate triggers for different maintenance needs. Large tables can accumulate substantial work before a scale-factor threshold is reached. Small, intensely updated tables may need more frequent attention. Table-level settings let a particular workload earn a different policy without moving every table to the same threshold.

Triggering earlier helps only if workers have enough time, I/O capacity and memory to finish. Cost throttling reduces interference with foreground queries, while also slowing the work. More workers increase concurrency and resource demand. Measure whether the backlog drains between bursts and whether age boundaries advance; changing one setting because “vacuum is slow” skips that diagnosis.

Anti-wraparound maintenance can run even when normal autovacuum is disabled. Treat forced activity and age warnings as maintenance urgency, not proof that PostgreSQL will always rescue a neglected cluster. Near exhaustion the server protects data by refusing commands that need new IDs. Use the version’s documented recovery procedure and an operator who can inspect every retention holder. Operating and diagnosing PostgreSQL owns that intervention.

H2 Choose the work that remains

Match the evidence to the maintenance job
| Evidence | Question to resolve

| Old snapshot; dead tuples remain after vacuum | When can that owner release its history?

| Removable backlog grows; no retained horizon explains it | Does vacuum start and complete quickly enough?

| Many heap fetches in a covering read | Are page changes or delayed vacuum preventing all-visible coverage?

| Old XID or multixact boundary | Is eligible freezing completing across all relevant relations?

| Large reusable gaps persist and hurt the workload | Does reclaiming the excess justify a planned rewrite?

| Bad row estimates after a distribution change | Are analyze and the statistics model appropriate?

VACUUM FULL writes a compact replacement and takes an exclusive lock that blocks normal table use. It needs working disk space as well as time. It can solve an established space problem, but it does not make old snapshots cease to exist or supply a sustainable maintenance policy. Index rebuilds and the locks involved belong with schema changes under load.

Healthy maintenance leaves room for the next round of updates, enough visibility coverage for the intended reads and safe transaction-age boundaries. File size need not fall after each successful vacuum. The useful result is that the next cycle of work fits and the boundaries keep moving.

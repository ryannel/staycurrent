H1 Indexes and access paths

Deep diveAbout 11 minutes AI-generated   

An index gives the database another way to reach rows. Without an index on orders.customer_id, finding Mina’s orders means checking every order. With one, the database can find entries for customer 1 and follow them to her rows. The answer is the same; the work needed to produce it changes.

The extra route costs something. The index occupies space, competes for memory with table pages and must be maintained as rows change. An index that saves a large read once a day might still be a poor exchange for work added to every purchase. Choosing indexes means identifying the work a query can avoid, then deciding whether that saving earns the ongoing cost.

This article follows ordinary ordered indexes, usually B-trees, through the shop’s order queries. PostgreSQL 18 supplies the concrete SQL and measured plans. The small drawings explain the mechanism; a separate generated table makes the difference in work visible on a running PostgreSQL 18.6 server.

H2 A second order for the same rows

A table has no guaranteed display order. PostgreSQL stores its rows in a heap: pages with space for rows, without keeping them sorted by customer or placement time. A page is the fixed-size block the database reads into memory; a normal PostgreSQL page is 8 kB. Several rows usually share one, so finding one row can still require reading a whole page.

A sequential scan visits the table’s pages and tests the rows against the query. It needs no additional structure. Its work grows with the table, even if the answer remains two orders.

SELECT order_id, placed_at, status
FROM orders
WHERE customer_id = 1
ORDER BY placed_at DESC, order_id DESC;

An index keeps the search values with a way to find each row again. Its entries can be in customer order while the table remains in its existing arrangement. Follow customer 1 through Figure 1: the adjacent entries lead to orders 101 and 103, whose rows need not be adjacent.

The shop’s three core orders, with invented page locations. This drawing makes each row a separate page so the references stay visible; it is not a PostgreSQL page measurement. Each index entry contains a customer ID and a row location. The order ID is read from the table row at that location.

The key of this index is customer_id. It is not a unique key: several entries may carry 1. The row location distinguishes which row each entry reaches. In PostgreSQL that location is a page and an item number, called a tuple identifier or TID. It describes a stored row version, rather than a business identity you should retain in the application.

Other storage designs use another route back. In MySQL’s InnoDB, a secondary index carries the primary key, and the table itself is stored as a tree ordered by that key. Finding a row through a secondary index then involves a search in the table’s tree too. The useful question remains the same: after finding a matching entry, what work is still needed to obtain the requested row?

H2 Jump to the start, then walk

A sorted list alone would still need a way to find its first 1. A B-tree arranges the index into pages. The bottom, or leaf, pages hold the ordered entries. Pages above them hold separators that direct a search towards the appropriate range. The search starts at one root page and follows a choice at each level until it reaches a leaf.

A real page holds many entries, so each extra level makes a large increase in the number of entries the tree can reach. The descent is usually a small part of a large result. After finding the first matching key, a scan can continue along the leaves until it reaches a key outside the requested range.

That gives a B-tree both equality searches and ordered ranges. An index on placed_at can find the first order at or after a specified instant, then continue until a second bound. It can also supply rows in time order. The database may still choose a different route, and SQL still needs ORDER BY whenever result order matters. An access path makes an order cheaper; it does not turn an unordered query into a promise.

The table rows reached by successive entries may be scattered. Ten matches can mean ten different table pages, while ten neighbouring rows might share one. Count the pages and rows reached after the descent, as well as the depth of the tree.

H2 Put the query in the key

The shop now wants Mina’s two newest orders since 15 October. For this example, add the later illustrative orders 105 and 106: Mina and Edda each place an order at 12:00 UTC on 21 October. Mina’s qualifying orders are 105 and 103, at different times. Edda’s 106 does not qualify for Mina’s list.

SELECT order_id, placed_at, status
FROM orders
WHERE customer_id = 1
AND placed_at >= timestamptz '2026-10-15 00:00:00+00'
ORDER BY placed_at DESC, order_id DESC
LIMIT 2;

A composite index has several key columns. It sorts by the first, then by the second among entries that tie on the first, and so on. For this query, customer equality should put one customer’s entries together; placement time should put that run newest first.

The query also specifies descending order ID. Mina’s displayed rows do not need it to settle a tie, but the same customer could place two orders at one timestamp. Time alone would then leave their relative order unspecified. The ID gives the list a total order for that case, and the index must match it to avoid a sort. In the global newest-first index below, the displayed tie is visible: 106 precedes 105 before the customer condition excludes 106.

CREATE INDEX orders_customer_history
ON orders (customer_id, placed_at DESC, order_id DESC);

The customer-only index stores customer IDs and row locations. Reading its three customer-1 entries fetches orders 101, 103 and 105 from the table; only those fetches reveal their dates, order IDs and status. Order 101 is too old. Sort the other two to return 105, then 103. The history key already stores customer, date and order ID: it reads 105, then 103 and fetches those two rows for status. The date-first key reads 106, 105 and 103, but rejects Edda’s 106 using its indexed customer ID, fetching only the two matching rows. All three routes return 105, then 103.

A conceptual entry walk over the core orders plus later illustrative orders 105 and 106. Locations are invented (page, item) pairs, continuing Figure 1; equal customer-only keys are shown in locator order. Dates and IDs appear in an entry only when its key contains them. Both later orders are pending, with no new lines or payments. This is not a native plan for five rows.

The history key can stop at orders 105 and 103, fetching those rows for the returned status. Customer alone has neither dates nor order IDs in its entries, so all three of Mina’s rows must be fetched, checked and the survivors sorted. Date first gives the required global order and carries the customer ID, so it can pass Edda’s 106 without fetching her row. On a busy shop it might pass thousands of other customers’ entries before finding two of Mina’s.

The general rule for a multicolumn B-tree is leading equalities, followed by the first range. Those conditions bound a contiguous part of the index. Later key conditions can reject entries without fetching the table row, but do not necessarily reduce how much index the scan traverses. PostgreSQL 18 can sometimes use repeated searches, called a skip scan, when a missing leading condition has few possible values. That is an additional option for the planner, rather than a reason to ignore key order.

Do not put the most selective column first as an automatic rule. If both customer and status are always fixed with equality, either can precede the time range. But an index beginning (status, customer_id, …) splits a customer’s history into separate status runs. A query that omits status loses the simple single run. Design for the questions the application actually sends, including which conditions are optional.

The requested sort has details too. A B-tree can be read backwards, reversing all its key directions. That serves ascending time and ID from the history key when customer is fixed. Mixed directions, missing-value placement and text collation need a compatible index order. Keep them in the query’s contract rather than assuming that every index on the same columns is equivalent.

H2 Few rows, or most of the pages?

Selectivity is the fraction of rows a condition matches. Customer 42 has 60 rows in our generated 60,000-order table: one in a thousand. A lookup can avoid most of the table. A query returning all paid orders has a different shape, even if status also has an index.

Matching half the table can put at least one match on nearly every page. Following index entries to scattered rows then adds index work to a read of most of the table anyway. A sequential scan can be the cheaper route. There is no universal percentage at which an index stops helping: row width, physical arrangement, cache state, storage costs and the columns returned all change the comparison.

PostgreSQL also has a middle route, a bitmap heap scan. It collects row locations from an index, groups them by table page and visits the pages in page order. That avoids repeatedly jumping back to the same page. It loses the original index order, so an ordered result may need a sort afterwards. Separate indexes can sometimes contribute bitmaps that are intersected or combined; they do not behave like a composite key that directly describes one ordered range.

The planner chooses among these routes before running the query. It uses statistics to estimate how many rows will match and a cost model to compare the work. An unused index can therefore mean the planner has sensibly chosen a scan. It can also mean the estimate is wrong. Query execution and bad plans follows how to tell those cases apart.

H2 Read the work the index saved

The native experiment asks for customer 42’s ten newest generated orders since 1 February. It creates access_orders, a separate synthetic table with 60,000 orders, 1,000 anonymous customer IDs and one order a minute from 1 January 2026 UTC. These are test rows, with no lines or payments, and do not extend the shop’s purchase history.

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT order_id, placed_at, status
FROM access_orders
WHERE customer_id = 42
AND placed_at >= timestamptz '2026-02-01 00:00:00+00'
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;

EXPLAIN displays the chosen plan. Its ANALYZE option executes the statement and measures what happens; it is separate from the standalone ANALYZE command that collects statistics. Use it with a query you are prepared to run. Here TIMING OFF removes per-node clock measurements while retaining counts and the total execution time.

Observed on PostgreSQL 18.6 · the same generated history query
| Available additional index | Chosen route | Buffer accesses at Limit

| None | Scan all 60,000 rows, keep 15, sort, return 10 | 984

| (customer_id) | Bitmap: fetch 60 rows, reject 45 by date, sort | 62

| Customer, time, ID | Index scan: return 10, no sort | 13

| Same key, include status; vacuumed | Index-only scan: return 10, no heap fetches | 4

These are buffer accesses, found in memory or read into it, rather than milliseconds or a claim about physical drive reads. The temporary table uses PostgreSQL’s local buffers. Repeated visits can count more than once, and an operating-system cache may satisfy a read. Compare the route and the work, then measure elapsed time under the workload that matters.

The plain customer index saved most of the scan, but it still fetched 45 rows the date condition would discard. The composite key removed that work and the sort. LIMIT 10 mattered: the ordered scan stopped after ten qualifying entries. A sort over unordered input must examine the candidates before it can know which ten come first.

H2 When the index holds the answer

The query returns status, which is absent from the history key. PostgreSQL must fetch each order row for it. Adding INCLUDE (status) stores that value in the index without making it part of the search order.

CREATE INDEX access_cover
ON access_orders (customer_id, placed_at DESC, order_id DESC)
INCLUDE (status);

This is a covering index for this query: it contains every column the query needs. An index-only scan can return values from the entries. PostgreSQL still has to establish that each row version is visible to the transaction. It consults the table unless the page’s visibility-map bit says that every row there is visible to all transactions. Cleanup with VACUUM can set that bit; a subsequent change to the page clears it.

The experiment vacuumed the table before its final measurement, giving Heap Fetches: 0. A busy, frequently updated table can show an index-only plan with many heap fetches. Holding the columns is necessary for this route, but does not promise that every table visit disappears.

Covering also enlarges the index and makes changes to the included value index maintenance. Wide text copied into several covering indexes can cost more than the table visits it saves. Use it for a specific frequent read, after checking that the columns and visibility state allow the intended saving.

H2 Other ways to limit entries

A partial index holds only rows satisfying a declared condition. A pending-order dashboard might use an index on (placed_at DESC, order_id DESC) WHERE status = 'pending'. Finished orders need no entry there. Moving an order out of pending also removes its eligibility. The planner must be able to prove from the query that the required rows lie inside the index’s predicate; a generic prepared plan with an unknown status parameter cannot assume it means pending.

An expression index stores the result of an expression, such as lower(name). It suits a query using that expression and its matching operators. An ordinary index on the original column does not automatically provide the same search. For a time interval, prefer direct typed bounds such as placed_at >= … AND placed_at < … when that expresses the question; wrapping the column in a date conversion can hide the range and introduce a session time-zone dependency.

A unique index additionally rejects repeated keys. PostgreSQL builds one for a primary-key or unique constraint. A foreign key is different: it establishes a relationship and does not automatically create an index on the referencing columns. An index on orders.customer_id can serve the search for a customer’s orders, a join and the lookup needed when deleting a referenced customer. Its usefulness is a workload question even when its correctness rule is already declared.

B-trees are not the right structure for every operator. Words inside documents, array membership, spatial overlap and nearest-neighbour searches need other methods. PostgreSQL index methods and operators matches those questions to their structures. Choosing the method begins with what comparison the query asks the index to make.

H2 Paying for the extra route

Every insert into an indexed table must make the corresponding entries. Updates may change keys, included values or whether a partial-index predicate holds. Full pages may split, and deleted or superseded entries need cleanup. The index also has to be read during construction, backed up and kept in memory if it is hot. Read savings and write costs concern the whole workload, rather than one attractive plan.

In PostgreSQL, an update can avoid new entries through a heap-only tuple, or HOT, update when indexed values do not require maintenance and the new version fits on the same table page. Adding an often-changing column to an index can remove that opportunity. Row versions, storage and cleanup develops why updates leave old versions and when their space can be reused.

Design the set of indexes together. The customer-history key can serve a customer’s newest-order list and a lookup of all their orders. A separate customer-only index may add little, though its narrower entries can still make it cheaper for some scans. Check usage, sizes, constraints and real plans before dropping an apparent duplicate. Never remove the index behind a correctness rule just because one query has another route.

Begin with a query and name the avoided work: scanning unrelated rows, fetching rejected rows, sorting an answer or visiting the table for returned columns. Derive the key and any predicate from that work, check it on representative data, then account for the writes it adds. Live construction and removal have locking and failure behaviour of their own; PostgreSQL schema changes under load handles that operational step.

PostgreSQL index methods and operators
Deep diveAbout 6 minutes AI-generated
An index on a column does not mean every question about that column has an indexed route. Comparing a whole array with another array, finding an element inside it and asking whether its elements overlap another set are different operations. An ordered copy of complete values cannot automatically answer all three.
PostgreSQL makes the distinction explicit. The access method chooses a family of storage and search structures. An operator class tells that method how a particular type’s values and operators fit the structure. Choosing an index therefore starts with the query’s operation, then asks which representation can avoid work.
The general index article established B-trees, composite keys and covering reads. Here we compare the alternatives, then inspect what a candidate-producing index actually saved. The native examples use anonymous generated test rows, separate from the shop’s orders and catalogue.

What is being compared?
A B-tree places complete keys in an order. It is the usual starting point for equality, ordered ranges and queries that can stop early in that order. A hash index instead maps a value to a hash code and supports equality. It does not supply an ordered range or sort. B-tree equality support means that “equality query” alone is not sufficient reason to add a hash index.
Containment needs another representation. Suppose a row holds the array ARRAY['tea','gift']. The condition tags @> ARRAY['gift'] asks whether the left array contains the right array’s elements. A GIN index can extract individual elements and associate each with the rows containing it.
CREATE INDEX method_tags_gin
ON method_rows USING gin (tags);
SELECT row_no
FROM method_rows
WHERE tags @> ARRAY['gift'];
USING gin selects the method. PostgreSQL chooses its default array operator class, array_ops. It knows how to extract elements and how to answer supported array comparisons. Writing the predicate as an arbitrary function call with the same intended meaning does not guarantee the same planner match; use a supported operator or verify the transformed plan.

Finding gift starts at one element’s list, A and C, rather than comparing every complete array. Finding both tea and gift combines the relevant information and retains A. One row contributes to several lists, which is useful for reads and adds maintenance to writes.
The method needs an operator class
The same method can offer several meanings for a type. PostgreSQL’s default jsonb_ops GIN class supports JSON containment, key-existence and selected JSON-path operators. jsonb_path_ops supports containment and the path operators, but not the key-existence operator ?. A smaller, more specific index is useful only if it serves the actual question.
CREATE INDEX catalogue_attributes_path
ON catalogue USING gin (attributes jsonb_path_ops);
-- Eligible operation: attributes @> '{"material":"ceramic"}'::jsonb
-- The same index does not serve: attributes ? 'material'
This is a schema illustration, not a claim that the core products table already has those attributes. JSON and structured alternatives develops the representation and checks both predicates natively.
Text has related choices. In a non-C locale, text_pattern_ops can supply the character-by-character B-tree behaviour needed for a fixed prefix such as name LIKE 'Blue%'. It does not replace a language-aware default index for every ordinary inequality or requested sort. A leading wildcard such as '%mug%' needs a different search; the pg_trgm extension supplies operator classes for that kind of work.
An operator family groups compatible classes and can include comparisons across related types. The practical lesson is to retain the intended types and collation at the query boundary. Casting an indexed column or changing its collation can ask for an operation the stored ordering does not provide. An expression index may be justified when that expression is the intended query, but adding one should follow an explicit meaning.
Overlap, distance and partitions of space
GiST and SP-GiST are frameworks for type-specific search strategies. GiST can organise summaries such as geometric bounding regions; SP-GiST supports partitioning structures such as tries and quadtrees. The method name alone does not tell you which operators, exactness or distance ordering a particular class supports.
A range overlap question uses &&, rather than comparing just the starts. A suitable GiST range class can search those overlaps. A nearest-neighbour query can sometimes use a class’s ordering operator, such as ORDER BY location <-> point '(0,0)' LIMIT 10 for supported point data. This is not a promise that every GiST class accelerates every distance function.
For room reservations, Types and extensions combines range semantics with an enforced overlap rule. For geometry, the coordinate system and distance units must be established before an index is meaningful. For embeddings, vector search owns approximate retrieval and its recall test. Sharing an index framework does not make these result contracts interchangeable.
Summarise physical ranges
BRIN takes a different trade. It stores a summary for a range of adjacent heap pages. A min/max summary can prove that a range contains no possible match. When the query overlaps the summary, PostgreSQL reads the candidate pages and rechecks the rows. The summary does not promise that each candidate actually matches.
That is useful when values track their physical placement. A time-ordered append history can leave old times in old page ranges. If every range instead contains times from across the whole history, its minimum and maximum exclude very little.

The ordered arrangement inspected four candidates for two matches; the mixed arrangement inspected all sixteen. BRIN did not become incorrect. Its summaries became less discriminating. Index size alone would miss this difference.
pages_per_range sets the granularity. Smaller ranges can reject more precisely while requiring more summaries. BRIN also needs newly added ranges to be summarised. Unsummarised ranges cannot safely be ruled out; background or explicit summarisation keeps that work current. Updates that broaden a summary or scatter replacement tuples can weaken an arrangement that began well ordered.
Read candidates and rechecks
The runnable fixture creates 50,000 anonymous rows. Each has a timestamp one minute after the previous one, a 100-character payload and a tags array; every hundredth row has gift. A deterministic modulo permutation produces a second physical arrangement of exactly the same rows.
With only a B-tree on the complete tags array, PostgreSQL scanned the table for containment and discarded 49,500 rows. Adding GIN gave a bitmap route returning the 500 matching rows. The B-tree existed, but it did not supply an element-containment search.
Bitmap Heap Scan on method_rows (actual rows=500.00 loops=1)
Recheck Cond: (tags @> '{gift}'::text[])
Heap Blocks: exact=500
-> Bitmap Index Scan on method_tags_gin
Index Cond: (tags @> '{gift}'::text[])
A Recheck Cond line identifies a condition available for heap rechecking; it does not establish that rows were rejected. This run reported exact heap blocks and no rows removed by index recheck. Bitmap memory pressure can instead turn detailed tuple locations into lossy page entries, requiring more rechecking even for an otherwise precise index.

Pay for the useful search
Read savings still need to earn write costs. GIN can extract many keys from one changed document. Its fast-update mechanism can accumulate entries in a pending list and merge them later; this shifts work rather than eliminating it. Searches may consult the pending list, and a large cleanup can make write latency uneven. Observe that workload before changing the setting.
GiST splits and updates depend on its class and data distribution. BRIN’s small summaries can be cheap to maintain but may become less selective. Ordinary indexed values also affect the HOT opportunity described in processes, pages and row versions; BRIN’s summarising rule is a specific exception, not evidence that index maintenance is free.
Compare the complete route: operators the class supports, rows or pages it admits, required rechecks, the requested order and visibility checks. Then compare insert and update work with and without the candidate on representative data. Live builds, invalid indexes and safe removal are separate operational steps covered by schema changes under load.
A useful choice can be stated precisely: “This GIN class searches array elements for this containment operator”, or “This BRIN summary excludes most old physical ranges for this interval”. “There is an index on the column” leaves the essential question unanswered.

CockroachDB keys, ranges and replication
Deep diveAbout 6 minutes AI-generated
CockroachDB stores SQL rows in an ordered map of keys and values, divides that map into ranges and keeps copies of each range on several nodes. A query can enter through any SQL node. That node finds the ranges holding the required keys and sends work to them.
The unit matters. A node need not own a whole table, and a replica is usually a copy of a range rather than the whole database. One table can spread over many ranges, with different nodes coordinating different parts. This distributes work without asking the application to choose a separate database for each shard.
Follow the shop’s orders through that arrangement. We use the tenant-scoped variant: shop 10 owns orders 101–103, and an order’s primary key is (shop_id, order_id). The drawings expose the ordering and agreement; a separate native check inspects a split on CockroachDB 25.4.17.

A row becomes a key
A SQL primary key identifies a row. CockroachDB also uses its order to organise the row’s primary-index data. Conceptually, a key starts with table and index identifiers, followed by indexed values. Order 103 has a primary key ending in 10 / 103.
The drawing substitutes readable names for byte encodings. Actual encodings preserve the ordering needed by the indexed types; they are not strings formed by joining printed numbers. Keeping that distinction prevents a misleading conclusion such as “103 sorts before 20 because it starts with 1”.
CREATE TABLE range_orders (
shop_id INT NOT NULL,
order_id INT NOT NULL,
customer_id INT NOT NULL,
status STRING NOT NULL,
PRIMARY KEY (shop_id, order_id)
);
CREATE INDEX range_orders_customer
ON range_orders (shop_id, customer_id);
The secondary index has another order. Its leading values group a shop’s entries by customer, so Mina’s 101 and 103 sit together. It also carries primary-key columns needed to locate the rows. Finding Mina through this index may therefore require two kinds of request: read matching secondary entries, then fetch primary rows.
That second request can cross an ownership boundary. Figure 1 starts with the primary entries in one range. Split before 103, then select Mina’s orders. Watch which primary entries the same secondary run reaches.

Symbolic keys, invented range labels and boundaries. Actual byte prefixes contain table and index IDs; families and versions are omitted. Highlighted entries are used by the selected read. A primary split changes ownership units, while the rows and the secondary ordering stay the same.
The split changed neither Mina’s identity nor the answer. It changed the primary ranges involved. Conversely, putting shop_id first in both indexes makes useful ordered prefixes but does not promise that every table and index for shop 10 lives together. Each index occupies its own portion of the key space.
A row need not mean exactly one key-value pair. A column family groups columns stored together as one value; a row with several families has several entries. The default groups a table’s columns into one family. Separating a large, seldom-changing value from a frequently changed one can avoid rewriting them together. Families are a storage choice inside a row’s representation, rather than independent SQL rows or tenant shards.
Where a range begins and ends
A range owns a contiguous interval of the ordered key space. Its start is included and its end excluded. Splitting at (10, 103) leaves earlier primary keys on the left and makes this key the lower bound on the right. Every key still belongs to one interval.
The database tracks intervals and replica locations in range metadata. Nodes cache this information so ordinary requests need not rediscover the map from its beginning. Splits and movement can make a cached route stale; the database refreshes it. Applications continue asking for keys through SQL, rather than retaining a node as the permanent owner of 103.
Growth can cause a range to split. Load can also make a split useful when different hot keys would benefit from separate ownership. A split creates smaller units the cluster can place and balance. It does not add a machine or promise the resulting intervals immediately occupy different nodes.
Below those intervals, each node’s store uses Pebble, a log-structured merge-tree engine, for local key-value storage. Pebble writes sorted files and compacts them. A range is an ownership and replication boundary, rather than a promise that one disk file contains exactly one range. Moving ranges and compacting files solve different problems.
The gateway and the leaseholder
The node accepting a SQL connection is the gateway. It plans the statement, coordinates execution and returns the answer. Some SQL work can run elsewhere. Being the gateway does not imply that its local store holds the requested rows.
A range has a leaseholder, one replica with authority to coordinate its ordinary current reads and writes. A request entering elsewhere is routed to that authority. There are therefore two locations to inspect: where the application connects and where each accessed range is served.
Raft supplies another role, the leader of the range’s replication group. In CockroachDB 25.4, leader leases keep this role with the leaseholder, apart from brief transfers. The roles answer different questions even on the same node: the lease governs serving the range, while Raft leadership coordinates agreement among voters.
Lease movement can shift which replica serves a range without creating another full copy of its data. Replica movement changes where copies live. A useful investigation names which moved. A lease count alone cannot tell whether the busiest leases are evenly spread.
One range, one agreement group
Each replicated range has its own Raft group. With three voting replicas, two make a majority. Receiving a command at the leaseholder does not commit it: the replication protocol needs agreement from enough voters.

An illustrative range command, not a trace or a complete SQL transaction. Replica B is chosen as the first responding follower; no elapsed time is implied. A multi-range purchase still needs a transaction decision after its participant ranges do their work.
One missing follower leaves two possible votes. Two missing followers leave only one. An isolated node cannot create a separate accepted history merely because clients can connect to it. Restoring majority communication is different from adding SQL connections to the isolated side.
A non-voting replica keeps another copy but does not count towards a write majority. It can serve eligible follower reads under a historical-read contract. Adding one is different from adding a vote. Isolation and follower reads develops that contract.
Range agreement is also smaller than transaction agreement. A purchase changes stock, an order and its lines, potentially in several ranges. Each range can replicate its work while the transaction is unresolved. The transaction protocol determines whether those changes form a committed purchase. Transactions and retries follows that additional decision.
Inspect the boundary
The native worksheet creates a projection containing shop 10’s three orders and a customer index. It inspects the primary index, explicitly splits at (10,103), then inspects both indexes and the row’s range.
SHOW RANGES FROM INDEX range_orders@range_orders_pkey
WITH DETAILS;
ALTER TABLE range_orders SPLIT AT VALUES (10, 103);
SHOW RANGES FROM INDEX range_orders@range_orders_pkey
WITH DETAILS;
SHOW RANGE FROM TABLE range_orders FOR ROW (10, 103);
SHOW RANGES exposes interval bounds and voting-replica locations; DETAILS adds information including the leaseholder. These commands need administrative or appropriate zone-configuration privileges. Detailed inspection has a cost: scope it to the table or index being investigated rather than repeatedly fetching every range in a large cluster.
In the recorded run, the primary projection went from one interval to two while retaining all three rows. The right interval began at the split key, and the customer index remained a separate ordered span. The run used one local node. It verifies inspection and the explicit split, rather than automatic splitting, rebalance speed or tolerance of a node failure.
Keep this observation separate from Figure 1’s invented range labels. Range IDs, byte prefixes and current node IDs belong to the run and may differ elsewhere. Reproduce the boundary and unchanged rows, rather than a particular internal number.
The hotspot that remains
Return to the last blue mug. Requests for different order keys can create work in different intervals. Transactions competing to decrement the same P7 stock row still meet at that row’s decision. Splitting the surrounding range cannot turn one stock value into independent allowances.
A growing key has another shape. If every new entry has a larger leading value, writes keep reaching the current end of the index. Splitting older keys creates more intervals while new writes continue at the new end. A secondary index on a growing timestamp can have this problem even when primary keys are well distributed.
Load-based splitting considers whether it can separate useful amounts of work and how many operations would cross the new boundary. More ranges are not automatically better. A scan crossing ten intervals has more coordination to do than the same logical scan crossing one.
Begin with the query and its keys. Identify primary and secondary spans, current leaseholders and voting copies. Then decide whether pressure comes from different keys sharing an interval, a moving index end, a lookup between indexes or contention on one row. Query work and hot ranges develops remedies; Table locality and region survival adds geographic placement.

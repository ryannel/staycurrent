CockroachDB transactions and retries
Deep diveAbout 7 minutes AI-generated
A CockroachDB transaction gives one outcome to changes that may touch several ranges. The replicas of each range agree about their own work; the transaction protocol connects that work into a purchase. The application still has to handle an attempt that must restart, and a commit whose reply never arrives.
These are different situations. A retry error says the current attempt cannot complete as executed. An ambiguous result leaves its outcome unknown. Repeating a stock decrement is safe only when the surrounding protocol knows which logical purchase it is trying to complete.
Rewind before Mina’s order 103. P7 has one blue mug and P3 has twelve packs of tea. The purchase must leave P7 0 and P3 10, create pending order 103 and store its two lines at agreed prices 20.00 and 4.50. Payment is separate. We follow that change through provisional writes, commit and client recovery.

Provisional is a real state
During a transaction, CockroachDB can write an intent: a provisional value associated with the transaction identity. It is more than a value waiting in the client’s memory. It can already be replicated by the range holding the key, while remaining uncommitted transaction work.
The transaction’s state lets a reader encountering an intent establish how to treat it. A committed transaction’s value can be resolved into an ordinary version. An aborted transaction’s intent can be discarded. Work still in progress can create a conflict that requires waiting or conflict resolution. Neither “the bytes exist” nor “this range replicated them” establishes the purchase’s final outcome.
The engine tracks a transaction record and its provisional writes. That internal transaction identity is one attempt’s database identity. It is distinct from order ID 103 and from the application’s stable request key, which must survive a fresh attempt.
This representation also explains why cleanup can continue after success. Removing every intent from every participant need not be on the caller’s critical path once the engine has established an atomic commit condition. A reader that meets unfinished cleanup must obtain the same decision, rather than treating a lingering intent as permission to undo the purchase.
When STAGING means committed
CockroachDB’s Parallel Commits protocol adds STAGING to the transaction record’s states. The record identifies writes still in flight. If all required writes have succeeded, that record and their confirmed presence together establish an implicit commit. The coordinator may acknowledge success before converting the record to COMMITTED and resolving the remaining intents.
STAGING by itself is insufficient. Figure 1 separates the record from the required writes. Compare the all-confirmed history with the one still missing an acknowledgement.

Read the commit condition as text
Writes begin as intents. A STAGING record identifies required in-flight writes. STAGING plus proof that all required writes succeeded establishes implicit commit. Later COMMITTED and intent resolution make that decision cheaper to read. STAGING alone, or one unconfirmed write, is insufficient evidence for success.
A Parallel Commits model, with logical groups of keys rather than observed range placement. Each relevant write must satisfy its range’s replication protocol. The drawing omits fast paths, individual messages and elapsed time; an unconfirmed write is not proved absent or aborted.
At implicit commit the purchase already has its final outcome. The later explicit record makes it cheaper for other work to discover that outcome. It is not an interval during which the database is free to choose abort after acknowledging success.
If a coordinator disappears while state is unresolved, the engine’s recovery protocol checks the required writes and establishes an authoritative outcome. A client cannot perform that recovery by reading a convenient row and guessing. A temporarily absent reply or one stale observation does not prove that a required write never succeeded.
This drawing explains one distributed path. Actual execution has optimisations, including paths whose writes fit one range. It is not a trace of the native fixture below, which runs one local node and checks the SQL error and purchase contract rather than internal Parallel Commits messages.
One transaction is the retry unit
CockroachDB’s default isolation level is Serializable. When it cannot retain a valid execution, it may retry internally or return SQLSTATE 40001, a transaction retry error. An interactive transaction often involves application decisions between statements. The server cannot replay code it does not possess.
Suppose the tea decrement ran, then the attempt received 40001 before the mug decrement. After rolling back, starting a new transaction at the mug statement loses the tea decrement. Inserting both order lines afterwards would record a sale of two packs without taking them from stock. Retrying only the statement that reported the error is therefore the wrong unit.
The native counterexample deliberately forces a real 40001 after changing tea. It rolls back, then executes only the suffix in a new transaction. Order 103 and its lines exist, P7 is 0, but P3 is still 12. The correct retry restarts the claim, reads, decisions and writes together; it leaves P3 10.
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- Claim the stable request identity, as described below.
UPDATE products SET stock = stock - 2
WHERE product_id = 'P3' AND stock >= 2
RETURNING product_id;
UPDATE products SET stock = stock - 1
WHERE product_id = 'P7' AND stock >= 1
RETURNING product_id;
-- Require a returned row for each reservation.
-- Insert order 103, both lines and the request outcome.
COMMIT;
No returned row is a business refusal on this new-purchase path. Roll back every preceding change before reporting it. Do not retain a stock value or successful validation from the aborted attempt: another buyer may have changed the answer before the next snapshot.
The engine can automatically retry some statements and batches while results remain buffered. Once an application has received intermediate results and acted on them, it owns replaying those decisions. Small result sets and fewer round trips can help, but do not remove the need to understand the driver’s actual retry boundary.

Read the SQLSTATE rather than matching a translated error sentence. Keep the object and application meaning too: a duplicate request key belongs to the replay protocol; an unrelated duplicate primary key may be a bug.
Bound retries by attempt count and total elapsed time. Use backoff with jitter, including connection acquisition and cleanup in the request budget. Frequent 40001 errors deserve investigation of contention and transaction scope. Repeatedly replaying a long transaction can multiply the load that caused its conflicts.
If resolution itself cannot finish, retain the key and report a pending or unresolved state. Retry exhaustion does not turn an unknown commit into a known failure. A later status request or reconciliation must continue with the same identity.
Claim the request before taking stock
Mina’s logical purchase uses purchase-mina-103. Every transport retry and transaction attempt reuses that key and a normalised payload containing her identity, both quantities and agreed prices. Reuse with a changed payload is rejected.
The worksheet adds purchase_requests(request_key, payload, order_id) to the scratch schema. Its unique primary key coordinates attempts. The request row, stock, order and lines are written in one Serializable transaction; a new attempt claims the request before taking stock.
INSERT INTO purchase_requests (request_key, payload, order_id)
VALUES ($1, $2, $3)
ON CONFLICT (request_key) DO NOTHING
RETURNING request_key;
-- If no key was returned, do not reserve stock:
SELECT payload, order_id FROM purchase_requests
WHERE request_key = $1;
A successful insertion owns this attempt’s purchase work. If the insertion did nothing, compare the recorded payload and return its matching order, then finish the read transaction. Do not run stock updates on that branch. A retry error anywhere, including commit, restarts this whole protocol.
Overlapping attempts meet at the unique key. An earlier absence lookup is insufficient because the first attempt may still commit. At Serializable, the follow-up lookup can itself require a restart; an unexpectedly absent row is unresolved work, rather than permission to take stock without owning the claim.
The fixture assumes request records are retained and immutable. Its small request relation has no deferred foreign key: the application writes and checks the complete outcome in the same transaction. A production schema should express the relationships it can enforce, and every write path must preserve the atomic protocol. Do not copy PostgreSQL’s deferred-constraint example here; CockroachDB’s constraint support has its own contract.
Retention is part of correctness. If the server forgets an identity while an old retry remains possible, it can treat that purchase as new. Authorise lookups, reject conflicting payloads and reconcile request records together with orders after a restore. A request key cannot recognise history that recovery has removed.
Keep effects outside the replayed code
A retry callback may execute several times. It must not send a confirmation email or charge a card on every execution. Rolling back an intent does not roll back a provider’s work. It also must not update process state as though an uncommitted order were already confirmed.
Record an outbox event with the order if downstream work must follow the purchase. Delivery then has its own identity and recovery contract. The database’s purchase key does not automatically deduplicate a payment provider. Outboxes and database-backed jobs develops that boundary.
CockroachDB also offers a special retry-savepoint protocol for libraries. SAVEPOINT cockroach_restart must be established before database work; a retry rolls back to it and repeats the body. Successful RELEASE SAVEPOINT cockroach_restart commits the work, so it can be the point where an ambiguous outcome occurs. The final COMMIT clears the connection’s state. An ordinary nested savepoint is not interchangeable with this protocol.
Use a driver’s supported implementation or a deliberately tested whole-transaction loop. The worksheet uses the latter. Mixing the two accidentally can place a fresh transaction around only part of the decision or let a library replay a callback containing an external effect.
Repeat the client contract
Download the owned purchase drill. In a separate Python environment, install psycopg[binary]==3.3.6, then run python purchase.py --cockroach /absolute/path/to/cockroach. The script accepts no existing database URL. On the checked macOS environment it starts a private loopback instance, verifies its listening process and cluster identity, and removes its process and store afterwards.
On CockroachDB 25.4.17 it verified the unsafe suffix result, then a complete retry after forced 40001 with exactly one request, order and two lines and the complete stock vector P3 10/P7 0/P9 4. It checked changed-payload rejection and both missing-reply histories: a successful commit deliberately withheld from a simulated caller, and a connection closed before commit. Resolution produced one purchase in each history.
The forced error and withheld acknowledgement are explicit injections. No native 40003, network partition, provider effect or production driver’s automatic replay is claimed. These tests establish the chosen application protocol; they do not measure a distributed commit’s messages or geographic latency.

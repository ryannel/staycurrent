Operating and diagnosing PostgreSQL
Deep diveAbout 9 minutes AI-generated
A PostgreSQL backend can be active without doing useful work. It may be waiting for a transaction, waiting for storage or waiting for the client to read its output. Meanwhile, another request may have no backend at all because it is still waiting to borrow a connection. Counting active queries cannot account for all of these requests.
The useful unit of investigation is a request and the resources it owns. Connect the application’s acquisition and ownership intervals to a particular backend, then follow that backend’s current dependency. An intervention is complete when the request path works again and its interrupted work has a known outcome.
We take the incident method from Diagnosing a database incident into a small PostgreSQL 18.6 experiment. Two requests borrow two pooled connections and block on one product row. A third expires before borrowing. We then cancel a waiter and end the identified holder, observing what each action changes. This is a disposable mechanism test, not a production incident or a pool-sizing benchmark.

Join the request to its backend
An application pool has its own queue. Until it hands a connection to a request, PostgreSQL cannot show that request’s SQL or lock wait. Once borrowed, the connection may outlive several statements and application steps. It returns to the pool only when its owner releases it, regardless of how quickly the final query finishes.
Instrument three boundaries separately: request arrival to acquisition, acquisition to release, and the statements and commit within that ownership interval. Record the connection’s pg_backend_pid() with the borrow interval so a representative slow request can be connected to server evidence. Keep the request identity distinct from the backend identity: a reused connection serves different requests over time.
SELECT pg_backend_pid(), session_user, current_user,
current_database(), current_setting('application_name');
application_name is useful for a service and instance label, such as a checkout worker. It is supplied by the client, so it helps correlation rather than proving ownership or authority. A proxy can also change which server backend handles a client’s transaction. Capture the identity within the scope in which the proxy promises to retain it; a PID from an unrelated health check will not locate the blocked request.
The drill uses a Python queue containing two persistent PostgreSQL client sessions. Its acquisition limit is a real queue timeout; its server work is real SQL through those sessions. It is deliberately a small teaching pool, not a claim about the reset or proxy behaviour of a particular production library.

The server cannot diagnose C’s queue on its own.
Read state and wait together
pg_stat_activity describes sessions. Read its state alongside its wait and transaction age. active means a query is in progress, not that the process is currently running on a processor. idle in transaction means the server is waiting for another client command while a transaction remains open.
SELECT pid, backend_start, usename, application_name,
state, wait_event_type, wait_event,
clock_timestamp() - xact_start AS transaction_age,
clock_timestamp() - query_start AS query_age,
backend_xmin
FROM pg_stat_activity
WHERE datname = current_database()
AND backend_type = 'client backend'
AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;
backend_start helps distinguish a session from a later reuse of its PID. xact_start describes the transaction’s age; query_start describes the current query when active and the last query when idle. The text shown for an idle session is likewise its last command. Do not describe an idle session’s last select as a query that has been executing all afternoon.
backend_xmin is a retained transaction horizon when one exists. A long transaction can be relevant to cleanup, but transaction age alone does not tell you which versions it retains. Establish the actual horizon before making a vacuum intervention. Vacuum and transaction age develops that investigation.

Use the monitoring authority appropriate to the task. Ordinary users cannot inspect every other role’s query details. The drill’s owner can inspect its own sessions; that is separate from proving a production monitoring login has the necessary, limited visibility. Roles, policies and privileged code separates monitoring, signalling and ownership powers.
Follow the dependency to its root
The fixture rewinds a scratch P7 stock row to 1. A maintenance session takes its row lock and inserts an uncommitted note, then goes idle without ending the transaction. A and B each try the conditional stock decrement. These are scratch reservations only: no order, payment or external effect is created, and the collection’s purchase history is unchanged.
-- Maintenance holder:
BEGIN;
SELECT stock FROM products
WHERE product_id = 'P7' FOR UPDATE;
INSERT INTO pending_note VALUES ('uncommitted maintenance note');
-- No COMMIT or ROLLBACK yet.
-- Each borrower:
BEGIN;
UPDATE products SET stock = stock - 1
WHERE product_id = 'P7' AND stock > 0
RETURNING stock;
Ask PostgreSQL for the dependency rather than trying to derive it by matching query text:
SELECT w.pid AS waiter_pid, w.application_name AS waiter,
w.wait_event_type, w.wait_event,
b.pid AS blocker_pid, b.backend_start,
b.application_name AS blocker, b.state AS blocker_state,
b.xact_start
FROM pg_stat_activity AS w
CROSS JOIN LATERAL unnest(pg_blocking_pids(w.pid)) AS x(pid)
LEFT JOIN pg_stat_activity AS b ON b.pid = x.pid
WHERE w.datname = current_database();
Follow the returned blockers too. The recorded run had A waiting on B, and B waiting on the idle holder. Its named waits included tuple and transactionid. A row conflict does not always appear as a visible tuple-lock wait directly against the final holder; PostgreSQL can wait for the transaction that controls the conflicting row version.

The complete recovery, as text
A and B borrow both pooled connections and wait on the same locked product. C expires while waiting to borrow. Cancelling the idle holder leaves its transaction open. Cancelling A stops A's statement; its application rolls back and returns one connection, while B still waits. Terminating the identified holder discards its uncommitted note and frees the lock. B completes its scratch stock decrement and returns its connection. A's fresh retry finds no stock and changes zero rows.
pg_blocking_pids includes both conflicting holders and earlier incompatible requests in a lock queue. A prepared transaction can appear as PID 0 because no ordinary live session owns it. Follow the appropriate recovery authority in that case; do not invent a session to terminate. Locks, contention and deadlocks develops the lock protocol, while Transactions across partitions explains unresolved prepared work.
A modest sampling rate is enough to follow a persistent dependency. Repeatedly querying the lock manager at a high rate adds diagnostic work. Keep observations in autocommit or explicitly refresh the statistics snapshot: a monitoring transaction left open can keep showing the session information it first collected.
Choose what the intervention must end
State the intended effect before sending a signal. Cancelling A should stop A’s current statement. It does not promise to finish the maintenance transaction. Ending the holder should release its transaction resources, at the price of discarding unfinished work and losing that connection.
The first experiment sends pg_cancel_backend to the idle holder. The signal is sent, but the transaction remains open and B remains blocked. There was no running query whose cancellation could finish the transaction. A true return from this function reports signal delivery, not the service outcome we wanted.
Next the experiment cancels A’s waiting statement. A receives 57014 and its session becomes idle in an aborted transaction. Its application executes ROLLBACK before returning the connection. One pool slot is now available; B is still blocked. Returning the connection without transaction cleanup would pass a broken transaction to the next borrower.
For a live action, obtain fresh session evidence and an owner’s decision about the interrupted work. Recheck PID, backend start, database, role, application label, transaction state and the current dependency immediately before signalling. Do not turn a captured PID list into a later automatic termination list.
-- Stop this backend's current query:
SELECT pg_cancel_backend(:checked_pid);
-- End this session, waiting up to 5 seconds for termination:
SELECT pg_terminate_backend(:checked_pid, 5000);
These are intervention fragments, not commands to run against an unidentified PID. PostgreSQL requires signalling authority, and non-superusers cannot signal superuser backends merely through the ordinary signalling role. A separate administration connection needs to remain available when the runtime pool is full.
After checking its exact session identity, the drill terminates the maintenance holder. With the positive timeout, the signalling call waits for termination rather than reporting only that a signal was sent. The subsequent activity check confirms the session is absent. Its uncommitted note is gone. B’s conditional update proceeds, returns stock 0 and commits.
That is the recovery cost as well as the improvement: a session and its unfinished transaction were lost. A complete purchase interrupted around commit would need the request-outcome protocol from Retries when a commit reply is missing. Our holder never submitted a commit, and A’s error is a known statement cancellation; the drill does not silently treat an uncertain commit as an abort.
Check recovery at both queues
A’s fresh retry uses the now available connection and tests stock again. It finds zero, changes no row and rolls back. B is the only successful scratch decrement. Both connections finish clean and return to the pool, while C’s original attempt remains an acquisition timeout.
“The database is responding” would miss these distinctions. Check request outcomes, transaction results, pool ownership and the original dependency. A shorter queue caused by cancelling everyone is a different outcome from serving the required work. Likewise, an available connection is not evidence that stock remains for its next caller.
Restore admission gradually. New requests that borrowed A’s released connection before the holder ended could simply join the same lock queue. Retried requests, reconnections and paused jobs can produce a burst when the obstacle disappears. The native run controls those admissions; a production recovery needs its own bounds and observations.
Prevent recurrence at the owner. End the maintenance transaction promptly, avoid holding it across unrelated application work, and give each relevant wait an explicit budget:
Budgets belong to different intervals

Choose settings for the workload and the pool’s handling of server-closed sessions. A statement deadline cannot end an idle holder whose last statement already finished. An acquisition deadline cannot cancel work another borrower owns. None alone is an end-to-end request deadline.
Raising max_connections would not have shortened the holder’s transaction. Nor would enlarging this pool make the single product accept more independent decisions. Across the fleet, count pool maxima, maintenance, replication and operational connections together. PostgreSQL reserves some connection slots for recovery access; preserve and test that path instead of consuming it with ordinary traffic.
When the evidence points to work instead
The lock investigation was selected because the activity and ownership evidence supported it. If statements instead reach execution promptly and touch excessive rows, take a representative query and parameter set into Reading and repairing PostgreSQL plans. An estimated plan avoids executing the operation; EXPLAIN ANALYZE runs it and must fit a safe diagnostic scope.
Compare executions per interval as well as work per execution. With pg_stat_statements configured, differences in calls, rows, execution time, blocks and temporary writes can distinguish a newly frequent query from one that has become more expensive. Record its reset boundary and query identity. Lifetime totals or an aggregate across unrelated parameter distributions do not describe one incident window.
For storage demand, connect the named waits to I/O, WAL and checkpoint evidence over the same interval. For retained versions, establish what holds the cleanup horizon before increasing vacuum work. For planned DDL, inspect its progress and lock budget through Schema changes under load. A broad maintenance command can add work to a server already short of I/O or free space.
Keep the intervention narrow enough to judge. Write down the predicted observation, stop condition and recovery cost, then compare useful completions, queue age and errors after the change. Preserve a small before/after record that explains why the chosen repair followed from the evidence.
Repeat the owned investigation
Download the pool and blocker drill. Run python3 pool-drill.py --bindir /path/to/postgresql/bin. It uses Python’s standard library and PostgreSQL’s installed clients, creates a private temporary cluster with TCP disabled, clears inherited PostgreSQL connection settings and proves each session reaches its owned endpoint before changing data or sending signals.
The recorded macOS run used Python 3.14.5 and PostgreSQL 18.6. It checks actual queue acquisition, server waits, cancellation state, rollback before reuse, targeted termination, loss of the uncommitted note, a successful scratch decrement and a zero-row retry. All owned sessions and the server are closed, and the temporary cluster is removed. The figure presents those chosen states; it does not execute SQL in the browser. Production authentication, proxy behaviour, fleet concurrency and capacity were not tested by this drill.

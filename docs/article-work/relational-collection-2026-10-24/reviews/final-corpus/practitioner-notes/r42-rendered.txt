PostgreSQL roles, policies and privileged code
Deep diveAbout 9 minutes AI-generated
A PostgreSQL row policy answers a question in an execution context. Change that context, and the same SQL may see different rows. A runtime login can be restricted to one shop while a function it calls executes as an owner, bypasses the policy and reads both shops.
The boundary therefore includes more than table grants. It includes inherited roles, deliberate role switches, object ownership, row policies, function execution rights and the names privileged code resolves. Test the path the application actually takes, including its helpers.
We continue the tenant-scoped catalogue from Database access and least privilege. Shop 10 has the Blue mug, P7 at 20.00. Harbour Tea, shop 20, has its own P7, the Copper mug at 18.00. Actual login sessions on a disposable PostgreSQL 18.6 instance will try both permitted work and deliberate escapes. No price change made for a test survives the drill.

Inheritance is not the same as becoming a role
A role can hold privileges, own objects and belong to other roles. LOGIN permits it to establish a connection; NOLOGIN does not stop members from using its authority. The membership’s inheritance and role-switch options decide how they can do so.
CREATE ROLE shop_owner NOLOGIN;
CREATE ROLE migration LOGIN NOINHERIT;
CREATE ROLE catalogue NOLOGIN;
CREATE ROLE runtime_10 LOGIN;
CREATE ROLE runtime_20 LOGIN;
GRANT shop_owner TO migration
WITH INHERIT FALSE, SET TRUE;
GRANT catalogue TO runtime_10, runtime_20
WITH INHERIT TRUE, SET FALSE;
The migration login cannot automatically use the owner’s rights here. It can deliberately SET ROLE shop_owner, and objects it creates in that context belong to the owner role. Runtime inherits the catalogue group’s grants while retaining current_user = runtime_10 or runtime_20. It cannot switch to the shared catalogue role.
That difference matters when a policy uses current_user. Inheriting a grant does not replace the effective user with the granting group. A permitted SET ROLE does change the effective user. Check indirect membership paths too: an intermediate group can provide authority the direct grant list does not reveal.
The native tests establish three boundaries. Migration’s direct base-table read is refused before it assumes the owner. Runtime can use catalogue privileges but cannot assume catalogue, the other runtime login or shop_owner. Migration can assume shop_owner and acquire its ownership power. These are tested capabilities, rather than conclusions drawn from role names.
Ownership remains powerful even if ordinary table privileges are revoked. An owner can redefine its object and restore grants. Keep runtime outside every owner membership path and outside the credentials or deployment mechanism that can create one. A role-creation or superuser attribute can undermine an otherwise careful object allowlist.
Combine command rights with row rights
The catalogue task can read products, insert their named fields and update price. It cannot delete products, change keys or alter the schema. It needs schema lookup permission separately from table privileges:
GRANT USAGE ON SCHEMA shop TO catalogue;
GRANT SELECT ON shop.products TO catalogue;
GRANT INSERT (shop_id, product_id, name, price), UPDATE (price)
ON shop.products TO catalogue;
Those grants alone expose all four product rows to runtime_10. The tenant key (shop_id, product_id) makes both P7 rows legitimate; it does not authorise the caller to see both. Enable row security and make the policy map the effective runtime identity to its shop.
-- Used in both USING and WITH CHECK:
shop_id = CASE current_user
WHEN 'runtime_10' THEN 10
WHEN 'runtime_20' THEN 20
END
USING restricts existing rows, while WITH CHECK restricts proposed inserted or changed rows. A policy does not grant the command itself. Both the SQL privilege and the policy must allow the operation. The unmatched identity produces no true comparison.
With row security enabled, runtime_10 reads three products and runtime_20 reads one. An explicit shop 20 select through runtime_10 returns no rows; a shop 20 insert is refused. Its permitted shop 10 price update succeeds inside a transaction that the test rolls back. A successful statement returning zero rows is a different result from a privilege error, and both need application handling.
Policy combinations deserve the same care as role combinations. Applicable permissive policies combine with OR; adding another permissive rule is not a way to tighten an existing one. Restrictive policies combine with AND, alongside an applicable permissive grant of row access. Inspect which policies apply to each execution role and command before treating an extra policy as an extra restriction.
Know who can bypass the policy
Table owners normally bypass row security. Superusers and roles with BYPASSRLS bypass it too. FORCE ROW LEVEL SECURITY subjects an ordinary table owner to policies, but does not remove the owner’s authority to change the table or remove those policies.

The experiment then has that same owner disable row security and read all four rows again. It restores enabled and forced security afterwards.
Whole-table commands such as TRUNCATE are outside row-policy filtering. Do not grant them to a runtime task merely because a tenant policy exists. Likewise, a backup, copied dataset or privileged report has its own access path. The policy on ordinary runtime table queries does not automatically govern every copy.
Acceptance as an administrator is therefore inadequate. An administrator applying WHERE shop_id = 10 has tested a query condition. The actual runtime login attempting to request shop 20 tests whether the authority boundary survives a hostile request.
A function adds another execution identity
A normal function runs with its caller’s authority. A SECURITY DEFINER function runs as its owner. This is useful for exposing one narrow operation without giving callers direct access to everything it needs. It also makes the function’s owner, arguments, body and execution grant part of the security boundary.
In the first counterexample, a function owned by shop_owner accepts a shop ID and product ID, then reads that product from the real table. Runtime_10 cannot directly read the Copper mug, but calling this helper with shop 20 returns 18.00. Its owner bypasses the table policy, and its argument lets the caller choose the otherwise forbidden scope.
Binding the argument safely as a value prevents SQL injection; it does not authorise shop 20. A valid integer supplied by an unauthorised caller is still an unauthorised shop. The helper must derive or check scope using an authority the caller cannot replace.
PostgreSQL exposes two useful identities. current_user is the effective execution identity, which becomes the definer inside the function. session_user is the session identity and normally remains the authenticated login through that call. In the repaired native helper the observed pair is runtime_10 / catalogue_code.
We deliberately use one authenticated login per shop in this example. A trusted backend selects that credential; request parameters cannot select another login. If one shared login serves every shop, session_user cannot distinguish those shops. Such a design needs a different trusted scope protocol and pool reset contract. A caller-settable app.shop_id is not an independent authority against arbitrary SQL under that same credential.
A table name can be an input too
A privileged function also needs to know which object it is reading. An unqualified name such as products is resolved through a search path. If an untrusted caller can create an object where the function searches, the caller can influence that lookup without changing a single character of the function body.
The second counterexample has the correct shop scope, derived from session_user, but reads unqualified products. The function sets search_path = shop. That appears specific, yet an existing temporary schema is searched first for relation names unless it is explicitly placed in the path.
Runtime_10 creates its own temporary products relation with a forged P7 value of 999 and grants the unsafe function owner permission to read it. Calling the owner function now returns 999. The real Blue mug still costs 20.00. This is a wrong-object lookup, rather than a change to the stored catalogue.

The complete lookup, as text
Both displayed rows have shop_id 10 and product_id P7. The caller owns a temporary products table containing forged price 999 and has granted the unsafe function owner permission to read it. The unsafe SECURITY DEFINER lookup runs as shop_owner and resolves unqualified products to that temporary table. The corrected lookup runs as catalogue_code, names shop.products explicitly and uses a policy based on the original runtime_10 session identity. It returns the real shop 10 price, 20.00. Neither routine changes the stored catalogue in this comparison.
Qualify important object names and fix the function’s search path to trusted schemas, explicitly placing pg_temp last if it is present. Keep untrusted object creation out of schemas that privileged code searches. A secure path also protects unqualified types, functions and operators; naming the table correctly is only one part of reviewing a larger routine.
For this fixed helper, the table is explicitly shop.products and its search path is just pg_catalog, pg_temp. It needs no user-writable schema in that path. The product ID stays a typed value in static SQL. If a different routine genuinely needs dynamic identifiers, treat identifier quoting and value binding as separate jobs and still authorise the selected object.
Give the helper only the authority it needs
The corrected function belongs to catalogue_code, a separate NOLOGIN role. It is not the table owner, has no bypass attribute and cannot be assumed by runtime. It receives schema lookup and SELECT, with a policy that derives its row scope from the original session identity:
CREATE ROLE catalogue_code NOLOGIN;
GRANT USAGE ON SCHEMA shop TO catalogue_code;
GRANT SELECT ON shop.products TO catalogue_code;
CREATE POLICY code_products ON shop.products
FOR SELECT TO catalogue_code
USING (
shop_id = CASE session_user
WHEN 'runtime_10' THEN 10
WHEN 'runtime_20' THEN 20
END
);
The runtime policy uses current_user because ordinary runtime SQL executes as runtime. The helper policy uses session_user because the helper executes as catalogue_code. These are deliberate rules for different principals; they are not two generally interchangeable spellings of “the user”.
-- Trusted deployment, with authority to assign the function owner:
BEGIN;
CREATE FUNCTION api.catalogue_price(p_id text)
RETURNS numeric
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = pg_catalog, pg_temp
AS $$
SELECT p.price
FROM shop.products AS p
WHERE p.product_id = p_id
$$;
ALTER FUNCTION api.catalogue_price(text) OWNER TO catalogue_code;
REVOKE ALL ON FUNCTION api.catalogue_price(text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION api.catalogue_price(text) TO catalogue;
COMMIT;
PostgreSQL normally grants new functions EXECUTE to PUBLIC. Revoking that default and granting the intended group in the same deployment transaction avoids exposing an intermediate public interface. Callers also need USAGE on the API schema. Runtime receives no CREATE there and cannot replace the function.
Under an actual runtime_10 login, this helper returns 20.00 even with the forged temporary relation still present and app.shop_id set to 20. Runtime_20 gets its own 18.00. A runtime attempt to assume catalogue_code or replace the function is refused. The final catalogue retains all four original rows and prices.
The function is intentionally a read helper. A privileged write routine would also need to enforce its complete business operation, validate values, preserve constraints and concurrency rules, and settle what callers may infer from errors. Reducing the owner’s table powers is useful defence even when the function is intended to expose a narrow interface.
Keep the deployment boundary testable
Inspect the stored function owner, security mode, configuration and execution grants after deployment. Test the actual runtime credentials, including successful calls and attempts outside their scope. A function definition copied into a review document is not evidence that the deployed owner and grants match it.

Check new objects too. Default privileges belong to the role that creates an object; changing ownership later is not equivalent to creating it under that role’s defaults. An ALTER DEFAULT PRIVILEGES rule affects future objects, while existing functions still need their execution grants checked and corrected. Keep the creating role and explicit grants part of a repeatable deployment.
Role revocation also needs the complete authority graph. Removing one direct grant does not remove the same authority inherited elsewhere or granted through PUBLIC. Credential rotation must account for existing pooled sessions, and a revoked query privilege cannot retract results already exported. Authentication, transport verification and credential storage remain separate from the SQL tests here.

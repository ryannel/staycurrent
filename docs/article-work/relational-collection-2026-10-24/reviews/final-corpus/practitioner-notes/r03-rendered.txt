Constraints and tenant boundaries
Deep diveAbout 12 minutes AI-generated
A constraint makes a rule part of the table’s definition. A positive order-line quantity, an order number used only once and a product reference that reaches an existing product are different rules, but they share one useful property: the database can refuse a write that breaks them. The checkout application, an import and an administrator’s SQL all meet the same boundary.
Choosing that boundary starts with the state you want to forbid. “A line has a positive quantity” concerns one row. “No two lines have the same order and line number” compares identities across rows. “This line belongs to an order in the same shop” follows a reference. Each needs a declaration that expresses the whole rule.
The examples use PostgreSQL 18 and the shop from the introduction. Later, a labelled tenant variant lets the application serve two shops. It reveals why a reference that merely reaches an existing row can still be the wrong reference. The figure illustrates reference matching; the downloadable SQL checks their accepted and rejected cases on PostgreSQL 18.6.

Rules about one row
Order 103’s first line contains one blue mug. Its quantity must be present and greater than zero. Those are two separate requirements:
quantity integer NOT NULL
CONSTRAINT
order_items_quantity_positive
CHECK (quantity > 0)
NOT NULL refuses an absent quantity. CHECK evaluates a condition for the row being inserted or changed. Here it refuses zero and negative quantities. Naming the check gives an error a useful identity: order_items_quantity_positive says which rule failed.
As Values, missing data and equality showed, a PostgreSQL check rejects false and accepts true or unknown. A missing quantity makes quantity > 0 unknown, so the check alone would allow it. The two declarations work together.

A check can use several columns of the same row. The shop’s status check allows only pending, paid and cancelled. A table storing two ends of an interval could require its end to follow its start. Neither rule needs to read another row.
The declaration says exactly that much. Allowing the word paid does not establish that the order has enough payments. Requiring stock >= 0 does not establish that every sale reduced stock. A constraint can preserve a property of the stored representation without proving the whole business process correct.
A default is different again. DEFAULT 'pending' supplies a status when an insert omits it; it does not restrict what an explicit value may be. Keep the check if other statuses must be impossible.
One identity, one row
The rule for line identity concerns a pair. Order 103 has lines 1 and 2, and order 101 also has a line 1. The database must permit those repetitions while refusing another line 1 on order 103:
PRIMARY KEY (order_id, line_no)
This primary key makes the pair unique and requires both columns. Separate declarations of UNIQUE (order_id) and UNIQUE (line_no) would mean something else: at most one line per order, and at most one line numbered 1 in the entire table. Composite means that the combination is the identity.
UNIQUE can preserve another identity beside the primary key. If a variant introduces a generated line_id, it still needs UNIQUE (order_id, line_no) and required values for that business identity. Generating different IDs for two inserts does not stop them recording the same line twice. Relations, keys and normalisation develops the choice of keys; constraints carry that choice into every write.
The comparison rule matters too. Uniqueness on text uses the column’s equality rules, so a rule that considers two spellings the same must be reflected in the constrained value or its comparison. Ordinary PostgreSQL uniqueness also permits several missing values. Use NOT NULL for a required identity; choose NULLS NOT DISTINCT when an optional unique value should allow at most one absence.
A preflight query is not the key
For a separate insertion experiment, start with line (103, 1) absent. A checkout writer and an import both intend to create it. Each can ask whether the line exists and get no row before either inserts it. A check in application code has now passed twice.
One possible schedule for two writers of the same line identity
StepCheckout writerImport writer

With an immediate primary key, PostgreSQL’s second insert waits for the conflicting transaction’s outcome. If the first commits and keeps the row, the second is refused. If the first rolls back, the second can proceed. The key’s enforcement includes the overlap that the separate lookup missed.
A disposable PostgreSQL 18.6 run checked the commit case: the second insert waited on the first transaction, then received a duplicate-key error, and one row remained. Without the key, two empty preflight results followed by two inserts left two copies. This is a constraint doing concurrent enforcement, rather than a reason to avoid constraints whenever transactions overlap.
A reference in both directions
An order line’s product_id names a product. A foreign key makes the database preserve that connection:
product_id text NOT NULL
REFERENCES products (product_id)
The parent, products, must offer a unique identity for the reference to target. Its primary key does that. The child, order_items, can repeat P7 on many lines, because each is a separate purchase of that product. The foreign key requires a match; it does not make the child’s product ID unique.
Enforcement works in both directions. Inserting a line for a nonexistent product is refused. Changing a line to that product is refused too. On the parent side, deleting P7 or changing its key would leave existing lines pointing nowhere, so the database must either refuse the change or carry out a declared action that preserves the rule.
With the core schema’s default action, deleting P7 while its lines remain fails. The same is true of deleting order 103 while its lines remain. The foreign keys protect those relationships; they do not decide whether the shop ought to retain an order forever.
What a delete should mean
An order line is a component of an order. If a separate deletion policy allows an order and all its lines to be removed together, the order reference can say so:
FOREIGN KEY (order_id)
REFERENCES orders (order_id)
ON DELETE CASCADE
CASCADE removes the child lines when their order is deleted. Applying that action to the product reference would have a different consequence: deleting a catalogue product would erase lines from old purchases. The references look similar, but the relationships mean different things.
PostgreSQL foreign-key actions when a referenced parent is deleted
ActionEffect on referencing rows
NO ACTION, the defaultThe reference must be valid when checked; otherwise the delete fails.
RESTRICTRefuses deleting a referenced parent without postponing that check.
CASCADEDeletes the referencing rows.
SET NULL or SET DEFAULTChanges the reference; the resulting row must still satisfy its other rules.
SET NULL suits an optional association, rather than the required product on this line. It cannot override NOT NULL. A default is no escape either: a non-missing default reference still needs its parent. ON UPDATE actions make the corresponding choice when the parent’s referenced key changes.
References also need a practical access path. PostgreSQL creates an index for a primary or unique key, but does not automatically create one on the child’s foreign-key columns. Deleting a product requires finding its lines. On a large line table an index on product_id can make that search cheaper; the line primary key already starts with order_id for the order-side search. Indexes and access paths develops that cost.
When the reference may be checked at commit
A default foreign key is not deferrable. If a transaction needs to create a connected group in an order that temporarily leaves a missing reference, declare that foreign key DEFERRABLE and defer its check for the transaction. The final state must still be valid.
CREATE TEMP TABLE deferred_orders (
order_id integer PRIMARY KEY
);
CREATE TEMP TABLE deferred_lines (
order_id integer NOT NULL,
CONSTRAINT deferred_order_exists
FOREIGN KEY (order_id)
REFERENCES deferred_orders
DEFERRABLE INITIALLY DEFERRED
);
Inside one transaction, a line for order 103 can now be inserted before order 103, provided the order is inserted before the check. SET CONSTRAINTS deferred_order_exists IMMEDIATE forces the pending check at that point. Leaving the parent absent still fails; deferral changes when the rule is tested, not what it requires. NO ACTION can participate in this deferred check; RESTRICT does not defer its deletion action. PostgreSQL does not permit deferring CHECK or NOT NULL.
The shop is part of the identity
Now enter the collection’s tenant-scoped variant. The application serves shop 10, the original shop, and shop 20, Harbour Tea. Each shop is a tenant: one customer organisation whose data shares the application with others. Mina is a customer of shop 10; she is not a tenant herself.
Shop 10’s P7 is the Blue mug at 20.00. Shop 20 has its own P7, a Copper mug at 18.00. P7 alone no longer identifies a product. The pair (shop_id, product_id) does. Orders are identified by (shop_id, order_id), and lines by (shop_id, order_id, line_no).
A line therefore needs the shop ID in its references as well as its own key. These small definitions show the identity and reference columns; descriptive order columns and the customer reference are omitted here. The worksheet includes the same-shop customer reference and the line’s quantity and price.

The two lookups, as text
With shop 10, the order reference asks for (10, 103), and finds Mina’s order. The product reference asks for (10, P7), and finds the Blue mug. Both references are satisfied.
With shop 20, the product reference asks for (20, P7), and finds the Copper mug. The order reference asks for (20, 103), which is absent. Order (10, 103) cannot satisfy it, so the order foreign key refuses the attempted line.
At shop 10 the line reaches order (10, 103) and the Blue mug (10, P7). At shop 20 it reaches the Copper mug, but there is no order (20, 103). The order foreign key refuses that attempted line. Finding order 103 in shop 10 cannot satisfy a reference asking for shop 20.
This is more than putting a shop label on a row. Every tenant-owned relationship must carry the scope: an order to its customer, a line to its order and product, a payment to its order. In this variant the order-to-customer reference is FOREIGN KEY (shop_id, customer_id) REFERENCES customers (shop_id, customer_id). Keeping an old unscoped reference leaves that relationship outside the boundary.
PostgreSQL will not accept REFERENCES products (product_id) against the composite product key above: product_id alone is not unique. Adding global uniqueness merely to make that declaration work would prohibit the two valid P7s. Preserve the intended identity, then reference all of it.
Queries need the same meaning. A join on i.product_id = p.product_id would pair shop 10’s mug line with both P7 products. Include i.shop_id = p.shop_id in that match. Foreign keys protect stored relationships; they do not insert the missing condition into a query.
Required and optional pairs
The tenant line’s primary key already requires its shop and order IDs, and product_id is explicitly NOT NULL. Those required values matter. Under PostgreSQL’s default MATCH SIMPLE, a composite reference with any missing component does not require a parent match. A nullable product ID could therefore leave a line with no checked product reference at all.
For a wholly optional composite association, MATCH FULL allows either a complete matching pair or an entirely missing pair; it rejects a half-missing pair. It still permits both values to be missing. The shop’s required product association needs required columns, rather than treating a missing pair as another way to pass.
Integrity does not grant access
The composite foreign keys answer whether stored relationships stay inside one shop. They do not answer whether the caller is entitled to act for that shop. A caller allowed to insert arbitrary values could supply a completely consistent shop 20 order and product pair. Every reference could pass while the caller had no authority over Harbour Tea.
The application must establish the caller’s authorised shop and carry that identity through its requests. Database privileges determine which operations its connection may perform. In PostgreSQL, row security policies can additionally restrict which rows that connection may read or change. These are access rules applied under a particular runtime identity, with their own behaviour for owners and privileged roles.
Keeping those questions distinct makes testing clearer. Try a shop 10 line with a parent from another shop to test integrity. Try a well-formed shop 20 operation through a shop 10 caller to test authority. The latter should fail even though the data would be internally consistent. Database access and least privilege develops runtime authority; PostgreSQL roles, policies and privileged code works through policy tests.
Rules that need a protocol
The shop can declare a positive payment amount and a reference to an order. Neither declaration establishes that an order marked paid has enough payments. If marking an order paid must mean that its payments cover its line total, that rule compares several changing rows, and a write affecting any of them could change its truth.
PostgreSQL row checks are not a supported way to enforce such a rule by reading other rows. Hiding that read in a function does not make it safe: changing a different row does not cause the original row’s check to run again. The same problem applies to a time-dependent check that is expected to become false merely because the clock advances.
Look first for a declarative form the engine supports. A unique key already expresses a cross-row rule. A foreign key expresses an existence rule. PostgreSQL exclusion constraints can forbid certain conflicting pairs, such as overlapping reservations for the same room. These declarations have enforcement designed for their particular relationships.
A class-session capacity limit is different: count several booking rows and keep the total within the session’s capacity. Two transactions can both count a free place before either adds its booking. Each new row can pass all its own checks while the combined result exceeds capacity. A trigger that simply repeats that count can make the same mistake.
Such a rule needs a complete write protocol: which changes belong in one transaction, how competing writers coordinate, what each reads after waiting and which failures require a complete retry. The introduction’s conditional stock update is one protocol for one stock row; it is not a general solution to counting bookings. Transactions and isolation develops these concurrent multi-row rules.
Keep the simpler constraints alongside that protocol. A booking protocol should not also have to remember to reject every missing reference or duplicate identity itself. Declarations preserve the parts they can express; transaction logic carries the remaining business rule.
Trying the boundary
Test a constraint with a valid write and the smallest write that would break its promise. For a composite key, repeat the whole key and also repeat just one component in a valid new combination. For a reference, try an absent parent, a changed child reference and a parent deletion. For tenant scope, use a parent that exists in the other shop; an entirely nonexistent ID would not distinguish a scoped reference from an unscoped one.
Check the returned error as well as the unchanged data. PostgreSQL reports 23502 for a not-null violation, 23514 for a check violation, 23505 for uniqueness and 23503 for a foreign key. Drivers expose the SQLSTATE and relevant object fields. Use those fields and named constraints to recognise an expected refusal, rather than parsing the wording of an error message.
In an explicit PostgreSQL transaction, an ordinary statement error leaves the transaction failed until it is rolled back, or recovered to an appropriate savepoint. The application should turn the refusal into a meaningful result and end or recover that transaction. Repeating the same invalid write is not a useful retry strategy.

It creates temporary objects, checks expected refusals by SQLSTATE and rolls the work back. Counterexamples remove the relevant rule so that the difference is visible.

Regional placement and survival
Deep diveAbout 7 minutes AI-generated
A database can hold copies in three regions and still depend on one of them for every write. It can put a shop’s rows near its application and still send each purchase across a regional link. The location of a copy tells us only part of the story.
To choose a placement, follow one operation. Where does its request enter? Where can its reads be answered? Which replicas must agree to its writes? Which other rows or services must participate? Then remove the failure domain you promised to survive and trace the operation again.
We use the shop collection’s logical region labels: shop 10, the original shop, has home eu-north; shop 20, Harbour Tea, has home eu-west. The third region is us-east. These names carry no assumed cloud topology or measured delay. The diagrams describe chosen placements, not a deployed regional database.

Name the failure you will survive
A server failure, a zone failure and a region failure remove different sets of replicas. Three replicas on three processes on one host might survive a process crash. They share the host’s power, storage and network fate. Putting them in separate zones reduces some shared risks, but it does not make them independent of a region-wide outage.
Start with a concrete promise: “Continue accepting correctly coordinated purchases after any one region becomes unavailable.” This says more than “keep a copy elsewhere”. A surviving copy might contain the data but lack authority to accept a write. It might need an unavailable peer to establish the current state. Data survival and continued service are separate requirements.
For a majority-based group with five voting replicas, a quorum requires three. Spread those votes two in eu-north, two in eu-west and one in us-east. Lose either two-vote region and three remain. Lose the one-vote region and four remain. In each case the survivors contain a majority, if they can communicate.

Read the failure cases
With all survivors connected, losing eu-north or eu-west leaves three votes; losing us-east leaves four. Each single-region loss retains a majority. Losing any two regions leaves at most two votes, so none can form a majority. With all three regions isolated, even five running votes are divided into groups of two, two and one: none has three. Additional unavailable regions cannot improve that.
The placement survives any one region’s loss at the voting level. It does not survive every combination of two region losses. Nor can an isolated two-vote region safely decide that the other three votes have disappeared and start a competing majority. From inside that region, a failed peer and a broken link can look alike.
Majority intersection is the useful property: two groups of three drawn from the same five members must overlap. The consensus protocol uses that overlap, along with durable state and its election rules, to preserve one accepted history. It is not enough for an application to count three arbitrary copies or change the membership independently on both sides of a partition.
Read-only replicas may improve read access without contributing a vote to this decision. Products can also have voting witnesses with different data-storage roles. Count the documented roles of the actual configuration, not every icon called a replica. Spanner’s configuration documentation, for example, distinguishes read-write, read-only and witness roles; a generic copy count cannot replace its configured quorum rules.
A local write can need a remote vote
Suppose the write authority for shop 10’s stock is in eu-north. Mina’s request enters there and finds the row there. The two local voting replicas can still supply only two of the required three votes. A successful quorum-based write must involve at least one vote outside that region.

That remote dependency buys the ability to lose the home region while retaining a majority elsewhere. There is no placement of five votes that puts a majority in each of three disjoint regions. If each region could independently form a majority of one fixed membership, those majorities would not intersect.
This does not give a universal millisecond price. The protocol can pipeline work, the authority can choose suitable peers, and queues, disk writes and transaction participants add their own costs. A slow replica that is not needed for a particular quorum need not set that write’s latency. But a required remote response cannot be removed by moving the SQL gateway closer to the user.
Trace the critical dependencies rather than adding every possible regional round trip. A purchase that touches several replica groups also needs its transaction protocol. Some work can overlap; some must wait for an earlier result. Transactions across partitions separates that decision from the replication of each participant.
Home is a routing and access choice
A home region expresses where a row or table is intended to be accessed efficiently. It is not a statement that every copy lives only there, or that every client reading it is physically nearby. Keep the application gateway, write authority, voting placement and eligible read replicas distinct.
Shop 10’s ordinary purchase path can group its products, orders and lines around its home. Harbour Tea can do the same in eu-west. Here we use the tenant-scoped schema variant: related keys and references include shop_id. Those tenant keys keep the shops’ respective P7 products distinct. Moving the gateway for a shop 10 request to eu-west does not turn it into a Harbour Tea request or move the authoritative shop 10 stock.
Reads have another choice. A nearby replica may serve a certified historical snapshot without contacting the current write authority for every request. That can suit a catalogue whose freshness contract permits it. Mina’s confirmation page must include her successful order, so an older local snapshot may be insufficient. Time, snapshots and distributed reads develops that boundary.
Products package these choices differently. CockroachDB distinguishes regional tables, rows with individual home regions, and global tables aimed at reads across regions. Its database survival goal is a separate setting that affects replication. “Global” is not a promise of cost-free local writes everywhere. The native settings and their interactions belong in CockroachDB table locality and region survival.
A home label also needs an operational meaning. If an application inserts data through a remote gateway, does that choose a different home by default? Does a missing regional predicate cause a wider search? What happens to secondary indexes and uniqueness checks? Check the actual schema and plan instead of assuming that a business field named home_region controls physical placement by itself.
A global rule can cross local boundaries
Now add the collection’s optional global promotion: at most 100 vouchers may be redeemed across all shops. For this illustrative schedule, 99 redemptions have already committed and one voucher remains. A request arrives in eu-north while another arrives in eu-west.
If both regions read a local old value of “one remaining”, each can accept one more redemption. The total becomes 101. Each request can have updated its own local rows correctly; the global rule still failed because nothing coordinated access to the same last entitlement.

The protected entitlement might be represented by a remaining-count row changed conditionally within a suitable transaction, or by uniquely claimed voucher identities. The complete isolation and commit protocol must enforce the rule. Merely wrapping two unprotected local observations in separate transactions does not make the limit global.
Whichever region owns that coordination state, some shop requests will need a remote dependency. Replicating the global row near every shop does not create separate last vouchers. Its copies must still represent one coordinated entitlement. The same is true of shop 10’s last Blue mug: additional replicas of its stock row do not create additional physical mugs.
Sometimes the business can divide rights in advance. A correct allocation protocol could give regions disjoint voucher entitlements, so accepting a voucher consumes a right already owned locally. This changes the coordination schedule: allocation, transfer and reclaiming rights must preserve the total, including during failures. It can also leave a region unable to redeem while unused rights exist elsewhere. That is a different application design, not a consequence of adding replicas.
Test the whole survival promise
A quorum that can form is necessary for this replicated write, but the customer needs more. A surviving application needs a reachable entry point, credentials, routing and all the data groups touched by its transaction. A global index or transaction record with a weaker placement can become the dependency that defeats an otherwise careful stock placement.
Inspect actual placement after the database has converged. Include voting and non-voting roles, authorities, secondary indexes and coordination metadata that the product exposes. A desired policy is not evidence that enough healthy replicas have already reached that state. Topology changes have a transfer interval; Rebalancing and cluster change follows that work.
For the promised failure, track labelled purchases from before the interruption through recovery. Which outcomes were acknowledged? Which timed-out requests have uncertain outcomes? Can a retried request create a duplicate? Confirm that a former authority cannot resume accepting conflicting writes merely because its network returns. A test that only checks whether the port responds misses those obligations.
Measure the remaining system under the intended load too. After losing a region, surviving machines inherit work and may later copy data to restore redundancy. A quorum on paper does not supply CPU, disk or network headroom. Record tail latency, queueing, rejected work and the time spent with reduced redundancy, rather than reporting only a successful single request.
Finally, distinguish regional survival from recovery from a bad committed change. Replicas normally reproduce an authorised deletion or application mistake. They do not supply an independent historical backup merely by living far apart. Similarly, a home region is not a complete data-residency guarantee: check all replicas, indexes, logs, backups and other exported data against the required boundary.
The useful placement decision connects a promise to a path: these operations need this freshness and these shared rules; these votes can survive this failure; these remote dependencies remain. With those explicit, the extra latency and operational cost have a reason the application can defend.

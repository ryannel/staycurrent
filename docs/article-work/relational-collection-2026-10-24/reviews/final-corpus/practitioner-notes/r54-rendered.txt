Where distributed PostgreSQL work runs
Deep diveAbout 9 minutes AI-generated
Shop 10’s receipt for order 103 needs two lines, their captured unit prices and the product names. If all those rows live on one PostgreSQL server, that server can join them and return a small result. If the lines and products live on different servers, someone must bring the matching rows together. The SQL can look almost identical while the work changes substantially.
That difference is the starting point for distributing PostgreSQL. Decide which rows must meet, where their constraints can be enforced, and who is allowed to change them during a move. Then choose the machinery that implements those decisions.

Four arrangements with different owners
A native PostgreSQL partition is a table belonging to a partitioned relation. Partition pruning can avoid irrelevant pieces, and old pieces can be detached as part of a retention policy. Ordinary local partitions still belong to the same database instance. Splitting a table into those pieces does not create independent PostgreSQL servers, a routing service or a failover protocol. The partitioning article follows that lifecycle.
An application shard is a separate database selected by application routing. The application might map shop 10 to database A and shop 20 to B. Each database executes ordinary PostgreSQL transactions over its own rows. The application owns the map and the procedures for changing it.
Citus adds distributed-table metadata and execution to PostgreSQL. In the hash-distributed arrangement considered here, a distribution column places rows into shards, which are ordinary tables on workers. The extension uses that metadata to plan and route work. This is a particular distributed database implementation, with its own supported operations and movement procedures.
A foreign table instead describes a relation reached through a foreign-data wrapper. With postgres_fdw, the relation is on another PostgreSQL server. The wrapper can send parts of a query there, but declaring a foreign table does not decide how tenants are assigned or how ownership changes. Foreign tables can also be used as partitions; their remote access remains a separate concern.

These arrangements can be combined. A tenant shard can contain time partitions. A reporting database can query shards through foreign tables. The useful question is which layer owns each responsibility; combining names does not combine guarantees automatically.
Keep a receipt’s work together
Suppose each shop has its own catalogue. Product P7 is Blue mug at 20.00 in shop 10, but Copper mug at 18.00 in shop 20. Product identity therefore includes shop_id. Order lines need that same shop identifier, both to identify the correct catalogue row and to preserve a useful distribution boundary.
SELECT i.product_id, p.name,
i.quantity * i.unit_price AS line_total
FROM order_items AS i
JOIN products AS p
USING (shop_id, product_id)
WHERE i.shop_id = 10 AND i.order_id = 103
ORDER BY i.line_no;
The captured line prices produce 20.00 for the mug and 9.00 for two packets of tea, totalling 29.00. Joining the current catalogue supplies names; it does not reprice the receipt. Keeping the shop’s products and lines together lets one worker perform the join, enforce its tenant-scoped product references and compute the line results.
Distributing products by product_id and lines by order_id gives no such placement relationship. A shared column in a SQL join is not enough: the placement rules must put the matching rows together. Otherwise the plan needs a remote lookup, a broadcast, a redistribution or some other way to assemble them.
Here is a Citus 13 configuration sketch for already defined, compatible tables. It is documentation-based SQL, not an executed result from the drill below.
SELECT create_distributed_table('products', 'shop_id');
SELECT create_distributed_table(
'order_items', 'shop_id', colocate_with => 'products'
);
The explicit co-location relationship makes the intention visible. Rows for one shop in both tables belong to matching shard placements. It does not create one shard per shop: a hash-range shard can contain many shops. Co-located shards are also related units when placement changes.
Constraint scope follows that grouping. Citus requires primary and unique keys on hash-distributed tables to include the distribution column. A key such as (shop_id, product_id) fits tenant-local uniqueness. It does not establish that product_id is globally unique across shops. Co-located foreign keys likewise need the distribution column in the relationship. A requirement for a single global identifier must be designed separately rather than inferred from local enforcement.
A small table shared by every tenant can sometimes be a Citus reference table, replicated to workers so their joins have a local copy. That buys read locality by adding replicated data and coordinated updates. Replicating a frequently changing, large catalogue merely to avoid choosing a distribution boundary can make the write problem larger.
Inspect the work that actually crossed the boundary
The downloadable drill uses PostgreSQL 18.6 and postgres_fdw 1.2. Two disposable clusters run on one host. The coordinator also holds dataset A, reached through a separately verified loopback FDW connection; the other cluster holds B. There are two foreign-server definitions and two remote connections. This arrangement tests execution and snapshot behaviour, not network latency or independent machine survival.
A holds shop 10’s products and order 103’s lines. B holds shop 20’s Copper mug. The coordinator declares a_products, a_items and b_products, with matching column types. A user mapping determines the remote identity; the private drill uses its own disposable owner, rather than suggesting a production privilege design.
For the receipt query, EXPLAIN (VERBOSE, COSTS OFF) produced one foreign scan whose relation description contained the join:
Foreign Scan
Relations: (public.a_items i) INNER JOIN (public.a_products p)
Remote SQL: SELECT ... FROM
(shop.order_items r1 INNER JOIN shop.products r2 ON (...))
-- includes shop_id = 10 and order_id = 103
This excerpt abbreviates the recorded remote SQL. The join and filters were sent to A; the coordinator sorted the returned lines. The observation is more specific than “FDW pushes down joins”. The tables used the same foreign server and compatible mapping, and this planner chose that remote path. Other expressions, mappings, estimates and costs can change what is shipped.
Now expose both catalogues through a UNION ALL view and ask for every P7. The observed plan had an Append with two foreign scans. Each remote SQL statement filtered on P7 and returned the needed columns; the coordinator combined and sorted Blue mug and Copper mug. The view made access convenient. It did not turn the two catalogues into one tenant-aware routing service.
When diagnosing remote work, read the Remote SQL as well as the local plan. A selective condition applied after transfer can send far more rows than the final result suggests. A local join can consume intermediate rows from both sides. Conversely, a remote join may return only a few rows while doing substantial work remotely. Inspect the remote server’s execution too before attributing a slow query entirely to transport.
A snapshot for each server
A local transaction reaching several foreign servers does not by itself establish one shared snapshot across them. The drill makes this visible with a deliberately ordered scratch price experiment. These temporary updates are not additions to the collection’s price history.
Figure 1 Two consistent remote snapshots can describe no common instant
Observed in PostgreSQL 18.6 with postgres_fdw 1.2. Separate scratch updates; canonical prices are restored afterwards.
Local transaction reads A.A’s remote snapshot sees shop 10 P7 at 20.00.
A commits its update.A’s current price becomes 21.00.
B commits its later update.B’s current shop 20 P7 price becomes 19.00.
The local transaction reads again.A still returns 20.00. First access to B returns 19.00.
Returned pair: A 20.00 · B 19.00Before B reached 19.00, A had already left 20.00.
The local transaction uses Read Committed. After its first read of A, another connection commits A’s change from 20.00 to 21.00. Only then does another connection commit B’s change from 18.00 to 19.00. Re-reading A through the foreign table still returns 20.00; accessing B for the first time returns 19.00.
For ordinary local isolation levels other than Serializable, postgres_fdw uses Repeatable Read remotely. The existing A connection therefore keeps its remote transaction snapshot. B establishes its own snapshot later. Each result is consistent with its server’s snapshot, but the returned pair never existed together: A had already changed before B reached 19.00. Ending the local transaction ends those remote transactions, and the drill restores both canonical prices.
This is a read-boundary result. It is not an experiment in distributed commit. PostgreSQL 18’s postgres_fdw does not support preparing its remote transactions for two-phase commit. If a workflow must atomically change several databases and recover a decision after a participant failure, choose and verify a protocol that provides that property. A transaction-shaped interface is insufficient evidence; transactions across partitions develops the required decision and recovery state.
A hot shop stays together
Co-location deliberately makes a shop one unit of work. It also means that adding workers does not divide that shop’s writes among them. If shop 10 dominates traffic, moving its shard can remove competition from other tenants, but the shop’s own transaction stream still lands together. Extra shard ranges do not divide a single hash-key value.
Measure load per placement and per tenant, including rows, bytes, request rate, contention and the work of joins. Equal shard counts need not mean equal work. A large tenant and many quiet tenants can produce an apparently balanced map with one saturated worker.
Splitting the busy tenant by a smaller entity can spread work, but then a receipt, stock check or uniqueness rule may cross the new boundary. That is a change to the transaction design. Derive the new remote operations and failure cases before treating a finer key as a capacity fix.
Cross-shop reporting has a different shape. It can send partial aggregates to several workers and combine them, provided the aggregate admits the appropriate decomposition. That creates coordinator work and fan-out even when tenant requests remain local. Evaluate both request families; a distribution key chosen solely from an evenly spread column can make the common joins expensive.
Move authority with the data
An application-owned route from shop 20 to B eventually needs to point to A. Copying the Copper mug row is the easy part. The dangerous interval starts when requests continue to write B after that copy, or reach both copies through different cached routes.
The drill adds a scratch revision and operation journal. A restricted runtime role cannot update the tables directly. Its only write function locks the shop’s ownership row, checks an expected epoch and an active flag, then records the operation identifier and increments the revision in the same transaction. Administrative code is trusted to manage ownership. The fence is meaningful because every runtime mutation must pass through that locked guard.

The complete handover, as text
The first copy has revision 0. B accepts one operation, then an in-flight operation reaches revision 2 while holding the ownership row lock. The fence waits for that transaction. A racing writer waits behind the fence and is refused afterwards. With B inactive, the final revision and both accepted operation identifiers are copied to inactive A and compared. A is activated at epoch 2. A new operation reaches revision 3; retrying an already accepted identifier leaves it at 3. B continues to refuse the old epoch. This protocol depends on every runtime write taking the ownership lock.
The first copy at A has revision 0. B then accepts an operation, so A is immediately stale. A second operation runs inside an uncommitted transaction holding the ownership lock. The administrative fence waits for it. A racing runtime call also waits, rather than passing around the guard.
Once the in-flight operation commits, the fence sets B inactive at epoch 2 and commits. The racing old-epoch call is refused. B’s final revision is 2, with two accepted operation identifiers. The drill copies that final state to inactive A and compares product identity, name, price, revision and the operation journal. A refuses writes before activation. Only after those checks does it accept epoch 2.
A new operation advances A to revision 3. Retrying the identifier of the earlier in-flight operation leaves it at 3: the retry history moved with the data. An old request routed to B is still refused. Updating a router cache would not have provided either property on its own.
This is an intentionally bounded, application-managed handover with a write pause. It is not Citus’s rebalancer. A production procedure also needs durable progress and a recovery decision for a crash at each transition. Before activation, it must be possible to determine that no target writer was enabled; after activation, reopening B requires another fenced transfer of all new target state. Keeping the source copy is useful for investigation, but does not make it safe to restore its write authority.
Citus supplies its own online rebalancing operations and co-location rules; use those supported operations for Citus-managed shards. Adding a worker alone does not relocate existing shards. Movement consumes copying, replication and coordination capacity, so test it under the workload it is meant to relieve. The rebalancing article follows the general membership and movement problem.
The choice becomes concrete when you can describe an ordinary request and a move in the same terms: the rows that meet, the node that enforces their rules, the snapshots a reader sees and the authority a stale writer must present. Those are the boundaries to preserve when changing the map.
Download the disposable distribution drill. Run with Python 3 and --bindir pointing to PostgreSQL 18 binaries. It creates only owned private-socket clusters, verifies endpoints, checks the observed plans and handover, then removes its instances. It installs no Citus extension and measures no production throughput.

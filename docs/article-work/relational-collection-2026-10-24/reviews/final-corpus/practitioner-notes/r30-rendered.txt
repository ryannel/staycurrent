Rebalancing and cluster change
Deep diveAbout 7 minutes AI-generated
Adding an empty machine does not immediately add usable database capacity. Existing machines must send it data while continuing to serve requests. The destination must catch up with changes made during the copy. If it will replace a voting replica, the database must also change who is allowed to agree on the history.
Removing a machine follows the same obligations in reverse. Its data, voting responsibilities and active request paths must be accounted for before the hardware disappears. A successful maintenance operation preserves one authoritative history throughout that interval, rather than checking only that the final placement looks balanced.
We follow one replica replacement, then the resource budget around it. The drawings are conceptual schedules and arithmetic. They do not claim native execution, independent physical failures or measured transfer rates.

Separate the things that move
A distributed database has several kinds of movement. Transferring leadership or a read/write lease to an existing up-to-date replica changes where requests are coordinated. Moving a replica copies stored history to a new destination. Splitting a key range changes the units the system can place and schedule. Routing a connection elsewhere changes where the request enters.
These operations can be related, but they solve different problems. Moving authority may relieve an overloaded coordinator without moving all its stored data. Adding replicas may improve resilience or distribute eligible reads without increasing the rate at which one contested row can change. A new gateway can be reachable while the work it forwards still runs on the same busy group.
For the shop, a burst spread across many independent products offers work that can move to different groups. Thousands of buyers competing for the same last P7 mug still need one correct decision about that stock. Splitting a surrounding range does not divide that single row’s entitlement. Sharding and distributed SQL develops the key and load distinction.
Choose the objective before starting: free disk on a particular node, restore a missing failure-domain copy, reduce a hot authority’s CPU, or retire hardware. Equal replica counts are not always the objective. A placement rule can require an uneven count to preserve regional diversity, and equal bytes can still conceal unequal request load.
Copy a starting point, then catch up
Suppose a group currently has voting replicas A, B and C. We want to replace A with D. D needs both a consistent starting state and the history that follows it. Copying arbitrary files while writes continue does not establish either boundary.
A common design transfers a snapshot representing an agreed point, then streams or replays subsequent log entries. The boundary ties the two together: which changes are already in the snapshot, and which must be applied afterwards? If the required tail is no longer retained, the destination may need a newer starting snapshot.
The new copy must not be treated as ready merely because the bulk transfer finished. During that transfer, Mina’s purchase can commit. A snapshot from before it still shows P7 stock 1 and no order 103; the current history has stock 0 and pending order 103. Read the six stages
The current group accepts writes. D starts copying an older snapshot without a vote. The snapshot is installed but misses purchase 103. D catches up, still without independent authority. A committed joint configuration requires a majority of each old and new voter set; authority transfers under the protocol. The final B–C–D configuration commits and A is removed from this group. The purchase survives every stage after its commit.
The drawing’s old state on D is not a second available mug. It is history being brought up to date. Read eligibility, voter readiness and write authority each follow their own protocol conditions. Even a caught-up non-voting copy cannot appoint itself the writer because the operator wants to retire A.
“Caught up” is also a moving target while requests continue. Systems establish a protocol-defined safe point and proceed through the membership operation while replication continues. The diagram pauses at useful teaching states; it does not require a perfectly simultaneous observation of every machine or a permanent zero-byte lag.
Change the voting rule safely
With A–B–C, two votes form a majority. With B–C–D, two votes also form a majority. It is tempting to edit the list on each machine and assume the common members make the transition safe.
But an old majority A–B and a new majority C–D do not intersect. If different machines use different configurations independently, “a majority agreed” has changed meaning midway through the decision. This is why membership belongs to the replicated protocol, rather than to unrelated local configuration edits.
One approach is Raft’s joint configuration: during the transition, decisions require a majority of the old set and a majority of the new set. The protocol commits the transition and then the final configuration. Figure 1 uses that approach; the union’s simple majority is not the joint rule. A–D alone meets neither majority, while B–C meets both.
Other implementations can use constrained changes or different safe transition mechanisms. Follow the database’s supported operation and completion evidence. Do not translate this drawing into manual membership edits, force a new quorum on both sides of a network break, or count a copying learner as an established replacement.
In our schedule, authority transfers to B under the protocol before A leaves. A’s old data can remain on disk afterwards without granting it authority. Returning hardware must rejoin through the current membership and fencing rules; it must not revive an independent old history.
Budget for the copy and the write stream
A transfer consumes resources on both sides. The source reads data and sends bytes; the destination receives, writes and applies them. Checksums, decompression, indexes and storage compaction may add CPU or I/O. Foreground queries, backups and other transfers compete for some of those same resources.
The available rate is therefore not a network interface’s advertised maximum. A source disk already busy with purchases may be the limit. The destination can have spare network capacity while its storage cannot install the snapshot quickly. Increasing transfer concurrency can lengthen queues on both, reducing the progress of each transfer and the customer’s requests.
After the starting snapshot is installed, the destination still needs a surplus over newly generated history to close its gap. Figure 2 fixes the initial backlog at 600 MiB and the incoming stream at 40 MiB/s. Compare applying 30, 60 and 100 MiB/s.

Constant-rate arithmetic for an already installed snapshot, with identical units for incoming and applied history. At 60 MiB/s the 20 MiB/s surplus would clear 600 MiB in 30 seconds; at 100 MiB/s the 60 MiB/s surplus clears it in 10. These are illustrative calculations, not measured database throughput or an operational completion estimate. Copying, stalls, compaction, protocol work and changes in traffic are excluded.
At 30 MiB/s, the destination makes progress through old records while falling farther behind the current end. “Bytes applied is increasing” is therefore a weak completion signal. Track the gap as well as the work done. At an equal incoming and applying rate, the gap remains unchanged in this model.
At 60 MiB/s, only 20 MiB/s closes the existing gap. Dividing 600 by the full 60 would underestimate the catch-up time. If foreground work consumes more of the destination midway through, the surplus shrinks again. A pause can leave the source retaining more history for longer, adding disk pressure there too.
Budget per constrained resource and preserve foreground headroom. A movement limit can reduce immediate customer interference but prolong the time spent below the desired redundancy. A faster repair can shorten that exposure while harming latency. Choose against the failure risk and service objective, then observe both; there is no universally correct throttle.
Do not spend the failure budget twice
A three-voter group can retain a majority with one unavailable member. If maintenance takes A down, B and C are the whole available majority. Taking B down next because “the cluster tolerates one failure” spends a tolerance that is already in use.
The new D is not extra safety until its state and membership meet the relevant conditions. An empty destination, a partial snapshot and a caught-up learner are different from a completed replacement. A control panel showing four processes cannot tell us which group can survive the next interruption.
Check the failure domains throughout the move, not only at the destination. Replacing a replica in a separate region with one beside an existing replica can preserve the replica count while reducing regional survival. Constraints can also make a move impossible: the remaining eligible machines may lack space or the required locality.
Do not make a routine move finish by lowering the required redundancy and treating the missing copy as capacity recovered. That changes the failure promise. If a deliberate temporary reduction is unavoidable, its exact risk, duration and recovery plan must be an explicit operational decision.
Draining and decommissioning have different endpoints
A temporary stop usually tries to move active responsibilities away cleanly while preserving the machine’s stored data for its return. A permanent removal must place its needed replicas elsewhere and finish the associated membership changes. Removing one of its many groups is not completion for the node.
CockroachDB calls these paths draining and decommissioning. Its drain transfers active responsibilities and handles client connections without evacuating all replicas; decommissioning also moves data off the node. Operating and securing a CockroachDB cluster owns the native health checks and removal procedure.
For a planned removal, establish that the remaining eligible destinations have space and foreground capacity. Stop directing new clients to the retiring endpoint as the supported procedure requires. Observe existing transactions and uncertain replies; clients may need to reconnect or retry with their existing idempotency rules.
Wait for the product’s replica, authority and membership completion signals before deleting storage or terminating the host permanently. If progress stalls, investigate the specific remaining group and constraint: an unavailable source, no eligible target, a lagging copy or a resource bottleneck requires a different response. Repeatedly restarting the removal job can discard useful progress without fixing the cause.
Logical shard movement in a distributed PostgreSQL system has similar boundaries but different mechanisms. It may copy rows and stream changes, then perform a controlled routing cutover. Where distributed PostgreSQL work runs owns that implementation. Do not infer a short or lock-free cutover from the word “online”.
Software change is another transition
A rolling software upgrade reduces simultaneous interruption, but “one node at a time” is not sufficient by itself. The participating versions must understand the on-disk formats and protocol messages they exchange. The current replica health and failure-domain budget must permit each restart, and a returning member must catch up before the next step depends on it.
Separate installing new binaries from enabling new cluster features or finalising a new format. Products can support a mixed-version interval while retaining an older compatibility mode, then make a later change that narrows or removes rollback options. Keep the exact supported upgrade path and its finalisation boundary with the native procedure; Upgrading a CockroachDB cluster develops that case.
Schedule other movement consciously during the rollout. A backup, a large backfill and replica catch-up can all be individually safe while collectively exhausting disk or CPU headroom. Pause the next planned change when observed progress or service health invalidates the budget, rather than continuing because a fixed timer expired.
Finish by checking what the change was meant to achieve. Inspect actual placement and remaining constraints, authority distribution, replication gaps and retained history, foreground latency and a labelled application result. For Mina’s purchase, stock and order identities should still represent the same committed decision after the transfer. A balanced diagram or a green process list alone cannot establish that.

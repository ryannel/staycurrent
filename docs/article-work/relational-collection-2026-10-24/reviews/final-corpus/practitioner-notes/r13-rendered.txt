Transactions and isolation
Deep diveAbout 11 minutes AI-generated
A transaction makes a group of changes all or nothing. Isolation governs how that group interacts with other transactions. The distinction matters whenever a decision depends on a value that another writer can change. Two purchases can each be complete and still sell the same last mug.
The introduction fixed that race with a conditional stock update. Here we use it to separate three promises: keeping the purchase together, deciding which committed data a query sees, and making concurrent decisions agree with some order of taking turns. A stable view of the data supplies the second promise. It does not, by itself, supply the third.
The examples use PostgreSQL 18. They begin with the shop’s purchase, then add two instructors covering a tea class. The drawings follow chosen schedules rather than elapsed time or physical storage. A downloadable experiment repeats the relevant schedules on an owned, disposable PostgreSQL instance.

What must stay true
Before choosing an isolation level, state the rule the transactions must preserve. Such a rule is an invariant: a condition that must hold after every successful change. “Stock must never be negative” and “sell no more units than are available” sound similar, but the introductory race showed that they are different.
With one mug left, Mina and Tariq both read stock 1. Each calculates 0. Mina writes 0 and records order 103; Tariq later writes his saved 0 and records order 104. Stock is non-negative throughout, so CHECK (stock >= 0) has no reason to reject either write. Yet two mug lines have been sold from one remaining mug. The rule concerns the relationship between the stock change and the admitted purchases.
Rewind to before order 103. Mina wants one P7 and two P3s. For this purchase to succeed, each product must have enough stock, both reductions must take effect, and the order and both lines must be recorded together.

Order 103 remains pending, with a mug line at 20.00 and two packs of tea at 4.50 each. Taking stock does not mean receiving a payment. The transaction boundary follows the business action being accepted: reserving this purchase, rather than completing every later part of its life.
A row constraint is still valuable. It catches negative stock however a writer arrived there. Primary and foreign keys catch duplicate identities and missing parents. Use those constraints alongside the transaction protocol; each closes a different way to reach an invalid state. Constraints and tenant boundaries develops the rules the schema can enforce directly.
One purchase, one commit
BEGIN starts the transaction. The application then takes stock, inserts the order and inserts its lines. COMMIT accepts the group; ROLLBACK discards it. This is atomicity. A failure after taking the mug must not leave the mug gone while its order is missing.
In PostgreSQL, other connections cannot read those uncommitted row changes. The purchasing connection can read its own work, which lets it continue building the order. When it commits, the changes become available together. A reader’s snapshot may still be older than that commit; atomic visibility does not mean every already-running reader immediately switches to the new state.
Without an explicit transaction, PostgreSQL normally commits each successful statement separately. A successful stock update followed by a failed order insert would then be two separate outcomes. Some drivers manage transactions for you, so check the driver’s behaviour and keep the entire operation on its transaction connection. SQL at the application boundary follows that boundary into application code.
An application can also decide to stop a purchase without a SQL error: perhaps the mug update returned no row. It must roll back explicitly in that case. A database statement error normally leaves a PostgreSQL transaction unable to continue until rollback; a savepoint can provide a smaller rollback boundary when the operation deliberately permits partial recovery. Neither a savepoint nor a caught exception makes a missing stock reservation acceptable.
Keep human input and calls to other services outside this short database transaction. A card provider cannot roll its charge back because PostgreSQL rolled back. A transaction can instead record work to be done later, alongside the order, as Outboxes and database-backed jobs explains. The separate question of a commit whose reply disappears belongs to Retries when a commit reply is missing.
Take stock from the row
The mug’s rule fits in one row. Combine the test and the change in the same UPDATE, deriving the new stock from that row rather than from an application’s earlier copy.
BEGIN ISOLATION LEVEL READ COMMITTED;
UPDATE products
SET stock = stock - 1
WHERE product_id = 'P7' AND stock >= 1
RETURNING stock;
A returned row means that this transaction took the mug. No returned row means it did not. The application must test that result before it does any more purchase work. For Mina, it next reserves two packs of P3 with stock = stock - 2 and stock >= 2, again requiring one returned row. If either reservation fails, roll back the whole purchase, including any reservation that succeeded earlier.
Only after both succeed does it insert order 103 and its two lines, then commit. A later insert error also rolls the stock changes back. These statements describe the transaction recipe; the application’s checks and branches are part of its correctness. Pasting the statements into a straight-line script and committing regardless of their results would omit that protection.
At PostgreSQL’s default level, Read Committed, a competing updater of P7 waits while Mina holds its row lock. If Mina commits stock 0, the waiting update tests stock >= 1 against that updated row and changes nothing. If Mina rolls back, the waiting transaction can take the still-available mug. The lock prevents the two row changes from passing each other, and the condition decides whether the second sale is allowed.
A saved-value write such as SET stock = 0 would still write 0 after waiting. Waiting alone cannot repair its stale calculation. Nor does a stock condition protect an unrelated count across several rows. PostgreSQL’s recheck applies to the target row; it does not refresh every other fact a transaction has read.
With Repeatable Read or Serializable, an update of a row changed since the transaction’s snapshot can fail with a serialization error instead of taking the Read Committed path. The application must handle that outcome too. The isolation level and the update protocol form one design; choosing a stronger level changes the failures the application must expect.
What a snapshot keeps
A snapshot determines which committed row versions a read may see. PostgreSQL keeps older versions so an ordinary query can read a consistent view while another transaction changes the rows. It does not have to wait for the writer’s new values. The physical versions and their eventual cleanup are followed in Row versions, storage and cleanup.
Read Committed gives each ordinary SELECT a snapshot taken when that statement starts. A query that began before Mina committed does not see half of her purchase. But a second query in the same transaction, starting after her commit, can see the whole new purchase. The two statements can legitimately return different stock values.
Repeatable Read keeps one snapshot for the transaction, fixed when it first needs a query snapshot. In the report below, that is the first SELECT. Neither BEGIN nor a setting such as SET LOCAL application_name = 'report' fixes the view: a commit between that setting and the first read can still enter it. Later reads keep the established view, plus the transaction’s own changes. A report can calculate several related results without another writer’s commit entering halfway between its queries.

This distinction also matters for a result split across queries. An order total read before a payment commits and a payment total read afterwards can describe different moments at Read Committed. One statement combining those reads uses one statement snapshot; a multi-query report can use Repeatable Read when it needs a shared view. Choosing that view is separate from deciding whether to allow a purchase.
Isolation names are not a portable list of identical implementations. PostgreSQL’s Repeatable Read uses snapshot isolation and also prevents a repeated query from acquiring new matching rows, often called phantoms. The SQL standard permits weaker Repeatable Read implementations. PostgreSQL also treats Read Uncommitted as Read Committed. Check the engine’s actual promises when moving a protocol.
A rule spread over two rows
A stable snapshot becomes less reassuring when the transaction writes a decision based on it. The shop also runs tea classes. In this separate example, session S502 has two instructors: Ada Lind, I1, and Tomas Ek, I2. Both start on duty. The rule is that at least one must remain.
Use a small duty table with one row per session and instructor. Its primary key is (session_id, instructor_id); on_duty is a non-null Boolean. The two starting rows are (S502, I1, true) and (S502, I2, true). These staff rows are separate from customers and shop orders.
Each instructor’s transaction counts the on-duty instructors. While both are on duty, a count of 2 lets either one leave. Here is Ada’s decision; Tomas’s version names I2 in the update.
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*)
FROM duty
WHERE session_id = 'S502' AND on_duty;
-- Only if the count is greater than 1:
UPDATE duty
SET on_duty = false
WHERE session_id = 'S502' AND instructor_id = 'I1';
COMMIT;
If Ada runs first and finishes before Tomas starts reading, Ada sees 2 and leaves. Tomas then sees 1 and stays. If Tomas runs first, the reverse happens. Either serial order preserves one instructor.
Now let both read 2 before either writes. Ada changes I1 and commits. Tomas changes I2 and commits. Their writes affect different rows, so there is no competing update of the same row to reject. At PostgreSQL Repeatable Read, both can succeed, leaving nobody on duty. This is write skew: transactions read overlapping facts, then make different writes whose combined result breaks their rule.

Serializable
Session S502 starts with Ada and Tomas both on duty. At least one instructor must remain.
Both transactions read the two on-duty rows before either changes one. Ada sees Tomas on; Tomas sees Ada on. Each decides that leaving would keep one instructor.
Ada sets her own row off duty and commits. The committed state now has only Tomas on duty. Tomas’s earlier read still says Ada was on.
With both transactions Serializable, PostgreSQL rejects Tomas’s transaction in this schedule with SQLSTATE 40001. His change does not commit. Tomas remains on duty.
Tomas retries the whole transaction with a fresh snapshot and reruns the decision. Only Tomas is on duty now, so he must stay.
The fresh attempt commits without turning Tomas off. Ada is off, Tomas is on: the same result as Ada leaving first, followed by Tomas deciding to stay.
Chosen two-transaction schedules for S502. At Repeatable Read, each instructor relies on the other’s old on-duty state. The Serializable schedule keeps Ada’s commit and rejects Tomas’s attempt; a real execution need not choose that same victim or reject at that same statement.
There is no serial order that explains both leaving under this decision rule. For Ada to leave, she must read Tomas before he leaves: Ada must come first. For Tomas to leave, he must read Ada before she leaves: Tomas must come first. Those requirements form a cycle. A transaction can keep every read repeatable and still participate in that cycle.
A row-level CHECK cannot express this minimum across the other duty rows. Reading a count does not lock the answer against change, and locking only the row being turned off leaves these two writers on separate rows. A multi-row rule needs protection that covers the facts on which the decision depends.
Serializable keeps the decision
Serializable promises that the successful transactions have an effect consistent with running them one at a time in some order. It need not execute them one at a time. PostgreSQL runs them with snapshots and tracks read/write dependencies, rejecting transactions when necessary to prevent a result that cannot have a serial explanation.
For S502, change both transactions’ opening statement to BEGIN ISOLATION LEVEL SERIALIZABLE. Keep the read, decision and update in that transaction. In the experiment’s schedule Ada commits first, and Tomas receives SQLSTATE 40001, serialization_failure. His change does not commit. Detection may happen during a statement or at commit, so a successful UPDATE alone is not success for the transaction.
Tomas must start a new transaction and rerun the count and the decision, not merely resend the failed update. The fresh count is 1. The correct outcome is to stay on duty, so this new attempt can commit without changing his row. Reusing the earlier count of 2 would throw away the information the retry exists to obtain.
The application still owns the rule. Serializable would happily run an unconditional “turn myself off” transaction after Ada’s transaction; that is a valid serial order of incorrectly designed actions. Every writer capable of reducing cover must participate in the chosen protocol, including administrative and background jobs. If a rule assumes all its competing transactions are Serializable, a bypass at another level needs separate protection.
Serializable has a cost. Tracking dependencies takes work, and rejected attempts repeat work; a busy rule can cause many retries. The application needs a bounded retry policy and a way to report that it could not complete. It must also keep irreversible external effects out of attempts that may be discarded. Retries when a commit reply is missing develops retry control and distinguishes a known serialization failure from an uncertain commit reply.
Explicit locking offers another design: make every decision for the same rule coordinate through a common protected row or set of rows. The lock, the time the snapshot is taken and every participating writer must agree. In particular, waiting for a lock does not refresh an existing Repeatable Read snapshot. Locks, contention and deadlocks works through complete protocols, empty matching sets, waits and lock ordering.
Choosing the protection
The choice starts with the smallest complete rule, then the reads and writes that can invalidate it. A single-row limit often admits a conditional update. A report may need a stable snapshot. A decision across several rows needs a protocol that protects the whole decision.

Check the choice by constructing a failing overlap. Have both buyers read before either writes; have both instructors count before either leaves. Then run the protected version with the same starting data. A test that only runs one transaction at a time cannot distinguish the broken protocol from the sound one.
Also check the transaction boundary in the application. A count before BEGIN, a write on a different connection or a branch that commits after a failed reservation can defeat the design even though each SQL statement is valid. Keep transactions short enough that they do not wait on a person or a remote service, and keep the rule visible enough that a later writer can follow it.
Repeat the schedules
Download the isolation experiment. It uses Python 3’s standard library and PostgreSQL’s installed command-line tools. Run it with python3 run-isolation.py --bindir /path/to/postgresql/bin. It creates its own temporary database cluster, connects through a private local socket, checks its ownership, then removes the cluster after the checks. It does not connect to an existing database. The binary directory must contain initdb, pg_ctl, postgres and psql.
The experiment starts with the displayed products and customers, empty order tables, and the two duty rows. Orders 101 and 102 are historical context and are not replayed as fresh stock deductions. Each purchase race resets to the state before order 103; the snapshot and instructor tests are separate histories.
Checked on PostgreSQL 18.6: rollback left no order or stock effect; the unsafe saved-value writes committed orders 103 and 104 with P7 stock 0; the conditional update waited, then admitted only 103, leaving P3 stock 10 and P7 stock 0. The repeated reads returned 1, 0 at Read Committed and 1, 1 at Repeatable Read. Both instructor changes committed at Repeatable Read; at Serializable the second attempt failed with 40001, and its fresh decision preserved Tomas’s cover. These are outcomes of the recorded schedules on one local engine, not latency measurements or a guarantee about which concurrent attempt always loses.

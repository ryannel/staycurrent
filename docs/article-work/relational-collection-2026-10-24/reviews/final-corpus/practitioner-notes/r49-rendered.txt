Operating and securing a CockroachDB cluster
Deep diveAbout 7 minutes AI-generated
A CockroachDB cluster can answer SQL while operating outside the boundary you intended. An application may be connected as an administrator. The next server failure may make some of its data unavailable. In both cases a successful query is real evidence, but it answers a smaller question than “is this service safe to depend on?”
Operating the cluster means checking those boundaries before an incident makes them matter. Follow two changes to the shop: give its catalogue runtime a secure, limited identity, then permanently remove a node. The examples use CockroachDB 25.4.17. The security fixture uses the explicit tenant-scoped variant: shop 10 has the Blue mug, P7 at 20.00; shop 20 has a different P7, the Copper mug at 18.00.

What the local check establishes
Follow the connection to its authority
Transport security answers who the peer is and who can read the connection. SQL authorisation answers what that authenticated identity may do. Keep both in the acceptance test. An encrypted connection to the wrong server is not the intended service, and a verified server does not make an administrator login suitable for application requests.
A secure self-hosted cluster uses certificates for node and client communication. A client trusts a certificate authority, verifies the server name, and authenticates its own SQL identity. Use the actual DNS name through which the application connects, including a proxy or load balancer where present. The server certificate must cover that name. Disabling hostname verification to make a deployment connect removes the check you needed.
SELECT session_user, current_user;
SHOW GRANTS ON TABLE shop.products;
SHOW ROLES;
session_user identifies the login; current_user identifies the effective role. Test the connection after the pool has performed its setup. A backend running as root does not become a runtime identity because its application name says “catalogue”. Protect node and root private keys especially carefully: they confer broad cluster authority. Keep certificate signing keys out of deployed application configuration.
For rotation, establish new connections with the replacement trust and identity first. Then retire the old credential and account for existing sessions. A pool that continues using an old session has not tested the new connection path. Network reachability, certificate expiry, authentication failures and the connection's effective role are separate observations.
Grant a task, then test the forbidden neighbour
For this fixture, catalogue runtime needs to read products, insert products and update them within one authorised shop. It receives no schema-change, deletion, role-management or cluster-setting task. Table ownership stays with a separate deployment authority. CockroachDB role membership and public grants contribute to effective privileges, so inspect the complete path rather than only the direct grants on a login.
Table privileges alone do not separate the two shops. A runtime with SELECT on the tenant product table can ask for both P7 rows unless another rule restricts rows. A composite primary key prevents the rows being confused as identities; it does not authorise the caller. This is the same distinction established in Database access and least privilege.
CockroachDB 25.4 supports row-level security. In this small identity model the trusted service selects one of two database logins, and neither login can assume the other. The row policy derives its shop from that effective identity:
ALTER TABLE shop.products ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_products ON shop.products
TO runtime_10, runtime_20
USING (shop_id = CASE current_user
WHEN 'runtime_10' THEN 10
WHEN 'runtime_20' THEN 20 END)
WITH CHECK (shop_id = CASE current_user
WHEN 'runtime_10' THEN 10
WHEN 'runtime_20' THEN 20 END);
USING filters existing rows. WITH CHECK checks proposed rows. Ordinary SQL privileges still have to permit the command. The mapping is deliberately fixed by the deployment authority; an unmatched identity gets no true shop comparison. Runtime has no ownership or bypass grant that would defeat the test.
A policy based instead on a session setting that runtime can change has a different boundary. It can help a trusted backend avoid omitted filters, but arbitrary SQL under that credential can choose another setting. Changing application_name to “shop20” must not turn the shop 10 credential into shop 20. This fixture keeps the identity model small enough to test; it does not prescribe one pool per tenant for every service.

Keep both shops populated during the test. An empty forbidden shop can hide a broken boundary. Keep a permitted edit too: a system that refuses everything has not established a usable runtime. Before enabling the policy, the same shop 10 login should expose the other-shop row; that counterexample shows which protection made the difference.
Row policies are not a complete boundary around every copy of the data. Backup and changefeed paths have their own authority and behaviour. Review them, privileged functions, ownership, bypass grants and administrative access separately. A restored table or an export can expose data through a route the ordinary runtime query never uses.
Read health at the range
The connection and permission tests above can be used on their own. Node maintenance needs a further model: Keys, ranges and replication follows SQL data into ranges, their voting copies and the leaseholder that coordinates ordinary access. Then Rebalancing and cluster change follows copying, catch-up and safe membership changes, including the capacity and failure allowance needed while data moves. Use that preparation before the health checks and permanent removal below.
A node is one running CockroachDB process; a range covers part of the keyspace and has replicas on several nodes. Its leaseholder coordinates ordinary current reads and writes, but writes still need a voting majority. Moving that lease changes the serving authority among existing replicas. Moving a replica requires a copy of the range on another node. The replica allocator chooses placements subject to the configured constraints and available capacity; an extra node is useful only if it is an eligible destination.
Availability belongs to each range's replica group. A healthy gateway can execute a query against one range while another range lacks a majority. Start with cluster-wide unavailable and under-replicated range counts, then inspect the affected ranges and their actual placement.
Unavailable means the range cannot serve work because it lacks the required available majority. Under-replicated means it has fewer replicas than its intended configuration. A three-voter range with two available voters can still have a majority, but it has no remaining voter-failure allowance. A non-voting or unfinished copying replica does not add another vote.
SHOW RANGES FROM DATABASE shop WITH DETAILS;
SHOW ZONE CONFIGURATION FOR DATABASE shop;
-- From the operator shell, with the intended cluster's credentials:
-- cockroach node status --all --timeout=10s
Compare intended replication and constraints with available voters, replica localities, leases and destination capacity. Check the age of the status: a stale last report is not current health. Storage exhaustion, a disk stall, an unreachable peer and an impossible placement rule can all prevent repair, but need different actions. The DB Console's Problem Ranges and range report help identify which replica group is affected and why the allocator cannot place another copy.
Do not fix every replication alarm by reducing the configured replica count. That can silence a mismatch by reducing the promise. Restore eligible capacity or connectivity, then verify that the intended placement has returned. Locality labels describe the configured topology; they do not prove separate power, storage or network failures. Table locality and region survival develops that larger placement contract.
Remove a node without spending the next failure twice
A temporary restart and permanent removal need different procedures. Draining moves work such as leases and SQL connections away so a node can stop cleanly; it does not evacuate all its stored replicas. Decommissioning removes a node from the cluster and transfers its replicas elsewhere. The latter can involve substantial copying while ordinary workload continues.
Suppose one range votes on A, B and C. A must leave permanently. D is an eligible destination with spare capacity. Watch when D first contributes a usable replacement, then follow a later failure of B.

A conceptual handover for one three-voter range. Actual CockroachDB placement, membership transitions and headroom must be inspected for every affected range. Four local processes do not establish four independent failure domains.
Stopping A before repair leaves B and C carrying the majority while copying still needs resources. Stopping B too can make that range unavailable. Scheduling two independent maintenance tickets does not give the range two separate failure budgets. Check the overlapping range placements before either ticket starts.
For a planned removal, first repair existing unavailable or under-replicated ranges and check the remaining nodes' storage, placement eligibility and workload headroom. Remove the target from application routing with enough time for the actual load balancer to react. Run decommissioning preflight checks for its verified node ID:
-- Operator shell; substitute the verified cluster and node ID.
-- cockroach node decommission <node-id> --dry-run ...
-- cockroach node decommission <node-id> --wait=all ...
A dry run checks the current cluster; it cannot reserve future capacity or prevent another failure. After starting the real operation, inspect its progress. Do not turn a stalled move into a success by killing the source. Find the blocked placement, unavailable replica or destination resource instead. Wait for replica evacuation and the decommissioned state, confirm the intended ranges and surviving application path, then stop the removed process. Keep monitoring until the promised failure headroom has been restored.
What the local check establishes
The companion native record runs fresh secure processes with private test certificates and stores, verifies the exact binary, connects separately as each runtime and checks the permitted and forbidden operations above. It also inspects voting placement and rehearses a four-node cluster becoming three through decommissioning. Certificate material and stores are removed afterwards.
These are local mechanism checks. All processes share one host and storage failure domain, with a tiny fixture and no production load. They do not measure regional latency, independent machine failure, production survival, certificate rotation through a real proxy or an application's complete connection-pool behaviour. Make those separate acceptance exercises in the deployment you intend to operate.
For the next maintenance operation, Upgrading a CockroachDB cluster adds binary and cluster-version boundaries. Backup and recovery handles the saved history that replication cannot provide after a valid but mistaken write.

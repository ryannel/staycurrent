Upgrading and migrating PostgreSQL
Deep diveAbout 8 minutes AI-generated
A PostgreSQL major upgrade transfers a cluster into a new version’s catalogues and runtime behaviour. A migration may also change its host, layout or operating environment. Both need more than a server that starts: the application must retain the right data, preserve its write rules and know which history to use if the change must be reversed.
There are two different return boundaries. A file-transfer mode can make the old files unsafe to start. Independently, accepting writes on the new authority can make an otherwise healthy old copy too old to serve. Preserving a directory does not preserve the work committed somewhere else afterwards.
We will compare the transfer methods, then follow an owned PostgreSQL 17.6-to-18.6 copy-mode rehearsal. Its shop begins with orders 101–103, their original lines and payments, and stock P3 10/P7 0/P9 4. Anonymous request probes show whether either copy is missing accepted work.

Choose what kind of transfer you need
A minor release keeps the storage format compatible within its major version. The usual procedure replaces executables while the server is stopped and restarts it, following the release notes and packaging procedure. A major upgrade needs a supported transfer into the new version, rather than merely pointing new binaries at an old data directory.
Three routes to a new PostgreSQL major version
RouteWhat movesWhere the cost and responsibility sit
Dump and restoreLogical object definitions and dataRebuild data and indexes; include roles and other globals; close the final source history.
pg_upgradeNew catalogues with compatible existing user data filesA stopped final transfer, compatible binaries/modules and the chosen copy/link/clone behaviour.
Logical replication migrationInitial selected rows followed by ongoing changesTwo live environments, compatible schemas, stream retention and final catch-up; move unreplicated state separately.
Dump and restore is comparatively portable and can support a deliberate schema change. Prefer a suitable newer dump tool that supports the old source, check its warnings and use the matching restore procedure. A single-database dump does not by itself include all cluster roles and tablespace definitions. A consistent dump also omits changes committed after its snapshot, so a final migration cannot simply ignore writers that continued afterwards.
pg_upgrade avoids dumping and reinserting all the user data by creating the new system catalogues and transferring compatible files. It requires old and new installations and compatible cluster settings. It is often simpler when a rehearsed write outage is acceptable.
Logical replication can keep a new destination catching up while the old source serves traffic. That reduces the work left inside the final write pause, but adds a second live system and a stream to operate. Schema, sequences, large objects and other unreplicated state remain separate responsibilities. The physical standby protocol generally does not bridge major versions. Logical replication and change feeds establishes those boundaries.
Check the application as well as the files
Inventory the actual installation before choosing a route: server and client versions, database encodings and locales, checksums, tablespaces, extensions, output plugins, procedural languages and configuration. Include tools that read system catalogues or monitoring views; a major version can change those interfaces even when the application’s main SQL still works.
Read the migration notes for every intervening major release. Then run the application’s important reads and writes on a representative upgraded copy. A faster plan is not proof of equivalent results, and an unchanged result on three rows is not a production capacity test. Parameter handling, authentication, collation, triggers, types and extension operators can all matter outside a simple SELECT.
Extension compatibility needs the extension’s supported upgrade path and correct new-version binaries, not merely a matching extension name. Install the required libraries before the transfer and follow the generated extension or rebuild instructions afterwards. pg_upgrade performs useful checks but cannot establish every external module’s binary and behavioural compatibility. The rehearsal here uses the built-in PL/pgSQL language and no third-party extensions.
A changed collation provider can invalidate the assumptions of existing text indexes. Rebuild affected objects under the intended new ordering, then refresh recorded collation versions as appropriate. Merely refreshing the version metadata suppresses a warning; it does not rebuild or verify the affected indexes.
Defaults can change too. PostgreSQL 18 enables data checksums by default at initialisation, whereas the drill’s PostgreSQL 17 cluster was initialised without them. pg_upgrade requires matching checksum settings. The first preflight deliberately exposed that mismatch; the compatible candidate was initialised with --no-data-checksums. This matches that fixture, rather than recommending disabling checksums for all upgrades.
Rehearse the transfer mode
Use the new version’s pg_upgrade, explicitly identifying both binary directories and both data directories. Give its temporary servers a private socket directory and controlled ports, and keep application clients out. The tool starts short-lived postmasters as part of its work; the destination directory is not just a pile of files being renamed.
/new/bin/pg_upgrade \
--old-bindir=/old/bin --new-bindir=/new/bin \
--old-datadir=/owned/old --new-datadir=/owned/new \
--old-port=55444 --new-port=55445 \
--socketdir=/owned/private/socket --username=drill \
--copy --check
--check reports compatibility problems and required adjustments without doing the conversion. Include the intended transfer-mode option so mode-specific checks run too. A successful preflight is permission to rehearse the actual conversion and acceptance, rather than proof the application already works.
Copy mode, used here, creates separate destination files and leaves the old data files available. It needs room and time for the copy. Clone mode uses supported filesystem copy-on-write cloning, preserving separate logical files while avoiding an immediate full copy; verify support and the later space demands on the actual filesystem.
Link mode uses hard links and needs compatible filesystem placement. Once the upgraded cluster starts, it can modify files shared with the old cluster, making the old copy unsafe to reuse. PostgreSQL 18 also offers swap mode, which has its own earlier destructive boundary during file transfer. Read the installed version’s precise return rules before choosing either. This drill executes copy mode only.
A recent restorable backup and a tested return plan remain necessary even when copy or clone preserves the old directory. They must include the files, keys, configuration and compatible binaries required under the failure being planned for. Neither a second directory on the same host nor a completed preflight proves recovery from losing that host.
Close the old write history
The final transfer needs a known last accepted source history. Stop new admissions, settle in-flight requests and resolve uncertain outcomes before the final capture. Enforce that closure for every writer, including background jobs and administrative paths, rather than relying on a new routing address.
The native fixture gives its application role one permitted scratch-write function. Each call holds a shared lock on an admission gate while checking that it is open and recording its stable request key. Closing the gate updates the same row, waiting for previously admitted calls. A request started behind the closing transaction waits and then receives source fenced.
The controller exercised that race before the upgrade. It recorded the closed shop state and the accepted before-upgrade probe, then stopped the old server. There was no other application writer or restart supervisor in this disposable fixture. In a real deployment, the enforced boundary must cover the actual credentials, processes and controllers that can still accept work.
Keep external side effects in the acceptance model too. A request that committed just before the source closed can have sent a message or initiated a charge. Replaying application work after cutover needs its request identity and provider outcome, rather than an assumption that a connection error meant rollback.
Accept the candidate before opening it
After the compatible preflight, the controller performed the PostgreSQL 17.6-to-18.6 copy upgrade and started the candidate in isolation. Its admission gate remained closed. A test through the application role was refused before acceptance, demonstrating that starting the upgraded server did not automatically open it for new requests.
The acceptance queries compared the products, orders and every line, then recomputed the still-due report by aggregating lines and payments separately. That matters for order 101, whose two lines and two payments would multiply if joined directly before summing. The upgraded result matched the source:

Rows and totals are necessary acceptance checks, not the entire application test. Exercise important write protocols, permissions, error handling and representative plans through the intended driver and pool. Confirm that rebuilt or replacement replicas follow the new authority and that the backup path can protect it.
Follow the post-upgrade instructions generated for this cluster. PostgreSQL 18 transfers most optimiser statistics through pg_upgrade, so it is inaccurate to assume all statistics are always discarded. Some statistics and cumulative counters are not transferred; run the instructed missing-statistics and analysis work. Required rebuild scripts may need to finish before affected relations are used safely.
For a logical migration, candidate acceptance additionally includes all initial synchronisation complete and the final required stream boundary reached after source closure. Compare required data under that closed boundary, align sequence allocators, move unreplicated objects, then establish exactly one new write authority. A “zero lag” value observed while the source still accepts changes is not that final boundary.

Before new writes, both copies contain the same accepted history. A planned return can choose the preserved old copy after closing the candidate and checking the chosen transfer mode.
Change the inspection point. A new accepted request changes the return problem even when every original shop row still compares equal. Link mode has an earlier physical boundary: starting the new cluster can modify files shared with the old one.
Read the return boundary as text
Copy mode preserves separate old files. Before new writes, accepted histories can match. After the new authority accepts after-cutover, the old copy lacks that request. Routing back then loses accepted work unless a tested reverse transfer or reconciliation preserves it. The figure keeps the old writer fenced in both cases.
To expose the trap, the controller stopped the candidate and restarted the preserved PostgreSQL 17 copy in quarantine. Its shop data was still intact and its old gate remained closed. It contained no after-cutover request. A write attempted through the old application route was refused.
The old files were physically usable, but sending traffic back would discard a request already accepted by the new service. That is the logical return boundary. A safe reverse transfer requires a rehearsed way to preserve those new operations, their identities and external effects. Restoring a backup of the old system has the same missing-history problem.
With link mode, there is an additional earlier physical boundary: after starting the new cluster, shared-file changes can make the old directory unusable even before application writes are admitted. Keeping both directory names is not a second independent copy. The file method and the business history therefore need separate return decisions.
A one-way logical subscription also does not become reverse replication when routes are reversed. Establish a supported reverse path ahead of time, account for schema and sequence compatibility, and test the exact return procedure. Keeping two systems writable to make a return seem easier introduces conflicting authority instead.
The complete upgrade rehearsal creates only its own PostgreSQL 17.6 and 18.6 instances, records the checksum counterexample and copy upgrade, tests the admission race, compares the shop and demonstrates the missing new request on the quarantined old copy. It uses Python 3 and both complete PostgreSQL installations at the declared paths. It is a small mechanism test, not evidence of an application’s production downtime or third-party extension compatibility.
Finish with a protected new authority
After opening the destination, update routes and discard stale pooled connections. Check actual read and write requests through the service path, including stable identities for retries. A healthy old connection can still be the wrong authority; a broken one can leave an uncertain commit that needs resolution.
Re-establish redundancy, archives and backups for the chosen new version. Physical standbys need the supported major-upgrade procedure or a fresh base from the new primary. Logical slots and subscription dependencies have version-specific upgrade support and prerequisites; do not assume every slot type or older source is automatically migrated. Keep consumers paused, caught up or resynchronised as the documented procedure requires.
Retire old files and credentials only after the accepted return window and recovery obligations have closed. Record what would happen to newly accepted work if service had to be reversed now. The useful completion condition is a verified new authority with recoverable history, working applications and restored protection, rather than a successful conversion command.

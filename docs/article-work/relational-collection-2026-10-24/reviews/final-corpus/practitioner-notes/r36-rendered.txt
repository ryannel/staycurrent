PostgreSQL WAL, checkpoints and durability
Deep diveAbout 8 minutes AI-generated
PostgreSQL can confirm a purchase before its changed table pages have reached their files. The promise rests on a different write: the purchase’s WAL records, including its commit, must reach durable storage first. After a crash PostgreSQL can replay those records to finish the pages.
Operating that promise means telling several kinds of progress apart. A record can be inserted into memory, written to a file or flushed to durable storage. A checkpoint advances the place from which recovery can start. None of those positions is an application timestamp, and making one advance does not automatically advance all the others.
We will follow a separate drill of Mina’s purchase 103. The starting stock is P3 12 and P7 1. The transaction takes two packs of tea and the last blue mug, then records the pending order and its two lines. After a successful recovery the acceptance condition is the whole purchase: order 103, both lines, P3 10 and P7 0.

Three positions in one log
A log sequence number, or LSN, identifies a byte position in WAL. PostgreSQL prints it as two hexadecimal numbers separated by a slash, such as 0/17F6580. It is useful for asking how far work has progressed and how many log bytes separate two positions. It does not say which customer’s work happened there or when that work committed.
Three functions expose different stages of local progress. pg_current_wal_insert_lsn() reports how far WAL has been inserted into the server’s buffers. pg_current_wal_lsn() reports the current write position. pg_current_wal_flush_lsn() reports the flush position. A file write can still be sitting in the operating system’s cache; a successful flush is the additional durability boundary.
SELECT pg_current_wal_insert_lsn() AS inserted,
pg_current_wal_lsn()        AS written,
pg_current_wal_flush_lsn()  AS flushed;
Other sessions and background processes can move these positions while the query runs. The three calls are observations, rather than an atomic photograph of the entire server. Equal values mean that, at these observations, the write and flush had caught up. They do not prove how long any individual commit waited.

Read the two paths as text
With on: insert purchase records; insert commit record; write WAL to the file; flush WAL; acknowledge. The heap pages may still be old. With off: insert purchase and commit; acknowledge; crash before their WAL is flushed; recover earlier history. An actual process crash may retain file writes in the operating system's cache, so the loss path assumes these records have not reached that cache either.
At the normal reply, the table pages may still be dirty. The backend does not need a checkpoint for each commit. It needs the WAL flush through its commit record. Conversely, finding the purchase’s changed page in a data file would not establish commitment: PostgreSQL can write a page containing an unfinished transaction too. Transaction outcome governs which row versions become visible.
You can subtract positions with pg_wal_lsn_diff(later, earlier) to obtain a byte distance. That distance covers all WAL between the observations, including other transactions and maintenance. It is not the size of Mina’s order, the count of missing rows or a duration. Keep the two positions on the same known WAL history; after recovery forks a timeline, a bare numeric comparison does not identify the branch.
What the commit setting changes
synchronous_commit chooses how much processing a commit waits for before returning success. With no synchronous standbys configured, on, local, remote_write and remote_apply all wait for the local WAL flush. The remote names acquire their additional meaning only when synchronous replication is configured. Physical replicas and promotion follows those remote boundaries.
off permits the reply before the local flush. The WAL writer flushes later; another transaction’s synchronous commit can also flush through earlier records. This is why a quick restart may retain every asynchronous commit in a test. Survival in that run does not turn the setting into a guarantee.
BEGIN;
SET LOCAL synchronous_commit = off;
-- Write rebuildable observations here.
COMMIT;
SET LOCAL limits the setting to the transaction, avoiding an accidental weaker promise on a reused application connection. The shop should not use this choice for its sole record of a confirmed purchase. It might use it for counters it can rebuild from a retained source, provided the replay position survives somewhere appropriate too.
The documented maximum risk window is three times wal_writer_delay, whose default is 200 ms. That describes PostgreSQL’s normal background-flush design, not a measured loss bound for failed storage or a stalled machine. It also does not mean each commit waits exactly 600 ms before becoming durable. A flush can cover it much sooner.
Choosing off preserves recovery consistency: an unflushed tail may disappear as though those transactions had aborted. Turning fsync off removes storage-ordering protection and can leave corrupt files after an operating-system or hardware failure. Turning full_page_writes off removes the normal full-page-image protection against partial page writes. Neither is an interchangeable way to get a cheaper acknowledgement.
The storage path must honour its flush contract in every mode that relies on durability. The native drill below used fsync_writethrough on macOS, with fsync and full_page_writes enabled. That records the selected method; stopping the PostgreSQL processes does not test whether the device survives a real loss of power.
Where a checkpoint leaves recovery
A checkpoint makes the data files sufficiently current that recovery can begin from a later redo position. PostgreSQL writes dirty buffers, ensures the required files are synchronised and records the completed checkpoint. New transactions can continue while that work happens.
The checkpoint’s own record is therefore later than the redo position it remembers. Figure 2 draws that distinction. In the drill, pg_control_checkpoint() reported checkpoint LSN 0/17E52B8 and redo LSN 0/17E5168. At restart, PostgreSQL began redo at the latter.

A conceptual log, read left to right; narrow screens stack it in that same order. The completed checkpoint establishes a safe restart position. It does not mean every page reflects the moment when the checkpoint record was inserted. Other retention needs, including archives and replicas, can still require older WAL.
Automatic checkpoints are driven principally by checkpoint_timeout and WAL generation approaching max_wal_size. More frequent checkpoints generally leave less history to replay, but write active pages repeatedly. With full-page writes enabled, the first modification of a page after a checkpoint normally adds a full-page image to WAL, so frequent checkpoints also add log traffic.
checkpoint_completion_target spreads the page-writing work across the available interval; its default is 0.9. It is not a promise that recovery will finish within that fraction of a minute. Nor is max_wal_size a hard quota on the pg_wal directory. Archive failures, replication slots and other retention needs can keep old segments beyond the normal checkpoint budget.
A healthy checkpoint does not authorise deleting WAL by hand. PostgreSQL decides which segments are reusable from all its retention requirements. If the directory grows, find which requirement is holding it: a failed archive command and a lagging slot require different remedies. Deleting files to force the directory under a target can destroy the recovery chain.
Read the counters before tuning
The question is which work is costing the service time. If commits wait on local WAL flushes, adding checkpoint frequency does not remove that wait. If checkpoints create bursts of page writes, weakening the commit promise is not a diagnosis. Observe the activity and its interval before changing a control.

Statistics can lag activity too, and a long transaction reading them can retain a cached view. Use fresh observations when following a changing incident.
A useful change starts with a stated goal: reduce repeated checkpoint work while keeping an acceptable restart, for example. Record a representative interval, alter one justified setting, then repeat both the workload observation and the recovery drill. Raising max_wal_size without checking available storage and retained-WAL causes merely moves the next failure.
A process crash you can account for
The owned PostgreSQL 18.6 drill created a fresh data directory, disabled TCP listening and connected through its private Unix socket. Before mutations it checked the server’s data directory, port and role. It enabled checkpoint logs, created the pre-purchase rows, then ran an explicit checkpoint. The one-hour checkpoint timeout was deliberate laboratory control, keeping a tiny run away from an unrelated timed checkpoint; it is not a production recommendation.
One durable transaction committed purchase 103 and also inserted a scratch row into an unlogged table. A second connection inserted another scratch row into a normal table but stayed inside an unfinished transaction. The controller waited until that connection was sleeping, then used immediate shutdown on this owned instance and restarted it.

The promise you have tested
The drill established a process-recovery result on this host. PostgreSQL’s shared memory disappeared; the operating system, filesystem cache and storage remained. It did not inject a torn page, reboot the host, detach a volume or demonstrate independent failure domains. A process restart with every row present cannot certify the storage service’s power-loss behaviour.
A service recovery target also extends past PostgreSQL’s “ready” line. Failure detection, restart orchestration, reconnection, uncertain purchase outcomes and cache warming can all delay useful service. Test acceptance from the application’s point of view, retaining stable request identities when a commit reply can be lost.
Finally, crash recovery preserves the surviving committed history, including mistakes. A durable deletion remains a deletion. Losing the data volume needs a separate usable copy. Restoring PostgreSQL to a recovery target starts from that copy and follows the WAL chain to the intended history; Physical replicas and promotion asks which remote copy can safely become the writer.

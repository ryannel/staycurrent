Upgrading a CockroachDB cluster
Deep diveAbout 6 minutes AI-generated
A rolling CockroachDB upgrade changes two versions. Each process runs a particular binary. The cluster also has a compatibility version that governs changes requiring all participating nodes to understand the new state. Replacing the last executable does not by itself establish that the latter transition is complete.
This separation gives an operator a useful acceptance interval. New binaries can run while the cluster retains its earlier compatibility version. If the supported return path remains open, a failed application check can lead back to the earlier binaries. Finalisation begins a different transition, and closes that return path.
Follow a rehearsal from CockroachDB 25.3.7 to 25.4.17. These are pinned versions for the exercise, not a claim that either is the latest release for every deployment. The shop's agreed order lines remain unchanged: order 103 still totals 29.00 before and after each accepted stage.

Establish the supported path
Read the target version's upgrade instructions and release notes before touching a node. CockroachDB distinguishes a patch change within a major release from a major-version upgrade. A major transition needs finalisation and can include backward-incompatible changes. Its allowed predecessors are a product rule, not something to infer from numerical closeness.
The 25.4 procedure accepts its preceding Innovation release, 25.3, or preceding Regular release, 25.2. Other starting versions need their own supported sequence. Review the exact patch requirements, changed defaults, deprecations and features deferred until finalisation. Pin the executable or container digest actually deployed on each node; a tag in a deployment file is not evidence of the running process.
Licensing is another precondition. The current major-upgrade procedure requires a valid licence, and Free/Trial finalisation has telemetry requirements. An installed CCL executable or a new cluster's temporary grace period does not establish entitlement for the production operation. Test the actual licence and upgrade capability in the intended deployment before scheduling it. Do not obtain an apparent success by bypassing that check.
Keep a tested recovery route alongside the rollout. A backup must be restorable with the chosen version and scope; its mere existence does not prove a way back. CockroachDB backup and recovery develops the saved chain and reconciliation of valid work that a restore excludes.
Make the return boundary explicit
Self-hosted clusters normally finalise automatically once every node rejoins with the new binary. If acceptance requires a return interval, disable that policy before the rollout and verify the value:
SET CLUSTER SETTING cluster.auto_upgrade.enabled = false;
SHOW CLUSTER SETTING cluster.auto_upgrade.enabled;
SHOW CLUSTER SETTING version;
The 25.4 documentation recommends cluster.auto_upgrade.enabled. The older cluster.preserve_downgrade_option mechanism also prevents automatic finalisation, but has a different workflow. Choose the documented policy for the exact release and record it; do not rely on an unverified setting left by an earlier operator.
Disabling automatic finalisation does not turn arbitrary old binaries into supported readers of today's storage. It preserves the product's documented pre-finalisation return route for the allowed predecessor. Nor does it promise that a new SQL feature is usable early: some changes remain gated by cluster version.
Watch the binary labels and cluster version separately. The player includes a return rehearsal before the complete rollout, then crosses the finalisation boundary.

Check cluster health and application behaviour before each restart
Before beginning, use the operational health branch: all intended nodes live, no unavailable or under-replicated ranges, and adequate storage, CPU, memory and request capacity while a node is absent. Account for dead nodes that have not been fully decommissioned. A previously degraded range can lose its majority during what otherwise looks like routine one-at-a-time maintenance.
“One at a time” is a limit on the procedure, not a promise about independent failures. A three-voter range with one member stopped is relying on its other two voters. Wait for the returning member and its required health before spending that allowance again. Three processes on one laptop do not prove three independent machine or regional failure domains.
Arrange the actual application route too. Clients connected only to the node being restarted lose their entry point even if the ranges remain available elsewhere. Verify load-balancer readiness handling, alternative endpoints and reconnection. Resolve uncertain transaction outcomes using stable request identities; an upgrade does not make a lost commit reply an aborted transaction.
Drain and stop the chosen node through the supported temporary-stop procedure. Preserve its store. Replace its binary, restart it with its intended configuration and verify that it rejoins the existing cluster. Decommissioning is a permanent-removal operation; it is not a necessary way to restart every node for a binary upgrade.

A query that returns 1 establishes basic SQL readiness. Add the labelled application checks that can expose a semantic regression: representative reads and writes, parameter and result types, transaction retry handling, permissions, prepared commands and important reports. Keep the tested old/new application versions and configuration with their results.
Proceed to the next node only after those checks and current range health permit it. Fixed sleeps are not substitutes for rejoin, replica and application evidence. A backup, schema backfill or replica movement can consume the same headroom, so schedule them as part of the rollout's combined load.
Rehearse the return while it is open
In the native exercise, three fresh local nodes start on 25.3.7 and automatic finalisation is disabled. One node is drained and restarted on 25.4.17. The record captures mixed binary tags, the retained 25.3 cluster version, and the fixture's receipt and transactional scratch-counter acceptance.
That node is then drained again and restarted with 25.3.7 against its same owned store. All three old binaries rejoin and the same application checks run again. This is the return rehearsal: it tests the supported path before finalisation, rather than merely asserting that an old executable is still on disk.
The exercise then rolls all nodes forward, one at a time, preserving the disabled automatic policy. All binary tags can now be new while the cluster version remains 25.3. The fixture is deliberately tiny, uses private loopback connections and has no production traffic; it does not establish an outage or performance budget for a real cluster.
A pre-finalisation binary return leaves the current database history in place. It is different from restoring a backup, which replaces history with an earlier state. Keep that distinction in the incident decision: one route changes software under the current history; the other must account for valid later work and external effects.
Finalise only the accepted state
After every required node and application check passes, and the exact deployment has the required licence and capability, manual finalisation advances the cluster version:
SET CLUSTER SETTING version = '25.4';
SHOW CLUSTER SETTING version;
This runs migration work needed by the new major release. Observe those jobs and their errors, then verify the resulting cluster version. Do not infer completion from every binary saying 25.4. A stalled migration or a node that has not properly left the cluster can prevent the expected final state.
The return limit is the start of finalisation. Once that process begins, rolling back to the previous major binary is no longer supported. If acceptance fails afterwards, investigate a forward repair or the separately rehearsed restore route. Never treat “put the old binary back” as a recovery procedure for a cluster whose format has advanced.
In the native run, the manual command succeeds and the observed cluster version advances from 25.3 to 25.4. The receipt still totals 29.00 and a scratch transaction commits afterwards. The recorded licence setting is empty: this observes the fresh disposable cluster's actual capability, not production entitlement. The exercise does not attempt an unsupported old-binary restart after finalisation. The documented return limit and the deployment's licence obligations still govern a production operation.
Keep current history in a recovery plan
A restore after finalisation can lose more than the mistaken upgrade. If the cluster accepted Mina's purchase after the chosen restore point, that valid operation must be accounted for alongside any other later work. Close and reconcile the history and external effects before authority transfers. A version-compatible backup is one dependency of that process, not proof that it is finished.
End the rollout with separate evidence: running binary versions, finalisation policy and cluster version, range/node health, application acceptance and the current recovery choice. Keep the policy's intended value explicit for the next operation. A successful binary rollout with finalisation deliberately held is a useful intermediate state, but it is not a completed major-version upgrade.

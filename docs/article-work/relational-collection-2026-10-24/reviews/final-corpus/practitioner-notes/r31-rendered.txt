PostgreSQL processes, pages and row versions
Deep diveAbout 7 minutes AI-generated
One PostgreSQL query crosses several kinds of boundary. An application sends SQL to a server process. That process works on pages shared in memory, finds a physical row version and decides whether the requesting transaction may see it. The product ID names a logical product; the address found in an index names a place in storage.
Keeping these roles separate explains several otherwise surprising observations. A second connection can find a page warmed by the first. Updating one price can create another physical tuple without changing the product’s identity. An index can contain an address for an older version and still lead a new reader to the right answer.
We will follow the shop’s blue mug, P7, through a lookup and an update. Its starting catalogue price is 20.00. The later update to 25.00 is a scratch storage experiment, separate from the collection’s dated price-correction history. Order 103’s agreed unit price stays 20.00.

One connection, one backend
The main postgres process accepts connections and starts a server process for each one. That process, usually called a backend, handles the connection’s commands. The client library communicates with it directly after connection setup; the supervisor does not relay each SQL statement.
This is why a connection is a resource even while it has no query to run. Each backend has its own process state and private working memory. A connection pool reuses a smaller set of connections across application requests. It does not make those requests share one SQL transaction unless the application explicitly arranges that.
For a query, the backend parses the SQL, resolves names and types, plans a route through the data and executes it. Prepared statements can reuse some of that work. A plan can also enlist parallel workers, so “one backend per connection” does not mean every query is limited to one process. The connection’s backend still coordinates its result.
SELECT price
FROM products
WHERE product_id = 'P7';

What a page address means
A normal PostgreSQL heap is a sequence of fixed-size pages, usually 8 kB each. A page holds a header, an array of small item identifiers, free space and the tuple bodies themselves. The item identifiers grow from the beginning of the page; the tuple bodies are allocated from the other end. Each item identifier, also called a line pointer, records where its tuple lies within the page.
An address such as (0,1) means page 0, item 1. It does not mean the first product in key order. PostgreSQL can move a tuple body within its page when compacting space and update the line pointer without changing that item number. Moving the row version to a different item or another page changes its physical address.
SELECT product_id, price, ctid, xmin, xmax
FROM products
WHERE product_id = 'P7';
ctid exposes this version’s page-and-item address. xmin identifies the transaction that inserted the version. xmax can describe a deletion or replacement, but also carries locking information. A non-zero value is not sufficient evidence that the row is absent: transaction outcome, tuple flags and the reader’s snapshot matter.
These columns help explain storage; they are poor application identities. An update can change ctid, a rewrite can move every tuple, and a freed address can later be reused. Keep P7 as the product identity. A transaction ID is likewise not a durable business sequence or a substitute for an explicit history record.
Shared pages, private work
Before examining a heap or index page, a backend needs it in shared buffers, PostgreSQL’s shared page cache. A hit finds the page there. A miss reads the page from its file into a buffer slot. The operating system may satisfy that read from its own file cache, so a PostgreSQL buffer read does not prove that the physical drive was accessed.
A query on another connection can reuse the same buffered page. Disconnecting the first client does not empty the shared cache. Conversely, restarting the server loses shared buffers even though its data files remain. A correct server can therefore need substantial reads while its working set warms again.
Private work has a different shape. Sorting candidate rows or building a hash table can need memory belonging to a query operation. The work_mem setting governs many such operations before they spill to temporary files; it is not a single reservation for the whole server or even a hard total for one query. Several nodes, workers and concurrent sessions can multiply that demand. Enlarging shared buffers and enlarging sort memory address different work.
Backends also share coordination structures, including locks. A long transaction can hold a row lock while doing little CPU work. A page being present in memory therefore says nothing about whether a query can proceed without waiting. Operating and diagnosing PostgreSQL connects process activity, waits and memory pressure to an incident.
Which version is visible?
Now a report begins a read-only Repeatable Read transaction and reads P7 at 20.00. Another connection updates the scratch catalogue to 25.00 and commits. PostgreSQL adds a replacement tuple to the heap rather than simply overwriting the old price.
The report retains the snapshot it established at its first query. The writer’s later committed version is outside that snapshot. A fresh reader can see the replacement, while the report continues to see the earlier tuple. Both readers can examine the same heap page and return different prices correctly.

This decision is more than comparing a transaction number with a clock. A snapshot records which transactions were still in progress as well as a visibility boundary; commit and abort status also matter. A transaction can obtain an ID before another and commit after it. The IDs in tuple headers alone do not reveal a total commit order.
At the default Read Committed level, a new statement takes a fresh snapshot. Two successive reads in one transaction can therefore return different committed prices. Repeatable Read was chosen deliberately for the report. Its older view also has a physical cost: the earlier tuple must remain available while a relevant snapshot can need it.
The same-page shortcut
A replacement tuple normally needs new ordinary index entries, even for indexes whose key values stayed the same. Their entries locate physical versions. PostgreSQL can avoid that work with a heap-only tuple, or HOT, update.
Two conditions make the shortcut possible. The update must not change columns referred to by the table’s non-summarising indexes, including expressions and included values. And the replacement must fit on the same heap page. The original index entry can then reach the new version through a same-page chain.

The native check produced all three outcomes. With room and only the primary-key index, page inspection marked the new tuple heap-only. Adding an ordinary price index prevented HOT despite the same-page replacement. Filling a page with four wide scratch rows forced the changed row from (0,1) to (1,1), also preventing HOT despite unchanged indexed values.
A lower table fillfactor reserves space during insertion and can make same-page replacements more likely. It also puts fewer initial rows on each page, increasing the pages a scan may need. It creates an opportunity rather than guaranteeing HOT indefinitely. A continually updated row can exhaust its space while old snapshots retain earlier versions.
Summarising indexes have a special rule. PostgreSQL’s built-in BRIN can allow HOT when one of its referenced columns changes, although the summary may still require maintenance. Treat “no indexed column changes” as shorthand for the ordinary index case, rather than a universal rule covering every access method.
Wide values and later work
A tuple must fit within a heap page. For suitable variable-length types, TOAST can compress wide values or store them in chunks in a separate relation, leaving a reference in the main tuple. This can keep the main heap compact, but the bytes still exist and a query asking for the value may have to retrieve them.
An unchanged out-of-line value can be reused by a replacement tuple. Updating stock therefore need not copy an enormous unchanged description. That is different from saying wide attributes are free: reading, transferring or changing the description has its own cost. Measuring only the main heap misses its TOAST storage and indexes.
Updates also dirty buffered pages and generate WAL. Background writers and the checkpointer help write data pages; the WAL writer handles another part of the log work. A backend can have to write a dirty buffer itself when it needs to reuse that slot. These processes share the server’s work, but none changes which snapshot may see a tuple. WAL, checkpoints and durability follows their ordering and the commit reply.
Finally, obsolete versions need cleanup. HOT chains can be pruned during ordinary page access; vacuum handles broader heap and index maintenance and maintains visibility information. Cleanup cannot discard a version merely because a newer one committed. Vacuum and transaction age follows the boundary that lets old versions go, and the maintenance required even when a table’s visible row count barely changes.

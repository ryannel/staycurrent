Table partitioning and data lifecycle
Deep diveAbout 10 minutes AI-generated
Table partitioning divides one logical table into physical pieces under declared rules. An application can still query the parent table, while the database stores September’s rows in one piece and October’s in another. The useful boundary might let a query skip old data, or let an expired month leave the table without deleting its rows one by one.
Neither benefit follows from making more pieces alone. A query needs a condition that lets the database exclude partitions. A retention operation needs a whole partition whose contents may all leave together. The partition key also affects what uniqueness and references can enforce. Choose the boundary from the work or lifecycle it serves.
We will add a separate relation of request events for the shops, with an event time, shop ID and endpoint. These events are a teaching fixture, not orders, payments or a retained audit of the purchase example. Three monthly UTC partitions let us inspect exact boundaries and a small retention drill on PostgreSQL 18.6.

One name, several physical tables
A partition key determines which piece holds a row. Range partitioning uses non-overlapping intervals of that key. Here occurred_at is a required timestamptz: the instant the request event occurred.
CREATE TABLE request_events (
event_id text NOT NULL,
occurred_at timestamptz NOT NULL,
shop_id integer NOT NULL,
endpoint text NOT NULL,
PRIMARY KEY (occurred_at, event_id)
) PARTITION BY RANGE (occurred_at);
CREATE TABLE events_oct PARTITION OF request_events
FOR VALUES FROM ('2026-10-01 00:00:00+00')
TO ('2026-11-01 00:00:00+00');
In PostgreSQL’s declarative design, the parent has no row storage of its own. Its partitions are tables holding the rows and their indexes. An insert addressed to request_events is routed according to its timestamp. A query addressed to it sees the rows of its attached partitions. The composite primary key in this declaration will need a closer look below.
The lower range bound is included and the upper bound excluded. An event at exactly 1 October 00:00 UTC belongs to October, and one at exactly 1 November 00:00 UTC belongs to November. The boundary belongs to only one partition. An insert with no suitable partition fails unless a default partition accepts it.

The partition month has a declared time basis. A UTC month and a shop’s local calendar month have different endpoints. As Values, missing data and equality explains, a named zone’s calendar boundaries must first be interpreted as instants. Writing explicit offsets here keeps connection settings from silently moving the storage boundary.
Other methods fit other boundaries. A list partition can hold named shop IDs; hash partitioning assigns key values to buckets. Hash buckets spread rows by a hash function, so removing one bucket does not naturally remove the oldest month. Conversely, time ranges put new writes into the current range, so they need not distribute a hot ingestion workload evenly.
Prove that a partition cannot match
Partition pruning excludes a partition whose declared bounds cannot contain a qualifying row. It is a proof from the query’s condition and the partition map. It does not need to inspect every stored timestamp to establish that September cannot contain an October instant.
SELECT event_id, occurred_at, endpoint
FROM request_events
WHERE occurred_at >= timestamptz '2026-10-01 00:00:00+00'
AND occurred_at <  timestamptz '2026-11-01 00:00:00+00'
ORDER BY occurred_at, event_id;
The range overlaps October only, so September and November can be excluded. That says which tables need attention; rows inside October still have to be read and tested. Switch the query in Figure 1 and follow the same reasoning for each partition.

The query from 31 October to 2 November needs two partitions. Its answer crosses their boundary, so neither can be excluded. A query for endpoint /catalogue with no time condition needs all three, even though only three rows qualify. The fact that the table is partitioned by time gives no proof about where an endpoint value occurs.
Expressions matter. Converting occurred_at to its UTC calendar date and testing for October gives the same two rows in this fixture. But PostgreSQL’s demonstrated plan did not turn that expression back into bounds on the timestamp partition key. It scanned all three partitions. Keep direct typed bounds available when they express the question. Partitioning by an expression instead would be a different design, with its own query-matching and constraint consequences.
The native experiment used EXPLAIN (ANALYZE, BUFFERS, TIMING OFF). The direct October query contained only a scan of events_oct. The endpoint query and the date-expression query contained an Append with scans of all three partitions. These four rows make pruning visible; they are not large enough to establish a performance advantage.
When the bounds become known
Some bounds are known while planning, such as the literals above. Others arrive as parameters or from another operation while a query executes. PostgreSQL can prune at execution time too. A generic prepared plan may show several possible child plans before the parameter values select the useful subset.
In the worksheet, a generic prepared query receives the October start and November start as parameters. Its measured plan says Subplans Removed: 2 and executes only the October scan. Other runtime cases can show branches that never execute or different loop counts. Read the measured plan rather than assuming that a child’s presence in an estimated plan proves it read rows.
Pruning does not require an index on the partition key. After excluding partitions, the planner can scan a surviving small piece or use one of its indexes. An endpoint lookup within October might benefit from an endpoint index even though the time bounds performed the pruning. An ID lookup without time bounds might need an index search in every partition. The earlier index article helps choose that route within each surviving piece.
Keys that cross the boundary
The example’s primary key is (occurred_at, event_id). That choice is visible in every reference to an event. It is not a declaration that event_id alone is unique across the whole parent.
PostgreSQL 18 requires a primary-key or unique constraint on a partitioned table to include all partition-key columns, and does not permit expressions in that partition key for this purpose. Its physical unique indexes enforce uniqueness within their own partitions. Including the range key makes equal constrained keys route into the same piece, where a local check can find the duplicate.
Try to create a unique index on event_id alone in the worksheet and PostgreSQL refuses it. Keep the composite key and a second E2 label at a November timestamp is accepted: the pairs differ. A second E2 at the same October timestamp is refused. Adding time to a unique key has therefore weakened the proposed “one E2 anywhere” rule into a different rule about a pair.
This matters especially for the shop’s orders. Its core order_id identifies an order globally within that schema, and lines refer to it. Partitioning orders by placement time and casually changing the key to (placed_at, order_id) would allow the same order ID at different instants. Every referencing line would also need the time, or another authority preserving the original identity. That is a model change, not an incidental performance setting.
If global identity is required, possible designs include keeping an unpartitioned identity relation with a global unique key and partitioning separate detail, or choosing a partition boundary compatible with the required uniqueness. A central identity relation still needs an atomic write and retention protocol; merely adding a registry table does not prove every detail row has exactly one correct identity. Sometimes retaining an ordinary indexed table is the better design.
References have a lifecycle too
A child that refers to this example’s partitioned key carries both values:
CREATE TABLE event_notes (
occurred_at timestamptz NOT NULL,
event_id text NOT NULL,
note text NOT NULL,
FOREIGN KEY (occurred_at, event_id)
REFERENCES request_events (occurred_at, event_id)
);
The reference promises a matching row in the parent relation. Detaching September removes E1 from that relation even if its bytes remain in a separate table. A retained note pointing to E1 therefore cannot simply be ignored.
The native drill creates such a note. PostgreSQL refuses the detach with a foreign-key violation while that note still refers to the parent’s September event. In a second, deliberately unconstrained note table, the same note survives a successful detach with no event visible through the parent. That is the counterexample: a retained string saying E1 does not itself preserve a valid relationship.
A retention policy must decide what happens to related data together. Expire the note too, preserve the event in the relation it references, or move the connected records under a deliberately different archival schema and contract. Co-partitioning related tables can make their dates line up, but it does not by itself make their detach and deletion actions safe. Check the actual foreign keys and operations supported by the engine.
The worksheet explicitly expires the constrained note before detaching its event partition. This is a small chosen policy drill, rather than a recommendation to remove notes whenever a reference blocks maintenance. A database refusal is information about the promise the operation would break.
Remove a month as a unit
Deleting old rows one by one creates row and index work and, in a versioned engine, later cleanup. Removing a whole expired partition can avoid that per-row operation. But the unit is the entire piece. If even one row must remain available there, the partition has not wholly expired under that policy.
Suppose this drill’s retention rule permits September’s request events to leave the operational parent. The September upper bound is 1 October UTC, so every event in it occurred before that instant. This is an illustrative cutoff; the article prescribes no retention duration for real request data.
Check that rule against every row class in the partition: holds, exceptions, ongoing references and correction requirements. If some events must stay, either choose another storage boundary or move the exceptions under a verified policy before removing the rest. A row’s age alone does not decide what the application is obliged to retain.

An illustrative retirement sequence. September begins attached; after a checked detach, the parent has three rows and the separate table still has E1. Dropping that table is a later policy decision. The worksheet verifies detach and reattach, including a reference that prevents detach; it does not measure an archival service or erase backups.
ALTER TABLE request_events
DETACH PARTITION events_sep;
After the checked detach in PostgreSQL, querying request_events returns three rows. Querying events_sep directly still returns E1. Detach changes membership of the parent; it does not erase the table, archive it elsewhere or make it unreadable. The next action might be a verified export, a period of restricted retention, reattachment or a separate drop.
Decide the point after which reattachment is no longer an acceptable undo. A pending policy change or an incomplete archive check may call for retaining the detached table. Once a separate drop happens, recovery depends on another copy and its procedure. Exporting without checking counts, identities, schema and the ability to read the result has not established an archive.
Partition operations also take locks. PostgreSQL’s ordinary detach takes an exclusive parent lock; DETACH … CONCURRENTLY uses a less restrictive parent lock but has additional restrictions and phases, including completion after interruption. It is not a universal “no blocking” switch. Schedule and test the appropriate native operation under the expected readers and writers. Live schema changes and backfills develops change protocols under traffic.
Late data and the next month
Dropping the old route does not stop an application from trying to use it. After September is detached, a late September event inserted into the parent fails in this fixture because no attached partition accepts its time. That refusal is better than silently claiming the event was stored, but the application still needs a deliberate response.
Choose whether late events are rejected, admitted into an explicitly managed exception relation, or routed through an authorised historical correction process. Close or redirect the relevant write path before claiming the month is complete. A process that checked “no more old rows” and then raced an admitted late writer has not established that boundary.
The choice of time axis affects the policy. Partitioning by occurrence time lets a late event target an old month. Partitioning by receipt time places it with today’s arrivals, but a retention rule based on occurrence age no longer lines up with whole receipt-time partitions. Keep both timestamps if both questions matter, and say which one owns the storage and expiry boundary. History, correction and deletion explains why effective and recorded time answer different questions.
New partitions need care too. Create the next interval before its first expected write and monitor that the operation succeeded. Without it, a healthy application can begin failing at midnight. A default partition can catch unmatched values, including unexpected or missing keys where permitted, but can also hide a failed provisioning job. Give it explicit monitoring and a procedure for moving its rows when a dedicated range is added.
Attaching an existing table requires proving that its contents fit the new bound. PostgreSQL may scan it for validation; a suitable validated check can avoid that scan. A default partition may need its own check to prove that no row belongs in the newly attached range. These are real work and locking costs, even when the final map change is small.
Choose a boundary that earns its cost
More partitions mean more tables, indexes, statistics and maintenance objects. Queries that cannot prune may plan or execute work against many pieces. Very fine intervals make expiry precise but increase that overhead. Coarse intervals reduce the object count but retain more old rows until the whole piece becomes eligible. Choose the interval by the amount of data per piece, the query windows and the removal unit.
Table partitioning here remains inside one PostgreSQL database. Its partitions can all live on the same machine and storage device. It has not created additional independent servers, a replicated copy or a way to keep serving after that machine fails. Splitting a hot current month into named tables also does not automatically split its CPU or disk work across machines. Sharding and distributed SQL owns those placement and coordination questions.
A useful design can explain its saving before deployment. For pruning, show the common query conditions and which bounds they exclude; measure the remaining work. For lifecycle, show a partition whose rows can all leave together, including its references and late writes. Then verify that the chosen keys still enforce the application’s identity rules. If those explanations do not hold, a well-chosen index and an ordinary table may offer a simpler route.

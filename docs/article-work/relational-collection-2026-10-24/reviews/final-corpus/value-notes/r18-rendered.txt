H1: Write-ahead logs and crash recovery  Deep diveAbout 6 minutes AI-generated       
A commit can survive a crash even while the table's newest pages exist only in memory. The database makes that possible by first preserving enough information to rebuild them. Its write-ahead log records changes in an order that recovery can follow after the process stops. 
This separates two jobs that look like one from the application. Committing a transaction makes its outcome recoverable. Writing every changed table and index page back to its file can happen later. Waiting for all those scattered page writes at every commit would make even a small transaction pay for the whole set. 
Rewind the shop to before Mina's purchase 103: P3 has stock 12 and P7 has stock 1. One transaction takes two packs of tea and the last mug, records order 103 and writes its two lines. The protected outcome is P3 10, P7 0 and the complete pending order. This is a separate recovery drill using the collection's purchase, rather than a later change to its core snapshot. 
H2: What must go first 
The engine changes copies of table and index pages in memory. A changed page is called dirty until it has been written back to its file. Losing that memory would lose the only new copy unless something durable describes the change. 
A write-ahead log, usually shortened to WAL, supplies that description. The engine appends records sufficient to redo the changes. These are internal recovery records, not simply the SQL text. Re-running stock = stock - 1 against an arbitrary later state could take another mug; recovery must reconstruct the intended physical change. 
The ordering rule has two parts. Before a changed data page reaches its file, the log describing that page change must be durable. Before a normally durable commit is acknowledged, the transaction's commit record and the preceding log it depends on must be durable. A page can reach its file before its transaction commits, provided the first rule holds. 
That last case is why recovery also needs transaction outcomes. A file can contain some unfinished work. Finding changed bytes is not evidence that their transaction committed. PostgreSQL can replay changes belonging to an unfinished transaction while keeping its row versions invisible. Engines that update records in place can use undo information to reverse unfinished work.

Conceptual cuts, not an observed power failure. The before-commit case deliberately has no surviving commit record; a real connection failure during commit does not reveal which side of the durable boundary it reached.    
The two committed histories recover the same purchase. The application knows different things. A crash just before the reply and one just before durable commit can both look like a dropped connection, so the missing reply cannot decide whether Mina should buy again. Retries when a commit reply is missing uses request identity to resolve that uncertainty. 
A multi-row transaction can require many change records. Recovery does not expose half of the purchase merely because it replays those records one by one. Visibility depends on the transaction's outcome. After recovery finishes, a reader sees the committed order, its lines and stock effects together, or none of that transaction's effects. 
On an owned PostgreSQL 18.6 instance, the native drill committed purchase 103, left a separate scratch insert uncommitted, then stopped that server with its immediate shutdown mode and restarted it. Order 103, both its lines and stock P3 10/P7 0 were present afterwards. The scratch insert was absent. The server log recorded crash recovery. This verifies a process restart on this machine; it did not cut the power, remove the operating system's cache or damage a page. 
H2: What durable means 
Writing a log record to a file is not necessarily enough. It may have reached only the operating system's memory cache. The database asks the operating system to flush it to durable storage, using an operation such as fsync, and waits for success before acknowledging the normal commit. 
Storage can have another cache behind that operation. The promise ultimately depends on the filesystem, device or storage service retaining what a successful flush says is safe. A database process crash leaves the operating system running, so it is a weaker test than a machine losing power. A fast process-restart experiment cannot certify the entire storage path. 
Many small transactions can share one flush. Their commit records accumulate in the log, one flush covers a group, and each covered transaction can receive its reply. This is group commit. It reduces the number of storage flushes per transaction without weakening the acknowledgement boundary. It also means a single client's commit rate does not predict the whole server's throughput. 
Batching several related rows in one transaction can reduce commit overhead too, but it changes lock duration, failure scope and retry cost. The shop's purchase belongs together for correctness. Putting unrelated purchases in one enormous transaction just to reduce flushes creates a different operational cost. 
H2: Where replay begins 
If recovery had to begin at the database's creation, the log could never be discarded and every restart would take longer. A checkpoint establishes a point from which recovery can proceed using sufficiently up-to-date data files. Background work writes dirty pages so the next recovery need not redo all earlier history. 
The checkpoint record and its recovery position are related but not interchangeable. PostgreSQL's checkpoint records a redo position; recovery can begin before the checkpoint record itself, because writes continued while checkpoint work ran. Think of a safe restart boundary, rather than an instantaneous photograph of every page at one clock time. 
Pages carry log sequence numbers, or LSNs, identifying progress through the log. Recovery uses them to recognise changes already reflected in a page and apply missing changes. It can redo a history that contains both older and newer page copies without applying the same change twice. An LSN is a log position, not an application order ID or a wall-clock timestamp. 
More frequent checkpoints can reduce the log that a restart must replay, while making active pages get written more often. Less frequent checkpoints can reduce repeated page work but leave more recovery work. The useful balance depends on the actual write workload and recovery requirement. PostgreSQL WAL, checkpoints and durability develops the settings and the observations that justify changing them. 
A half-written page needs additional protection. A few redo bytes cannot repair an arbitrary mixture of old and new page contents. PostgreSQL normally includes a full-page image with the first modification of a page after a checkpoint, giving replay a sound page to rebuild from. A checksum can help detect damage, but detecting damage does not by itself supply the missing good copy. 
H2: Changing the acknowledgement 
PostgreSQL's synchronous_commit = off allows a successful reply before the local WAL flush. A background writer flushes later. A crash before that happens can remove a transaction the application already heard was successful. Recovery still follows a consistent surviving history; the guarantee about the most recent acknowledgements has changed. 
Three durability decisions with different consequences
 | Decision | What success waits for | Consequence
 | Normal local durable commit | Local WAL flush, plus any configured synchronous replication requirement | Local recovery can reconstruct it if its durable storage survives
 | Asynchronous local commit | Less than that local flush | Recent acknowledged commits may be lost after a crash
 | Disable storage ordering safeguards | The engine can no longer rely on its required durable ordering | Corruption is possible, rather than merely losing a recent consistent tail 
The third choice is materially different from the second. Turning off fsync is not just a larger version of the asynchronous-commit window. It can invalidate ordering between the log and pages and leave the files unrecoverable. Keep these separate when someone proposes a “faster commit” setting. 
Choose the acknowledgement boundary from the consequence of loss. A counter that can be rebuilt from a retained source has different needs from a confirmed order whose only record is this database. The application receives an ordinary success in either commit mode, so it cannot discover the weaker promise from the reply text. 
H2: Recovery is part of the outage 
A server accepting connections again is only one point in recovering a service. Someone must detect the failure and start the server; log replay must finish; applications must reconnect and resolve uncertain requests; useful data must be read back into memory. A correct database can initially answer more slowly because its working set is cold. 
Measure those phases in a disposable recovery drill shaped like the service you need to run. Record the log span, storage state, workload and acceptance queries. A replay rate observed with warm filesystem caches on a laptop is not a production recovery-time guarantee. Neither is the configured checkpoint interval. 
Crash recovery also faithfully preserves a committed mistake. If an operator deletes order 103 and commits, the log's job is to make that deletion survive. A replica can copy it too. A lost disk or missing recovery files may leave the local log unable to recover anything. Those failures require another usable history, which Backup, restore and reconciliation follows from a saved copy through acceptance of later valid work.

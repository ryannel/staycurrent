H1: Relations, keys and normalisation  Deep diveAbout 12 minutes AI-generated       
A data model decides what the database is saying. A row in orders says that one customer placed one order; a row in order_items says that one numbered line of that order contains a product, a quantity and an agreed unit price. Choosing those meanings determines which facts can change independently, which values identify them and which tables a query must combine. 
A receipt puts a customer’s name beside every product they bought. That is a useful answer to display, but it makes a troublesome place to keep the original facts. Mina’s name would be repeated on several lines. Changing it would mean finding every copy, and the shop would have nowhere to record Edda until she bought something. 
Normalisation separates facts according to what determines them, so that a change has one place to go. The resulting tables usually need joins to recreate a receipt. The trade is worthwhile when it lets the shop record a customer independently of an order, change a name without changing purchases and keep an agreed price when the catalogue moves on. 
This article develops the shop from the introduction, using its three customers, three orders and five order lines. We will compare those tables with a sales sheet that keeps the same purchases in a different shape. 
H2: What one row says 
Start a table design by completing the sentence “one row records …”. For customers it is one customer. For order_items it is one numbered line on one order. That choice is often called the table’s grain. Quantity and unit price make sense at the grain of an order line; the customer who placed the order belongs to the order as a whole. 
The distinction matters before any SQL is written. If an order row has product_1, product_2 and product_3, the schema has made three products a limit. Adding a fourth requires another column, and a query for mugs has to search each product column. Separate order-line rows let the number of products vary without changing the table definition. 
Putting P7, P3 in one text field avoids the fixed limit but hides the individual relationships inside a string. A product reference can no longer describe each item directly, and quantity and price need some other way to line up with the right product. The line table gives each occurrence its own row, with those facts together. 
This does not mean every value must be split into its smallest imaginable pieces. The product name “Green tea, 50 g” can be one text value. Split the weight into its own typed column if the application needs to compare or calculate with weights. PostgreSQL also supports arrays and JSON values. The question is whether their contents form one value for this purpose or are independent items that need their own identities, references and updates. Order lines have all three reasons to be rows. 
A mathematical relation is a set of tuples, the formal counterpart of rows, over named attributes. A set has no duplicate members and no inherent order. SQL tables approximate that model but permit identical rows unless constraints rule them out. The shop therefore declares keys rather than relying on the rows happening to look different. A row’s position on the screen supplies neither identity nor a lasting order. 
H2: Which values identify it? 
A key is a rule about every valid state of the table. In orders, an order_id identifies one order. In order_items, the pair (order_id, line_no) identifies one line. Order 103 has lines 1 and 2; other orders can also have a line 1. Neither half identifies a line alone. 
A candidate key is a minimal set of columns that uniquely identifies a row. Minimal means that removing any column would lose that guarantee. Adding product_id to (order_id, line_no) would still give a unique combination, but the extra column is unnecessary. Such a larger identifying set is a superkey; a candidate key is a superkey with no unnecessary columns. One candidate is chosen as the primary key. 
Do not choose a key just because it is unique in the sample. Every customer here has a different name, but the model permits two people with the same name. The displayed order lines also happen to use each product at most once per order. The schema does not promise that: a line is identified by its number, not by its product. Declaring UNIQUE (order_id, product_id) would add a different business rule, forbidding two lines for the same product on one order. 
A natural key uses values that already identify something in the application’s world, such as a product code under a rule that keeps it unique. A surrogate key is an identifier introduced for the database, such as an allocated integer. The shop’s customer ID lets Mina change her name while every order continues to refer to customer 1. A good identifier remains useful when the descriptive facts change. 
A surrogate does not decide when two rows represent the same business fact. Suppose a schema variant gives each order line a generated line_id. Two inserts for order 103, line 1 could receive different IDs and both pass a primary-key check. If the original line numbering still defines identity, it still needs a uniqueness rule: 
-- Alternative to PRIMARY KEY (order_id, line_no):
line_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
order_id integer NOT NULL REFERENCES orders,
line_no integer NOT NULL,
UNIQUE (order_id, line_no) 
In this alternative definition, the primary key gives other tables one value to reference; the unique pair preserves the meaning of an order line. Generating an identity value and enforcing uniqueness are separate jobs in PostgreSQL too: GENERATED … AS IDENTITY alone is not a unique constraint. 
Keys also explain relationships. Many orders can carry customer ID 1 because the customer ID identifies a customer, not an order. A foreign key requires each referenced customer to exist; NOT NULL on orders.customer_id requires each order to name one. Neither requires every customer to have an order, so Edda can remain a customer with none. The order-line table connects orders to products and carries the facts about each occurrence of that connection. 
H2: Follow what determines what 
Knowing a key tells us which other values must agree. If two rows describe line 1 of order 103, they must agree about its product, quantity and agreed price. We write that as a functional dependency: 
(order_id, line_no) → product_id, quantity, unit_price 
The arrow means that whenever two rows agree on the left-hand values, they must agree on the right-hand values. The left side is the determinant. It is a statement of meaning, not a formula for calculating the right side. Order number 103 does not mathematically produce Mina’s customer ID. 
A dependency describes agreement within one valid state. It does not freeze a value for all time: customer 1 can have a different current name tomorrow. Nor does it run backwards. One customer can determine one current name, while the same name can belong to several customers.

The order-line key determines the order’s customer too, through order_id. But the line number adds nothing to that determination: every line on order 103 has the same customer. And the customer’s current name depends on customer_id, regardless of how many orders they have. These shorter dependencies tell us where facts belong. 
They come from the application’s rules. Inspecting existing data can disprove a proposed dependency: two different names for the same customer ID would contradict the current-name rule. Finding no contradiction in five rows cannot establish the rule for every future purchase. Ask whether a valid future state is allowed to break it.

Edda reveals an insertion anomaly. The shop knows she is a customer, but a table whose rows require an order line cannot record that fact alone. Leaving the order-line identity missing or inventing an order would weaken what a row means. A customer row records her without either compromise. 
Removing order 102 reveals a deletion anomaly. Removing the only sale carrying Tariq’s details also removes the fact that he is a customer. With separate tables, deleting an order and deleting a customer are distinct decisions. Whether the shop should retain either is a lifecycle policy; History, correction and deletion develops that policy. 
Repeating values is not itself the problem. Customer ID 1 should appear on both of Mina’s orders: those are two different facts, each saying that an order belongs to her. The troublesome repetition is several independently editable copies of her one current name. Normalisation leaves the references repeated and gives the name one authoritative location. 
H2: Separate the facts, keep the connection 
First separate the order-level facts from the line-level facts. Keep the product, quantity and agreed price with (order_id, line_no). Put the customer, placement time and status with order_id. Every line still carries its order ID, so the separation preserves which order it belongs to. 
Then separate the customer’s current name from the orders. Keep customer_id on each order and put the name in customers. A customer ID now determines the name in one place, and the order ID determines which customer to follow. Products follow the same reasoning: the catalogue name belongs with the product ID, while each line carries the ID of the product bought. 
A split must preserve the associations, not just the individual values. Keeping a list of order IDs and a separate list of customer IDs would lose who placed which order. Joining the two lists with no matching condition would invent combinations. Keeping customer_id on each order preserves the pair. 
We can recreate the sales sheet’s selected columns from the separated tables: 
SELECT i.order_id, i.line_no,
       c.customer_id, c.name,
       i.product_id, i.quantity, i.unit_price
FROM order_items AS i
JOIN orders AS o ON o.order_id = i.order_id
JOIN customers AS c ON c.customer_id = o.customer_id
ORDER BY i.order_id, i.line_no; 
Each line finds one order through the order primary key, and that order finds one customer through the customer primary key. The non-missing foreign keys ensure the referenced rows exist. There are still five result rows, with the same line-to-customer associations. Edda’s customer row does not manufacture a sale; this query starts from order lines. 
This is the practical test of a lossless decomposition: joining the separated facts reconstructs the original relation without losing rows or inventing new combinations. The keys provide the at-most-one match, and the required references provide the match’s existence. These properties need to remain true for every valid state, not just this one. 
Normalisation gives a rule a suitable home; the SQL declarations and write protocol enforce it. An order_items table without the declared composite key could still admit duplicate line identities. A customers table without its key could make the reconstruction multiply lines. Constraints and tenant boundaries follows the enforcement, including references that must remain inside one shop. 
H2: The checks called normal forms 
The familiar normal forms name progressively stronger checks on these dependencies. They are useful for explaining a split and finding a dependency you missed. Counting tables or adding an ID does not establish a normal form. 
First normal form gives the relation its regular shape: one value at each row-and-column position, without repeating groups hidden inside the row. The shop’s repeated product columns became order-line rows. At this stage, the sales sheet can still repeat customer and order facts on every line. 
Second normal form rules out a fact outside the candidate keys depending on only part of a candidate key. In the sales sheet, the customer ID depends on order_id, which is only part of (order_id, line_no). Moving order-level facts to orders removes that partial dependency. Check every candidate key, including a business key retained beside a surrogate. Giving the sheet a single-column row ID would leave the original dependency in place. 
Third normal form also addresses indirect dependencies. If an orders table stores the customer’s current name, then order_id determines customer_id, which determines that name. The name depends on the order through the customer. Moving it to customers removes this transitive dependency between the order key and the name. 
The common shorthand is “the key, the whole key and nothing but the key”. It helps with this shop, provided “the key” means every candidate key and “nothing but” is about the dependency being tested. More involved schemas need the precise definitions.  
Overlapping candidate keys and BCNF 
A column belonging to any candidate key is called prime. Second normal form requires every non-prime column to depend on each whole candidate key. The usual dependency definition of third normal form says that, for every nontrivial dependency X → A, either X is a superkey or A is prime. Nontrivial means that A is not already in X. This prime-column exception matters when candidate keys overlap; the shop examples above do not need it. 
Boyce–Codd normal form, or BCNF, strengthens that rule: every nontrivial determinant must be a superkey. Higher forms address further dependencies, such as two independent sets of facts accidentally combined into every possible pair. Fagin’s paper below develops that case. For this shop, identifying the dependencies and preserving their connections did the useful work; the normal-form names describe why the splits work.  
H2: When a copy is a different fact 
The mug has two prices: products.price and order_items.unit_price. At the time of order 103, they both say 20.00. Deleting the line price and looking up the catalogue price would seem to remove duplication, until the catalogue changes.

P7’s catalogue price changes on 21 October 2026. The existing order line keeps its agreed 20.00. These are different facts; their earlier equality did not make one a redundant copy of the other.  
The catalogue says what a buyer would pay now. The line says what Mina agreed to pay then. Its determinant is the line identity, not the product ID alone. Keeping 20.00 on that line preserves a purchase fact; replacing it with today’s 25.00 would change the meaning of the old order. 
The same judgement applies to names and addresses retained on an issued invoice. A field meaning “customer’s current address” is a copy that must track the customer. A field meaning “address printed when this invoice was issued” is a historical fact with a different rule for change. Name it and document that rule before deciding whether its repetition is an anomaly. The lifecycle article follows corrections and retention in more depth. 
H3: A derived copy needs an owner 
A stored order total is different again. In this shop, the total is derived from the lines: order 103 is 1 × 20.00 + 2 × 4.50 = 29.00. The shop calculates it rather than storing an authoritative orders.total. A view can package that calculation for callers while the lines remain its source. 
Sometimes a measured workload justifies storing a derived result. A materialised view, a report table or an application cache can save repeated work, but the copy brings a maintenance contract. State which rows are authoritative, which changes refresh the result and how old a reader may find it. If the copy must be current at commit, every relevant write has to maintain it with the source change. If it is refreshed later, readers need to accept that delay, and there must be a way to rebuild it. 
That is deliberate denormalisation: accepting redundant storage for a defined use while owning the risk of disagreement. A vague expectation that application code will “keep it in sync” leaves the original anomaly intact. First establish the correct model, then use query measurements to decide which copy earns its upkeep. Query execution and bad plans helps identify the work before changing the design. 
H2: Trying the design 
Test a proposed model with changes, as well as with the screen it must display. Change a description, add something that has no relationships yet, and remove its final relationship. For the shop, those were Mina’s name, Edda without orders and Tariq’s only order. Each exposed a different way the sales sheet bound unrelated facts together. 
Then test the keys. Which valid future rows should be allowed to share each value? Which pair would represent the same fact twice? Finally reconstruct the original view through the retained references. The result should preserve the associations, not merely contain the same names and numbers.

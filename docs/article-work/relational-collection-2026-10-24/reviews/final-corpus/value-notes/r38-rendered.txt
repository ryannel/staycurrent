H1: PostgreSQL physical replicas and promotion  Deep diveAbout 7 minutes AI-generated       
A PostgreSQL physical standby follows the primary’s WAL and reconstructs the same cluster’s files. It can hold a durable copy of a committed purchase before its queries can see that purchase. It can also be promoted without containing the primary’s last acknowledged commits. 
Operating a standby therefore requires two decisions: which progress a commit must wait for, and which history may become authoritative after a failure. Promotion ends recovery. It does not fence the former primary, recover unavailable WAL or merge two writable histories. 
This article’s separate local drill starts before Mina’s purchase 103, with P3 stock 12 and P7 stock 1. It commits the complete purchase, deliberately holds standby replay behind receipt, then transfers authority and rebuilds the former primary as a standby. Anonymous scratch rows expose a later loss boundary without changing the collection’s core purchase history. 
H2: Build a copy of the same cluster 
Physical replication begins with a supported base backup, not independently created tables that happen to have the same names. WAL records refer to the cluster’s physical structures. Primary and standby normally use the same PostgreSQL major version and compatible architecture. Keep minor versions aligned where practical and follow the release procedure; physical replication is not a general major-version migration path. 
pg_basebackup -d 'host=/owned/socket port=55440 user=replicator application_name=copy_a'   -D /owned/empty/standby -X stream -R -C -S copy_a 
This command shape takes a base with streaming WAL, writes standby connection settings with -R and creates a physical replication slot named copy_a. The role needs replication permission and an appropriate connection rule. -R creates standby.signal; on startup that signal makes the restored server continue recovery rather than open as another primary. 
Review the copied configuration before starting. Ports, socket locations, tablespace paths, archive commands, credentials and connection rules need to suit the destination. primary_conninfo points the standby at its upstream source. The standby’s application name identifies its connection for monitoring and synchronous selection; it is not a security identity. 
A streaming connection carries WAL promptly instead of waiting for whole segment files. An archive can also supply older WAL when it remains available independently of the primary. If no source retains a required segment, the standby cannot catch up from its old position and may need another base. 
H2: Read the progress in order 
On the primary, pg_stat_replication reports each directly connected sender’s sent, written, flushed and replayed positions. “Sent” says what left the primary. The other fields reflect standby progress reported back to it. A connected sender is therefore only the beginning of the observation. 
SELECT application_name, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication; 
On the standby, pg_stat_wal_receiver describes the receiver, while pg_last_wal_receive_lsn() reports streaming WAL received and synchronised to disk. Despite its name, this function is not simply an unflushed network-receipt counter. pg_last_wal_replay_lsn() reports the applied position. Check pg_is_in_recovery() too, since the recovery positions remain historical after promotion. 
The native drill paused replay and confirmed the actual state was paused, using pg_get_wal_replay_pause_state(). It then committed purchase 103 with synchronous_commit = on and a configured synchronous standby. Remote flush reached 0/300EB58, while replay remained at 0/3000000. A fresh standby query found no 103. Receipt and durable storage had caught up; application visibility had not. 
Pausing replay does not pause receipt. WAL can keep accumulating, and a long pause can fill standby storage. Nor does it safely manufacture an asynchronous failover loss test: promotion ends a replay pause and can apply WAL already present. The later loss test stopped the standby before the deliberately unreplicated write. 
H2: Choose the remote acknowledgement 
synchronous_standby_names defines which standby acknowledgements count. For example, FIRST 1 (copy_a, copy_b) chooses by priority; ANY 1 (copy_a, copy_b) accepts an acknowledgement from any one of the listed candidates. They express different selection policies. Neither means every replica has the commit.

The chosen setting moves the earliest permitted success reply. It does not make a different asynchronous standby participate or refresh an old query snapshot. File write and durable flush remain separate storage promises. 
Read the boundaries as text
Every mode shown waits for the primary’s local flush. local adds no remote wait; remote_write waits for the selected standby’s file write; on waits for its durable flush; remote_apply waits for its replay. A fresh standby query includes 103 only after replay of the commit. With no configured synchronous standby set, all four modes shown have only the local wait.    
All four illustrated settings wait for local WAL flush. local adds no remote condition. remote_write waits for the selected remote filesystem write, which may still be volatile through an operating-system crash. on waits for remote durable flush. remote_apply additionally waits for replay. With an empty synchronous standby configuration, these names all reduce to the same local wait. 
The native on transaction returned while standby replay was paused. A subsequent remote_apply scratch transaction remained waiting at SyncRep. After replay resumed, that client completed, and fresh standby queries found the scratch row and the complete purchase: two order lines, P3 10 and P7 0. This checks the distinction between the two configured modes, rather than inferring it from their names. 
The stronger wait adds a dependency. If the required copy cannot reach the chosen boundary, commits can wait even though the primary is locally healthy. Removing that requirement to restore write availability changes the loss promise. Treat the configuration change as a deliberate service decision, and resolve request outcomes if a client disconnects while waiting. 
remote_apply does not refresh a Repeatable Read snapshot established earlier, and a different asynchronous standby can still lag. To read your own write, choose the intended copy, wait for its required history boundary and start a suitable fresh snapshot. Replicas, lag and read routing develops that application protocol. 
H2: Keep the needed WAL available 
A physical slot retains WAL that its consumer may still need. That helps a disconnected standby resume, while making an abandoned slot a threat to primary disk space. wal_keep_size provides a minimum retained amount; it is not a promise to retain an arbitrarily long outage. 
Observe the slot’s restart_lsn, WAL availability and retained byte distance as well as whether a consumer is active. max_slot_wal_keep_size can limit retention at checkpoint time, but exceeding that allowance may remove WAL needed by the standby. A storage safeguard can therefore turn into a rebuild requirement. An archive may supply the gap if its chain is usable. 
Transmission, flush and replay need different remedies. Growing sent-to-flush distance can point towards transport or remote storage. Growing flush-to-replay distance means the remote log is ahead of its data state. Time-based lag fields are observations about recent acknowledgements, not a forecast of catch-up time. Subtracting the last replayed transaction’s timestamp from now on a quiet primary can report age even when there is no missing work. 
Read queries share the standby’s resources with replay and can conflict with recovery. A long report may need versions that vacuum removed on the primary; replay can wait or cancel the report according to policy. hot_standby_feedback can reduce some cleanup conflicts by retaining versions on the primary, moving cost into bloat there. A reporting standby and a tightly bounded failover candidate need an explicit policy for those trade-offs. 
H2: Fence before promotion 
First decide who can still write. An unreachable primary may remain alive for another client. Changing DNS or a pool target does not close old sessions. PostgreSQL’s promotion command does not turn off the former primary. Failover and fencing explains why an enforced authority boundary must accompany the role change. 
For a planned transfer, close admissions, settle in-flight and uncertain requests, capture the final required history boundary and verify that the chosen candidate contains it. Then enforce the old writer’s exclusion. For an unplanned failure, the latest old-primary boundary may be unknowable; candidate selection must follow the service’s stated loss policy and the history evidence actually available. 
SELECT pg_promote(wait => true, wait_seconds => 60);
SELECT pg_is_in_recovery(); 
These commands show the PostgreSQL part of the procedure. A false recovery result confirms that this server left recovery; it does not prove any remote fence or application acceptance. Promotion creates a new timeline, preserving a distinct continuation of WAL. It does not reconcile transactions that exist only on the abandoned branch. 
The native loss boundary was explicit. After the complete purchase had replayed, the controller stopped the standby. The old primary committed a scratch row named local-only using local acknowledgement, then exported its known scratch history. The controller stopped that primary, confirmed its private endpoint was unavailable and had no supervisor capable of restarting it. This was the fixture’s enforced process fence. 
Starting and promoting the stopped candidate retained the complete purchase but not local-only. Its unavailable source could no longer supply that WAL. The scratch row’s deliberate exclusion demonstrates the cost of accepting local commits while the candidate is absent. It is not a claim that synchronous purchase 103 was lost, or that the amount of a production failure’s missing history would always be known. 
Keep application traffic closed until accepted and uncertain requests have been accounted for. If discarded history contains a confirmed purchase, copying only its order row omits its lines and stock effect. External effects have separate authorities too. Recovery and reconciliation follows that complete operation. 
H2: Return the old primary as a standby 
The former primary must not restart independently with its old files. Preserve evidence of its discarded history, then make it follow the chosen authority. A fresh base backup from the new primary is the straightforward method. Start that copy with the correct standby signal and upstream settings, then verify its role and actual replication. 
pg_rewind can instead synchronise a divergent copy by copying changed blocks from the selected source. It requires the relevant WAL and timeline history, full_page_writes, and either data checksums or wal_log_hints set appropriately before the divergence. Review its precise prerequisites for the installed version. Rewind chooses one history; it does not merge the valid business operations unique to both. 
Rewind also copies configuration files. Correct the destination’s ports, paths, credentials and recovery settings before restart. If rewind fails partway through, the target may be unusable; rebuilding from a fresh backup can be necessary. A successful tool exit still needs recovery completion and acceptance. 
The drill used a fresh base, rather than claiming a rewind test. It replaced only the stopped, owned old-primary directory with a backup of the promoted source and started it as a standby. The former endpoint reported recovery, replayed a new scratch write from the new authority, and rejected an attempted local insert as a read-only transaction. One endpoint was now the writer and the other a following copy. 
The complete physical-replication drill creates and cleans its own private PostgreSQL 18.6 pair. Run it with Python 3 and the stated binaries from an empty working directory. It records progress, waits, the known discarded scratch tail and rejoin acceptance. Two processes on one host demonstrate these mechanisms; they do not demonstrate independent disks, power domains, regional latency or a production fencing integration.

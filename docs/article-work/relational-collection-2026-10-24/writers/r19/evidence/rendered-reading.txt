Backup, restore and reconciliation
Deep dive
About 7 minutes
AI-generated

A backup gives you an earlier copy. A recovery procedure has to turn it into a service whose data you can trust. That requires finding a usable history, restoring it to the intended boundary, and accounting for valid work and external effects that boundary leaves out.

Consider a separate shop recovery drill. At the scenario's 11:00 UTC on 23 October, an erroneous transaction deletes order 103 and its two lines. At 11:05, Edda places valid order 107: one P3 at 4.50. P3 starts this drill at stock 10, so that purchase leaves 9. A restore to before the mistake brings 103 back, but also removes 107 and returns P3 to 10. The earlier 101–103 report remains the collection's core report; 107 belongs only to this alternative history.

Those times describe the scenario. The native experiment below identifies its actual transactions and uses a named log restore point, rather than pretending its application timestamps are captured commit times. The distinction matters: a recovered clock time alone does not prove that the wrong transaction was excluded.

Start from a failure. A killed database process may need only local crash recovery. A failed storage device needs files from somewhere else. A mistaken committed deletion needs an earlier state, since normal recovery and replication faithfully preserve the deletion. An account compromise can put both live data and reachable backups at risk.

The location and access of a saved copy are therefore part of its usefulness. A second directory on the same disk does not survive losing that disk. A backup that the same compromised authority can erase may not survive that authority being abused. Keep restoration credentials, encryption keys and the route to the copies usable under the failure you are planning for.

Two objectives make the business requirement explicit. The recovery point objective, or RPO, bounds how much committed history the service can afford to lose, usually expressed as time. The recovery time objective, or RTO, bounds how long restoring acceptable service may take. They are requirements to test, not properties conferred by scheduling a backup job.

A daily copy alone may leave nearly a day's later work outside the saved history. Adding a continuous log archive can give more recent recovery points, provided the archive is complete and available. Restoring a larger base or a longer sequence of increments and logs may cost more time. Include retrieving keys, provisioning, transfer, replay, validation and reconciliation in the outage; measuring only the copy command misses much of it.

Keep a restorable chain

A logical backup describes database objects and rows in a form a tool can recreate. A PostgreSQL dump is one example. It is useful for selective restoration or moving data between supported environments, but loading it may involve recreating objects and indexes. Its snapshot does not become arbitrarily newer merely because the live server retained more WAL.

A physical base backup preserves the engine's files in a supported form. With the required WAL, PostgreSQL can make those files consistent and replay onward. Point-in-time recovery, or PITR, starts from such a base, follows saved log history and stops at a chosen target. The physical format has engine and version compatibility requirements; it is not a general SQL interchange format.

What the saved pieces contribute
Piece	What it gives recovery	What still has to be present
Logical dump	Objects and data from its consistent view	Compatible restore tools, required roles or other globals, and application configuration
Physical base	A supported starting copy of the files	WAL needed to make that copy usable, compatible engine and required configuration
Incremental backups	Changes relative to earlier backups	The dependencies and supported combination or restore procedure
Continuous log archive	History after the base, up to the available target	A complete required sequence on the right history branch

An incremental file can be perfectly readable and still useless without the base it depends on. Likewise, a missing required log segment can stop replay before the desired target. Retention must preserve whole usable chains, not merely the newest file of each name. After a restore creates a new history branch, keep the timeline information that identifies which continuation belongs to it.

A backup tool coordinates a consistent copy while the database is changing. Copying arbitrary live data files without the engine's supported procedure can mix incompatible states. Filesystem snapshots can be part of a supported backup design, but the word “snapshot” alone does not establish that all required volumes, logs and consistency rules were covered.

Prove the boundary

For a mistaken change, preserve evidence before destroying anything. Record which transaction was wrong, what it changed, the suspected time range and the unaffected history you still need. Restore into an isolated candidate so inspection cannot send messages, take payments or accept live writes by accident.

The target must be before the bad transaction's effects become part of the recovered state. A tool may express that using a transaction ID, log position, timestamp or named restore point. Read its inclusivity rules. “Stop at this transaction” and “stop immediately before this transaction” can give opposite answers for the very change you are removing.

In this article's native PostgreSQL 18.6 drill, a base backup completed before a named restore point, r19_before_bad. The erroneous transaction then deleted exactly order 103 and its lines; its recorded transaction ID was 765 in that run. Valid order 107 followed. Saved WAL included the restore point and the later transactions. Recovery used the named pre-mistake point and stopped there; the error was beyond the target, rather than relying on timestamp inclusivity.

The restored candidate contained orders 101, 102 and 103, including 103's two original lines. Order 107 was absent and P3 stock was 10. Those queries establish both sides of the boundary. Seeing only that the server started or that 103 returned would have missed the excluded valid purchase.

Close the history before reconciliation

Restoration can take time while the source system still processes work. Comparing with a source that keeps changing gives no final list of excluded requests. A new purchase could commit after the comparison and before traffic moves, leaving a customer confirmation on the discarded side.

Before the final enumeration, remove the old authority's ability to accept more writes. This is fencing: an enforced boundary, not simply a request to stop or a changed routing address. Wait for previously admitted work to commit or abort, and resolve uncertain request outcomes. Keep that history closed through the final data and external-effect acceptance.

The local drill makes the boundary concrete with a single write gate. Every purchase takes a shared row lock on the gate and checks it while holding that lock through its transaction. Closing the gate updates the same row, so it must wait for already-admitted purchases. A purchase waiting behind that update sees the closed gate and is refused. All purchase paths in this deliberately small fixture use the gate.

The test held the fence transaction open, started a racing request, verified that it was waiting for the gate lock, then committed the fence. The request was rejected with “source fenced”. Only after both outcomes were known did the drill enumerate accepted request identities. It found purchase-edda-107. The source was then stopped before restoring the candidate, so the rest of the drill could not accidentally read a moving source.

That gate demonstrates the required ordering in one database. A real service may need to revoke application roles, stop other writers, control old credentials and prevent an isolated former primary from resuming writes. Failover and fencing develops authority across servers. A gate that only one of several writers obeys is not a closed history.

The old source stays fenced. The candidate's database starting successfully is followed by acceptance work, not by automatic permission to serve customers. This is the gap between restoring a copy and restoring a service.

Reconcile the operation, not just the row

Order 107 is a valid later purchase. Copying its orders row alone would lose its line and fail to consume its stock. Copying the line but decrementing stock twice would sell the same unit twice in the accounting. Reconciliation must preserve the operation's identity and its complete invariant.

The drill reapplies Edda's purchase as one transaction: create order 107, create its single line for one P3 at 4.50, reduce P3 from 10 to 9 and record purchase-edda-107 with the outcome. Repeating that same identity and payload finds the existing outcome and makes no further stock change. Reusing it for a different order or customer is a conflict.

The native first application returned “created”; the second returned “existing”. Final queries found one order 107, one matching line and P3 stock 9. The restore without reconciliation is the counterexample: a structurally usable database, correct exclusion of the mistake, and a missing valid order. The repeated application checks why a stable request identity matters during recovery as well as during ordinary retries.

External effects have separate authorities. If a payment provider already charged 107, restoring the database did not refund it. If an email was delivered, it cannot be unsent by restoring a table. An outbox event missing from the candidate does not prove it was never delivered from the old source. Check the provider's effect identity, consumer records or other authoritative evidence before deciding to send, suppress or compensate.

This native drill deliberately executed no payment, message or email. Its external acceptance decision is therefore “no external effect was generated by this fixture”, not a simulated provider reconciliation. A production procedure needs the relevant external records preserved outside the state being rolled back. It may also need to reapply deletion or suppression policy so a restore does not make deliberately removed data available again.

Test the recovery you will use

A successful backup command proves that a command completed. A manifest or checksum check proves more about the bytes it inspected. Neither proves the server can restore through the required log chain, reach the intended target and satisfy the application's acceptance queries. PostgreSQL's backup-verification documentation explicitly still asks for test restores.

A useful drill starts with the saved objects and dependencies you expect to possess after the failure. Restore without help from the live source. Confirm the target transaction's presence or absence, check the important related rows and invariants, and exercise the application in isolation. Time the whole route to acceptable service if RTO is the requirement; this article reports no RTO measurement.

Also test an unavailable dependency. Can the operator find the older base an increment needs? Can recovery reach the archive when its normal account or region is unavailable? Does a missing required segment stop the operation visibly? A copy that works only while every live-system dependency is healthy has not demonstrated the failure you set out to survive.

The local evidence restored from a saved base and archive with its source stopped, then checked the exact target, fence race and idempotent reconciliation. Both instances and all disposable files were removed afterwards. The copies shared one machine and its storage, so this proves the mechanics of that drill, not recovery from losing the host or the backup account.

For an executable operational procedure, continue with Restoring PostgreSQL to a recovery target or CockroachDB backup and recovery. Each engine has its own backup dependencies, target semantics and restore commands. Carry the same acceptance question into either: which history is now authoritative, and which valid effects still need to be accounted for?

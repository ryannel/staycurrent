## Retain

All three favour the existing simple composition: coloured balls and curved
routes, a retained result in Redis, a quiet database during later hits, and space
around the drawing. The scoped teaching review found no technical blocker: the
server owns cache lookups, source rows remain, and the cached answer is copied.
SQL evidence supports the example data, not the animated duration.

## Prioritised recommendations

1. **Make the first join handoff explicit (medium teaching finding).** The joined
   pair rests at the join point for only 0.35 seconds; the waiting ball acquires
   the same answer separately above it. Hold the combined pair for a readable
   beat, then visibly transfer a copy into the ball. Preserve the source rows.
   This is the only finding classified as a substantive reader difficulty.
2. **Make answer identity easier to follow (optional polish).** The pair inside a
   response ball occupies roughly eleven SVG units. Slightly enlarge it and
   reduce competing highlight. At the first hit, form a visible copy beside the
   retained Redis result, then let it return. Do not add a legend or extra labels.
3. **Let one complete cache hit establish the pattern (optional pacing).** Warm
   requests start every 1.5 seconds but complete in 2.9 seconds. Let the first
   warm request finish alone, then introduce the present overlapping rhythm.
   Preserve the lively stream once the operation is understood.

These recommendations are unimplemented follow-up work, not claims of completed
repairs. No finding has been downgraded to certify delivery. The current reviewed
prototype remains unchanged, as requested for discussion.

Lower-priority suggestions: a short fading stroke could replace the barely
visible ghost-dot tail; the two selected table rows could show actual values.
The coordinator would defer additional row text for now: it risks returning to
the visual density the user rejected. Distinguish the answer by its paired shape,
not by introducing more colour rules. Keep Redis's requested symbol and name;
the prose already establishes it as one cache implementation.

## Other approaches worth considering

### Same lesson, different motion

Travelling coloured pulses along the existing curves, with small arrival ripples.
The join and retained pair stay the same. This is a quieter editorial treatment,
but loses some of the balls' physical personality. Try as an optional separate
variant, not an automatic replacement of the approved direction.

A two-request-only sequence is another possible beginner version: first miss,
one hit, then rest. It is easier to follow but loses the sense of ongoing reuse.
The coordinator prefers a clear first hit followed by the current stream.

### Expiry, in its own article

Begin with a populated cache and ordinary hits. A quiet lifetime arc runs out;
the result disappears. Nothing refreshes until the next request, which misses,
performs the familiar join and refills Redis. Show the expiry duration as
illustrative, and do not imply TTL alone guarantees source freshness.

### Stampede, in its own article

Several coloured requests arrive while the cache is empty. Their overlapping
source work is visible without duplicating all the tables. A later contrasting
version holds waiting requests at the server while one refill supplies them.
This is necessarily busier; it should not be folded into the introduction.

## Coordinator recommendation

refinements, then use the same drawing vocabulary for the expiry example.
Avoid another wholesale redesign, additional dashboards or mandatory controls.

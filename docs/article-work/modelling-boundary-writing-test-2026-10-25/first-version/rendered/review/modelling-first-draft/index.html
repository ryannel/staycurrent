Relational data modelling

Deep diveAbout 21 minutesAI-generated

A relational data model says which facts a database can remember and how those facts belong together. An order has a customer. A line on that order has a product, a quantity and an agreed price. A payment settles an order. Choosing where those facts live decides whether a name correction changes one row or twenty, whether a product can exist before anyone buys it, and whether the database can distinguish two lines for the same product.

The tables may all have primary keys and valid foreign keys and still express the wrong thing. A key that allows each product only once per order rules out separate lines. A row that combines an order line with a payment suggests a connection the shop never recorded. The first modelling question is what one row means; columns and keys follow from that answer.

Every example follows the same small shop. Mina Shah, customer 1, places order 103 with one blue mug, P7, at 20.00 and two packs of green tea, P3, at 4.50 each. The lines total 29.00. Order 101, also Mina’s, has two lines and two payments. Edda Berg, customer 3, has no orders. The examples add hypothetical catalogue and supply rules where a different shape of fact needs them; they do not change that starting snapshot.

A useful design lets each fact be recorded, corrected and removed at the level where it belongs, while retaining the links needed to read the whole purchase. Normalisation gives us tests for facts repeated in the wrong place. It works alongside the business rules: it cannot decide whether repeated products are allowed, what a payment settles, or what the shop needs to retain after a sale.

What one row represents

State a table’s row meaning as a sentence with a precise subject. One row of orders says that this order was placed by this customer at this time and has this status. One row of order_items, an order line, says that this numbered line on this order is for this quantity of this product at this agreed unit price. One row of payments says that this payment settled this amount against this order by this method.

The level of detail represented by one row is often called its grain. An order, an order line and a payment have different grains. The fact that they appear together on a receipt does not make them one thing.

Order 101 shows why. It has green tea worth 4.50 and a teapot worth 35.00. Payment 501 pays 30.00 by card; payment 502 pays 9.50 by gift card. Match each line to each payment through their order number and watch how often each amount appears.

Each line appears twice, once beside each payment. Each payment appears twice, once beside each line. Adding either amount column in the combined rows gives 79.00, twice the order’s 39.50. Nothing is wrong with the stored amounts. The combined result has one row per line–payment combination, so it is the wrong grain for either sum.

Keep lines and payments as separate facts. A report can total each list per order before combining the totals; Queries develops that work. If the shop really needs to record which payment paid for which line, it needs an allocation relationship with its own amount. No such allocation can be inferred from these four combinations.

The row sentence also exposes missing cases. A payment row cannot stand in for an order, because pending order 103 has no payment. An order line cannot stand in for a product, because a catalogue product can exist before its first sale. Give each of those facts a row that can exist independently.

Keys and identity

A key identifies a row in every state the design permits, not just in the sample on the page. Mina, Tariq and Edda happen to have different names. That is no reason to make name a customer key: two customers can share a name, and one customer can change theirs without becoming someone else.

A superkey is a set of columns whose values identify at most one row. A candidate key is a minimal superkey: remove any column and it no longer has that guarantee. “Minimal” concerns the columns needed for the guarantee, not the shortest value or the smallest number the database can store. With customer_id unique, (customer_id, name) is a superkey but not a candidate key; the name adds nothing to identification.

Choose one candidate as the primary key. The other candidates remain uniqueness rules. A shop’s product code can be a natural key if the business assigns it uniquely and keeps its meaning stable. A database-generated number is a surrogate key: its job is identification rather than describing the product. Either can work. Ask who assigns the value, whether it can change or be reused, and which references would have to follow a change.

A surrogate does not replace a business rule. If a product code must be unique, adding a product_row_id does not make two rows with the same product code acceptable. Retain that uniqueness rule as well as the new primary key. Conversely, do not impose uniqueness on a name just because an ID would otherwise allow duplicate names. The two columns express different rules.

Composite keys

An order line’s line_no is local to its order. Both order 101 and order 103 have a line 1. The pair (order_id, line_no) is the line’s composite key: several columns identify it together.

Two possible line identities, with different business rules
KeyWhat it permitsWhat it rules out
(order_id, line_no)Separate numbered lines for the same product.Two different lines with the same number in one order.
(order_id, product_id)One line per product per order, with quantity on that line.A second line for the same product on that order.

Suppose the shop wants P7 on a possible line 3 of order 103 as well as on line 1: perhaps the lines have different agreed prices or fulfilment instructions. The numbered-line key can distinguish them. The order–product key cannot. This is a test of what the structure permits, not another purchase in our snapshot.

A separate line_id can give each line a single-column reference, which may be convenient when other records refer to a line. It still leaves the business decision open. Keep (order_id, line_no) unique if line numbers must not repeat, and add uniqueness on (order_id, product_id) only if a product must occur once. Making every row numerically distinct does not tell you whether the rows describe a forbidden duplicate.

Keep identity separate from display order too. If lines must remain identifiable after a receipt is rearranged, decide whether line_no is a stable line number or an editable position. An identifier people refer to should not silently change meaning when a list is sorted. Identifier types and storage costs belong in Values and Indexes; the modelling choice comes first.

Relationships and cardinality

A relationship needs rules in both directions. One customer can have many orders; each order has one customer. “Many” is a maximum, and says nothing about whether any must exist. Edda has zero orders. The shop nevertheless requires every order to name a customer.

Cardinality describes those limits. Read 0..many as zero or more, and 1..1 as exactly one. Writing the minimum as well as the maximum prevents “one-to-many” from hiding an optional relationship.

Read each relationship from both ends
Starting rowRelated rowsHow the structure records it
One customer0..many ordersSeveral orders can carry the same customer ID.
One order1..1 customerA required customer reference on the order.
One order line1..1 order and 1..1 productBoth references on the line.
One order0..many paymentsEach payment references its order; none is required just to record a pending order.

For a one-to-many relationship, put the reference on the many side. An order’s one customer_id names its customer. A list of order IDs in a customer row would have to grow with every purchase and would repeat the relationship if the order stored its customer too.

A one-to-one relationship adds an upper bound on the referencing side. A separate row of optional product details, keyed by the same product ID, can give each product at most one details row. Making its product reference required ensures every details row has a product. It does not ensure every product has details: the product can exist with no referencing row. That reverse minimum needs a separate rule. Foreign keys, required values and uniqueness implement different parts of these statements; Constraints explains their enforcement.

Many-to-many relationships

An order can contain many products, and a product can appear on many orders. An order line connects the two. Its quantity and unit_price describe that occurrence of the relationship, not the order or product alone. P3 can appear once on one line and twice on another, without either row contradicting the product.

A junction table for a relationship that is a unique pair can use the two references as its key. Order lines need the extra distinction we chose earlier: one order–product pair may have several numbered occurrences. The many-to-many label describes the relationship’s ends, but does not decide its row identity.

Relationships involving three things

Some facts involve more than two participants. Suppose a supplier offers a product to a particular shop location. Knowing that S1 supplies P7, that S1 serves North, and that North receives P7 does not establish that S1 offers P7 to North. Each pair could be true through a different offer.

A row of offers(supplier_id, product_id, location_id) keeps the complete statement together. Under a rule of one current offer per triple, the three references form its key. An offer price would belong to that triple if it can vary by all three. The reconstruction in Decomposing tables safely makes the false offer visible.

Functional dependencies

A functional dependency says that agreement on one set of columns requires agreement on another. Write customer_id → name, read “customer ID determines name”. For the customer’s current name, two rows naming customer 1 must not disagree. The arrow is a rule about permitted data, not a description of the order in which code runs.

A few rows can disprove a proposed dependency: two rows with the same customer ID and different current names contradict it. They cannot establish it for every future row. Our three distinct names do not prove name → customer_id. That would require a business rule forbidding two customers with the same name.

Imagine a flattened table with one row per order line, carrying the order date, customer name and current product details on every row. Its row identity is still the line key, but smaller sets of columns determine some of its facts.

What determines each fact in the illustrative flattened table
DeterminantFacts it determines
order_idCustomer ID, placed-at time and order status.
customer_idThe customer’s current name.
product_idThe product’s current name and catalogue price.
(order_id, line_no)Product ID, quantity and agreed unit price for that line.

The columns before an arrow are its determinant. They need not identify the whole flattened row: customer 1 determines one current name but appears on several lines. That mismatch is where repeated facts enter. Figure 2 separates them in stages. Start with the flattened rows, then use Next to follow the references that remain.

Update, insertion and deletion anomalies

In the flattened design, a correction to Mina’s current name needs every row for customer 1 to change. Correct one and overlook another, and two answers now claim to be her current name. This is an update anomaly. A transaction can make one chosen set of edits succeed together, but it cannot make a missing edit part of that set. Moving the name to one customer row removes the copies that could disagree.

A new product presents an insertion anomaly. If its name and price have a home only on order-line rows, recording it requires a sale that has not happened, or a special incomplete row that is not an order line. A separate product row can describe it before any orders exist. Edda’s customer row works the same way: being a customer does not depend on already having bought something.

A deletion anomaly appears when removing an association removes an independent fact as well. P9 occurs on just one line in the snapshot, order 101’s line 2. If that flattened row were its only record, deleting the line would also erase the teapot’s catalogue details. With separate products, removing a line removes that purchase association; it need not remove P9.

Repetition alone is not the diagnosis. Customer 1’s ID belongs on both of Mina’s orders because it records two relationships. Removing either reference would lose which customer placed that order. The repeated current name is different: both copies claim one fact that can change independently of either order.

Normalisation

Normalisation uses dependencies to diagnose a table and, where necessary, split it into tables with clearer row meanings. The resulting normal forms name particular conditions a design meets. They help explain why the repairs in Figure 2 work; they are not a substitute for deciding what the facts mean.

Repeating groups and first normal form

Before the flattened table, there is a simpler trap: product_1, quantity_1, product_2, quantity_2 on an order. A third line needs more columns. Finding orders containing P7 must examine every product column, and each new slot changes that work. The design makes an arbitrary number of lines part of the table’s structure.

Encoding the products as "P7,P3" in one text value removes the column limit but leaves individual lines hidden inside the value. The database sees one string; referring to a line, attaching its quantity or checking its product requires unpacking it. Putting each line in its own row gives the same operation to the first and the hundredth.

First normal form treats each attribute value as one value from its domain rather than a repeating group. Numbered scalar columns can still pass that value-level test; they leave the arbitrary line limit in the schema. What counts as one useful value depends on the operations: a name need not be split into characters, and a document may be treated as a document. Here a list of products is the wrong unit because the shop must identify and constrain each line separately. Values develops those choices. Separate line rows solve addressability, but our flattened line table still repeats names and order dates, so the diagnosis continues.

Partial dependencies and second normal form

The flattened line key is (order_id, line_no). Quantity needs both columns: order 103 has a quantity of 1 on line 1 and 2 on line 2. The order’s placed-at time needs only order_id. It is therefore partially dependent on this composite key, and is repeated for every line of the order.

Second normal form removes partial dependencies of non-key attributes on candidate keys. In this simple case, move the order’s facts to orders, one row per order, and leave the order reference on each line. Figure 2’s first step does this. The date now has one place to change, and an order can have a row before its lines are assembled.

Adding a surrogate line_id does not perform that repair. If the numbered-line uniqueness rule is retained, (order_id, line_no) remains another candidate key, and the partial dependency remains. If that rule is dropped, the set of candidate keys and the normal-form diagnosis may change, but the order date is still copied across lines. A new ID cannot remove the duplicated fact.

Transitive dependencies and third normal form

After moving order facts out, suppose orders still contains customer_id and the customer’s current name. The order determines its customer, and the customer determines their name: order_id → customer_id → name. That is a transitive dependency. A current-name correction would still need both of Mina’s orders to change.

Move the name to customers(customer_id, name) and retain customer_id on orders. For this schema, that removes the transitive dependency that prevents third normal form. The product’s current name and catalogue price need the corresponding home in products. The lines retain the product reference and their own agreed price.

The familiar advice that a non-key fact should depend on “the key, the whole key and nothing but the key” is useful for these repairs. It is not the full definition of third normal form when candidate keys overlap. Boyce–Codd normal form, or BCNF, gives the stronger rule: every non-trivial determinant must be a superkey. “Non-trivial” excludes an arrow that merely repeats columns already on its left. A determinant that identifies only part of what a row asserts deserves investigation.

A normal-form label is relative to the dependencies you have established. Inventing a uniqueness rule to pass a test changes which business states are allowed. And reaching a normal form does not prove that a required relationship is present, that an agreement is retained, or that a deletion policy is right. Those are still modelling questions.

Decomposing tables safely

Splitting a table is a decomposition. To check a split, put the pieces back together and ask whether you recover exactly the original facts. Returning fewer associations would lose some; returning extra associations would make it impossible to tell which were real. A split that preserves the information is lossless.

Consider separating the order facts in Figure 2. An order row for 103 holds its customer and placed-at time; each of its two line rows retains order_id = 103. Reconstructing a flattened row matches each line to exactly that order row. It gets the same order facts for both lines and cannot attach either to order 101, because the order ID is preserved.

The guarantee comes from the rule that order_id identifies one order row. It is not just that these two sample orders happen to match correctly. In every permitted state, each line has one existing order to match. Choosing columns that happen to connect the sample is weaker. Figure 3 tries a split through the customer instead.

The split retains which orders belong to Mina and which products Mina bought. It no longer retains which order each product was on. Reconstructing through customer 1 places P7 on order 101 and P9 on order 103, neither of which was there. “Lossy” describes the lost distinction, not necessarily a shorter result.

This is why a decomposition needs the relationships as well as the attributes. A list of all the original column names is not enough. Preserve the key that binds a fact to the rest of its row, then check the reconstruction against the rules that will hold for future rows too.

Why three pairs do not always make one fact

The supplier offer from earlier has the same danger even if we keep every pair. In this hypothetical catalogue, S1 offers P7 to South and P3 to North; S2 offers P7 to North. There are three offers in all. Step through Figure 4 and watch the candidate offer S1–P7–North.

All three pair lists contain something that supports the candidate. S1 and P7 occur together through South. S1 and North occur together through P3. P7 and North occur together through S2. None of that makes S1’s offer of P7 to North true. The complete triple must remain a fact unless the shop declares a stronger rule under which pairwise compatibility really does establish an offer.

Keeping rules checkable

Preserving the rows and preserving the dependencies are separate goals. A decomposition is dependency preserving when the dependencies can be checked on its separate tables, with their consequences together enforcing the original rules. Reconstructing the original rows correctly does not automatically give that property.

The customer split makes the current-name rule local: one customer ID has one name in customers. A different lossless split could leave the information needed to check a rule scattered across tables, requiring them to be read together. That is a practical cost when every write must establish that the rule still holds. Keys and references make many common rules local, but do not express every possible dependency.

The planned companion Normalisation and decomposition will develop candidate-key derivation, precise normal-form tests and decomposition procedures, including cases where BCNF and dependency preservation pull in different directions. It is not available yet. For an ordinary schema review here, name the dependencies, check that the split preserves the associations, and identify where each rule can be checked. Overlapping keys or several plausible splits are reasons to do the deeper analysis.

Independent multivalued facts

Functional dependencies do not account for every kind of repetition. Suppose P7 has tags blue and gift, and two suppliers, S1 and S2. The tags describe the product independently of who supplies it. In a table with one product, tag and supplier per row, what does an individual combination mean?

If the table is to represent both complete sets without implying a tag–supplier pairing, it needs all four combinations. Adding a third tag requires another row for each supplier. Removing one supplier means removing every row carrying that supplier while leaving the tag set intact. The repetition grows as the product of the set sizes.

None of product_id, tag or supplier_id determines the other two under these rules. The dependency is instead that a product’s set of tags is independent of its set of suppliers: a multivalued dependency. Split the table into product_tags(product_id, tag) and product_suppliers(product_id, supplier_id). Each pair is unique in its own table. Recombining the two sets produces the four combinations, and independence is precisely why that is safe here.

This is the problem addressed by fourth normal form. It can arise even after a design has passed the functional-dependency checks. The contrast with the offers is essential: tags and suppliers were declared independent, while an offer’s location restricts which supplier–product combinations exist. Do not split a real three-way relationship merely because three columns look like two lists. The planned normalisation companion will cover the formal multivalued and join-dependency tests.

Historical facts and derived data

Two equal values are not necessarily copies of the same fact. P7’s catalogue price and the unit price agreed for order 103’s line 1 both start at 20.00. Their equality at purchase time does not mean one can replace the other.

Current price and agreed price

Suppose the shop later raises P7’s catalogue price to 22.00. The agreed unit_price on the existing line remains 20.00. Compare which values move.

The catalogue answers what the shop asks now. The line answers what was agreed for this purchase. They have different subjects and different reasons to change. Keeping the agreed price on the line is therefore not an update anomaly, even though it once matched the catalogue.

A model that stores only product_id and looks up today’s price cannot reliably reconstruct the agreement. Discounts or negotiated prices could have made it different even at the time. Decide explicitly which purchase facts must be retained. A product’s current description, a description printed on a past receipt and the catalogue description at a particular date can be three different facts. History develops how to represent versions, effective dates and corrections; retaining the line’s agreed price is the immediate modelling decision.

Totals, caches and denormalisation

Order 103’s total in this model is calculated from its lines: 1 × 20.00 + 2 × 4.50 = 29.00. Storing 29.00 on the order as well creates a derived copy. If a permitted correction changes a quantity or agreed price, that copy needs to change with it. Otherwise the stored total and the lines give different answers to the same question.

A derived copy can be useful. A frequently requested total may save repeated aggregation over a large set of lines. Storing a repeated or precomputed result deliberately for such a saving is denormalisation. It trades read work for maintenance work and the possibility of disagreement. For these two lines, the illustration establishes no performance benefit.

Before accepting a stored total, specify its authority and maintenance. If the lines are authoritative, say which changes refresh the total, whether readers may see a stale value, and how to rebuild and compare it from the lines. A rebuild route is what makes a cache disposable rather than another uncertain source of truth. If a final invoice amount is instead an independent agreement, give it that meaning and define how it relates to the lines; calling it a cache would hide the rule.

Measure the saving on the queries that need it before taking on that maintenance. Indexes covers reducing read work, and Transactions covers maintaining related changes under concurrency. The structural question is whether the extra value is an independent fact, an authoritative calculation, or a copy that can be rebuilt.

Modelling variations in the data

The shop’s core tables give each kind of row a fairly uniform set of attributes. Product descriptions and classifications often vary more. The same questions still apply: which facts belong together, which distinctions must be preserved, and which rules should the database be able to check?

Shared attributes and subtypes

Tea and teaware share product identity, name and catalogue price. Tea might also have a leaf style; teaware might have a capacity in millilitres. One option is a products table with a type column and both specialised columns. A leaf style does not apply to a mug; capacity may not apply to a pack of tea. Those missing values need a clear meaning, rather than treating “not applicable” and “not recorded yet” as interchangeable.

For a small, stable set of specialised attributes, one table can be straightforward. Its rules must say which fields apply to each type. As the types grow, an alternative is a common product row with separate subtype rows:

Schema sketch: a common identity with specialised details
TableRow meaningIdentity and reference
productsA product, with shared name and price.product_id is its key.
tea_detailsTea-specific details, such as leaf style.product_id is both its key and a reference to products.
teaware_detailsTeaware-specific details, such as capacity.product_id is both its key and a reference to products.

The shared identity lets order lines keep one product reference regardless of subtype. Each details table can hold at most one row per product. It still leaves two questions unanswered. May a product have both kinds of details, or are the subtypes disjoint? Must every product have one of them, or may the catalogue contain other products? Those are business rules, not consequences of drawing two subtype tables. Choose them explicitly, then arrange their enforcement as Constraints describes.

Recursive relationships

A category can relate to another category in the same table. For a tree, categories(category_id, name, parent_id) gives each category at most one parent, with parent_id referring to another category’s key. A root has no parent. In a hypothetical shop classification, Shop contains Tea and Teaware, and Teaware contains Cups.

If Cups must also appear below Gifts, one parent column no longer expresses the requirement. A separate category_edges(parent_id, child_id) table permits several parents, with each pair unique. That is a different structure from a tree, and a descendant can now be reached through several paths.

Either design needs a cycle rule if the hierarchy must be acyclic. A foreign key can confirm that a parent category exists; it does not stop Teaware naming Cups as its parent while Cups already names Teaware. Both references would find real categories, but following parents would never reach a root. Even a ban on self-parenting would miss this two-category cycle.

The planned companion Modelling hierarchies will compare parent references, edge tables, paths, closure tables and nested sets, with traversal and reparenting procedures. It is not available yet. Use that deeper treatment when subtree reads, several parents or frequent moves determine the design. The first decision here is whether one parent is a true rule, and what must remain true when a category moves.

Tables, JSON and entity–attribute–value models

A product’s variable descriptive material need not become a column for every possible sentence. A small JSON document for care instructions or display notes can keep a piece of content together when it is usually read and edited as one unit. Its structure should still be predictable enough for the operations that use it. A document that changes independently in several parts may contain several facts that would be better represented separately.

Putting established relationships inside a document changes the work. An order with a JSON array of product IDs and quantities hides the numbered lines from ordinary keys and references. PostgreSQL can validate JSON syntax, query its contents and enforce some rules through expressions, but a product ID inside an array is not automatically a foreign key to products. Preserving line uniqueness and product validity now needs additional machinery. Flexibility has moved the rules; it has not removed them.

An entity–attribute–value design, or EAV, makes the flexibility into rows, such as (product_id, attribute_name, value). It can suit user-defined attributes whose names are themselves data. For established attributes it makes simple questions harder: which attribute names are valid, what type belongs to each, which are required, and how many values may each product have? If every value is text, comparing capacities numerically requires interpreting the text first.

A metadata model with typed values and explicit rules can answer those questions, but it is a model to design and maintain in its own right. It is not free generality. Keep product identity, order relationships and stable attributes visible when the database must join, compare or constrain them. Use a document or attribute model for variability the application actually needs, and define where it ends. Values covers the representation choices; the PostgreSQL documentation’s JSON design guidance discusses keeping documents coherent.

Assessing a schema

A schema is easier to judge by trying changes than by admiring its table diagram. Start with a concrete requirement, walk the rows it needs, and say which rule permits or rejects it. The shop gives us a small set of useful trials.

Walk a proposed design through ordinary changes
Try thisWhat the shop model should let you say
Register a customer with no orders.A customer row can exist alone, as Edda’s does. No invented order is needed.
Add a product before its first sale.A product row can exist without an order line. Its identity and catalogue facts have their own home.
Put P7 on two separate lines of one order.The numbered-line key distinguishes the occurrences. If the shop forbids them, an additional order–product uniqueness rule says so.
Settle one order by card and gift card.Two payment rows reference one order, as 501 and 502 do. Neither needs to be attached to a line.
Correct a current customer name.One customer row changes. Orders retain the same customer identity.
Remove an order line.The purchase association disappears without erasing the product. Whether removing a placed line is allowed is a separate retention rule.

Then try the reads. Can you list a customer’s orders, reconstruct an order’s numbered lines at their agreed prices, and find the amount still due? Order 103 must still appear when it has no payment. Separate lines and payments must not multiply either total, as Figure 1 showed. These questions expose a missing relationship or a mistaken grain before query syntax obscures it.

Finally separate structural guarantees from remaining obligations. A required customer reference can make every order name an existing customer. It cannot require every customer to order. A line key prevents two lines sharing one number, but does not ensure an order has at least one line or that line numbers have no gaps. A product reference says the product exists; it does not reserve stock. A positive payment amount says nothing about whether payments exceed the amount due.

Record those obligations with the design. Decide where to enforce them and what a correction or deletion should mean, using Constraints, History and Transactions for their working detail. A good model makes the facts and their relationships clear enough that these rules can be stated precisely, and ordinary changes have an unambiguous place to happen.

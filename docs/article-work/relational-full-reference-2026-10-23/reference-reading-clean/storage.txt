 Databases and storage
Storage and durability
 Deep diveAbout 30 minutesPostgreSQL 18, with InnoDB (MySQL 8.4), SQL Server and SQLite comparisons AI-generated
 Durability is the promise that a committed change survives a crash. Once the database tells your application that COMMIT succeeded, the change must still be there after a power cut, a kernel panic or a killed server process. Relational databases keep that promise through the way they store data: how rows sit on disk, how they are copied into memory to be changed, and what is written to disk before the reply.
 Every example follows one change. A shop’s products table holds P7, a blue mug priced at 20.00, and an UPDATE raises it to 22.00.
 BEGIN; UPDATE products SET current_price = 22.00 WHERE product_id = 'P7'; COMMIT;
 Memory is fast and lost in a power cut. Disk survives, but every write to it is slow. So where does P7 live, and what has to reach the disk before the database can say COMMIT?
 In most engines the answer has the same shape. P7 lives inside a fixed-size page, and the engine changes a copy of that page in memory. At COMMIT it appends a small record of the change to a log, and waits until the drive confirms the record is stored. The page itself goes to disk later. If the server crashes first, the engine replays the log to bring the page up to date.
 Two more facts shape what a table costs. Some engines keep a table as a heap that indexes point into; others store the rows inside the primary-key index, which is why the choice of key affects size and insert speed. And a change never simply erases the old row. The old version is kept until no transaction needs it, so tables grow and rarely shrink.
 The wait at COMMIT is the main cost of a commit. On a drive that takes 5 ms to flush, one client can commit at most 200 times a second; concurrent commits share flushes, which raises the total. Every change is also written at least twice, once to the log and once to its page. Most storage settings trade that wait, and the page writes behind it, against what a crash can take away and how long recovery takes.
 The promise has two limits. It holds only if the storage really keeps what it reports as flushed, and only for this one machine: a lost disk or a mistaken DELETE needs another copy. Within those limits there are two ways to weaken it. Relaxing the wait can lose the last few commits. Turning off the safeguards can corrupt the database.

Where the numbers come from
Pages
 Relational engines store a table as a file of fixed-size pages, and every row lives inside one page. To read one row, the engine reads the whole page that holds it. The size differs: PostgreSQL uses 8 kB, InnoDB 16 kB by default (fixed when the instance is created), and SQLite 4 kB by default, adjustable from 512 bytes to 64 kB.
 A row can’t span two pages, so a value too wide for one is stored elsewhere and referenced from the row.
 PostgreSQL keeps each table as a heap, with rows wherever there is room. InnoDB keeps it as a B-tree ordered by primary key, and SQLite as one keyed by an integer rowid. SQL Server lets each table be either a heap or a clustered index on a key you choose. What that changes for a lookup and for the choice of primary key is explained in Indexes.

 Every index on a table is stored in pages too, and one row change usually touches several. An insert adds an entry to every index. Which indexes an update changes depends on the engine.
 InnoDB, SQL Server and SQLite change only the indexes whose columns changed. In InnoDB every secondary index holds the primary key, so changing the primary key changes them all. PostgreSQL adds an entry to every index unless no indexed column changed and the new row version fits on the same page. What that costs each write is explained in Indexes.
 Each of those pages is changed in memory first and written to disk later, and every change is logged. That is why a table with many indexes writes more log per row, and why a commit that touches one row can still change pages in several places.

The first part of the row
 Moving a value out keeps pages dense for the queries that don’t need it. A query for P7’s price never touches its 50 kB description, while SELECT * fetches and sends it every time. In PostgreSQL an update that leaves an out-of-line value unchanged keeps the existing copy, so raising the price doesn’t rewrite the description. SQLite reads an overflow chain only as far as the columns a query needs, which is why wide columns are best declared last.
 Below the threshold, a wide value stays in the row and costs every reader. A 1,900-byte description stays in line in PostgreSQL, because with its 4-byte length header the row comes to 2,028 bytes, just under the 2,032-byte threshold. It leaves room for only four rows on a page, so a scan of the table reads fifteen times as many pages as it would for the 100-byte rows above.
 Buffer pool
 No engine reads or changes a page on disk directly. Each keeps a cache of pages in memory, called the buffer pool, and works only on the pages in it. To read P7, the engine first needs page 12 in a slot.
 PostgreSQL calls its pool shared buffers, shared by every connection, and starts it at 128 MB, or 16,384 pages of 8 kB. InnoDB’s buffer pool also defaults to 128 MB. SQLite has no server, so each connection keeps its own page cache, about 2 MB by default.

PostgreSQL’s EXPLAIN (ANALYZE) reports these counts on each plan node, in a line such as Buffers: shared hit=3 read=1.
 A read doesn’t always reach the drive, because the operating system keeps its own cache of file data. PostgreSQL leans on that cache, where InnoDB bypasses it. The two caches, and how to size the pool, are covered in The buffer pool.
 What matters here is that the pool is memory, so a crash empties it. The first queries after a restart read from disk, and a recovered server can be correct and still slow until its working set is back.
 Row versions and undo logs
 An update can’t simply overwrite P7. A long report that began before the update must still see 20.00, the value as it was when the report started. If the update rolls back, 20.00 has to come back too. So the engine keeps the old version of the row somewhere.
 Where it keeps it is the largest design difference between the engines, and it decides what a long-running transaction costs. The figure runs the same update in PostgreSQL and in InnoDB.  Free space and fill factor
 Once no snapshot needs an old version, its space is free. Engines reuse that space for new rows, but rarely give it back to the operating system, so a table that grew during a long transaction usually stays that size on disk.
 PostgreSQL’s VACUUM marks the space reusable and returns only empty pages at the very end of the file. InnoDB, SQL Server and SQLite also reuse freed space inside their files. Getting the space back means rewriting the table, and every rewrite costs something:
 PostgreSQL’s VACUUM FULL copies the table under an exclusive lock that blocks reads and writes, and logs the whole copy.
 MySQL’s OPTIMIZE TABLE rebuilds an InnoDB table, and the space returns to the operating system when the table has its own file, which is the default.
 SQL Server compacts a table inside its file when the table or its clustered index is rebuilt. Only DBCC SHRINKFILE returns space to the operating system, and it moves pages and leaves indexes fragmented.
 SQLite’s VACUUM rebuilds the whole file, and auto_vacuum can trim it as pages free up.
 Free space can also be left on purpose. PostgreSQL’s table fillfactor, from 10 to 100 and 100 by default, sets how full an insert may make a page. The rest stays free for updates.
 That free space is what lets an update put P7’s new version on page 12 beside the old one. When no indexed column changed, the update then adds no index entries at all. PostgreSQL calls this a HOT update, for heap-only tuple. For a table whose rows are updated often, a fill factor of 80 or 90 makes those cheap updates more likely, at the cost of more pages for every scan.
 In InnoDB, and in a SQL Server table with a clustered index, the table is an index, so its fill factor is an index setting applied when the index is built or rebuilt. Its main use is preventing page splits, which are explained in Indexes.
 Dirty pages
 A dirty page is a page in the buffer pool that has changed since it was last written to disk. After the update, page 12 in memory holds the 22.00 version, while page 12 in the table file still holds only 20.00. A dirty page has to be written out before its slot can be reused for another page.
 A dirty page may also hold a change from a transaction that has not committed yet. Writing the page doesn’t wait for that commit, so the table files can contain uncommitted changes. After a crash, those changes have to be undone or hidden, using the old versions described above.

 The drawing keeps the update record in memory until COMMIT; a background flush may write it to disk sooner.
 The log records reached the disk before the reply, and page 12 reached the table file only later. That order gives the log its name. PostgreSQL’s write-ahead log, or WAL, is a record of every change to a page, precise enough to repeat it. InnoDB’s redo log does the same job.
 Both append records to the end of a file and number them with a log sequence number, or LSN: a position in the log that only grows. Each page remembers the LSN of the last record that changed it, which is the page LSN the figures show.
 That order is a rule, the write-ahead rule. Before a dirty page goes to the table file, the log up to that page’s LSN must already be on disk. The reason is recovery: a page on disk may already hold a change, perhaps from a transaction that never commits, and after a crash only that change’s log record lets recovery finish it or undo it. A page written before its record could hold a change that nothing on disk describes.
 The table file still said 20.00 when the application heard COMMIT, and that’s fine, because the log on disk can rebuild 22.00.
 Who writes a dirty page
 If commit writes the log and not the pages, something else must write the pages. Which writer does the work decides where the cost lands.
 PostgreSQL has three writers. The checkpointer writes every dirty page on a schedule, so that crash recovery has less log to replay. The background writer writes some dirty pages early, so that queries find clean slots. And a query that needs a slot, and finds the page chosen for eviction dirty, must write that page out itself before it can read.

SQLite has no background writer: the connection that commits writes its own pages. PostgreSQL reports how many pages each of its writers flushed, and the PostgreSQL series reads those counts in WAL, checkpoints, and recovery.
 What COMMIT waits for
 While a transaction runs, its log records collect in a buffer in memory: the WAL buffers in PostgreSQL, the log buffer in InnoDB. At COMMIT the engine appends a commit record, writes the buffer to the log file, and asks the operating system to flush the file. Only when the flush returns does it reply.
 The flush is the slow step, because it waits for the storage to confirm. So a single client committing one row at a time can’t commit faster than the storage flushes, however fast the processor is.

 Group commit
 Sixteen clients get eight times the throughput because their commits share flushes. Their commit records sit in the same log buffer, so one flush makes all of them durable, and every one of them gets its reply.
 A commit that arrives during a flush waits for the rest of it and then the whole of the next. With every client committing again the moment it’s answered, nearly every commit arrives just as a flush starts, so each waits almost two: 10.2 ms, twice 5.1.
 Sharing a flush this way is called group commit. PostgreSQL does it, and InnoDB does it for its redo log and its binary log. The figure models the ceiling it sets. A drive with a slow flush limits a write-heavy workload more than its raw bandwidth would suggest. SQLite has nothing to group, because it allows one writer at a time.
 Log records and MySQL’s binary log
 Redo and write-ahead records describe changes to pages, in a form precise enough to repeat. They are not SQL statements. Replaying a statement against whatever data happens to be there could give a different answer; replaying a page change gives the same page.
 MySQL also keeps a binary log, a separate record of changes written for replicas and for point-in-time recovery. It describes changes in terms of the data rather than the pages. Both logs are written at commit.
 SQLite’s rollback journal and WAL mode
 SQLite’s default mode works the other way round. Before changing a page, it saves the page’s original contents in a rollback journal. It then writes the new pages into the database file, flushes them, and deletes the journal. The deletion is the commit.
 After a crash, a journal that is still there means the commit never finished, and SQLite copies the saved pages back. A commit in this mode needs several flushes: two for the journal and one for the database file.
 SQLite’s WAL mode works like the logs above instead. Commits append page frames to a separate file, and a frame marked as the end of a transaction is the commit. The first connection to open the database after a crash reads the log, ignoring frames whose checksums fail. A commit in WAL mode needs one flush instead of several, and the log is written in order, which is a large part of why it is faster. The pages still reach the database file a second time, when a checkpoint copies them back.
 Crash recovery
 Crash recovery replays the log after a crash to bring the table files up to date. It doesn’t start at the beginning of the log. It starts at the last checkpoint: a log position before which every change is already in the table files.
 Each record is applied only where it is missing. Recovery compares the record’s LSN with the LSN on the page it changes. If the page is older, the change is missing and recovery applies it. If the page already has it, recovery skips it, so no change is applied twice.
 Checkpoints keep that replay short. Each one makes sure every page changed before a log position is in the table files, then records the position. Log before it is no longer needed for recovery and can be reused. Checkpointing more often means less to replay, but more page writes, because a page that keeps changing is written again after each one. PostgreSQL checkpoints in rounds, every 5 minutes or sooner when the log grows fast; InnoDB and SQL Server move the position forward continuously. How to size that trade is in the companion, Checkpoints, torn pages and the log.
 Replay also needs a whole page to apply records to. A torn page, one only partly written when the power failed, is part old and part new, and a record that changes a few bytes can’t fix it. So engines keep a clean copy. PostgreSQL logs a full-page image, a copy of the whole page, with the first change to each page after a checkpoint, and recovery starts from that copy. InnoDB writes each page to a doublewrite buffer before writing it in place, and recovery takes a good copy from there. The companion’s section on torn pages compares the engines and what each copy costs.
 What the crash costs depends on what it destroyed. A killed server process leaves the operating system’s cache intact, so everything the server had written survives, flushed or not.  Unfinished transactions
 Recovery brings back exactly the transactions whose commit records reached disk. The log may also hold records of transactions that never committed, and what happens to those depends on where old versions live. PostgreSQL replays them like any others, and their versions stay invisible: with no commit record in the log, the transaction counts as aborted, so no snapshot is allowed to see its versions.
 InnoDB replays the redo log first, which restores the unfinished changes too, and then rolls those transactions back using the undo log. It accepts connections before that rollback finishes, so new connections can briefly meet locks held by transactions that are being undone.
 A transaction that had changed millions of rows takes correspondingly long to undo. Killing the process doesn’t help: the rollback starts again on startup. SQLite’s recovery is the journal restore or the checksummed log described above.
 SQL Server undoes unfinished transactions at restart in the same way, so the time grows with the longest transaction that was running at the crash. Accelerated database recovery, available since SQL Server 2019 and always on in Azure SQL Database, keeps old versions in the database itself. Recovery then hides the unfinished changes instead of undoing them, as PostgreSQL does, and both rollback and restart take about the same time however long the transaction ran.
 Recovery time
 Replay time is roughly the amount of log from the last checkpoint to the end of the log, divided by how fast the server can apply it. That is why checkpoint settings set recovery time.
 On the same laptop, an update-heavy test wrote 566 MiB of log in 20 seconds, about 28 MiB a second, and the server was then stopped as if it had crashed. Replaying that log took 3.35 seconds, about 169 MiB a second. Another 0.56 seconds went on a checkpoint at the end of recovery, before the server accepted connections.
 Treat that rate as a ceiling. The log in that test was mostly full-page images, which replay quickly. The files were also in the operating system’s cache. After a reboot, or on a standby that has just started, replay can be much slower. Your own rate is worth measuring the same way, by crashing a copy under load.
 Replay is only part of the outage. The server also has to notice the crash and restart, InnoDB may still be rolling back a large transaction, and the cache starts cold. A recovery-time target should include all four.
 PostgreSQL’s server log reports where replay began (redo starts at), where it ended (redo done at) and how long replay took. The difference between the two positions is the log replayed. The PostgreSQL series reads that log line by line in WAL, checkpoints, and recovery, and what each engine adds to restart time is in the companion, Checkpoints, torn pages and the log.
 What recovery cannot repair
 Recovery replays the log it finds, so it fixes only what the log can fix. Four kinds of loss are beyond it:
 Commits whose log records were never really on disk, which is what a drive that acknowledged a flush early causes.
 Damage that is not a tear, such as a bit flip or a bad sector. PostgreSQL and InnoDB detect it with checksums, but replaying the log does not rewrite the page; the remedy is a copy from elsewhere.
 Missing or replaced files: log files deleted by hand, a SQLite journal or -wal file moved away from its database, or a data directory restored without its log.
 A lost disk.
 Checking the drive prevents the first, as the section on fsync explains. The rest is covered in Backups and recovery.
 fsync and drive caches
 Every guarantee so far rests on one report: the operating system saying that a flush has finished. PostgreSQL, InnoDB, SQL Server and SQLite all rely on it, and if it is wrong, a committed transaction can vanish.
 To make a log record durable, a database writes it to the log file and then calls fsync. That asks the operating system to put the file’s data on durable storage and to return only when it has. On Linux, PostgreSQL uses the variant fdatasync by default, which skips file metadata the log doesn’t need.
 Two caches sit between the database and the storage itself. The operating system’s page cache holds data the database has handed over but not yet flushed. The drive has its own write cache, and on many drives that cache is ordinary volatile memory. Drives sold with power-loss protection hold enough stored energy to finish writing their cache, so their cache is safe to count on. On a virtual machine or a network volume, the guarantee is whatever the provider documents an acknowledged write to mean.
 A drive that answers early loses commits in a power cut, and can corrupt the database, because the order between log and pages is no longer kept. Nothing reports it in normal running. Only a test that cuts the power during writes, or the drive’s documented protection, shows that a flush is honest.
 The flush time is also the floor for commit latency, as the commit rates showed, and it differs widely between local flash, network volumes and spinning disks. Each layer, a flush that fails and how to test a volume are covered in the companion’s section on trusting the flush.
 Asynchronous commit
 Waiting for a flush at every commit is the expensive part of a write, as the commit rates above showed. So every engine lets the reply come before the flush. This is asynchronous commit, and the trade is the same everywhere: a crash can lose the most recent commits, and nothing else. The settings differ in name and in grain.
 The setting in each engine
 In PostgreSQL, synchronous_commit = off replies as soon as the commit record is in memory, and a background process, the WAL writer, flushes it soon after. The WAL writer wakes every 200 ms by default (wal_writer_delay). Because it prefers to write whole pages when busy, the longest risk window is three times that delay: about 600 ms at the default. You can set it for a single transaction.

 With the binary log on, which is the default in 8.4, a commit also writes the binary log. With sync_binlog and innodb_flush_log_at_trx_commit both at 1, their defaults, a commit flushes both logs. After a crash, InnoDB completes or rolls back each prepared transaction so that the two logs agree.
 With sync_binlog = 0, the server leaves flushing the binary log to the operating system, and a power cut or an operating-system crash can lose its last events. That can go wrong in two directions.
 The database can keep committed transactions that its binary log lacks. Replicas and point-in-time recovery read the binary log, so those transactions never reach them.
 Or a replica may already have read events that the source then lost. The replica then holds commits the source no longer has.
 SQL Server calls it delayed durability, and it is off by default. A database set to ALLOWED lets a transaction ask for it with COMMIT WITH (DELAYED_DURABILITY = ON); one set to FORCED applies it to every commit. The log is flushed when its buffer fills, when a fully durable transaction commits, or when sp_flush_log runs.
 In SQLite, the defaults are the rollback journal (journal_mode = DELETE) and synchronous = FULL. A common tuned choice is WAL mode with synchronous = NORMAL, which skips the flush at commit. The database stays consistent, but a transaction that committed can roll back after a power loss or operating-system crash.
 Choosing what may be lost
 The settings are cheap to change and easy to regret, so decide per kind of data what its last few seconds are worth. Ask what losing them costs, and whether the data can be recovered another way: from an upstream queue or an event log, or simply rebuilt.
 Asynchronous commit suits some data and not other data in the same database. That is why PostgreSQL and SQL Server let you choose per transaction. InnoDB’s setting is server-wide, and SQLite’s synchronous pragma applies to each connection.

 Asynchronous commit never tells the application anything. COMMIT returns success either way, and the loss only shows up after a crash, by comparing with what the application remembers.
 What else asynchronous commit changes
 Other sessions see an asynchronous commit before it is durable. A second transaction can read 22.00 and act on it, sending a confirmation, say, and a crash a moment later brings back 20.00. The second transaction’s own work may survive, built on a price that no longer exists.
 A planned stop isn’t always safe either. SQL Server’s documentation warns that a shutdown or restart can lose delayed-durable commits just as a crash can, so running sp_flush_log first is the safe habit. PostgreSQL’s immediate shutdown, pg_ctl stop -m immediate, skips the shutdown checkpoint and counts as a crash: the next start runs recovery and empties unlogged tables.

 A commit is as durable as the places it has been flushed. A replica on another machine can add to the local flush, but only if the commit waits for it; after a failover to an asynchronous one, the commits it hadn’t received are gone. What each synchronous level waits for is set out in Replication and failover.
 The commonest way to lose track of a commit has nothing to do with storage. If the connection drops while COMMIT is in flight, the application can’t tell whether it committed, however healthy the server, so its retry has to be safe to repeat, as in the crash above.
 The last row is outside what durability promises. Crash recovery faithfully keeps a committed DELETE FROM products, and a replica copies it. Undoing it needs a copy from before the mistake. Point-in-time recovery is crash recovery started from an older copy of the files, fed with a saved log, and stopped just before the mistake. How it works, and what it costs, is explained in Backups and recovery.
 Where the numbers come from
 The commit rates and the replay time come from PostgreSQL 18.6 on one Apple-silicon laptop with its internal SSD. They are observations about that machine, and show the pattern rather than typical numbers.
 For the commit rates, pgbench ran a script that inserts one row per transaction. The settings were the defaults, except that wal_sync_method was fsync_writethrough, which asks the drive to flush its own write cache. With the default method, a flush returned in a fraction of a millisecond, because macOS acknowledges a plain flush before the drive has finished, and the laptop managed about 25,000 commits a second.
 For the replay rate, an update-heavy pgbench test ran for 20 seconds after a checkpoint and wrote 566 MiB (594 MB) of log. The server was then stopped with pg_ctl stop -m immediate, which skips the shutdown checkpoint much as a crash does, and started again.
 The figures are models of documented behaviour, built from the engines’ manuals and PostgreSQL’s source. No MySQL or SQL Server instance was available, so nothing about either was measured; the row sizes are worked from their documented formulas.

 Indexes
 Deep diveAbout 35 minutesPostgreSQL 18, with InnoDB, SQLite and SQL Server comparisons AI-generated
 An index lets a database find rows by their value without reading the whole table. Ask a database for customer 42’s orders with no index, and it reads every row in the table to find them. With an index on customer_id, it looks up 42 and goes straight to the matching rows.
 It works like the index at the back of a book. The terms are sorted, so you can find one quickly, and each term lists the pages it appears on. A database index is a sorted list of values from one or more columns, and each entry records where its row is stored. The B-tree is the ordinary kind in PostgreSQL, MySQL’s InnoDB, SQLite and SQL Server, and it is this article’s subject.
 Indexes speed up queries that filter on a column (WHERE customer_id = 42), ask for a range (BETWEEN 20 AND 34) or sort (ORDER BY placed_at). They also enforce uniqueness and speed up joins on a key. In return, each index takes space, and inserts and many updates have to change it as well.
 Databases store a table in fixed-size blocks called pages: 8 kB in PostgreSQL, 16 kB in InnoDB. Each page holds many rows, and the database reads a whole page even when it needs only one row from it. So the work a query does is mostly the number of pages it reads.
 An index helps when it lets the database read fewer pages than a scan of the whole table would. That takes two things. The query’s conditions and sort order have to line up with the index’s columns, starting from the first, and few enough rows have to match. The database’s planner judges both from its estimates and may decide a full scan is cheaper, so an index that exists isn’t always used.
 Counting pages is how you choose an index, and how you check in a query plan that the database used it.

 Sequential scan
 A sequential scan, also called a full table scan, reads every page of a table in order and tests each row against the query’s conditions. In PostgreSQL a table’s pages make up its heap, so called because its rows sit in no particular order. The storage article’s Pages section looks inside one.
 The figures in this article use an invented table of 36 orders, six to a page, so every row stays visible. Most figures also show, under their counters, the same measurement on the 60,000-order table, taken in PostgreSQL 18. It holds one order a minute from 1 January 2026, placed by 1,000 customers in turn, so each customer’s 60 orders are spread through the table, while consecutive customers share pages.

 Index entries and row locations
 An index entry pairs a key with a row location. The key is the indexed column’s value. The row location is whatever the database needs to find the row again, and it depends on how the table is stored. Databases store tables in one of two ways.
 Tables stored as a heap
 Rows in a heap aren’t moved to keep an order, so an index entry can point straight at a row’s page and position. In PostgreSQL that location is a TID, short for tuple identifier; a tuple is PostgreSQL’s word for a stored row. A TID is a page number plus an item number on that page, and PostgreSQL shows it as the hidden column ctid. Order 3, the third row on page 0, has TID (0,3).

 Clustered tables
 The other design keeps the table itself sorted by its primary key. The table is stored as a B-tree, the structure the next section describes, and is called a clustered table. MySQL’s InnoDB stores every table this way, and its documentation calls the table the clustered index. SQLite stores tables this way too, and so does SQL Server whenever a table has a clustered index, which a primary key creates by default.
 A row in a clustered table moves when its page fills up and divides in two, so it has no fixed page and position to point at. Each entry in another index stores the row’s primary key instead. Finding a row through such an index then takes two searches: one in the index, then one in the table for the key the entry carries. The section on searching a clustered table follows both, once the B-tree has been explained.
 B-tree
 So far, nothing says how a search finds the first 42. A B-tree is a tree of index pages that lets a search jump there instead of reading the entries from the start. The sorted entries live on leaf pages. Above them, branch pages hold one key for each page below, marking where that page’s range begins; PostgreSQL’s documentation calls them internal pages. The single page at the top is the root.

 Range scans
 A range scan descends to the first entry at or above a lower bound, then reads entries in order until it passes the upper bound. B-trees serve <, <=, =, >=, >, BETWEEN, IN and IS NULL this way.

 Searching a clustered table
 With the B-tree in hand, a clustered table is easy to picture: its rows sit on the leaf pages, in primary key order. A lookup by primary key is one descent, like the searches above. Rows with neighbouring keys share pages, so a range of keys reads few pages. In a heap, rows land wherever there is room, so the key says nothing about the page.
 Any other index on the table is a secondary index, and each of its entries carries the row’s primary key. Figure 5 follows customer 42 through a secondary index on customer_id, with order_id as the table’s key.

 Selectivity and the planner’s choice of scan
 Selectivity is the fraction of a table’s rows that a condition matches. A condition matching 60 rows out of 60,000 is very selective; one matching half the table is not. The planner, the part of the database that chooses how to run a query, estimates selectivity from statistics that a command such as ANALYZE collects. Then it picks one of three routes:
 An index scan follows each entry to its row, in index order.
 A bitmap heap scan collects the matching TIDs from the index, sorts them by page, then reads each table page once. It saves repeat visits but returns rows in page order, not index order. MySQL’s Multi-Range Read does the same job, sorting row lookups before it makes them; its plan says Using MRR.
 A sequential scan ignores the index and reads every page.

 The order of reads matters too. A sequential scan reads pages one after another, which storage serves quickly, while index lookups jump around, so planners price a jumping read higher. PostgreSQL makes that price two settings, seq_page_cost and random_page_cost, which you can change.
 Selectivity belongs to the value, not the column. Four in five of the 60,000 orders are paid and the rest pending. With an index on status, a query for the paid orders was still a sequential scan of all 1,725 pages. The pending orders used the index.
 Their layout helped: they arrived in blocks of 1,000 consecutive orders, so the fifth of the table they make up sits on 365 pages. Scattered, a fifth of the rows would have touched nearly every page.
 The planner knows this only through its statistics, so a skewed value or an out-of-date count can send it the wrong way. Indexing queries shows how to tell.
 Composite (multicolumn) indexes
 A composite index has more than one key column. Its entries sort by the first column, then by the second among entries that tie on the first, and so on. The column order decides which entries sit together.

 An index on (a, b) helps a query that filters on a, or on a and b, because entries with the same a sit together. It generally doesn’t help a query on b alone, because the matching b values are spread through every a.
 More precisely, equality conditions on the leading columns, plus a range condition on the next one, limit how much of the index is read. So put the columns compared with = first, then the column used for the range or the sort.
 When the leading column has no condition, PostgreSQL 18 can still search the index once for each distinct value of that column. This is a skip scan, and MySQL and SQLite have narrower versions of it. It pays only when the leading column has few distinct values, so don’t design an index around it.

 With an index that lacks status (the covering index of the next section), PostgreSQL fetched 12 rows and threw away 2 pending ones to return 10. Its plan listed status under Filter. For a customer whose recent orders were mostly pending, it would read much further.
 That Filter line is one of three things a condition can do, and the plan tells you which:
 It narrows the scan. Equality on the leading key columns, plus one range on the next, decides where in the index the scan starts and stops. In the history query, customer_id = 42 and the date since 1 February did this.
 It is checked inside the index. A condition on a later key column is tested against each entry the scan reads. It saves table visits for the entries it rejects, but the scan reads just as many entries.
 It is checked at the table. A condition on a column the index lacks can be tested only after the row is fetched, so every rejected row costs a table visit. This is where status was.
 Adding status as the last key column moves its check into the index, as the end of the next section measures. Putting status before placed_at would narrow the scan as well, but it splits each customer’s history by status, so it suits only queries that always name a status.
 PostgreSQL lists the first two under Index Cond and the third under Filter. MySQL calls the second index condition pushdown and reports it as Using index condition. SQL Server lists the first under Seek Predicates and the others under Predicate.
 A condition reaches the index only when it compares the bare column with a value of a matching type. lower(email) = ..., customer_id + 0 = 42 or a cast applied to the column leave it to be checked at the table at best, and usually lead to a full scan. Indexing queries measures each case.
 Indexes and ORDER BY
 The history query needed no sort step, because its index entries came out in the order it asked for. So an index can answer an ORDER BY as well as a WHERE.
 The rule is the composite one: the columns the query fixes with = come first, and the columns it sorts by follow in the index’s order. An index can be read backwards as well as forwards, so reading customer 42’s entries from the end serves ORDER BY placed_at DESC from an index declared ascending.
 Four things decide whether the match works:
 Direction in a composite key. A whole index can be read forwards or backwards, but a mixed request needs a matching index. With an index on (customer_id, placed_at), ORDER BY customer_id, placed_at DESC was not served, and PostgreSQL added an Incremental Sort. An index declared (customer_id, placed_at DESC) serves it.
 Where NULLs sort. PostgreSQL puts NULLs last in ascending order and first in descending order, and an index stores them the same way. On a nullable column such as a shipped_at date, ORDER BY shipped_at DESC NULLS LAST needs a sort unless the index is declared (shipped_at DESC NULLS LAST).
 Collation. Text sorts by a collation, a set of rules for ordering strings, and an index serves only an ORDER BY in its own collation. In a database using en_US.UTF-8, ORDER BY email LIMIT 10 used the index and ORDER BY email COLLATE "C" LIMIT 10 sorted. The two orders really differ: "C" puts every capital letter first, so 'Zoe' comes before 'adam', while en_US puts 'adam' first.
 LIMIT. Reading a whole table in index order costs a table visit per row, which is more than a scan and one sort. Without a LIMIT, ORDER BY customer_id, placed_at was planned as a sequential scan and a sort. The index pays when the query stops early, as the history query does after ten rows.
 The other engines follow the same rules with their own defaults. SQLite reports a mixed-direction order it can’t serve as USE TEMP B-TREE FOR LAST TERM OF ORDER BY. MySQL can declare DESC key parts for a mixed order, and it puts NULLs first in ascending order, the opposite of PostgreSQL.
 Keep the ORDER BY in the SQL, because the index only makes it cheap. Indexing queries works through the cases that break it.
 Combining indexes
 A query with conditions on two columns doesn’t need one composite index for them. PostgreSQL can search two indexes, turn each result into a bitmap of row locations and combine the bitmaps: BitmapAnd when both conditions must hold, BitmapOr when either may.
 On the 60,000-order table, with separate indexes on customer_id and status, customer 42’s pending orders came from a BitmapAnd. It read 2 pages of the customer index and 12 of the status index, collecting all 12,000 pending entries only to narrow 60 rows down to 12. A composite index on both columns would have gone straight to the 12.
 In the other direction, customer_id = 42 OR order_id = 7 became a BitmapOr over two indexes, which no single composite index could serve.
 The planner adds a second index only when reading it looks cheaper than the table visits it saves. For order_id = 7 AND status = 'pending', the primary key led to one row in 3 pages, so the plan checked status on that row and left the status index alone.
 Choose by how the conditions combine. Conditions joined by AND that appear together in most queries belong in one composite index. Conditions joined by OR, or columns filtered in many different combinations, are better served by separate indexes the planner can combine.
 MySQL calls combining index merge, and its plan says Using intersect, Using union or Using sort_union in Extra. SQLite normally uses one index for each table in a query, so on SQLite conditions joined by AND want the composite index. Its exception is a condition joined by OR, where it can search each branch with its own index (MULTI-INDEX OR in the plan).
 Covering indexes and index-only scans
 An index-only scan answers a query from the index without visiting the table. The first requirement is columns: every column the query uses must be in the index. An index holding them is a covering index for that query.
 The history query returns total, which the composite index lacks, so each of its ten rows needs a table visit. PostgreSQL’s INCLUDE clause adds columns to every entry as stored values that are not part of the sort, as in (customer_id, placed_at DESC, order_id DESC) INCLUDE (total).
 Holding the columns is not always enough. When PostgreSQL updates or deletes a row, it keeps the old version while a transaction that began earlier might still need it. So an index entry may lead to a row version the current transaction can’t see, and the entry alone can’t say which.
 PostgreSQL therefore checks the table unless a bit in its visibility map says every row on that page is visible to every transaction. VACUUM, its cleanup of old row versions, sets the bit, and any change to the page clears it.

 Partial, expression and unique indexes
 Partial indexes
 A partial index holds entries only for rows that match its own WHERE clause. A fifth of the 60,000 orders are pending:
 <code><span class="line"><span style="color:var(--astro-code-token-keyword)">CREATE</span><span style="color:var(--astro-code-token-keyword)"> INDEX</span><span style="color:var(--astro-code-token-function)"> index_orders_pending</span></span>
<span class="line"><span style="color:var(--astro-code-token-keyword)">ON</span><span style="color:var(--astro-code-foreground)"> index_orders (placed_at)</span></span>

 This index is 35 pages, against 166 for a full index on placed_at, and inserts of paid orders skip it. A query for the ten newest pending orders read it backwards and touched 4 pages. The planner uses a partial index only when the query’s own conditions imply the index’s WHERE clause.
 Two patterns come up often. A queue of unprocessed work is a small slice of a large table, so an index on only the rows still waiting stays small however many finished rows pile up.
 Soft deletion is the other. A unique partial index such as CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL refuses a second live user with the same address, but a deleted user’s address can be used again. Indexing queries works it through.
 Expression indexes
 An expression index indexes the result of an expression instead of a column. A report of one day’s orders can’t use an index on placed_at through placed_at::date, and that cast can’t be indexed either. Its result depends on the session’s time zone, so one stored moment could give two different dates, and the index could not hold a single value for it. A fixed time zone makes it indexable:

The same question written as placed_at::date = date '2026-02-01' read all 1,725 pages. The planner matches the expression as written, in SQLite as in PostgreSQL, so even x+y and y+x count as different expressions.
 Unique indexes, foreign keys and joins
 A unique index also refuses a second entry with the same key. That is why a unique constraint is built on an index: checking for an existing copy of a key is a search in the index. PostgreSQL creates one for every primary key and UNIQUE constraint, so index_orders_pkey is one. An index on (customer_id, placed_at) declared UNIQUE would refuse two orders for one customer in the same instant.
 NULL is the exception, and the engines disagree about it. PostgreSQL, MySQL and SQLite treat NULLs as distinct from each other, so any number of rows can have a NULL key; PostgreSQL 15 and later accept NULLS NOT DISTINCT to allow only one. SQL Server allows only one NULL in a unique index, so an optional column such as a second email address needs a filtered unique index, WHERE email IS NOT NULL, to allow the rest.
 A foreign key’s referencing column wants an index of its own. If customer_id referenced a customers table, deleting a customer would have to find that customer’s orders, and without an index that is a scan of the whole orders table. InnoDB creates that index for you; PostgreSQL, SQL Server and SQLite don’t. Indexing queries measures the difference.
 The same index serves joins. Joining orders to customers, a nested-loop join takes each customer and looks up that customer’s orders through the index on orders.customer_id. A hash join or merge join reads both sides in full instead, so an index helps them only by filtering rows or supplying order. How a query runs explains the join methods.

 InnoDB updates the row in place in the clustered index and leaves a secondary index alone unless one of its columns changed. Then it marks the old record deleted and inserts a new one.
 Page splits
 When the leaf page where an entry belongs is full, the page splits: half its entries move to a new page, and the branch page above gains a pointer to it. A split can travel upwards when the branch page is full too, and a split of the root adds a level to the tree. Where new keys land decides how often this happens.

 That 90% is the index’s fill factor. You can lower it with WITH (fillfactor = 70) on CREATE INDEX, to leave more room on each page for keys that land in the middle. SQL Server’s FILLFACTOR and InnoDB’s innodb_fill_factor apply only when an index is built or rebuilt. Microsoft advises keeping the default except for an index that splits heavily under random keys, and a lower fill factor makes every scan read more pages.
 Choosing the primary key of a clustered table
 In a clustered table the primary key does three jobs at once. It orders the table, it is the row locator stored in every other index, and it decides where new rows land. A choice that suits one job can hurt another, so check all three.
 Width. Every secondary index entry carries the key, so a 4-byte or 8-byte integer adds that much to each of them. A UUID written as 36 characters of text adds 36 bytes, or 16 if stored as a binary value, and a composite key adds the sum of its columns. A table with six secondary indexes carries the key seven times.
 Insert pattern. A key that grows with time, such as an auto-increment integer or a time-ordered identifier like UUIDv7 (PostgreSQL 18 has a uuidv7() function), puts new rows at the end of the table. A random UUID puts each row on an arbitrary page, so inserts split table pages across the whole table, as Figure 10 showed for an index.
 Stability. A key that never changes keeps secondary indexes still. Changing it moves the row and rewrites its entry in every secondary index, so a value people edit, such as an email address, makes a poor key.
 Some systems need identifiers that can’t be guessed, or that several clients generate. The usual compromise is a short integer primary key for the table, with the public identifier in a unique secondary index. In a heap table such as PostgreSQL’s, the primary key is one index among several, so width and randomness cost only that index and not all of them.

 A bloated index costs more pages for every range scan and more memory for the same hot entries. Maintaining indexes shows how to measure the bloat and repair it without blocking writes.
 Building, finding and dropping indexes
 Loading a lot of data into a new or empty table goes faster without its indexes, which would otherwise be updated row by row. PostgreSQL’s documentation advises loading first and creating the indexes afterwards: the build sorts every entry at once and fills each page in turn, and InnoDB builds a new index the same way. Run ANALYZE after the load, so the planner sees the new rows.
 On a live table a build can hold up writes until it finishes, and each engine has its own way round that, which Maintaining indexes covers.
 An index that no query reads still costs every write, so the list of indexes needs pruning as well as growing. To find indexes worth removing, look for ones no query has read since the usage counters were last reset, ones made redundant by a wider index (an index on (a) beside one on (a, b)), and invalid leftovers from failed builds. Maintaining indexes covers each check in every engine and the safe order of steps for a drop.

 Designing an index for a query
 Choosing an index starts from a query, and it can be done in a fixed order. The worked case is the history query, customer 42’s ten newest orders since 1 February, which reached 13 pages once the index was shaped for it.
 Sort the query’s columns into roles. Equality conditions, the range or sort, and the columns the query only returns.
 Build the key from the roles in that order. Equality columns first, then the range or sort column, then a tie-breaker if the order needs one.
 Ask whether the equality columns narrow the table. Together they should cut it to a small fraction. If they don’t, the index will lead to much of the table anyway, as the selectivity section showed.
 Add returned columns only if the query earns it. Covering columns pay for a frequent query on a table that changes slowly.
 Create it on production-shaped data and read the plan. The conditions meant to narrow the scan should appear under Index Cond, the sort step should be gone, and the pages read should drop, as in the plan of the previous section.
 Count what it costs. Check which existing indexes it makes redundant, as Building, finding and dropping indexes describes, and what it adds to every write.

The history query’s composite index can replace the plain customer_id index, because an index on (a) is redundant beside one on (a, b). Then every write pays for one index instead of two.
 Designing for several queries
 A real table serves several queries, so design the set of indexes together rather than one per query. Suppose the orders table answers four: the history query; a customer’s order list, newest first with no date bound; the foreign-key check when a customer is deleted; and the pending dashboard. The composite index (customer_id, placed_at DESC, order_id DESC) serves the first three, because each fixes customer_id and needs at most the columns that follow it, in that order. The partial index on pending orders serves the fourth. Two indexes answer four queries, where one index per query would have made four, and Figure 9 showed what each extra index adds to every insert.
 Queries that join tables, page through results or combine many optional conditions follow the same steps with a few more rules. For those, and for plans that ignore an index you expected them to use, see Indexing queries: diagnosis and patterns.
 Other index types
 A B-tree serves any value with one sort order. Some questions have no such order, and each engine offers other index types for them. In PostgreSQL, USING chooses one: CREATE INDEX ON products USING gin (tags).
 Words inside text, or a substring. A full-text index lists every row containing each word: GIN in PostgreSQL, FULLTEXT in InnoDB, the FTS5 module in SQLite. PostgreSQL’s pg_trgm extension indexes substrings for LIKE '%mug%'. See full-text search.
 Values that hold many keys. Arrays and JSON documents, searched by containment such as tags @> ARRAY['gift'], want GIN in PostgreSQL. See GIN indexes and JSON.
 Overlap and distance. Booking ranges, geometry and network addresses want GiST or SP-GiST in PostgreSQL, spatial R-trees in InnoDB and the R*Tree module in SQLite.
 Nearest neighbours among embeddings. PostgreSQL’s pgvector extension adds HNSW and IVFFlat indexes. See Vector search.
 Very large tables in time order. A BRIN index records only the smallest and largest value in each range of table pages, so it stays tiny on an append-only log. See BRIN indexes.
 Reports over most of a table. No index helps a query that reads most rows of a few columns. A column store does; see Column stores.
 Partial and expression indexes work with any of these types.

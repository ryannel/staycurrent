Inspected `visual/index-order-1280-light.png` at its original resolution, `renderResults` and `node` in `src/lib/sql-sandbox-client.ts`, the sandbox table styles, and the worker's existing display budgets. Review only; root owns changes and verification.

**Finding: the current presentation materially impairs the new plan-reading lesson.** The result area has roughly 770 pixels available, but the one-column plan occupies only about 400. Proportional text and wrapped continuation lines make the indentation harder to follow. Each PostgreSQL output line gets cell padding and a horizontal rule; the 25rem viewport consequently shows only about seven plan lines before scrolling. The lesson asks the reader to relate scan candidates, discarded rows and a Sort, while those parts are unnecessarily separated by this presentation.

The smallest sufficient repair retains the existing table rendering and identifies the special presentation only when the completed response tag is `EXPLAIN` and the fields are exactly `['QUERY PLAN']`. Add a modifier class to its existing scroll wrapper. For that class, render cells in the existing monospace font, preserve whitespace without wrapping, remove the per-line bottom rules, reduce vertical padding, and remove the 25rem cell-width cap. Let the table use its content width with a minimum width of 100% of its wrapper. Keep horizontal scrolling for long plan lines. A compact plan can remain in the existing bounded-height region; the important fix is preserving its hierarchy and removing accidental table-row spacing, not expanding every result indefinitely.

This is deliberately a presentation change. Keep `node(...).textContent`, the original row/cell loop, SQL NULL handling, the focusable region and its accessible label. Keep the existing empty-result and shortened-result messages after the table. Do not parse a visual tree, execute markup, or reconstruct the SQL.

The proposed class and CSS do not alter the worker's limits: 200 rows, 40 columns, 2,000 characters per cell, 5,000 cells and 250,000 cell characters per run, plus response limits. Existing truncation flags still produce their visible explanations. Hostile HTML contained in a predicate or identifier remains literal text because no innerHTML path is introduced. An ordinary SELECT aliased as `QUERY PLAN` remains an ordinary table because its response tag is not EXPLAIN. If a response is incomplete or has a different shape, it also retains the existing table path.

Verify the repair with the same index plan and one nested-loop or merge plan on desktop and phone, checking indentation, scrolling and absence of page overflow. Check one ordinary result table and one value containing literal HTML to confirm the scoped style and safe text behaviour. Retain the existing truncation notices for long output. No broader sandbox redesign is required for this finding.

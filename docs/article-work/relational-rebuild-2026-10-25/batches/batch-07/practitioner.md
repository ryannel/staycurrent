## Finding

**Medium — the observed join is given PostgreSQL’s name for a different parallel implementation.** Locations: `article.astro:118` (Change the cause and measure again), repeated at `:140` (Testing a repair against the workload). Both call the observed route a “parallel hash join”. The saved full-year and common-customer plans instead contain `Hash Join` and `Hash` with `Parallel Aware: false`, each with two executions, over a parallel-aware line scan. The full-year hash/order scan each produces 20,158 rows per execution. This is the duplicated-build route correctly described by the following sentences. PostgreSQL’s [Parallel Joins documentation](https://www.postgresql.org/docs/18/parallel-plans.html#PARALLEL-JOINS) expressly distinguishes an ordinary hash join inside a parallel plan, where each process builds a copy, from a parallel hash join with a shared, jointly built hash table. A reader comparing the prose with the downloadable plan or following that source must reconcile incompatible method names; the distinction also changes the memory/work judgement. Identify the observed ordinary hash join within the parallel plan consistently, preserving the correct duplicated-build explanation. This needs a bounded terminology correction, not a native counter lesson or new measurements.

## Example and continuity decisions

- Order-history scenario uses the ordinary starting rows: customer 1 is Mina Shah, with orders 101 and 103 and four order lines between them. No payment-504 or renamed-customer variant is active. A list query followed by one line query per order gives three queries here; a list plus one batched line query gives two; an ordinary order/line join gives four result rows containing two parent orders. These are worked counts, not measured execution or timings. Bound the selected parents first; batching does not bound an individual order's arbitrarily large collection.
- Driver examples can use PostgreSQL with node-postgres as a concrete, small API. Confirm the actual installed driver version and conversions before presenting observed output. Keep amounts exact; do not casually coerce numeric amounts to binary floating point. Use existing `placed_at` instants and explicit names for columns. A missing row and a NULL column are different outcomes. Large-integer identifiers are a useful secondary mapping caution, but the shared identifiers remain integers.
- Transaction scenario **replays the creation of order 103**, independently of the history read: before it exists, P3 has stock 12, P7 has stock 1 and P9 has stock 4. Mina buys P7 × 1 at 20.00 and P3 × 2 at 4.50. Success creates pending order 103 and its two lines, leaves P3 10 and P7 0, and records no payment. An aborted attempt leaves neither its stock changes nor its order. Do not decrement stock again on top of the post-purchase starting state.
- The zero-row guard does not uniquely mean “out of stock”: the target may be absent or another predicate may fail. Map it to the operation's stated acceptance rule, without adding a diagnostic race or a stock-reservation protocol.
- Any constraint-error illustration can fail a line write in the replay and roll back; do not quietly alter the shared committed data. Request identity/recovery records and a concrete outbox schema remain with their accepted owners. A confirmation email may illustrate external work conceptually without inventing an address or provider behaviour.
- The authority example assumes the application has already established Mina's customer identity. It does not derive authority from an arbitrary request parameter or add tenant columns to the core schema. Tenant and native role-policy procedures retain their existing owners.

No shared extension is required. The proposed order-103 replay should be recorded centrally as an explicit scenario, so eventual writer and reviewer know which state its stock figures describe.

## Primary-source checks (25 October 2026)

- [node-postgres: Queries](https://node-postgres.com/features/queries): values travel separately from SQL text; identifiers are not bindable parameters; a named prepared statement is per connection. This supports the controlled-structure distinction. Naming a prepared statement is optional and does not provide authorisation.
- [Data Types](https://node-postgres.com/features/types) and [Result](https://node-postgres.com/apis/result): driver parsing is configurable, unknown types can be strings, JavaScript dates lose PostgreSQL microseconds, and returned rows differ from command affected-row counts. Pin and observe the writer's actual conversions rather than presenting an unexecuted transcript.
- [Transactions](https://node-postgres.com/features/transactions) and [Pool API](https://node-postgres.com/apis/pool): one client must carry a PostgreSQL transaction; pooled convenience queries may use different clients; acquired clients must be released, with explicit destruction available. A generic release is not evidence of rollback or session reset.
- [PostgreSQL 18: Transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html): individual statements have implicit transactions; some client libraries manage boundaries automatically; a transaction in aborted state needs rollback or rollback to a suitable savepoint. The article's ordinary error path can roll back the whole purchase without teaching savepoint recovery.
- [PostgreSQL 18: SET](https://www.postgresql.org/docs/18/sql-set.html): ordinary session settings can persist after commit; `SET LOCAL` ends with its transaction. Use this for request-specific settings, without introducing tenant policy machinery.
- [SQLAlchemy 2.0: Relationship Loading Techniques](https://docs.sqlalchemy.org/en/20/orm/queryguide/relationships.html): lazy relationship access can cause N+1; joins multiply result rows, and batched loading is another strategy. Loader choice trades SQL executions, query complexity and transferred data. This is a documented ORM example, not a claim that all ORMs share its defaults.
- [SQLAlchemy 2.0: Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html): a session can acquire a connection/transaction, track pending changes and autoflush before queries or commit; flushing and committing are distinct. Keep the specific behaviour labelled rather than generalising its method names across ORMs.
- [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html): successive SELECTs at default Read Committed may see different committed states even inside one transaction. The article recognises this consequence of split loading; the transaction reading owns the isolation solution.
- [PostgreSQL 18: Error Codes](https://www.postgresql.org/docs/18/errcodes-appendix.html): inspect stable SQLSTATE codes and separately reported object fields rather than matching localised message text. Preserve the original error if rollback also fails; domain translation is an application design choice.
- [Client Connection Defaults](https://www.postgresql.org/docs/18/runtime-config-client.html), [Canceling Queries in Progress](https://www.postgresql.org/docs/18/libpq-cancel.html) and [node-postgres Client API](https://node-postgres.com/apis/client): server statement/lock limits and a client's query-call timeout have distinct scopes; successful dispatch of a PostgreSQL cancellation does not prove it took effect. Do not imply node-postgres exposes libpq's API or accepts an unverified HTTP AbortSignal. The writer should use a verified mechanism for any runnable cancellation example.

## Writer verification and boundaries

No runtime, builds or article review were run for this planning assignment. Native PostgreSQL 18.6 in the coordinator's owned Docker is available for eventual SQL and driver verification. The most useful execution checks are the small relationship-load counts/result shapes; purchase success and middle-step rollback; a zero-row guarded write; timeout leaving an aborted transaction; and disposal when cleanup cannot establish a reusable state. Any failure timing model must be labelled illustrative unless actually exercised. Do not turn an unobserved lost-commit case into a claimed native trace.

Keep one coherent code path small enough to read: a transaction helper must await completion, preserve its original error, discard on failed cleanup and release exactly once. It must not blindly retry a write or pretend that a failed rollback proves COMMIT did not happen. The writer chooses the final code and figures, and coordinates rendered checks with the root. Pool sizing/admission, general isolation analysis, retry/deduplication, worker delivery and least-privilege procedures remain outside this article. No unresolved ownership change blocks writing.

## Primary-source checks

Checked the PostgreSQL **18** documentation on 26 October 2026. These are documented behaviours; no native execution was performed by this planner.

- [ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html): default lock level and strongest combined subcommand; metadata-only additions with non-volatile defaults; type/rewrite exceptions; scan versus rewrite; dropped-column space; rewrite snapshot caveat; NOT VALID check, foreign-key **and not-null** constraints in 18; validation locks; unique-index attachment restrictions. The named table-constraint form `ADD CONSTRAINT ... NOT NULL price_hundredths NOT VALID`, followed by `VALIDATE CONSTRAINT`, makes the 18-specific distinction explicit. If illustrated, the writer must verify the exact syntax on its owned server. Installation still needs a strong lock. Adding or changing a default cannot express this row-dependent price conversion.
- [Explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html) and [system information functions](https://www.postgresql.org/docs/18/functions-info.html): ordinary SELECT's ACCESS SHARE, ACCESS EXCLUSIVE conflicts, SHARE for ordinary CREATE INDEX, SHARE UPDATE EXCLUSIVE for concurrent maintenance, transaction-lifetime locks and hard/soft blockers reported by `pg_blocking_pids`. A queued strong request can hold later conflicting requests behind it; it need not already own the table lock.
- [Client connection defaults](https://www.postgresql.org/docs/18/runtime-config-client.html): lock_timeout limits each acquisition attempt, while statement_timeout bounds the statement; use distinct per-session limits. `SET LOCAL` fits an explicit short DDL transaction; concurrent index commands require session settings outside a transaction block, with restoration before reusing the connection. A timeout does not commit an explicit transaction.
- [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html): concurrent builds have extra scans/waits and resource cost; failed builds can leave invalid entries; uniqueness can affect other writers before validity and after some failures. Only one concurrent build per table; no concurrent build inside a transaction block or directly on a partitioned parent. `IF NOT EXISTS` does not certify an equivalent definition. Parent-partition limitations deserve a bounded qualification, not another partitioning tutorial.
- [pg_index](https://www.postgresql.org/docs/18/catalog-pg-index.html): `indisready`, `indisvalid`, `indislive` and `indcheckxmin` describe different obligations. The useful first distinction is write maintenance versus safe query use; do not present every index as a universal three-stage automaton or claim every invalid index has identical update behaviour.
- [Progress reporting](https://www.postgresql.org/docs/18/progress-reporting.html): `pg_stat_progress_create_index` covers CREATE INDEX and REINDEX, including writer/old-snapshot waits and counters for the current phase. Those are not one overall completion percentage or an ETA.
- [REINDEX](https://www.postgresql.org/docs/18/sql-reindex.html): concurrent rebuild replacement/cleanup, transient `_ccnew` versus old `_ccold` leftovers, added resource demand, transaction restrictions, and no concurrent rebuild of exclusion-constraint indexes. Ordinary REINDEX's index lock can obstruct reads too; do not abbreviate it to “only blocks writes”. Confirm catalogue state and dependencies before cleanup rather than deleting by suffix alone.
- [Routine reindexing](https://www.postgresql.org/docs/18/routine-reindex.html) and [pgstattuple](https://www.postgresql.org/docs/18/pgstattuple.html): partially occupied B-tree pages can persist while empty pages are reusable; optional `pgstatindex` supplies leaf-density/page evidence and has privilege and scan costs. Treat density against fillfactor and insertion pattern, without a universal rebuild threshold. Extension lifecycle belongs to its existing owner; this article can explain optional diagnostics without installing an extension.
- [GIN](https://www.postgresql.org/docs/18/gin.html) and [CREATE INDEX storage parameters](https://www.postgresql.org/docs/18/sql-createindex.html): vacuum/autoanalyze, the explicit `gin_clean_pending_list` function or the size threshold can merge pending entries; searches must include the pending list. Disabling fastupdate does not empty it. Prefer evidence-driven upkeep over “disable it” as a default answer.
- [BRIN maintenance](https://www.postgresql.org/docs/18/brin.html): new ranges can need summarisation; autosummarize is off by default; `brin_summarize_new_values` and `brin_summarize_range` fill absent summaries, whereas `brin_desummarize_range` permits recomputing an over-broad summary. An outlier still present will still widen the replacement. No summary procedure sorts the heap.
- [DROP INDEX](https://www.postgresql.org/docs/18/sql-dropindex.html) and [cumulative statistics](https://www.postgresql.org/docs/18/monitoring-stats.html): concurrent removal waits rather than locking out ordinary table accesses, accepts one index, has no CASCADE, cannot remove the supporting index of a UNIQUE/PRIMARY KEY constraint that way, cannot run inside a transaction block and does not support partitioned indexes. Usage counters describe an observation history, not proof that no rare job or constraint needs an index; preserve the established workload/dependency judgement.

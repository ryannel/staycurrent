A PostgreSQL query runs inside a server process, using pages that other processes can use too. Each stored row version is called a tuple . A query's answer depends on more than the bytes on those pages. Two readers can inspect the same cached page and return different prices, because their snapshots admit different row versions. Follow the shop's blue mug, P7, from an application connection to its stored tuple. Then change its catalogue price from 20.00 to 22.00 and follow both readers back through the index. This gives query plans, buffer counts and vacuum a physical setting: which process does the work, where it finds a version, and what must remain after an update. This is the independent price experiment from Storage and durability . Order 103 remains pending, with no payment; its agreed prices still total 29.00. Stock remains P3 10, P7 0 and P9 4. The drawings use invented page addresses, buffer contents and schedules, rather than tracing a running server. PostgreSQL's supervisor process accepts a new connection and starts a backend , the server process that handles that conversation. Subsequent commands and replies pass between the client and its backend. Figure 1 gives the shop and a report their own connections. A pool may lend these connections to different requests. The supervisor is involved in establishing a connection; it does not forward each query between the client and its backend. A connection, a transaction and a query are different things. One connection can carry many transactions over its lifetime. A transaction can contain several SQL commands. Without an explicit BEGIN , each ordinary standalone command still runs in a transaction of its own. A connection pool lends existing connections to application requests. A backend may be idle while its client decides what to send, waiting for a lock or I/O, or executing a query. Having borrowed a connection does not mean useful query work is happening. Some plans also enlist parallel worker processes; those workers are extra participants, rather than a replacement for the client's backend. The map locates the participants, but cannot identify the cause of a slow request. Pool waiting can occur before the request reaches any backend. Operating and diagnosing PostgreSQL (planned) follows that request using evidence from the pool and server. From SQL to an execution plan The shop asks for one price: SELECT price FROM products WHERE product_id = 'P7' ; Inside the backend, parsing checks the syntax. Analysis resolves names such as products and price , their types and the operators to use. Rewriting transforms the query where needed, for example expanding a view into its underlying query. The planner chooses a plan for producing the answer. It compares estimated work: scanning the products heap, or finding P7 through its primary-key index and fetching a tuple. The executor follows that chosen plan and returns the resulting price through the connection. Those stages in Figure 1 are work inside the backend, not separate servers passing the request along. The primary key supplies an index; it does not require an index scan. With only the three shop products, reading the tiny table can be cheaper. We will draw an index route to explain its mechanics, without claiming it is the plan this query must choose. Reading and repairing PostgreSQL plans tests the planner's choices against actual rows, buffers and repeated work. Shared buffers A backend needs a page in memory before it can read its tuples. PostgreSQL's shared buffers cache holds table and index pages for the server's backends. A page belongs to a particular table or index and has a block number within that stored object. A buffer slot is merely the place currently holding that page; the slot number is not the page's address. The first query can bring in a page that the next backend reuses. The cache holds pages for indexes as well as heaps; an index lookup can need both. Pins, content locks and replacement A pin prevents a buffer from being repurposed while a backend uses its page. A short buffer content lock protects access to the page's contents. A backend can release the content lock after selecting a tuple while retaining its pin to use the tuple data. Neither mechanism is the transaction's row lock: they protect the shared page and its memory slot, rather than deciding which transaction may update P7. Replacement uses a clock sweep , not a perfectly ordered list of last access times. A hand visits buffer slots. Pinned buffers cannot be reused; an unpinned buffer with a positive usage count gets its count reduced and another chance. An unpinned buffer at zero can supply a slot. Figure 2 chooses one hand position and set of counts; concurrent access can change what a real sweep encounters. The chosen page was clean. If it were dirty, its changes would need writing before the slot could safely hold another page. That can put write work on the path of a query trying to read. We will return to who performs it after following the update. Heap pages and row addresses An ordinary PostgreSQL table is a heap : its tuples are not kept in primary-key order. Each heap page has a header, an array of line pointers , free space and tuple data. A line pointer records where a tuple's bytes lie within that page. An index's heap locator is a TID , or tuple identifier: a block number and an item number. In Figure 3, (12,3) means page 12, line pointer 3. Follow it through the line pointer rather than treating 3 as a byte offset. The indirection lets PostgreSQL compact tuple bytes within a page without changing their outside address: it adjusts the line pointer's offset. It does not make that address a lasting product identity. PostgreSQL exposes the physical version's location as the system column ctid . An update creates a new version with another location, and a table rewrite can move versions too. Use product_id to identify P7. Its actual ctid comes from that table's current storage; it need not be the drawing's (12,3) . Large values and TOAST A heap tuple cannot straddle pages, but a logical value can exceed one page. For supported variable-length types, TOAST can compress a large value or store it in chunks in an associated TOAST table. A small pointer then represents the out-of-line value in the main tuple. Imagine a wide product description stored that way. Reading only price need not fetch and reconstruct the description; returning the description does. The exact representation depends on the type, storage policy and compressibility. Wide values that remain inline still reduce the number of tuples per page, so the displayed character count is a poor storage estimate. What the tuple header tells the reader A tuple carries a creator transaction identity, exposed as xmin , and information about its deletion or replacement, associated with xmax . An update marks the earlier version and creates another tuple. Transaction status tells whether that work committed or aborted; the snapshot tells whether that transaction's effects belong in this reader's view. The report excludes W's new tuple even after W commits, because W was not part of the committed history its snapshot admits. For the same reason, W's replacement does not hide the old tuple from that report. The later snapshot admits W and therefore makes the opposite choice. Transaction IDs alone are insufficient. A transaction with a lower ID can still have been in progress when the snapshot was established. Snapshot membership and commit outcome matter, not just comparing two numbers. A non-zero xmax does not by itself prove that a tuple is dead: it can reflect unfinished or aborted work, and row locking can use the field too. Header flags distinguish those cases. If W rolls back, its new 22.00 tuple does not become an ordinary reader's value, and its attempted replacement does not remove 20.00. While W is uncommitted, other ordinary readers likewise cannot return its new price. This is why finding bytes that say 22.00 is insufficient evidence that a query should return 22.00. These versions serve concurrency and can be removed when no longer needed. They are not a business price-history table, and they do not change the agreed 20.00 on order 103's mug line. When an index-only scan can skip the heap If a supporting index holds every value needed by the query, it can be eligible for an index-only scan . Our primary-key index alone lacks price , so it cannot answer this price query from its stored values. Even with the values present, an index entry does not carry the heap tuple's full visibility information. PostgreSQL consults the heap page's all-visible bit in the visibility map. When set, it certifies that the page's tuples are visible to all relevant transactions, allowing the scan to avoid a heap visit. When clear, the scan must check the heap; a clear bit does not prove that a tuple is invisible. Vacuum sets the proof when safe; changes to the heap page clear it. Updating another row on P7's page can therefore make an eligible index-only lookup visit the heap again. Covering a query and avoiding heap fetches are related conditions, rather than the same condition. Heap-only tuple updates The price changed, but the primary-key value P7 did not. PostgreSQL can sometimes keep the existing index entry and follow a link from the old tuple to the new one. This is a heap-only tuple , or HOT , update. It needs space for the new version on the same page, and the update must not change columns referenced by the table's ordinary indexes. “Referenced” includes expression inputs, partial-index predicates and included columns, not just B-tree keys. Summarising indexes are an exception: PostgreSQL's BRIN can still need its summary updated without requiring a new per-tuple index entry. Free space and fillfactor A table's fillfactor limits how full inserts try to make its pages, leaving space for later versions. Reserving more space can make same-page updates more likely, while needing more pages for the same initial rows. That trades scan and cache space for update opportunities. It is not a HOT guarantee: the remaining space can run out, and an index-referenced change still fails the other condition. Changing the setting also does not immediately redistribute an already packed table. Choose it from the update workload rather than treating one percentage as universally right. Reclaiming old versions While the report still needs 20.00, cleanup must keep that tuple. Once it is no longer required, pruning can remove obsolete tuple bytes on the page. For a surviving HOT chain, the original line pointer can become a redirect to the oldest version still needed. The index keeps its original target while that redirect preserves the route. Ordinary page access, including reads, can perform pruning when conditions permit; it is not exclusively a periodic vacuum job. Reusable bytes inside the page do not imply that the heap file became smaller. HOT also does not remove the need for vacuum's wider work.

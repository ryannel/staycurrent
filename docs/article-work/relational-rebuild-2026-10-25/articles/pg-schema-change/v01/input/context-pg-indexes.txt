Reviewed draft · this collection is not yet published. An index can store an ordered value, the keys inside a value, or a summary covering many values. Those choices determine which questions it can answer. A customer ID has an order that a B-tree can search. “Contains the tag gift” asks about an element inside an array. “Overlaps this reservation” asks about two intervals. “Falls on this day” can sometimes exclude whole ranges of table pages. PostgreSQL supplies six built-in access methods : B-tree, hash, GIN, GiST, SP-GiST and BRIN. The method supplies the structure. An operator class connects a particular type and its operators to that structure. Choosing both starts with what the query means, then asks what information the index must retain to help answer it. Indexes and access paths develops composite keys, selectivity and ordered limits. Inside PostgreSQL follows an index entry to a visible heap tuple. Here we keep those ideas and change the information in the index. Small drawings are models; the plan observations come from an owned disposable PostgreSQL 18.6 server. The name after an indexed column, when present, selects its operator class. Leaving it out chooses the default class for that type and method: CREATE INDEX products_name_prefix ON products USING btree ( name text_pattern_ops); CREATE INDEX product_tags_gin ON product_tags USING gin (tags array_ops); The first definition keeps a B-tree but changes how text is compared. The second indexes the component values of a text[] column. product_tags is a separate illustrative catalogue projection; P7 retains its established gift and ceramic tags. The class determines the particular keys, summaries, partitions and operators. Several methods can support the same predicate. The right column can have the wrong comparison The shop wants names beginning with Blue : SELECT product_id, name FROM products WHERE name LIKE 'Blue%' ; A B-tree can turn a fixed prefix into a narrow search when its comparison puts the relevant strings together. Locale-aware text order can prevent that transformation. In a deterministic non-C collation, text_pattern_ops supplies the character-wise comparison used for the prefix bounds. With the C collation, the default text class already supports this search. The resulting plan can show special bounds such as name ~>=~ 'Blue' and name ~<~ 'Bluf' , followed by a LIKE filter. The bounds locate candidates; the original predicate remains the test. This does not serve LIKE '%mug%' , whose unknown beginning supplies no such fixed prefix. Nor is the pattern class a replacement for every ordinary text comparison. It supports equality, but queries using ordinary < , > or locale-aware ordering need appropriate default-class support. Match the expression, operand types and collation, as well as the column name. Inspect the definition with pg_get_indexdef . To discover available classes, join pg_opclass to pg_am ; opcintype identifies the indexed type. The class belongs to an operator family , which can also contain comparisons between related types. PostgreSQL's psql commands \dAc , \dAf and \dAo list classes, families and operators. An operator's spelling alone does not identify its supported search: array && and range && have different operand types and implementations. B-tree and hash indexes The established history request fixes a customer, bounds time, asks for descending time and ID, and stops at ten: SELECT order_id, placed_at, status FROM orders WHERE customer_id = 1002 AND placed_at >= timestamptz '2026-01-01 00:00+00' ORDER BY placed_at DESC , order_id DESC LIMIT 10 ; CREATE INDEX orders_history ON orders (customer_id, placed_at DESC , order_id DESC ); The B-tree's ordered run supports both the time bound and the early stop. A hash index on customer_id can help find that customer's rows, but it supplies no time order. PostgreSQL must test the time condition and sort the eligible results before choosing ten. A hash index computes a 32-bit hash code and uses it to find a bucket. Each index tuple stores the code and a heap locator, rather than the original customer ID. Different values can have the same code, so a candidate still needs an equality recheck against the heap value. This is a lossy representation: the code has discarded information. The query must not return a different customer merely because their hash codes collide. Hash supports single-column equality searches. It cannot replace a multicolumn history key, supply range bounds or sorted output, enforce uniqueness, or supply an index-only scan. B-tree supports those capabilities where its class and definition fit the request. Equality alone therefore does not establish that hash is the faster choice. Bucket concentration, overflow pages, key width, caching and the rows fetched all matter. On the generated shop fixture, compare a common customer's 84,000 orders with customer 1002's 36. A direct bucket lookup does not make 84,000 heap candidates cheap. The native comparison below keeps one secondary index at a time so that the requested order, rather than another index, explains the difference. GIN indexes and component values An array's ordinary B-tree order compares whole arrays. It does not place every array containing gift in one run. A Generalized Inverted Index , or GIN, works the other way round: each component key points to the rows containing it. P7 supplies two keys, gift and ceramic . Each has a posting list of heap locators; a large list can use a posting tree. To find arrays containing both, look up both keys and keep locations present in both lists. GIN does not reconstruct the whole array for an index-only scan, nor does it supply the final product-name or relevance order. A search can identify matching rows and still need heap work and a sort. Keep ORDER BY in the query when the result order matters. The same inverted structure can index text lexemes or JSONB keys, with different extraction and matching rules. PostgreSQL JSON and structured alternatives chooses JSON operators and classes from the facts being queried. GiST and SP-GiST indexes Overlap does not have the same useful ordering as a customer ID. A reservation can begin before another and still overlap it, contain it or end before it. PostgreSQL's built-in range classes support indexed overlap through both GiST and SP-GiST: CREATE INDEX reservation_during ON reservation_probe USING gist (during); SELECT id FROM reservation_probe WHERE during && tstzrange( '2026-11-02 10:30+00' , '2026-11-02 11:30+00' , '[)' ); The stored reservation 7001 is 10:00–11:00 UTC. This search finds it. A search for 11:00–12:00 does not: the existing upper bound is excluded by the half-open [) interval. An index accelerates that operator's meaning; it does not turn adjoining intervals into an overlap. Generalized Search Tree , or GiST, provides a framework whose internal summaries cover the values below them. A search can reject a child when its summary proves that no value inside can match. Otherwise it follows the child. Different classes define different summaries and tests. A bounding rectangle is a useful geometric example, not the definition of every GiST index. Space-partitioned GiST , or SP-GiST, instead supports structures which repeatedly divide a search space. Quadtrees, k-d trees and text tries are examples. The partitioning rule determines which children a query can reach. Figure 3 keeps the same four mathematical points and draws one possible pruning step in each framework. Neither method is one universal spatial index, and neither method name alone tells you whether a leaf match needs rechecking. The selected class determines how much information survives. Distance ordering and nearest neighbours Some GiST and SP-GiST classes also supply a distance-ordering operator. For the native point classes, this lets a search produce the nearest points without sorting every point's distance first: SELECT id, p <-> point '(0,0)' AS distance FROM point_probe ORDER BY p <-> point '(0,0)' LIMIT 2 ; The first two points in Figure 3 are also the nearest to (0,0). An assisted plan shows the distance expression under Order By in its index scan. This order depends on the query point; it is different from a B-tree's fixed value order. Support belongs to the particular class and operand types, so check its documented ordering operators. This native geometric example does not establish the recall of an approximate embedding index. BRIN indexes and physical correlation A Block Range Index , or BRIN, can retain much less than one entry per tuple. Its timestamp min/max class records the lowest and highest timestamp in each group of adjacent heap pages. If a requested day cannot lie between them, every page in that range can be skipped. It cannot identify which tuples match within a surviving range. PostgreSQL collects the pages and tests their tuples. Figure 4 stores the same timestamp values in two orders. With two pages per range, only the range spanning days 5–8 survives: two pages, four timestamp tests, one match. With one page per range, only page 3 survives: one page, two tests, one match. In mixed order, page n holds days n+1 and n+9. Every one-page and two-page min/max summary spans day 8. All eight pages survive: sixteen tests still find the same one match. Increasing time puts narrow spans in each summary. Mixed time broadens them until all eight pages remain possible. The matching values did not change; the information lost by summarising each physical range did. A timestamp column is therefore not sufficient reason to choose BRIN. Arrival order, backfills and later updates determine whether its values remain usefully correlated with physical placement. CREATE INDEX orders_time_brin ON orders USING brin (placed_at) WITH (pages_per_range = 32 ); pages_per_range trades summary count for precision. Smaller ranges give more summaries and can exclude more heap pages, while making the index larger. They cannot recover useful separation when even individual pages mix widely separated timestamps. Other BRIN classes retain different summaries, including multiple min/max intervals or Bloom filters; the figure and experiment use ordinary timestamp min/max. Building BRIN summarises existing ranges. Inserts into summarised ranges update their summaries as needed. Newly extended ranges can remain unsummarised until vacuum or explicit summarisation processes them; autosummarize is off by default. An unsummarised range must remain a candidate, preserving correct results at the cost of extra scanning. An old summary that is too broad can also keep unnecessary pages. The upkeep procedure belongs with PostgreSQL schema changes under load (planned) . Candidates, rechecks and visible rows A heap visit can answer three different questions. First, does this candidate actually satisfy the indexed operator? Hash collisions, GIN array equality and BRIN summaries can require that index recheck . Second, does another SQL condition pass? A condition on an unindexed stock column is a filter . Third, is this tuple visible to the reader's snapshot? That is the visibility check already developed in Inside PostgreSQL . There is another way to lose precision: the bitmap itself. A bitmap heap scan collects locations before reading heap pages. With enough memory, it can retain exact tuple positions on a page. Under memory pressure it can keep just the page, requiring the executor to retest tuples there. This can happen even when the original index predicate was exact. Keep those two losses separate. A GIN equality candidate can have an exact tuple location but an unproved predicate. A B-tree comparison can have a proved predicate but lose its exact tuple location in a page-level bitmap. BRIN already supplies page ranges, so tuple tests are intrinsic to that route. A focused native check made the second loss visible. A diagnostic copy of the same 120,003 order IDs and timestamps added a constant 512-byte padding column to spread tuples over more pages. With a B-tree timestamp predicate, a forced bitmap route and work_mem=64kB , it reported 811 exact and 7,761 lossy heap blocks, rejecting 44,279 tuples by recheck. At 4 MiB, it reported 8,572 exact blocks and no recheck rejects. Both returned the same 70,360 order IDs. The padding is an experimental physical width, not another shop fact or an instruction to increase memory globally. What each method adds to writes The read saving comes from information maintained during writes. A B-tree maintains ordered entries and may split pages. Hash adds codes to buckets; concentrated values can build overflow chains, and growth can split buckets. GiST maintains covering summaries, while SP-GiST maintains the chosen partitions. The shape and number of affected entries depend on the data and class. GIN can extract many keys from one row. One new document can therefore add many posting-list memberships. With fastupdate enabled, new entries can first accumulate in a pending list and be merged into the main structure later. Searches must include that list, and an insert that crosses its cleanup threshold can inherit a large cleanup. Deferring work changes when it is paid. A small native insert comparison made that distinction measurable. Each of 1,000 rows contained the same twenty distinct tag keys. The insert generated 331,241 WAL bytes without an index, 795,933 with default GIN pending entries, and 12,295,046 with fastupdate=off . The pending index then occupied 425,984 bytes, versus 49,152 for the direct-update index. Those are initial insert observations on separately created empty tables: the pending list had not yet been cleaned. They show why a quick insert and a compact settled index are different measurements; they do not rank lifetime cost or production throughput. BRIN usually has far fewer summary entries, but an inserted outlier can widen a summary and reduce future pruning. New ranges need summarising. A small index still has a maintenance contract. An update must also account for PostgreSQL's row versions. Changing a column used by an ordinary index can prevent a HOT update, including expression inputs, included columns and partial-index predicates. Without HOT, unchanged ordinary indexes can also receive entries for the new tuple. BRIN is the summarising exception: a HOT update can still require summary maintenance. Same-page space remains another HOT condition. Measure a candidate's size, write log and buffer work, plus any deferred cleanup, under the relevant mix of inserts and updates. Do not infer write cost from one definition's column count. Concurrent builds, failed builds and operational cleanup need the procedures in PostgreSQL schema changes under load (planned) . Choosing and checking an access method Start with the operator and its meaning. Check supported classes for the stored type, expression and collation. Then predict the information that will remove work: an ordered run, component memberships, a region to prune, or a block-range summary. Include the requested order and limit in that prediction. The native checks use the exact 120,003-order shop fixture already used by the index introduction. Sorted and mixed BRIN copies contain the same rows. Small diagnostic tables isolate array matching, point searches, half-open intervals and prefix comparison. Mechanical demonstrations discourage sequential scans where necessary so that the index route is visible; those demonstrations are not claims that the planner would choose that route on a tiny table. The method verifier and focused bitmap verifier include their generated fixture, settings and exact safety guards. They require the specifically named disposable database, user and cluster and roll their changes back. They record these observations rather than supplying commands for an application database. For an application choice, restore the normal planner settings and test representative values and layouts. Compare common and rare customers, narrow and broad bounds, stable and recently changed pages. Check the complete ordered result, then the actual plan and buffers. Finally test the write workload and cleanup over time. Keep an index only when the useful work it removes earns its ongoing cost.

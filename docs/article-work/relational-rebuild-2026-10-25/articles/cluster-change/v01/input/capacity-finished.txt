A connection lets an application send work to a database. It does not give that work a processor, memory or a share of the storage. A server can accept a hundred connections and still do less useful work with a hundred queries running together than with ten. Capacity is the workload a system can serve while meeting its requirements: correct results, acceptable delay and enough room to keep operating through the conditions it must survive. Counting connections is part of planning that capacity. Counting what occupies them, what waits outside them and what resource the work needs is the rest. The shop’s application serves Mina’s order history and also runs reports. Mina wants her recent orders; a report sums paid-order line values across many customers. Both use connections to the same database, but they need different amounts of work. Every rate, deadline and capacity limit below is an illustrative assumption. The drawings show the consequences of those assumptions, not measured limits of the shop or PostgreSQL. Connections and work in progress Throughput, latency and concurrency Find the resource that limits useful work Budget connection pools across the application Bound waiting and reject excess work Leave capacity for recovery Test the workload and the overload policy Connections and work in progress A connection pool keeps connections open for reuse. A request borrows one, sends its statements and releases it when the driver has finished using it. An idle connection is open but available to borrow. An occupied connection is borrowed by a request, whether the database is executing its statement, waiting for a lock, or waiting for the application to send its next statement. Mina’s history request asks for customer 1’s ten newest orders since the start of October. In the small shop state, it returns pending order 103 followed by paid order 101. It changes no row. The same symptom, a slow history page, consumes different resources at those two boundaries. Opening another connection could let another request reach the database; it would not release the lock. The lock in this drawing is an ACCESS EXCLUSIVE table lock on orders, which can block an ordinary PostgreSQL SELECT. An ordinary row-update lock does not explain this read waiting. Diagnosing a database incident distinguishes those causes, and Locks, contention and deadlocks develops the locking protocols. Here the consequence is that a waiting request still takes up a borrowed client. Keep these populations separate in measurements. Count open pool connections, occupied clients, callers awaiting checkout, and database statements executing or waiting. A database activity view cannot see requests still in an application queue. Conversely, a request timing out in the application does not prove that its database work has ended. SQL at the application boundary handles that individual connection’s cleanup and safe reuse. Throughput, latency and concurrency Throughput counts completions per unit of time. Latency measures elapsed time for one request. Concurrency counts work present at once. They are related, but a rate such as 100 requests a second does not tell you how many connections are occupied unless you also know how long each request holds one. Suppose a stable workload completes 100 requests a second, each borrowing one connection once. With a mean borrow-to-release time of 40 ms, it occupies four connections on average. Now suppose another stable workload sustains the same completed rate, but holds each connection for a mean 200 ms. Its mean occupancy is twenty. Figure 2The same completed rate, five times the occupancy Two stable workloads · both complete 100 requests/s 40 ms mean borrow-to-release 100/s × 0.04 s = 4 occupied on average 200 ms mean borrow-to-release 100/s × 0.2 s = 20 occupied on average One filled square = one occupied connection in the mean. Empty squares are a common scale, not a pool limit. This is Little’s Law: mean work in a boundary equals the rate through that boundary multiplied by mean time inside it, often written L = λW. For the borrowed-connection boundary, time starts at checkout and ends at release. It includes database waits and any application delay while holding the connection. Waiting to borrow is outside it. Use the same boundary for all three quantities. If instead you count requests from arrival until reply, include the application queue in both the population and the elapsed time. Use mean times, not a 99th percentile substituted into the formula. If requests borrow several times, count borrow episodes and their rate for connection occupancy, or account for each request’s total connection time explicitly. The twenty is an average, not a recommended pool maximum. It leaves burst variation and tail latency unanswered. More importantly, the second calculation assumes the system sustains 100 completions a second. It does not establish that a capped pool or the database can do so. If demand keeps arriving faster than work finishes, the queue grows; dividing an arrival rate by a hoped-for latency does not make that state stable. Find the resource that limits useful work A history lookup can touch a few index and table pages and return a small result. The paid-order report may scan many rows, join order lines, aggregate and sort. Calling each one “a query” conceals the difference. A change in their mix can exhaust capacity while the request count stays the same. MemoryCached pages, connections, sorts and hash tablesMore simultaneous operators can cause spills or memory exhaustion. StoragePage reads, temporary files, log flushes and background writesReads and writes wait longer when their shared storage is busy. Contended dataTransactions needing the same lock or hot recordMore callers join a wait without making the holder finish sooner. Memory is especially easy to undercount. PostgreSQL’s work_mem is a budget for a sort or similar query operation, not one allowance for the whole server. Several operations and sessions can use allowances together, and hash operations have a multiplier. Multiplying connection count by work_mem is therefore not a complete server memory budget. To choose an execution limit, vary admitted concurrency on a representative workload and compare useful completions, latency and resource use. At low concurrency, adding work may keep otherwise idle resources busy. Eventually another request mostly waits or adds interference. Choose a limit within the region that meets the service requirement, with room for variation. The highest throughput point alone may already have unacceptable tail latency. A lower limit controls the work competing now. Reducing the work each request needs can move the limit later: a suitable history index, a better report plan or a shorter contended transaction may help. How a query runs and Indexes explain those changes. Neither the processor count nor the database connection ceiling supplies a universal pool-size formula. Budget connection pools across the application A pool maximum is local to the process that owns it. The database receives connections from every application instance, job worker, migration tool and operational session. Ten pools of twelve can ask for 120 connections even if each application instance usually borrows only a few. Suppose the server has a 100-connection ceiling. The shop allocates ten slots to background workers and ten to operational access and tools, leaving eighty for application pools. Each application instance has a maximum of twelve. Add ten worker slots and ten operational slots and the budget reaches 92. Keeping four old instances alive during that rollout raises the total to 140. A pool that opens connections lazily might not hit the limit immediately, but it has not made that worst case affordable. Either bound overlap, reduce each pool’s maximum, or allocate a shared application ceiling before allowing that deployment shape. Count each distinct pool, including separate read and write pools that reach the same server. Recalculate for autoscaling and for failover that directs several clients to a smaller set of servers. More application instances can provide more application capacity while leaving the database budget unchanged. The ten operational slots are a planning allowance, not a guarantee that arbitrary users can open them. PostgreSQL has reserved-connection settings and privileges for that purpose; the effective ordinary connection allowance depends on the configuration. Its max_connections also affects resource allocation. Raising it is a configuration change with a cost, not evidence that more active queries will meet the latency target. Operating and diagnosing PostgreSQL (planned) covers native controls. The connection ceiling and execution limit answer different questions. The first says how many sessions may exist. The second says how much work may compete at once. A service could budget 72 application connections while admitting far fewer simultaneous database operations. Enforce the active-work budget across all instances, or divide it into allocations whose sum stays within it. Independent per-instance gates that all assume they own the full budget do not do that. A pooler adds another boundary A connection pooler sits between applications and the server. For example, PgBouncer’s transaction mode lends a server connection for one transaction and returns it afterwards. Many client connections can share fewer server connections because clients that are between transactions do not each retain one. The extra boundary has its own waiting: application checkout, then perhaps a wait inside the pooler for a server connection, then execution or waiting in the database. Bound and measure all three. Moving a queue into a pooler does not make it disappear, and a hundred client connections sharing ten server connections still have only ten server connections for simultaneous transactions. Choose a pooling mode against the driver and application’s state requirements. Session pooling retains a server connection for the client session; transaction pooling can move the next transaction to another one. Session-level locks, temporary-table lifetimes and session settings can therefore change meaning. Prepared-statement support depends on the protocol, pooler version and configuration; PgBouncer’s feature map distinguishes protocol-level prepared plans from SQL PREPARE. Check the exact combination before adopting it. Bound waiting and reject excess work Admission control decides whether work may begin consuming a protected resource. Put the decision before borrowing a connection when that is where work can wait cheaply. Give admitted work a concurrency bound, waiting work a finite queue and a maximum wait, and excess work an explicit outcome. Figure 4 gives seven simultaneous requests two execution places. Every request takes exactly 100 ms once started, an invented constant chosen to make the queue visible. The bounded policy allows two more requests to wait, for at most 120 ms. All have a 300 ms end-to-end deadline. Step through it, then compare the unlimited queue that keeps expired work. All four admitted requests finish by 200 ms. With an unlimited queue and no expiry removal, 1–6 finish by 300 ms; request 7 starts at its 300 ms deadline and finishes at 400 ms, too late. These fixed service times are assumptions, not engine measurements. The bounded policy completes four requests by 200 ms and refuses three immediately. The unlimited policy eventually completes seven, but request 7 finishes too late. Counting only database completions would hide that wasted work. In a less tidy workload, a few slow requests can keep the whole queue waiting; a length limit alone cannot bound time. Choose both bounds from the service’s delay budget. For this model, a queued request waits 100 ms and then uses 100 ms of execution, leaving 100 ms of the deadline for the rest of the request path. Those constants do not guarantee a real 300 ms response. Real execution varies, so enforce queue expiry and a remaining deadline as well as testing the limits. When a request leaves a queue, check again whether there is time left for useful work. An overload response can tell an interactive caller to try later with backoff. An optional report can be deferred into a bounded, durable job system if the product promises a later result. A reduced response is another choice only when its meaning is acceptable: a clearly labelled cached history, for example, if the product permits stale history. Returning a false payment success or quietly omitting required orders is not a capacity policy. Outboxes and background jobs covers durable deferred work. Keep work classes within the shared budget Separate the interactive history path from optional reports at admission. Limit report concurrency, give interactive work an allocation, and cap a noisy caller’s share. Decide whether unused allocations may be borrowed and how long already-running borrowed work can delay higher-priority requests. A report already using storage does not instantly stop because Mina arrives. Separate pools can keep report callers from taking every history pool slot. They do not reserve processors, memory or storage. The two classes still need a common resource budget and a test with both running together. A report may need a much smaller concurrency allowance than a history read; giving each twenty slots treats unequal work as equal. Deadlines, cancellation and retries A request’s remaining time shrinks while it waits. If a 300 ms deadline has already spent 100 ms in queues, the next stage cannot receive a fresh 300 ms allowance. Carry the remaining deadline through checkout, statements and any retry. PostgreSQL’s statement_timeout starts at the server’s statement boundary; it does not include an earlier application-pool wait. Remove expired requests from queues. For running work, request cancellation and retain its execution allowance until the work has actually ended and the connection has been cleaned up or discarded. Releasing an admission token as soon as the caller gives up can admit replacement work while the old query still consumes resources. Retries are additional offered work. Let one layer own them, cap attempts and total elapsed time, use backoff with jitter, and limit aggregate retry traffic. In a simple example, 100 original requests a second plus one extra attempt for every original is 200 attempts a second before any further retries. An overload refusal should not trigger an immediate new attempt. Safe retry identity and the meaning of a missing commit reply belong to Retries and uncertain commit outcomes; spare capacity does not make a write safe to repeat. Leave capacity for recovery Headroom is capacity deliberately left available for variation or other work the service must perform. That includes background cleanup, checkpoints, backups, repairs and warming a cold cache. Free storage must also accommodate growth, retained logs, temporary files and any extra copy a planned operation needs. A percentage of idle processors cannot substitute for free disk space. Recovery also has a rate. Suppose a separate queue contains 600 units of background work that are still needed, and 80 more arrive each second. If the system can complete 100 of these equal-cost units a second, only twenty completions a second reduce the old backlog. If work gets more expensive, a retry wave arrives, or recovery itself consumes the limiting resource, the spare twenty can vanish. Gradually restore paused reports and connection establishment after an outage, measuring whether queues drain. Releasing all deferred work at once spends the very headroom needed to recover. Test the reduced-capacity state the service promises to survive. If losing a node redirects the same demand onto the survivors, the normal-state limit may no longer be safe. Data movement and replica catch-up also use resources while redundancy is reduced. Rebalancing and cluster change (planned) budgets those operations; a surviving copy is not automatically spare capacity for them. Test the workload and the overload policy A useful capacity test answers a service question: what history demand can be served within the chosen latency target while the required reports and upkeep also run? Use an isolated environment with representative hardware, settings, data size, customer skew, result sizes and request mix. The shop’s two-row Mina result checks query meaning; it cannot establish production capacity. Start below the intended demand, increase offered load in steps and hold each long enough to see whether queues stabilise. Compare admission limits as well as pool sizes. Then exercise bursts, slow statements, a blocked statement, a cold start and the reduced-capacity recovery state. Keep the arrival pattern and data comparable when changing one limit, so a different workload does not masquerade as an improvement. Keep the demand and its outcomes in the same record MeasureWhat it establishes Offered originals and retry attemptsHow much work callers wanted, including attempts that never reached the database. Admitted, refused and expired requestsWhat the overload policy did with that demand. Useful completions and errorsHow many correct results arrived within their required time. Queue wait, connection hold, total latencyWhere time went; include tail percentiles and separate successes from refusals. Active work and resource useWhich limit constrained work and whether another resource ran out first. Backlog after the burstWhether the service recovered while new traffic continued. Be careful with a generator that sends a fixed number of requests, waits for their replies and only then sends more. When replies slow down, this closed workload automatically offers less traffic. It can measure what those clients experience, but it can hide the growing demand of callers who continue arriving independently. Use an arrival schedule for that question and report how far the generator falls behind it. Otherwise the generator becomes the admission limit without appearing in the service’s results. PostgreSQL’s pgbench, for example, offers a scheduled rate mode and reports schedule lag; scheduled requests skipped under a latency limit are counted separately. A database-only test still omits the application’s queues, pool checkout and response path. Use it to isolate database work, then exercise the complete request path to validate the service policy. Keep the workload, limits and operating conditions with the result. A defensible capacity claim names the request mix and latency requirement, shows the refusal and recovery behaviour, and states the conditions under which it was tested. Repeat the affected test when a release, data growth, resource change or new report changes those conditions.

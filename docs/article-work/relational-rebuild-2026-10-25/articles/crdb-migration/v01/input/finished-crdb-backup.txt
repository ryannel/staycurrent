 CockroachDB’s BACKUP preserves a consistent state of selected tables, databases or a cluster. RESTORE builds new objects from that material. To recover an earlier moment between backups, the backup must also contain the revisions needed for that moment. A live cluster retaining old versions and a backup retaining those versions are two different promises.
 This article follows the recovery branch from Backup, restore and reconciliation. Order 103 has already bought one blue mug at 20.00 and two packets of tea at 4.50, total 29.00. Stock is now P3 10, P7 0, P9 4. A mistake changes P7’s catalogue price to 2.20. Later, a provider accepts a 10.00 card charge and the shop records payment 504. Restoring before the mistake also omits that valid payment record.
 We will find a complete backup path, restore the earlier shop into a separate database, then account for the accepted charge without charging again or repeating the purchase. The SQL uses CockroachDB v26.2 syntax; a small native drill ran on v26.2.8. The drawings show illustrative ordering, with no invented commit times or recovery-rate measurements.

If the only problem were this one catalogue value, restoring an isolated copy to inspect the old price and correcting the live database might be sufficient. Here we follow the wider restore to make its obligations visible.
 Identify the unwanted commit from retained database and application evidence. The time someone noticed the price is not its commit time, and an application’s updated_at need not mark that boundary. Choose a supported timestamp before the unwanted change, record the source and object scope, then verify the resulting facts. The engine accepting a timestamp does not establish that it is the right business cut.
 Full backups and incremental chains
 A full backup supplies a complete starting copy for its selected scope. An incremental backup supplies changes since the preceding backup in its chain. A backup collection can contain several full backups, each with its following increments. The collection URI identifies the container of those paths; it is not itself one recoverable point.
 These two commands do different work. The first starts a new full backup. Run the second later to append an increment to the latest full-backup path. Here external://shop_recovery stands for an already configured external storage connection, with suitable SQL and storage access.

 Revision history and interior restore points
 Without captured revision history, the chain supports its saved backup points. Having A and B does not make every moment between them restorable. With captured revisions, a restore can select an interior point within the history actually saved. Switch Figure 2 to Backup points only: the dependency chain stays the same, but its stopping points change.
 A full backup with revision history can include retained revisions from before its backup timestamp. An increment with revision history captures the changes since its preceding backup within the available revision window. An increment can add revision history even if an earlier backup omitted it; that does not fill older gaps. Neither can recreate versions already collected before capture. Inspect the actual captured bounds and test the desired target; the source’s garbage-collection period alone does not establish the backup’s coverage. Scheduled backups protect the revisions they still need to capture, as the revision-history documentation explains.
 Request the option explicitly when interior recovery is required. In the v26.2.8 drill, an unqualified BACKUP chain rejected an interior restore because revision history had not been captured. An explicit revision_history = false chain rejected it too. A separate full-and-increment chain using revision_history = true restored the intended interior cut. The current BACKUP option reference describes a true default; that differs from this observed run. Do not base recoverability on an assumed default.
 Use AS OF SYSTEM TIME on RESTORE for the chosen point. This command’s path and timestamp are placeholders to replace with the inspected backup path and established cut:

 Choosing the restore scope
 Choose the unit whose facts must agree. Restoring only payments would leave its references and the order agreement to be accounted for separately. This shop candidate uses a database restore so that products, orders, order lines, payments and operation mappings share the same cut.

 A table restore is not an automatic dependency collector. Include the needed related objects deliberately. Options such as skip_missing_foreign_keys remove the missing constraint; they do not recover the referenced facts. A successful restore after skipping it has a different integrity contract. The restore dependency rules cover the supported combinations.
 A database restore also does not recreate cluster users. By default, the restore operator owns the restored objects. Establish the intended runtime identities and grants, and check application access using those identities. The GRANTS option can restore backed-up privileges for corresponding destination usernames; it is not a substitute for verifying who those users are or what the service should now access.
 Check the destination’s supported source version, capacity, required regions and storage access before starting. CockroachDB cannot restore a newer-version backup into an older engine; the documented forward path is the same or the next major version. Encrypted backups need the correct passphrase or usable KMS key. An operator able to list a bucket today has not established that a recovery cluster can read and decrypt every required object during an outage. The RESTORE reference specifies version, region, privilege and destination restrictions.

 The small native drill restored only a projection of this shop: three products, order 103, two lines and the payment-operation tables. Its interior restore produced the expected earlier facts; a latest restore produced 2.20 and payment 504. This establishes those SQL outcomes on one disposable node with local backup storage. It does not measure production recovery time, test cloud credentials, demonstrate node survival or prove application runtime access. Rehearse the whole recovery path with representative size and access arrangements before relying on an outage budget.
 Reconcile the later payment
 The candidate can be prepared while the source is still serving traffic. Final reconciliation needs a finite source history. Stop new source writes and external dispatch, account for transactions and provider calls already in flight, and prevent stale callers or workers from adding authoritative work there. Preserve the final source evidence. Moving a SQL application to CockroachDB (planned) owns the complete application handover; these are the conditions the recovery depends on.
 If the source was destroyed, work from the evidence that survived and retain any gaps explicitly. A missing local payment row does not establish that the charge failed. In this branch, the hypothetical provider offers a retained, queryable result for order-103-part-payment-1. Its immutable meaning is order 103, 10.00 by card, with local result payment 504. Query and compare that result before repairing the database.

 The mapping’s operation identifier is a primary key, and its payment identifier is unique and references the payment. Keep the mapping immutable. A constraint can reject a second identity or payment; the recovery procedure must still compare the stored payload and result. Plain ON CONFLICT DO NOTHING would hide whether the existing record means the same thing.
 Before insertion, verify that order 103’s agreed lines still total 29.00, its state permits the payment, and the known 10.00 fits the remaining balance. Stop on partial or inconsistent local evidence. If the transaction aborts, retry the whole database decision using the same operation identity; if its commit result is uncertain, look up that identity before choosing the next action. CockroachDB transactions and retries develops those native retry paths.
 The native drill inserted the payment and mapping, then read back the same mapping on a repeat. A blind duplicate insert was rejected with 23505. Payload comparison was performed by the verifier; no constraint was claimed to decide whether a changed amount was a valid retry. No provider request ran: the accepted outcome was supplied evidence.
 Keep the retained purchase
 The repaired database records 10.00 against 29.00, leaving 19.00 due and order 103 pending. P7’s agreed unit price remains 20.00. Its recovered catalogue price does not reprice the order. Stock remains P3 10, P7 0, P9 4 because the purchase already consumed it before the restore point.
 Do not send another charge or call the purchase routine to recover this payment. An unavailable provider outcome remains unresolved. A mismatched order or amount requires investigation. If other later work depended on the 2.20 price, assess its original agreement and dependencies separately; restoring a database cannot decide its business treatment.
 Return the recovered service to use
 For this branch, the completed result is concrete: P7 at 20.00; order 103 pending for 29.00; payment 504 and its original operation mapping recorded once; 19.00 due; stock still 10/0/4. The old source can add no more authoritative work, and the finite set of later operations has dispositions, including named unresolved cases.
 Verify runtime access and application reads, route callers to one recovered authority, and resume external dispatch only after its earlier effects are accounted for. Operating and securing a CockroachDB cluster covers cluster health and access in more detail.
 Establish and test backup coverage for the recovered history before relying on it. Keep the original recovery material and evidence according to the agreed retention decision. Record the achieved recovery point, elapsed stages, restricted service and remaining exceptions. A restored database becomes a recovered service when its facts, authority and external obligations agree.

 A PostgreSQL upgrade moves a database to a new server version. A migration can also move it to different hardware, storage or a managed service. In both cases, the shop must emerge with the same accepted orders, payments and stock, and with exactly one place allowed to accept new work.
 Copying the data is only part of that move. The application needs its schema, access identities, extensions and sequence state. Its workers need to know which database now owns their work. And the last accepted source change must reach the target before the target accepts new shop work.
 We will move the small shop after order 103. P7’s catalogue price is 20.00; stock is P3 10, P7 0 and P9 4. Order 103 is pending, has no payment and contains agreed lines totalling 29.00. After the handover, a target-only change raises P7 to 22.00. Following those two prices will show when returning to the old server stops being a simple switch.
 Choose an upgrade method
 A minor update, such as 18.5 to 18.6, stays within one major release. PostgreSQL keeps its storage format compatible: stop the server, replace its executables and restart, following the package and release instructions. A major upgrade, such as 17 to 18, needs a supported transfer. Starting version 18 on version 17’s data directory is not that transfer.
 Read the Migration notes for every major release crossed, even when skipping directly to a later one. The question is whether your clients, SQL, extensions and operating tools remain compatible. Promoting a physical standby also stays within its compatible server version; it does not turn that standby into a new major release.
 There are three ordinary transfer routes. Figure 1 puts their work on either side of the write pause. Compare where the large copy happens, then look at what must still happen before callers return.

 A work map, not a time scale. Every route includes draining writers and moving callers. The logical route moves the bulk copy earlier; it adds a stream whose coverage and final applied state must be established.
 pg_upgrade creates the new version’s system catalogues and transfers the user data files. It avoids reconstructing every row and index through SQL. It suits a compatible cluster when you can stop it for the transfer and acceptance, and can provide both versions’ software and the required storage access.
 Dump and restore reconstructs definitions and data in an independent target. A final dump taken after closing source writes gives the target a finite state to reproduce. The pause includes exporting and restoring that state, so the simplicity can be expensive for a large database. It is useful when changing the physical environment or when the application can tolerate the measured interruption.
 Logical replication copies selected table data while the source remains in service, then follows changes. This moves much of the copying before the pause. In exchange, you must maintain a compatible target and stream, account for state outside that stream, and prove final catch-up. Choose it when those obligations are worth the shorter final copying interval, rather than because a worker reports zero lag.
 A provider may wrap these routes in its own migration service. Check its actual scope, supported versions, extension restrictions and return procedure. A button labelled Upgrade still has to satisfy the same data and authority conditions.
 Define what must survive the move
 Begin with the service the target must provide. A catalogue copy with three correct products cannot take over the shop: it lacks customers, orders, order lines and payments. The products-only publication in PostgreSQL logical replication and change feeds deliberately serves a narrower purpose.
 The migration inventory joins each required thing to a way of transferring and checking it. This small shop fits in one database. If your service spans several databases, include them all and establish a coordinated final state across them; independent live exports do not create a shared business boundary.

 A single-database pg_dump does not export cluster-wide roles or tablespaces. A reviewed pg_dumpall --globals-only export can supply required globals, with destinations and access deliberately adapted. Neither tool moves an email worker’s configuration or proves that the application’s password works at the target.
 Rehearse using the intended target server, extension versions, driver and application build. Run representative requests through the runtime identity, including transaction boundaries and error handling. Exercise migration and monitoring tools too: a tool reading system catalogues can break even when the shop’s ordinary SQL still works.
 Include the operating system and collation libraries in that rehearsal. A collation defines text comparison and ordering. A changed library version can require rebuilding affected indexes; merely refreshing the recorded collation version does not rebuild them. Test the text comparisons and uniqueness rules the application depends on, alongside the required maintenance.
 Rehearse pg_upgrade
 Use the new version’s pg_upgrade. Install compatible extension software and initialise an empty target with compatible cluster settings. For a 17-to-18 move, check checksums explicitly: version 18’s initdb enables them by default, while an older cluster may have them disabled. The rehearsal here used --no-data-checksums for the new cluster to match its source.
 Run --check with explicit old and new binary and data directories, then perform a complete upgrade on a separate rehearsal copy. These command shapes assume verified, stopped clusters and a server-owned socket directory; the variables name those deliberately chosen resources.

Keep the reports from the full run. Complete its required repair and extension work before using affected objects, and its recommended statistics work before judging representative plans. PostgreSQL 18 can preserve planner statistics; that does not mean every needed statistic from an older source is available.

 In the isolated PostgreSQL 17.11-to-18.6 rehearsal, --check and the full upgrade completed in both copy and link modes. The order table’s files had different underlying file identities in copy mode and the same identity in link mode. The copy-mode source restarted separately; the link-mode source was never started after its target. Both targets retained pending order 103, total 29.00 and stock 10/0/4.
 Keep an independent, tested recovery copy whichever mode you choose. Copy needs space for independent user files. Clone uses copy-on-write where the filesystem supports it. Link needs both data directories on the same filesystem and shares user files; once the new server starts, the linked old cluster is unsafe to use. Before that start, returning requires the documented control-file procedure. An old directory still being present is not sufficient evidence that it can be started.
 Measure the complete rehearsal: stopping and draining, the transfer, required follow-up work, acceptance and reconnecting callers. A small fixture checks mechanics, not a production duration. Changes in data size, extension work, storage throughput or the chosen mode invalidate a duration borrowed from another rehearsal.
 Prepare an independent logical target
 A dump is a consistent saved view, even when the source is live. It does not include commits made after that view. For a stopped-writer migration, close and drain source writes before taking the final dump, then keep the source closed while reconstructing and accepting the target. Restoring PostgreSQL to a recovery target gives the restore procedure and its checks.
 A streaming move needs its initial copy and following changes to fit together. An arbitrary dump followed by a new stream can miss a transaction committed between their starting points. Use a coordinated copy protocol, such as native table synchronisation, and check every required table reaches its ready state. The logical replication article develops publication selection, replica identity, setup and repair.
 Keep application writes and external dispatch off the candidate while it is being prepared. Coordinate DDL on both sides. Native logical replication transfers table changes, not schema changes, sequence state or large objects. Prepare those separately where required, and check relationships explicitly: normal logical apply does not provide the same foreign-key enforcement as ordinary application writes.
 The whole-shop rehearsal used one subscription for customers, products, orders, order lines and payments, plus a fixture-only migration marker. All six tables reached ready state. The five business tables then matched exactly. Yet the target’s separate demonstration sequence still held 1, is_called = false, while the source’s demonstration sequence had been set to 103. Correct rows had not made the target ready to allocate order numbers.
 After source allocation stopped, the rehearsal transferred that sequence’s final state. Its next target value was 104, without creating an order. In a real migration, handle every sequence’s actual increment, bounds, cycling and allocation policy; max(id) alone can miss reserved values or a sequence used elsewhere. Sequence state must be final before any target allocator starts.
 Close the source history
 The final source boundary is the point after which no more accepted source work can appear. A connection address does not establish it. Old pools can keep existing connections, and an import worker or scheduled task can wake later using its saved settings.

 First stop new work at every entry point, then drain work already admitted. Include application pools, imports, jobs, administrators and automatic restarts. Establish the outcome of transactions whose commit reply was lost, using retained request identities rather than blindly repeating them. Stop external dispatch and account for calls already in flight: a database pause cannot cancel an accepted provider operation.
 Next prevent the former source from accepting more authoritative work. The mechanism depends on the deployment: access revocation, connection termination, isolation, stopping the server and controlling its restart may each cover different paths. Merely setting the application’s new address, or changing a default that existing privileged sessions can override, leaves those paths open. Test a stale caller and the restart path in the rehearsal.
 Only with that closure can you identify a finite required source history, B in the drawing. For a logical move, wait for durable applied progress in the exact target’s source stream to cover B. Check all required tables are ready as well. Received messages, an active apply process and a displayed lag of zero answer different questions.
 In the native rehearsal, the only application writing role lost its source write privileges. A subsequent write through that role failed. After the final required shop changes, the verifier sampled a source WAL position and committed a published marker beyond it. On the subscriber it checked that this subscription’s replication origin had durably applied through the sampled position, and that the marker was visible. Fresh queries then compared every row of all five shop tables.
 The marker ensured there was a later published transaction to observe; it did not turn omitted tables into replicated data. The origin’s source position and the sampled source position belonged to the same identified publisher history. A subscriber’s local WAL position, or a position from an unrelated cluster, is not interchangeable with either. A move spanning several independent streams needs closure and coverage evidence for each required history.
 This was a bounded local role test. It did not establish that a real deployment’s administrators, old hosts or failover automation were excluded. Those are part of the authority rehearsal you must supply for that deployment.
 Accept the target before admitting writers
 A final boundary makes comparison meaningful: source facts can no longer change beneath it. Take fresh target observations, rather than reusing an old report snapshot. Compare required keys and values, deletions and relationships. Equal row counts can hide a missing order and an extra order, and equal totals can hide wrong lines.

 Those results are useful because they describe different obligations. Order 103 must remain pending; absence of a payment is meaningful. Its agreed mug price must remain 20.00 even when a later catalogue update makes P7 cost 22.00. Stock already includes the purchase, so replaying order creation would decrement it again. The inspection query is a readable summary, not a substitute for the complete comparison.
 For a larger service, rehearse how complete comparisons will finish inside the permitted pause. You can prepare comparisons earlier, but their final change coverage must still be accounted for. Decide which exceptions are acceptable and reconcile them explicitly; an unexplained difference is not an acceptance result.
 Test the actual application identities, ordinary reads, guarded writes and expected refusals. Keep external dispatch disabled. The local rehearsal rolled back a controlled price update, then checked that 20.00 remained. Such a test avoids a retained table change, but a transaction rollback does not rewind sequence allocation or a call already sent outside PostgreSQL. Use isolated test identities where needed and account for retained effects before deciding whether return is still simple.
 After acceptance, move callers and dependent work deliberately. Replace old pooled connections, check each caller’s actual destination and keep the source excluded. Enable jobs and external dispatch only under the new authority, preserving stable work identities and resolved outcomes. Required consumers and replicas need their own compatibility and progress checks; they do not follow just because the primary application has reconnected.
 Know when a simple return ends
 Before new authoritative target work, returning can mean excluding the candidate, confirming the preserved source is usable and complete, then moving callers back. Rehearse that path as carefully as the forward path. Link mode may already have removed it at target startup. Validation may also have left accepted changes or external effects before public traffic was enabled.
 The last step of Figure 3 crosses a different boundary. The target commits P7 at 22.00 while the excluded source remains at 20.00. Both databases can be physically healthy. Reopening the old one would still lose an accepted price change. This target-only update and the unchanged 29.00 agreement were observed in the native rehearsal.
 After that boundary, a return needs a tested way to preserve target work: transfer compatible changes back, reconcile them into a suitable restored system, or repair the target and continue there. Close target writes before defining that recovery’s final history. Preserve order, payment and request identities, and account for external effects independently. An email sent or a charge accepted does not disappear when the database changes.
 Reverse replication is a new compatibility and completeness problem, not an undo switch. Nor does a dump from a newer server promise restoration into an older major version. Decide the recovery route and its limits before the first target write, while you still have time to rehearse it.
 Finish the migration
 The accepted target needs a recovery path of its own. Establish backup and required redundancy, test restoration with the new version and extensions, and verify that archive destinations, credentials and monitoring name the new service. Keep the former recovery material until a tested replacement and the agreed retention decision make it safe to retire.
 Retire the old application access, connection settings and restart paths as well as its files. Remove obsolete subscriptions and slots deliberately once they are no longer needed, checking both ends; a disabled consumer can keep source WAL retained. Record the achieved interruption, accepted exceptions and any remaining obligations.

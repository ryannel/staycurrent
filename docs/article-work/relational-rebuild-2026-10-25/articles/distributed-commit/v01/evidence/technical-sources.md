# Primary sources checked · 25 October 2026

- Gray & Lamport, *Consensus on Transaction Commit*, https://lamport.azurewebsites.net/video/consensus-on-transaction-commit.pdf . Read sections 2–3 (requirements, durable state, blocking), recovery discussion and abstract/conclusion for Paxos Commit. Initial `/pubs/transaction-commit.pdf` was inaccessible; recovered authoritative author-hosted PDF at `/video/consensus-on-transaction-commit.pdf`.
- Microsoft protocol overview https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tpsod/e34079f0-22de-4c03-9cb8-84c2448a4613 . Positive readiness, negative refusal, second-phase outcome delivery and pre-vote unilateral abort. The figure is explicitly simplified and does not prescribe this native protocol.
- PostgreSQL18 PREPARE TRANSACTION https://www.postgresql.org/docs/18/sql-prepare-transaction.html . Prepared state detached from session, stored durably, locks retained and effects not visible until committed. Used as concrete corroboration, not instructions for ordinary application code.
- Google Spanner https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes , especially multi-split write steps 7–13. Participant/replica distinction, replicated preparation/decision, apply-after-commit and safe-read waits. No Spanner execution, latency or clock claim reported.
- Spanner https://cloud.google.com/spanner/docs/secondary-indexes (global index entry in a different split entails distributed transaction; uniqueness at commit) and https://cloud.google.com/spanner/docs/foreign-keys/overview (enforced-reference maintenance/backing indexes and extra requests). These corroborate possible extra ownership work; the shop drawing is not a Spanner schema.
- CockroachDB https://www.cockroachlabs.com/docs/stable/architecture/transaction-layer . Cross-range atomic commit, provisional writes, state-based resolution and post-commit cleanup; native implementation delegated to crdb-transactions. No native timings, retry code or complete native protocol taught here.

All schedules are conceptual. `verify-model.mjs` checks a finite safety model and counterexamples; it proves neither production protocol correctness nor liveness. `verify-purchase.mjs` checks ordinary local SQL in owned PGlite; it does not exercise distributed commit, quorum recovery or native server behaviour. The reader article reports no observed engine run and offers no runnable SQL/download.

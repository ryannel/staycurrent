# Assembled relational collection: review context

Audience, scope and publication boundary are in ../commission.md. All59 articles are independently accepted; the single assembled review reuses those checks. Do not rereview the whole corpus prose or reopen optional polish.

## Accepted learning routes

- Read the shop: relational-introduction. Acquire the vocabulary to read related facts, a first query and an atomic purchase.
- Design and query facts: data-modelling, values, constraints, query-results, aggregation, history. Choose row meaning, keys, values and rules, and construct results with the intended grain.
- Build an application: writes, application-sql, pagination, transactions, locks, retry-outcomes, outboxes-jobs, access-control. Carry correct reads and conditional writes through a real connection, large results and recoverable requests.
- Explain and reduce work: query-execution, indexes, partitioning, storage-durability. Trace work through operators and physical storage, then test access paths and lifecycle boundaries.
- Keep service and history: backups, replicas, failover, incidents, capacity, schema-change. Recover usable history, route to copies deliberately and intervene safely while callers and schemas change.
- Distribute deliberately: distribution, distributed-commit, distributed-snapshots, placement, cluster-change. Choose distribution from locality and invariant scope, establish authoritative agreement within replicated partitions, and reason about cross-partition transactions, reads, placement and membership.
- Practise on the chosen system: pg-architecture, crdb-architecture. Use native evidence and procedures in PostgreSQL or CockroachDB, entering at the task at hand and adding the concepts it requires.

## Direct task routes

- I have never used a relational database: relational-introduction → data-modelling, query-results, writes, transactions, application-sql. A short useful foundation; formal modelling children are optional depth.
- Design a schema: data-modelling → values, constraints, history. Take normalisation or hierarchies only when the design needs their deeper analysis.
- Fix duplicated or missing query results: query-results → aggregation. Result correctness before physical tuning. The still-due report is complete in query results.
- Make checkout safe: transactions → writes, locks, retry-outcomes, outboxes-jobs. Read application SQL for driver and connection ownership. A one-row stock guard does not establish a multi-row capacity rule.
- Fix a slow request: incidents → capacity, locks, query-execution, indexes. Choose the branch evidence identifies; these are alternatives, not a compulsory reading sequence. Native evidence is in pg-operations, crdb-performance for SQL/KV work, or crdb-operations for cluster health.
- Recover from a failure or bad change: backups → storage-durability, replicas, failover. Choose restore, restart or promotion from the failure; native procedures begin at pg-backup/pg-wal/pg-replication or crdb-backup.
- Change a live schema: schema-change → pg-schema-change, crdb-schema-change. Select the native article for the system in use; they are alternatives.
- Operate PostgreSQL: pg-architecture → pg-operations, pg-plans, pg-vacuum. Use the native task article directly when already familiar with its prerequisite concepts.
- Operate CockroachDB: crdb-architecture → crdb-transactions, crdb-performance, crdb-operations. Use the native task article directly when already familiar with its prerequisite concepts.
- Decide whether and how to distribute data: distribution → distributed-commit, distributed-snapshots, placement, cluster-change. Distribution establishes agreement within a replicated partition before these consumers. Native alternatives are pg-distribution and crdb-architecture; common SQL does not imply a common operating contract.
- Add PostgreSQL search or specialised data: pg-indexes → pg-text, pg-vector, pg-json, pg-extensions. Select by query semantics; these capabilities are alternatives, not a single search ladder.

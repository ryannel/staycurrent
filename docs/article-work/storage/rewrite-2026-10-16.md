## Running model

The figures share one PostgreSQL server and one update. The `products` table has rows P3 at 18.00, P9 at 9.50 and P7 at 20.00, all on page 12. Transaction 812 sets P7 to 22.00. The prices, the page number, the transaction id and the LSNs are invented and labelled as such in the intro.

The server figures have two lanes:

- **Memory** holds shared buffers (page 12) and WAL buffers. It is lost in a crash.
- **Disk** holds the table file (page 12) and the WAL file in `pg_wal`. It survives.

The application sits above both lanes. Rows and records fly in from where they came from. Figures 4, 5, 6 and 10 use this exact layout. The others zoom in on one part of it: the page, the buffer pool, the WAL stream or the flush path.

## Animations

Every figure has play/pause, back, next, a scrubber and reset. Parameters are listed where a figure has one.

| # | Scene | Job | Parameter |
|---|---|---|---|
| 1 | `page-fill` | Shows how row width sets rows per 8 kB page (120, 61, 28, 7, 4). | Row data: 40 to 2,000 bytes |
| 2 | `buffer-read` | Shows reads as hits or misses in a four-slot buffer pool, with eviction. | None |
| 3 | `row-versions` | Shows an UPDATE adding a new version, with xmin/xmax deciding what each reader sees. | None |
| 4 | `dirty-crash` | Shows a dirty page lost in a crash when there is no WAL. This is the simple version that breaks. | None |
| 5 | `wal-commit` | Shows the WAL record flushed before COMMIT returns, with the page written later. | None |
| 6 | `crash-recovery` | Shows what replay recovers for crashes at three points. | Crash: before flush, after flush, after reply |
| 7 | `checkpoints` | Shows checkpoint frequency trading replay length against page writes and full-page images, over 40 fixed page touches. | Every 5, 10 or 20 records, or never |
| 8 | `torn-page` | Shows a half-written page as 16 sectors, and the full-page image repairing it. | full_page_writes on/off |
| 9 | `flush-path` | Shows a commit moving through four layers, and a drive that acknowledges early. | Drive honours or ignores flushes |
| 10 | `async-commit` | Shows the reply arriving before the flush, so a committed change is lost. | Crash before or after the WAL writer |
| 11 | `vacuum` | Shows HOT pruning keeping updates on one page, and a held snapshot forcing an update onto page 13. | Snapshot: none or held |

## Unsure about

- **TOAST.** The wording that TOAST aims to fit "at least four rows" on a page paraphrases the 2 kB threshold rationale. It is worth a second read against storage-toast.
- **7,200 rpm.** The figure of "about 120 flushes a second" for a 7,200 rpm disk is a standard back-of-envelope estimate (one commit per rotation). It does not come from the PostgreSQL docs.
- **Power-loss protection.** The sentence on server drives with power-loss protection is general hardware knowledge. The docs only say to check for it.
- **Simplifications in the figures.** Checkpoints happen instantly instead of spread over checkpoint_completion_target. Pages hold six row slots in the vacuum figure. The buffer model has no index pages. Each simplification is noted in the captions or step text where it matters.
- **The "never" checkpoint option.** It exists for comparison only. PostgreSQL always checkpoints, by time or WAL volume.
- **Torn pages.** The torn-page figure writes sectors in order. Real drives give no ordering guarantee, so the tear could be anywhere.

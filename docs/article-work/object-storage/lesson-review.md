# Object-storage lesson review

Reviewed 16 October 2026. This is an informed independent review of all 14 lessons and 78 steps in `src/lib/object-storage/lessons.mjs`, compared with their linked articles and the implementation boundaries in `model.mjs`. It follows the earlier browser review; it does not claim a fresh reader's perspective or repeat the coordinator's execution of every step.

The lessons teach useful decisions rather than merely demonstrate successful API requests. Their strongest sequences make a reasonable assumption fail, expose the state that explains the failure, then ask the reader to repair the decision. The changes below make that teaching more self-contained and prevent simplified application commands from appearing to provide real content validation or service execution.

## Progression and limits

Readers can move from named objects to conditions and transfer state, then use those mechanisms in application publication and recovery. The advanced lessons reuse those ideas with clear boundaries: table commits use a simplified manifest, and vector retrieval uses exact arithmetic. Neither claims to emulate the managed AWS service.

Direct entry is now supported by explicit starting contents in the lessons that rely most heavily on seeded state: keys, concurrent writers, publication, cache and table commits. Other sequences either start empty, reveal their seed through the first read, or display the full fixed dataset before prediction. The instructions identify relevant inspectors without making the learner discover hidden setup by trial and error.

The local exercises deliberately cover selected mechanisms from the articles. IAM evaluation, content safety, SQL commits, actual transfer concurrency, lifecycle scheduling, Iceberg metadata and approximate retrieval require the articles or real-service practice. These omissions are bounded in the lesson scopes. No extra exercise is required simply to match every article section.

## Focused article repairs

The Tables figure previously compressed the reference chain enough to obscure what was a file and what was a record inside a file. It now traces catalog → table metadata file → snapshot record inside that metadata → manifest-list file → manifest files → data files in an ordered figure. The following commit example still supplies the competing operations and selected file sets.

The delayed-commit discussion now explains that “noncurrent” belongs to S3 Tables' managed cleanup, rather than ordinary version history available through a version-specific GET. Checked the current [table-bucket maintenance guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-table-buckets-maintenance.html): viewing or recovering such files requires AWS Support; deletion after that stage is permanent. This is a recovery route to contact, not a guarantee that a particular file will be restored. The article separately preserves the distinction between extending future cleanup eligibility and restoring already inaccessible data.

Vectors now introduces the reason for approximate indexing before its exact-recall baseline: avoiding comparison with every stored vector can speed retrieval at scale, while missing exact nearest neighbours remains possible. It does not name or infer S3's internal algorithm. The distinction between recall and answer usefulness is unchanged.

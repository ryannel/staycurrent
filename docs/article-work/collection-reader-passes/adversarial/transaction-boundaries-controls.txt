The whole database attempt, including connection cleanup

This JavaScript-shaped teaching function joins the branches we have followed. Its query and pool methods follow node-postgres. The injected isKnownTransactionRejection function is an application adapter with a narrow contract: it returns true only when the error establishes that this transaction did not commit, such as a confirmed serialization failure or deadlock rejection. A PostgreSQL error response is not enough on its own: transaction-resolution-unknown (08007) and statement-completion-unknown (40003) must return false, as must a timeout or disconnected socket. Implementing that adapter, HTTP responses and durable recovery is outside this example.

// Teaching application code using a node-postgres-shaped client.
// isKnownTransactionRejection must confirm the attempt did not commit (for example 40001/40P01).
export async function checkoutAttempt(pool, purchase, isKnownTransactionRejection) {
  const client = await pool.connect();
  let commitSent = false;
  let reusable = false;
  try {
    await client.query('BEGIN');
    const reservation = await client.query(
      `UPDATE stock SET available = available - $1
       WHERE product_id = $2 AND available >= $1
       RETURNING available`,
      [purchase.quantity, purchase.productId]
    );
    if (reservation.rows.length === 0) {
      await client.query('ROLLBACK');
      reusable = true;
      return { status: 'unavailable' };
    }
    await client.query(
      `INSERT INTO orders (order_id, customer_id, placed_at)
       VALUES ($1, $2, $3)`,
      [purchase.orderId, purchase.customerId, purchase.placedAt]
    );
    await client.query(
      `INSERT INTO order_lines
         (order_id, line_no, product_id, quantity, unit_price)
       VALUES ($1, 1, $2, $3, $4)`,
      [purchase.orderId, purchase.productId,
       purchase.quantity, purchase.unitPrice]
    );
    commitSent = true;
    await client.query('COMMIT');
    reusable = true;
    return { status: 'purchased', orderId: purchase.orderId };
  } catch (error) {
    if (commitSent && !isKnownTransactionRejection(error)) {
      const unknown = new Error('Commit outcome unknown', { cause: error });
      unknown.outcome = 'unknown';
      throw unknown;
    }
    try {
      await client.query('ROLLBACK');
      reusable = true;
    } catch {
      // Cleanup failed. Keep reusable false: discard this connection.
    }
    throw error;
  } finally {
    client.release(!reusable); // true tells the pool to discard it
  }
}

finally runs whether the function returns or throws. A connection with confirmed commit or rollback can be reused. Passing true to node-postgres’s release discards a connection whose state we could not clean up. If COMMIT was sent and the error does not establish a known rejection of that attempt, the function throws an outcome-unknown error and discards the connection; it does not silently retry or claim a rollback. The caller must keep that operation unresolved until recovery establishes its outcome.

Optional: send the featured-products commands from psql

Add this table once to a fresh practice schema. In two connections, begin the transaction below and let both SELECT statements return two before either update. You are acting as each staff handler: run its SELECT first, read the returned count, and send the UPDATE only if the count exceeds one; otherwise enter ROLLBACK and stop. SQL comments do not perform that check. A hides P7; B hides P8. Both use Serializable. One may receive a serialization failure during its work or at commit, so do not depend on a particular victim or error location.

CREATE TABLE featured_products (
  product_id text PRIMARY KEY REFERENCES products (product_id),
  enabled boolean NOT NULL
);
INSERT INTO featured_products (product_id, enabled)
VALUES ('P7', true), ('P8', true);
-- A hides P7 below. B runs the same count, then hides P8.
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) AS enabled_count
FROM featured_products WHERE enabled;
-- Application continues only if enabled_count > 1.
UPDATE featured_products SET enabled = false
WHERE product_id = 'P7';
COMMIT;
-- A serialization failure means retry the whole decision.

Recovery uses a unique key on the order, verifies matching purchase details, and changes stock only in the successful new-claim branch. Availability and order counters show committed state.

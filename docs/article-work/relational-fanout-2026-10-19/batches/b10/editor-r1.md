# b10 — adversarial editor, round 1

Reviewed all three adoption plans and their supplied contexts against the original relational-practice goal. No context-linked or other review report was read. The test is whether each destination adds decision-changing implementation knowledge after the common curriculum and selection parent.

## a32 — Checking an embedded choice with SQLite

**Pass.** File ownership, loaded-library behaviour, writer coordination, journal settings and consistent recovery have implementation consequences that the predominantly server-based common examples do not supply. This remains a conditional adoption article rather than a required SQLite course. No children are justified.

- Keep deployment/file access as an early rejection gate. The library/build-options check should be a compact acceptance record, not an extension/threading catalogue.
- Reuse one two-connection case for write acquisition, busy outcomes and reader/writer lifetime. Explain only the journal/checkpoint mechanics that change those observations or the durability choice; avoid a second storage-engine account.
- The data-contract section should exercise required differences through the actual driver. Reuse the existing schema/representation fixtures and omit unrelated SQL features. This loses a SQLite syntax tour, not a capability needed to accept or reject this deployment.
- Keep one independent restore as the concrete recovery check. Restart/upgrade/interruption cases should add only the embedded-file failure conditions; link general restore/cutover methods. The closing decision record should collect the evidence rather than repeat all the tests in prose.

## a33 — Checking a server choice with PostgreSQL

**Repair: fold the candidate configuration and evidence record into a08, “Choosing a relational database”, rather than retain this as a separate teaching article.** The expansion makes the duplication visible. Most common worked articles already use PostgreSQL, and every a33 section either re-runs those existing examples or applies the selection parent's existing deployment/rejection checklist.

- “Turn the shortlist into a checkable deployment” is the parent's process/hosting choice with a version/driver record.
- “Verify the application contract” explicitly reuses the common schema/query/correctness tests. Preserve links to their observed PostgreSQL evidence and record only what differs in the intended service.
- “Check connections and transaction lifetimes” adds no distinct lesson beyond integration's PostgreSQL/driver ownership, performance's retained-version consequences and the common capacity method. Keep the candidate's measured limits in its acceptance record.
- “Establish the hosting and durability contract” repeats the parent's deployment responsibility table and operations' contract/recovery evidence. Preserve service-specific restrictions, dates and unresolved obligations as entries in that shared table.
- “Record a starting configuration and adoption decision” is useful output, but it is the parent's existing final decision record populated for the server candidate. A concise linked record or worked table is sufficient.

Concrete repair: keep a compact PostgreSQL candidate record beneath the parent's server-choice/adoption sections, linking common evidence for configuration, correctness, workload and recovery gates. Include version/tier, actual driver/pool path, relevant settings, restrictions, acceptance gaps and owners. **Useful understanding lost: none.** The starting configuration and candidate-specific limits remain available; the reader avoids another destination restating which common tests to perform. If a genuinely new server-specific adoption failure is later identified, it can justify additional explanation then; the current plan does not identify one.

## a34 — Checking a distributed choice with CockroachDB

**Pass.** Placement, cross-region coordination, compatibility differences and the named failure goal create acceptance questions that the common PostgreSQL examples cannot settle. The plan stops at a minimal topology and one workload, which serves relational adoption rather than product specialism. No children are justified.

- Keep “which simpler deployment fails?” as the early gate. Topology and locality should use one annotated transaction route; explain replica/leaseholder/quorum terms only where they predict an acceptance result. No consensus or locality-feature catalogue is needed.
- SQL/client checks should reuse common fixtures and add the candidate's actual differences. Retry/unknown-outcome tests should demonstrate the existing integration contract on this implementation, not teach a second retry/idempotency design.
- Share the same regional workload between locality/contention and failure tests. Test only failure cases required by the adoption brief; an unrelated full node/zone/region/partition tour would add expensive breadth.
- Keep restore evidence separate from survival evidence, but reuse operations' procedure. The final cost/decision record should point to measured cases and unresolved gaps rather than restate common benchmarking, migration or recovery methods.

The repair removes a duplicate teaching destination, not PostgreSQL as a concrete implementation. SQLite and CockroachDB retain their bounded, different adoption decisions; none should grow a parallel vendor curriculum.

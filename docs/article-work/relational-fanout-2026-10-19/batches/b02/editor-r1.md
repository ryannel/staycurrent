# b02 — adversarial editor, round 1

Reviewed a04, a05 and their supplied contexts against the original relational-practice commission. No other review report was read. These findings concern scope, boundaries and reading cost.

## a04 — Building applications around a relational database

**Pass.** The four child splits correspond to distinct decisions: connection ownership, generated work, recovery of an application operation, and recovery of work outside its transaction. Removing one would either lose a required capability or substantially enlarge the parent.

- **Keep a complete ordinary request path in the parent.** A novice should see parameter binding, a bounded transaction and cleanup on success/error without visiting four child articles. Children should deepen failure cases rather than repeat that walkthrough. This saves repeated setup without losing the first usable integration pattern.
- **Separate resource cleanup from operation recovery.** “Managing connections and transaction lifetimes” owns session state, transaction affinity, draining/resetting/discarding and pool diagnosis. “Recovering database requests safely” owns what the timeout/cancellation establishes, whether work may still commit, and what the caller should do next. Explain cancellation/connection-reuse mechanics once in the connection child and link from request recovery. Conversely, keep idempotency, request budgets and reconciliation out of the connection child. No useful understanding is lost by consolidating these shared mechanics.
- **Bound “Controlling the queries your application performs” at generated work.** Captured SQL, query counts, row multiplication and materialisation bounds justify this child. Teach pagination semantics in the SQL branch and execution costs in performance; do not add independent pagination, streaming or ORM-specific curricula here. Retain only their application loading/ownership decisions.
- **Cut the downstream messaging curriculum from “Connecting transactions to background work and events”.** Keep event meaning, replay and retention only where needed to explain whether the relational change remains discoverable and recoverable. One transactional outbox/job example plus a bounded CDC comparison is sufficient. Broker administration, general consumer recovery and transport-wide ordering do not earn space here. The loss is messaging specialism; the practitioner retains the ability to account for committed intent, repeated effects, stalled publication and reconciliation.
- Keep binding, authorisation and value conversion in the parent as proposed. Driver round-trip checks are a different task from schema type choice and SQL expression semantics; link to those owners rather than repeating their money/time/null explanations. Do not create an additional security or driver-type article merely to elaborate this section.

## a05 — Understanding and improving database performance

**Pass.** The children serve recognisable investigations, rather than requiring mastery of storage engines or optimiser construction. The parent must complete one diagnosis-to-measured-improvement loop; it should not become five technical introductions followed by a testing checklist.

- **Give plan reading and plan-choice diagnosis one shared worked case.** “Following a query through its execution plan” owns collecting and interpreting the evidence; “Explaining and correcting plan choices” owns the estimation/parameter hypothesis and its remedies. The first consequential estimate/observation mismatch is the hand-off. Avoid teaching joins, plan instrumentation and the same skewed report twice. Keep the split while these remain distinct reader tasks; merge the two if their breakdowns simply repeat a plan walkthrough with increasingly detailed commentary. Such a merge loses no capability and saves a second reconstruction of the query and plan.
- **Trim the physical-storage child to diagnostic differences.** Keep pages/locality, row locators, wide values and retained versions where each explains measured work or a remedy. The index child owns B-tree traversal, key order, coverage and index eligibility. Fold repeated secondary-index/base-row access explanation into that owner. Keep physical pruning as one testable layout intervention, not a separate partitioning curriculum; operational reorganisation procedures belong to evolution/operations. This cuts implementation breadth while preserving the ability to explain cache pressure, page traffic and unreclaimed space.
- **Retain the index child.** Candidate design and read/write validation are too consequential to hide in a general plan article. Partial/expression/other index forms should appear only when a workload requires them; an index-family survey would add reading without another practical decision.
- **Retain concurrent-load diagnosis, but consolidate its resource model.** It owns offered load, achieved throughput, queuing and measured competition. The connection child in a04 owns pool implementation and cleanup; operations owns service budgets and provisioning. The physical-storage child owns retained-version mechanics. Reuse those explanations and test their workload consequences here. No additional pool-sizing, capacity-theory or version-maintenance destination is justified by this plan.
- **Cut repeated benchmarking instructions from the children.** The parent's final section should own the common comparison method and evidence checklist. Each child needs only its distinctive experiment and additional costs or confounders. Useful understanding lost: none; experiments still state enough conditions to interpret their results.

No blocking repair is required. The next breakdowns should preserve these task boundaries and reject descendants that merely expand a feature or mechanism inventory.

# Relational collection: improvement plan

Read-through commissioned on 5 October 2026. This is a plan for improving working
drafts. Article changes and publication are not part of this pass. The initial
revision is `985e5f71da2e346faf322bf48765a3124c740cbf`, with a clean working tree.

The collection has a strong explanatory spine: represent facts, enforce their
rules, ask questions, read changing results, group writes, coordinate decisions,
choose visibility and recover uncertain outcomes. The most useful repairs concern
the steps between that understanding and the examples a reader is asked to use.
They do not require a wholesale rewrite or more media on every page.

Evidence is preserved separately:

- [Sequential first reading](first-reader.md): independent questions recorded as
  the explanation arrived, with an inherited-concept ledger.
- [Browser reading](browser-reading.md): assembled prose and teaching aids in
  reading order, plus observed model outcomes.
- [Technical review](technical-review.md): scope, consequential claims and source
  checks, including the limits of existing execution evidence.

## Repairs to do first

### 1. P2 — Make the first SQL examples readable at their actual position

**Trigger.** Schema design's `#schema` presents aliases `l` and `p`, an expression
alias and ordering. Constraints' `#keys` uses multi-column positional inserts.
JSON's `#missing-values` presents `WITH samples`, `VALUES` and `::jsonb` before
the query article introduces general query syntax. The introduction explained
SELECT, ON and WHERE, but did not establish all these reading conventions.

**Reader consequence.** A reader can accept the prose's answer while being unable
to connect each instruction to that answer. Opening a complete table definition
does not explain how unnamed INSERT values map to it.

**Repair.** Keep the collection order. Give the receipt query a brief reading map
for its aliases and calculated output. Use explicit column lists in the multi-column
constraint and details-row inserts, explaining one VALUES mapping where first used.
Introduce the JSON diagnostic as a temporary named set of sample rows and explain
the cast notation before the block. Link to Queries and joins for practice. These
are local bridges, not a second full query tutorial in the design branch.

**Recheck.** Ask an independent reader to trace O12's €36 through the actual code,
map one rejected INSERT to its intended fields, and explain which sample columns
the JSON probe creates. Require passage-based reasoning and record any supplied
SQL knowledge. Verify changed runnable examples against the stated engine.

### 2. P2 — Finish one compatible JSON validation and querying path

**Trigger.** JSON's `#queries-and-rules` permits every JSON number, including 350.5, then
uses an integer text cast for querying. `#access-and-change` gives an expression
index using the same cast. The prose accurately admits that a permitted fraction
breaks that cast, and that conversion can fail during index maintenance.

**Reader consequence.** The reader understands the limitation but must invent the
remaining design before using the illustrated query and index reliably.

**Repair.** Complete one choice. A bounded route is to keep varying descriptions
in JSON and move correctness-critical capacity to the already introduced
`mug_details.capacity_ml` integer column. Show what happens to the valid, missing,
string and fractional cases, then query the accepted capacities. If capacity stays
in JSON, supply compatible validation, conversion and index expressions, including
the allowed range. Keep the weaker number check visibly an intermediate example.

**Recheck.** Every value accepted by the final rule must be usable by its query and
index. Exercise missing keys, JSON null, numeric strings, fractions, zero, negatives,
and an out-of-range number. Explain required versus optional capacity separately.
A reader should be able to say which representation they would choose and why.
Check the actual ingestion expression as well as the stored type: conversion of a
numeric fraction to integer can round, while converting extracted text such as
`'350.5'` to integer fails. If fractions must be rejected, enforce that policy before
conversion hides them. Do not use written AND/OR evaluation order as a cast guard.
If capacity moves to a column or details row, establish one authoritative value
rather than retaining independently editable JSON and typed copies.

### 3. P3 — Identify when the example starts again

**Trigger.** The introduction's index figure assigns O13 to C8; the design sequence
uses O13 for C4. Queries uses O14 at 11:00; pagination uses O14 at 12:00 to teach
ties; transaction boundaries begins without O14 and creates it. Later practice
setups often explicitly request a fresh database, but that does not always explain
the reset to someone reading only the main narrative.

**Reader consequence.** Reused identities invite the reader to carry their earlier
meaning forward. Changes can look like lost facts or an unexplained mutation.

**Repair.** Align the introduction's index sample where practical. At deliberate
changes, name the reset immediately before the starting records: for pagination,
say that this independent example gives three orders the same placement time; for
checkout, say O14 is a new purchase in a fresh setup. Keep a short authoring record
of shared identities versus independent schedules. Avoid a global dataset that
makes every teaching example harder to express.

**Recheck.** Read each affected transition without opening setup details. A reader
should know whether a changed value is an event to explain or a new starting state.
Confirm figures, tables, downloads and practice instructions agree within each case.

## Make two demanding passages easier to follow

### 4. P2 — Show how a stale whole-object write loses another change

**Trigger.** JSON's `#access-and-change` says `jsonb_set` avoids replacing an object
assembled from an earlier read. It also teaches that both writers take the same
row lock. The missing causal step is how serialized writes can still lose a change.

**Smallest useful aid.** Start with capacity 350 and material ceramic. A and B both
read it. A changes capacity to 375 and commits. B later sends its old whole object
with material changed to stoneware; capacity becomes 350 again. Place the stored
result beside the intended capacity 375/material stoneware. Then show the current-row
expression preserving both changes. A static four-event table may suffice; consider
an interaction only if comparing the two update forms adds useful exploration.

**Recheck.** The reader can explain why a write lock did not refresh B's already
assembled object. Any model must distinguish early reads, pending changes and
committed results and name its isolation assumptions.

### 5. Optional — Give the retry article a compact reference for later use

**Trigger.** The recovery article combines waits, cancellation, server error codes,
whole-transaction retries, missing replies, key lifetime and conflicting intent.
Each mechanism is explained, but recalling the appropriate response requires
scanning a long page.

**Smallest useful aid.** After the detailed explanation, collect observed evidence,
what it establishes, and the next action in a small table. Include an ordinary
zero-row result, waiting, a known retryable rejection, and an uncertain commit.
Retain “pending” when authoritative state is unavailable and require the same
operation identity during recovery. A static reference is preferable unless an
outcome-choice exercise exposes a specific misunderstanding.

**Recheck.** Give a reader a lost reply, an empty lookup while the first attempt
is active, and a deadlock error. They should choose distinct responses and explain
why starting another operation is unsafe in the uncertain case.

## Preserve differences between the readings

The independent reader understands the constraint outcomes table, the stated
limitations of the JSON number check and the benefit of jsonb_set. The technical
reviewer still supplies knowledge when adapting positional writes, completing a
compatible capacity contract and tracing the stale-object cause. The browser
reading also finds that the JSON contention drawing shows shared row locking,
while the lost-edit consequence has to be reconstructed separately.

Those observations support local practical repairs without establishing that every
reader is blocked. Similarly, the independent reader finds the fresh practice
setups clear enough to identify the new pagination and checkout examples. The
browser reading finds the reset less explicit when following the main prose without
opening setup details. Improving that main path is a navigation and continuity
repair, not a claim that the supplied practice instructions are wrong.
The first reader also gives the composite-reference counterexample more weight
than the technical reviewer. It is a recommended small clarification: O12 exists,
and line 2 exists under O13, but that does not establish line 2 of O12. Keep this
as an existence illustration; do not invent an executable foreign key to a
non-unique line-number column. No new interactive is justified by that finding.

The independent reader's pending-claim question is answered by the immediately
following recovery section. That is successful staged pacing. Keep the original
question and its resolution; a rewrite that moves every detail to the first claim
would remove useful progression without fixing an established blocker.

## Keep what is already teaching well

Preserve the introduction's transition from an empty order to atomic work; schema
design's dependence-driven transformations, lossless reconstruction and historical
price; constraint acceptance versus expression truth; JSON's explicit reconciliation
with normalisation; the query article's row identities, Cara's nonqualifying match,
fanout and separately grouped summaries; pagination's tied boundary and mutable-key
counterexample; transaction boundaries' zero-row branch and same-connection rule;
concurrency's waiting-before-decision distinction; isolation's own-write and write-skew
examples; and recovery's stable-key claim that waits on the original attempt.

There is no evidence here that the collection needs every SQL feature, all normal
forms, a complete payment integration, or every planned operations article to make
these focused explanations useful. Collection completeness remains broader than
article completeness. Human first-time-reader feedback would test the remaining
uncertainty better than another expert declaring the concepts present.

## Suggested implementation order and checks

Begin with the SQL reading bridges and example resets, because later repairs rely
on the reader recognising the examples. Finish the JSON design path next. Add its
stale-write schedule and the retry reference only where the existing prose still
requires excessive reconstruction. Then choose the optional worked examples from
actual reader questions rather than commissioning all of them together.

For article implementation, execute changed SQL examples as needed and run
`pnpm build`. Recheck narrative changes with an independent sequential reader;
inspect changed aids in the browser, including their relevant controls and layouts.
The browser observations in this pass are illustrative-model checks, not database
concurrency tests or a complete accessibility review.

## Workflow changes and validation

copies under `.claude/skills/`. The guidance now explicitly routes read-through

and did not ask for additional media merely because an idea was difficult. It also
noticed that extraction exposed optional and fallback text before those boundaries
were classified. The final guidance explicitly asks for visibility markers before
chunk delivery. This limited check does not establish full collection comprehension
or verify browser behaviour.

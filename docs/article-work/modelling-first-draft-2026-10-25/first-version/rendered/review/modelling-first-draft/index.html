Relational data modelling

Deep diveAbout 19 minutesAI-generated

Relational data modelling is deciding which facts a database records, what one row means, and how rows refer to one another. A shop can put a customer’s name on every order line, or store it once in customers and refer to that row. Both designs can display the same receipt. They differ when the name changes, when a customer has no orders, and when an order is removed.

A useful model makes those changes straightforward. Each fact has a place where it can be recorded without inventing another fact, and a correction has a clear set of rows to change. Keys preserve the distinctions the shop cares about. Relationships say which things belong together. Normalisation checks whether some of those facts have been copied into places where they can disagree.

The examples follow the small tea shop from the relational introduction. Mina Shah has orders 101 and 103, Tariq Aziz has order 102, and Edda Berg has no orders. Order 103 contains one blue mug, P7, at 20.00 and two packets of green tea, P3, at 4.50 each. Its total is 29.00 and it has no payment. Later sections add small hypothetical catalogue and supplier examples; they do not change those orders.

What one row represents

Before choosing columns, finish the sentence “One row records …”. One row in orders records one order placed by one customer. One row in order_items records one numbered line on one order. One row in payments records one payment towards one order. These are three different levels of detail, often called the grain of a table.

The difference matters when two things can happen independently. Order 101 has two lines, green tea and a teapot, and two payments, 30.00 by card and 9.50 by gift card. Neither payment is assigned to a particular line. Put a line and a payment in the same row, matching only their order, and each line meets both payments.

The four rows are a valid answer to “Which line–payment combinations share an order?” They are a poor home for either fact. Adding a payment would require copying every line; adding a line would require copying every payment. An order awaiting payment would need an empty payment field just to hold its lines.

Keep the lines and payments separately, each referring to the order. A report can combine them when needed, taking care to total each set at its own grain first. Query results develops that reporting problem. If the shop later allocates a payment to individual lines, that allocation is a new fact, with its own line, payment and amount. It cannot be recovered from the four combinations above.

Keys and identity

A key says which values distinguish one row from every other row the table may contain. The important word is may. Mina, Tariq and Edda happen to have different names; the shop must still be able to register another Mina Shah. Names cannot identify its customers.

A customer’s ID identifies the customer while their name changes. The name describes that customer now. Confusing those roles either makes a correction change identity or prevents two people sharing a name.

Candidate keys and surrogate keys

A superkey is any set of columns that uniquely identifies a row. A candidate key is a minimal superkey: remove any of its columns and the guarantee disappears. “Minimal” concerns unnecessary columns, not how many bytes the key occupies. The primary key is the candidate key chosen as the table’s main identifier; other candidate keys still express real uniqueness rules.

A natural key uses a value that already identifies something in the domain, such as a shop’s established product code. A surrogate key is introduced to identify the row, such as an otherwise meaningless customer number. A surrogate is useful when existing identifiers are missing, wide or liable to change. It does not decide when two rows describe the same thing.

Suppose an order line gains a new line_id. Two rows could then have different line IDs but both claim to be line 2 of order 103. If the shop permits only one such line, it still needs uniqueness on (order_id, line_no). Adding an ID gives another way to address the line; it does not replace that rule. Constraints covers how to declare and maintain these guarantees.

Composite keys

An order line’s number is local to its order. Orders 101 and 103 both have a line 1, so line_no alone is not a key. Their pair, (order_id, line_no), is a composite key: a key containing more than one column. The order identifies the list, and the line number identifies an occurrence within it.

Using (order_id, product_id) would impose a different rule: one row per product on an order. Quantity could combine several identical units into that row, but a second occurrence of the same product could not have its own line. That might suit another shop. It is not the rule expressed by numbered order lines.

Try a hypothetical third line on order 103 for another P7, agreed at a different price. The composite key would distinguish (103, 3) from (103, 1). A key of (103, P7) would collapse that distinction. The core order has only two lines; the proposed third line tests the design’s meaning. No generated line ID can settle whether that occurrence ought to be permitted.

Relationships and cardinality

A relationship says which rows belong together. Its cardinality describes how many can participate. Read it in both directions, separating the minimum from the maximum: an order belongs to exactly one customer, while a customer can have no orders or many.

Figure 2 reads the shop’s references in words. Arrows point from a row carrying a reference to the row it identifies. “Exactly one” and “zero or many” describe permitted participation; Edda and Mina show two actual cases.

One-to-many and one-to-one relationships

The customer–order relationship is one-to-many. Put the customer reference on the many side, in orders. A single customer column can identify each order’s customer, while any number of orders can repeat that ID. A list of order IDs in the customer row would put the growing set on the wrong side of the relationship.

In the shop schema, a non-null customer reference makes an order identify one customer, and the foreign key requires that customer to exist. Neither requires every customer to be referenced. Edda’s row is complete without an order. Nor does a foreign key from lines to orders prove that every order has a line. If an empty order must be forbidden at checkout, that is an additional rule about when the order becomes valid.

For a one-to-one relationship, the reference must also be unique. A row of optional details keyed by product_id, for example, can belong to only one product, and each product can have at most one such row. That still permits a product without details. “At most one” and “must have one” need separate decisions. The subtype example later uses this distinction.

Many-to-many relationships

One order can contain several products, and one product can occur on many orders. This is a many-to-many relationship. The order line gives each occurrence a row carrying both references.

Its quantity and agreed unit price describe that occurrence. They belong neither to the product alone, which can sell in different quantities and at different prices, nor to the order alone, which has several lines. A row that connects two things can carry facts of its own.

Some connecting tables represent a unique pair, such as “P7 has the tag ceramic”. Their two references can be the key. Others represent repeatable occurrences, as numbered lines do. A diagram showing two boxes connected through a third does not choose between them. Read the row’s sentence and decide whether the same pair can happen again.

Functional dependencies

A functional dependency states that whenever two rows agree on some columns, they must agree on another. Write customer_id → name and read it as “customer ID determines the customer’s current name”. The arrow is a rule for every permitted table state. It is not a correlation found in the sample.

For example, only Mina has two orders here, but nothing says a customer determines one order ID. Edda may place her first order, and Tariq his second. In contrast, an order ID does determine its customer ID: one order cannot belong to two customers under the shop’s rules.

Flatten the shop into one row per order line, copying the order date, customer’s current name and product’s current name into every row. Several dependencies now overlap inside that table:

Two lines of order 103 must carry the same order date. All four lines across Mina’s orders must carry the same current customer name. Those agreements are work the flattened design creates.

Update, insertion and deletion anomalies

Suppose Mina asks the shop to correct her name. In the flattened table, four rows must change. Miss one and the database now gives two current names for customer 1. This is an update anomaly: one fact has several stored copies that can disagree.

Now add a new product that nobody has ordered. A table whose rows must identify an order line has nowhere to put it. Inventing a line to hold the product, or leaving the line’s identity empty, changes what a row means. This is an insertion anomaly.

Finally, remove the teapot line from the flattened data. It is the only line for P9 in the core orders. If this table is also the only record of products, removing a sale line removes the shop’s knowledge that the teapot exists. This is a deletion anomaly. The product and the sale have different lifetimes but have been made to share a row.

Give customers and products their own tables and all three problems change shape. Mina’s current name changes in one row. A product can be recorded before its first sale. Removing a line leaves the product row intact. Repeated customer and product IDs remain in the referencing rows, because those repetitions express different associations. It is the repeated description of one fact, rather than repeated values of any kind, that caused the disagreement.

Normalisation

Normalisation uses dependencies to find these problems and separate facts into suitable tables. Its normal forms name particular conditions a table satisfies. They are useful diagnoses: a design can satisfy one and still express the wrong business rule, omit payments or confuse a current price with an agreed price.

Figure 3 starts with the flattened lines. Step through the split and watch which references remain when the descriptions move. Each step gives another fact a home of its own. These are teaching steps, not one formal normal form per screen.

The last screen has more tables but fewer places to correct the same fact. Orders own their dates and customer references; customers own current customer names; products own current product names. A line retains its order, number, product, quantity and agreed price. The references let a reader put those facts together again.

Repeating groups and first normal form

Before that split, a more basic design could have put product_1, quantity_1, product_2 and quantity_2 on each order. The third line then needs new columns. Finding every order containing P7 means checking every numbered product column. The schema has mistaken positions in a growing list for different kinds of fact.

Encoding P7:1,P3:2 in one text field removes the fixed limit, but a line can no longer be addressed without interpreting the string. Its product reference and quantity rule are hidden inside that encoding. Separate line rows give every occurrence the same columns and a key.

First normal form, 1NF, treats each attribute as a single value of its domain rather than a repeating group of rows. What counts as one value depends on its intended operations: an entire description can be text while an order’s independently identified lines deserve rows. It is not a rule that every string must be split into words, or that a database must never contain JSON. Values develops the choice of domain and the treatment of missing data.

Partial dependencies and second normal form

In the flattened line table, placed_at depends on order_id alone, a proper part of the candidate key (order_id, line_no). This is a partial dependency. Quantity needs the whole pair; the order date does not. Moving the date to orders removes its repetition across lines.

Second normal form, 2NF, requires 1NF and no dependency of a non-key attribute on only part of a candidate key. Here “non-key” means not belonging to any candidate key. Check all candidate keys, not just the one labelled primary.

Adding a single-column line_id cannot do this work for you. The pair (order_id, line_no) still identifies a line and the order date still repeats. If you also remove that pair’s uniqueness rule, you have weakened the model rather than explained why two rows may call themselves the same line.

Transitive dependencies and third normal form

Putting the customer’s current name on orders would remove repetition within one order but leave it across Mina’s orders. The dependency runs through another fact: order_id → customer_id → current_name. This is a transitive dependency. Keeping the name with the customer removes the repeated end of that chain.

Third normal form, 3NF, rules out these dependencies on non-keys, with an exception for attributes that belong to candidate keys. More precisely, for each non-trivial dependency X → A, either X is a superkey or A belongs to a candidate key. “Non-trivial” means A is not already part of X. The shop’s current customer name meets neither exception in orders, so it belongs elsewhere.

Boyce–Codd normal form, BCNF, uses the stronger rule that every non-trivial determinant must be a superkey. A determinant is the left side of the arrow. The distinction matters with overlapping candidate keys; it does not change this shop repair. Normal-form names help locate a dependency to examine. They do not establish whether “current customer name” was the fact the receipt needed in the first place.

Decomposing tables safely

Separating a table is a decomposition. It must preserve the associations the original table recorded. Keeping every column somewhere is not enough: you must still know which values occurred together.

Consider the first split in Figure 3. There is one order 103 row, with its date and customer, and two lines carrying order_id = 103. Matching each line to that one order restores its order facts. No line can pick up a second date from another order 103, because the order key rules that second row out.

This is a lossless split. For the original line facts, joining the pieces gives exactly the original associations. The reason is the order ID’s declared meaning and uniqueness, not merely that the five sample rows happen to reconstruct correctly. The separated tables can also hold things that the old line table could not, such as a product with no sales.

Relationships involving three things

A supplier example shows an unsafe split. Suppose North offers P3 to the Town location and P7 to Station, while Harbour offers P3 to Station. An offer therefore involves a supplier, a product and a location together. These are hypothetical catalogue facts, separate from the orders.

Replace the offer table with three lists—supplier–product, supplier–location and product–location—and every ID survives. Figure 4 tests the offer “North, P3, Station”. Check the three pairs, then look for the complete offer in the original table.

North supplies P3, North supplies Station, and P3 is supplied to Station. All three statements are true. They do not say North offers P3 to Station: the first comes from Town’s offer, and the last from Harbour’s. Rejoining the pairs invents a fourth offer.

Keep (supplier_id, product_id, location_id) together in offers. Under a rule allowing one current offer per triple, that triple can be its key; an offered price would describe the triple. If offers can recur or have versions, their identity needs that extra distinction. Giving each offer an ID and references to all three things is another representation of the complete fact. Keeping only the three pair lists is what lost it.

Dependency preservation

Losslessness asks whether the information comes back. A second question is whether the pieces let you check the original dependencies separately, called dependency preservation.

Consider just the order, customer and current customer name from the flattened lines. Split these columns into (order_id, customer_id) and (order_id, current_name), with one row per order in each. Order ID would reconstruct the customer and name without extra combinations. But customer 1’s name could differ between orders 101 and 103, and neither table alone would reveal it. To check “one current name per customer”, you would have to put the pieces together.

The customers(customer_id, name) table gives that dependency a direct home. Some more complicated dependencies force a trade between BCNF and checks confined to individual tables. The planned deeper article Normalisation and decomposition will develop candidate-key derivation, formal lossless and dependency-preservation tests, and the higher normal forms. The practical test here is already useful: reconstruct the facts, then locate each rule in the resulting tables.

Independent multivalued facts

Not all troublesome repetition comes from a value being determined by a smaller key. Suppose P7 has the tags gift and ceramic, and both North and Harbour supply it. For this separate hypothetical example, tags describe the product independently of its suppliers. There is no fact “North supplies the gift version”.

A table of product, tag and supplier would need every pairing to represent both complete sets. Figure 5 puts the four combinations beside the two sets they came from.

In the combined table, no product determines a single tag or a single supplier. With no further rules, all three columns form the candidate key, and the table can satisfy BCNF. Yet removing just one pairing makes the sets ambiguous: did the product lose a tag, lose a supplier, or gain a restriction tying them together?

A multivalued dependency describes the independence that requires those combinations. Fourth normal form, 4NF, addresses the repetition it creates. Here the useful repair is two tables, keyed by (product_id, tag) and (product_id, supplier_id). Do not apply that repair to the offer table: its location and supplier are part of the same fact, as Figure 4 showed. Independence is a business assumption to establish, not something the column count can tell you.

Historical facts and derived data

Normalisation depends on what a column means. Two columns holding 20.00 may describe the same fact twice, or two different facts that happen to agree. Prices show why the distinction has to come before a decision to remove a copy.

Current price and agreed price

products.price is the shop’s current catalogue price. order_items.unit_price is the price agreed for that line. Both are 20.00 for P7 when order 103 is placed. Suppose the catalogue price later rises to 22.00. Watch which value changes in Figure 6.

The product ID determines the current catalogue price. It does not determine the agreed price across all lines and all sales. The line key determines that. Keeping an agreed price is therefore not the same redundancy as copying the current catalogue price onto every line.

The same question applies to names and addresses. If an invoice must reproduce the name used at purchase, following a customer reference to today’s name does not meet that requirement. A purchase-time name is another explicitly defined fact. Do not silently change every “current name” column in the earlier example into a historical snapshot; that changes the dependencies being analysed. History and correction develops how to retain versions, effective dates and corrections.

Totals, caches and denormalisation

Order 103’s line total, by contrast, is calculated from existing facts: 1 × 20.00 + 2 × 4.50 = 29.00. In this example there are no taxes, delivery charges or discounts outside the agreed line prices. The lines are sufficient to derive that total.

Storing orders.total = 29.00 as well creates a copy of the calculation. If a pending line’s quantity changes, the stored total can disagree with its source. Keeping the copy may save repeated work, but it also creates maintenance work. This is a common form of denormalisation: deliberately retaining redundant data for a useful access pattern.

Before accepting it, define the authority and the repair. If the lines are authoritative, which changes refresh the total? Must the refresh commit with the line change, or may a display lag? How is a stale value detected, and how is every total rebuilt from the lines? A checkout amount that must agree immediately needs a different maintenance rule from an approximate dashboard.

Measure the saving before taking on that obligation. The extra join or calculation may already be cheap, or an index may remove the expensive part. Indexes follows the reads that make a query expensive; Transactions covers changes that must stay together. If a legally or commercially agreed final amount is authoritative in its own right, name that fact explicitly rather than treating it as a disposable cache of this simple line sum.

Modelling variations in the data

The shop’s orders share one shape, but not everything in its catalogue does. A tea’s brewing instructions do not describe a teapot. Categories can contain other categories. These cases still start with the same questions: what does a row assert, which key identifies it, and which facts depend on that identity?

Shared attributes and subtypes

Suppose tea products have a recommended brewing temperature, while teaware has a material. One products table could contain both columns, with a product type saying which applies. P3 might have a temperature of 80 °C and no material; P7 might have material ceramic and no brewing temperature. Those are optional descriptive extensions, not changes to their sale prices.

This is manageable with a few stable types and a few attributes. The model must distinguish “not applicable to this type” from “applicable but unknown”, and rules must prevent a mug accidentally receiving a tea-only value. As the number of unrelated type-specific fields grows, reading a product row increasingly means knowing which columns to ignore.

An alternative keeps the shared identity in products and puts (product_id, brewing_temperature) in tea_details, and (product_id, material) in teaware_details. In each detail table, product_id is both its key and a reference to products. Order lines still refer to the common product table, so a sale does not need a different kind of reference for each type.

These detail tables are subtypes. Decide whether they may overlap and whether they cover every product. For this illustration, tea and teaware are disjoint, and every product must be one of the two. Two separate detail tables do not themselves enforce either promise: a product could otherwise have both rows or neither. The benefit is that each subtype’s attributes have an appropriate home; the cost is joining to details and enforcing the coverage rule across tables. A modest single-table model may be the better choice when it expresses those rules more simply.

Recursive relationships

A category can refer to another category in the same table. For a tree, use categories(category_id, name, parent_id), with parent_id referring to category_id and empty for a root. This is an adjacency list: each row records its immediate parent.

In a hypothetical catalogue, Mugs can sit under Drinkware, which sits under Tea things. Each category has at most one parent. To move Mugs under Gifts, change Mugs’ parent; descendants do not need new identities. That is a structural benefit, even though finding all descendants now requires following several references.

If Mugs must appear under both Drinkware and Gifts, a single parent column cannot express it. Use a separate category_edges(parent_id, child_id) table with one row per direct connection. The pair is its key. A category can then have several parents, and two routes can lead to the same descendant.

Neither representation is automatically a tree or even acyclic. Mugs could point to Drinkware while Drinkware points back to Mugs; both targets exist. Cycle prevention is an additional rule. Recursive query cycle detection can make a traversal stop, but does not prevent such data from being stored. The planned article Modelling hierarchies will compare adjacency lists, edge tables, paths, closure tables and nested sets, including traversal and reparenting. Choose the parent-count and cycle rules before choosing an optimisation for walking them.

Tables, JSON and entity–attribute–value models

A product may also carry a small description document whose fields vary: tasting notes, care text or presentation hints. JSON can keep such a document together while product identity, price and stock remain ordinary columns. A predictable document shape is still useful, even where every product need not have the same descriptive fields.

The boundary changes if order lines become a JSON list inside an order. The application still needs line identity, quantities and valid product references. A normal foreign key on a product column no longer states the rule for each embedded item. Those checks need another representation or additional machinery. JSON has not removed the relationship; it has moved it into a value that the model must interpret.

An entity–attribute–value model, EAV, goes further: rows such as (P7, 'material', 'ceramic') store an attribute name as data. A new attribute then needs a row rather than a new column. That flexibility is useful when users genuinely define open-ended attributes. It also means “material applies only to teaware”, “temperature is numeric” and “this attribute occurs once” no longer follow from a dedicated column’s declaration. They need metadata and rules of their own.

Do not pay that cost just to avoid an occasional schema change. Stable facts used in joins, calculations and integrity rules benefit from visible columns and references. Variable descriptive material may benefit from a document. Judge the boundary by the operations and guarantees each fact needs, rather than trying to fit the whole catalogue into one storage style.

Assessing a schema

A schema can draw neatly and still fail its first awkward change. Walk concrete cases through it before implementing it. Start with the rows the shop must be able to create independently, then try changes that cross the distinctions its keys and relationships make.

Read the shop model through its changes
Try thisWhere the fact belongsWhat to check
Register a customer before any purchaseOne customers row; Edda is the existing exampleNo invented order is needed
Add a product before its first saleOne products rowNo invented line is needed
Put the same product on a second lineA new (order_id, line_no)The key preserves occurrences; decide any additional restrictions
Pay an order partly by card and partly by gift cardTwo payments rows referring to the orderNo second copy of its lines; order 101 already does this
Correct a customer’s current nameOne customer rowCurrent displays follow the reference; historical wording needs a separately defined fact
Remove a lineThe line rowThe product survives; order totals and the rule about an empty order need attention

Read the model in the other direction too. Can you list Mina’s orders, find the products on one order, and distinguish an order with no payment from a customer with no order? To calculate what remains due, the order’s lines supply its value and its payments supply what has been received. These questions expose missing associations without requiring a stored row shaped exactly like each report.

Then separate what the structure can express from what has actually been enforced. The line key can distinguish repeated products; a uniqueness declaration must protect it. A foreign key can require an existing order; it does not require a non-empty one. Separate payment rows permit split payment; they do not prove the sum paid is within the amount due. A model that makes a rule legible is the starting point for choosing its enforcement.

When a design is hard to assess, write one row’s meaning again and try the change that makes it uncomfortable. A customer without an order, a product appearing twice, a later price or a third participant often reveals the missing distinction. Repair that distinction first. The number of tables follows from the facts you need to preserve.

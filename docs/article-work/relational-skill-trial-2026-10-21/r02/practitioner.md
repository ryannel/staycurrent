## Findings

### practitioner-15 · required · a00, "Changing a live database": stage 1 row of the staged table, and the paragraph beginning "Stages 1 and 5 each take PostgreSQL's strongest table lock"

Problem: The article says stage 1 succeeded "holding a lock on the whole table for a moment" and that adding a nullable column "holds it only briefly". That describes how long the lock is held, not how long the statement and everyone behind it wait. ACCESS EXCLUSIVE must first wait for every open transaction that has touched `orders`, including a long report, and while it waits every new read and write of `orders` queues behind it. Reproduced on PostgreSQL 18.6 against the scaled shop: a report held `SELECT count(*) FROM orders` open in a transaction for 4 s; `ALTER TABLE orders ADD COLUMN delivery_country text` then waited about 3.5 s (wait event `Lock/relation`), and a checkout read of order 103 issued after it waited about 3 s in the same queue (`pg_stat_activity` showed all three). The a00 sources record that a plain SELECT waited, but only while the ALTER held the lock inside an open transaction.
Effect: A reader who stops at the parent, as its brief allows, takes away that the "expand" step is harmless and can stall checkout in production behind any long-running query. This is the most common way a "safe" migration causes an outage.
Suggestion: Say that the brief lock must first be acquired, that it waits behind running transactions and blocks everything queued after it, and that the change should therefore run with a short `lock_timeout` and be retried (the a06 and a29 drafts already teach this). If space allows, note in the same place that PostgreSQL 18 can add a not-null constraint `NOT VALID` and validate it under a weaker SHARE UPDATE EXCLUSIVE lock (ALTER TABLE reference), so the stage-5 scan need not block reads. Both can be one or two sentences that point to the child.

### practitioner-16 · required · a03, "Choosing a protection" table (last row) and "Rules that span several rows"

Problem: The table recommends "a shared row that every writer locks before reading" for multi-row rules without saying it depends on the isolation level. The protocol works only because, at Read Committed, the count after the lock is a new statement with a new snapshot. At PostgreSQL Repeatable Read the snapshot is taken by the `SELECT … FOR UPDATE` itself, before the wait, and a lock on a row that was not changed raises no 40001. Reproduced on PostgreSQL 18.6 with the article's rows: Lena and Ravi each ran `BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT class_id FROM classes WHERE class_id = 21 FOR UPDATE;`. Ravi's lock waited for Lena's commit, his count then still returned 2, both updates committed, and class 21 was left with no available instructor, with no error. The article tells the reader the conditional-update listing depends on Read Committed and must not be carried across. It gives the guard row no such warning, although Figure 3's caption and a code comment mention Read Committed in passing. The Serializable section's "every transaction that can affect the rule must run at Serializable" may also suggest that a stricter level is always safer. The child a18 does warn about this ("Do not carry the recipe unchanged to Repeatable Read"), but the parent is where the reader chooses.
Effect: A team whose connections run at Repeatable Read (a framework or pool default, or a reader who raised the level "to be safe") adopts the guard row and keeps the write skew it was meant to remove, with no error to reveal it.
Suggestion: Make the condition explicit wherever the guard row is offered. For example, state the assumption in the table cell or in the paragraph after Lena's listing: at PostgreSQL Repeatable Read the count must not rely on the lock, so either run the protocol at Read Committed or make the guard an actual write (for example an UPDATE of the class row), which then fails with 40001 and must be retried as a whole.

### practitioner-17 · optional · a00, "From a request to a committed order": the paragraph after Figure 5 beginning "If the order is not there"

Problem: The parent works through the in-flight first attempt, why the transaction inserts order 103 first, how a repeat then waits and fails with 23505, and why a claim-first repeat would wrongly report "sold out". This is the same lesson, with the same structure, as a03's Figure 5 and its two paragraphs, and a22 owns reconciliation. The a00 plan asks only for "the difference between a database error and an unknown outcome" and why deadlines, retries and external effects must be designed together. The claims are correct: I reproduced the in-flight case with a COMMIT held by a synchronous standby that never connects. The lookup found nothing, the keyed repeat waited, and after the session was ended it failed with 23505.
Effect: A newcomer gets protocol depth at the point where the parent should hand over, and the collection now teaches the same mechanism twice in two different examples.
Suggestion: Keep Figure 5 and the conclusion: a missing row proves only that nothing has committed yet, so the repeat must be designed to meet the first attempt through the order's identity. Then link to a03's lost-reply section for the mechanism and to a04/a22 for the procedure.

### practitioner-18 · optional · a03, "A lost reply to COMMIT" and "Retrying a transaction"

Problem: The article bounds the repeat's wait with `lock_timeout` but does not say what happens to the first attempt itself. If the client vanishes without the server noticing, as in the "held" option, the first attempt stays "idle in transaction" while it holds class 21's row lock. Every other booking for class 21 then waits too, not just the repeat, until TCP keepalives or a server timeout end the session. In PostgreSQL 18, `idle_in_transaction_session_timeout` and `transaction_timeout` both default to 0 (disabled). I confirmed this with `postgres --describe-config`. The plan's "bounded transaction duration" is taught only as client discipline ("keep transactions short").
Effect: A practitioner who applies the lock-timeout advice still has an open transaction that can block a popular class indefinitely, and does not know which server setting ends it.
Suggestion: Add a sentence that an abandoned open transaction blocks everyone who needs its rows, and that the server can bound it with `idle_in_transaction_session_timeout` or `transaction_timeout`. Add the resulting error to the outcomes table if wanted, and link to a20 for the policy. A sentence is enough.

### practitioner-19 · optional · a00, "Transactions and competing buyers", paragraph on isolation

Problem: "Under PostgreSQL's Repeatable Read, Tariq's write would be refused … because Mina changed the row after his transaction began." PostgreSQL takes the snapshot at the transaction's first statement, not at BEGIN. a03 ("taken at its first statement") and a19 ("BEGIN alone had not fixed the data snapshot") both say so. In Figure 4's schedule the result is the same, because Tariq reads before Mina writes.
Effect: The parent states a slightly wrong rule that its children then contradict. A reader who reasons from BEGIN time would mispredict a transaction whose first query comes late.
Suggestion: Say "after his transaction took its snapshot, at its first statement", or "after he read it".

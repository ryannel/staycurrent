# Sequence diagrams: rebuild, 16 October 2026

The article at `/learn/drawing-systems/sequences/` was rebuilt as a house reference
from the brief of 16 October 2026. The text and all nine animations are new.

## Hosting

The article is now an Astro page, `src/pages/learn/drawing-systems/sequences.astro`,
not Markdown. That lets it hold components without adding `@astrojs/mdx`, which would
have changed shared config while other articles were being rebuilt in parallel.
`src/articles/drawing-systems/sequences.md` was removed, so the `[...article].astro`
glob no longer generates this route. The page passes its own heading list to
`DrawingArticle.astro`, so the collection switcher, contents list and previous/next
links still work. The six static SVG figures the old article used were deleted from
`public/images/drawing-systems/`. No other page linked to them or to the old
article's heading anchors.

## Running model

The collection's invented repair service, unchanged in its parts: Browser, Repair API,
Repair DB (PostgreSQL), notification worker and email provider. Mina books a
dishwasher repair and gets R17; the notification job is J9. The timeout and retry
animations add Mina's inbox as a lifeline the worker cannot see.

## Animations

One component, `SequencePlayer.astro`, renders every animation from scenarios in
`sequence-model.ts`. Each has play/pause, step back, step forward, a scrubber with a
tick per message (arrow keys jump between ticks) and reset.

| # | Scenario | Job | Parameter |
| --- | --- | --- | --- |
| 1 | `booking` | Messages arrive in order down the lifelines; the API can't reply before the DB | none |
| 2 | `waiting` | Activation bars and who is blocked; the clock changes but the drawing doesn't | Repair DB time: 5 ms to 3 s |
| 3 | `email` | Synchronous vs asynchronous: who waits, and a reply nobody is waiting for | Waits / doesn't wait |
| 4 | `outbox` | Booking and job in one transaction; browser done before the worker starts | Provider down |
| 5 | `timeout` | Three histories look identical from the worker's lifeline | Request lost / reply lost / slow |
| 6 | `retry` | A retry after a lost reply duplicates the email; an idempotency key prevents it | First attempt; key on/off |
| 7 | `fragments` | alt runs one section, opt may be skipped; untaken paths stay drawn, faded | Details valid; new customer |
| 8 | `loop` | One drawn loop runs several passes; pass counter and clock | Pass on which status is scheduled |
| 9 | `par` | Both requests leave before either reply; either reply order is allowed | Which reply arrives first |

Design notes:

- Rows are order, not time. A scenario clock (ms) is shown separately where it matters.
- State is carried by line style and text as well as colour: solid/filled = call,
  dotted/open = reply, solid/open = asynchronous, dot = lost; hatched bar = waiting,
  solid bar = handling. A status line under each name says waiting/working/idle with
  the elapsed time. Wait bars darken as the wait grows.
- The server renders the finished diagram, so it reads without JavaScript. With
  JavaScript the SVG is rebuilt at the container's pixel width, so labels stay at
  11.5–13 px on a 375 px phone. Long participant names wrap; "Notification worker"
  shortens to "Worker" when it can't fit.
- Each figure has a visually hidden summary (the SVG's label), a live step line, and
  a "Messages in order, as text" list that updates with the parameters.
- Reduced motion: the figure starts showing the finished diagram, never autoplays,
  and Play steps through messages about once a second without tweening. Otherwise
  each animation plays once when half of it scrolls into view.
- Colours are defined as `--seq-*` tokens on `seq-player`, with dark values under
  `:root[data-theme="dark"]` and a `prefers-color-scheme` fallback for no-JS.
- Mermaid draws one kind of activation bar. The hatched waiting bar is this
  article's addition, and the text says so.

Checked in the browser at desktop width and at 375 px, in light and dark themes, with
no horizontal page scroll. All nine Mermaid sources were rendered with Mermaid 11.4.1
without errors, which also confirmed that Mermaid adds the brackets around guards.

## Independent review

One reviewer subagent read the brief, the page and the scenario code. It found that
the asynchronous animation's clock read about 108 ms where the prose said 70 ms (the
one-way send was charged 40 ms; now 1 ms), and that "two workers never take the same
row" overstated `SKIP LOCKED`. It also flagged a maxim, an aphorism, hearsay ("many
teams"), a second-sentence term definition and the missing cost of idempotency keys
(the provider forgets them after 24 hours). All were repaired. Stepping now stops
just before the next event starts, so each step's text, bars and status line agree.

## Second review (coordinator)

Applied: `alt` runs at most one section (exactly one with `else`); `SKIP LOCKED`
now explained as skipping rather than waiting, with `FOR UPDATE` doing the locking;
loop guard changed to `[status not scheduled]` to match "while its guard holds";
timeout section introduces the slow-provider case and says how to set a timeout
(`AbortSignal.timeout`, or an undici dispatcher); idempotency names Stripe's "at
least 24 hours" and the rejection of a reused key with a different body, and drops the
255-character figure; the slow case's late reply is now an ordinary reply reaching a
lifeline with no bar; "Replies and activation bars" opens with the term; "receipt"
replaced with `201 Created` or R17. The overview's "two possible histories" sentence
was updated to the three cases, with the coordinator's approval.

## Sources checked

- Mermaid sequence diagram syntax (arrows `->>`, `-->>`, `-)`, `-x`; `+`/`-`
  activation shorthand; `alt`, `opt`, `loop`, `par`, `critical`, `break`, `rect`;
  `autonumber`): https://mermaid.js.org/syntax/sequenceDiagram.html (docs source on GitHub).
- UML 2.5 message notation (filled arrowhead synchronous, open arrowhead
  asynchronous, dashed reply, lost message ending in a small filled circle,
  ExecutionSpecification). The OMG PDF was too large to fetch, so this relies on the
  PlantUML documentation, which cites UML 2.5 section 17.4.4.1, and on Sparx and
  IBM's tool references.
- Transactional outbox and duplicate publishing:
  https://microservices.io/patterns/data/transactional-outbox.html
- `SKIP LOCKED` quote: https://www.postgresql.org/docs/current/sql-select.html
- Resend idempotency keys, kept 24 hours:
  https://resend.com/docs/dashboard/emails/idempotency-keys
- Stripe idempotency keys, kept at least 24 hours; a reused key with different parameters errors:
  https://docs.stripe.com/api/idempotent_requests
- undici `headersTimeout` and `bodyTimeout` default `300e3` ms:
  https://github.com/nodejs/undici/blob/main/docs/docs/api/Client.md
- Node.js `fetch` is based on undici, and `AbortSignal.timeout(delay)`:
  https://nodejs.org/api/globals.html
- AWS Builders' Library, timeouts, retries and backoff with jitter:
  https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/

Invented figures, labelled as invented or plainly scenario values: provider takes
2.5 s, worker polls about once a second, 10 s timeout, 2 s retry wait, 30 s retry
delay, 2 s status polling, 14 s slow provider.

# Indexes rewrite, 16 October 2026

The article at `/learn/databases/relational/indexes/` was rebuilt from the
brief in the orchestrator's scratchpad (`reading/brief.md`). The aim is a
house reference for an engineer who skims for terms: each section names its
term first, gives a short example, and anchors on an animation.

## Running model

Two scales, kept distinct and labelled in the article.

- **Figures:** an invented `orders` table of 36 rows, six per heap page,
  defined in `src/components/explainers/indexes/model.ts`. Sixteen customers;
  customer 42 has four orders, on pages 0, 1, 3 and 5. Each order has a date
  (1 Jan to 5 Feb) and a total. Every figure draws from this one model, so the
  reader sees the same rows from the scan in figure 1 to the writes in
  figure 8.
- **Measurements:** the generated temporary table `index_orders` from
  `setup.sql`, with 60,000 orders for 1,000 customers. Customer 42 has 60
  orders. The history query asks for customer 42's ten newest orders since
  1 February.

## Animations and their jobs

All eight share one engine (`player.ts`, `scene.ts`, `IndexFigure.astro`,
`indexes.css`): play/pause, back, next, reset, a step counter, arrow keys,
a live status line, autoplay once when scrolled into view (never under
reduced motion), a `<noscript>` text alternative, site colour tokens for light
and dark, and a stacked layout below 600px.

1. **ScanFigure:** a sequential scan tests every row of every page. Job:
   show that the cost follows the table, not the answer.
2. **BuildFigure:** entries copy out of the heap in table order, sort, and
   customer 42's four entries end up adjacent, with pointers back to four
   pages. Job: show what an index contains and why sorting helps.
3. **DescentFigure:** a sideways B-tree; root, branch, leaf, then table rows.
   Parameter: which customer to find. Job: one page per level, whatever the
   key.
4. **RangeFigure:** one descent, then a walk along leaves and across the
   sibling link, stopping past the upper bound. Parameters: lower and upper
   bound. Job: range scans and free ordering.
5. **SelectivityFigure:** widen `customer_id <= k` one customer at a time;
   bars compare index scan, bitmap heap scan and sequential scan page visits.
   Job: matches spread to every page early, and then the index stops paying.
6. **CompositeFigure:** the same entries re-sort as the index changes between
   `(customer_id)`, `(customer_id, placed_at DESC)` and
   `(placed_at DESC, customer_id)`. Job: column order decides which entries
   sit together and when the scan can stop.
7. **CoveringFigure:** one leaf page beside the table, with visibility-map
   boxes. Switches: `INCLUDE (total)` and "table vacuumed". Job: an index-only
   scan needs both the columns and the visibility bits.
8. **WriteFigure:** an insert or an update passes through the table and up to
   four indexes, with a leaf split and a HOT update. Parameters: statement and
   number of indexes. Job: the write cost of each extra index.

## Uncertainties

- PGlite is a 32-bit WebAssembly build. Page counts on a 64-bit server may
  differ slightly; the article says so.
- The selectivity threshold (bitmap heap scan up to `customer_id <= 500`,
  sequential scan from 550) does not depend on the generator's layout. A
  shuffled copy of the table switches at the same point; the planner's
  correlation statistic is near zero in both. The switch comes from the cost
  estimates, which ANALYZE's sampling moves slightly between runs, so the
  article quotes only their order and the flat 2,475 sequential estimate.
- The HOT measurement used `fillfactor = 90`; with the default 100, none of
  the 600 updates was HOT because freshly loaded pages had no room. Both are
  reported.
- The WAL figures (3.3 MB with the primary key, 7.7 MB with four more
  indexes, for 10,000 inserts) follow a checkpoint, so they include full-page
  images. Absolute values vary with checkpoint timing; the ratio is the point.
- The fill levels in WriteFigure are invented. The split happens in
  orders_history, whose keys are distinct, and writes 4 pages: the old leaf,
  the new leaf, the right sibling's link and the branch page above.
- The figures draw one entry per row, although PostgreSQL deduplicates
  repeated keys into posting lists. The B-tree section names posting lists in
  one sentence.
- `pg_stat_user_indexes` counts stayed at zero in PGlite, so the usage query
  is run but its output is not recorded.
- The reversed-index row (about 11,000 entries read) is derived from the scan
  starting at order 60000 and stopping at 49041; the plan's own row count is
  smaller because the scan checks customer 42 inside the index. The reversed
  index is now part of experiment.sql.

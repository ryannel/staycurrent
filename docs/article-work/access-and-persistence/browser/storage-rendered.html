Storage and durability

A relational database presents tables, rows and columns. Behind that view, it must arrange bytes so it can find a row, change it while other people are reading, and remember the change after a restart. These jobs meet at a deceptively small event: the database tells an application that its transaction committed.

What has actually reached storage when that reply arrives? It need not be the changed table page. A database can preserve enough information to reconstruct the change before it finishes writing the table itself. Understanding that distinction explains both how commits can be efficient and why recovering from a crash is different from recovering a lost database.

We’ll follow ordinary, logged tables in PostgreSQL 18, on one server with reliable persistent storage. The page layout and version cleanup belong to that engine. SQL’s relational model does not prescribe them.

Rows and pages

Suppose a shop’s products table contains P7, a blue mug whose current price is 20.00. A product-page request sends this query to PostgreSQL:

SELECT current_price
FROM products
WHERE product_id = 'P7';

The table is stored in a collection of fixed-size pages, usually 8 kB each. A page contains row versions, a header, locations for finding those versions within the page, and unused space. The stored row includes bookkeeping alongside its column values. Three columns in SQL therefore do not become just three values on disk. PostgreSQL’s page layout describes these parts.

Our small rows fit their values together on a page. Larger values can be compressed or moved into separate storage by PostgreSQL’s TOAST mechanism. Reading a short product ID and reading its long description can consequently require different amounts of physical work, even though both are columns of one logical row.

Nothing about P7’s identity means it occupies page 7 or sits between P6 and P8. An ordinary PostgreSQL table is a heap: its arrangement does not maintain a chosen key order. An index provides a separate way to locate records; the table and its indexes have their own storage. The indexes article follows that search. Here we’ll begin once the engine has located P7 on an illustrative page 12.

PostgreSQL works on the page in its shared buffers, a cache in server memory. If page 12 is already there, the reader can reuse it. Otherwise the engine reads it from the table file. That read might be satisfied by the operating system’s cache, so a PostgreSQL buffer miss does not by itself establish that a physical drive was accessed. PostgreSQL uses both its own buffers and the operating system’s caching; the memory configuration documentation describes their relationship.

This gives physical arrangement a consequence the query does not reveal. Fetching one price can bring neighbouring rows into memory too. A second request for another product on the same page may reuse that work. Conversely, a query returning a handful of scattered rows may need several pages. Counting returned rows alone misses that difference.

SQL also works over column-oriented storage, where grouping values from the same column changes what a wide scan can leave unread. Tables describe the information we query; storage layout decides how the engine brings that information to the processor.

Changing a buffered page

A staff member changes the blue mug’s price to 22.00. The shop’s update handler borrows one database connection, sends BEGIN, sends the update, and checks that it succeeded for P7 before sending COMMIT. These are the statements on that successful path, all on the same connection:

BEGIN;
UPDATE products
SET current_price = 22.00
WHERE product_id = 'P7';
COMMIT;

In PostgreSQL, this update creates a new row version. The earlier version still contains 20.00; the new one contains 22.00. Transaction information lets the engine decide which version a reader can see. An ordinary query from another connection cannot see the unfinished price change. A report with an older snapshot may continue to see 20.00 even after the writer commits. This is multiversion concurrency control, developed further in Isolation and snapshots.

The new version may fit on the same page or need another page. PostgreSQL can sometimes avoid creating new ordinary index entries when the changed columns and available space allow a heap-only tuple update. Either way, setting one value can involve more work than overwriting the bytes for a price.

Changed buffer pages are called dirty: their in-memory contents have changes that need writing back. They may contain work from transactions that have not committed. They can also contain committed work that has not yet reached the table file. “Dirty,” “committed,” and “visible to this query” describe different things.

That last distinction matters if the server fails. Memory can vanish while a table file still contains an earlier page. Writing every changed table and index page before acknowledging each transaction would preserve the work, but it would tie each commit to all of those writes. PostgreSQL uses a log to make a different promise.

The write-ahead log

As it changes pages, PostgreSQL generates write-ahead log records, or WAL. They describe changes the recovery machinery can redo. The log is a stream shared by transactions, stored separately from the table and index files. It is not a list of SQL queries to run again. Repeating “increase a price by two” would be quite different from restoring the page change produced by that statement.

The essential ordering rule is between durable writes: before a changed data page can be written out, the WAL describing its changes must have been flushed to persistent storage. The in-memory page can change earlier. PostgreSQL records a position in the log on each page so the buffer manager can enforce this rule. During replay, that position also helps it recognise changes already present. The transaction-system source notes explain the ordering.

Now consider the price change. PostgreSQL can flush its change records and commit record to WAL, then acknowledge the commit while page 12’s file still contains the earlier contents. If memory disappears immediately afterwards, the retained log supplies what the table file lacks. It can redo the work.

This is why WAL reduces the work a commit must wait for. It lets the engine append to the log and defer scattered data-page writes. Several transactions can share one log flush, and several changes to a buffered page can be written back together. The data pages still have to reach storage; the system has more freedom about when to write them.

A flush means more than handing bytes to an operating-system write call. There may be volatile caches between PostgreSQL and persistent media. The database requests the synchronisation needed to make the write survive a failure, and depends on the operating system and storage devices honouring it. PostgreSQL’s reliability documentation explains this chain. A device that reports success while leaving the only copy in memory breaks the assumption.

After a crash

At restart, the table files may contain a mixture of older pages and newer ones. Recovery reads the durable WAL and redoes the necessary changes. It does not replay only transactions that eventually committed: physical changes belonging to an unfinished transaction can also appear in the log and on data pages. Transaction status and row visibility prevent those changes from becoming committed query results. PostgreSQL’s heap replay and visibility code implement these separate jobs.

For our ordinary price-change transaction, if no commit record survives, a new query after recovery still sees 20.00. Bytes for a 22.00 version may exist, but its transaction did not commit. If its update and commit records survive, recovery can restore 22.00 even when the table page had not been written. PostgreSQL’s transaction guarantee concerns the complete committed change, rather than whether traces of unfinished work occupy storage.

Case C is awkward for the application. It sent COMMIT, then lost the connection. The database remembers 22.00, but the caller never learned that it succeeded. Losing a reply is therefore not evidence of a rollback. Handling conflicts and uncertain outcomes explains how an application can recover the original operation’s outcome without blindly repeating its effects.

A crash can also interrupt the writing of a page itself. The surviving page might contain a mixture of old and new pieces, rather than either complete version. With full_page_writes enabled, PostgreSQL includes a full image of a page in WAL on its first modification after a checkpoint. That gives recovery a complete image to restore when a partially written page cannot safely accept incremental changes. This protects against a torn write; it does not recreate a lost storage device. The setting’s documentation describes the protection.

Checkpoints

We would not want every restart to replay the database’s entire history. A checkpoint establishes a more recent place from which recovery can begin. PostgreSQL writes the required dirty pages and records the recovery starting position. Once the checkpoint completes, changes before that position are known to be reflected in the data files.

Transactions continue while the checkpoint is being written. Its work can be spread over time; it does not mean the whole database freezes into one instantaneous image. Recovery uses the checkpoint’s recorded redo position, then follows later WAL to bring the files forward. Older log segments can eventually be reused when they are no longer needed for recovery or retained for such purposes as archiving and replication. The checkpoint documentation describes this relationship.

Our acknowledged price change does not wait for the next checkpoint to become durable. WAL already preserves it. The checkpoint reduces the old work a future recovery must revisit. More frequent checkpoints can reduce that replay work while increasing write pressure and full-page-image logging. That is an operating tradeoff, not a stronger promise for each ordinary synchronous commit.

Why unchanged row counts can still take more space

After the price change, the shop still has one blue-mug product. Physically, it can have both the 20.00 and 22.00 versions. Repeated updates and deletions leave versions that queries eventually no longer need. A long-running snapshot can delay reaching that point: removing its old version would take away information the report is still allowed to read.

PostgreSQL’s vacuuming reclaims dead versions so the space can be reused. Autovacuum arranges routine cleanup, while page pruning can also recover space during normal work. A free space map helps later writes find pages with room. Cleanup is part of sustaining this storage design, even when the application’s number of current rows stays steady.

Reusable space inside a table is not the same as space returned to the filesystem. Ordinary VACUUM generally leaves the table’s allocated files in place, apart from opportunities to remove empty pages at the end. That can be useful: the next round of changes has somewhere to go. VACUUM FULL rewrites a compact copy, requiring extra temporary disk capacity and an exclusive table lock. Routine vacuuming explains why regularly reusing space is usually preferable to repeatedly shrinking and regrowing it.

Checkpoints and vacuuming consequently solve different problems. A checkpoint advances the recovery starting point. Vacuuming manages versions and their reusable space, along with other visibility and transaction-age maintenance. A checkpoint cannot make an old report stop needing its snapshot; vacuuming cannot replace the log needed to recover an unwritten committed change.

What the commit promise covers

Our crash histories assume fsync = on, full_page_writes = on, and synchronous_commit = on, with no configured synchronous standby. For an ordinary logged table, commit success then includes waiting for the required WAL to become durable locally. Server or operating-system failure, including a power loss, can be recovered when the necessary storage survives and honours those flush requests.

synchronous_commit = off changes when the reply is allowed. It can acknowledge before WAL is durable, so a crash can lose recent acknowledged transactions while still recovering a consistent database. Disabling fsync is more serious: it removes required write-synchronisation protection and a system crash can leave corruption. These are distinct choices, explained in Asynchronous Commit.

The table’s kind matters too. PostgreSQL’s UNLOGGED tables skip ordinary WAL protection for their data and are reset after a crash or unclean shutdown. They are useful only when that data can be discarded and rebuilt. The same COMMIT spelling does not turn their contents into a durable record. See the unlogged-table documentation.

Now destroy the storage containing both the table and its WAL. There is nothing local to replay. Or commit an accidental deletion: crash recovery will faithfully preserve the deletion too. Recovering either situation requires another suitable copy and a recovery process. A physical base backup plus an unbroken sequence of archived WAL can support restoring to a chosen later point, including a point before the mistake. Keeping only the active WAL directory is not that backup. PostgreSQL’s point-in-time recovery guide explains the required pieces.

When deciding whether a stored record is safe enough, ask which event it must survive. Restarting with intact storage, losing the storage, and undoing an accepted human mistake demand different evidence. A successful commit answers the first question under the stated configuration. The other two require preserving and testing a way back.

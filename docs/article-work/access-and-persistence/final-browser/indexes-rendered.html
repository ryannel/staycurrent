Indexes

Relational deep diveRelational introduction ↗Next: How a query runs →

A customer opens their order history. The shop has years of orders, but this screen needs only ten recent ones belonging to that customer. SQL can express that request in a few lines. The database still has to find the records.

It could read the whole orders table, keep the rows for this customer, discard the old ones, and put the remaining orders in date order. That works. It also repeats a great deal of work whenever someone opens their history. An index is an additional structure the database maintains so that queries can take a more direct route to data.

The useful question is what route this particular query needs. An index that finds a customer may still leave dates to check and results to sort. Another arrangement can put the desired records together, already in the order the screen needs. We’ll build up that arrangement, inspect the work it saves, and account for the extra work when orders change.

The concrete engine here is PostgreSQL 18. We’ll use its ordinary ordered index, a B-tree. The reasoning about grouping keys and avoiding unnecessary work applies more widely; the separate table storage, plan details and visibility checks described below are PostgreSQL’s implementation.

An index gives the query a route

Imagine keeping a separate list of customer IDs, each beside the location of an order. Sort the list by customer ID. Now all of customer 42’s entries are together, even if their orders arrived months apart and occupy different parts of the table. Once we find the first 42, we can follow the run of matching entries and use their locations to fetch the orders.

A long sorted list still needs a way to find that starting point. A B-tree adds a hierarchy above it. The database stores information in fixed-size chunks called pages. At the top of the tree, the root page divides keys into ranges and points towards smaller parts of the index. Each step excludes ranges that cannot contain the requested key. Eventually the search reaches a leaf page, where the entries point to table rows.

This is a wide tree: a page can point to many children. Adding more orders usually enlarges the bottom of the tree long before it adds another level to every search. We pay for navigating to the relevant part, then for reading its matching entries. A range query uses the same machinery: find the boundary and continue through the ordered leaves until the range ends. PostgreSQL’s B-tree structure describes these pages and links.

Finding an entry is only part of retrieving an order. In PostgreSQL, an ordinary index scan follows its reference into the table’s main storage, called the heap. That is where it can get fields the index does not contain and check that the row version belongs in this query’s view of the database. Nearby index entries can point to distant table pages. Keep those two kinds of work in mind: searching the index, and fetching the rows it identifies.

The visibility check matters when requests overlap. PostgreSQL can retain an earlier row version for a reader whose view predates an update, while newer requests see the changed version. An index entry locates a candidate; the engine must still check whether that version belongs in this query’s view. The storage article follows how those versions are created and eventually removed.

Give the route a useful order

Let’s put the order-history request into a running database. You are the developer, sending SQL from a query editor or psql to a PostgreSQL 18 session. Run the setup below once in a fresh session, then keep that session open as we change the indexes. It creates a temporary table that disappears on disconnect. All the commands in this article act on that table. The practice guide explains how to open a PostgreSQL database; use the separate setup here for this investigation.

We generate 60,000 invented orders for 1,000 customers. Each customer has 60 orders, spread through time. Order IDs increase by one each minute from 1 January; customers repeat in a cycle. Customer 42 has 15 orders on or after 1 February. The long delivery note makes a complete table row appreciably wider than a customer ID. These deliberately regular records let us check the work; they are not a model of a real shop’s traffic.

-- PostgreSQL 18. Run in a new session; the table disappears on disconnect.
-- No production table is read or modified.
SET TIME ZONE 'UTC';
CREATE TEMP TABLE index_orders (
  order_id integer PRIMARY KEY,
  customer_id integer NOT NULL,
  placed_at timestamptz NOT NULL,
  status text NOT NULL,
  total numeric(10,2) NOT NULL,
  note text NOT NULL
);
INSERT INTO index_orders
  (order_id, customer_id, placed_at, status, total, note)
SELECT n, 1 + n % 1000,
       timestamptz '2026-01-01 00:00:00+00' + n * interval '1 minute',
       CASE WHEN (n / 1000) % 5 = 0 THEN 'pending' ELSE 'paid' END,
       (1000 + n % 9000)::numeric / 100,
       repeat('delivery note ', 12)
FROM generate_series(1, 60000) AS series(n);
ANALYZE index_orders;

ANALYZE collects statistics that help PostgreSQL estimate how many rows a condition will match. The primary key already creates an index on order_id. That index is useful when we know an order ID. Our history request knows a customer and a date instead:

SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
  AND placed_at >= timestamptz '2026-02-01 00:00:00+00'
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;

WHERE specifies the customer and earliest date. ORDER BY asks for newest first, with descending order ID breaking any timestamp ties. LIMIT 10 keeps the first ten of that ordered result. The query returns order IDs 59041, 58041, 57041, 56041, 55041, 54041, 53041, 52041, 51041 and 50041. We will keep checking that answer as the access path changes.

Start by giving the database the customer lookup we just pictured:

CREATE INDEX index_orders_customer
ON index_orders (customer_id);

Now the engine can identify the customer’s 60 orders without inspecting every other customer. But the index has no date key. It still has to fetch those orders, reject the 45 before February, and sort the remaining 15 to find the newest ten. We have shortened the search without finishing the job.

A composite index has more than one key column. Its column order defines how entries are arranged: compare the first column, use the next to order entries tied on the first, and continue if those values tie too. For this screen, put the customer first and dates newest first within each customer:

DROP INDEX index_orders_customer;
CREATE INDEX index_orders_history
ON index_orders (customer_id, placed_at DESC, order_id DESC);

The equality condition selects customer 42’s run. Within that run the dates are ordered, so the February boundary cuts off the older entries. Starting from the newest end also produces exactly the requested order. Once ten qualifying rows have been returned, the executor can stop. It does not need to collect and sort all 15.

The final order_id DESC makes the index order agree with the complete SQL order, including ties. These examples contain no tied timestamps, but actual order histories can. An index on just customer and date does not itself supply the requested ordering between orders placed at the same instant. Keep ORDER BY in the query even when an index can provide it: SQL does not promise result order without it.

Would putting the date first do the same thing? It would group all customers’ newest orders together. That could help a screen showing the newest orders across the shop, but finding ten for one customer could require passing many other customers’ entries. There is no universal best column order. Describe the run you want to read, including where it starts and where it can stop.

PostgreSQL can scan a B-tree backwards as well as forwards. An all-ascending index on these same three keys could serve this query by scanning customer 42’s run backwards. Mixed ordering needs more care: scanning backwards reverses every key direction together. The ordering documentation develops that distinction.

What still needs checking?

Suppose the history screen now asks for paid orders only. Add one condition to the same request:

SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
  AND placed_at >= timestamptz '2026-02-01 00:00:00+00'
  AND status = 'paid'
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;

The customer and date still locate a useful run. But status is absent from our index, so PostgreSQL fetches each candidate order to check it. In our data, the scan encounters two pending orders before finding ten paid ones. It returns ten rows after examining twelve candidates. With a customer whose recent orders were mostly pending, it could inspect much more of the run.

This is a remaining filter: work left after the index has identified candidates. An index being used does not mean every query condition is doing navigation. PostgreSQL’s plan labels the conditions used by the scan as Index Cond, and a separately applied condition as Filter. Later key columns can sometimes reject entries inside an index without making the scanned interval smaller.

If paid-only histories are important enough, a candidate key is (customer_id, status, placed_at DESC, order_id DESC). The two equality conditions select one customer’s paid run before the date range. That rearrangement has a consequence for the original history screen: a customer’s orders are now grouped by status, so dates across all statuses no longer form one uninterrupted sequence.

This is why “put every filtered column in the index” is not a complete design method. The order has to serve an actual pattern of equality, range and ordering. A missing leading condition does not make a PostgreSQL index unusable, either: PostgreSQL 18 can sometimes make repeated searches over distinct leading values, called a skip scan. It is most useful when there are few such values. Read the multicolumn rules as an account of how much can be skipped, then inspect the chosen plan for your data.

There is another way to specialise a frequent query. A partial index contains only rows satisfying its own condition. An index of pending orders could be small if almost every order is already complete. It earns its space only for queries whose conditions let the planner establish that all needed rows are in that subset. A parameter whose value is unknown when a reusable plan is made can prevent that proof. The partial-index documentation explains the matching requirement. For our general history screen, we will keep the full index.

Returning values from the index

Return to the original history query, which includes pending and paid orders. Our composite index contains customer ID, timestamp and order ID. The result also asks for total. Each of its ten rows therefore needs a table fetch to obtain that amount.

We could store the amount alongside the index entry. It need not participate in sorting: PostgreSQL’s INCLUDE clause adds a value as payload.

DROP INDEX index_orders_history;
CREATE INDEX index_orders_cover
ON index_orders (customer_id, placed_at DESC, order_id DESC)
INCLUDE (total);

This index covers the query: all the values it needs are available there. An index-only scan can return those values. PostgreSQL still has to establish that each row is visible to the transaction. It keeps a small visibility map recording table pages whose rows are visible to all transactions. When a page has that mark, the scan can avoid fetching it; otherwise it must visit the heap to check.

That distinction is visible in our experiment. Before cleanup, the covering plan reported Heap Fetches: 10. To reach the next state in your practice session, run this command on its own, with autocommit enabled:

VACUUM (ANALYZE) index_orders;

Vacuum marked eligible pages as visible to all transactions. The same history query then reported Heap Fetches: 0. The index definition had not changed. The table’s state had. The final section shows how to collect these plan counters at each step. A busy table with recent changes may offer fewer opportunities to avoid those visits. The index-only scan documentation explains the visibility check.

Covering also changes how we think about a broad query. Consider summing the amounts for 900 of our 1,000 customers:

SELECT sum(total)
FROM index_orders
WHERE customer_id BETWEEN 1 AND 900;

That condition matches 54,000 orders. With an index that requires table fetches, visiting nearly the whole table through individual references can be more work than simply scanning it. With our vacuumed covering index, PostgreSQL chose an index-only scan instead: the smaller index supplied all the amounts. The number of matching rows alone did not decide the plan.

Selectivity describes the fraction of rows a condition selects. A condition matching very few rows is usually called selective. But the access decision also depends on row width, how matching rows are spread over pages, what is already cached, and whether the query can stop early. A sequential scan can be a good answer. So can reading much of a narrow covering index. There is no useful universal percentage at which every query should switch.

The cost of keeping that route

The database has to preserve the index as orders arrive and change. Inserting an order adds a table row and entries in its indexes. If a B-tree leaf page has no room, PostgreSQL can split it and update the parent’s routes. Changing an indexed value requires maintaining its new position; including a frequently changed amount also creates upkeep even though that amount does not guide searches.

Deleted rows and superseded versions can leave entries that become removable later. PostgreSQL performs index cleanup through mechanisms including vacuum. Keeping an index healthy therefore consumes ongoing CPU, memory and I/O as well as the bytes occupied by its current contents. The B-tree implementation notes explain splits and version cleanup, while routine vacuuming describes the operating work.

In our generated example, the table occupied about 13.5 MiB and the covering index about 2.9 MiB in the test runtime, excluding the separate primary-key index. The extra amount column is only a few bytes per entry here. Including a long delivery note would be a different decision: it would copy much more data into an index used to answer a small history screen. Index pages also compete with useful table pages for cache space.

A primary key or unique constraint has a second reason to keep its supporting index: enforcing the rule. Check that purpose before treating an infrequently read index as redundant. Likewise, a new composite index beginning with customer_id may make a separate customer-only index unnecessary for this workload, but its smaller size can still matter for other queries. Compare the whole workload before removing an existing access path.

Creating the index is work too. It must read existing data and build the structure. Our ordinary CREATE INDEX commands are appropriate for an isolated temporary table. On a live PostgreSQL table, an ordinary build blocks writes while it runs. A concurrent build changes that behaviour and adds its own costs and failure handling; the concurrent-build documentation is the next step before planning that operation.

Check the choice against the work

We can now make a testable prediction: the customer index should avoid other customers’ rows, the composite index should also remove the sort and permit early stopping, and the covering index may avoid heap visits. Ask PostgreSQL what happened by prefixing the history query with:

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
  AND placed_at >= timestamptz '2026-02-01 00:00:00+00'
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;

EXPLAIN ANALYZE executes the query and reports what its plan nodes actually did. BUFFERS adds page-access counters; TIMING OFF avoids measuring each node’s elapsed time while retaining row counts and total execution time. The word ANALYZE here means “run and observe”; the standalone ANALYZE index_orders command earlier collects planner statistics.

The complete experiment runs the setup and each replacement in order, with a plan after each step. It also exercises inserts, amount changes and deletes. Run the file with psql -f index-experiment.sql against your practice database, or execute its statements individually in a query editor with autocommit enabled. VACUUM cannot run inside a transaction block. Use a fresh session; running the setup twice in the same session will find the temporary table already there. Our verification used PGlite 0.5.8, an embedded WebAssembly build reporting PostgreSQL 18.3. These are observed row counts in that setting, not server latency measurements:

For the customer-only case, PostgreSQL chose a bitmap scan: collect matching row locations, then visit the table pages holding them. That improves the organisation of table access, but does not preserve the index’s ordering. It still needed the date filter and sort. PostgreSQL can also combine results from multiple indexes this way; two single-column indexes do not automatically supply the ordered run of one composite index. See combining indexes.

The essential part of the composite plan looked like this, with costs, buffer counts and PostgreSQL’s explicit type casts omitted:

Limit (actual rows=10 loops=1)
  -> Index Scan using index_orders_history on index_orders
       (actual rows=10 loops=1)
       Index Cond: ((customer_id = 42) AND
         (placed_at >= '2026-02-01 00:00:00+00'))

Read it from the indented scan towards its parent. The scan supplies rows in order; Limit stops requesting them after ten. actual rows=10 means ten rows emitted by that node, not ten total operations inside the tree. It does not count all key comparisons or page visits. Here each node ran once. In more complex plans, row counts are per loop and need to be read with loops.

Finally, give the candidate the work it will have to live with. The downloadable experiment inserts another 1,000 orders, corrects 200 amounts and deletes 100 orders. Those mutations are deliberately visible:

-- Continue after the covering-index experiment.
INSERT INTO index_orders
  (order_id, customer_id, placed_at, status, total, note)
SELECT n, 1 + n % 1000,
       timestamptz '2026-01-01 00:00:00+00' + n * interval '1 minute',
       'pending', 25.00, repeat('delivery note ', 12)
FROM generate_series(60001, 61000) AS series(n);

UPDATE index_orders
SET total = total + 1.00
WHERE order_id BETWEEN 60001 AND 60200;

DELETE FROM index_orders
WHERE order_id BETWEEN 60901 AND 61000;

The script verifies the resulting count of 60,900 rows and reports relation sizes. It gives us a reproducible check that the candidate remains usable as data changes. It cannot tell us the production cost of maintaining it: temporary tables have different storage and logging behaviour, and PGlite does not reproduce a networked server’s workload.

For a real choice, repeat the comparison on a disposable representative database with its normal durable tables, realistic row widths, large and small customers, and the application’s prepared queries. Run the same read and write mix against the current indexes and each candidate. Compare query latency and throughput, including slower requests, alongside changed plans, buffer work, index size and write latency. Let the run include sustained updates and maintenance; a freshly built index on an otherwise idle database misses part of the cost.

Keep the simplest candidate that meets the workload’s needs. For this history screen, the composite index supplies the useful route: one customer, newest qualifying orders first, stop after ten. The covering variant adds a specific possible saving—avoiding table fetches—for a specific storage and update cost. That is a choice we can measure and revisit as the screen, the data and the write traffic change.

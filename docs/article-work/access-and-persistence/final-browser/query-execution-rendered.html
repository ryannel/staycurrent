How a query runs

Querying your data · Further depthMain: Querying your dataRelated: Indexes →

A shop’s support team wants to see which products a customer bought most. The report finds that customer’s orders, joins their purchase lines, and adds the quantities by product. Later, someone asks for the same report across every customer. We change one filter. The answer still has three rows, but producing it now involves a thousand times as many purchase lines.

That change gives us a way to investigate execution. We’ll follow PostgreSQL’s chosen route for each report, see why an operation that suits one can be expensive for the other, and deliberately give the planner a question its initial statistics misunderstand. Querying your data develops the meaning of joins and grouping. Here we assume those ideas and investigate the work beneath them.

A report we can account for

For this investigation, use a new, empty PostgreSQL 18 practice database and one SQL-editor or psql connection. Load the generated shop setup once, then keep that connection open for the statements below. This is a separate dataset from both the earlier receipt examples and the larger shop used in Indexes. The practice guide explains how to create a practice database.

The setup creates 10,000 orders shared equally among 1,000 customers. Every order has three lines: one unit of product 1, two of product 2, and three of product 3. Customer 42 owns orders 42, 1042, 2042, and so on through 9042: ten orders in all. The deliberately regular data lets us calculate the answer before asking the engine for it.

orders has an index on customer_id. The primary key of order_lines creates an index on (order_id, line_no), which can locate an order’s lines together. An index is a maintained search structure; Indexes explains its organisation and cost. For now, these two available routes are enough.

SELECT l.product_id, sum(l.quantity) AS units
FROM orders AS o
JOIN order_lines AS l ON l.order_id = o.order_id
WHERE o.customer_id = 42
GROUP BY l.product_id
ORDER BY units DESC, l.product_id;

The join supplies 30 lines. sum(l.quantity) adds their quantities in three product groups; ORDER BY units DESC puts the largest total first, with product ID breaking any tie. Ten orders contribute ten copies of each quantity.

The query describes the answer. It does not demand that PostgreSQL start by reading orders, or tell it how to find matching lines. Those decisions belong to the plan.

Ten orders, ten small searches

Put the following line before the report and run the whole statement. ANALYZE here means execute the query and report observed work; plain EXPLAIN would show only the proposed plan. We turn per-operation timing off to concentrate on rows. This is a read in our practice database; the same command around a write would execute that write.

EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF, SUMMARY OFF)
SELECT l.product_id, sum(l.quantity) AS units
FROM orders AS o
JOIN order_lines AS l ON l.order_id = o.order_id
WHERE o.customer_id = 42
GROUP BY l.product_id
ORDER BY units DESC, l.product_id;

This is an abbreviated version of the observed PostgreSQL 18.3 plan. It preserves the operations, indentation and row counts while omitting costs and other detail. A different PostgreSQL installation can choose another route.

Sort (actual rows=3.00 loops=1)
  Sort Key: sum(l.quantity) DESC, l.product_id
  -> GroupAggregate (actual rows=3.00 loops=1)
       Group Key: l.product_id
       -> Sort (actual rows=30.00 loops=1)
            Sort Key: l.product_id
            -> Nested Loop (actual rows=30.00 loops=1)
                 -> Bitmap Heap Scan on orders o
                      (actual rows=10.00 loops=1)
                      -> Bitmap Index Scan on orders_customer
                           (actual rows=10.00 loops=1)
                 -> Index Scan using order_lines_pkey on order_lines l
                      (actual rows=3.00 loops=10)
                      Index Cond: (order_id = o.order_id)

Find the Bitmap Index Scan near the bottom. It searches orders_customer for customer 42 and records where the ten matching rows live. The Bitmap Heap Scan above it uses those locations to fetch the order rows. “Heap” is PostgreSQL’s name for the table storage here.

Why split that into two operations? The index groups entries by customer, but the corresponding orders can be scattered across the table. A bitmap lets the engine collect locations first and then visit the table’s pages in physical order. It gives up the index’s ordering in exchange for organising those visits. It can also combine locations from several indexes, though this query uses only one. PostgreSQL’s bitmap-scan explanation develops that tradeoff.

The nested loop takes an order from that outer branch and runs its inner branch with the order ID. For order 42, the inner index scan finds lines 42/1, 42/2 and 42/3. It then repeats for 1042 and continues through all ten orders. Each returned line carries the matching order’s contribution into the join.

Read actual rows=3.00 loops=10 as three rows per execution, averaged over ten executions. That is 30 emitted line rows altogether. It is not three rows overall, and the ten loops are not ten application requests: PostgreSQL repeats this operation inside one statement. Counts displayed as averages can be rounded; the product is approximate when they are.

This plan avoids searching the 9,990 unrelated orders through the join and avoids scanning all 30,000 lines. A nested loop can begin finding lines as soon as it has an outer order, but that does not yet mean the report can return its first total. The operations above the join still have work to do.

The two sorts answer different questions

The joined rows arrive one order at a time: product 1, product 2, product 3, then the next order’s products. To total product 1, we need its contributions from all ten orders. This plan first sorts the 30 rows by product ID. All ten product-1 rows become neighbours, followed by the product-2 and product-3 rows.

GroupAggregate can now accumulate one group at a time. It adds ten ones and finishes product 1 when product 2 begins; ten twos make 20, and ten threes make 30. That explains the change from 30 input rows to three output rows. The output count measures completed groups, not how much input the operation consumed.

But the report asks for the biggest total first. Product-ID order does not tell us which total is largest, so the top Sort orders the three completed groups by units sold. A sort below aggregation groups contributions together; a sort above it ranks the resulting answers. Their shared name conceals quite different amounts of work.

PostgreSQL’s executor normally asks a child operation for its next row as it needs one. Some children can supply a row promptly; others must gather input first. The ordinary Sort below this aggregate consumes its input before returning the first sorted row. That makes it a blocking operation in this plan: it interrupts the flow of rows until its preparation is done. It does not mean it is waiting for a lock. The executor overview explains this request-for-the-next-row model.

Even adding LIMIT 1 to this report would not let this route stop after the first order. The first order’s favourite need not be the favourite across all ten. The inputs needed to calculate the winning total still have to be consumed; limiting the output can save later work without removing that dependency.

When nearly everything is relevant

Now replace o.customer_id = 42 with o.customer_id <= 1000. Every customer in the fixture qualifies. The totals become 30,000, 20,000 and 10,000 units, still in three result rows. Run the same EXPLAIN command with that changed filter.

The naturally chosen plan changes in two places. It joins using a hash table and accumulates totals using another hash table. Here is the abbreviated observation:

Sort (actual rows=3.00 loops=1)
  -> HashAggregate (actual rows=3.00 loops=1)
       Group Key: l.product_id
       -> Hash Join (actual rows=30000.00 loops=1)
            Hash Cond: (l.order_id = o.order_id)
            -> Seq Scan on order_lines l
                 (actual rows=30000.00 loops=1)
            -> Hash (actual rows=10000.00 loops=1)
                 -> Seq Scan on orders o
                      (actual rows=10000.00 loops=1)
                      Filter: (customer_id <= 1000)

Start with the orders branch underneath Hash. A sequential scan reads the table and checks the customer condition. All 10,000 orders qualify, so an index would not let this report leave any order out. Reading the table directly avoids using the customer index as an extra route to those same rows.

The Hash operation organises these order IDs in a temporary lookup. The other branch then scans all 30,000 purchase lines. Each line uses its order ID to find a candidate in the lookup; PostgreSQL checks the join condition and emits the matching pair. Order 42’s three lines all find the same order header. A hash value helps locate candidates, but equality of the actual keys still decides the match.

Building that lookup costs work and memory before this hash join can emit matches. It pays that preparation once, rather than making 10,000 separate searches through the lines’ index. On our fixture the planner prefers the two scans and a hash join. This observation explains a choice; it is not a claim that hash joins always win or a timing comparison between the strategies.

The HashAggregate has a different lookup, keyed by product ID. Each joined line updates a running total: a product-2 line adds two to product 2’s entry. With three products it needs only three groups even though 30,000 rows contribute. It consumes those contributions before emitting the finished totals. There is no need to sort all 30,000 rows together by product first; only the three answers need the final sort.

Neither the three-row answer nor the presence of an index tells us which route to expect. The useful question is how many rows each operation will receive, and what it will have to do with each one.

What if both inputs already have the same order?

Our tables offer another possibility. The primary-key indexes can supply orders and lines in order-ID order. A merge join can advance through those two ordered inputs together. When the order side reaches ID 42, it can match the consecutive lines for 42 before advancing to the next order. It does not need to restart its search for each line.

This is a real alternative, but it was not PostgreSQL’s first choice for the broad report. To inspect it, temporarily discourage the other two join methods in our practice connection. Run the whole block; ROLLBACK ends the diagnostic transaction and restores the settings. These controls help us expose an alternative, not establish a configuration to keep.

BEGIN;
SET LOCAL enable_hashjoin = off;
SET LOCAL enable_nestloop = off;
EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF, SUMMARY OFF)
SELECT l.product_id, sum(l.quantity) AS units
FROM orders AS o
JOIN order_lines AS l ON l.order_id = o.order_id
WHERE o.customer_id <= 1000
GROUP BY l.product_id
ORDER BY units DESC, l.product_id;
ROLLBACK;

The resulting plan used Merge Join with an index scan on each primary key. Its result was the same. The lines’ index is ordered by (order_id, line_no), so it supplies the needed order without a separate sort. If suitable ordering were absent, preparing sorted inputs would add work before merging could proceed. Even with these indexes available, the natural broad plan preferred scanning and hashing.

Notice which order merge joining supplies: order ID. Our report groups by product ID and ranks by units sold. Those are different keys. The diagnostic plan still used HashAggregate and a final sort. Having an ordered stream helps only the operations that can use that particular order.

The plan is chosen before the rows arrive

We know customer 42 has ten orders because we generated the data. The planner needs an estimate before it executes the report. PostgreSQL’s statistics describe table size, common values, value distributions and distinct counts; ANALYZE refreshes them. Large tables are sampled, so these are useful approximations rather than a fresh census for every query. The ANALYZE documentation describes what is collected.

Take the unabridged inner scan from our narrow plan:

Index Scan using order_lines_pkey on order_lines l
  (cost=0.29..11.49 rows=3 width=12)
  (actual rows=3.00 loops=10)

The first rows=3 is the predicted output for one execution; the later actual rows=3.00 is the observed average. Here they agree. width=12 estimates the bytes per output row. The two cost numbers estimate the work before output can begin and the work for completing the operation, in planner units. They are not milliseconds. An upper operation’s cost includes its children, so adding every printed cost would count the same work again.

An inaccurate row estimate can change the choice. If the planner expects ten outer orders, ten line lookups may look attractive. If there are actually 10,000 outer orders, that inner scan runs far more times than expected. To investigate such a surprise, look for where estimated and observed rows first diverge, then follow the extra rows into the operations that depend on them. Using EXPLAIN explains these fields and repeated-operation averages.

We can create a smaller, exact example of a mistaken estimate in this fixture. Orders for customers 1–100 have sales_region = 'north'; all others have 'south'. Customer 42’s ten orders are therefore all in the north. Run this query with the same EXPLAIN prefix:

SELECT order_id
FROM orders
WHERE customer_id = 42 AND sales_region = 'north';

Initially, the bitmap index scan estimates ten orders for customer 42 correctly. But the table scan above it estimates only one after applying the north condition; it actually emits ten. It treats the additional condition as though north might independently eliminate nine in ten of this customer’s orders. In the whole table, north is 10%; within customer 42’s orders, it is 100%.

Running ordinary ANALYZE orders again does not teach it this relationship. The individual-column statistics already describe both distributions correctly. We need to ask for statistics about their dependency:

CREATE STATISTICS orders_customer_region (dependencies)
ON customer_id, sales_region FROM orders;
ANALYZE orders;

Run the filtered query’s EXPLAIN again. In our execution the table scan’s estimate became ten, matching its ten observed rows. No orders changed and no search index was added. We improved information used to choose a plan. The access route remained a bitmap scan; fixing an estimate does not require changing the plan’s shape.

Dependency statistics suit these equality conditions on columns of the same table. They are not a general cure for every join or every correlated expression. The useful lesson is to identify what information is missing: stale distributions need refreshing; a relationship absent from individual-column statistics needs something more. Extended planner statistics explains the supported cases, and the worked examples show other kinds of estimate repair.

When preparation outgrows memory

The broad report’s final sort has only three totals. Its hash join retains 10,000 order IDs, while its hash aggregate retains three product groups. These operations have very different memory demands even within one query. More contributing rows do not necessarily mean more groups; more distinct products would enlarge the aggregate’s retained state.

PostgreSQL uses work_mem as a base limit for operations such as sorts, with a multiplier for hash operations. It is not a single allowance for the whole query or connection. Multiple operations and concurrent queries can each use memory. When a sort cannot keep its input in the permitted memory, it can write temporary runs and merge them; hash operations can also divide work into batches involving temporary storage. The memory settings documentation explains these boundaries.

To see a sort spill without inventing a huge shop, temporarily give a detailed line listing a small allowance. This query returns all 30,000 lines sorted by product and order, so its sort must handle the lines themselves rather than three totals.

BEGIN;
SET LOCAL work_mem = '64kB';
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT order_id, product_id
FROM order_lines
ORDER BY product_id, order_id;
ROLLBACK;

Our execution reported Sort Method: external merge, Disk: 544kB, and temporary blocks read and written. Those fields establish temporary-file work. The size can differ on another build; this PGlite run does not measure physical disk speed. The ROLLBACK restores the connection’s earlier memory setting.

A spill is a reason to inspect the amount and shape of input, not an instruction to raise memory everywhere. Perhaps the query needs every line; perhaps the application asked for detail when it only needed totals. The plans above let us distinguish those cases before changing a resource setting.

Read the work that leads to the answer

Begin with the result you intend to preserve. Then follow the plan’s branches: which rows can the scan leave out, how does a join find partners, and which operation repeats? Compare predicted and observed rows at the same operation, accounting for loops. Finally, follow ordering and grouping upwards to see how much input must arrive before the result can emerge.

These observations explain why “three rows returned” can describe either 30 or 30,000 joined rows, why an index lookup can be useful ten times and costly ten thousand times, and why a report with a limit may still have to finish its underlying totals. They also give you a concrete next experiment: change a filter, inspect an estimate, or compare an alternative while checking that the answer stays correct.

The complete experiment script runs after the setup and includes all three join routes, the statistics comparison, and the spill observation. Use a fresh setup when repeating the statistics experiment: creating its statistics object changes what subsequent plans know.

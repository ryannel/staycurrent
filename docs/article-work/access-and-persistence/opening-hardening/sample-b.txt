Indexes

A customer opens their order history. The shop has years of orders, but this screen needs only ten recent ones belonging to that customer. SQL can express that request in a few lines. The database still has to find the records.

It could read the whole orders table, keep the rows for this customer, discard the old ones, and put the remaining orders in date order. That works. It also repeats a great deal of work whenever someone opens their history. An index stores selected values from a table in a structure that makes them easier to find. The database keeps it up to date as rows change.

For the history screen, finding the customer is only the start. The database also needs to check dates and return the newest orders first. We’ll start with an index on customer ID, then add columns so PostgreSQL can read the orders in the order we need. Each addition can save work when reading, but also takes space and must be maintained when orders change.

We’ll use PostgreSQL 18 and its default index type, a B-tree. Other databases use B-trees too, though they can store table rows differently and have different rules for deciding which row versions a query can see.

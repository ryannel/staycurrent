Durability guarantees
The crash examples assume fsync = on, full_page_writes = on, and synchronous_commit = on, with no configured synchronous standby. With these settings, PostgreSQL waits for the required WAL to become durable on the local server before acknowledging a transaction that changes an ordinary logged table. It can then recover that transaction after a server crash, operating-system crash or power failure, provided the storage survives and correctly honours flush requests.
With synchronous_commit = off, PostgreSQL can acknowledge a commit before its WAL is durable. A crash can then lose recent transactions whose commits were acknowledged, although recovery still produces a consistent database. Disabling fsync also removes the write synchronisation needed to prevent corruption after a system crash. Asynchronous Commit explains why turning off these two settings has different consequences.
PostgreSQL also lets you create UNLOGGED tables, whose data changes are not written to WAL. They are emptied after a crash or unclean shutdown, including data from committed transactions. Use them only for data you can discard and rebuild. The unlogged-table documentation describes their behaviour.
Even with reliable storage and all these protections enabled, the log has limits. If the device holding both the table and WAL is destroyed, PostgreSQL has nothing to recover from locally. If someone commits an accidental deletion, crash recovery preserves that deletion. Recovering the lost data requires another copy. A physical base backup together with an unbroken sequence of archived WAL lets you restore to a chosen point after the backup, such as just before the deletion. The active WAL directory alone is insufficient. PostgreSQL’s point-in-time recovery guide explains how to keep the backup and log archive needed for this.
For our price update, a successful commit means PostgreSQL can recover 22.00 after a crash with its storage intact. To recover after losing a device or making a mistaken update, keep a suitable copy elsewhere, such as a backup with archived WAL, and test that you can restore the data you need.

Vacuum and space reuse
The table still has one blue-mug product, but it may be storing both the 20.00 and 22.00 versions. Further updates create more versions. Once no query can need an old version, PostgreSQL can remove it and reuse the space. A report holding an older snapshot can delay that cleanup because it still needs to read the old price.
PostgreSQL’s vacuuming reclaims dead versions so the space can be reused. Autovacuum arranges routine cleanup, while page pruning can also recover space during normal work. A free space map helps later writes find pages with room. A table that is updated regularly needs this cleanup even if it always contains the same number of products.
Ordinary VACUUM generally leaves the table’s files at their existing size, though it can remove empty pages at the end. The freed space inside those files is available for later inserts and updates. VACUUM FULL rewrites a compact copy, requiring extra temporary disk capacity and an exclusive table lock. Routine vacuuming explains why regularly reusing space is usually preferable to repeatedly shrinking and regrowing it.
Writing a checkpoint will not remove these old row versions. Checkpoints save dirty pages so recovery can start further along in the log. Vacuuming finds versions that can be removed, makes their space reusable, and performs other visibility and transaction-age maintenance. A regularly updated database needs both.

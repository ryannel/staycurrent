Filtering
Suppose the history screen now asks for paid orders only. Add one condition to the same request:
SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
AND placed_at >= timestamptz '2026-02-01 00:00:00+00'
AND status = 'paid'
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;

PostgreSQL can still find customer 42’s recent orders in the index. It then has to fetch them from the table to check status, which the index does not contain. In our data, the scan encounters two pending orders before finding ten paid ones. It returns ten rows after examining twelve candidates. With a customer whose recent orders were mostly pending, it could inspect much more of the run.
The status check is a filter applied after finding the rows through the index. In PostgreSQL’s execution plan, Index Cond shows conditions checked by the index scan, while Filter shows a separate check. Even an Index Cond does not always reduce how much of the index is scanned: a condition on a later key column may reject entries along the way.
If the shop often needs paid-only histories, we could try (customer_id, status, placed_at DESC, order_id DESC). The two equality conditions select one customer’s paid run before the date range. For the original history screen, however, a customer’s orders are now grouped by status, so dates across all statuses no longer form one uninterrupted sequence.
Adding status helps one query and changes what the index can do for another. The column order matters as much as which columns are present. A missing leading condition does not make a PostgreSQL index unusable, either: PostgreSQL 18 can sometimes make repeated searches over distinct leading values, called a skip scan. It is most useful when there are few such values. The multicolumn documentation explains when these searches can help. Check the execution plan to see what PostgreSQL chooses for your data.
There is another way to specialise a frequent query. A partial index contains only rows satisfying its own condition. An index of pending orders could be small if almost every order is already complete. PostgreSQL can use that index when it knows the query asks only for pending orders. If the query instead supplies status as a parameter, a reusable plan made without knowing its value may have to allow for other statuses too. The pending-only index cannot answer those requests. For our general history screen, we will keep the full index.

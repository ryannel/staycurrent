Planner estimates
We know customer 42 has ten orders because we generated the data. The planner needs an estimate before it executes the report. PostgreSQL keeps statistics about table size, common values, value distributions and distinct counts. ANALYZE refreshes them, using a sample of the rows for large tables.
Here is the inner index scan from the first plan, this time with its estimates included:
Index Scan using order_lines_pkey on order_lines l
(cost=0.29..11.49 rows=3 width=12)
(actual rows=3.00 loops=10)

PostgreSQL estimated three rows for each index scan, and that is how many it found on average. It also estimated 12 bytes per output row, shown as width=12. The first cost, 0.29, estimates the work needed before the scan can return a row; 11.49 estimates the cost of completing it. These costs use the planner’s own units, rather than milliseconds. Each operation’s cost includes the operations beneath it, so adding all the costs in a plan would count the same work repeatedly.
A nested loop that looks cheap for ten orders may be expensive for 10,000: the inner scan has to run a thousand times more often. If the planner underestimates the number of orders, it can choose that plan without anticipating the extra lookups. When investigating an unexpectedly slow query, look for the first operation where the estimated and actual row counts differ substantially. Then check how the extra rows affect the operations above it. PostgreSQL’s Using EXPLAIN guide has more examples of interpreting these counts and costs.
Our example data also lets us see how an estimate can go wrong. Orders for customers 1–100 have sales_region = 'north'; all others have 'south'. Customer 42’s ten orders are therefore all in the north. Run this query with the same EXPLAIN prefix:
SELECT order_id
FROM orders
WHERE customer_id = 42 AND sales_region = 'north';

Initially, the bitmap index scan estimates ten orders for customer 42 correctly. But the table scan above it estimates only one after applying the north condition; it actually emits ten. Ten per cent of the table’s orders are in the north, and the planner applies that proportion to customer 42’s orders too. It has no statistics telling it that this customer’s orders are all in the north.
Running ANALYZE orders again would refresh the statistics for each column, but those already describe both distributions correctly. To record the relationship between customer and region, we need to ask for dependency statistics:
CREATE STATISTICS orders_customer_region (dependencies)
ON customer_id, sales_region FROM orders;
ANALYZE orders;

Run the filtered query’s EXPLAIN again. In our run, the table scan’s estimate rose to ten, matching the ten rows it returned. PostgreSQL still chose a bitmap scan, but now it had an accurate estimate of how many rows would pass both conditions. We changed only its statistics; the orders and indexes stayed the same.
Dependency statistics can help with equality conditions like these on columns of one table. Their support is more limited for other conditions, and they do not generally fix estimates for joins or correlated expressions. Before adding statistics, check what the planner is missing. If the data has changed since it was last analysed, refreshing the existing statistics may be enough. Here, the missing information was the relationship between two columns. Extended planner statistics explains the supported cases, and the worked examples show other kinds of estimate repair.

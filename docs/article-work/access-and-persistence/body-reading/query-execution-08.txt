Merge joins
The primary-key indexes also let PostgreSQL read both tables in order of order ID. A merge join can work through them together. When it reaches order 42, it matches the consecutive lines for 42 before advancing to the next order. Because both inputs are ordered, it can keep moving forwards instead of starting a new search for each line.
Merging orders and order lines

The next line belongs to order 2. Move to order 2 in the orders table.
Match order 2 with its three lines, then continue to order 3.
Each order ID appears once in the orders table, so each line matches one order. If both sides had repeated keys, the join would need to return every matching pair.
To see a merge join for this report, we can temporarily discourage the other two join methods. Run the whole block below in the practice connection. The settings apply only within this transaction; ROLLBACK restores them afterwards. This lets us inspect the alternative without changing the connection’s usual planner settings.
BEGIN;
SET LOCAL enable_hashjoin = off;
SET LOCAL enable_nestloop = off;
EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF, SUMMARY OFF)
SELECT l.product_id, sum(l.quantity) AS units
FROM orders AS o
JOIN order_lines AS l ON l.order_id = o.order_id
WHERE o.customer_id <= 1000
GROUP BY l.product_id
ORDER BY units DESC, l.product_id;
ROLLBACK;

This produced a Merge Join with an index scan on each primary key, returning the same totals as before. The lines’ index is ordered by (order_id, line_no), so it can supply rows in the order the join needs. Without suitable indexes, PostgreSQL would have to sort the inputs first. Even with these indexes, its original plan for the report used scanning and hashing.
The merge join returns rows in order of order ID, which does not help us group by product or rank the totals by units sold. This plan therefore still uses HashAggregate and a final sort.

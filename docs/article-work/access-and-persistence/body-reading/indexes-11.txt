Storage and maintenance
Every insert or update may also require changes to the indexes. Inserting an order adds a table row and entries in its indexes. If a B-tree leaf page has no room, PostgreSQL can split it and change the parent page to point to the new pages. Changing a key value requires an entry at its new position. Updating an included value such as total also requires index maintenance, even though it is not a search key.
Deleted rows and superseded versions can leave entries that become removable later. PostgreSQL removes these entries through mechanisms including vacuum. These changes and the later cleanup use CPU, memory and I/O in addition to the index’s storage space.
In our generated example, the table occupied about 13.5 MiB and the covering index about 2.9 MiB in the test runtime, excluding the separate primary-key index. The extra amount column is only a few bytes per entry here. Including a long delivery note would be a different decision: it would copy much more data into an index used to answer a small history screen. Index pages also compete with useful table pages for cache space.
A primary key or unique constraint has a second reason to keep its supporting index: enforcing the rule. Check that purpose before treating an infrequently read index as redundant. Likewise, a new composite index beginning with customer_id may make a separate customer-only index unnecessary for this workload, but its smaller size can still matter for other queries. Check the other queries that use an index before removing it.
Creating the index is work too. It must read existing data and build the structure. Our ordinary CREATE INDEX commands are appropriate for an isolated temporary table. On a live PostgreSQL table, an ordinary build blocks writes while it runs. A concurrent build changes that behaviour and adds its own costs and failure handling; the concurrent-build documentation is the next step before planning that operation.

Rows and pages
Suppose a shop’s products table contains P7, a blue mug whose current price is 20.00. A product-page request sends this query to PostgreSQL:
SELECT current_price
FROM products
WHERE product_id = 'P7';

The table is stored in a collection of fixed-size pages, usually 8 kB each. Each page has a header, row data and usually some unused space. It also records where each row begins within the page. A stored row has its own header, including transaction information that PostgreSQL uses to decide which queries can see it. We’ll see shortly why a row can have more than one stored version.
The values in our small product row fit together on a page. A long product description might be compressed or moved into separate storage by PostgreSQL’s TOAST mechanism. Reading that description could then require additional reads that a query for just the product ID would avoid.
An ordinary PostgreSQL table is a heap, which means rows are not kept in a chosen key order. P7 could share a page with products added at much the same time, whatever their IDs. An index can locate P7 without searching the whole table; the indexes article explains how. For this example, suppose PostgreSQL has located P7 on page 12.
PostgreSQL works on the page in its shared buffers, a cache in server memory. If page 12 is already there, PostgreSQL can read P7’s price from it. Otherwise it reads the page from the table file, possibly through the operating system’s file cache. A page missing from shared buffers therefore does not always require a read from the drive.

PostgreSQL reads the whole page, including P3 and P9, to return P7’s price of 20.00. Later queries can read any of these products from the buffered page. This drawing shows three products; a real page is usually 8 kB and can hold as many row versions as fit.
Reading P7’s price brought P3 and P9 into memory too, because they share page 12. A request for either product can now use the same buffered page. If those three products had occupied separate pages, fetching all three could have required three page reads. The number of rows a query returns tells us only part of what PostgreSQL had to read.
This arrangement also means reading each product’s name and price together, even when a query only asks for prices. Column-oriented databases group values from the same column instead, so a query can read prices without bringing the other columns into memory. Both arrangements can support SQL tables.

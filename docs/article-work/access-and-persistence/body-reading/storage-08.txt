After a crash
At restart, the table files may contain a mixture of older pages and newer ones. Recovery reads the durable WAL and redoes the necessary changes. Some of those changes may belong to transactions that never committed. Replaying them can restore their row versions to a page, but PostgreSQL checks transaction status when deciding which versions a query can see.
If no commit record survives for our price change, a new query after recovery sees 20.00. The table may contain a 22.00 version, but PostgreSQL treats its transaction as uncommitted and keeps that version hidden. If the update and commit records both survive, the query sees 22.00, even if recovery had to restore it from the log. This is how PostgreSQL preserves its transaction guarantee through a crash.

Success received.

Recovery restores the 22.00 version from WAL. Queries can see it because the commit record survived too.

C · Before the reply arrives
Durable WAL
Update and commit records survive.

Table file at the crash
Still has the earlier page with 20.00 only.

Application’s reply
Connection lost before any success arrived.

New query after recovery: 22.00
The transaction committed, but the application never received confirmation.

These examples use synchronous local commit and reliable storage. In B and C, a query after recovery returns 22.00. In C, the application lost its connection before it could learn that the transaction committed.
Case C is awkward for the application. It sent COMMIT, then lost the connection. PostgreSQL recovered the committed price of 22.00, but the application never received confirmation. It cannot assume the transaction rolled back and safely repeat the operation. Handling conflicts and uncertain outcomes explains how an application can recover the original operation’s outcome without blindly repeating its effects.
A crash can also interrupt the writing of a page itself. The surviving page might contain a mixture of old and new pieces, rather than either complete version. With full_page_writes enabled, PostgreSQL includes a full image of a page in WAL on its first modification after a checkpoint. That gives recovery a complete image to restore when a partially written page cannot safely accept incremental changes. This kind of partially completed page write is called a torn write.

Updates and row versions
A staff member changes the blue mug’s price to 22.00. The shop’s update handler borrows one database connection, sends BEGIN, sends the update, and checks that it succeeded for P7 before sending COMMIT. These are the statements on that successful path, all on the same connection:
BEGIN;
UPDATE products
SET current_price = 22.00
WHERE product_id = 'P7';
COMMIT;

In PostgreSQL, this update creates a new row version. The earlier version still contains 20.00; the new one contains 22.00. Transaction information lets the engine decide which version a reader can see. An ordinary query from another connection cannot see the unfinished price change. A report with an older snapshot may continue to see 20.00 even after the writer commits. This is multiversion concurrency control, developed further in Isolation and snapshots.
The new version may fit on the same page or need another page. PostgreSQL can sometimes avoid creating new ordinary index entries when the changed columns and available space allow a heap-only tuple update. The old price remains in its row version until PostgreSQL can remove it safely.
A changed buffer page is called dirty because it needs to be written back to its file. The page can contain changes from both committed and unfinished transactions. Writing it to the file does not commit those unfinished transactions, and committing a transaction does not necessarily write the page.
If the changed page in memory were the only copy of our update, a server crash could lose the new price. PostgreSQL could wait for every changed table and index page to be written before acknowledging a commit. Instead, it saves the changes in a log that it can use to restore those pages.

Memory and temporary files
The report across all customers uses memory in several places. The hash join stores 10,000 order IDs, the hash aggregate keeps three running totals, and the final sort orders those three totals. The aggregate needs one entry for each distinct product, however many lines it reads. More orders make the join’s hash table grow; more distinct products make the aggregate’s hash table grow.
PostgreSQL’s work_mem setting provides a base memory limit for operations such as sorts, with a multiplier for hash operations. Each operation can use its own allowance, so several operations in one query, or several queries running together, can use much more than work_mem in total. When a sort runs out of allowed memory, it can sort portions of its input into temporary files and merge them. Hash operations can also split their work into batches that use temporary storage.
We can make a sort spill to temporary files by giving it a small memory allowance. The query below sorts all 30,000 lines by product and order ID, which takes more memory than sorting the three totals in our report.
BEGIN;
SET LOCAL work_mem = '64kB';
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT order_id, product_id
FROM order_lines
ORDER BY product_id, order_id;
ROLLBACK;

Our run reported Sort Method: external merge, Disk: 544kB, and counts of temporary blocks read and written, confirming that the sort used temporary storage. The size may differ on your installation. We ran these examples in PGlite, so this does not measure the speed of a server’s physical disk. ROLLBACK restores the connection’s previous memory setting.
Before increasing work_mem, check what the query is sorting. If the application needs only product totals, returning every line makes the sort do unnecessary work. If it really needs all the lines in this order, more memory may help, but the setting also affects other operations and concurrent queries.

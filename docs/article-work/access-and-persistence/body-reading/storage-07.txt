The write-ahead log
As it changes pages, PostgreSQL generates write-ahead log records, or WAL. These records describe the changes to pages, so PostgreSQL can reconstruct them during recovery. Transactions append to the same log, which is stored separately from table and index files. Recovery uses those records rather than running the original SQL again: repeating an instruction to increase a price by two could increase it a second time.
Before PostgreSQL writes a changed data page to its file, it must flush the WAL records for those changes to persistent storage. This is the ordering that gives write-ahead logging its name. The page can change in memory before that flush. Each page records its position in the log, allowing PostgreSQL to check that the WAL has been flushed up to that point. During recovery, it uses that position to avoid applying changes the page already contains.
For our price update, PostgreSQL can flush the change records and commit record, then tell the application that the commit succeeded. Page 12 in the table file may still contain just the 20.00 version. If the server crashes now, PostgreSQL can recover the 22.00 version from the log.

Reply to the application
The handler receives confirmation. The table file still has the earlier page with only the 20.00 version.

Write the changed table page later
The table file now contains the 22.00 version too. If this page survives a crash intact, recovery can skip reapplying the change.

The table page can also be written earlier, even before commit, once the WAL for its changes has been flushed. To acknowledge a synchronous commit, PostgreSQL must also flush the transaction’s commit record.
This is why WAL reduces the work a commit must wait for. Appending to the log lets PostgreSQL defer writes to scattered table and index pages. Several transactions can share one log flush. A page can also accumulate several changes in memory before PostgreSQL writes it back, reducing how often that page has to be written.
A normal write call may leave data in a cache that loses its contents when the power fails. To flush WAL, PostgreSQL requests that the operating system and storage devices make the write durable. This depends on them reporting completion correctly. If a drive reports success while the only copy is still in a volatile cache, PostgreSQL may acknowledge a transaction that a power failure can erase. PostgreSQL’s reliability documentation explains the requirements for reliable storage.

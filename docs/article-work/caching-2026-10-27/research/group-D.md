# Article 7: `how-redis-works`

## 7.A One main thread executing commands

- **7.A1** Redis serves all client requests with a mostly single-threaded design: one process, using multiplexing, serving one request at any moment, sequentially. "Mostly" because since 2.4 background threads do slow I/O (disk). Source: [doc:operate/oss_and_stack/management/optimization/latency/] ("Single threaded nature of Redis").
- **7.A2** The event loop is `ae.c`. `aeMain` repeatedly calls `aeProcessEvents`, which calls a `beforesleep` hook, waits for readiness events, then runs handlers. The backend is chosen at compile time: evport (Solaris), epoll (Linux), kqueue (macOS/BSD), select (fallback). Observed on this machine: `multiplexing_api:kqueue`. Source: [src:ae.c] lines 32-41 and 365-412, 497-505; transcript "redis-cli -p 7204 info server".
- **7.A3** Per client event: Redis performs a single `read()` per readable event, so a fast sender does not starve others; then it processes **all complete commands already in that client's buffer** in sequence. Order across clients is "unspecified" (set by file-descriptor number and kernel event order). Source: [doc:develop/reference/clients/] ("What Order are Client Requests Served In?").
- **7.A4** Consequence 1, atomicity: a request from another client is never served in the middle of a command, a `MULTI`/`EXEC` block or a script/function. Source: [doc:develop/using-commands/transactions/] ("A request sent by another client will never be served in the middle of the execution of a Redis Transaction"); [doc:develop/programmability/eval-intro/] ("While executing the script, all server activities are blocked during its entire runtime").
- **7.A5** Consequence 2, one slow command delays everyone. "When a request is slow to serve all the other clients will wait for this request to be served." Source: latency doc above. **Observed** (`probe.py`, 1,000,000 keys of `user:%08d` with 10-byte values): `KEYS *` took 103.7 ms to produce its first reply byte; a second client PINGing every ~1 ms saw a single reply delayed by **103.7 ms** (idle median 0.15 ms, max 3.7 ms). `KEYS user:0000099*`, which matches only 10 keys, still blocked for **81 ms**: the pattern filters after walking every key. Docs say `KEYS` is O(N) "and the constant times are fairly low ... an entry level laptop can scan a 1 million key database in 40 milliseconds" ([doc:commands/keys/]); the observed 80-100 ms includes building and sending a 20 MB reply.
- **7.A6** Each command is timed by the server and logged by SLOWLOG when it exceeds `slowlog-log-slower-than`; "the execution time does not include I/O operations like talking with the client, sending the reply", just execution, "the only stage of command execution where the thread is blocked". Source: [doc:commands/slowlog-get/]. Defaults observed: `slowlog-log-slower-than 10000` (µs, i.e. 10 ms), `slowlog-max-len 128`, `slowlog-entry-max-argc 32` (the doc calls it `slowlog-max-argc`; **the config name on 8.10.3 is `slowlog-entry-max-argc`**), `slowlog-entry-max-string-len 128`. Redis 8.10 added a 7th field to SLOWLOG entries (total argument count); observed.
- **7.A7** `INFO commandstats` gives per-command `calls`, total `usec` and `usec_per_call` of execution time. Observed after loading 3.4 million `SET`s: `cmdstat_set ... usec_per_call=0.24`; a `GET` showed ~1.4-2 µs; `KEYS` over 1M keys `usec_per_call=92227`. So server-side execution of a cached read is about a microsecond, far below the network round trip (see 8.A). Source: transcript "latency tooling".
- **7.A8** Timers: `hz` (default **10**, range 1-500) controls how often the event loop runs background tasks (expiry, client timeouts); `dynamic-hz yes` is the default. [conf] ("hz 10" block); observed.

## 7.B I/O threads

- **7.B1** Threaded I/O arrived in Redis 6.0 (socket reads/writes/parsing on helper threads, opt-in). Redis 8.0 replaced the implementation: the main thread assigns clients to I/O threads; each I/O thread reads and parses queries, then notifies the main thread; **the main thread executes the commands and generates replies**; I/O threads write the replies to the sockets. Source: Redis blog [https://redis.io/blog/redis-8-0-m03-is-out-even-more-performance-new-features/] ("Better multithreading with a new asynchronous I/O threading implementation"); 8.0.0 release notes (#13695 "New I/O threading implementation") [rn:8.0.0]; code header [src:iothread.c].
- **7.B2** Version facts: in 8.0 `io-threads-do-reads` stopped having any effect ("The new I/O threading implementation always use threads for both reads and writes") [rn:8.0.0]. In 8.2: commands' argv/rewrite object freeing offloaded to I/O threads (#13968), main and I/O threads processing in parallel (#13969), memory prefetching in I/O threads (#14017) [rn:8.2.0]. In 8.4: lookahead prefetching across several parsed commands (#14440) [rn:8.4.0]. In 8.8: batched prefetch for `MGET` and `MSET` (#15133) [rn:8.8.0].
- **7.B3** Default `io-threads 1` ("Single threaded by default"); immutable at runtime (`IMMUTABLE_CONFIG`), range 1-128. [src:config.c] line 3507. [conf]'s advice: "enable it only in machines that have at least 4 or more cores, leaving at least one spare core"; "only if you actually have performance problems, with Redis instances being able to use a quite big percentage of CPU time"; example "four cores boxes, try to use 3 I/O threads, ... 8 cores, try to use 7". The same text says the thread count includes the main thread (the "1" setting "will just use the main thread").
- **7.B4** Vendor performance claims, with the version: M03 blog, io-threads 8 on a multi-core Intel CPU: "from 37% to 112% improvement in throughput (contingent on the commands being executed)". 8.4.0 release notes: "I/O threading: substantial throughput increase (e.g. >30% for caching use cases (10% `SET`, 90% `GET`), 4 cores)" [rn:8.4.0]. These are vendor numbers under their conditions; present them as such, or not at all.
- **7.B5** What threads do not do: command execution stays on the main thread. Other helper threads (BIO) do background work: freeing memory for `UNLINK`/lazy-free, closing files, fsync. Source: [doc:commands/unlink/] ("performs the actual memory reclaiming in a different thread"); [src:lazyfree.c].
- **7.B6** **Observed** (`INFO threads`, `--io-threads 4`): `io_threads_active:1`, one row per thread (`io_thread_1:clients=1,reads=386912,writes=386836` etc.), plus `io_threaded_reads_processed` and `io_threaded_writes_processed` in `INFO stats`. With 1 thread `io_threads_active:0`. Transcript "restart with --io-threads 4".
- **7.B7** Caution on benchmarking: [conf] says to benchmark I/O threads with `redis-benchmark --threads N` matching the server, "otherwise you'll not be able to notice the improvements". My runs did not use `--threads`, so the client was the bottleneck and I **make no throughput claim**. Observed only: `-P 1`, 50 connections, GET: ~136k/s (1 thread) vs ~117k/s (4 threads); `-P 16`: ~1.34M/s vs ~1.63M/s. Pipelining mattered about **10x** (136k to 1.34M GET/s at one server thread); the thread count did not on a client-limited test. Transcript "restart with --io-threads 4" and "baseline".
- **7.B8** UNCONFIRMED: independent (non-vendor) benchmarks of the 8.x I/O threads; I did not find one.

## 7.C Command cost, `KEYS` vs `SCAN`, `DEL` vs `UNLINK`

- **7.C1** Time complexity is documented per command and is "a good practice ... to systematically check it" for unfamiliar commands; in `redis-cli`, `COMMAND DOCS <name>` prints it. Source: latency doc; [cdocs]. Examples observed: `GET`, `SET`, `INCR`, `GETDEL`, `GETEX` O(1); `MGET`/`MSET` O(N) in keys; `HGETALL` O(N) in hash size; `KEYS` "O(N) with N being the number of keys in the database"; `SCAN` "O(1) for every call. O(N) for a complete iteration"; `DEL` O(N) in elements for collections; `UNLINK` "O(1) for each key removed regardless of its size. Then ... O(N) work in a different thread".
- **7.C2** `SCAN` guarantees: an element present for the whole iteration is returned at least once; an element never present is never returned; but **an element can be returned more than once**, and elements added/removed during the iteration may or may not be returned. A call may return zero elements; only a returned cursor of `0` ends the iteration. `COUNT` is "just a hint" (default **10**); `MATCH` is applied after the elements are fetched, so a rare pattern yields mostly empty pages. Source: [doc:commands/scan/] ("Scan guarantees", "The COUNT option"). Observed: `SCAN 0 COUNT 10` returned cursor `851968` and 10 keys; with `MATCH user:0000099*` the same page returned cursor `851968` and no keys.
- **7.C3** **Observed full-iteration cost** (1,000,000 keys, second client PINGing ~every 1 ms; `scanprobe.py`):

  | `SCAN ... COUNT` | calls | wall time | PING p99 | PING max |
  | --- | --- | --- | --- | --- |
  | 10 | 95,467 | 9.50 s | 0.30 ms | 16.6 ms (single outlier) |
  | 1,000 | 1,000 | 0.58 s | 0.71 ms | 4.0 ms |
  | 100,000 | 10 | 0.42 s | 18.0 ms | 29.9 ms |

  Reading: `SCAN` trades total time for bounded pauses; a large `COUNT` reintroduces `KEYS`-like stalls. `COUNT` 10 pays ~95k round trips. These are single runs on a laptop; the 16.6 ms outlier at COUNT 10 is not explained (UNCONFIRMED cause; plausibly OS scheduling).
- **7.C4** `DEL` frees memory on the main thread; `UNLINK` removes the key from the keyspace at once and frees the value on a background thread (4.0+). Source: [doc:commands/unlink/], [cdocs]. Lazy free is used only when the object has more than **64** allocations (`LAZYFREE_THRESHOLD`, [src:lazyfree.c] line 226; "free effort" is element count for hashtable sets/hashes/zsets, 1 for strings). **Observed:** a set with 2,000,000 members (70.8 MB by `MEMORY USAGE`, hashtable encoding): `DEL` blocked **279.5 ms** (SLOWLOG 278,493 µs; the second client's PING saw 279 ms); `UNLINK` replied in **0.3 ms**, PING max 0.49 ms. `UNLINK` of a small string left `lazyfreed_objects:0`; `UNLINK` of a 100-member hashtable set raised it to 1.
- **7.C5** Redis frees objects on its own in four situations: eviction, expiry, a command overwriting an existing key (`SET`, `RENAME`, `*STORE`), and a replica flushing for full sync; each has a config `lazyfree-lazy-eviction`, `-expire`, `-server-del`, `replica-lazy-flush`; plus `lazyfree-lazy-user-del` (make `DEL` act like `UNLINK`) and `lazyfree-lazy-user-flush`. **Defaults are all `no` in Redis 8.0 to 8.10** (checked `config.c` at 8.0.0, 8.2.0, 8.4.0, 8.6.0, 8.8.0, 8.10.3; observed with `CONFIG GET`). Source: [conf] lines 1340-1386, [src:config.c] lines 3410-3414. **Valkey differs materially:** Valkey 8.0 `valkey.conf` sets all of `lazyfree-lazy-eviction`, `-expire`, `-server-del`, `-user-del`, `-user-flush` and `replica-lazy-flush` to `yes` (https://github.com/valkey-io/valkey/blob/8.0/valkey.conf lines 1283-1304). Decision relevance: a cache that expires or evicts big values blocks the main thread on Redis by default; the writer can say "set the lazy-free options to yes" as a tuning option (UNCONFIRMED whether any Redis managed service flips these).
- **7.C6** Other O(N) hazards named by the docs: `SORT`, `LREM`, `SUNION`, intersections of big sets; `KEYS` "should only be used for debugging purposes"; use `SCAN`, `SSCAN`, `HSCAN`, `ZSCAN`; or run slow queries on a replica. Source: latency doc.
- **7.C7** Many keys expiring in the same second can block the active-expire cycle. The docs say the cycle samples 20 keys per loop and repeats if more than 25% were expired. **Discrepancy:** `expire.c` at 8.10.3 has `ACTIVE_EXPIRE_CYCLE_KEYS_PER_LOOP 20`, `ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC 25` (max % of CPU for the slow cycle) and `ACTIVE_EXPIRE_CYCLE_ACCEPTABLE_STALE 10` (% of stale keys after which it repeats). The docs' "25%" appears to describe an older rule. **Owner is article 4; flag to its researcher.** Sources: latency doc; [src:expire.c] lines 96-99.

## 7.D Data types, encodings and per-key memory

- **7.D1** Small aggregates use compact encodings ("up to 10 times less memory", average 5x) which convert to the normal encoding automatically once a threshold is crossed. Defaults on 8.10.3 (observed with `CONFIG GET`, and matching [conf] lines 2215-2332 and [doc:operate/oss_and_stack/management/optimization/memory-optimization/]): `hash-max-listpack-entries 512`, `hash-max-listpack-value 64` (bytes), `set-max-intset-entries 512`, `set-max-listpack-entries 128`, `set-max-listpack-value 64`, `zset-max-listpack-entries 128`, `zset-max-listpack-value 64`, `list-max-listpack-size -2` (8 KB nodes). Doc version notes: ziplist names to Redis <= 6.2; listpack from 7.0; set listpack from 7.2.
- **7.D2** **Observed conversions** (default thresholds): set of 512 integers `intset`, 513 `hashtable`; 4 members "1 2 3 abc" `listpack`; set of 128 strings `listpack`, 129 `hashtable`; zset of 128 `listpack`, 129 `skiplist`; hash of 512 fields `listpack`, 513 `hashtable`; a hash field value of 64 bytes stays `listpack`, 65 bytes converts to `hashtable`; **a hash does not convert back** after the large field is deleted (stayed `hashtable`); a list of 100 values of 100 bytes became `quicklist`; a list of 2 is `listpack`. Transcript "encoding conversion thresholds" and "one big hash".
- **7.D3** String encodings: `int` (integers fitting a signed 64-bit; observed `9223372036854775807` is `int`, `...808` is `embstr`, `007` is `embstr`), `embstr` (up to **44 bytes**: `OBJ_ENCODING_EMBSTR_SIZE_LIMIT 44`, chosen to fit a 64-byte jemalloc arena), `raw` otherwise; `APPEND`/`SETRANGE` make a string `raw`. Source: [src:object.c] line 337; [doc:commands/object-encoding/]; observed 44-byte string `embstr`, 45 `raw`.
- **7.D4** Per-key overhead, **Redis 8.2+ layout**: the key is embedded in the value object (`kvobj`, 16-byte object header + 1-byte key-header size + key bytes) and a small string whose key+value fit in one 64-byte cache line is stored in a single allocation; expiry adds an 8-byte field (reserved up front only for keys of 128+ bytes). Source: [src:object.c] lines 42-60, 155-200, 280-296. `kvobj` appears in `object.c` at tags 8.2.0 to 8.10.3 and **not** at 8.0.0 or 7.4.0 (checked by fetching the file at each tag). UNCONFIRMED: the release note or PR that introduced it; I found none in the release notes (searched for "embed", "kvobj"). So per-key overhead numbers from older articles (7.x, jemalloc) do not transfer.
- **7.D5** `MEMORY USAGE key` returns bytes for the key and value including administrative overhead (and allocator rounding); for nested types it samples (`SAMPLES`, default 5; `0` = all). Docs example with jemalloc, Redis 7.2: empty string key costs 56 bytes. Source: [doc:commands/memory-usage/]. **On this libc build** `MEMORY USAGE` of a 5-byte int value is 20 and of a 100-byte value under a 13-byte key is 144, so the doc's 56 does not reproduce here. Writers should quote the docs' jemalloc figure only with its source, and put "per-key overhead is roughly 50-60 bytes on libc, more on jemalloc size classes" as UNCONFIRMED for Linux/jemalloc.
- **7.D6** **Observed per-key and per-object memory** (`used_memory` delta over `--pipe` loads; 13-byte key `user:%08d`; libc):

  | Layout | Bytes per item (measured) |
  | --- | --- |
  | 200,000 strings, 100-byte values | 164.8 (`MEMORY USAGE` 144) |
  | same with `EX 3600` | 201.4 (`MEMORY USAGE` 152) (expiry costs about 37 bytes here) |
  | 200,000 hashes, 5 fields of 100-byte values (values over 64 bytes so `hashtable`) | 783.3 |
  | 200,000 objects as one hash of 5 fields, 20-byte values (`listpack`) | 207.3 |
  | the same 200,000 objects as 5 separate string keys | 390.4 |
  | 200,000 hashes, 5 named fields (`title_en`, `price_cents`, ...), 20-byte values, plain `listpack` | 255.3 (`MEMORY USAGE` 204) |
  | same with `hash-min-template-entries 3` (Redis 8.10 compact hash, encoding `template-listpack`) | 191.3 (`MEMORY USAGE` 154), about 25% less |

  Lessons for the article: (a) fixed per-key overhead dominates small values; (b) a small hash costs about half what separate keys cost (207 vs 390), matching the docs' "use hashes when possible" advice; (c) the saving vanishes when any field value exceeds 64 bytes or the field count exceeds 512 (783 B), so a writer must show the threshold; (d) per-key expiry has a measurable cost. 1,000,000 keys with 100-byte values used 152.4 MiB (159.6 million bytes; `used_memory_human` prints MiB), about 160 bytes per key; RSS was 168 million bytes on a fresh load (a later run on the same process, after earlier loads and flushes, showed 241 MiB, which is the effect described in 7.E).
- **7.D7** Redis 8.10 compact hashes: "a new hash encoding that reduces memory usage by storing hash field names just once for keys that share a schema" [rn:8.10]. Controlled by `hash-min-template-entries` (default **0 = off**), `hash-max-template-entries`; conversion is one-way; hashes with field expiry (`HEXPIRE`) are never converted. `INFO stats` shows `hash_templates`, `hash_template_keys`; `MEMORY USAGE` adds the key's share of the template. Source: [conf] lines 2224-2282; [src:config.c] lines 3594-3595; [doc:commands/memory-usage/] ("Added in Redis 8.10"). Observed above. Relevance: article 3 (strings vs hashes) should link here; this is off by default and so a tuning option, not default behaviour.
- **7.D8** Redis 8.6 release notes: "Substantial memory reduction for hashes (hashtable-encoded) and sorted sets (skiplist-encoded)" with no figures [rn:8.6.0]; `key-memory-histograms` config (#14695) collects memory histograms per type. UNCONFIRMED magnitude of the 8.6 saving; I did not measure it separately.
- **7.D9** Value-size effects (**observed**, `bigval2.py`, one GET round trip, loopback): 1 KB 0.15 ms; 100 KB 0.24 ms; 1 MB 0.43 ms; 10 MB 2.46 ms; 100 MB 19.97 ms, during which another client's PING waited up to 14.4 ms (worst-case sample; smaller values mostly produced no probe sample inside the window, so read the first rows as "no visible effect"). Server-side `GET` execution stayed ~1-2 µs regardless; the cost is copying and sending bytes. Max string 512 MB (`proto-max-bulk-len`) [doc:develop/reference/protocol-spec/].

## 7.E Memory accounting: `used_memory`, RSS, fragmentation

- **7.E1** Definitions (docs): `used_memory` is the sum of Redis's allocations; `used_memory_rss` is what the operating system reports as resident; `mem_fragmentation_ratio` = RSS / `used_memory`. Redis "will not always free up (return) memory to the OS when keys are removed ... how most malloc() implementations work"; so provision for **peak** usage; freed chunks get reused; and "the fragmentation ratio is not reliable when you had a memory usage that at the peak is much larger than the currently used memory". Source: [doc:operate/oss_and_stack/management/optimization/memory-optimization/] ("Memory allocation").
- **7.E2** **Observed (libc, macOS):** after loading 1,000,000 keys `used_memory` 159.6 million bytes, RSS 168.2 million, ratio 1.09; after `FLUSHALL` `used_memory` 1.55 million bytes but RSS 169.3 million, ratio **110.3**. An empty instance shows ratio 4.51 (4.1 MB RSS for 0.96 MB used), which is meaningless at that size. `MEMORY DOCTOR` declines to diagnose a near-empty instance. This is the docs' warning reproduced; do not present 110x as typical. UNCONFIRMED: how much a jemalloc Linux server would return to the OS after the same flush.
- **7.E3** Useful `INFO memory` fields observed: `used_memory_overhead`, `used_memory_dataset`, `allocator_allocated`, `allocator_active`, `allocator_resident`, `mem_clients_normal`, `mem_not_counted_for_evict`, `mem_aof_buffer`; `MEMORY STATS` gives `peak.allocated`, `total.allocated`, `startup.allocated`, `clients.normal`, etc. With `maxmemory` set, eviction/OOM decisions do not count AOF buffers and the part of replica output buffers beyond the backlog, to avoid an eviction feedback loop ([src:evict.c] lines 310-335; article 4 owns the policy).
- **7.E4** **Observed `noeviction` behaviour** (`maxmemory 2mb`, 100,000 pipelined `SET`s of 100-byte values): 96,409 of 100,000 replies were `-OOM command not allowed when used memory > 'maxmemory'.`; the first ~3,600 were accepted; reads still worked; `evicted_keys:0`. Source: transcript "OOM on writes".
- **7.E5** A client with a large unread reply uses server memory: see 8.B7 (205 MB observed). `maxmemory-clients` (7.0+, default 0 = off; docs suggest starting at `5%` for large deployments) caps aggregate client memory. [doc:develop/reference/clients/].
- **7.E6** Allocator note for the article: official Linux builds use jemalloc by default (source of the docs' numbers); this macOS build uses libc. UNCONFIRMED for each distro package (not checked); say "typically jemalloc" only if the writer verifies `INFO memory` `mem_allocator`.

## 7.F Latency sources and diagnosis

- **7.F1** The docs' checklist: avoid slow commands (use SLOWLOG); fork cost; disable transparent huge pages (`echo never > /sys/kernel/mm/transparent_hugepage/enabled`); measure intrinsic latency on the server (`redis-cli --intrinsic-latency 100`, which does not connect to Redis); enable the latency monitor. Source: [doc:operate/oss_and_stack/management/optimization/latency/].
- **7.F2** Network baseline per docs: "typical latency of a 1 Gbit/s network is about 200 us, while ... a Unix domain socket can be as low as 30 us"; virtualisation raises it. Same page.
- **7.F3** Fork: copying the page table. Docs' arithmetic: 24 GB / 4 kB pages x 8 bytes = 48 MB page table for a 24 GB instance. Docs' table (old measurements): e.g. physical Xeon 6.9 GB forked in 62 ms (9 ms/GB); old Xen EC2 6.1 GB in 1,460 ms; modern EC2 HVM 1 GB in 10 ms. **Observed here (macOS):** `BGSAVE` of a 152 MB dataset: `latest_fork_usec:6769` (6.8 ms; roughly 45 ms/GB, not comparable to Linux). With transparent huge pages enabled, copy-on-write after fork can copy "almost the whole process memory" (docs). Article 9 owns persistence; article 7 should only name fork as a latency source.
- **7.F4** Swapping: pages swapped out cause multi-millisecond stalls when touched; check `/proc/<pid>/smaps` `Swap:` and `vmstat` `si/so`. AOF `fsync` can stall (`appendfsync everysec` uses a background thread; `always` is slow). Latency doc. (Persistence semantics: article 9.)
- **7.F5** Tools, with defaults (observed on 8.10.3): `SLOWLOG GET/RESET`; `LATENCY` subsystem (`latency-monitor-threshold` default **0 = off**; with `CONFIG SET latency-monitor-threshold 50` the `KEYS *` run on 1M keys produced event `command` of 92 ms; `LATENCY LATEST`, `LATENCY HISTORY command`, `LATENCY DOCTOR` printed an English report with advice about slow commands and large objects); `INFO latencystats` (percentiles p50/p99/p99.9 per command, `latency-tracking yes` by default); `redis-cli --latency` (observed non-interactive output line `0.148 5.139 0.272 83`, which I read as min, max, average in ms and sample count; UNCONFIRMED column order, check `redis-cli --latency` interactively before quoting), `--latency-history`, `--intrinsic-latency` (observed on this laptop: average 0.96 µs per loop, worst run 6.6 ms, i.e. even an idle laptop has multi-millisecond scheduler hiccups). Redis 8.10 adds `redis-cli --latency-percentiles` [rn:8.10]. Sources: [doc:operate/oss_and_stack/management/optimization/latency-monitor/]; transcript "latency tooling".
- **7.F6** UNCONFIRMED: the `LATENCY DOCTOR` output wording is a joke persona ("Dave ...") in the source; avoid quoting it verbatim in a serious article.
- **7.F7** Redis 8.6 added a `HOTKEYS` command and the `volatile-lrm`/`allkeys-lrm` eviction policies [rn:8.6.0]. Not in this group's scope but absent from the coverage map; see "Gaps" below.

# Article 8: `clients-and-pipelining`

## 8.A Protocol and round trips

- **8.A1** RESP (Redis serialization protocol): requests are an **array of bulk strings** (`*3\r\n$3\r\nSET\r\n$5\r\nhello\r\n$5\r\nworld\r\n`); replies are typed by first byte (`+` simple string, `-` error, `:` integer, `$` bulk string, `*` array; RESP3 adds `_` null, `#` boolean, `,` double, `%` map, `~` set, `>` push and others). Designed to be "simple to implement, fast to parse, human readable"; length prefixes mean no scanning or escaping. Source: [doc:develop/reference/protocol-spec/]. **Observed** on the wire (`raw.py`): `+OK\r\n$5\r\nworld\r\n` for SET then GET; a missing key gives `$-1\r\n` in RESP2; after `HELLO 3` the server replied with a map (`%7`...) and the connection then uses `_\r\n` for null.
- **8.A2** Versions: RESP2 is the default for new connections and became standard in Redis 2.0; RESP3 opt-in via `HELLO 3` since 6.0; from 7.0 both can call all core commands; "unlikely that RESP2 will become entirely deprecated". Same source. **Observed** `HELLO 3` reply fields: `server redis, version 8.10.3, proto 3, id, mode standalone, role master, modules [...]`.
- **8.A3** Inline commands (a space-separated line, e.g. `PING\r\n`) are accepted, for telnet use. Observed: `PING\r\n` gives `+PONG\r\n`; `GET hello\r\n` works.
- **8.A4** A request costs one network round trip (RTT) plus server execution. Docs example: with an RTT of 250 ms "even if the server is able to process 100k requests per second, we'll be able to process at max four requests per second" per connection. Even on loopback "typically sub-millisecond ... will add up". Source: [doc:develop/using-commands/pipelining/].
- **8.A5** Redis docs' network baselines: 1 Gbit/s about 200 µs; Unix domain socket as low as 30 µs ([doc:.../latency/]); Unix sockets can give "around 50% more throughput than the TCP/IP loopback" on Linux, a benefit that shrinks with long pipelines ([doc:operate/oss_and_stack/management/optimization/benchmarks/]).
- **8.A6** **Observed model of sequential vs batched reads** (`rtt.py`, 1,000 keys of 100 bytes, loopback; client is Python so its RTT is 95 µs; a compiled client is faster):

  | Method | Median for 1,000 GETs |
  | --- | --- |
  | 1,000 sequential `GET`s | 94.6 ms |
  | 1,000 `GET`s pipelined as one batch | 1.22 ms |
  | pipelined in batches of 100 | 2.28 ms |
  | one `MGET` of 1,000 keys | 0.99 ms |
  | `MGET` in batches of 100 | 1.83 ms |
  | `MGET` in batches of 10 | 10.64 ms |

  Loopback `PING` round trip: median 95.3 µs, p99 161 µs. The numbers fit **time ~ (number of round trips) x RTT + (number of keys) x ~1 µs**: 100 round trips x 95 µs = 9.5 ms (observed 10.6); 10 x 95 µs = 0.95 ms plus ~0.9 ms of per-key work (observed 1.83). Server execution of a `GET` was ~1.4-2 µs (7.A7), so the round trip, not the server, is the cost. Derive the formula in the article and let the figure vary RTT, key count and batch size. For a production-like RTT the writer should **label the RTT illustrative** (for example 0.5 ms; UNCONFIRMED as a typical same-zone figure: I found no primary source, the docs only give 200 µs for 1 Gbit/s).
- **8.A7** Pipelining also reduces CPU on the server: without it each command costs a `read()` and a `write()` syscall ("the context switch is a huge speed penalty"); with it many commands share one read and replies share one write; throughput "initially increases almost linearly with longer pipelines, and eventually reaches 10 times the baseline". Docs' Ruby example on a Mac over loopback: 1.185 s vs 0.251 s for 10,000 `PING`s. Source: pipelining doc. **Observed with `redis-benchmark`** (50 clients, 100-byte values, io-threads 1): GET 135,612/s at `-P 1` vs 1,340,483/s at `-P 16` (9.9x). Transcript "baseline".
- **8.A8** Pipelining mechanics: send many commands without reading, then read all replies in order; there is no per-command acknowledgement. The server queues replies in memory, and the docs advise batches of "a reasonable number, for instance 10k commands". Pipelines are **not transactions**: "The commands in a pipelined request run in the order they are sent, but other clients' commands may be interleaved". Source: pipelining doc; [doc:develop/programmability/eval-intro/] ("`EVALSHA` in the context of pipelining"). **Observed:** three pipelined `INCR x` in one TCP write returned `:1 :2 :3` in order; an error in the middle of a pipeline returns an error reply for that command only and later commands still run.
- **8.A9** Pipelining versus scripting: pipelining cannot help when a later command needs an earlier reply ("read, compute, write"); scripts can. Same pipelining doc.
- **8.A10** Multi-key commands: `MGET`/`MSET` are O(N) and single round trip; `MGET` and `MSET` got batched prefetch in Redis 8.8 (#15133) [rn:8.8.0]. In a Redis Cluster all keys must be in one hash slot or the server returns `CROSSSLOT` (detail: article 10); the docs' latency guidance is to prefer aggregated commands over pipelining where possible and pipelining over round trips, and to keep connections long-lived ([doc:.../latency/]).
- **8.A11** Real-world batching figure for the page-fan-out story: Facebook's memcache paper reports a popular page loads on average **521 distinct items** from memcache (95th percentile 1,740), and that web servers build a DAG of data dependencies to fetch concurrently so that "on average these batches consist of 24 keys per request" (95th percentile 95 keys). Source: Nishtala et al., "Scaling Memcache at Facebook", NSDI 2013, section 3 and footnotes 1-2, https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf (read the PDF text). Same paper: gets that fail are treated as cache misses, and the web server then skips re-inserting into the cache to avoid adding load to an overloaded server (section 3.1). Useful for the "client behaviour on overload" point.
- **8.A12** Tail amplification model (derive, not cite): if each of `k` independent cache reads has probability `p` of being slow, a page that waits for all `k` is slow with probability `1 - (1-p)^k`. With `p` = 1%: `k` = 24 gives 21.4%; 100 gives 63.4%; 521 gives 99.5%. The 63% figure is also in Dean and Barroso, "The Tail at Scale", Communications of the ACM 56(2), 2013 (100 servers, 1-second 99th percentile). **UNCONFIRMED against the primary text:** I could not retrieve the paper's own text, only secondary summaries (e.g. https://blog.acolyer.org/2015/01/15/the-tail-at-scale/); the arithmetic is mine and exact. A writer who cites the paper should read it first.
- **8.A13** Connection setup is expensive, so keep connections long-lived. **Observed (loopback, plain TCP, no TLS, no AUTH):** persistent connection 105 µs per `GET`; new TCP connection per `GET` 340 µs (3.2x); adding `HELLO 3` per connection 375 µs. A real network adds TCP round trips, and TLS and `AUTH`/`HELLO`/`SELECT` add more, so the ratio is larger in production (UNCONFIRMED magnitude). Docs: "Do not systematically connect/disconnect ... Keep your connections as long lived as possible" ([doc:.../latency/]; also [doc:develop/clients/pools-and-muxing/]).

## 8.B Connections, pools, timeouts, retries, overload

- **8.B1** Two ways clients manage connections: **pooling** (a set of connections; borrow one per operation or transaction and return it) and **multiplexing** (one shared connection; "the multiplexer can often combine the commands into a pipeline"). Pooling clients named by the docs: redis-py, Jedis, go-redis; multiplexing: StackExchange.Redis; Lettuce supports both. Multiplexing "can't support the blocking 'pop' commands" (they would stall the shared connection). Source: [doc:develop/clients/pools-and-muxing/]. Implication for transactions: `WATCH`/`MULTI` state lives on a connection, so with a pool the sequence must stay on one borrowed connection.
- **8.B2** Server-side limits (observed on 8.10.3; docs [doc:develop/reference/clients/]): `maxclients` **10000** (clamped to the file-descriptor limit minus 32 reserved); at the limit the server replies `-ERR max number of clients reached` and closes (observed: with `maxclients 3` and one control connection already open, the first two new connections worked and the next three got that error and `INFO stats` `rejected_connections` rose to 4); `timeout 0` (idle clients are never closed unless set; observed: with `timeout 1` an idle client was closed after about a second; the docs warn timeouts are imprecise); `tcp-keepalive 300`; `client-output-buffer-limit normal 0 0 0 slave 268435456 67108864 60 pubsub 33554432 8388608 60`; `proto-max-bulk-len` 512 MB. Sizing arithmetic for the article (illustrative): 200 application instances x 50 pooled connections = 10,000, exactly `maxclients`; pool sizes multiply across instances.
- **8.B3** Docs inconsistency: [doc:develop/reference/clients/] says the 1 GB query-buffer limit is "non-configurable", but 8.10.3 has `client-query-buffer-limit` (default 1073741824, modifiable; [src:config.c] line 3610; observed with `CONFIG GET`). Trust the server.
- **8.B4** Client eviction: `maxmemory-clients` (Redis 7.0+; default 0 = off; "`5%`, for example, can be a good place to start" for large deployments) disconnects the clients using the most memory; `CLIENT NO-EVICT on` exempts a control connection. Source: clients doc.
- **8.B5** **Timeouts and side effects.** A client-side timeout does not stop the server executing a command. **Observed (`abandon.py`):** sending `INCR` and closing the socket straight away (normal FIN) executed the command in 200 of 200 trials (and every time in 3+3 earlier trials); an immediate close with a TCP reset (`SO_LINGER 0`) did not (0 of 3). In one early trial the command was not executed for a reason I did not establish (UNCONFIRMED); the safe statement is "may still execute". A slow script continued to completion after its client had gone. A retry of a non-idempotent `INCR` therefore double-counts; `SET` of the same value is safe to retry. Source for the principle: Marc Brooker, "Timeouts, retries, and backoff with jitter", Amazon Builders' Library, https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/ ("A timeout or failure doesn't necessarily mean that side effects haven't happened ... APIs with side effects aren't safe to retry unless they provide idempotency").
- **8.B6** **Retry amplification.** Same source: "If calls to a system are timing out, and that system is overloaded, retries can make the overload worse"; with a five-deep stack and three retries at each layer "the load on the database will increase 243x" (3^5); remedies: capped exponential backoff with jitter, a retry token bucket that limits retries locally, retry only at one layer; circuit breakers "introduce modal behavior". Choose timeouts from downstream latency percentiles (they use a 0.1% false-timeout rate against p99.9). For a cache client the consequence is: a short timeout and treating a failed read as a miss is usually safe for reads; retrying writes needs idempotency; retries during a Redis stall add load exactly when the server is slowest. Owner of breakers and load shedding: article 11.
- **8.B7** **Pipelined replies queue in server memory.** **Observed (`obuf.py`):** 20,000 pipelined `GET`s of a 10 KB value from a client that read nothing: `CLIENT LIST` showed `omem=204834960` bytes (about 205 MB) for that one client and `mem_clients_normal:204860048`; normal clients have no output limit (`client-output-buffer-limit normal 0 0 0`). After the client read 205,000,000 bytes `used_memory` returned to 1.24 MB. So: a slow or stuck reader plus a large pipeline can consume the server's memory; batch (docs: ~10k commands per batch) and bound reply sizes.
- **8.B8** Client library defaults vary by version and language; **don't generalise, advise setting timeouts and retries explicitly.** Read from source on 2026-10-27 (default branches, so for current releases): go-redis `options.go`: `ReadTimeout` 5 s, `DialTimeout` 5 s, `MaxRetries` 3 with 10 ms to 1 s backoff, `PoolSize` 10 x GOMAXPROCS (https://github.com/redis/go-redis/blob/master/options.go). redis-py (`redis/_defaults.py`, `__version__` 8.0.0 on master): socket timeout 5 s, default `Retry` with `ExponentialWithJitterBackoff` base 10 ms cap 1 s and up to 10 retries, connection pool `max_connections` 100 by default (https://github.com/redis/redis-py/blob/master/redis/_defaults.py). Jedis: `Protocol.DEFAULT_TIMEOUT = 2000` ms (https://github.com/redis/jedis/blob/master/src/main/java/redis/clients/jedis/Protocol.java). Lettuce: `RedisURI.DEFAULT_TIMEOUT = 60` seconds (https://github.com/redis/lettuce/blob/main/src/main/java/io/lettuce/core/RedisURI.java). UNCONFIRMED: the defaults of older released versions (I read default branches, not tags); do not state them as "the defaults" without checking the writer's chosen version.
- **8.B9** Observability of pipelining on the server (8.10.3): `INFO stats` has `avg_pipeline_length` (with `_sum` and `_cnt`); observed 4.2 after my Python tests; per-client `avg-pipeline-len-sum`/`-cnt` in `CLIENT INFO`. The 8.8 release notes call the same idea `commands_per_parse_batch_*`/`parse-batch-*`; the names changed before 8.10.3, so UNCONFIRMED which name appears in which release; use the 8.10.3 names. `CLIENT LIST` also shows `omem`, `qbuf`, `tot-cmds`, `io-thread`. Transcript "pipelining depth observability".
- **8.B10** Overload errors a client can meet: `-OOM command not allowed when used memory > 'maxmemory'` (writes under `noeviction`), `-BUSY Redis is busy running a script` (see 8.C), `-LOADING` (dataset loading after restart; UNCONFIRMED by observation, named in docs), `-ERR max number of clients reached`. Sources: observed ones above; [doc:develop/reference/clients/].

## 8.C Atomic operations

- **8.C1** Single commands are atomic (7.A4). The race to demonstrate: a read-modify-write (`GET`, add in the client, `SET`) from many clients loses updates. **Observed (`race.py`):** 20 client threads x 200 increments, expected 4,000: `GET`+`SET` ended at **376**; `INCR` 4,000; a `WATCH`/`MULTI`/`EXEC` retry loop 4,000 but with **55,790 retries** and 5.2 s (versus 0.07 s); an `EVAL` of `INCR` 4,000 in 0.07 s. The lost-update count varies from run to run (thread timing), so show it as one run. Contention model: with `n` clients competing for one key, each round one wins and the others fail, so at most `n - 1` failed attempts per success; the observed average was 13.9 failures per success against a bound of 19. The docs make the same point ("In many use cases, multiple clients will be accessing different keys, so collisions are unlikely"). Source: [doc:develop/using-commands/transactions/].
- **8.C2** `MULTI`/`EXEC` guarantees (docs): commands run "serialized and executed sequentially", no other client's request is served in the middle; either all run (after `EXEC`) or none (connection lost before `EXEC`). **No rollback**: "Redis does not support rollbacks of transactions since supporting rollbacks would have a significant impact on the simplicity and performance of Redis." **Observed (`multi.py`):** (a) `MULTI; SET k 1; INCR k; EXEC` returned `['OK', 2]`; (b) a queue-time error (unknown command) makes `EXEC` reply `-EXECABORT Transaction discarded because of previous errors.` and nothing ran (since 2.6.5); (c) a run-time error (`LPUSH` on a string) yields an error element in the `EXEC` array while the other commands **did** apply (`x`=1, `y`=2). You cannot branch on a read inside `MULTI` (reads reply `QUEUED`).
- **8.C3** `WATCH` gives optimistic locking (check-and-set): if any watched key is modified before `EXEC`, `EXEC` returns null and nothing runs. "Modification" includes writes by Redis itself (expiry, eviction) (since 6.0.9, "In Redis versions before 6.0.9, an expired key would not cause a transaction to be aborted"). All watches are cleared by `EXEC` (even when aborted), `UNWATCH`, or disconnect. **Observed:** another client's `SET ver 99` aborted `EXEC` (null reply) and `GET ver` stayed 99; a no-interference run applied; **a `SET` that wrote the same value still aborted the transaction** (key counts as touched); a `DEL` of a different, non-existent key did not. Source: transactions doc; observed.
- **8.C4** Lua scripts (`EVAL`, 2.6+; Lua 5.1): atomic, "all server activities are blocked during its entire runtime". Script cache is keyed by SHA1 and is "**always volatile**": lost on restart, failover or `SCRIPT FLUSH`; clients should use `EVALSHA` and on `NOSCRIPT` run `SCRIPT LOAD` then retry (most clients do this); in a pipeline or `MULTI`, `NOSCRIPT` can't be handled, so libraries fall back to `EVAL`. Declare every key via `KEYS` (needed for Cluster); scripts without `#!` can touch keys of different slots, scripts with a `#!lua` shebang cannot. Redis 7.0 added shebang flags (`no-writes`, `allow-oom`, `allow-stale`, ...). Replication is by effects (default since 5.0; verbatim removed in 7.0). Source: [doc:develop/programmability/eval-intro/]. **Observed (`lua.py`):** `EVALSHA` of an unloaded script gave `-NOSCRIPT No matching script. Please use EVAL.`; `SCRIPT LOAD` returned the SHA1 `78ca175d...`; a script error does **not** undo earlier writes (`before`=1 remained, `after` never ran); `redis.pcall` returns the error to the script instead of raising; `_VERSION` is `Lua 5.1`; `cjson` is available.
- **8.C5** Slow scripts block everyone. `busy-reply-threshold` (alias `lua-time-limit`; default **5000 ms**): after it elapses other clients get `-BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.` `SCRIPT KILL` works only if the script has **not yet written**; otherwise `-UNKILLABLE Sorry the script already executed write commands against the dataset...` and the only remedy is `SHUTDOWN NOSAVE`. **Observed (`busy.py`, threshold lowered to 200 ms):** a read-only infinite loop made `GET` and `PING` return `-BUSY`; `SCRIPT KILL` returned OK and the script's client got `Script killed by user with SCRIPT KILL`; a script that wrote then looped could not be killed (`UNKILLABLE`); `FUNCTION STATS` also returned `-BUSY` during it; the server had to be shut down with `SHUTDOWN NOSAVE`. Sources: eval-intro; [conf] line 1745; [src:config.c] line 3573; observed.
- **8.C6** Functions (`FUNCTION LOAD`, `FCALL`, `FCALL_RO`; **Redis 7.0+**): code is stored in the server, named, in libraries (`#!lua name=...`), persisted and replicated, so there is no `NOSCRIPT` problem; atomic like scripts. "When Redis is used as an ephemeral cache, additional mechanisms ... are required to make functions more durable" (reload at startup; `redis-cli --functions-rdb`). In Cluster, functions must be loaded on every node by the administrator. Flags such as `no-writes` allow `FCALL_RO` and use on read-only replicas. Source: [doc:develop/programmability/functions-intro/]. **Observed (`fn.py`):** `FUNCTION LOAD` returned the library name; `FCALL` ran it; loading the same library again failed with `Library 'cachelib' already exists` until `FUNCTION LOAD REPLACE`; `FCALL_RO` of a function without `no-writes` failed with `Can not execute a script with write flag using *_ro command.`
- **8.C7** **Worked example: compare-and-set for a versioned cached value** (used by article 5). Observed to work as a Lua script (`EVAL` with one key and arguments: unused expected value, new version, new payload) and as a function: store a hash `{v: version, data: payload}`; write only if the key is absent or the stored version is lower than the incoming one: sequence of versions 5, 4 (stale, rejected, returns 0), 6 left `v=6, data=price=11`; with `EVALSHA` after `SCRIPT LOAD`. The script text is in the transcript appendix (`lua.py`). Alternatives, with their limits:
  - `WATCH`/`MULTI`/`EXEC` loop: correct, 2+ round trips plus retries under contention (8.C1).
  - **Redis 8.4+ string compare-and-set:** `SET key value IFEQ expected`, `IFNE`, `IFDEQ digest`, `IFDNE digest`; `DELEX key IFEQ|IFNE|IFDEQ|IFDNE ...` (compare-and-delete); `DIGEST key` (XXH3 hash of a string value); `MSETEX` (set several keys with one expiry). The transactions doc calls this "much simpler and faster" than `WATCH`. Source: [doc:develop/using-commands/transactions/]; [rn:8.4.0] (#14435, #14434); [cdocs] (`since 8.4.0`). **Observed (`cas.py`):** `SET cv v2 IFEQ v1` gave OK when the value was `v1`, a null reply when it was not (or the key was missing); `DELEX cv IFEQ wrong` returned 0, `DELEX cv IFEQ v2` returned 1; `DIGEST d` returned `9555e8555c62dcfd`; `MSETEX 2 m1 a m2 b EX 60` set both with TTL 60. Limit for the worked example: `IFEQ` compares the **whole string value**, so a version-in-the-value design must read the full value or its digest first; "greater than" comparison (newest version wins) still needs a script or function. This is the clean way to release a lock only if you still own it (`DELEX lock IFEQ token`), observed working; correctness limits of Redis locks belong to article 6.
- **8.C8** Other single-command atomic primitives useful for caches, with introduction versions from `COMMAND DOCS` on 8.10.3: `SET key v NX|XX EX|PX ... GET KEEPTTL` (the `NX`+`PX` lock/claim idiom), `GETDEL` and `GETEX` (6.2), `INCR`/`INCRBY`, `SETNX`, `MSETNX`, `HGETEX`/`HSETEX` (8.0, hash-field expiry variants; article 3). Observed introduction versions are in the transcript "introduction versions and complexity".
- **8.C9** `EVAL`/functions interplay with `maxmemory`: when over `maxmemory` the first write that needs memory aborts the script (unless flagged), but a script whose first write frees memory (`DEL`) runs fully and may exceed the limit. Source: eval-intro ("Execution under low memory conditions").

## 8.D Serialisation cost on the client

- **8.D1** Format choice is article 3's; for article 8 the point is that client CPU for (de)serialisation is small relative to a round trip for small values but grows with size. **Observed (Python 3.14, `serdes.py`, an illustrative product object):** 551-byte object: `json.dumps` 2.4 µs, `json.loads` 2.1 µs, `pickle.dumps` 0.9 µs; 1.8 KB: 6.3 / 5.3 / 1.9 µs; 13.6 KB: 44.6 / 34.1 / 10.1 µs; `zlib` level 1 compress 6-15 µs and decompress 2-6 µs. Compressed size was 211 B / 320 B / 729 B respectively, but the test text is artificially repetitive (repeated review strings), so **do not quote compression ratios**. Compare with the 95 µs loopback round trip and ~0.5 ms+ real RTT: serialisation is not the bottleneck until values reach tens of KB. `pickle` is language-specific and unsafe on untrusted data (general knowledge; not tested here).
- **8.D2** Cost scales with bytes moved: see 7.D9 (10 MB value 2.5 ms round trip on loopback); pipelining many large values also hits 8.B7.

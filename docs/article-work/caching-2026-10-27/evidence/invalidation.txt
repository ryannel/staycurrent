## F2. Versioned values with tombstones: the script used in the article
# A value is a hash {version, value}; a tombstone is a hash {version} with no value field.
# Write if the cache has nothing, or an older version, or a tombstone of the same version.
local cur = tonumber(redis.call("HGET", KEYS[1], "version") or "-1")
local new = tonumber(ARGV[1])
local dead = redis.call("HEXISTS", KEYS[1], "value") == 0
if new > cur or (new == cur and dead and ARGV[2] ~= "") then
  redis.call("DEL", KEYS[1])
  if ARGV[2] == "" then redis.call("HSET", KEYS[1], "version", ARGV[1])
  else redis.call("HSET", KEYS[1], "version", ARGV[1], "value", ARGV[2]) end
  redis.call("EXPIRE", KEYS[1], ARGV[3])
  return 1
end
return 0

## Repair-1 sources read
- redis.io WAIT (since 3.0.0): returns the number of replicas that acknowledged the connection's previous writes, on success or timeout. 'WAIT does not make Redis a strongly consistent store'; a replica that received the write is more likely, 'but not guaranteed', to be promoted; 'it is possible to still lose a write synchronously replicated to multiple replicas.'
- redis.io replication (quoted by the technical reviewer, evidence/invalidation-review-1.txt): replication is asynchronous by default; with WAIT, acknowledged writes can still be lost during a failover.
- Failover itself was not observed: only one port was available. The article's failover paragraph rests on the documented semantics above.

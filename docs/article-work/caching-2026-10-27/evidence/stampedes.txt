# Every Redis command is real. The database is simulated: a 200 ms timer with a counter of queries and of
# queries running at once. Requests arrive as a seeded Poisson process at 500 a second and are spread
# at random over four application 'processes', each with its own Redis connection (one Node.js process
# stands in for all four). Latency is measured in the client and includes the simulated database.

################ K. Settling XFetch's expected stampede size (MODEL, not Redis)
# Vattani, Chierichetti and Lowenstein, PVLDB 8(8) 2015, read in full from https://www.vldb.org/pvldb/vol8/p886-vattani.pdf
# Definition 3: stampede size = number of processes regenerating in [Z, Z+1), Z = first regeneration, recompute = 1 unit.
# Theorem 7: Exp(lambda) is ((e^lambda - 1)(1/lambda + 1/e), (1/lambda) log n)-effective, where (s, gamma)-effective
# (Definition 5) means E[S] <= (1 + o(1)) s. At lambda = 1 the bound is (e - 1)(1 + 1/e) = e - 1/e = 2.35, the figure
# the paper's text quotes ('e - 1/e ~ 2.4 processes'). It comes from Lemma 16's series estimate. My reading (not
# confirmed with the authors): that proof bounds E[S | T in (nu-i-1, nu-i)] by n e^(-lambda(nu-i)) = e^(lambda i),
# which uses the smallest per-request rebuild probability in the stampede window rather than the largest.
# Direct derivation (article): rebuild starts are a Poisson process with intensity n e^(-y/beta) at y units before
# expiry; the intensity still ahead at the first start is Exp(1) with mean 1; the window of one rebuild after it adds
# (e^(1/beta) - 1) times that; so E[S] = 1 + (e^(1/beta) - 1) = e^(1/beta), for n large. Lead: beta(ln(n beta) + 0.5772).

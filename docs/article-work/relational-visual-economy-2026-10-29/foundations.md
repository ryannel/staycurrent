## Findings to act on

No Critical finding was established. The following Medium findings concern substantial reader effort or a missing visual explanation, rather than stylistic uniformity.

**F1 — Medium: two consecutive modelling players rebuild essentially the same answer.** In `/learn/databases/relational/modelling/`, Figures 5 and 6 both move from duplicated purchase/customer facts to the same separate homes for customers, orders, lines and products. The first already shows a customer correction leaving inconsistent copies; the next repeats the separation and reaches another full schema display. Normal-form distinctions deserve explanation, but replaying the whole destination does not make those distinctions clearer. Keep one evolving example and let the next stage expose only the new dependency being removed, or replace the second full player with a compact dependency annotation on the first result. Preserve the difference between an agreed sale price and the current catalogue price.

**F2 — Medium: relationship diagrams sometimes leave the relationship to prose labels.** In modelling Figure 3, the stacked entity cards and cardinality words require the reader to reconstruct which relationship each label describes. Figure 11 calls its comparison a tree and a graph, but the tree side is effectively a list of nodes with parent labels. Use actual keyed connections for the schema and a tiny three-node tree beside the multiple-parent graph. These are cases where a few edges would remove reading, not add ornament. The article's candidate-key comparison and product/subtype form already earn their space and should remain.

**F3 — Medium: constraints uses a procedural player for a small truth comparison.** `/learn/databases/relational/constraints/` Figure 1 combines quantity 2, 0 or NULL with CHECK alone or NOT NULL plus CHECK, then makes the reader step through each selected case. The tall drawing repeatedly includes unaffected stored order rows, separating controls from the explanation. A six-case comparison, or an immediate result beside the selected candidate, would expose the important distinction with less effort. Explicitly retain that CHECK accepts unknown while NOT NULL rejects NULL. Figure 3 has the same opportunity: place the separate-reference and composite-reference checks against the same proposed `(tenant 10, customer 4)` together, so the missing pair is immediately visible. This recommendation does not extend to Figure 5: immediate versus deferred checking actually depends on when checking occurs.

**F4 — Medium: a window-total player mostly reveals emphasis, not new understanding.** `/learn/databases/relational/aggregates-and-windows/` Figure 3 already displays the input rows and repeated partition totals. Its three stages highlight P3, P7 and P9 in turn and restate each sum. The central lesson—preserve every row while attaching its partition total—is available in the initial table. Keep that table with one partition annotated, or let the reader directly choose a partition without playback chrome. Retain the separate frame player: moving the current row and changing ROWS/RANGE changes which rows contribute and genuinely benefits from interaction.

**F5 — Medium: completed transaction views erase the cause of their result.** `/learn/databases/relational/transaction-boundaries/` Figures 2 and 3 replace the actors' earlier reads and writes with the latest status. At the end of the mug race, acceptance or rollback remains but the earlier shared read and waiting sequence have gone. In the two-read report example, the final read remains while the earlier snapshot observation needed for comparison is no longer visible. A compact persistent event axis, with a commit marker and snapshot spans, would explain the final outcome without requiring Back or replay. `/learn/databases/relational/locks-and-deadlocks/` already demonstrates a better local form: aligned event rows preserve both actors' history. This is a form recommendation, not a request to repeat all lock details in the parent article.

**F6 — Medium: repeated-write comparison asks the reader to remember its missing intermediate state.** `/learn/databases/relational/updates-and-imports/` Figure 2 contrasts assigning a price with incrementing stock using separate selected runs. The final state alone cannot show why repetition is harmless in one case and changes the result in the other. A two-row comparison with before / once / twice columns would make `22 → 22 → 22` and `1 → 3 → 5` directly comparable. Remove unchanged catalogue/line facts from that compact comparison. The import-progress player has a different purpose and should remain: rejection, durable progress, interruption and resumed work are genuinely temporal.

**F7 — Medium: the join-method player names the mechanism more than it draws it.** `/learn/databases/relational/query-execution/` Figure 2 uses substantially the same ordered input cards and growing output for nested-loop, hash and merge methods. In the observed hash probe state, a caption mentions the candidate bucket, but no bucket is visible. In the merge state, text says to advance both sides, but the form is still selected cards and output rows. If the intended lesson is different physical methods producing the same occurrences, draw the distinguishing operation: repeated inner lookup, build/probe structure, and paired ordered cursors. If the intended lesson is only result equivalence, use a smaller static comparison and leave the mechanisms to a deeper explanation. Keep the small dataset and the common output; they remove unnecessary setup.

The following Low findings are optional simplifications; they should not trigger broad redesign.

- **Overview Figure 4**, `/learn/databases/relational/`: ten tall numbered actor boxes contain repeated reads, holding states and initially empty slots. Keep the persistent history but compress it to aligned event rows with a wait span. The final guarded path is understandable; its space cost is the issue.
- **Normalisation Figure 2**, `/learn/databases/relational/normalisation/`: the same lossy order/customer/time split has already been demonstrated in modelling Figure 7. A compact reminder before the new chase demonstration would save a second full reconstruction. The chase itself adds a new proof technique and should remain.
- **Values Figures 5–6**, `/learn/databases/relational/values/`: the calendar-versus-duration comparison relies on text saying that an hour repeats; a short clock timeline could make the 25-hour/24-hour difference visible. Splitting “Green tea, 50 g” into name, amount and unit needs only a compact inline breakdown, not a large panel.
- **Application SQL Figure 3**, `/learn/databases/relational/application-sql/`: the query-count and assembled-result comparison succeeds. The caption also mentions repeated order columns in joined transport, which the shared assembled output does not show. Add a tiny joined-transport excerpt only if that trade-off is intended to be part of this figure's lesson; otherwise leave it to the adjacent prose. This is not a Medium defect merely because the figure omits a secondary cost.
- **Indexes Figure 5**, `/learn/databases/relational/indexes/`: downward arrows beside three index alternatives can suggest a sequential path. A shared update branching to three alternatives, or simply a comparison table without arrows, would better match the meaning.
- **Storage Figure 6**, `/learn/databases/relational/storage-and-durability/`: a two-by-two set of text cards is called a work map, but the logical update has the same visual status as its three consequences. A small source-to-three-consequences form would express the relationship more directly; a concise list would also be sufficient.

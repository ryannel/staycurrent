Databases and storage

# Maintaining indexes
 Companion to IndexesAbout 28 minutesPostgreSQL 18, with InnoDB (MySQL 8.4) and SQLite comparisons   
An index is built once and then lives in the database for years, while the table under it is inserted into, updated and deleted from. Three things drift. The index can end up much larger than the rows it covers. The statistics the planner uses to decide whether to use it can fall behind the data. And the set of indexes itself collects members that nothing uses, duplicates and half-finished builds. This companion to Indexes is about noticing each of these, choosing the repair, and knowing what the repair locks while it runs. 
It follows an orders table that has grown for a year. Every example is a question an on-call engineer might ask: why is this index 200 MB for a table with 100,000 live rows, can it be rebuilt while the shop is taking orders, why did a query switch to a sequential scan after last night's import, and which of the thirteen indexes on this table can go. PostgreSQL 18 is the worked example. The text says where InnoDB, MySQL 8.4’s storage engine, and SQLite differ in ways that change what you would do. The measurements come from PostgreSQL 18.6 and SQLite 3.54.0 on one laptop, with a million-row table. They show how big things are and what blocks what, not how fast anything runs. MySQL was not run for this article; its behaviour is as the 8.4 manual describes it.

## Why an index stays large after deletes 
A B-tree index stores its entries in fixed-size pages, sorted by key, and each page holds as many entries as fit. Deleting a row removes its entries from the index, and what that frees is space inside a page. Whether a whole page becomes free, and whether the file gets smaller, depends on how the deletes were spread. Indexes introduced the pages and splits; this section follows what happens when entries leave. 

### Pages that empty and pages that thin out 
Two deletions with the same row count leave very different indexes. To see this, take a table of one million orders with indexes on id (the primary key), placed_at (increasing with id), customer_id and total (both effectively random). Make two copies. In one, delete 90% of the rows at random. In the other, delete the oldest 90% by id, as a retention job would. Run VACUUM on both, which is the step that removes dead index entries. 
  Index state after deleting 90% of one million rows and running VACUUM (PostgreSQL 18.6) 
 | Index | Size before and after | Leaf pages in use | Pages marked deleted | Average leaf density  
 | Primary key, 90% deleted at random | 21 MB, 21 MB | 2,733 | 0 | 9% 
 | customer_id, deleted at random | 7.8 MB, 7.8 MB | 969 | 0 | 19% 
 | Primary key, oldest 90% deleted | 21 MB, 21 MB | 274 | 2,467 | 90% 
 | total, oldest 90% deleted | 30 MB, 30 MB | 3,832 | 0 | 6.7%    
No index file got smaller. In the first row, the random deletes left every leaf page about a tenth full. No page was entirely empty, so no page could be released: a tenth of the entries are still scattered through all 2,733 pages. In the third row, deleting the oldest keys emptied whole pages. PostgreSQL took 2,467 of them out of the tree and marked them deleted, and the 274 pages still in use are 90% full. That index is not bloated in the sense that matters, because the empty pages are available for new entries. It is still 21 MB on disk. The total index was in the same table as the tidy primary key and is as bad as the random ones, because its keys are unrelated to age. Which indexes on a table go sparse depends on how the key relates to whatever decides which rows are deleted. 
PostgreSQL’s routine reindexing page states the rule: pages that have become completely empty are reclaimed for reuse, but a page that keeps a few entries stays allocated, so patterns where most but not all keys in each range are deleted waste space. The table behind these indexes behaved the same way. Its 96 MB file did not shrink after VACUUM either; vacuum makes the space reusable, it does not return it. Row versions and vacuum explains why dead rows linger until vacuum and what can hold it back. 

### When freed pages come back into use 
A page marked deleted is not available at once. After the first VACUUM of the oldest-deleted copy, pg_freespace listed no free pages in the primary-key index. Inserting 900,000 new rows grew it from 21 MB to 41 MB, as if nothing had been freed. A second VACUUM listed all 2,467 pages as free, and a further 500,000 inserts left the index at 41 MB. The nbtree README gives the reason. A deleted page is stamped with a transaction ID, and it can be reused only once no running scan could still follow a link into it, which means every transaction that was running at that point has finished. A VACUUM places a page in the free space map at its end only if that is already true. On a busy system it often is by the next run. On an idle copy nothing has moved, so two VACUUMs back to back free nothing. Here the 900,000 inserts were the newer transactions that started and finished between the two runs. 
The practical reading is that an index which stays flat while the table churns is healthy, and that one vacuum after a large delete is not the end of the story. If you delete a lot and then insert a lot, expect the file to settle at roughly the peak. If the work is a one-off cleanup after which the table stays small, the space is wasted and a rebuild is the way to recover it. 

### Updates leave debris too 
Deletes are the clearest case, but any update that cannot be a heap-only update (the HOT updates in Indexes) adds a new entry to every index and leaves the old one for vacuum. PostgreSQL has two defences. Bottom-up deletion removes entries it can see are dead when a leaf page is about to split because of that churn, and deduplication stores a repeated key once with a list of row locations when the page would otherwise split. The B-tree implementation chapter says an index can stay the same size under constant update churn. Neither helps the scattered-delete case above. Deduplication is also switched off for some types, numeric and floating-point columns among them, and for INCLUDE indexes. 

### InnoDB and SQLite 
InnoDB deletes in two steps. A delete marks the record, and a background purge removes it once no transaction can see it. When a delete leaves an index page less than half full (the MERGE_THRESHOLD, 50 by default), InnoDB tries to merge it with a neighbour. So InnoDB resists the 10%-full pages above more than PostgreSQL does, though not completely: its pages vary between half and fully full, and the manual says it is difficult to say how much space a table should take. A secondary index is a separate tree, but the table itself is also an index, ordered by primary key, so its sparse pages count toward the same problem. Lowering MERGE_THRESHOLD makes merging happen later and leaves more empty space, so the manual presents it as a trade, not a fix. 
SQLite puts a page that empties onto a freelist and reuses it before it grows the file. In the SQLite run, deleting 90% of a million rows left the file at its original 27,705 pages, 23,741 of them on the freelist. The random-key indexes had been compacted somewhat, to about 46% full, but not rebuilt. As in PostgreSQL, the file stays the size of its peak until something rewrites it.  

## Measuring size and bloat 
Bloat is not a number any engine reports. What each gives you is size and, in two of the three, how full the pages are. The judgement is yours: is this index larger than it needs to be, and will the space come back into use by itself? 

### How large should it be? 
Divide the index size by the number of live rows. The million-row primary key was 21 MB, about 22 bytes an entry, and after a rebuild the 100,000 rows that survived the random delete took 2.2 MB, the same 22 bytes. That ratio is your baseline for an index with that key. A rebuilt PostgreSQL B-tree fills its leaf pages to 90% (the default fillfactor), and InnoDB fills a rebuilt clustered index to about 15/16, per its manual, so the table is about 93% full after a rebuild. A key twice as wide costs roughly twice as much per entry, and an index on a column that is mostly NULL or on a partial predicate covers fewer rows than the table has. 
Two cheap checks use only sizes. Compare the index with the same ratio on a fresh copy, such as a database restored from a logical dump, which builds every index from scratch. And watch growth: an index that grows much faster than the table’s live row count, or that keeps growing while the row count is flat, has pages that are not being reused. 

### PostgreSQL 
pg_relation_size gives the size of any relation in bytes, and pg_stat_user_indexes adds how many times each index has been scanned. Put them in one query and the biggest, least-used indexes come first. 

-- Size of every index on a table, with how often it has been used
SELECT i.indexrelid::regclass AS index,
       pg_size_pretty(pg_relation_size(i.indexrelid)) AS size,
       s.idx_scan, s.last_idx_scan
FROM pg_index i
JOIN pg_stat_user_indexes s ON s.indexrelid = i.indexrelid
WHERE i.indrelid = 'o_rand'::regclass
ORDER BY pg_relation_size(i.indexrelid) DESC; 
To see inside an index, the pgstattuple extension ships with PostgreSQL and provides pgstatindex. It reads the whole index, so run it off-peak on a large one, and it needs the pg_stat_scan_tables role. 

CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT tree_level, index_size, leaf_pages, empty_pages, deleted_pages,
       avg_leaf_density, leaf_fragmentation
FROM pgstatindex('o_rand_customer_idx');
--  tree_level | index_size | leaf_pages | empty_pages | deleted_pages | avg_leaf_density | leaf_fragmentation
-- ------------+------------+------------+-------------+---------------+------------------+--------------------
--           2 |    7987200 |        969 |           0 |             0 |            19.19 |                  0 
avg_leaf_density is the average percentage of each leaf page in use. A rebuilt index reads about 90, and the table above shows 9 and 19. deleted_pages and empty_pages count pages that are out of the tree and waiting for reuse. leaf_fragmentation measures how far the leaf pages' physical order has drifted from key order; it matters for range scans, less for space. A density in the teens alongside a size that is many times the baseline is the signature of the random-delete case. A large deleted_pages with a dense remainder is the other case, where the space is reusable and the question is whether you need it back. 

### InnoDB 
InnoDB keeps index sizes in its persistent statistics. The size row of mysql.innodb_index_stats is the index’s total page count, and n_leaf_pages is the leaves. Multiply by the page size, 16 KB by default. 

-- Pages in each index of one table, from InnoDB's persistent statistics
SELECT index_name, stat_value * @@innodb_page_size AS bytes
FROM mysql.innodb_index_stats
WHERE database_name = 'shop' AND table_name = 'orders'
  AND stat_name = 'size';

-- 'n_leaf_pages' is the same table's leaf-page count, and ANALYZE TABLE
-- refreshes both numbers. 
These are page counts as of the last statistics update, refreshed when the table changes by more than 10% or when you run ANALYZE TABLE. size counts allocated pages, so it does not fall when rows are deleted. There is no page-density report in the server, so judge by size per live row against a baseline. The table’s clustered index is the table itself, and appears here under PRIMARY. 

### SQLite 
The dbstat virtual table gives one row per page, with the bytes in use and unused, and exists only when SQLite was compiled with SQLITE_ENABLE_DBSTAT_VTAB. It was available in the shell used for this article, and sqlite3_analyzer reports from it. PRAGMA freelist_count against page_count says how much of the file is empty. 

-- Pages and how full they are, per table and index (needs the dbstat table)
SELECT name, count(*) AS pages,
       round(avg(100.0 * (pgsize - unused) / pgsize), 1) AS percent_used
FROM dbstat
GROUP BY name
ORDER BY pages DESC;

PRAGMA page_count;       -- pages in the file
PRAGMA freelist_count;   -- pages in the file that hold nothing  

## Rebuilding an index 
A rebuild reads the live entries, sorts them and writes a fresh index with full pages, then retires the old one. It is the one operation that returns the space in a thin index, and it costs a full scan of the table (or index) plus the writes, so the questions are when it is worth it and what it holds up. 

### When a rebuild is worth doing 
Not on a calendar. A scheduled weekly reindex of every index spends I/O and WAL, and for most indexes it changes nothing. The manual states a modest benefit, that a fresh B-tree is slightly faster to scan because neighbouring pages are physically adjacent, and the case for a rebuild is mainly space. Rebuild when you have measured an index at a fraction of its baseline size, the table is not about to grow back into it, and the space matters: disk close to full, backups and replicas that copy it, or a working set that no longer fits in the buffer pool because of half-empty pages (The buffer pool shows why that costs reads). If the rows are about to return, as in a table that is purged and refilled each month, the space is already reusable and a rebuild saves nothing. 

### PostgreSQL: REINDEX and what it locks 

-- One index, writes allowed throughout (cannot run inside BEGIN ... COMMIT)
REINDEX INDEX CONCURRENTLY o_rand_customer_idx;

-- Every index on a table, one after another
REINDEX TABLE CONCURRENTLY o_rand;

-- The blocking form: faster, but writes wait and so do most queries
REINDEX INDEX o_rand_customer_idx; 
Plain REINDEX is the simple one. In the trial it held a ShareLock on the table, which stopped inserts, and an AccessExclusiveLock on the index itself. A query using the index waited, which is expected. So did EXPLAIN of a primary-key lookup on the same table, because the planner takes a lock on every index of a table when it plans, and the manual says REINDEX blocks nearly every query that is not a cached plan. Use it on a table nothing is using, such as one in a maintenance window or a new staging copy. 
REINDEX ... CONCURRENTLY takes no lock that stops INSERT, UPDATE or DELETE. It builds a second copy of the index while writes continue, catches up with the rows written meanwhile, swaps the new one in and drops the old. This is the mechanism of CREATE INDEX CONCURRENTLY, which Indexes in PostgreSQL explains, and it has the same costs:  
- It needs room for both copies. Until the swap, the old and new index coexist. Check free disk against the size of the largest index being rebuilt, and note that REINDEX TABLE CONCURRENTLY builds new copies of all the table’s indexes before it drops any old one, so it needs room for all of them at once. 
- It writes the index twice over. Rebuilding an 11 MB index on customer_id, in a table of 1.5 million rows, wrote about 10 MB of write-ahead log, whether concurrent or not, and the log is what a standby replays. A large rebuild is a burst of replication traffic. 
- It waits for older transactions. The build must wait for every transaction that started before a step, so a long-running one stalls it. In the trial, a transaction left open for seven seconds kept the rebuild in wait_event = virtualxid until it ended, while inserts from other sessions went through. The query below shows a rebuild in that state. 
- It takes a ShareUpdateExclusiveLock. That does not block ordinary reads and writes, but it blocks other schema changes on the table, and only one concurrent build per table can run at a time. A rebuild during a migration will collide with it; Schema locks and timeouts covers bounding how long a command waits. 
- It cannot run in a transaction block. It runs as several transactions, which is a problem for migration tools that wrap every migration in one.  

-- Is the rebuild running, or waiting for an older transaction?
SELECT pid, state, wait_event_type, wait_event, left(query, 40) AS query
FROM pg_stat_activity
WHERE query ILIKE 'reindex%' AND pid <> pg_backend_pid();
-- pid  | state  | wait_event_type | wait_event | query
-- 4121 | active | Lock            | virtualxid | reindex index concurrently o_rand_cust 
Several things are not rebuildable concurrently: an index behind an exclusion constraint (skipped when you reindex a table, an error for that single index), and the system catalogs. For the heaviest case, VACUUM FULL and CLUSTER rewrite the table and rebuild all its indexes, but they hold an AccessExclusiveLock on the table for the duration. For one thin index, REINDEX CONCURRENTLY is the narrower tool. 
The rebuild the trial ran on the randomly emptied table took each index from its old size to 2.2 MB (the primary key, from 21 MB), 1.7 MB (customer_id, from 7.8 MB) and 2.2 MB each for placed_at and total. Together the four indexes went from about 72 MB to 8 MB, and the relation total from 169 MB to about 104 MB. The table’s own 96 MB was not touched, since REINDEX only rebuilds indexes. Recovering the table’s space is a separate decision, with VACUUM FULL or an external tool such as pg_repack that rewrites it with a shorter lock. 

### When a concurrent rebuild or build fails 
A concurrent command that stops part way, cancelled by a timeout, a deadlock or a unique violation, does not undo everything. It leaves an index that queries ignore but writes still maintain, so it costs you the write overhead for nothing. A cancelled REINDEX CONCURRENTLY in the trial left o_rand_cust_ccnew next to the intact original; a failed CREATE UNIQUE INDEX CONCURRENTLY over a column with duplicates left the new index too. Look for them with pg_index: 

-- Indexes that queries ignore and writes still maintain
SELECT c.relname AS index, i.indrelid::regclass AS table_name,
       i.indisvalid, i.indisready
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
WHERE NOT i.indisvalid;
--  index              | table_name | indisvalid | indisready
-- --------------------+------------+------------+-----------
--  o_rand_cust_ccnew  | o_rand     | f          | t

DROP INDEX CONCURRENTLY o_rand_cust_ccnew; 
The two columns say different things. indisvalid = false means queries do not use it. indisready = true means writes still update it, as with the _ccnew leftover, and so it is costing every write. The manual names the leftovers: a _ccnew index is the unfinished new one, and the fix is to drop it and run the rebuild again. A _ccold index is the old one that could not be dropped after a successful swap, and is safe to drop. In psql, \d table marks them INVALID. Check for them after any failed migration, and consider a monitoring query that alerts on any row. 

### InnoDB: the table is rebuilt, not one index 
InnoDB has no statement that rebuilds one secondary index. The tools rebuild the table and with it every index. OPTIMIZE TABLE is mapped to ALTER TABLE ... FORCE for InnoDB, which copies the rows into a new table file in place using online DDL: reads and writes continue, with a brief exclusive metadata lock when it starts and again when it commits. Because the commit waits for older transactions, a long-running one can hold up the finish, much as it holds up REINDEX CONCURRENTLY. Tables with a FULLTEXT index fall back to a table copy that blocks writes. OPTIMIZE TABLE accepts no ALGORITHM or LOCK clause, so if you want the server to refuse anything that would block, use the ALTER form. 

-- Rebuilds the table and every index on it, in place; writes continue
OPTIMIZE TABLE orders;

-- The same rebuild, spelled so you can state the locking you require
ALTER TABLE orders FORCE, ALGORITHM=INPLACE, LOCK=NONE; 
With one file per table, which is the default, the old file’s space goes back to the operating system once the new one is in place. A rebuild needs disk space for the second copy and generates redo log in proportion to the table, and a replica that applies the statement repeats the work; large rebuilds are a reason replicas lag. External tools such as gh-ost and pt-online-schema-change exist to run the same rebuild with finer control. To rebuild just one index, drop and re-add it in one statement, ALTER TABLE orders DROP INDEX i, ADD INDEX i (...). Two separate statements would leave a window with no index. The manual lists both operations as in place and allowing concurrent changes, and nothing else is rebuilt. 

### SQLite: REINDEX frees pages, VACUUM shrinks the file 
REINDEX in SQLite deletes and recreates indexes. The manual gives changed collations and changed expression-index functions as its reasons, and as a space tool it does less than it might: in the trial it rebuilt o_customer from 46% to 99% full, but the file stayed 27,705 pages and the freelist grew by 328 pages. The space is reusable inside the file, not returned. Only VACUUM rewrites the file, here from 27,705 pages to 2,674, and every b-tree came out 99% full. 

REINDEX o_customer_idx;   -- rebuild one index; freed pages go to the freelist
VACUUM;                   -- rewrite the whole file; needs free disk, shrinks it 
SQLite has one writer at a time. A transaction that held REINDEX open for four seconds let a second connection read but made its write fail with database is locked (with a busy timeout of zero), in both rollback-journal and WAL modes. VACUUM is a write that copies the entire database to a temporary file and back, so it can need up to twice the database size in free disk and it fails if the connection has an open transaction. VACUUM INTO 'file' writes a compacted copy without touching the original, which suits a nightly compacted backup. 

### The rebuild options side by side 
  What each rebuild does to the file, to writers and to the disk 
 | Operation | What it rebuilds | Writes during it | Needs  
 | PostgreSQL REINDEX INDEX | One index | Blocked, and most queries on the table too | Room for the new copy 
 | PostgreSQL REINDEX INDEX CONCURRENTLY | One index | Allowed; waits for older transactions; blocks other schema changes | Room for both copies; about the index size in WAL 
 | PostgreSQL VACUUM FULL | Table and all indexes | Blocked, reads too | Room for the new table 
 | InnoDB OPTIMIZE TABLE or ALTER TABLE ... FORCE | Table and all indexes | Allowed; brief exclusive locks at start and end | Room for the new file; redo log 
 | SQLite REINDEX | One index, or all of a table’s | One writer at a time; others wait or fail | None extra; the file does not shrink 
 | SQLite VACUUM | The whole file | Same, for the whole time | Up to twice the file in free disk     

## Building new indexes safely 
A new index is also a maintenance operation, and the lock it takes is the first thing to know. The engines differ.  
- PostgreSQL: CREATE INDEX blocks writes until it finishes, CREATE INDEX CONCURRENTLY does not, at the price of a second scan and a wait for older transactions. Indexes in PostgreSQL explains why. 
- InnoDB: adding a secondary index is an in-place operation that allows concurrent changes and does not rebuild the table. The statement finishes only after the transactions that were using the table when it started complete, so one long transaction can leave it waiting. While it runs, InnoDB records concurrent changes in a log whose size innodb_online_alter_log_max_size limits, and the build fails when that log fills. 
- SQLite: the build holds the single write lock until it finishes, so every other writer waits for the whole build.  
For all three, put a bound on how long the command may wait for its locks, as Schema locks and timeouts describes, because a command stuck behind a long transaction holds up everything queued after it. 

### Time and memory 
A build sorts every entry. In PostgreSQL the sort uses maintenance_work_mem, which defaults to 64 MB, and a B-tree build can use max_parallel_maintenance_workers parallel workers, default 2. Raising them for the session that runs the build is the usual way to shorten it, bearing in mind that the memory limit applies to the command as a whole and that the build competes with production traffic for CPU and I/O. 

-- PostgreSQL: for this session's build only
SET maintenance_work_mem = '1GB';             -- default 64MB
SET max_parallel_maintenance_workers = 4;     -- default 2
CREATE INDEX CONCURRENTLY orders_customer_placed_idx
  ON orders (customer_id, placed_at); 
InnoDB has settings for the same trade, innodb_ddl_buffer_size and innodb_ddl_threads for the session and innodb_sort_buffer_size for the server, which the manual’s InnoDB parameters page documents. 

### Replicas 
A build runs on the primary and then reaches each replica. PostgreSQL’s physical standbys replay the write-ahead log the build produced, which for a rebuild was about the size of the index. InnoDB replicas normally run the same ALTER themselves, one statement at a time, so a long build on the primary becomes a long stretch on each replica during which later changes queue. Watch replication delay while a large build runs, and for InnoDB prefer to schedule a heavy one where lag is tolerable.  

## Keeping statistics current 
An index only helps when the planner decides to use it, and the planner decides from statistics: row counts, the number of distinct values in each column, and the most common values and their frequencies. Statistics are a sample taken at one moment. When the data changes a lot and they do not, the planner estimates from a table that no longer exists. Plans and changing data and Planner estimates show how those estimates become plans; this section is about keeping them fresh in each engine. 

### PostgreSQL: autovacuum analyzes, eventually 
PostgreSQL’s autovacuum process runs ANALYZE on a table once the rows inserted, updated or deleted since the last one exceed autovacuum_analyze_threshold (50) plus autovacuum_analyze_scale_factor (0.1) times the table’s row count. A table of a million rows triggers after about 100,000 changes, and a worker picks it up on a later scheduled pass, not at that moment. Two situations leave the statistics wrong in the meantime.  
- Right after a bulk load. The table is large but has never been analyzed, or has statistics from when it was empty. In the trial, a freshly loaded table of 500,000 rows with autovacuum off had no row estimate at all, and the planner guessed 2,301 rows for both state = 'done' (really 499,500) and state = 'queued' (really 500). It chose an index-driven bitmap scan for the half-million-row query. After ANALYZE it estimated 499,617 and chose a sequential scan. 
- A partitioned parent. Autovacuum never analyzes a partitioned table itself, only its partitions. The manual tells you to run ANALYZE on the parent after the first load and whenever the distribution changes much.  

-- jobs: 500,000 rows, 499,500 with state = 'done', loaded just now
EXPLAIN (ANALYZE, TIMING OFF) SELECT * FROM jobs WHERE state = 'done';

-- Before ANALYZE
Bitmap Heap Scan on jobs  (cost=26.26..4378.42 rows=2301 width=72)
                          (actual rows=499500.00 loops=1)
  ->  Bitmap Index Scan on jobs_state_idx  (rows=2301) (actual rows=499500.00)

-- After ANALYZE
Seq Scan on jobs  (cost=0.00..11932.00 rows=499617 width=64)
                  (actual rows=499500.00 loops=1) 

-- After a bulk load, collect statistics now instead of waiting for autovacuum
ANALYZE jobs;

-- Is autovacuum keeping up? Rows changed since the last ANALYZE, and when it last ran
SELECT relname, n_live_tup, n_mod_since_analyze, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'jobs';

-- Partitioned parents are never analyzed automatically
ANALYZE measurements; 
The habit is simple: finish every bulk load, restore and large backfill with an ANALYZE of the tables it touched. The cost is a sample read of the table. Two other levers exist and belong to the planner articles: raising a column’s statistics target with ALTER TABLE ... SET STATISTICS for a skewed column, and CREATE STATISTICS for columns that are correlated. Creating an expression index also makes PostgreSQL gather statistics for the expression, which is one reason a new index can change plans for queries that did not use it. 

### InnoDB: persistent statistics 
InnoDB stores its statistics in mysql.innodb_table_stats and mysql.innodb_index_stats so they survive a restart (innodb_stats_persistent, on by default). It recalculates them in the background when more than 10% of a table’s rows have changed (innodb_stats_auto_recalc, on by default), and always when an index is added. The estimate samples 20 index pages per index by default. Run ANALYZE TABLE after a big load. It takes a read lock while it samples, and the manual says the recalculation is neither instant nor replicated: each server does its own automatic one, while a manual ANALYZE TABLE is replicated and so runs on the replicas too. 

ANALYZE TABLE orders;    -- read lock while it samples; refreshes persistent statistics

-- Per table, if the defaults do not suit:
ALTER TABLE orders STATS_AUTO_RECALC=1, STATS_SAMPLE_PAGES=50; 
InnoDB estimates a skewed value on an indexed column by searching the index for it, not from these statistics, so a long IN list or a parameterised statement is the thing to examine there, along with eq_range_index_dive_limit. Histograms (ANALYZE TABLE ... UPDATE HISTOGRAM) serve columns that have no index, where the optimizer has nothing to search. 

### SQLite: PRAGMA optimize 
SQLite collects statistics only when asked, with ANALYZE, and keeps them in a table that planning reads. Its documentation recommends PRAGMA optimize instead of calling ANALYZE yourself. It decides which tables could benefit, runs ANALYZE on them with a limit on how long that may take, and is “usually a no-op or nearly so”. The documented routine is to run it just before closing a short-lived connection, to run PRAGMA optimize=0x10002 when a long-lived one opens (the 0x2 bit runs ANALYZE where it would help, and the 0x10000 bit makes it consider every table, not only those this connection has used, which matters on a connection that has used none yet) and then every hour or day, and to run it after any schema change, especially after CREATE INDEX. 

-- Long-lived connection: once at open, then now and then
PRAGMA optimize=0x10002;
PRAGMA optimize;

-- Short-lived connection: just before closing. Also after CREATE INDEX.
PRAGMA optimize; 

### Recognising stale statistics 
The symptom is a plan whose estimated row counts are far from the actual ones. EXPLAIN (ANALYZE) prints both side by side: 2,301 against 499,500 above. A new index that the planner does not pick up, a sequential scan where an index is obvious, or a plan that regressed after an import point the same way, and the fix is to refresh statistics first and consider the index second. Understanding database performance works through the diagnosis.  

## Finding indexes to remove 
Every index costs space and write work whether or not any query uses it, and tables acquire them over the years. There are three kinds to look for, each with a different test, and then the question of how to drop one safely. 

### Unused indexes 
PostgreSQL counts index scans in pg_stat_user_indexes, and since version 16 records last_idx_scan, the time of the last one. MySQL’s sys schema lists unused indexes in schema_unused_indexes, and SQLite keeps no usage counts. The size query under Measuring size and bloat includes both columns. A zero is evidence only if the counters have covered everything the system does. PostgreSQL resets them after an unclean shutdown or point-in-time recovery, each replica has its own, and a monthly report or year-end job can use an index that no scan has touched since the counters began. MySQL’s counters come from the performance schema, which starts empty at every server restart, so right after one every index looks unused; the manual says the view is most useful once the server has run a representative workload. Check stats_reset in pg_stat_database, look at every replica that serves reads, and ask whether a rare job needs it. An index that enforces a primary key or a unique constraint stays however few scans it records, and so does one on a foreign key’s referencing column if deleting from the parent table runs often. 

### Duplicate and redundant indexes 
Two indexes can be the same index, and a short one can be covered by a longer one. An index on (customer_id) is redundant beside (customer_id, placed_at), because the longer index serves a lookup on its leading column. Both cost writes. The first PostgreSQL query below finds exact duplicates by comparing the stored definition, the second finds non-unique indexes that are a leading prefix of another. Both were run against a table with a deliberate duplicate and prefix and reported them. If one_enforces_a_constraint is true, the unique or primary-key index is the one to keep and its plain twin is the one to drop. Both queries ignore two things you should check by eye before dropping: INCLUDE columns, which may make the shorter index the one that answers a query without the table, and a descending column, where the prefix index does not give the same order. 

-- Indexes with exactly the same columns, operator classes, ordering and predicate
SELECT indrelid::regclass AS table_name,
       array_agg(indexrelid::regclass ORDER BY indexrelid) AS same_definition,
       bool_or(indisunique) AS one_enforces_a_constraint
FROM pg_index
GROUP BY indrelid, indkey, indclass, indcollation, indoption,
         coalesce(indexprs::text, ''), coalesce(indpred::text, '')
HAVING count(*) > 1;

-- Non-unique indexes whose columns are a leading prefix of another index
SELECT a.indexrelid::regclass AS shorter, b.indexrelid::regclass AS longer
FROM pg_index a
JOIN pg_index b
  ON a.indrelid = b.indrelid AND a.indexrelid <> b.indexrelid
 AND a.indnkeyatts < b.indnkeyatts
 AND (string_to_array(a.indkey::text, ' '))[1:a.indnkeyatts]
   = (string_to_array(b.indkey::text, ' '))[1:a.indnkeyatts]
 AND (string_to_array(a.indclass::text, ' '))[1:a.indnkeyatts]
   = (string_to_array(b.indclass::text, ' '))[1:a.indnkeyatts]
 AND a.indpred IS NOT DISTINCT FROM b.indpred
 AND a.indexprs IS NOT DISTINCT FROM b.indexprs
WHERE NOT a.indisunique AND a.indisvalid; 
MySQL’s sys.schema_redundant_indexes does this and prints the DROP statement. 

SELECT table_name, redundant_index_name, dominant_index_name, sql_drop_index
FROM sys.schema_redundant_indexes; 

### Invalid indexes 
The query in When a concurrent rebuild or build fails finds the third kind: indexes left half built. Unlike the others they have no benefit at all. 

### Dropping without making things worse 
A plain DROP INDEX in PostgreSQL takes an AccessExclusiveLock on the table, so it stops reads and writes until it gets the lock and finishes. DROP INDEX CONCURRENTLY waits for conflicting transactions instead of blocking, with limits: one index per statement, no CASCADE, not inside a transaction block, and not for an index that backs a unique or primary-key constraint, which you drop with ALTER TABLE ... DROP CONSTRAINT. 
The risk of dropping is a query you forgot. MySQL lets you test it first. An invisible index is ignored by the optimizer but still maintained, so making it visible again is immediate and needs no rebuild. A primary key cannot be made invisible. PostgreSQL has no equivalent, so the way to retain the option of undoing a drop is to keep the CREATE INDEX statement and have the time and disk to run it again, a rebuild of a large index being exactly the cost this article keeps pointing at. SQLite is the same, and cheaper only because its databases are usually smaller. 

-- Hide the index from the optimizer; it is still kept up to date
ALTER TABLE orders ALTER INDEX orders_customer_idx INVISIBLE;

-- Something got slower? Undo it at once, without a rebuild
ALTER TABLE orders ALTER INDEX orders_customer_idx VISIBLE;

-- After a representative period with no regressions
ALTER TABLE orders DROP INDEX orders_customer_idx;  

## Replacing an index in production 
Changing an index, to add a column, change the order or turn it into a partial index, is a build, a check and a drop, in that order, with both indexes present in between. Never drop first: a query that depended on the old index runs against the table until the new one exists. The steps, in PostgreSQL: 

-- 1. Build the replacement beside the old index (PostgreSQL)
CREATE INDEX CONCURRENTLY orders_customer_placed_idx
  ON orders (customer_id, placed_at DESC);

-- 2. Confirm it finished
SELECT indisvalid FROM pg_index
WHERE indexrelid = 'orders_customer_placed_idx'::regclass;

-- 3. Check the queries it is for: EXPLAIN (ANALYZE) and look for the new name

-- 4. After a representative period, compare scans on old and new
SELECT indexrelname, idx_scan, last_idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'orders';

-- 5. Drop the old one without blocking
DROP INDEX CONCURRENTLY orders_customer_idx; 
Step 2 matters because a failed concurrent build looks like a completed command to a migration tool that ignores the error. Step 3 is the point of the exercise: run the plans for the queries the new index is meant to serve, on data shaped like production, and look for the new index’s name. Step 4 is optional but cheap; if the old index shows no scans after a representative period while the new one does, the drop is safe. In MySQL, replace step 5 with making the old index invisible, waiting, and dropping it as in the example above. In SQLite, create the new index, check the plans with EXPLAIN QUERY PLAN, drop the old one and run PRAGMA optimize. 
If the new index has the same definition as one being rebuilt for space, there is no need for this procedure: REINDEX CONCURRENTLY does the same swap for you.  

## Checking that an index is sound 
An index can be wrong in a way that no query reports: entries in the wrong order, entries missing for rows that exist, or pointers to nowhere. A hardware fault, a bug, or a change to the rules that sort text can cause it. The last is the one to know. If the operating system library that supplies collation rules changes under a text index, which can happen when a replica or restored server runs a different OS version, the stored order stops matching the order the server now expects, and lookups quietly miss rows. PostgreSQL’s amcheck documentation lists this among its cases. SQLite’s REINDEX page gives a changed collation as its first reason to rebuild. 

-- PostgreSQL: AccessShareLock, safe on a live primary or a standby
CREATE EXTENSION IF NOT EXISTS amcheck;
SELECT bt_index_check('orders_pkey', heapallindexed => true);

-- MySQL (InnoDB): QUICK skips the row-link scan
CHECK TABLE orders QUICK;

-- SQLite: one row 'ok', or one row per problem
PRAGMA integrity_check; 
bt_index_check in PostgreSQL takes only the lock an ordinary SELECT takes and works on a standby, and with heapallindexed it also checks that every table row has its entry, at the cost of several times the work. bt_index_parent_check is more thorough and takes a ShareLock that blocks writes, and cannot run on a hot standby. A passing check does not prove an index is sound, only that this test found nothing, and the manual says REINDEX may not repair every failure. InnoDB’s CHECK TABLE checks index structure and entry counts, and only the QUICK option changes what it does for InnoDB. It can block other work on large tables, and the manual warns that a corrupt page can stop the server. SQLite’s PRAGMA integrity_check reads the whole database and reports ok or a list of problems; quick_check skips the comparison of index contents with the table. 
When a check finds a bad index, rebuilding it is usually the repair, and the section above says how. Treat the cause as the problem, though: an index that was damaged once by a disk or a collation change can be damaged again.

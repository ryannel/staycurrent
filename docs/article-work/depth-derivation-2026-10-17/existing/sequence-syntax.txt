Drawing systems and processes 

# Sequence diagram syntax: Mermaid, PlantUML and others 
 Companion to Sequence diagramsAbout 10 minutesMermaid 12.2 · PlantUML 1.2026.9    
Sequence diagrams teaches what a sequence diagram says and writes every example in Mermaid. This page is for the other moment: you know the picture you want and need the text that draws it, or someone has sent you a PlantUML file and you want to know what its arrows mean. 
Mermaid and PlantUML draw most of the same diagrams from different text. Many constructs line up one for one. Some differ only in spelling, and a few arrows look alike in both tools yet mean different things. Each tool also draws things the other can’t, and where a diagram will render depends on which of them the place supports. 
Syntax changes between releases, so every listing here was rendered on 17 October 2026 with Mermaid 12.2.0 and PlantUML 1.2026.9. GitHub and GitLab run their own copy of Mermaid, which can be older than that one. Where a piece of Mermaid syntax is newer than version 11.0, the table in Mermaid syntax by version gives the release that introduced it.

## One booking in both syntaxes 
Mina books a repair. The API starts an email request and answers her without waiting for it, so the provider’s reply, when it comes, has no one to receive it. That is the asynchronous message from the main article, with the fact written down in a note. Both listings draw the same thing: three lifelines, a call that starts an activation bar on the API, an asynchronous message, a reply that ends the bar, and the note. 
sequenceDiagram
    actor Mina
    participant API as Repair API
    participant Provider as Email provider
    Mina->>+API: POST /repairs
    API-)Provider: POST /emails
    API-->>-Mina: 201 Created: R17
    Note over API,Provider: Nobody waits for this reply 
@startuml
actor Mina
participant "Repair API" as API
participant "Email provider" as Provider
Mina -> API ++ : POST /repairs
API ->> Provider : POST /emails
API --> Mina -- : 201 Created: R17
note over API, Provider : No reply within 10 s: outcome unknown
@enduml 
A few differences show up already. Mermaid declares a participant’s short name first and its display text after as. PlantUML takes the display text first, in quotes, and the short name after as. Mermaid’s call arrow is ->> and its asynchronous arrow -). In PlantUML the call is -> and the asynchronous message is ->>. PlantUML wraps a diagram in @startuml and @enduml, except inside a GitLab plantuml block, which adds them. 

## Constructs side by side 
The first column of each table says what the construct means, in the terms the main article uses, and links to where that article explains it. The mark … stands for the lines inside a block. “None” means the tool has no syntax for it, which the section on what each tool can’t draw explains further. 

### Participants, notes and text  
 | Meaning | Mermaid | PlantUML 
 | A lifeline with a display name | participant API as Repair API | participant "Repair API" as API
 | A person | actor Mina | actor Mina
 | A database or a queue | participant DB@{ "type": "database" } (11.11 and later; add as Repair DB from 11.13) | database "Repair DB" as DB
 | Lifelines grouped in a labelled box | box Aqua Our services … end | box "Our services" #LightBlue … end box
 | A message from a lifeline to itself | A->>A: Check postcode | A -> A : Check postcode
 | A note over one or two lifelines | Note over A,B: text | note over A, B : text
 | A note beside a lifeline | Note right of B: text | note right of B : text
 | A note attached to the previous message | none | note right : text
 | A line break inside a label | first<br/>second | first\nsecond
 | A comment | %% text, on its own line | ' text  
Both tools draw a lifeline for any name that first appears in a message. Declare participants anyway, in the order you want them across the page. PlantUML also has entity, control, boundary and collections shapes, which Mermaid reaches through the same type setting as database. 
Mermaid reads a # in a message as the start of an entity code and cuts the text there. ticket #42 comes out as “ticket”, and ticket #35;42 keeps the whole label. A semicolon ends a statement, so write #59; inside a label. PlantUML shows both characters as typed. 

### Activation, creation and numbering  
 | Meaning | Mermaid | PlantUML 
 | An activation bar starts as a call arrives | A->>+B: call | A -> B ++ : call
 | It ends as the reply leaves | B-->>-A: reply | B --> A -- : reply
 | Start and end a bar on their own lines | activate B … deactivate B | activate B … deactivate B
 | A reply to whichever call last activated a lifeline | none | return reply
 | Every call activates its receiver | none | autoactivate on
 | A lifeline that starts partway down | create participant Q, on the line before the message that creates it | create Q, on the line before the message that creates it
 | A lifeline that ends partway down | destroy Q, on the line before the message that ends it | destroy Q, on the line after the message that ends it
 | A number on every arrow, with an optional start and step | autonumber 10 5 | autonumber 10 5  
The + and - in Mermaid and the ++ and -- in PlantUML do the same job from opposite sides of the arrow. Mermaid writes them on the arrow itself, and - ends the bar of the lifeline the reply leaves. PlantUML writes them after the target, and -- ends the bar of the lifeline the message leaves. Read them as “start a bar on the receiver” and “end the sender’s bar” in either tool. 
destroy is the one place where position matters in opposite ways. Mermaid wants it before the message, and PlantUML after it. In both, the lifeline ends at that message. 

### Frames  
 | Meaning | Mermaid | PlantUML 
 | Alternatives: at most one section runs | alt guard … else guard … end | alt guard … else guard … end
 | A step that may not happen | opt guard … end | opt guard … end
 | A section that repeats | loop guard … end | loop guard … end
 | Sections with no order between them | par one … and two … end | par one … else two … end
 | Leave the enclosing fragment | break guard … end | break guard … end
 | A region that no other message may interleave with. Both tools also let you add named cases, which is their own reading | critical name … option case … end | critical name … else case … end
 | A reference to another diagram | none; use a note across the lifelines | ref over A, B : name
 | A frame with only a label, no UML operator | none | group Label [secondary label]
 | A coloured background behind some messages | rect rgb(200,255,200) … end | none  
The two tools part ways on par and critical. Mermaid separates parallel sections with and and the cases of a critical region with option. PlantUML uses else for both and reports an error on and or option. A guard is written without square brackets in both tools, and both add them when they draw the frame. 

## Arrows that change meaning between tools 
Translating a diagram by eye is where most mistakes happen. The two tools use the same characters for different arrows, so a diagram that converts without an error can still say something else.  
 | Meaning | Mermaid | PlantUML 
 | A call: solid line, filled head | ->> | ->
 | A reply: dotted line, head | -->> | -->
 | An asynchronous message: open head | -) | ->>
 | An asynchronous message, dotted | --) | -->>
 | A lost message: cross | -x | ->x
 | The same, dotted | --x | -->x
 | A lost message: ends in a filled circle | none | ->o
 | A message in both directions | <<->> (11.0 and later) | <->  
Three traps follow from the table:  
- Mermaid’s -> and --> draw a line with no arrowhead at all. PlantUML’s -> is a call and its --> is a dotted reply. Copying A->B from one to the other swaps a call for a bare line, or the reverse. 
- Mermaid’s ->> is a call and PlantUML’s ->> is a thin-headed asynchronous message. A call that is pasted across unchanged turns into a message nobody waits for. 
- Mermaid marks a lost message with a cross and has no circle. PlantUML has both: ->x for the cross and ->o for the filled circle the main article calls a lost message.  
PlantUML’s default arrowheads are sharp rather than UML’s triangle. Adding skinparam style strictuml to the diagram draws the triangle. 

## What each tool can’t draw 
Most sequence diagrams stay inside what both tools draw. These lists are for the ones that don’t. 

### In Mermaid 
Mermaid 12.2.0 has no syntax for the following. Where a line looks plausible, Mermaid often accepts it and draws something unintended, so look at the result.  
- A ref frame that stands for another diagram. It is a parse error. The main article’s workaround is a note across the lifelines. 
- A found message or a message to the edge of the diagram. PlantUML writes [-> and ->]. Mermaid reads [->>A: text as a message from a new participant named “[”. 
- A lost message that ends in a circle. Writing A->>oB creates a participant called “oB”. 
- A delay or a divider, which PlantUML writes ... and == Phase ==. Both are parse errors in Mermaid. The main article says how to show a wait without them. 
- Messages that start together. PlantUML’s & puts two messages at the same height. Mermaid reads & A as a participant name. par says the order is free, which is a different claim from “at the same moment”. 
- A duration marker between two messages, such as “10 s limit” drawn as a bracket. PlantUML does it with anchors. The main article’s section on order, gaps and time covers where a limit goes instead. 
- A note on a message, return and automatic activation. These are parse errors or absent; write the reply and the + and - yourself.  
Mermaid also draws half arrowheads and central connections, which this page leaves out because the main article’s diagrams don’t use them. They need 11.13.0 or later. 

### In PlantUML 
PlantUML 1.2026.9 can draw every construct in the tables above except a coloured background behind messages: rect is a parse error. Mermaid also offers menus of links on a participant, and PlantUML’s sequence documentation describes nothing like them. 
The more practical limit is where it runs. PlantUML renders through Java or through a PlantUML server, so a place that only runs JavaScript in the browser can’t draw it. The next section lists the places that can. 

## Where each one renders 
A diagram that doesn’t render is a block of text, so check the place where readers will see it before choosing the tool. The first rows follow each place’s own documentation as of 17 October 2026. The Notion, Confluence and Google Docs rows rest on Mermaid’s list of integrations and a search of the Atlassian Marketplace, because those products’ own documentation either didn’t mention Mermaid or couldn’t be read here. Test a diagram in the page itself before committing to a tool there, and treat a PlantUML answer for those three as unknown.  
 | Place | Mermaid | PlantUML 
 | GitHub: Markdown files, issues, pull requests, discussions and wikis | Renders a fenced mermaid block. | Not rendered. GitHub’s documentation lists four diagram syntaxes, and PlantUML isn’t one of them.
 | GitLab | Renders a mermaid block. GitLab’s documentation says it supports Mermaid version 11. | Renders a plantuml block on GitLab.com. A self-managed GitLab needs an administrator to enable it and a PlantUML server to call.
 | Docusaurus | The @docusaurus/theme-mermaid theme, switched on with markdown.mermaid in the site configuration. | Not covered by its diagrams documentation.
 | Material for MkDocs | A custom fence for mermaid in the superfences setting; no plugin. | Not covered by its diagrams documentation.
 | Sphinx | The sphinxcontrib-mermaid extension. | The sphinxcontrib.plantuml extension, which runs a local PlantUML jar through Java.
 | Asciidoctor | Asciidoctor Diagram. | Asciidoctor Diagram.
 | Kroki, a service that renders both from text | Supported. | Supported.
 | Notion | Mermaid’s list of integrations marks Notion as supported. Notion’s own help page on code blocks, the one checked, doesn’t mention Mermaid. | Not checked.
 | Confluence | Not built in as far as this page could confirm. Several third-party apps on the Atlassian Marketplace add Mermaid macros, and Mermaid’s integrations list names some of them. | Not checked.
 | Google Docs | No built-in support found. Mermaid’s integrations list names a third-party add-on. | Not checked.  
Where PlantUML isn’t rendered, the usual answer is to commit the exported image beside the source file, or to generate it in the build. The main article’s Keeping diagrams useful covers keeping source and picture together. 
GitHub doesn’t publish the Mermaid version it uses. Its documentation suggests putting info alone in a fenced mermaid block, which draws the version number. A docs build uses whatever version its plugin installed, so the answer there is in the lock file. Syntax from 11.13.0 onward, listed next, is the part most likely to hit an older renderer. 

### Mermaid syntax by version 
The release is taken from Mermaid’s release notes where they name the change, and from the sequence page where they don’t. The last column records what rendering showed. The releases tried were 11.1.0, 11.4.0, 11.4.1, 11.12.2, 11.12.3, 11.13.0 to 11.17.2 and 12.2.0; a release not on that list was not tried.  
 | Syntax | First in | Source | Rendered check 
 | create participant and destroy | 10.3.0 | Mermaid’s sequence page | Parsed and drawn by every 11.x release tried, from 11.1.0.
 | Arrows that point both ways, <<->> | 11.0.0 | Mermaid’s sequence page | Parsed from 11.1.0, the oldest release tried.
 | Participant types, such as participant DB@{ "type": "database" } | 11.11.0 | The 11.11.0 release notes | Rejected by 11.4.0 and 11.4.1; parsed by 11.12.2.
 | An alias after the type, @{ … } as Name | 11.13.0 | The 11.13.0 release notes | Rejected by 11.12.3 and parsed by 11.13.0.
 | Half arrowheads such as -|\ and central connections such as ->>() | 11.13.0 | The 11.13.0 release notes | The sequence page says 11.12.3. Release 11.12.3 rejected the arrows and drew the central connection as text; 11.13.0 parsed both.
 | A decimal start or step, such as autonumber 1.5 0.5 | 11.15.0 | The 11.15.0 release notes | Rejected by 11.14.0 and parsed by 11.15.0. Plain autonumber and whole-number starts are older.
 | A new default theme and look for sequence diagrams | 12.0.0 | Mermaid’s sequence page | Appearance only; the syntax is unchanged.  
PlantUML’s documentation is for the current release and rarely says when something arrived. It does record one removal: since 1.2025.5 the old skinparam lifelineStrategy solid no longer works, and solid lifelines come from a <style> block. PlantUML also documents !pragma teoz true for &, anchors and nested boxes. 1.2026.9 drew & and anchors without it, but a renderer that is older, such as one bundled with a wiki or an IDE plugin, may need it. 

## D2 and drawing by hand 
D2 draws sequence diagrams too, with no syntax of its own for them. Setting shape: sequence_diagram on a diagram or an object turns the connections inside it into messages, in the order you write them. Children of the diagram share one scope, so api means the same lifeline everywhere. A group is a labelled container for a stretch of messages, and a span, which D2 uses for an activation bar, is an object nested on a lifeline. A note is an object nested on a lifeline with no connection to it. The same booking looks like this: 
shape: sequence_diagram
mina: Mina
api: Repair API
provider: Email provider

mina -> api: POST /repairs
api -> provider: POST /emails
api -> mina: 201 Created: R17 {style.stroke-dash: 3}
api."Nobody waits for this reply" 
D2 treats a message as an arrow and styles it like any other, as the dashed reply shows. It has no alt, loop or par operators, so a frame is a group with a label you write yourself. Choose it when the rest of your diagrams are already D2 and one of them is a sequence. This page checked it against D2 0.9.0. GitHub doesn’t render D2, but Kroki and Asciidoctor Diagram do. 
Drawing by hand in an editor such as draw.io trades the text source for control over layout, and the main article’s guide to keeping diagrams useful weighs that trade. draw.io’s documentation describes inserting Mermaid source and then editing the shapes it creates. Check how it handles a sequence diagram before relying on it, because this page didn’t.

Drawing systems and processes 

# Sequence diagrams 
 Deep diveAbout 32 minutesMermaid 12    
A sequence diagram shows the messages that pass between parts of a system during one interaction, in the order they happen. A message might be an HTTP request, a database query or the reply to either. Each part gets a vertical line. Time runs down the page, and each arrow is one message. 
A drawing of boxes and arrows can show that an API talks to a database and to an email provider. A sequence diagram shows which call comes first, which part sits waiting while another works, and what each side knows when a reply never comes back. You reach for one when that order is the question: when you design a request that crosses several services, work out why a page is slow, or decide what should happen if a service never answers. 
Every example here follows one invented repair service. Mina books a dishwasher repair in her browser. A Repair API stores the booking in a PostgreSQL database, Repair DB. A notification worker, a separate process running in the background, later emails her through an external email provider. Each section changes one thing about that booking, from the plain request through timeouts and retries to steps that repeat or run side by side. Each diagram is also written in Mermaid, a text format that GitHub and GitLab render as diagrams. The last section points to PlantUML for what Mermaid can’t draw. 
The diagrams build to a practical question. Why does sending Mina’s confirmation email inside her booking request make her wait, and how can one retry send her the same email twice? The later sections cover timeouts inside timeouts, how much to put in one diagram, and how to review a diagram someone else drew.

## Lifelines and messages 
A lifeline is the dashed line running down from each participant’s box at the top of a sequence diagram. A message is an arrow from the sender’s lifeline to the receiver’s, labelled with what is asked or answered. 
Press play and watch the order in which the four messages arrive.   
Figure 1
Mina books a repair 

The browser sends POST /repairs to the Repair API. The API inserts the repair request into Repair DB, the database replies that the commit succeeded, and only then does the API reply 201 Created with request R17.  

 Play Back Next     Reset     Messages in order, as text 
- Browser → Repair API: POST /repairs (call)
- Repair API → Repair DB: INSERT repair request (call)
- Repair DB → Repair API: COMMIT ok (reply)
- Repair API → Browser: 201 Created: R17 (reply)     
The API can’t answer the browser until the database has answered the API. Reading down the page gives you that order without reading any code. Left to right carries no meaning. Put whoever starts the interaction on the left, so requests travel right and replies come back left. 
Label each arrow with the operation and the data that matters, such as POST /repairs or 201 Created: R17. A label like “data” or “response” hides whether the database is being asked to read, write or confirm something. 
A lifeline stands for a role, not a machine. “Repair API” means whichever copy of the API handles the request, and one lifeline is enough while the story doesn’t depend on which copy that is. When it does, give each copy its own lifeline. Two workers that claim the same job, or two API instances that both accept a cancellation, need “Worker A” and “Worker B” side by side, or the race has nowhere to appear. Keep the lifelines at one level: services beside services, not a service beside a class inside another service. How much to draw returns to this. 
In Mermaid, the same booking takes eight lines: 
sequenceDiagram
    participant UI as Browser
    participant API as Repair API
    participant DB as Repair DB
    UI->>API: POST /repairs
    API->>DB: INSERT repair request
    DB-->>API: COMMIT ok
    API-->>UI: 201 Created: R17 
participant declares the lifelines from left to right, and as gives each one a readable name. ->> draws a solid arrow for a call, and -->> a dotted one for its reply. 

## Replies and activation bars 
Calls are the solid arrows in the booking: the sender asks, then waits for the answer. The dotted arrows are the replies. Between sending a call and getting its reply, the caller does nothing else for that request. An activation bar is a narrow bar on a lifeline that shows when that participant is handling a call. 
The next animation adds activation bars to the booking, plus a hatched bar for waiting. The hatched bar is this article’s addition, not standard notation. It darkens the longer the wait goes on. The status under each name and the clock in the corner give the same information as words and numbers. Watch the browser’s bar while the database works. Then set the database to 3 s and watch again.

The browser waits for the whole chain. With a 3-second database write it waits a little over 3 seconds, and the API waits almost as long inside it. The API’s wait is nested inside the browser’s, so each extra second in the database is an extra second for Mina. 
The diagram didn’t get taller. Vertical distance shows order, not elapsed time, so a 5 ms write and a 3-second write draw the same picture. When the question is how long something took, write the times in a note, a box of text attached to a lifeline, or draw a timeline. 
UML, the standard notation these diagrams come from, calls an activation bar an execution specification. Mermaid has one kind of bar. It draws a bar wherever you ask for one, on any participant, so it can’t tell working from waiting, and the hatched waiting bars won’t appear in Mermaid output. A + after a call’s arrow starts a bar on the participant receiving it, and a - after a reply’s arrow ends the bar of the participant sending it:

    participant DB as Repair DB
    UI->>+API: POST /repairs
    API->>+DB: INSERT repair request
    DB-->>-API: COMMIT ok
    API-->>-UI: 201 Created: R17 
A bar can also begin without a message. activate and deactivate start and end one on a named participant, which suits a worker that wakes on a timer: 
sequenceDiagram

    DB-->>Worker: Job J9

Not every diagram needs the bars or every reply. Draw a reply when it carries data or a decision, such as 201 Created: R17 or a 422. A bare “OK” that only closes the call can go, as long as nothing in the design hangs on that reply failing to arrive. Draw activation bars when who is blocked is the question, as in this section, and leave them off when it isn’t. Most diagrams later in this article leave them off. 

## Synchronous and asynchronous messages 
Every call so far has been a synchronous message: the sender waits for the reply. UML draws it with a filled arrowhead. An asynchronous message is one the sender doesn’t wait for. It has an open arrowhead, and the sender carries straight on. 
The two words describe the sender, not the protocol. A browser’s await fetch(...) is a synchronous message in a diagram, because the code stops until the reply comes, even though JavaScript calls the style asynchronous. An HTTP request whose response nobody reads is an asynchronous message, even though HTTP is a request and response protocol. A message sent to a message broker is a synchronous call to the broker, which answers that it has stored the message, followed by an asynchronous delivery to whoever consumes it. Label each arrow by what its sender does next. 
Suppose the API also sends Mina’s confirmation email before it answers her. The email provider takes 2.5 seconds to reply, an invented figure. Watch the API wait for the provider first. Then switch the API to Doesn’t wait and see when the browser gets its 201 Created.

When the API doesn’t wait, the browser gets its 201 Created in about 70 ms. The provider’s 202 Accepted comes back 2.5 seconds later to an API that has moved on. Nothing is waiting for it. Had that reply been an error, nothing would have handled it. The email would never have been sent, and nobody would know. 
Mermaid writes an asynchronous message with -). Its documentation names that arrow the asynchronous one, but describes ->> only as a solid line with an arrowhead. Reading ->> as a call is the UML convention this article follows, so say so if your readers might take Mermaid’s output as exact UML.

Neither version suits a booking. The first makes Mina wait for an email. The second ignores any error the provider sends back. The repair service moves the email out of the request instead. 

## Background workers and the transactional outbox 
A transactional outbox is a table where a service writes the work it wants done, in the same database transaction as the change that caused it. Here the work is notification job J9. The booking and the job are committed together, or neither is. So there’s never a booking without its email job, or an email job for a booking that failed. 
A background worker is a separate process that picks the work up later. It polls: it asks the database for the next job about once a second, and the database never calls it. 
The animation adds the worker and the provider as two more lifelines. Watch when the browser gets R17 compared with when the email goes out.

The diagram draws one pass of the worker’s poll. The polling repeats, but that is the worker’s business and not part of this interaction, so a note such as “Polls about once a second” says it without a loop frame. 
With several workers, claiming has to be safe. Each worker claims with a locking read (FOR UPDATE SKIP LOCKED in PostgreSQL), which skips any job another worker is claiming at that moment, so two workers can’t take J9 together. That lock lasts only until the claim commits, long before the email goes out. So the claim also sets the job’s “taken until” time five minutes ahead: the “for 5 min” in the diagram. If the worker dies, the time passes and another worker can claim J9. Draw two workers to see the claim work: 
sequenceDiagram
    participant DB as Repair DB
    participant A as Worker A
    participant B as Worker B
    A->>DB: Claim a job for 5 min
    B->>DB: Claim a job for 5 min
    DB-->>A: Job J9
    DB-->>B: No job free 
The database gives J9 to one claim and tells the other that no job is free. The diagram doesn’t decide which worker wins. It says only that exactly one does. 
The outbox still has a gap. Set Worker crashes. The provider sends the email, and the worker crashes before it marks J9 sent. Five minutes later the claim expires, a worker claims J9 again, and the provider sends a second email. The next two sections show why the worker can’t simply check what happened, and how to stop the duplicate. 

## Lost messages and timeouts 
A lost message is one that is sent but never received. UML draws it as an arrow that ends in a small filled circle instead of at a lifeline. 
Take the worker’s POST /emails. The request can be lost on the way out, or the provider’s reply can be lost on the way back. Or the provider can be slow, and its reply arrives after the worker has stopped listening. To the worker, all three look the same. 

### What the caller knows 
All the worker has is a timeout, a limit on how long it waits before giving up. Here the limit is 10 seconds. This animation keeps only the worker and the provider, and adds Mina’s inbox, which the worker can’t see. Try all three cases and watch the worker’s bar and status in each.   
Figure 5
What the worker sees after a timeout 

The worker sends POST /emails and waits. The provider accepts the request and delivers the email, but its reply is lost on the way back. In every case the worker sees the same thing: no reply after 10 seconds.

 Play Back Next     Reset     Messages in order, as text 
- Notification worker → Email provider: POST /emails (call)
- Email provider → Notification worker: 202 Accepted (lost on the way)
- Email provider → Mina’s inbox: Deliver email (one-way message, sender does not wait)
- Note on Notification worker: Timeout after 10 s. Outcome unknown.     
The worker’s bar and status are the same every time. It sends, waits 10 seconds and gives up. Mina’s inbox is not the same. When the request is lost, she gets nothing. When the reply is lost, or the provider is slow, she gets the email. 
A timeout records only that 10 seconds passed. It doesn’t say whether the email was sent. Draw it as a note on the caller’s lifeline, such as “Timeout after 10 s”. Don’t draw a reply arrow labelled “failed”: nobody sent one. 
An error reply is different. Figure 4’s Provider down case has the provider answering 503 Unavailable. That is a reply, so draw it as one, and the worker knows the provider says it didn’t take the request. A 5xx still doesn’t prove that nothing was done, because a server can fail after it has acted. The clearest case is a 502 or 504 from a gateway in front of the provider: the gateway gave up, and the provider behind it may have finished the work. Check the provider’s documentation before relying on a 5xx. Only silence is drawn as a timeout. 
Mermaid has no lost-message arrow with a circle. Use the cross arrow, -x, and put the timeout in a note: 
sequenceDiagram
    participant Worker as Notification worker
    participant Provider as Email provider
    Worker-xProvider: POST /emails
    Note over Worker: Timeout after 10 s. Outcome unknown. 
Library defaults are often far longer than 10 seconds. Node.js’s built-in fetch, which is based on undici, waits up to 300 seconds for a response’s headers, so one stuck email would hold the worker for five minutes. Set the limit yourself, for example with signal: AbortSignal.timeout(10_000). 

### Timeouts inside timeouts 
Figure 2 holds waits inside waits: the browser waits for the API, and the API waits for the database. Each wait can have its own limit, and the limits have to fit together. If the outer caller gives up before the inner work finishes, the work carries on after nobody is listening. 
Go back to Figure 2, set the database to 3 s and then set Browser gives up after to 2 s. The limit only matters when the write takes longer than it. The browser shows Mina an error at 2 seconds. The write commits at 3 seconds, and the API sends 201 Created for R17, which no browser is waiting to receive. The booking exists, and Mina was told it failed. She tries again, and now there are two bookings. 
sequenceDiagram
    participant UI as Browser
    participant API as Repair API
    participant DB as Repair DB
    UI->>API: POST /repairs
    API->>DB: INSERT repair request
    Note over UI: Timeout after 2 s. Shows an error.
    DB-->>API: COMMIT ok, at 3 s
    API-->>UI: 201 Created: R17
    Note over UI,API: Nobody is listening. R17 is stored. 
Each caller’s limit has to be longer than the longest its callee can take, counting the callee’s own waits. If the browser waits 5 seconds, the API should stop waiting for the database at, say, 2, so that it answers the browser with an error while the browser is still listening. That doesn’t remove the uncertainty: the API’s timeout leaves it as unsure about the write as the worker was about the email. But the part of the system that learns of the failure is then one that can do something about it. And a key on the booking request, like the one on the email in the next section, makes Mina’s second attempt safe. 

### Messages with no sender in the diagram 
A lost message is sent and never arrives. Its mirror is a found message: one that arrives from a sender the diagram doesn’t show. UML draws it as an arrow that starts from a filled circle instead of from a lifeline. Mermaid has no form for it. PlantUML writes [-> Worker : Poll timer fires. 
Flows that start by themselves, with no person or caller, can be drawn three ways. A timer that fires a poll, as in the outbox, is incidental: put a note on the worker’s lifeline, such as “Poll timer fires”, and start from there. When the trigger is something outside your system that you don’t want to draw, such as another company’s request, a found message says so: the message arrives, and who sent it is out of scope. In Mermaid, use the note, or a participant that stands for the outside world. When the timer’s own behaviour is part of the question, because it can be cancelled, rescheduled or fire late, give the clock a lifeline of its own, a scheduler, so those arrows have somewhere to start. Flows that last hours or days draws one. 

## Retries and idempotency keys 
A retry sends the same request again, unchanged, after a failure or a timeout. For the worker it is the obvious next step. Whether it is safe depends on what happened the first time. 
Start with the reply lost, and count the emails in Mina’s inbox. Then switch the first attempt to Request is lost.

When the request was lost, the retry is harmless and Mina gets one email. When the reply was lost, the provider had already sent the email, so the retry sends a second copy. Every retry therefore risks a duplicate, unless the provider can recognise a repeat. 
An operation is idempotent if doing it twice has the same effect as doing it once. Sending an email isn’t. An idempotency key lets the provider make it idempotent. The worker attaches a key that names the operation, here repair-email-J9, and sends the same key on every attempt. The provider remembers keys it has seen, and a repeat gets the saved reply without a second email. Derive the key from the job, not from the attempt. A new random key on each retry tells the provider that each attempt is a new email. 
Now set Idempotency key to Sent and play both cases again. Mina gets one email in each. The same key closes the outbox’s gap too: the worker that claims J9 after the crash sends repair-email-J9 again, and the provider recognises it. 
The key protects only while the provider remembers it. Resend, an email API, keeps keys for 24 hours, so a retry 25 hours later sends a second email. 
Space retries out, too. Wait longer after each failed attempt, and add a random amount, called jitter, so workers don’t all retry at once. Amazon’s guidance on timeouts, retries and backoff with jitter recommends both. 
A drawing doesn’t have to show every attempt. Draw them out when what differs between attempts is the point, as in the listing below, where the second carries the same key. When the retry is policy, write a loop labelled “up to 3 attempts”, or a note such as “Retried up to 3 times with backoff”, and keep the picture for what you want discussed. Retries also stack. An HTTP client that retries three times inside a worker that retries three times, inside a queue that redelivers three times, can make 27 attempts at the provider. Draw a layer’s retries when they multiply like this, and leave them out when they don’t (One question, one level of detail says more about what to omit).

    participant Provider as Email provider
    Worker->>Provider: POST /emails, Idempotency-Key: repair-email-J9

    Note over Worker: Timeout after 10 s. Wait 2 s.
    Worker->>Provider: POST /emails, Idempotency-Key: repair-email-J9
    Note over Provider: Key seen before: return the saved reply
    Provider-->>Worker: 202 Accepted 

## Order, gaps and what a diagram leaves open 
Reading down a lifeline gives a firm order. So does each message: it is sent before it is received. Those two rules are all a sequence diagram promises. Two events on different lifelines that no chain of messages connects have no order between them, even though one is drawn higher on the page. 
Take the outbox diagram. The API sends 201 Created after the commit, and the worker claims J9 after the commit too. Nothing links the two. The worker can claim J9, and even send the email, before the browser has R17. The drawing puts the 201 first because the rows have to go somewhere. This is the same interaction with the other order: 
sequenceDiagram
    participant UI as Browser
    participant API as Repair API
    participant DB as Repair DB
    participant Worker as Notification worker
    participant Provider as Email provider
    UI->>API: POST /repairs
    API->>DB: INSERT request + job J9
    DB-->>API: COMMIT ok
    Note over Worker: Polls just after the commit
    Worker->>DB: Claim a job for 5 min
    DB-->>Worker: Job J9
    API-->>UI: 201 Created: R17
    Worker->>Provider: POST /emails 
Both listings are the same diagram. Here the difference doesn’t matter, because the page for R17 exists from the commit onward. When a design does depend on one of these orders, the diagram needs a message that makes it so, or a note that admits nothing guarantees it. This is also why par exists: it says openly that the order between its sections is open. 
As Figure 2 showed, a diagram has no scale, so a gap of two days looks the same as a gap of two milliseconds. Mark a long gap in words. Mermaid has no delay marker, so put a note across every lifeline, such as Note over UI,Provider: Two days later. PlantUML has ...Two days later... and == heading == dividers. Write deadlines and durations in notes too, such as “reply within 2 s”. UML has formal duration constraints for this, but a note is read by everyone. 
Messages can also overtake each other: two sent in one order and delivered in the other. A plain arrow can’t show that, and Drawing asynchronous and event-driven interactions covers how to draw it. 

## Combined fragments 
Some messages happen only sometimes, some repeat, and some run side by side. A combined fragment is a frame drawn around those messages that says which. The tag in its top-left corner is the operator, which names the kind of frame. A condition in square brackets, the guard, says when they run. A dashed line divides a frame into sections, each with its own guard. 

### alt and opt 
An alt fragment holds alternatives, and at most one section runs: one whose guard is true. If several guards could be true, one of those sections is chosen. With an else section, exactly one runs. An opt fragment holds one section, which runs only if its guard is true. 
In the next animation the API checks Mina’s details before it stores anything. Watch which section of the alt runs. Then set Details to Invalid.

        API->>DB: SELECT status
        DB-->>API: status: received
        API-->>UI: 200: received
        Note over UI: Wait 2 s
    end 
UML writes a loop’s bounds in its tag: loop(1, 30) means at least once and at most 30 times, and you will meet that form in UML tools and in diagrams drawn by others. Mermaid has no bound syntax, so put the cap in the label, as the next listing does. 

### par 
A par fragment holds sections that run independently. Messages from different sections can interleave in any order. Within one section, the order still holds. 
Once Mina has R17, the page loads the repair’s status and the free appointment slots together. Watch both requests leave before either reply returns. Then change which reply comes back first.

### break 
A break fragment runs its messages in place of the rest of the enclosing fragment. Inside a loop, it leaves the loop. The polling loop can stop as soon as the status is scheduled, and the cap moves into the loop’s guard: 
sequenceDiagram
    participant UI as Browser
    participant API as Repair API
    loop up to 30 times
        UI->>API: GET /repairs/R17
        API-->>UI: 200: status
        break status is scheduled
            Note over UI: Show the appointment
        end
        Note over UI: Wait 2 s
    end 

### critical 
A critical fragment marks a region that other messages can’t interleave with. In UML, no other event on the lifelines it covers can fall between its first and last message. It says something about order, and nothing about databases or fallbacks. 
That makes it the most misread operator. Engineers often draw it around a database transaction, but a transaction is about isolation and commit, and the fragment promises neither. Mermaid’s documentation gives critical a second reading: something that must happen, with option sections for what to do if it fails. That is Mermaid’s own reading. UML gives a critical region no fallback sections; it only forbids interleaving. Use critical when the claim really is that no other message may come between these ones, as in the listing. Where you mean a transaction, a note says it more plainly, as the alt example did with “One transaction, ending at COMMIT”. 
sequenceDiagram
    participant Worker as Notification worker
    participant DB as Repair DB
    critical Claim a job
        Worker->>DB: Claim a job for 5 min
        DB-->>Worker: Job J9
    end 

### ref: splitting one interaction into several 
A ref fragment, which UML calls an interaction use, stands in for another sequence diagram. It is a frame tagged ref with the other diagram’s name inside, and it is the main way to split a diagram that has grown too big. Split the outbox diagram at the database, and the worker’s diagram can start with a ref to the booking. Mermaid has no ref, so use a note across the lifelines instead: 
sequenceDiagram
    participant DB as Repair DB
    participant Worker as Notification worker
    participant Provider as Email provider
    Note over DB,Worker: ref: Mina books a repair (writes job J9)
    Worker->>DB: Claim a job for 5 min
    DB-->>Worker: Job J9
    Worker->>Provider: POST /emails
    Provider-->>Worker: 202 Accepted 
PlantUML draws the real frame with ref over DB, Worker : Mina books a repair (writes job J9). How much to draw shows a diagram split this way. 

### Rare operators and deep nesting 
UML defines more operators than these: seq, strict, neg, assert, ignore and consider. They matter mostly in formal specifications. You may meet neg in a review, where it marks a sequence that must never happen. 
Fragments also nest, and a few levels in they stop helping. When alt branches each hold a screenful of messages, or a loop sits inside a par inside an alt, the diagram holds several scenarios. Split it, as How much to draw describes. 

## Actors, self-messages, notes and short-lived participants 
An actor is a participant that is a person. UML and Mermaid draw it as a stick figure. Use one when the interaction starts with someone’s action, such as Mina submitting the booking form. 
A self-message is an arrow from a lifeline back to itself. It shows a step a participant takes on its own, such as the API checking a postcode. Draw one only when the reader needs that step. 
A note holds anything that isn’t a message: a timeout, a wait, an assumption. Mermaid places a note over one participant or across two, or to the left of or right of one. 
Some participants exist for only part of an interaction. Since version 10.3, Mermaid writes create participant on the line before the message that creates one, and destroy on the line before the message that ends it. Only a message’s receiver can be created. Either end of a message can be destroyed. 
sequenceDiagram
    actor Mina
    participant UI as Browser
    participant API as Repair API
    Mina->>UI: Submit the booking form
    UI->>API: POST /repairs
    API->>API: Check postcode
    create participant Quote as Quote renderer
    API->>Quote: Render quote for R17
    destroy Quote
    Quote-->>API: quote.pdf
    API-->>UI: 201 Created: R17
    Note right of API: The renderer exists only for this request 
A participant can also carry a symbol that says what it is. PlantUML has keywords for database, queue, boundary, control, entity and collections. Mermaid sets them with a JSON-style configuration such as participant Q@{ "type" : "queue" }, which only newer releases accept (the syntax companion gives the version). A symbol only helps the reader recognise the participant. Like the queue shape in the whiteboard shape vocabulary, it says nothing about how a queue delivers. 
A box groups participants: by service, by owner, or by which side of a trust boundary they sit on. It answers questions such as which of these calls cross into the provider’s systems. Mermaid writes box LightBlue Our systems before the participants and end after them, and doesn’t support hex colours. PlantUML writes box "Our systems" #LightBlue and end box. A boundary can mean ownership, execution location or trust, so write which one you mean, as the layout article advises for any boundary. 

## Queues, events and callbacks 
Moving work off the request path doesn’t have to mean polling a table. The API can publish a message to a queue, or the email provider can report a bounce days later. Two things change in the drawing. A queue gets a lifeline of its own when its acknowledgement, retention or redelivery affects the outcome, and a plain asynchronous arrow when it only carries the message. And an answer that comes back later is a new message from the other side, tied to the original by an id, not a dotted reply to a call that finished long ago. 
Each of those has its own consequences, and they are the subject of Drawing asynchronous and event-driven interactions: the broker as a participant, redelivery, fan-out and webhooks. This site doesn’t yet cover how brokers themselves behave. Those articles are about what a drawing claims, not about any broker’s guarantees. 

## How much to draw 
Each diagram should answer one question. “What does Mina wait for?” and “What happens to the email when the provider is down?” are two questions. They share the API and the database, and little else. A diagram that tries to answer both ends up too crowded to answer either. 

### One question, one level of detail 
Choose the question first, then draw only the lifelines and messages that change its answer. A gateway that forwards every request unchanged, a token check that always passes, logging, a cache that only saves time and a client library’s internal retries can all stay off the page. A question about gateway timeouts needs the gateway. 
Keep to one level of detail. Lifelines can be services, or they can be objects inside one service, but a diagram that mixes the two says little about either. A diagram with a lifeline per class goes stale fastest, because every refactor changes it. Generate it from the code or don’t draw it. C4, a set of zoom levels for architecture diagrams, makes the same point about its code level, as the architecture article explains. 
Draw the happy path first, then one diagram for each failure that matters, rather than one diagram whose alt branches hold them all. This article does that: each failure has its own figure. 
The figure shows the same facts twice. Start with Everything in one, then switch to the two focused diagrams.

### Making it readable 
Order the lifelines so that most arrows travel between neighbours. An arrow that skips over lifelines crosses their activation bars and is hard to follow. Put the initiator on the left and external systems on the right, as the email provider is in the outbox diagram. 
Keep labels short. In Mermaid a long label widens the whole diagram, and <br/> breaks a label or a note over two lines. Number the steps when the diagram will be discussed: autonumber puts a number on every arrow, so a reviewer can say “step 7 has no timeout”. Add notes sparingly: a note on every arrow turns the diagram into prose. rect rgb(240, 240, 240) shades a region, such as the one transaction, but never let colour carry meaning alone. The layout article covers the general principles for labels, colour and splitting that dense drawings share. 

## Reviewing a design with a sequence diagram 
A sequence diagram is something you review: your own before you share it, someone else’s before you build from it. Each section above ended with something to look for. Together they make a list of questions to put to any diagram.  
- Who is waiting at each point, and for how long in the worst case? 
- Does every call that can hang have a timeout, and is each caller’s timeout longer than what its callee can take? 
- For every asynchronous message, who notices if it fails? 
- What does each participant know after a timeout? 
- Which arrows can be retried, and what makes a repeat safe? 
- Where does a crash between two arrows leave the data? 
- Can the participant that makes each choice evaluate its guard? 
- Which events are drawn in an order that nothing guarantees? 
- Does the diagram agree with the request’s state lifecycle, the statuses it may move through, as drawn in States and lifecycles?  
Try three of them on the outbox diagram. Who notices if the email fails? The worker, which records that J9 should be tried again in 30 seconds. The browser never learns of it. Where does a crash between two arrows leave the data? Between the provider’s 202 and “Mark J9 sent”, the email is out and J9 is unmarked, so the claim expires and a second email goes unless the key stops it. Which events are drawn in an order nothing guarantees? The browser’s 201 and the worker’s claim. 
To reconstruct an incident, start from evidence rather than the design. Logs and distributed traces record which calls were actually made and how long each took. A trace’s waterfall view is a timeline of one request, not a sequence diagram, but it tells you which messages to draw and what the diagram leaves out, which is the real time. Draw what happened, then compare it with the design diagram. The differences are the finding. 

### Keeping a diagram true 
The maintaining article covers owners, review when the system changes, and labelling a drawing as current or proposed. For a sequence diagram, what makes it stale is a call added or removed, a timeout or retry policy changed, or work moved between synchronous and asynchronous. Renaming a function doesn’t. Keep the Mermaid source next to the code that implements the flow, and when a reviewer doubts the diagram, compare it with a trace of the real flow. 

## Common mistakes  
- A callback drawn as a reply to the original call, when it is a new message tied back by a correlation id (Webhooks and callbacks). 
- A reply labelled “failed” that nobody sent after a timeout (What the caller knows). 
- An outer timeout shorter than the work it waits for (Timeouts inside timeouts). 
- A guard that the participant making the choice can’t check (alt and opt). 
- par around calls where one needs the other’s reply (par). 
- critical read or drawn as a database transaction (critical). 
- Arrows for things that aren’t messages, such as “uses” or data flow. That is an architecture diagram’s job. 
- Services, classes and a gateway’s internals on one set of lifelines (One question, one level of detail).

## Practise with a cancellation race 
R42 is Approved. At almost the same moment, Mina cancels it in her browser and a technician starts the repair in an app. Two instances of the Repair API handle the two requests, and both use Repair DB. Draw one sequence diagram of this. Decide which participants need lifelines, what each person is told, and what the database does when both requests want to change the same row. Write down what Mina and the technician each see before you read on.  Discussion 
The diagram needs five lifelines: Mina’s browser, the technician app, API instance A, API instance B and Repair DB. One API lifeline would look as though a single place handled the requests one at a time, and the race would vanish. 
The tempting drawing has each instance select the status, see Approved, then update it. That draws both updates succeeding. The check and the change are separate messages, and nothing orders one instance’s select against the other’s update, as the order section explained. The repair is a single message that checks and changes together, UPDATE ... WHERE status = 'Approved', with the database reporting how many rows changed. One request gets one row and succeeds. The other gets none. That tells its instance only that R42 was not Approved, not why, so the instance reads the status again before it answers 409 with the reason. 
sequenceDiagram
    participant Mina as Mina’s browser
    participant Tech as Technician app
    participant A as API instance A
    participant B as API instance B
    participant DB as Repair DB
    par cancel
        Mina->>A: POST /repairs/R42/cancel
        A->>DB: UPDATE status = Cancelled WHERE status = Approved
        DB-->>A: 1 row changed
        A-->>Mina: 200 Cancelled
    and start
        Tech->>B: POST /repairs/R42/start
        B->>DB: UPDATE status = In repair WHERE status = Approved
        DB-->>B: 0 rows changed
        B->>DB: SELECT status
        DB-->>B: Cancelled
        B-->>Tech: 409 Already cancelled
    end
    Note over DB: Check and change are one statement. The other order is equally valid. 
The listing lets the cancellation win. The start winning instead is an equally valid drawing, and the diagram can’t say which will happen, only that exactly one does. The par frame says neither request waits for the other. A note carries the rule that the check and change are one statement, which avoids drawing it as critical and having it read as a transaction. Compare the result with the lifecycle for R42: either order ends Cancelled or In repair, and never both. The technician must also wait for the success reply before starting the physical repair. Otherwise the record and reality can disagree.

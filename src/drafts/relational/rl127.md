CockroachDB table locality describes where data should be convenient to use. A survival goal describes which loss the database must tolerate. They influence the same replica placement, but they answer different questions: serving a booking near its customer does not automatically make that booking available after its entire home region disappears.

A nearby SQL connection is also not enough. The gateway may need to reach the row's range authority and a write quorum elsewhere. Locality helps place that work; it does not remove a cross-region dependency that the transaction's data or survival contract requires.

This article uses CockroachDB **25.4.17** on nine local processes labelled as three regions, `eu`, `us` and `ap`. All run on one macOS ARM64 host. The native drill can demonstrate configuration, replica placement and a bounded group of process failures. It cannot demonstrate independent regional power loss, WAN latency or a production recovery time.

## Declare regions the cluster can actually provide

A node's startup locality identifies its region and zone. A database then chooses which available cluster regions it uses. These are separate layers: declaring `eu` on a database cannot create nodes or storage in `eu`.

The worksheet starts three labelled processes per region, then creates the database:

```sql
CREATE DATABASE regional PRIMARY REGION 'eu';
ALTER DATABASE regional ADD REGION 'us';
ALTER DATABASE regional ADD REGION 'ap';
ALTER DATABASE regional SURVIVE REGION FAILURE;
```

The primary region is the database's initial home and default for regional tables. The additional regions become eligible homes for data and supporting replicas under the configured policy. Inspect `SHOW REGIONS FROM DATABASE regional` and the resulting ranges; a successful DDL statement alone does not prove that all required replicas have been placed yet.

Database context matters too. An early native attempt created a `REGIONAL BY ROW` table using a qualified name while the session's current database remained `defaultdb`. The following insert failed with SQLSTATE `42P12`: the current database was not multi-region enabled. Use a connection whose current database is `regional`, or explicitly `USE regional`, before the worksheet's locality-dependent statements. A qualified table name does not substitute for every session-level database dependency.

## Give a row the home its work needs

A workshop tenant operating in Europe usually reads and changes its bookings from Europe. A tenant operating in the US may need a different home. A regional-by-row table can keep both in one logical table:

```sql
USE regional;
CREATE TABLE bookings (
  tenant STRING, request STRING, amount DECIMAL(10,2),
  PRIMARY KEY (tenant,request)
) LOCALITY REGIONAL BY ROW;
```

The default regional-by-row implementation adds a hidden `crdb_region` column and partitions the table and its indexes by the row's region. The row's home controls preferred range authority placement; other replicas still exist according to the survival policy. The initial default comes from the inserting gateway's region, so a maintenance job connected through an unexpected gateway must not accidentally choose the business home.

Make locality explicit where the data model requires it. For example, this additional statement assigns a new row to `us` regardless of the inserting gateway:

```sql
INSERT INTO bookings (crdb_region, tenant, request, amount)
VALUES ('us', 't5', 'home-example', 20.00);
```

This is an illustrative variation, separate from the recorded `t4` failure drill. Selecting `crdb_region` explicitly lets the caller check the home it assigned. Routing every request through a European gateway cannot make a US-homed row European; it can instead add a remote lookup. Conversely, choosing a row's home does not enforce who may read it or keep all copies inside that region. Replicas under the survival policy, backups and exports have their own locations. Tenant authorisation, reference integrity and any geographic restriction therefore need separate checks.

The native comparison also creates a global catalogue in the regional database:

```sql
CREATE TABLE regional.catalogue (id INT PRIMARY KEY, name STRING)
LOCALITY GLOBAL;
INSERT INTO regional.catalogue VALUES (7,'Repair basics');
SHOW CREATE TABLE regional.catalogue;
SHOW RANGES FROM TABLE regional.catalogue WITH DETAILS;
```

`SHOW CREATE` retains `LOCALITY GLOBAL`, and the range observation shows the actual replica placement at that time. Placement was still converging when this early catalogue observation was taken, so its initial three-voter range is not evidence that the region-survival policy had already finished applying. The later booking-range gate deliberately waits for the intended count before introducing loss.

A global reference table is attractive when many requests read the same small facts but updates are infrequent. It is less attractive for a remaining-seat counter changed on every booking. “Global” is a read-placement policy, not permission to weaken the counter's current-value or concurrency requirement.

[History, correction and deletion](/review/relational/rl80/) explains why an agreed order amount remains an order fact even if the catalogue is global. Region placement must not turn historical agreements into views of today's reference data.

## A survival goal changes the write path

For the region-survival goal in a three-region database, CockroachDB places five voting replicas across the regions so that losing one region leaves a majority. A representative distribution is two voters in `eu`, two in `us` and one in `ap`. The exact voters and leaseholder vary with placement; inspect the actual ranges instead of assigning permanent authority to a node number.

The additional survival has a normal-operation price. A write whose home region has only two voters needs a voter outside that region to reach three. With real regions, inter-region communication therefore enters the commit path. A zone-survival configuration can optimise for a different loss boundary and keep its normal write quorum nearer the home.

Do not generalise the five-voter count to every object in the cluster. Supporting system ranges, database settings, zone configuration and the exact deployment topology matter. The application also needs a surviving SQL endpoint, credentials, networking, DNS or load balancing and any external service it depends on. Database range survival cannot make an application reachable when its only gateway or identity service is down.

## Verify placement before introducing loss

The worksheet waits until the regional booking ranges report five voting replicas, using a direct observation:

```sql
SELECT count(*) AS ranges,
       min(array_length(voting_replicas,1)) AS min_voters
FROM [SHOW RANGES FROM TABLE regional.bookings WITH DETAILS];
```

It then records the full `SHOW RANGES ... WITH DETAILS` output, including replica localities and the leaseholder. The minimum count alone is not enough: five voters all inside the lost region would not satisfy the goal. The locality columns establish the distribution that gives the count meaning.

A range can be temporarily under-replicated while placement converges. Wait for the intended state and healthy survivors before taking another group down. A deliberate failure drill on an already degraded cluster answers a different question from the commissioned survival goal.

The failure action stops the three processes labelled `eu` while keeping the other six alive. A query through a surviving gateway then tests both a read and a new committed booking. Bringing the stopped group back and reading the accepted records checks that rejoining did not discard the work accepted during the outage. The native record identifies the particular requests and results, rather than inferring success from the surviving processes being live.

During the recorded `eu` process-group outage, the surviving gateway returns the original `region-r1` booking for €20, accepts `region-r2` for €22, and then reports:

```text
count | sum
2     | 42.00
```

After the stopped eu group returned, the query still reported two bookings totalling €42. That is an actual committed foreground result preserved through the permitted group loss and rejoin. The earlier range observation had reached five voters across the labelled regions; the native record retains the exact identities rather than deriving them from process numbering.

This is stronger than a static placement screenshot, but narrower than a geographical disaster test. Shared host memory, disk and networking remain common dependencies. Its elapsed times should not become an availability SLA.

## A cross-region transaction can lose the local advantage

A regional booking and its session counter may be colocated and serve one local transaction well. Add a write to a tenant-independent table homed elsewhere, and the transaction now needs another region even before considering the survival quorum. Adding a global table write can introduce another coordination pattern.

Follow every range touched by the transaction, including secondary indexes and reference checks. Regional-by-row indexes have a region prefix, and a lookup without enough locality information may search beyond the gateway's region. A local hit in one example does not prove every tenant's query stays local.

The query-plan counters in [CockroachDB query work and hot ranges](/review/relational/rl126/) distinguish SQL execution placement from KV work. Use them with actual client locations and a representative transaction mix. Measure current reads, writes, retries and cross-home operations separately; an average dominated by local catalogue reads can hide slow reservation commits.

If the transaction intrinsically needs two homes, choose which coordination and latency the service accepts rather than promising that locality removes it. Changing the data model to avoid the remote write has correctness and reconciliation consequences of its own.

## Keep the failure policy and the lifecycle aligned

Changing a row's home, adding a region or removing nodes can trigger replica and index work. That work consumes capacity and takes time. Do not combine a major topology change with an unrelated index backfill merely because both use SQL DDL.

For a planned permanent removal, use the membership procedure in [Operating and securing a CockroachDB cluster](/review/relational/rl128/). A temporary region outage keeps those members expected to return; decommissioning asks the cluster to move away from them. [CockroachDB backup and recovery](/review/relational/rl129/) supplies a recovery copy for losses that replication cannot repair, including a committed bad change copied to every region.

The configuration decision is concrete: which rows should be convenient where, which failure must leave them writable, and what communication remains necessary when all regions are healthy. Verify those three claims separately before treating a multi-region declaration as the service's complete availability design.

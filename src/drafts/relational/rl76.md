A relational database stores facts in tables and lets you combine them by their values. A workshop session has an identifier, a title and a capacity. A booking names that session and the customer attending it. The database can answer “who has booked this session?” without storing a second customer list inside the session.

It can also make several changes succeed together. Accepting a booking might consume a place and create an order. A **transaction** makes those changes one decision: commit both, or leave neither. Constraints and concurrency control help that decision remain correct when another customer books at the same time.

Those two capabilities belong together. Tables let different questions use the same facts; transactions protect changes that cross those facts. They make relational databases a useful starting point for orders, bookings, accounts and many other applications. The difficult choices begin with how those facts are represented, which changes must agree, and where the system must keep working.

## Follow one booking through the tables

The workshop service serves tenant `t4`. Customer 42 wants a place in session `s7`. Keep the customer, the session and the accepted booking in separate tables:

A booking carries the keys of its customer and session. The customer’s name and the session’s current title have one home. The tenant is part of each reference because customer 42 in another tenant is a different identity.</figcaption></figure>

A **key** identifies a row. Here `(tenant, customer)` identifies a customer, and `(tenant, session)` identifies a session. A **foreign key** can require each booking’s referenced customer and session to exist. These are rules checked by the database, including when a maintenance script bypasses the application.

A query joins the rows whose keys agree:

```sql
SELECT c.name, s.title
FROM bookings AS b
JOIN customers AS c
  ON c.tenant = b.tenant AND c.customer = b.customer
JOIN sessions AS s
  ON s.tenant = b.tenant AND s.session = b.session
WHERE b.tenant = 't4' AND b.booking = 'b17';
```

| name | title |
| --- | --- |
| Ada | Repair basics |

The aliases `b`, `c` and `s` are short names for the three tables. Each `ON` says which rows match. The result combines existing facts; it does not move them into another stored customer list. [Joins and the meaning of a result row](/review/relational/rl81/) follows what happens when more than one row matches.

A changed requirement tests the representation. Ada changes her name. Updating the customer row changes what this current-detail query returns. An order’s agreed price is different: changing today’s session price must not alter yesterday’s purchase. Store that agreed amount on the order as a historical fact. [Relations, keys and normalisation](/review/relational/rl77/) develops that distinction.

“Relational” does not mean every value must be a small scalar or every query must join. Engines can offer JSON, arrays, full-text search and other capabilities. Their presence gives us alternatives to test; it does not establish that all implementations store, index or transact over them in the same way.

## Make acceptance one database decision

Imagine the application first reads two remaining places, creates an order, then crashes before reducing the capacity. Its tables now disagree. Reversing the order creates the opposite failure: a consumed place with no order.

Put the related changes inside one transaction. The following is the *shape* of a booking operation. The application must inspect the conditional update’s result and roll back if it changed no row:

```sql
BEGIN;
UPDATE sessions
SET remaining = remaining - 1
WHERE tenant = 't4' AND session = 's7' AND remaining > 0;
-- Continue only if exactly one row changed.
INSERT INTO orders (tenant, request, customer, amount)
VALUES ('t4', 'r81', 42, 20.00);
COMMIT;
```

`r81` is the stable identity of this purchase request. A unique key on `(tenant, request)` helps prevent another order for the same request. The complete replay protocol, including a reply lost after commit, is in [Retries when a commit reply is missing](/review/relational/rl93/).

The conditional update makes the capacity check part of the write. Reading `remaining` in an earlier request and later writing a calculated number would let two buyers act on the same old value. A transaction alone does not fix every such history. [Transactions and isolation](/review/relational/rl90/) shows which protection the invariant needs.

If acceptance also sends email, record the work to send in the same database transaction and let a worker perform it afterwards. Otherwise a message can be sent for an order that later rolls back. [Outboxes and database-backed jobs](/review/relational/rl94/) completes that boundary, including retries and workers that return late.

## Choose where the database runs

The tables and transaction do not tell us whether there should be a database server. Three versions of the workshop application lead to different starting architectures.

| Situation | Credible starting design | What must be demonstrated |
| --- | --- | --- |
| One organiser’s offline desktop application | SQLite embedded in the application | Local file ownership, short writer transactions, backup and recovery of the application’s file |
| A shared booking service with several application instances | A PostgreSQL, MySQL/InnoDB or SQL Server service | The invariant under concurrent requests, predictable query work, access controls, overload and useful restore |
| A service requiring continued writes through a regional outage | A deliberately placed distributed SQL design, such as CockroachDB, or another architecture that meets that exact requirement | Healthy and degraded write paths, transaction/placement cost, client retries and the specified failure survival |

SQLite executes inside the application process. It avoids a separate database service and coordinates one writer at a time per database file. An application server can itself use SQLite; the browser being remote does not put SQL clients on a shared network file. Growing writer contention or several machines needing direct SQL access changes that decision. Test the application’s actual writer queue rather than reject SQLite from a traffic label.

A conventional server concentrates database access behind a service protocol. Several application instances can use it while the server coordinates their work. This adds connections, authentication, deployment, maintenance and recovery responsibilities. A managed server transfers some of those tasks to a provider; our transaction, schema, query and recovery acceptance still belong to us.

Distributing a database changes more than node count. A purchase may now wait for replicas or authorities in different places. Placing every buyer’s rows nearby cannot make a global quota local to every buyer. First establish the requirement that a conventional service cannot meet, then follow [Sharding and distributed SQL](/review/relational/rl105/).

## Compare actual implementations against the same job

PostgreSQL, MySQL and SQL Server can all serve the shared booking service. A list of supported features does not choose among them. We need to know whether each candidate can perform *our* operation, with the required meaning and operating conditions.

For the first comparison, use PostgreSQL 18, MySQL 8.4 with InnoDB, and a specified SQL Server 2025 edition/deployment. SQL Server’s edition affects available facilities and limits; a hosted SQL service is another concrete contract. SQLite provides the embedded contrast. CockroachDB provides the distributed branch, with its own SQL compatibility and retry obligations.

| Question | Evidence that would change the choice |
| --- | --- |
| Does the application already depend on a dialect, extension, driver or ORM behaviour? | Run representative reads, writes, migrations and error paths on the candidate. “Accepts PostgreSQL connections” is insufficient. |
| What protects the booking invariant? | Execute competing reservations, including absent rows, deadlocks and the actual retry path. An isolation-level name is insufficient. |
| What does the workload cost? | Use tenant skew, result sizes, sustained writes, background maintenance and connection pressure. Include the operating and hosting bill under that workload. |
| What can be recovered? | Restore to an isolated destination and make the application pass its acceptance checks. Include keys, roles, extensions, jobs and useful later orders. |
| Can the team operate and leave it? | Rehearse deployment/change, inspect an incident and test the export or migration path. Include contractual and platform requirements in procurement. |

The choice can reasonably follow existing operating competence when the candidates meet the same needs. Introducing an unfamiliar database buys little if it merely moves an already acceptable latency from one figure to another while making recovery uncertain.

A document store can be credible when the application reads and changes bounded aggregates together. A search service can be credible for ranked discovery. Neither removes the booking invariant. Keep the source of acceptance explicit and account for any extra copies that must remain current.

## Turn the choice into a small acceptance trial

Write down the current decision before collecting more features. For the workshop service it might be: “Use a conventional relational server for shared bookings; retain PostgreSQL as the first implementation because the team can operate it; compare InnoDB and SQL Server if compatibility, platform or cost changes that judgement.” That is a conditional decision we can test and revisit.

The trial needs seeded records, a driver, the critical queries, competing requests and a restore. Record expected business results before timings. A fast run that accepts three bookings into two places has failed. A restore that reaches the target timestamp but cannot authenticate the application has failed too.

Change one requirement next. Take the application offline on one device; add many overlapping writers; then require region survival. Each change should either leave the original choice defensible or supply a specific reason to change it. The collection’s implementation branches give those investigations their necessary detail.

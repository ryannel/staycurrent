A replica keeps another copy of database history on a separate server. It can provide a recovery destination and, where supported, serve reads. The copy advances through several stages: receive the change, make it durable and apply it so queries can see the changed rows.

Those stages need not finish together. A replica can be connected and holding a committed order's log while still answering that the order does not exist. A successful write on the primary therefore does not automatically make a following read safe to route to any replica.

We will follow tenant t4's request r81 and its order o81 through that gap. PostgreSQL supplies a native two-server observation. The replication contract, rather than the word “synchronous”, determines which failure or read the acknowledgement protects.

## One commit has several progress positions

The primary appends changes to its log and commits according to its configured durability policy. A replication sender transmits the log to a replica. The receiver writes it; a flush makes it durable under that storage's contract. Replay, also called apply, changes the replica's database state.

A replication position identifies a prefix of history. It answers “has this replica reached the part containing my change?” more directly than a rounded lag in seconds. Product and topology matter: PostgreSQL LSNs belong to WAL history and timelines; MySQL GTIDs identify transactions; SQL Server exposes its own send, harden and redo positions.

A healthy transport connection proves little about replay speed. A large transaction, a slow disk, a conflicting standby query or competing work can let the receiver move ahead while visible state remains behind.

## Watch receipt advance while reads stay old

Our native PostgreSQL 18.6 drill creates a physical standby from a base backup. Both servers initially contain one marker row named `acknowledged`. We pause WAL replay on the standby, commit a second marker named `replicated` on the primary, then capture a primary WAL position after that commit.

The script waits until the standby's receive position reaches that token. It then asks both about progress and visible rows:

```text
received token?  true
applied token?   false
visible markers: 1
```

Receipt was ahead of the requested commit position; replay was behind it. A new standby SELECT still returned only the first marker. Resuming replay and waiting for the apply position to pass the token made a new statement return both markers.

## Route by what the next read needs

A confirmation page for r81 usually needs **read-your-writes**: it must include the purchase the same caller was just told completed. A public catalogue may tolerate a short delay. A report may prefer a stable earlier snapshot over the newest value. These requests need different routes.

Primary affinity is simple: after a write, route that session's dependent reads to the current primary. It can cost primary capacity or cross-region latency. A fixed “use the primary for five seconds” window is an operational heuristic, not a proof that the replica has caught up when the window expires.

A replication barrier can be more precise. Return or retain a token at or after the operation's commit, choose a replica and wait until its apply position covers the token. Then begin a new snapshot and read. If the wait exceeds the request's budget, use the primary or return a pending answer. A transaction that already established an old snapshot does not become fresh merely because the apply position advanced beside it.

```text
write r81 on authority → commit succeeds → capture token T
next request chooses replica R
R applied through T? → yes → begin fresh read → return o81
                     → no  → bounded wait, primary fallback or pending
```

The token must identify the right replication history. After promotion, do not compare a bare number against an unrelated or divergent stream and declare success. A routing service must understand the current authority, timeline or equivalent transaction history, and what the failover lost.

A **bounded-staleness** contract is another option: serve from a view no older than a chosen bound. It needs an engine-supported safe boundary or a verified application mechanism. A metric saying “lag was low a moment ago” does not guarantee the next read's age.

The application must also avoid using a stale absence as proof that an uncertain purchase failed. [Operation recovery](/review/relational/rl93/) needs authoritative identity coordination, even when catalogue reads normally use replicas.

## Synchronous acknowledgements wait for different things

A primary can wait for a replica before replying, reducing some data-loss windows. Ask which replica stage must finish and how many independent copies must reach it.

<table><caption>Replication acknowledgements that are often grouped under “synchronous”</caption><thead><tr><th>Contract</th><th>What it buys</th><th>What it does not establish</th></tr></thead><tbody>
<tr><td>Local durable commit only</td><td>Survives the stated local crash</td><td>A failover destination has the commit</td></tr>
<tr><td>Remote receipt/write</td><td>A remote system has received written log</td><td>That system survives wider failure or can already query it</td></tr>
<tr><td>Remote durable flush/harden</td><td>A remote durable copy can recover the commit</td><td>Replay has made it visible to ordinary replica queries</td></tr>
<tr><td>Remote apply</td><td>The selected replica applied the commit before acknowledgement</td><td>Every replica applied it, or an old snapshot sees it</td></tr>
</tbody></table>

PostgreSQL exposes remote-write, flush and remote-apply waits through different `synchronous_commit` levels when synchronous standbys are configured. InnoDB's MySQL semisynchronous replication waits for a replica's receipt and relay-log persistence, rather than its SQL apply; timeout behaviour can fall back to asynchronous operation. SQL Server synchronous-commit availability groups wait for log hardening on participating secondaries, with redo a later stage. Check the actual configuration and failure transition for each.

Stronger waits spend latency and availability. If the required remote copy is unavailable, a commit may wait even while the local server and data are healthy. Relaxing that wait to restore service changes the acknowledged loss budget. Record that decision rather than letting a monitoring label imply the previous guarantee still holds.

SQLite core has no separate network replica service with these stages. A copied SQLite file or an external replication product needs its own consistency and acknowledgement contract; its name cannot inherit PostgreSQL's protocol.

## Lag is work accumulating somewhere

Separate generation, network transfer, durable receipt and replay rates. If the primary generates 20 MB/s of log while a replica applies 15 MB/s, backlog grows by 5 MB/s. Adding 10 GB of disk delays exhaustion; it does not close the rate gap. Catch-up also needs spare throughput above the continuing write rate.

A lagging replica or replication slot may retain logs on the primary. Archive failures can do the same. Monitor retained bytes and free-space runway alongside progress, and know whether the configured limit invalidates the consumer or risks filling the primary. Removing a slot can free retention while destroying the consumer's ability to resume; that choice requires a rebuild plan.

Long standby reads can conflict with replay. Depending on the engine and settings, the database may cancel those reads, delay replay or preserve history on the primary. Report freshness, replay rate and primary cleanup are one operating tradeoff, not three independent knobs.

Read replicas can move read work off the primary, yet each must still receive and apply relevant writes. They do not divide the primary's write authority into independent shards. [Sharding and distributed SQL](/review/relational/rl105/) addresses that different scaling choice; [failover and fencing](/review/relational/rl98/) addresses who may write after a failure.

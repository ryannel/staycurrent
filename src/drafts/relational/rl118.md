Logical replication sends changes to published tables rather than reproducing every physical page. A subscriber starts with a copy of selected rows and then applies later changes. That makes it useful for a selected read model, moving tables or feeding another installation with a compatible schema.

The selectivity is also a boundary. A subscriber does not automatically contain the source’s roles, schema changes, sequence progress or every kind of stored object. Row replication can be healthy while the subscriber remains unsuitable as an application’s replacement writer.

Our workshop exercise copies only tenant `t4`, changes an order’s status, restarts the subscriber and deliberately introduces an incompatible schema. The [native replication lab](/review/relational/evidence/rl110-native.py) runs a real PostgreSQL 18.6 publisher on port 56810 and an independently initialised subscriber on 56812.

## The publication names the data contract

Both servers start with this table. The tenant belongs in the primary key and request uniqueness; another tenant may use the same local identifiers.

```sql
CREATE TABLE feed_orders (
  tenant text, order_id text, request_id text, price numeric,
  status text DEFAULT 'pending',
  serial_id bigint GENERATED BY DEFAULT AS IDENTITY,
  PRIMARY KEY (tenant, order_id),
  UNIQUE (tenant, request_id)
);
```

The publisher starts with `t4/o81/r81` at the agreed price 20 and `t5/o90/r90` at 90. Only `t4` is published:

```sql
CREATE PUBLICATION workshop_feed FOR TABLE feed_orders
WHERE (tenant = 't4');
```

The subscriber’s matching table is empty. It creates a subscription using an explicit source endpoint:

```sql
CREATE SUBSCRIPTION workshop_sub
CONNECTION 'host=127.0.0.1 port=56810 dbname=postgres user=lab'
PUBLICATION workshop_feed;
```

The lab’s local trust and superuser connection keeps setup disposable. A deployed subscription requires an authenticated replication connection, appropriate publisher table access and subscriber-side ownership/apply privileges. Treat the connection credentials and stream as privileged data access.

The subscriber eventually has exactly `t4/o81`. `t5/o90` is absent. An existing source row need not have changed after subscription creation to appear: the initial table synchronisation copied it.

## Initial copy and subsequent changes meet at a boundary

The initial copy and ongoing stream must meet without a gap. PostgreSQL coordinates the snapshot and replication progress while synchronising tables. `pg_subscription_rel` shows their states:

```sql
SELECT srrelid::regclass, srsubstate FROM pg_subscription_rel;
SELECT subname, pid, received_lsn, latest_end_lsn
FROM pg_stat_subscription;
```

Our table reached state `r`, ready for normal replication. A connection being present is weaker evidence than a table having completed its initial synchronisation and a known change having appeared.

On the publisher:

```sql
UPDATE feed_orders SET status = 'confirmed'
WHERE tenant = 't4' AND order_id = 'o81';
```

A fresh subscriber query eventually reads `confirmed`. The price stays 20: status progression does not overwrite the historical agreement. The replication is asynchronous in this fixture, so the source commit’s reply does not promise immediate visibility at the subscriber.

The harness stops the subscriber, inserts `t4/o82/r82` at 25 on the publisher, then starts it again. Its logical slot becomes inactive during the outage and retains WAL. After restart the subscriber contains two orders. Keep `o82` in place for the schema-change test below.

Changing a publication’s table set requires coordinating schema, refresh and initial-copy choices at the subscriber. Do not assume that adding a table at the publisher immediately establishes a complete destination table. Row filters also affect which updates can be represented; the replica identity must cover columns required by an update/delete filter.

## Update and delete need row identity

An insert supplies a new row. An update or delete must identify the existing destination row. A primary key normally supplies that **replica identity**.

In a separate publisher-side test, the lab adds another published table with no key:

```sql
CREATE TABLE no_identity (tenant text, order_id text);
INSERT INTO no_identity VALUES ('t4','x');
ALTER PUBLICATION workshop_feed ADD TABLE no_identity;
UPDATE no_identity SET order_id = 'y';
```

The publisher rejects the update:

```text
ERROR: cannot update table "no_identity" because it does not have
       a replica identity and publishes updates
```

The lab completes the repair by adding a tenant-aware primary key and repeating the update:

```sql
ALTER TABLE no_identity ADD PRIMARY KEY (tenant, order_id);
UPDATE no_identity SET order_id = 'y';
-- UPDATE 1; the row is now t4/y.
```

A table without a key is therefore not merely a slower choice. Its update contract is incomplete for this publication. Choose a stable primary key, a suitable eligible unique index via `REPLICA IDENTITY USING INDEX`, or deliberately assess `REPLICA IDENTITY FULL`.

Full identity sends old row values and can require more transfer and destination lookup work. Its support depends on the destination’s types and usable comparison/index operators. It does not repair an unstable business identity or make unrestricted subscriber writes safe.

The tenant-aware key avoids matching a row from the wrong tenant. A destination that changes its key or collapses tenants needs an explicit transformation outside this simple native apply contract.

## DDL is not in the row stream

The source adds a note column and updates it:

```sql
-- Publisher
ALTER TABLE feed_orders ADD COLUMN note text;
UPDATE feed_orders SET note = 'new-schema'
WHERE tenant = 't4' AND order_id = 'o82';
```

The subscriber does not acquire the column. Its apply worker logs:

```text
logical replication target relation "public.feed_orders"
is missing replicated column: "note"
```

The worker fails and retries. The subscription object still exists, but the new row change is not applied. Looking only for the object’s existence would miss a broken feed.

The lab repairs the destination schema:

```sql
-- Subscriber
ALTER TABLE feed_orders ADD COLUMN note text;
```

On retry the note arrives on `o82`. Only after that repair does the lab delete `o82` on the publisher and wait for its removal on the subscriber. The subscriber returns to one order.

For a compatible additive change, updating the subscriber first generally avoids this interruption: an unused nullable destination column can exist before the publisher starts sending it. Later incompatible changes need a deployment sequence for both ends, including the period when old application versions still run.

The destination may intentionally have extra tables or a different compatible structure. That flexibility requires explicit ownership of schema deployment and acceptance. It is not an automatic upgrade of the whole installation.

## Replicated values do not advance a sequence

The initial `o81` carries `serial_id=1` across to the subscriber. After the insert/delete variation, its local identity sequence still reports `last_value=1, is_called=false`. Inserting a new row with its default would request 1 again.

Sequence state is not part of this native row stream. The row’s explicit identity value replicated; the sequence generator did not progress with it. A uniqueness constraint may reject the collision, or a schema without a suitable uniqueness rule may accept a duplicate local number.

If the subscriber will become a writer, stop and fence source writes, catch up the intended stream and repair sequence state from a verified final source position or a safe value derived under the fence. With incrementing positive IDs, a value at or above the accepted maximum can be appropriate; non-default sequences need their actual increment, bounds, cycle and allocation policy considered.

Also inventory large objects, roles, privileges, extensions, functions, triggers and tables outside the publication. A complete replacement requires each dependency to have a tested home. [Upgrading and migrating PostgreSQL](/review/relational/rl122/) follows the authority switch and acceptance boundary.

## Subscriber writes create another conflict source

The lab treats published destination rows as owned by apply. Ordinary writes to them can conflict with incoming primary keys, updates or deletes. A duplicate key can stop apply instead of producing a useful merged record.

Separate locally owned derived data when possible, and define any transformation/rebuild protocol explicitly. Turning replication off, modifying conflicting rows and restarting without understanding the source history can discard accepted changes or repeat a conflict.

Inspect the apply log, subscription statistics, relation readiness and source slot before intervening. Some failures are data conflicts, others are missing schema or permissions. Their repairs differ. Skipping a transaction is a correctness decision about all its effects, not a harmless way to move an LSN forward.

## A general change-feed consumer owns more work

Native subscription apply already knows how to write PostgreSQL rows and retain replication progress. A service consuming decoded changes into a search index, object store or remote API needs its own contract.

It must persist where the initial snapshot meets the stream, distinguish transaction/order boundaries, identify events or rows stably and advance its durable checkpoint only after the intended effect is safe. If it crashes after the effect but before checkpointing, replay is possible. The sink needs an idempotent operation identity or a version/position check that rejects obsolete updates.

A database commit position does not automatically make a remote email or HTTP request exactly once. Nor does a per-table stream necessarily provide an application’s desired global ordering across independent subscriptions and consumers. Keep the required ordering as narrow and explicit as the invariant needs.

Source retention completes the protocol. An offline consumer can hold WAL and catalogue history. Monitor `restart_lsn`, `confirmed_flush_lsn`, slot activity and storage budget. If required history is no longer retained, the consumer may need a new snapshot and handover rather than simply reconnecting from an unavailable offset.

Logical replication is useful precisely because it can carry a chosen part of the database into another role. Choose it with that part and its missing responsibilities named: schema, identity, replay, retention and any eventual write authority.

A CockroachDB cluster remains useful only while clients can reach the right authority and its ranges retain enough healthy replicas to act. Security and operation meet at that boundary: a node must establish its cluster identity before it can hold replicas, and a client must authenticate before its SQL privileges matter.

A failed connection, denied statement and unavailable range therefore need different repairs. Disabling TLS will not restore a missing quorum. Granting administrator privileges will not fix a wrong server name. Adding a node will not help if it cannot authenticate or if placement rules prevent its storage from being used.

The native workshop lab uses CockroachDB **25.4.17**, locally issued certificates and loopback listeners on one macOS ARM64 host. It tests real TLS connections and SQL permissions. Locality labels and stopped processes expose membership behaviour; they do not create independent physical failure domains.

## Establish trust before testing SQL permissions

The lab creates a certificate authority, then a node certificate whose names include `localhost` and `127.0.0.1`. Each server starts with the certificate directory and advertises a name clients can verify. A root client certificate supplies the bootstrap SQL identity.

The client verifies both the issuing authority and the requested host. Connecting to an address absent from the certificate's names is a different failure from trusting the wrong CA. Client certificates also have a principal: the `booking_app` certificate identifies that SQL user. Merely copying the root client's URL and changing a username does not create the corresponding client identity.

Keep the CA signing key outside the ordinary node deployment path, restrict private-key access and distinguish node certificates from application-client certificates. The worksheet's shared temporary certificate directory makes the disposable experiment repeatable; it is not a production key-distribution design. Certificate renewal and revocation also need a tested procedure for the chosen identity mechanism. A functioning certificate today says nothing about the effect of its expiry tomorrow.

## Test the least-privileged identity directly

The administrator creates a deliberately read-only application identity:

```sql
CREATE USER booking_app;
GRANT CONNECT ON DATABASE workshop TO booking_app;
GRANT USAGE ON SCHEMA workshop.public TO booking_app;
GRANT SELECT ON TABLE workshop.sessions TO booking_app;
```

The lab also issues a client certificate for `booking_app`, then opens a new connection authenticated as that user. It does not simulate the user by running a successful statement as root.

```sql
SELECT * FROM workshop.sessions;
```

```text
tenant | session | remaining
t4     | s7      | 1
```

The new connection uses `workshop` as its current database. On that same identity, an update is denied:

```sql
UPDATE sessions SET remaining = 99;
```

```text
ERROR: user booking_app does not have UPDATE privilege on relation sessions
SQLSTATE: 42501
```

The read and denied write are a useful pair. The first proves connectivity, authentication and the intended read grant. The second proves that this identity cannot take a write path merely because it connected successfully. Check the post-state when testing a mutation boundary, and keep both success and rejection in the deployment evidence.

This fixture's table-level grant permits reading every row in `sessions`, not only tenant `t4`. It does not establish a tenant isolation policy. A production service must supply that access boundary through trusted queries and, where appropriate and supported, row policies or a different ownership design. Composite keys still protect references separately, as [Constraints and tenant boundaries](/review/relational/rl79/) explains.

An absent privilege can be intentional. Before repairing `42501`, identify the authenticated user, its inherited roles, object ownership and the exact operation it should perform. Giving `admin` to a reporting client because one write failed removes the very boundary the test demonstrated. Use separate identities for ordinary application work, schema changes and cluster administration.

## Repair trust before adding a member

A [separate native drill](/review/relational/evidence/cockroach-identity-observed.json) starts a fresh three-node cluster, then tries to join a fourth process using a different certificate authority. The new process cannot verify the cluster's certificate. Its join log reports:

```text
transport: authentication handshake failed:
tls: failed to verify certificate:
x509: certificate signed by unknown authority
```

The existing membership listing still contains three nodes, and a foreground query returns session `s7` with two places remaining. A running fourth process has not become a useful cluster member merely because its listener started.

The worksheet stops that process and restarts its same fresh store with certificates from the intended lab CA. Membership now lists four nodes, and a query through the new member returns the same session and capacity. The change repaired the failed trust boundary; no SQL privilege grant or replication setting was needed to make an unknown issuer trusted.

This supplemental fixture starts with two places, separately from the accumulated worksheet used for the read-only result above. The [drill source](/review/relational/evidence/lab/cockroach_identity.py) retains the certificate setup, exact failed join, corrected restart and foreground probes.

## Replacing a certificate does not retire the old identity

The same fresh drill creates `booking_app` with the read-only grant above and issues its client certificate. It saves the old certificate and key, then generates a replacement for that same user. The public certificate's fingerprint changes, and a fresh connection using the replacement can read the session.

A fresh connection using the saved old certificate can still read it too. Replacing files on one client did not revoke another valid certificate signed by the same trusted authority. Both authenticate the same SQL identity and inherit its authority.

To retire that identity, the administrator sends:

```sql
ALTER USER booking_app WITH NOLOGIN;
```

New connections using either certificate now fail with `28000`, reporting that `booking_app` lacks login privilege. A replacement identity, `booking_app_v2`, receives only the same database/schema access and table SELECT grant. Its newly issued certificate can read the session, while UPDATE remains denied with `42501`.

This tests retirement at the new-connection boundary. It does not terminate or test already pooled sessions. An operational change must account for those sessions separately, and a certificate-revocation design must use the chosen PKI's supported mechanism. Keep certificate renewal, SQL identity retirement and session termination as distinct operations.

Keep both certificate copies visible while changing the SQL login’s status. A fresh connection using either copy reaches the same identity; an already authenticated pool connection belongs to a separate boundary.

## Observe nodes and ranges separately

The supported native surfaces used here are:

```sql
SHOW RANGES FROM TABLE workshop.events WITH DETAILS;
SHOW COLUMNS FROM crdb_internal.kv_store_status;
```

The CLI adds membership and storage context:

```bash
cockroach node status --host=localhost:56901 \
  --certs-dir="$lab_certs" --ranges --stats
```

`lab_certs` denotes the worksheet's certificate directory. The complete start flags and certificate setup are in the [lab record](/review/relational/evidence/cockroach-observed.json).

Node status answers whether a member is live and available at that observation. Range details answer where a particular span's replicas and leaseholder sit. A live node can hold no useful replica for the failing query; a cluster can accept one query while another range lacks authority. Follow the actual table/index span from the affected statement.

Do not assume an internal view name from another release. An earlier worksheet query for `crdb_internal.replication_stats` failed because that relation was absent. The repaired observation uses `SHOW RANGES` and discovers the columns of the internal store view before depending on them. Treat internal diagnostic interfaces as version-specific, and keep the exact query with the observed release.

A newly joined cluster can briefly show placement still converging. A successful SQL ping is not the same as every range reaching its intended voter count. Wait for the configured replication and placement requirements before beginning a failure drill or removing another node.

## Distinguish slow work from lost authority

A query that spends time in contention needs a different intervention from one waiting for storage, admission or a missing quorum. Connect the statement's plan and contention evidence to node CPU, memory, disk and replica state. [CockroachDB query work and hot ranges](/review/relational/rl126/) follows the SQL-to-KV work; the operation here is to identify which resource or authority is unavailable.

Disk headroom supports more than foreground data. Replication and rebalancing need destinations that can accept copies. Schema jobs and restores create overlapping state. Old versions retained by protected timestamps or long-lived consumers can also delay reclamation. A node removal that requires another copy cannot finish merely because the remaining disks have some free bytes; the placement and usable-capacity requirements must both be satisfied.

Use bounded admission and client concurrency while diagnosing pressure. Retrying every slow transaction immediately can add work to the overloaded ranges. Preserve retry identity and the whole transaction boundary, then reduce or defer competing work rather than converting one symptom into a retry storm. [CockroachDB transactions and retries](/review/relational/rl124/) supplies that programming contract.

## A temporary stop is not a permanent removal

For a temporary restart, drain or stop the node under the documented procedure and bring its same identity and store back. Draining moves activity away and lets connections finish where possible; the cluster still expects the member to return.

For permanent removal, decommissioning changes that expectation and moves replicas to other members. First discover the **node ID** from status. It is not the listener's numeric suffix or the order the process was started: the worksheet's node IDs can differ from its port numbers.

```bash
cockroach node decommission "$removal_node_id" \
  --host=localhost:56901 --certs-dir="$lab_certs" --wait=all
```

The command is a procedure template: set `removal_node_id` from the inspected status of the intended member. With `--wait=all`, the command waits until replicas on the specified nodes have moved to other nodes. Inspect the resulting placement and application results as well. Do not wipe the member's store merely because a request to begin decommissioning returned.

In the native nine-process drill, the listener at `localhost:56909` belonged to **node ID 5**. The decommission command's successive observations reduced its replica count from 27 to zero. Its final message said that no more data was reported on the target node and asked the operator to verify cluster health before removal. The worksheet then stopped that process and queried the surviving cluster:

```text
regional bookings: 2
sum(amount):       42.00
```

The recorded booking ranges no longer list node 5 among their replicas. This verifies relocation and this foreground result after the planned removal. It does not measure behaviour when disks are full or placement constraints make removal impossible; those are separate failure conditions to inspect before beginning the operation.

If relocation stalls, keep the source available while checking free capacity, locality constraints and unhealthy destination nodes. Removing additional members to “finish faster” can destroy the replicas the relocation needs. If enough voters for a range are permanently lost, normal membership changes cannot manufacture the missing authority from an arbitrary surviving copy. Recovery then needs a supported disaster-recovery procedure and an explicit data-loss decision.

The separate [table-locality failure drill](/review/relational/rl127/) stops all processes carrying one region label and verifies foreground work from another. That demonstrates the configured placement under a bounded process outage. A planned decommission tests another promise: after replicas move away, the member is no longer needed for that configured topology.

## Accept the service, not just the command

After a node returns or is removed, query known application records, verify the expected voter and placement state, and check that clients use reachable endpoints with valid identities. The surviving database can be correct while a client pool keeps trying only the departed gateway.

Keep backups outside the cluster's shared failure boundary, protect their access separately and test the restored application's role. Replication preserves a committed mistake, and TLS does not make a backup readable after its keys or credentials are lost. [CockroachDB backup and recovery](/review/relational/rl129/) closes that part of the operating contract.

Moving an application to CockroachDB changes more than the server behind its connection URL. A driver may still connect through the PostgreSQL wire protocol while a constraint, type conversion or transaction outcome behaves differently. The migration must preserve the application's contract, including the awkward writes and failures that a simple read-only smoke test never exercises.

It must also decide which database may accept work. A copied target is a candidate until the source is fenced, the chosen source state is accounted for and the target becomes the authority. Once the target accepts an order absent from the source, returning traffic to the source needs reconciliation.

This rehearsal uses a **bounded offline window**. It stops source application writes, exports one PostgreSQL snapshot, copies it into CockroachDB **25.4.17**, and compares the resulting workshop records. No live change-data-capture pipeline or zero-downtime cutover is claimed. Both engines run locally; the example tests compatibility and authority, not production migration throughput.

## Start with a source behaviour that matters

The source has session `s7` in tenant `t4` and request-keyed orders. Request `r81` identifies the accepted purchase in this small fixture; an application with a separate order ID such as `o81` must preserve that identity and its request mapping too. The agreed price is a historical fact and must not be recomputed from a current catalogue during migration.

The PostgreSQL schema permits a reference to be checked at commit:

```sql
CREATE TABLE sessions (
  tenant text, session text, remaining integer,
  PRIMARY KEY (tenant,session)
);
CREATE TABLE orders (
  tenant text, request text, session text, amount numeric(10,2),
  PRIMARY KEY (tenant,request),
  FOREIGN KEY (tenant,session) REFERENCES sessions(tenant,session)
    DEFERRABLE INITIALLY DEFERRED
);
BEGIN;
INSERT INTO orders VALUES ('t4','r81','s7',20.00);
INSERT INTO sessions VALUES ('t4','s7',1);
COMMIT;
```

The order is inserted before its session. PostgreSQL accepts the completed transaction because the session exists when the deferred constraint is checked. A source compatibility test that only selects the resulting rows would hide this dependency on write order.

The target test attempts the equivalent deferred foreign key. The pinned CockroachDB version rejects the unsupported deferred-check syntax with SQLSTATE `0A000`. Removing the unsupported clause is not yet a repair: it creates an immediate foreign key, which changes when the writer must have made the parent visible.

## Change the writer without weakening the invariant

The target schema retains the composite tenant/session reference and checks it immediately. Replaying the old child-first sequence then fails at the order insert with SQLSTATE `23503`, before the parent statement can repair it. The transaction has not produced the accepted purchase the source sequence produced.

The repair is to insert the parent first, then its child in the same transaction. That changes a sequencing dependency while preserving the committed-state rule. Dropping the foreign key would instead remove the rule from every writer.

Real schemas may have cycles where a simple parent-first ordering is impossible. Resolve that design explicitly: an optional relationship filled later in the same supported transaction, an intermediate domain state with its own invariant, or a different representation. Reject the move if the required contract cannot be preserved. Do not replace a database-enforced rule with “the application normally does this” without accepting the weaker guarantee.

## Test the rest of the application contract

Use representative statements and values, not only a schema translator. Exact decimals, integer widths, timestamps, collations, JSON operators, generated columns, sequences and extension-dependent values need a deliberate source-to-target mapping. A successful cast can still round, shift a zone or compare differently.

Identity needs special care. A tenant's local customer `42` must not begin identifying another tenant's row after keys or indexes are redesigned. Preserve the reference pair everywhere. Preserve stable request `r81` across retries and imports, rather than generating a fresh request key when the new driver receives an uncertain reply.

CockroachDB's transaction behaviour also belongs in the port. A serializable conflict can surface as SQLSTATE `40001`; a correct retry repeats the required transaction from a new attempt, including the reads that informed its decision. Repeating only the final insert can preserve a decision that was rejected. An email or payment call inside the repeated callback can run twice even if the database commits once.

[CockroachDB transactions and retries](/review/relational/rl124/) executes that conflict and teaches the retry boundary. [Retries when a commit reply is missing](/review/relational/rl93/) distinguishes a known rejection from an uncertain commit. The migration should test both through the chosen driver and pool; it cannot infer their handling from the server accepting `BEGIN`.

## Fence the source's actual write identity

A maintenance-page banner only stops cooperative clients. A forgotten worker or old application instance can still write if its database identity retains permission. The native source uses a dedicated `source_app` role, and the rehearsal revokes its mutation grants:

```sql
REVOKE INSERT, UPDATE, DELETE ON sessions, orders FROM source_app;
```

A new write attempted as `source_app` is then denied:

```text
ERROR: permission denied for table orders
```

The administrator can still read for export; that privileged path is held outside ordinary application admission.

This is a bounded fence for the fixture's named writer. A production cutover must account for every writable role, privileged worker, scheduled job and open transaction. Revoking one role's grants does not terminate already completed work or prove that no other authority exists. Drain admitted work, resolve uncertain requests, then verify that the source cannot accept a new ordinary write under the old service.

The source can remain available for read-only checks during the copy. Keep its identity and access controls distinct from the destination's credentials, so changing a pool endpoint cannot quietly reopen the former writer.

## Export one state and copy in reference order

The worksheet opens a PostgreSQL Repeatable Read, read-only transaction and exports sessions and orders from the same snapshot. It uses a small JSON representation to carry the entire fixture, including ordered identities and exact agreed amounts. That is convenient for this bounded test, not a proposed transfer format for a large installation.

The captured source payload contains the one session and one order:

```json
{"sessions":[{"tenant":"t4","session":"s7","remaining":1}],
 "orders":[{"tenant":"t4","request":"r81","session":"s7","amount":20.00}]}
```

The fixture uses integral euro amounts. A larger transfer must preserve decimals through its parser and binding layer, for example as exact decimal values or validated strings; routing arbitrary prices through binary floating point would weaken the source type contract. The source rehearsal is also ASCII-only and does not establish an encoding/collation migration for arbitrary text.

The destination already has the repaired immediate-reference schema. The copy transaction inserts sessions first, then orders. Before granting it authority, compare the copied identities, amounts, references and remaining capacity with the exported source state. Count and total are useful summaries, but equal totals alone cannot detect two swapped identities or compensating errors. Preserve a sorted identity-level comparison for the real dataset.

The actual corrected copy reports `1, 20.00` for order count and sum. After the target-only request, its result is `2, 42.00`; the fenced source still reports `1, 20.00`. Reconciliation later changes the source to `2, 42.00`. These small summaries accompany the captured identities, rather than substituting for them.

In a larger offline migration, use a tested export/import mechanism, enough outage budget and a documented restart point. Check invalid and rejected records rather than declaring completion from a process exit code. If the data volume makes that window unacceptable, an online design needs a separately proved catch-up protocol: one source boundary, a complete snapshot, ordered change capture, deletion handling and a final cutover position. This rehearsal supplies none of those live-CDC guarantees.

## A target-only order changes the return path

After copy acceptance, the target takes a new request `r82` for €22 and consumes the remaining seat. It now contains two orders totalling €42. The old source still contains only `r81`, totalling €20, and still reports one remaining seat.

The native worksheet demonstrates the stale source, then repairs it by inserting `r82` and setting the correct remaining capacity in one transaction. The source then also has two orders totalling €42. A real return must first fence the target, capture all accepted target work and make replay safe through stable identities. It must include cancellations, dependent rows and external effects, not just the one visible amount.

If new target data cannot be represented in the old schema, that is another closed return boundary. The choice becomes a forward repair, a transformation with an explicit loss policy, or remaining on the target until compatibility is restored. Keep that decision separate from whether the old server can start.

## Make acceptance a service decision

Before reopening traffic, verify clients, schema jobs, permissions, backups, monitoring and the request outcomes the service promises. Exercise a conflict, a rejected constraint and an interrupted connection with the actual application code. Compare latency and resource use under representative workload after correctness is established; the old query plan is not portable performance evidence.

The bounded rehearsal has a useful end: an actual source behaviour fails on the target, its writer is repaired, the source's application identity is fenced, one consistent state is copied, and later accepted work is reconciled before a hypothetical return. That is enough to test this migration contract without claiming an unbuilt online migration system.

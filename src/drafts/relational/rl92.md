An update changes the value future readers should see. It cannot always erase the value earlier readers still need. A report may be halfway through a snapshot of the workshop's orders when another transaction changes a record. The database needs enough history to finish the report consistently and enough information to discard unfinished changes.

Where that history waits shapes the cost of writes. PostgreSQL keeps replacement row versions in the table. InnoDB keeps undo records behind a current row. SQLite's WAL can preserve a reader's earlier page view. These arrangements provide related abilities through different storage work.

We will follow tenant t4's catalogue price, then a long report that outlives several rounds of updates. Prices already agreed on an order remain historical facts: changing today's catalogue must not rewrite order o81's agreed price.

## A row lives inside a page

Relational engines move fixed-size blocks called **pages** between storage and their memory cache. PostgreSQL normally uses 8 kB pages; InnoDB defaults to 16 kB; SQLite defaults to 4 kB. A request for one value can therefore bring a whole page into memory.

A row needs more than its application values. Headers describe its columns and visibility; a small page entry locates it. Free space lets later inserts and updates fit. A rough `row count × application bytes` estimate leaves all three out, as well as indexes and history.

In a **heap**, rows occupy pages wherever space is available. PostgreSQL indexes point to a page and item number. In a **clustered table**, the bottom pages of a key-ordered tree contain the rows themselves. InnoDB uses its primary key for that tree; its secondary indexes carry that key to find the row again. SQLite rowid tables use an integer rowid; WITHOUT ROWID tables use their declared primary key. SQL Server offers both heaps and clustered indexes.

A short, stable key limits that repeated locator cost. Random new keys spread inserts through the tree and can split full pages; increasing keys concentrate inserts at the end. A heap has different costs, including extra index references when replacement versions move. [Indexes and access paths](/review/relational/rl86/) follows the searches and writes in detail.

## One value, two visible histories

Suppose a report takes a snapshot while a catalogue item costs 20.00. Another transaction changes the current price to 22.00 and commits. A later query reads 22.00; the report must still read 20.00.

**Multiversion concurrency control**, or MVCC, is the use of these retained versions to let overlapping transactions read appropriate values. A snapshot determines which changes were committed and visible at its boundary. The older reader's view is not invalid just because a newer value exists.

PostgreSQL marks an old version as replaced and writes a new version. A transaction that aborts leaves its new versions invisible; cleanup can reclaim them later. InnoDB can undo a failed writer by applying undo information. This difference also changes the cost of rolling back a very large transaction.

Indexes must still reach the version a query can see. PostgreSQL can sometimes keep its old index entries and follow a chain on the same heap page, called a HOT update. It requires room on that page and no relevant indexed column change. Otherwise replacement versions generally add index work. InnoDB changes the clustered row and updates affected secondary indexes; an old reader may reconstruct an earlier row using undo.

## A long reader sets a retention boundary

The oldest snapshot that might need history creates a **cleanup horizon**. Committing the writer does not by itself move that horizon. A report left open for an hour can keep history needed to answer its old view while thousands of newer transactions complete.

We tested this on PostgreSQL 18.6 with 1,000 rows. Each row had an integer value and a 100-character padding field. A Repeatable Read connection established its snapshot at value zero. A separate connection updated every value five times, committing each round. Automatic vacuum was disabled only on this disposable table so we could control cleanup.

```sql
-- Reader A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT sum(v) FROM churn; -- 0

-- Writer B, five committed rounds
UPDATE churn SET v = v + 1;
```

After the five rounds, a new reader saw current values of 5. A still summed to zero. We ran VACUUM and inspected the physical table with `pgstattuple`, which scans the relation rather than relying on an estimated dead-row statistic.

Ending A allowed cleanup to reclaim 5,000 obsolete versions. The file stayed the same size. Those are two different outcomes: the engine can reuse interior space without returning it to the operating system.

A high dead-row estimate is therefore a starting observation, not a reason to repeatedly run a larger cleanup command. If a horizon still pins the rows, another pass cannot make them removable. Find what owns the old view and whether it is still useful. A legitimate long report may need a separate replica, a bounded export, or a design that tolerates a newer view between batches. Killing it loses its work.

Readers are not the only retention owners. Replication settings can retain row history or logs for downstream consumers. A failed replication consumer can fill storage even when application tables barely change size. Row-version retention and log retention are related operating concerns with different owners; [replicas and lag](/review/relational/rl97/) explains that distinction.

## Cleanup does not compact every file

A delete marks facts as no longer current. Older readers may still need them; after that need ends, cleanup makes their space reusable. New writes refill gaps only where the storage layout allows.

A key-ordered append workload may keep adding pages at the high end while gaps remain among older keys. A heap may reuse interior free space yet retain sparse pages. Indexes can also stay large after most entries disappear. File size alone cannot tell you whether a rewrite would save enough work to justify its cost.

A rewrite needs space for the new copy, extra writes and a controlled cutover. It can block, retain old copies for concurrent readers or generate substantial log. Rewriting because the disk is almost full can exhaust the last headroom before it saves anything. Measure live density and the workload first, then choose a product-specific maintenance method.

Wide values complicate density further. Engines can compress or move large values to overflow storage, leaving a pointer or a prefix in the row. A query for a price may avoid fetching the description, while `SELECT *` demands it. Small values below the overflow threshold remain on the main pages and reduce rows per read. Measure the whole table, overflow storage and indexes when estimating physical work.

## Where each engine charges for old readers

<table><caption>Version retention and space reclamation differ by implementation</caption><thead><tr><th>Engine</th><th>Retained history and useful consequence</th></tr></thead><tbody>
<tr><td>PostgreSQL</td><td>Old versions occupy heap space and can retain index entries. VACUUM reclaims eligible history and generally preserves interior file space. Rewriting is a separate operation.</td></tr>
<tr><td>InnoDB, MySQL 8.4</td><td>Consistent readers can keep undo history alive until purge can advance. The current clustered row does not show the full retained history cost. Tablespace layout affects what a rebuild returns to the operating system.</td></tr>
<tr><td>SQL Server</td><td>Snapshot-based isolation stores versions in tempdb, or in a persistent version store when accelerated database recovery applies. With ordinary locking reads, reader/writer blocking is a different cost. Inspect the enabled database options.</td></tr>
<tr><td>SQLite</td><td>In WAL mode, readers retain an earlier log boundary and can prevent checkpoint completion or log reset. In rollback-journal mode, readers and the committing writer coordinate through file locks instead. VACUUM can rebuild the file.</td></tr>
</tbody></table>

The database may have little current business data yet substantial obligations to earlier readers. Track both: the bytes serving today's facts and the bytes still serving unfinished histories. Then ask whether the owner of the oldest obligation can safely finish.

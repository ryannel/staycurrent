A database read has two separate questions to answer: which changes may it observe, and where can that observation be served? CockroachDB’s isolation level controls the permitted transaction history. A historical read chooses a time in that history. A follower-read optimisation can serve an eligible old observation from a nearby replica.

These choices can make a report cheaper without making it a valid capacity check. A consistent answer from before the last booking is still the wrong evidence for accepting another booking now.

We will change the workshop’s remaining places from 2 to 1, inspect both versions, and then distinguish a historical report from a transaction that consumes the current place.

## Name the isolation actually in use

The branch’s native cluster uses CockroachDB 25.4.17. Inspect the session rather than infer its setting from a product label:

```sql
SHOW default_transaction_isolation;
BEGIN ISOLATION LEVEL READ COMMITTED;
SHOW transaction_isolation;
COMMIT;
```

`SERIALIZABLE` is the default in this release. `READ COMMITTED` is also supported, with a different contract. Under serializable execution, accepted transactions must have an outcome consistent with a serial order. A conflict can require a whole transaction retry. Under read committed, statements can observe different committed states during the same transaction, and the product handles many statement retries internally.

Neither description means the application may reuse an old value however it likes. Two read-committed transactions can each make a decision from a value read before the other changes it. A later assignment of a calculated value does not become a safe capacity decrement just because the statement itself completed atomically.

| Application action | What must be protected |
| --- | --- |
| Read a dashboard count | State which freshness and consistency the displayed number promises |
| Read capacity, decide, then consume it | Protect the complete read-dependent invariant against competing requests |
| Perform a conditional decrement | Make the precondition and decrement one accepted mutation, then interpret whether it matched |
| Read several changing facts for one decision | Choose the transaction history that makes those facts meaningful together |

The native conflict history is in [Transactions and retries](/review/relational/rl124/). This page owns the read choice; that page owns what the client repeats after an exposed retry.

## Preserve one timestamp before the change

Connect to the branch’s disposable cluster, introduced in [Keys, ranges and replication](/review/relational/rl123/). Its workshop fixture has `(tenant='t4', session='s7', remaining=2)`.

Capture a timestamp, then commit the capacity change:

```sql
SELECT cluster_logical_timestamp();
-- Keep the returned value as T0.

UPDATE workshop.sessions
SET remaining = 1
WHERE tenant = 't4' AND session = 's7';

SELECT tenant, session, remaining FROM workshop.sessions;
```

The current result contains 1. Now use the *actual saved value*, not the text `T0`, in the historical query:

```sql
SELECT tenant, session, remaining
FROM workshop.sessions AS OF SYSTEM TIME '<saved T0>';
```

That query asks for the row at the earlier timestamp, where the remaining count was 2. The worksheet records the timestamp and result together. It does not infer history from two wall clocks that happen to show the same second.

`cluster_logical_timestamp()` exposes a hybrid logical timestamp in the product’s supported decimal form. It is useful here because we can preserve an exact database observation. Normal applications can often use timestamp or bounded-staleness forms instead of manipulating this representation themselves.

A historical transaction is read-only. An attempt to lock or mutate historical rows is not a method of reserving today’s capacity. The earlier value can guide a display or analysis; the current write still needs its own protection.

## Give a multi-table answer one time

Suppose a report joins orders to session details. Reading the order table at T0 and today’s session state can describe a combination that never existed. An `AS OF SYSTEM TIME` query over several tables applies one selected historical time to the statement. It is not a per-table invitation to mix arbitrary moments.

For several report statements, establish a read-only historical transaction before reading:

```sql
BEGIN AS OF SYSTEM TIME '<saved T0>';
SELECT tenant, session, remaining FROM workshop.sessions;
SELECT tenant, request, amount FROM workshop.orders;
COMMIT;
```

The schema at that time matters too. A table or column created later is not automatically available in the old view. Choosing a timestamp must preserve the facts and schema the report expects. The exact result and any schema-boundary error belong in the recorded trial before building a historical API around it.

This can be a useful alternative to a long current transaction when the report accepts an older answer. It does not create an indefinite archive, and it does not promise that every engine or external system in a larger report supports the same timestamp.

## A follower needs a safe read time

A replica may have old versions without being entitled to serve an arbitrary read from them. It needs enough progress information to know that later replication will not invalidate the answer at the requested timestamp. CockroachDB uses closed timestamps and replication progress to establish eligible historical observations.

That is the distinction between a follower read and “return whichever bytes this node currently has”. The latter could be arbitrarily incomplete. The former answers a specified read contract.

```sql
SELECT tenant, session, remaining
FROM workshop.sessions
AS OF SYSTEM TIME follower_read_timestamp();
```

The helper selects a sufficiently old timestamp for an exact-staleness follower read. Its documented offset and eligibility depend on the pinned product configuration. The important application decision is that this is an explicitly historical observation. A recent write may be outside it.

Our local worksheet executes this syntax. A returned row alone does not prove that a particular nearby follower served it, nor measure the latency saved by regional routing. To establish that performance claim, inspect the actual execution/routing evidence in the intended topology and compare the same workload. All our loopback nodes share one host.

## Bound staleness when an exact old time is unnecessary

A dashboard may need “no more than ten seconds old” rather than a particular timestamp. Bounded-staleness forms can let the database choose an eligible time within the application’s limit:

```sql
SELECT tenant, session, remaining
FROM workshop.sessions
AS OF SYSTEM TIME with_max_staleness('10s')
WHERE tenant = 't4' AND session = 's7';
```

The full primary-key predicate matters. In the native run, the same bounded-staleness query without it failed with SQLSTATE `0A000`: this version does not support that form when it may touch multiple ranges or require an index join. The documented bounded-staleness contract requires a single-row read without an index join; the full primary-key lookup above meets that shape. Exact historical reads have different restrictions. Check the actual statement, rather than generalising from one successful lookup. A bounded read is a distinct request, not a change to every future read on that connection. `with_min_timestamp(...)` can instead require an observation no earlier than a known event. Its optional nearest-only behaviour changes whether the request may fall back or must fail when a nearby replica cannot meet the bound.

Use the returned answer according to that contract. A dashboard badge can say that places were available within the permitted freshness window. The actual purchase must still succeed through a current protected mutation. Keeping those roles separate lets an approximate display coexist with a correct acceptance decision.

## Historical versions have a retention boundary

CockroachDB eventually garbage-collects old versions. A query older than the available history can fail even though a similar query worked yesterday. The garbage-collection window and any protected timestamps are operating state, not an unlimited time-travel promise.

A longer retained history has a storage and maintenance cost. A shorter history can invalidate a long-running export or a reader that saved a timestamp and returned too late. Choose the retention needed by the real readers and validate their maximum duration. [Backup and recovery](/review/relational/rl129/) supplies a different mechanism for recovering older states; extending every live table’s history is not automatically the right backup design.

Historical content does not establish permission to view it now. An application that must enforce a *current* revocation cannot assume that an old snapshot is sufficient authority. Separate the historical content being viewed from the permission to view it now, and test the actual identity at the boundary.

## Choose the read from its consequence

For a report that must reproduce T0, preserve T0 and use an exact historical contract within retained history. For a display with a freshness budget, test bounded or exact-staleness reads and identify their routing benefit. For a current invariant, use the current protected transaction and its retry protocol.

A read that is fast, local and internally consistent can still be the wrong read. The decisive question is what the application will do with its answer.

A JSON value gives a PostgreSQL column an internal structure: fields, objects and arrays that queries can navigate. It is useful when records share a stable identity but some details vary, such as a workshop’s equipment requirements. PostgreSQL can search those details without requiring every optional field to become a column.

The choice becomes harder when a flexible field acquires a rule or an important query. A customer reference needs a tenant boundary. A price agreed on an order must remain the agreed price. A field queried by numeric range needs a clear numeric type. JSON syntax alone supplies none of those decisions.

We will retain a flexible workshop payload long enough to see its behaviour, then move a frequently tested property into a stronger representation. The [native core lab](/review/relational/evidence/rl110-native.py) runs the representation, plan and storage observations on PostgreSQL 18.6.

## JSONB represents a value, not its original text

PostgreSQL has both `json` and `jsonb`. `json` retains the input text, while `jsonb` parses it into a searchable representation. That affects what can be recovered from storage:

```sql
SELECT '{"seat":"A1","seat":"B2","n":1.00}'::json,
       '{"seat":"A1","seat":"B2","n":1.00}'::jsonb;
```

The first result retains the text’s field order and duplicate `seat`. The second contains one `seat`, with value `B2`, and displays the object in its own order. Duplicate keys and original whitespace are not preserved by JSONB. If an incoming signed message must be retained byte for byte, store those bytes separately from a parsed representation.

JSON numbers also face JSONB’s numeric representation limits. Do not assume that every syntactically valid external JSON number can become JSONB, or that a string containing digits becomes a number. Representation checks belong at the ingestion boundary.

Missing, JSON null and SQL null need separate policies:

```sql
SELECT ('{"x":null}'::jsonb -> 'x') IS NULL AS sql_null,
       ('{"x":null}'::jsonb ->> 'x') IS NULL AS extracted_text_null,
       '{}'::jsonb ? 'x' AS key_exists;
-- false | true | false
```

`->` returns a JSON value, so JSON null is a present value. `->>` extracts text and maps that null to SQL null. A missing key also extracts as SQL null. Use existence and type tests when that distinction changes what a writer or query should accept.

## Stable identity remains relational

The workshop’s order identity is `(tenant_id, order_id)`, and its customer reference is `(tenant_id, customer_id)`. Tenant `t5` can have customer 42 too. A flexible document containing only `"customer_id":42` does not establish which customer the order references.

Keep the tenant-aware primary and foreign keys as ordinary columns. Keep `agreed_price numeric(10,2)` on the order as the accepted historical amount. A later edit to the workshop catalogue must not rewrite that fact by changing a shared JSON template.

A payload might contain `level`, required tools and presentation options. Fields that belong to another independently updated entity, require foreign keys or have their own history should earn a related row. A JSON object is one value inside one row, not a private relational database hidden behind a column.

## The operator decides which index helps

The native fixture has 10,000 payloads. Every hundredth has `"level":"advanced"`; the rest have `"level":"intro"`. Each also has a roughly 3.2 KB note made from independent hashes, avoiding a trivially compressible repeated string.

```sql
CREATE INDEX payload_gin ON payloads USING gin (payload jsonb_path_ops);
ANALYZE payloads;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM payloads WHERE payload @> '{"level":"advanced"}';
```

`@>` asks whether the left value contains the structure on the right. It does not require equality of the complete object. The observed bitmap plan used the GIN and returned 100 rows.

Now ask for the same logical property through an extracted text expression:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM payloads WHERE payload->>'level' = 'advanced';
```

The whole-document GIN did not serve that equality. The server scanned the table, returned 100 rows and removed 9,900. It also performed substantial TOAST access to extract the field from wide values. Index support belongs to a particular operator on a particular expression, not merely to a column somewhere underneath it.

```sql
CREATE INDEX payload_level ON payloads ((payload->>'level'));
ANALYZE payloads;
```

The same extracted-text query then used an ordinary B-tree expression index and returned the same 100 IDs. The access path changed while the answer stayed fixed.

GIN operator classes narrow the contract further. Default `jsonb_ops` supports key existence as well as containment. `jsonb_path_ops` supports containment and path matching, but not `?`. Choose from the actual workload rather than treating the smaller index as universally better.

An extracted numeric range needs a numeric expression. Indexing text orders `"100"` before `"20"`, which is wrong for a capacity comparison. Decide whether strings are rejected, repaired or deliberately converted before building the index. A `CASE` expression can cast only a branch whose `jsonb_typeof` is `number`; a separate `AND` condition does not promise evaluation order. Enforce a strict policy on writes when inconsistency is not acceptable.

## Validate a shape when it becomes a rule

Valid JSON can still violate the application’s type contract. Requiring a string field also means deciding which root shapes are allowed.

The key-existence test `payload ? 'level'` accepts the array `["level"]` and scalar `"level"`. Extracting a field from them returns SQL null, which a check accepts as unknown. This rule requires an object and a true string-type test, while permitting SQL null for the whole column:

```sql
ALTER TABLE payloads ADD CONSTRAINT level_shape
CHECK (payload IS NULL OR (
  jsonb_typeof(payload) = 'object'
  AND jsonb_typeof(payload->'level') = 'string'
) IS TRUE);
INSERT INTO payloads VALUES (10001,'{"level":42}');
-- Rejected: level must be a JSON string.
```

The value is valid JSONB, but the field has the wrong type. `IS TRUE` also rejects the unknown result from a missing field. The object test excludes arrays and scalars; JSON null fails the string test. The whole column is still nullable in this fixture: add a separate `NOT NULL` rule if every row must carry a document. This does not restrict the string to recognised levels or provide an independent referenced level record. Choose those stronger rules if the field has acquired those meanings.

## Keep conditions attached to one array member

A workshop can have multiple supplier offers. Consider these two payload fragments:

```json
{"offers":[{"seller":"A","price":12},{"seller":"B","price":18}]}
```

```json
{"offers":[{"seller":"A","price":18},{"seller":"B","price":12}]}
```

Only the first has an offer from A below 15. Independent existence tests can wrongly accept the second: it has an A offer and a cheap offer, but they are different members.

```sql
WITH offer_examples(id,payload) AS (VALUES
  (1,'{"offers":[{"seller":"A","price":12},{"seller":"B","price":18}]}'::jsonb),
  (2,'{"offers":[{"seller":"A","price":18},{"seller":"B","price":12}]}'::jsonb)
)
SELECT id, payload @? '$.offers[*] ? (@.seller == "A" && @.price < 15)'
FROM offer_examples;
-- 1 | true
-- 2 | false
```

Inside the filter, `@` means the current offer. Both conditions apply before the path advances to the next member. Keeping the identity of that member is the difference between the two business questions.

For a report that needs seller, amount and a join to a supplier table, expand the array into query rows. PostgreSQL 18’s SQL/JSON facilities, including `JSON_TABLE`, can provide typed columns and explicit conversion/empty-result policies. Expansion changes cardinality: two offers produce two report rows, not one workshop row. Counting those rows counts offers.

Once each offer needs a supplier foreign key, its own update, acceptance history or uniqueness rule, a stored offer table is usually clearer. Query-time expansion cannot supply those stored invariants.

## Promote a property without leaving two authorities

Suppose every published workshop must now have one known level. A typed column makes the requirement and common query visible to the schema. Adding the column is only the beginning; old writers may still send JSON alone.

Use a compatibility phase with a stated authority. Initially the JSON field remains the source. A database trigger or a single enforced write path derives the new column for old and new callers. Backfill existing rows in bounded transactions, then validate equality and requiredness before changing readers. [Schema changes under load](/review/relational/rl119/) executes that pattern with old and new writer forms.

A completion check must include disagreement, not only missing columns:

```sql
SELECT count(*)
FROM workshop_payloads
WHERE level IS DISTINCT FROM payload->>'level';
```

Zero at one instant is useful evidence, but a constraint or maintained write protocol must keep it zero while writers continue. Otherwise the backfill can finish and the next old client can immediately make the copy stale.

At the final transition, make the column authoritative and remove the old writer contract deliberately. You can stop storing the duplicate field, or derive it for compatibility reads. Allowing either copy to win according to whichever service last wrote it leaves an unresolved representation decision.

## A small JSON edit is a row update

`jsonb_set` constructs a new JSONB value from the current stored value:

```sql
UPDATE payloads
SET payload = jsonb_set(payload, '{level}', '"advanced"')
WHERE id = 1;
```

That avoids replacing the whole object with a stale client copy that could discard another field’s intervening edit. It still locks and updates the containing row. Two callers editing different JSON keys do not get independent field locks.

Our wide value occupied 3,235 bytes; the table had about 41 MB of TOAST storage. The one-field change advanced the measured WAL insertion position by 4,200 bytes in that run. This is an observation about one changed value and its indexes, not a fixed cost formula. Compression, size, index definitions and full-page images change the work.

The consequence is larger than the changed field’s few characters. PostgreSQL versions the containing tuple, and a newly constructed large value can need new TOAST chunks. An unrelated ordinary-column update can reuse an unchanged external value. Keeping a large mutable document in one field therefore defines both a storage and a contention boundary.

Split independently edited sections according to ownership and invariants. Keep JSON where the fields form one useful flexible value. A document-shaped API response does not require every underlying fact to share a stored document.

## Arrays, ranges and extensions are conditional alternatives

A homogeneous list of tag strings may fit a typed PostgreSQL array better than a JSON array. Arrays retain an element type and support useful containment/overlap operators. They still occupy one row value and do not provide a foreign key for every embedded member.

A booking interval may fit a native range type. Its overlap and containment rules make endpoint semantics explicit and connect to GiST indexing. That is a different representation from loosely storing start/end strings inside JSON.

An extension can supply spatial, text or vector types and operators when the workload needs them. Verify the exact installed extension and hosted-provider support, its version, operator class and migration path. “PostgreSQL supports extensions” does not establish that a particular deployment can install the one your schema requires.

The useful design is specific: stable tenant-aware facts in columns and related rows, flexible coherent details in JSONB, and indexes shaped for the operators actually used. Observe both the read savings and the updates that maintain them.

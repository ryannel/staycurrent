A PostgreSQL restore can reconstruct an earlier database by starting from a physical base backup and replaying archived WAL. A recovery target says where to stop. That can undo a committed mistake, something ordinary crash recovery and a current replica faithfully preserve.

Stopping earlier also removes useful later work. If a bad deletion precedes a valid order, restoring before the deletion loses that order too. Choosing a recovery target is therefore only part of the recovery: the application must identify and reconcile the valid work excluded by it.

We will restore before a deletion of tenant `t4`’s orders. Order `o81`, accepted as request `r81` at 20.00, must return. A valid later order `o82/r82` at 25.00 must then be recovered without replaying the deletion. The [native lab](/review/relational/evidence/rl110-native.py), in `recovery` mode, executes every stage on isolated PostgreSQL 18.6 clusters.

## Retain a base and its required history

A physical base backup copies the cluster’s files while PostgreSQL coordinates the backup boundary. It needs WAL to make the copied files consistent and to reach any later target. A collection of table files copied without that protocol is not interchangeable with a base backup.

The lab’s source uses `archive_mode=on` and archives completed segments into another directory. Its command refuses to overwrite an existing name:

```text
archive_command = 'test ! -f /owned/archive/%f && cp %p /owned/archive/%f'
```

This is a private lab command with substituted owned paths. A real archive command needs reliable failure reporting, protection against conflicting existing contents, permissions and a surviving storage location. A directory on the same disk as the source tests retrieval mechanics; it does not protect against losing that disk.

Monitor `pg_stat_archiver` and test retrieval. An “archive configured” flag does not prove that the required segment was saved. A failed archive can retain WAL locally and eventually fill the source volume.

The starting relation deliberately records tenant and replay identity:

```sql
CREATE TABLE recovery_orders (
  tenant text, order_id text, request_id text, price numeric,
  PRIMARY KEY (tenant, order_id), UNIQUE (tenant, request_id)
);
INSERT INTO recovery_orders VALUES ('t4','o81','r81',20);
```

The lab then takes and verifies a base backup:

```sh
pg_basebackup -h "$SOURCE_SOCKET" -p 56810 -U lab \
  -D "$BASE" -X stream -c fast
pg_verifybackup "$BASE"
```

`-X stream` supplies WAL needed for the backup’s own consistency. It does not remove the obligation to retain later archived segments through the desired recovery target. `pg_verifybackup` checks the backup against its manifest; it is valuable before attempting restore, but does not establish application correctness or future archive completeness.

## Create a target and a destructive history

A named restore point gives this drill an unambiguous target after the base backup:

```sql
SELECT pg_create_restore_point('before_bad_delete');
DELETE FROM recovery_orders WHERE tenant = 't4';
INSERT INTO recovery_orders VALUES ('t4','o82','r82',25);
```

The delete and insert are separate committed statements. The source’s final relation contains only `o82`. Before restoration we export its verified valid later order as reconciliation evidence, independently of the restored cluster.

```sql
SELECT * FROM recovery_orders;
-- t4 | o82 | r82 | 25
SELECT pg_switch_wal();
```

Switching WAL makes the current completed segment available for archiving. The harness waits for successful archive progress rather than assuming a command’s return means the segment is already retrievable.

In an incident, a restore point from before the unknown mistake may not exist. PostgreSQL also supports time, transaction-ID and LSN targets with different interpretation and inclusive/exclusive choices. Identify the actual transaction boundary using evidence, then practise that exact target type. An application clock timestamp is not automatically an exact database commit boundary.

## Restore into an isolated cluster

Keep the source and backup intact. The lab copies the verified base into a new data directory, changes its port and socket, and disables its source archive configuration. It creates `recovery.signal` and adds:

```text
restore_command = 'cp /owned/archive/%f %p'
recovery_target_name = 'before_bad_delete'
recovery_target_action = 'pause'
```

Start this copy on port 56813. Do not let an old application connection pool discover it as a production writer. Tablespace paths, credentials and external integrations also need isolation in a real restore drill.

PostgreSQL first makes the backup consistent, then replays towards the target. The observed log reported `recovery stopping at restore point "before_bad_delete"`, followed by `pausing at the end of recovery`. A successful server start by itself would not prove either condition.

```sql
SELECT pg_is_in_recovery(), pg_get_wal_replay_pause_state();
-- true | paused
SELECT * FROM recovery_orders;
-- t4 | o81 | r81 | 20
```

This is the intended pre-delete state. It is still read-only recovery. Confirm both the target and the business records before deliberately ending recovery:

```sql
SELECT pg_wal_replay_resume();
```

With this paused recovery target, resuming ends recovery and the server becomes writable; no separate promotion command is needed. The lab polls until `pg_is_in_recovery()` is false. Its log records a newly selected timeline, separating subsequent writes from the original history.

Timeline history files describe branches after promotion. Archive names encode timeline as well as segment position. Keep the history needed to select the intended branch; a segment number without its history is an incomplete recovery specification. Reusing a recovery copy as a new source also requires its own correct archive and access configuration.

## Restore the valid later order by reconciliation

`o82` is absent, as expected. The restored cluster remains isolated from application writers while the lab checks and imports the reviewed later record. Replaying the original history onwards would also replay the bad deletion, so reconciliation uses a staging relation:

```sql
CREATE TABLE recovered_later (LIKE recovery_orders INCLUDING ALL);
INSERT INTO recovered_later VALUES ('t4','o82','r82',25);
```

First check whether any request identity already exists with conflicting facts:

```sql
SELECT l.*
FROM recovered_later l JOIN recovery_orders r USING (tenant, request_id)
WHERE (l.order_id,l.price) IS DISTINCT FROM (r.order_id,r.price);
-- zero rows
```

A conflict needs investigation. “Ignore duplicates” is safe only after proving that a duplicate represents the same accepted operation. The tenant belongs in this comparison; another tenant may use `r82` independently.

```sql
INSERT INTO recovery_orders
SELECT * FROM recovered_later
ON CONFLICT (tenant, request_id) DO NOTHING;
SELECT * FROM recovery_orders ORDER BY order_id;
-- t4 | o81 | r81 | 20
-- t4 | o82 | r82 | 25
```

Replaying the same accepted record now leaves one `o82` under request `r82`. A conflict on a different identity, such as an occupied order ID, still fails rather than silently replacing history.

This miniature case has no payment provider, booking-capacity ledger or email job. A real acceptance test must reconcile those effects too: stable payment/request identities, session capacity, agreed prices and any outward acknowledgement. Database row recovery alone cannot undo an email already sent or reconstruct a payment from a current price list.

Keep recovery staging evidence and an explicit decision for each later operation. If the later source still exists, isolate its final state before losing it. If only upstream request logs survive, verify that they record accepted outcomes and complete payloads rather than just attempted requests.

## Break the WAL chain deliberately

The harness creates a second copy of the same base and points it at an empty archive. It removes copied local WAL only from that disposable copy, so no accidental local segment hides the archive dependency. The good archive and backup remain intact.

That copy cannot retrieve the required checkpoint segment. Its log ends with:

```text
invalid checkpoint record
FATAL: could not locate required checkpoint record at ...
```

It does not reach the intended target. Deleting `backup_label` to force a start would discard the backup’s recovery contract and risk a corrupt cluster. The repair is to retrieve the actual missing required history from another surviving copy, or choose another complete recovery chain and accept its different recoverable state.

A “file not found” message alone is not sufficient to diagnose failure: recovery can probe for optional timeline history or the next segment after a target. Correlate the required segment, the fatal/stop condition and whether the target was actually reached.

## Make the restore an operating capability

Retain complete base-plus-WAL chains for the intended recovery window and failure domain. Coordinate archive cleanup with every backup and consumer that still needs a segment. A standby’s current replay position is not permission to erase history required by an older retained base.

A useful drill records retrieval time, replay time, target evidence and application acceptance, then the exact steps needed to reopen a writer. Repeat after changing backup tools, archive credentials, encryption keys, tablespaces, major versions or dependencies. A successful backup job is evidence of a saved input; this executed restore is evidence that the inputs form a usable path.

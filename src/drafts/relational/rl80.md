A current-state table answers what the service believes now. History answers a different question: what was agreed, what applied on a particular date, or what the service knew when it sent a report. Updating a row can preserve the first answer while destroying the others.

History therefore starts with the question that must remain answerable. A catalogue's former price, the price agreed on order `o81`, and the price used in a report sent yesterday are related facts with different lifetimes. Keeping every old row without recording what those rows mean does not settle which answer is correct.

The workshop examples use tenant `t4`, customer `42` and order `o81`. Dates are illustrative business dates. The executable interval queries use PostgreSQL.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Preserve the agreement locally

Order `o81` contains two seats agreed at €20 each. The catalogue later rises to €22. The receipt should still total €40. Joining to the current catalogue produces the wrong historical answer, even though the join itself is valid.

```sql
CREATE TABLE catalogue (
  tenant_id text, product_id text, current_price numeric(10,2),
  PRIMARY KEY (tenant_id, product_id)
);
CREATE TABLE order_lines (
  tenant_id text, order_id text, line_no integer,
  product_id text NOT NULL, quantity integer NOT NULL,
  agreed_price numeric(10,2) NOT NULL,
  agreed_description text NOT NULL,
  PRIMARY KEY (tenant_id, order_id, line_no)
);
INSERT INTO catalogue VALUES ('t4','seat',20);
INSERT INTO order_lines VALUES ('t4','o81',1,'seat',2,20,'Workshop seat');
UPDATE catalogue SET current_price = 22 WHERE tenant_id = 't4';
SELECT l.order_id, l.quantity * l.agreed_price AS agreed,
       l.quantity * c.current_price AS repriced
FROM order_lines l JOIN catalogue c USING (tenant_id, product_id);
```

```text
order_id | agreed | repriced
o81      | 40.00  | 44.00
```

The line owns the agreement, so a catalogue edit has no reason to update it. This is the distinction made in [Relations, keys and normalisation](/review/relational/rl77/): identical values need not be the same fact. Copy the description or tax treatment too when reproducing the agreement requires them. A foreign key back to the product can remain useful for classification, provided deletion policy preserves the agreed facts.

A correction to an agreement needs its own business meaning. If the original €40 charge was valid and the customer receives €5 back, a refund is a new fact, not evidence that the original charge was €35. If the entered price was a clerical error, preserve who corrected it and why when that distinction matters. The query contract decides whether a report includes the correction, the original or both.

## Effective time describes when a fact applied

Suppose the catalogue price is €20 through 9 October and €22 from 10 October. A dated price table stores intervals. Use a half-open interval: include `valid_from`, exclude `valid_to`. Two adjacent versions then meet without sharing a day.

```sql
CREATE TABLE price_history (
  tenant_id text NOT NULL, product_id text NOT NULL,
  valid_from date NOT NULL, valid_to date NOT NULL,
  price numeric(10,2) NOT NULL,
  CHECK (valid_from < valid_to),
  PRIMARY KEY (tenant_id, product_id, valid_from)
);
INSERT INTO price_history VALUES
 ('t4','seat','2026-10-01','2026-10-10',20),
 ('t4','seat','2026-10-10','infinity',22);
SELECT price FROM price_history
WHERE tenant_id = 't4' AND product_id = 'seat'
  AND valid_from <= date '2026-10-10'
  AND date '2026-10-10' < valid_to;
```

```text
price
22.00
```

A different price beginning on 8 October would overlap the first interval. A primary key on start date would allow it: the start dates differ. Detect overlapping pairs with the condition `a.valid_from < b.valid_to AND b.valid_from < a.valid_to`, scoped to the same tenant and product. Detecting a violation after insertion is not preventing one; concurrent writers need enforcement.

PostgreSQL supports exclusion constraints on ranges, and PostgreSQL 18 also has temporal key facilities. Other engines have their own temporal or application-managed designs. Pick an enforcement mechanism supported by the actual engine; a row's `from < to` check cannot constrain its neighbours. A no-overlap rule also does not prove no gaps. If every business date must have a price, define how a change preserves continuous coverage.

## Recorded time preserves what was known

On 15 October, an administrator learns that the €22 price should have begun on 8 October. Correcting the effective intervals makes a report for 9 October change from €20 to €22. That may be the right current answer. It cannot explain why a report sent on 12 October used €20.

Keep a second time dimension when both questions matter. Effective time says when the price applied. Recorded time says when this version was the service's recorded belief.

Here is the resulting four-row history. A production correction closes and inserts versions together in one transaction, under a protocol that prevents competing corrections from overlapping.

```sql
CREATE TABLE price_beliefs (
  tenant_id text, product_id text,
  valid_from date, valid_to date,
  recorded_from date, recorded_to date,
  price numeric(10,2)
);
INSERT INTO price_beliefs VALUES
 ('t4','seat','2026-10-01','2026-10-10','2026-10-01','2026-10-15',20),
 ('t4','seat','2026-10-10','infinity','2026-10-01','2026-10-15',22),
 ('t4','seat','2026-10-01','2026-10-08','2026-10-15','infinity',20),
 ('t4','seat','2026-10-08','infinity','2026-10-15','infinity',22);
SELECT q.known_on, h.price
FROM (VALUES (date '2026-10-12'),(date '2026-10-16')) q(known_on)
JOIN price_beliefs h
  ON h.recorded_from <= q.known_on AND q.known_on < h.recorded_to
WHERE h.tenant_id = 't4' AND h.product_id = 'seat'
  AND h.valid_from <= date '2026-10-09' AND date '2026-10-09' < h.valid_to
ORDER BY q.known_on;
```

```text
known_on   | price
2026-10-12 | 20.00
2026-10-16 | 22.00
```

Recorded time should come from a trusted write path, not an arbitrary client claiming it knew something earlier. At higher precision, several changes can share a timestamp; add a stable revision identity and define ordering. Keep the report's input snapshot, rule version or finished output when reproducing a sent document requires more than a price lookup.

This two-dimensional history is often called bitemporal data. It earns its extra rows and query complexity only when the service needs both questions. A simple immutable order agreement does not require it.

## An audit log has a different job

An audit trail records who attempted or made a change, when and why. A history table records versions that support business queries. Either can help investigate an incident, but one does not automatically supply the other. Application logging can miss direct SQL changes; a trigger may capture row changes but lack the authenticated person unless the trusted connection supplies that context.

The audit writer's permissions matter too. A history row that the same unrestricted account can silently edit is weak evidence of an unaltered past. Give the writer only the operations it needs, preserve correlation with the request, and decide how audit records survive an administrator mistake.

Event sourcing goes further: the event history is the authoritative record from which current state is reconstructed. That requires event semantics, ordering, replay and versioning rules. Keeping old prices or an audit table does not commit the service to that architecture.

## Deletion has several destinations

Deleting customer `42` first meets references. `ON DELETE CASCADE` could remove their bookings and orders. Restricting deletion could retain everything, including personal details that no longer need to remain. Separate the enduring transaction facts from personal attributes whose lifetime differs: an order can retain amount, tax and a non-personal reference while the profile is removed or anonymised under the service's retention policy.

Soft deletion adds a marker such as `deleted_at`. It preserves rows and references, but every ordinary read and uniqueness rule must account for it. It is not physical erasure. A partial unique index may allow a live account to reuse a deleted account's login, which raises another question: which historical references should the reused name resolve to? Stable IDs keep those identities distinct.

Follow the deletion beyond the primary table. Search indexes, exports, replicas, caches and analytical copies may hold personal data. A tombstone or deletion record may need to remain long enough for a delayed consumer to remove its copy. Backups usually retain the older value until they expire; restoring one can resurrect it. A deletion ledger held outside that restore boundary can reapply removals before the restored service is reopened.

State the actual promise: which active copies are removed, which retained records remain, how long backups persist and what restore does before serving traffic. Database deletion supplies one step of that contract. [Database access and least privilege](/review/relational/rl104/) develops the wider controls; [Backup, restore and reconciliation](/review/relational/rl96/) follows the restored database.

A query states the result the application wants. A plan describes how the engine will produce it: which rows it reads, how it matches them, and what it must retain before returning an answer. Two plans can return identical rows while doing very different amounts of work.

The planner chooses before it knows the actual answer. It estimates how many rows each condition will match, prices candidate operations, and selects a route. A bad estimate matters through the operation it selects: one inexpensive lookup is a good choice for one row and a costly choice when repeated forty thousand times.

We will first move a workshop query through two plans, then recreate that mistake in PostgreSQL. The operator ideas are shared by relational engines; plan wording, cost units and diagnostics differ.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Read the plan as rows flowing towards the result

Suppose an event service has 90,000 events and one delivery row per event. A query wants deliveries for events marked `new`. One plan finds the matching event keys, then looks up each delivery through its index. Another retains those keys in a hash lookup and scans all deliveries once, checking each delivery key against it.

For one matching event, the indexed nested loop needs one delivery probe. With 40,000 matching events, it repeats that probe 40,000 times. One delivery scan plus a retained lookup can then cost less. Neither join name is inherently fast or slow. The input cardinalities and usable access paths decide the work; the native experiment below measures this same events-and-deliveries query.

A merge join walks two inputs in join-key order, advancing until matching keys meet. It can reuse index order or pay for sorts first. Equal keys can have several matches on either side, so it still has to produce the same matching pairs as any other join. An access method cannot remove the multiplicity taught in [Joins and the meaning of a result row](/review/relational/rl81/).

## Some operators retain state

An index or table scan can usually produce rows incrementally. A sort generally consumes its input before knowing the first output row. A top-N sort can retain fewer candidates, but still has to inspect the input unless an access path already provides the requested order.

Hash joins retain a build-side lookup. Hash aggregation retains groups and aggregate state. Sorted grouping can process one key group at a time once its input is ordered. Window functions may need a sorted partition or further retained rows depending on the frame.

Memory limits therefore apply to operations, not just returned rows. Several sorts, hash nodes, workers and concurrent queries can each need memory. When PostgreSQL cannot keep a sort in memory it can write sorted runs to temporary files and merge them. Hash operations can batch work through temporary storage. The query can remain correct while its resource cost changes sharply.

The native variation sets `work_mem` to 64 kB and sorts the 90,000-row event fixture. Its plan reports `Sort Method: external merge`, 10,584 kB of temporary disk space and temporary reads and writes. That is a measured spill, not a claim that every sort needs a larger global memory limit.

A limit above a blocking sort does not imply that only a few table rows were read. Read the child operator. Nor should you add parent and child elapsed times as if they were independent: a parent's measurements include work in its descendants. The same caution applies to inclusive buffer counts.

## Estimated rows and actual rows answer different questions

PostgreSQL `EXPLAIN` gives a plan without running the query. `EXPLAIN (ANALYZE, BUFFERS)` runs it and adds observed rows, loops and page accesses. Use `ANALYZE` with care on mutations: it performs the write. A rollback can undo transactional row changes but not every external effect or sequence advance.

Read from leaf operators towards their parents. At the first place an estimate diverges sharply from actual rows, ask which predicate or join assumption caused it. A wrong estimate above an already wrong input may be only a consequence.

A PostgreSQL node's `actual rows` is per loop, averaged when it runs repeatedly. An inner node showing one row and `loops=40000` produced about forty thousand rows in total. `Rows Removed by Filter` reveals rows fetched only to be rejected. `Index Cond` names conditions evaluated by an index, but does not by itself prove a narrow scan; page and row work still matter.

Buffer hits are accesses satisfied by the database cache, while reads brought pages into that cache. A read may still be satisfied by the operating system cache. Counts include repeat accesses, so “120,000 hits” does not mean 120,000 distinct pages or physical disk operations.

## Make the statistics miss new data

This disposable example creates 50,000 completed events and collects statistics. It then inserts 40,000 new events without recollecting them. Every event has one delivery row. Event and delivery IDs are globally unique in this lab; a tenant-scoped production schema must also carry tenant identity through references and joins.

```sql
CREATE TABLE events (
  event_id integer PRIMARY KEY, kind text NOT NULL, payload text NOT NULL
) WITH (autovacuum_enabled = false);
CREATE TABLE deliveries (
  event_id integer PRIMARY KEY, address text NOT NULL
);
INSERT INTO events SELECT n,'done',repeat('x',100)
FROM generate_series(1,50000) n;
INSERT INTO deliveries SELECT n,repeat('y',40)
FROM generate_series(1,90000) n;
CREATE INDEX events_kind ON events(kind);
ANALYZE events;
ANALYZE deliveries;
INSERT INTO events SELECT n,'new',repeat('x',100)
FROM generate_series(50001,90000) n;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT count(*) FROM events e JOIN deliveries d USING (event_id)
WHERE e.kind = 'new';
```

The autovacuum setting is confined to this disposable fixture so background analysis cannot repair it mid-experiment. Do not disable maintenance on a live table to reproduce this lesson.

The initial statistics contain no `new` values. In the native run, the event scan estimates one matching row but finds 40,000. Its nested loop consequently probes the delivery primary key 40,000 times. The exact plan and counts are in the [native plan record](/review/relational/evidence/rl87-native.txt).

The relevant operators read like this, with timings and costs removed:

```text
Before ANALYZE
Aggregate: count = 40000
└─ Nested Loop: estimated 1 row, actual 40000 rows
   ├─ Index Scan events_kind: estimated 1, actual 40000
   └─ Index Only Scan deliveries_pkey: 1 row × 40000 loops
      40000 index searches; 40000 heap fetches
Total execution buffers: 120723 hits
```

Now change only the statistics:

```sql
ANALYZE events;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT count(*) FROM events e JOIN deliveries d USING (event_id)
WHERE e.kind = 'new';
```

The estimate moves close to 40,000, and PostgreSQL chooses a hash join in this run. It scans deliveries once rather than probing the key forty thousand times. Both queries return a count of 40,000. The repair changed the model of the data, not the requested result.

```text
After ANALYZE
Aggregate: count = 40000
└─ Hash Join: estimated 40275 rows, actual 40000 rows
   ├─ Seq Scan deliveries: 90000 rows, one pass
   └─ Hash: 40000 event keys, one batch
      └─ Index Scan events_kind: 40000 rows
Total execution buffers: 1565 hits
```

These are observations from the recorded run; a fresh statistics sample may change the estimate slightly. The event input still takes 723 buffer accesses. The saving comes from replacing 120,000 repeated delivery accesses with one 842-page scan.

A table scan after this repair is evidence of a better plan for broad work, not an index failure. [Indexes and access paths](/review/relational/rl86/) separates selectivity from index existence and counts where matching rows sit.

## Fresh statistics can still model the wrong distribution

Statistics commonly include row counts, value frequencies, distinct-value estimates and histograms. A small tenant and a very large tenant need different work even when they use the same SQL shape. An average tenant size is not enough to price both well.

Correlated predicates create another error. If nearly every `paid` order is also `settled`, multiplying the two independent selectivities can undercount rows satisfying both. PostgreSQL extended statistics can describe dependencies and common value combinations within a table. They do not solve every join estimate or describe arbitrary relationships across tables.

Check the first wrong estimate against the actual predicates and value distribution. Recollect stale statistics first. For a known but poorly represented value, a higher statistics target may improve its sample or histogram at a collection and planning cost. For correlated columns, gather appropriate multicolumn statistics. If a function hides the distribution, an expression statistic or a different predicate may be needed.

A schema or query repair can sometimes teach the planner more directly: a valid unique constraint proves at most one matching row, while a selective condition moved to its correct input reduces work early. Do not move predicates across an outer join merely to obtain a prettier plan; that can change the answer.

## Reused plans can fit one parameter and hurt another

Prepared statements can reuse a plan rather than plan every call. PostgreSQL can choose custom plans using parameter values or a generic plan independent of them. A generic choice that serves ordinary tenants may be poor for an unusually large one.

Compare representative parameter shapes, including the large tenant and an empty result. Record the plan actually used by the application; an editor running a literal query can get a custom plan and miss the production problem. PostgreSQL's `EXPLAIN EXECUTE` and diagnostic `plan_cache_mode` settings help separate generic from custom choices. Force modes as a controlled experiment, then remove the setting unless it is the justified production remedy.

A database plan is also local to the executing engine. A distributed scan or lookup can repeat network work, so a cardinality mistake may amplify remote calls as well as page accesses. [Sharding and distributed SQL](/review/relational/rl105/) owns that authority and placement decision.

## Choose the next measurement from the cause

A plan can explain expensive execution and still miss why the endpoint is slow. Lock waits, pool queues, client decoding and transfer may dominate. Compare server execution with request duration and waiting evidence before changing indexes or memory. [Diagnosing a database incident](/review/relational/rl103/) puts that investigation in service context.

When the work is inside the plan, preserve the query, parameters, schema, statistics state and plan before changing one cause. Compare output correctness first, then rows, loops, page accesses, temporary I/O and latency under comparable cache and concurrency conditions. A warm second run cannot fairly establish an index's cold-read improvement.

The useful end of diagnosis is a causal statement: an estimate of one selected repeated key probes, but the input contained 40,000 rows; refreshed statistics selected a single scan and hash. That explains why the remedy worked and which future change could make it fail again.

A CockroachDB transaction can change keys on several ranges and still commit as one database decision. A booking can consume a place, create an order and record notification work even when those keys have different leaseholders. Replicating each range is necessary, but it does not by itself decide whether *all* those changes commit.

The application sees a simpler boundary: statements, results and a commit reply. Some conflicts are handled inside the database. Others return a retry error after the application has already used a result. A reliable client must know which attempt has ended, which decisions to recompute, and which effects belong outside the retryable transaction.

We will reserve the last place in workshop `s7`. Its capacity is a database invariant. A payment or email is a separate effect, and a missing commit reply is a separate uncertainty.

## Keep the invariant inside the transaction

Use the disposable cluster from [Keys, ranges and replication](/review/relational/rl123/), with `workshop` as the current database. Its tables already exist; these definitions show their relevant shape:

```sql
CREATE TABLE sessions (
  tenant STRING,
  session STRING,
  remaining INT CHECK (remaining >= 0),
  PRIMARY KEY (tenant, session)
);
CREATE TABLE orders (
  tenant STRING,
  request STRING,
  customer INT,
  amount DECIMAL(10,2),
  PRIMARY KEY (tenant, request)
);
```

The native conflict test resets session `('t4','s7')` to one remaining place before opening its two clients. The reservation below starts from that same one-place state. This is a disposable setup change; resetting capacity after accepted orders would invalidate the booking invariant.

For a new request `r81`, the transaction must establish that a place was consumed before accepting its order. With one place remaining, a successful conditional update returns zero as the new count:

```sql
BEGIN;
UPDATE sessions
SET remaining = remaining - 1
WHERE tenant = 't4' AND session = 's7' AND remaining > 0
RETURNING remaining;
-- Insert the order only when the update returned one row.
INSERT INTO orders VALUES ('t4', 'r81', 42, 20.00);
COMMIT;
```

The application performs the branch represented by the comment. If there is no returned row, it rolls back and reports that no place is available. Sending the whole listing blindly would insert an order even when the update matched nothing.

A stable request ID is also part of the protocol. Before accepting the purchase again, the application must determine whether `r81` already has a result and whether the repeated request has the same meaning. A uniqueness failure alone does not reconstruct the response, nor does it safely justify consuming another place. [The missing-reply investigation](/review/relational/rl93/) develops that lookup and reconciliation path in full.

## Provisional writes are not yet accepted facts

Below SQL, a transaction writes provisional values associated with its identity and timestamp. CockroachDB calls these **write intents**. Other transactions encountering the same keys need to discover whether the owner is still running, has committed or has aborted.

A transaction record supplies durable decision information. The coordinator keeps track of the participating writes and their progress. The application’s client connection, this coordinating work and each range’s replicated state are different things. Losing one SQL connection does not erase intents that were already replicated.

A simple implementation could first make the participant writes durable and then durably publish a commit decision. CockroachDB’s **Parallel Commits** protocol overlaps work. Its `STAGING` state records enough information about in-flight writes for another observer to establish whether every required write succeeded. A staging record whose required writes are proven present is implicitly committed; the coordinator can later mark it explicitly `COMMITTED` and clean up intents.

That last cleanup can continue after the client has success. It does not make the acknowledged transaction partially committed. The durable proof has to support the same all-or-nothing answer if the coordinator disappears before cleanup. We are describing the documented mechanism, not claiming that our SQL worksheet directly exposes every internal staging transition.

This is why “three replicas” is not an explanation of distributed transactions. Replication protects each participating range’s history. The transaction protocol establishes what their provisional writes mean together. [Transactions across partitions](/review/relational/rl106/) works through that distinction without product-specific state names.

## Observe two ranges across a lost reply

A separate [native fault worksheet](/review/relational/evidence/cockroach-atomicity-observed.json) tests SQL outcomes across faults. It creates `tx_left` and `tx_right`, each with an `effect` row whose `n` starts at zero. Range inspection confirms different range IDs and authorities: the left table is placed on the process labelled `us2`, the right on `ap3`.

These tables deliberately have one replica each, so stopping their sole process makes that participant unavailable. This isolates a transaction dependency; it is not a resilient deployment configuration. These counters form a separate fixture from the booking example.

Through a third process acting as SQL gateway, the client sends:

```sql
BEGIN;
UPDATE tx_left SET n = 1 WHERE k = 'effect';
UPDATE tx_right SET n = 1 WHERE k = 'effect';
COMMIT;
```

A small TLS protocol client receives the server's actual `COMMIT` completion, discards it before returning to the application, and kills that gateway. The test machinery knows the reply existed; the simulated application has no commit reply and cannot infer the outcome from its lost connection.

A fresh connection through a surviving gateway reads both values in one SQL statement and gets `1, 1`. The accepted pair survived gateway loss. That supports the SQL outcome for these two ranges; it does not identify the internal decision or intent-cleanup stage at which the process died.

The second attempt begins after that gateway returns. It provisionally changes the left value to two, then the worksheet stops the right table's sole process. An unrelated `health` row on the left still answers zero through a surviving gateway, showing that some useful SQL remains available. The required right-side update, however, cannot complete and reaches its two-second statement timeout with `57014`.

The client rolls back the incomplete transaction. After the stopped participant returns, one statement again reads `1, 1`. The provisional left value did not become an accepted half of the pair. This timeout is not a `40001` serialisation retry: the failed statement depended on unavailable data. Repeating work cannot replace its missing participant.

The [fault worksheet source](/review/relational/evidence/lab/cockroach_atomicity.py) retains placement gates, exact fault actions and SQL results. All processes share one host.

## A conflict can change the transaction’s timestamp

Suppose A and B each read one remaining place. A changes that row and commits. B later tries to write using the value it read before A committed.

CockroachDB uses multiversion values and transaction timestamps to decide which histories can be accepted. Under `SERIALIZABLE`, it may move a transaction forward in time and check whether its earlier reads remain valid. This check is **read refreshing**. If an intervening write changes what the transaction relied on, refreshing cannot simply bless the old decision.

| Event | A | B |
| --- | --- | --- |
| Read | Sees 1 place | Sees 1 place |
| First acceptance | Writes the booking and commits | Still holds its earlier decision |
| Later write | Finished | Tries to act on the old 1 |
| Required response | — | Re-evaluate from a new transaction if the attempt is rejected |

The exact conflict path depends on statements, isolation and ordering. The native two-client worksheet deliberately returns the read to each client before the conflicting write. That prevents us from mistaking a server’s transparent retry for proof that the application handled an exposed retry.

In the recorded history, A's `concurrent-A` order commits. B receives `40001`; a fresh attempt reads zero remaining places, and no `concurrent-B` order exists. Retrying has to revisit the decision to accept the booking.

`SQLSTATE 40001` identifies the transaction-retry path in this product. Inspect the SQLSTATE supplied by the driver; do not parse a particular paragraph of error prose. Other error classes, constraints and an uncertain connection loss require their own decisions.

## Retry the decision, not the last statement

If the transaction has been rejected, replaying its final `UPDATE` in a fresh transaction while keeping the old capacity decision can accept the same mistake again. A retry starts a new attempt, rereads the facts and repeats every dependent decision.

```text
repeat while attempts and deadline remain:
    begin a fresh transaction
    look up stable request r81
    if an accepted result exists:
        verify the repeated request matches it
        finish and return that result
    attempt the conditional capacity change
    if no place was changed:
        roll back; return unavailable
    insert order r81 and durable notification work
    try to commit
    on success: return the accepted result
    on known transaction retry (40001):
        end the failed attempt; wait with bounded jitter; repeat
    on an uncertain outcome:
        leave the blind-retry path; reconcile r81
```

This is client-protocol pseudocode, not a driver API. A driver adapter may supply the retry loop, but its callback still has to be safe to invoke again. Its result handling and transaction lifetime must match the actual library.

Sending several statements in one server-visible batch can allow internal retries that are impossible after results escape to the application. That is an optimisation opportunity, not permission to omit the client contract for other paths. A streaming result, a larger response or a changed application branch can expose an error that an earlier small example handled transparently.

## Keep external effects out of the retried callback

Imagine the callback charges a payment provider after reading capacity, then the SQL transaction returns `40001`. Retrying the callback can charge twice. The database can roll back its rows; it cannot unsend the first payment.

Record the intended external work in the same transaction as the accepted order. A separate worker performs it using a stable operation identity supported by the actual effect authority. When a reply disappears, that worker must reconcile the same operation rather than create a new charge.

An expired worker lease has a related boundary. A worker that paused before losing its lease can return and call the provider anyway. The resource accepting the effect must reject stale authority where exclusion is required. [Outboxes and database-backed jobs](/review/relational/rl94/) shows an actual fenced effect authority rather than treating a timer as a proof.

## Reduce conflicts without weakening the rule accidentally

First reduce the time and data covered by the transaction. Remove an unnecessary remote call from inside it. Use an access path that reads the relevant tenant and session instead of scanning many unrelated rows. An early locking read can make a competing writer wait instead of making it act on a soon-invalid decision; the waiting remains a cost to measure.

Do not change to historical reads for a current acceptance check. A perfectly consistent answer from several seconds ago can still promise a place that has been sold. Do not change isolation just to make retry errors disappear without checking which application anomalies become possible. [Isolation and follower reads](/review/relational/rl125/) runs that changed requirement.

One extremely popular session can remain a point of serialisation. Adding nodes does not let several incompatible changes to the same remaining-place value all succeed. If the workload cannot tolerate that contention, change the application’s allocation design and prove its invariant. Preserve the meaning of acceptance while measuring the new cost.

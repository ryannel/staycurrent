PostgreSQL chooses a query plan before it knows the query’s actual answer. Statistics and the query’s conditions let it estimate how much work each route will do. The executor then follows the chosen route and can report what happened.

That leaves two different failures to diagnose. The planner can underestimate an answer and choose a route that scales badly. Or it can estimate correctly while the application has simply asked for a great deal of work. Adding an index or increasing memory addresses neither distinction by itself.

Our workshop service has one unusually large tenant. The same prepared query asks for 50 rows when its parameter is `t5` and 45,000 when it is `t4`. We will change the information available at planning time, then repair a separate correlated estimate. All quoted plans were executed on PostgreSQL 18.6 by the [native lab’s core investigation](/review/relational/evidence/rl110-native.py).

## Establish the query and its data

The table is generated so the expected cardinalities can be calculated. It has 50,000 activity rows, deliberately wide enough for heap access to matter. This is the native lab's `access_lab` setup; use a fresh schema or reset that fixture before creating it again:

```sql
CREATE TABLE access_lab (
  id integer PRIMARY KEY, tenant text, created_at timestamp,
  tags text[], slot int4range, note text
) WITH (autovacuum_enabled = false);
INSERT INTO access_lab
SELECT n, CASE WHEN n <= 45000 THEN 't4' ELSE 't' || (n % 100 + 5) END,
       timestamp '2026-01-01' + n * interval '1 second',
       ARRAY['web', CASE WHEN n % 100 = 0 THEN 'audit' ELSE 'ordinary' END,
                    CASE WHEN n % 250 = 0 THEN 'urgent' ELSE 'routine' END],
       int4range(n,n+2,'[)'), repeat(md5(n::text),5)
FROM generate_series(1,50000) n;
CREATE INDEX access_tenant ON access_lab (tenant);
ANALYZE access_lab;
SET max_parallel_workers_per_gather = 0;
```

The first 45,000 rows belong to `t4`. The remaining 5,000 cycle through 100 other tenants, giving each 50 rows. The native fixture also has the method-comparison indexes from [index methods and operators](/review/relational/rl112/); those are not needed for this tenant lookup.

```sql
PREPARE tenant_lookup(text) AS
SELECT * FROM access_lab WHERE tenant = $1;
```

Run prepared-statement experiments in one session. A named prepared statement does not survive moving to an unrelated backend. The lab disables parallel workers in this diagnostic session to keep the compared trees serial.

The predicate excludes nearly everything for `t5`. For `t4` it requests nine tenths of the table. A sequential scan for that large answer is a plausible choice, not proof that PostgreSQL ignored a useful index.

## Read estimates beside observations

`EXPLAIN` shows the planned tree. `EXPLAIN (ANALYZE, BUFFERS)` executes it and adds observations. For a modifying statement, that means actual writes and locks. A rollback can undo transactional data changes, but it does not make execution free or reverse sequence advancement.

A node’s estimated `rows` is its output estimate. Actual rows describe output per execution; multiply by `loops` to understand repeated work. A node returning three rows over 10,000 loops produces about 30,000 rows across those executions. Rounded averages can hide variation between loops.

Read from the leaf operations towards their parents. Locate the first important estimate error where values have become known, then follow how repeated work or join choices amplify it. A parent’s time includes its children; summing every displayed time double-counts work.

`Buffers` separates PostgreSQL cache hits, reads and temporary work. A buffer read can be served by the operating-system cache. A hit count can include repeated visits to the same page. Neither is a direct count of physical device operations. Keep the result size, plan shape and cache state beside elapsed time.

## Custom plans know this tenant

Force a custom plan as a diagnostic comparison:

```sql
SET plan_cache_mode = force_custom_plan;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE tenant_lookup('t5');
EXPLAIN (ANALYZE, BUFFERS) EXECUTE tenant_lookup('t4');
```

The first plan used `Index Scan using access_tenant`, estimated about 50 rows and returned 50. The second used `Seq Scan`, estimated about 45,000 and returned 45,000, removing the other 5,000 rows by its filter.

The index route avoids most heap work for the small tenant. For the large tenant the scan can visit the table directly instead of consulting an index to reach nearly all of it. Both choices use the same index inventory; knowledge of the parameter changes the estimated value of each route.

Now require one parameter-independent plan:

```sql
SET plan_cache_mode = force_generic_plan;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE tenant_lookup('t5');
EXPLAIN (ANALYZE, BUFFERS) EXECUTE tenant_lookup('t4');
RESET plan_cache_mode;
```

Both executions used the tenant index and estimated 495 rows. The displayed condition contained `tenant = $1`. Actual output was still 50 or 45,000. The generic plan cannot make its route depend on which value this call supplies.

This fixture demonstrates estimate and route sensitivity. In the captured warm run, the large-tenant custom execution took 4.845 ms and the generic execution 5.281 ms. One comparison does not establish a production remedy. The index route reached the contiguous large-tenant part of the heap, while the sequential scan also examined the other tenants’ pages. Index work, cache state and measurement overhead still affect elapsed time.

The engineering question is whether representative application executions, with their data placement and concurrent load, justify the extra planning. Compare repeated latency distributions, buffer work and CPU across both tenant classes. A literal query pasted into a fresh session may choose a custom plan and fail to reproduce the application’s prepared-plan behaviour.

Under `plan_cache_mode = auto`, PostgreSQL initially uses five custom plans, compares their average estimated cost with a generic alternative, and chooses whether to reuse the generic plan. This is an estimated-cost decision, not a race of measured executions on every call. Check what the driver prepares and how the pool retains sessions before changing server-wide settings.

## Correlated columns break independent estimates

Our next table makes a different estimation problem exact. It has 9,000 `t4/paid` rows and 1,000 `t5/pending` rows. There are no other combinations.

```sql
CREATE TABLE correlated (tenant text, status text);
INSERT INTO correlated
SELECT CASE WHEN n <= 9000 THEN 't4' ELSE 't5' END,
       CASE WHEN n <= 9000 THEN 'paid' ELSE 'pending' END
FROM generate_series(1,10000) n;
ANALYZE correlated;
EXPLAIN (ANALYZE)
SELECT * FROM correlated WHERE tenant = 't5' AND status = 'pending';
```

Each condition alone matches one tenth. Treating them independently predicts one hundredth: 100 rows. They actually identify the same tenth: 1,000 rows. The observed plan showed precisely that error.

An extended-statistics object tells `ANALYZE` to collect information about this combination:

```sql
CREATE STATISTICS tenant_status (mcv, dependencies)
ON tenant, status FROM correlated;
ANALYZE correlated;
EXPLAIN (ANALYZE)
SELECT * FROM correlated WHERE tenant = 't5' AND status = 'pending';
```

The estimate became 1,000. The scan still read the same table and returned the same result. Correcting this estimate did not itself accelerate that simple scan; it gives later costing a better premise. In a larger join the wrong input estimate can change join order or the expected number of inner lookups, which is where the correction may earn its cost.

Choose statistics that address the demonstrated shape: most-common combinations, dependencies or distinct-group estimates. Increasing every column’s target without a hypothesis can increase collection and planning work while missing the relationship. Nor do these statistics give PostgreSQL arbitrary cross-table knowledge.

Inspect `pg_stats` for frequencies and distinct estimates, and verify that `ANALYZE` ran after a distribution-changing load. A larger target may help a rare or skewed value absent from a sample. A stale count, an unseen correlation and a generic parameter are different causes of similar row-estimate errors.

## A spill is execution evidence

Sort the full wide fixture with deliberately little memory:

```sql
BEGIN;
SET LOCAL work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM access_lab ORDER BY note;
ROLLBACK;
```

Here is the captured tree with timings omitted. The `cost` numbers are planner estimates in internal cost units; they are not milliseconds. `width` estimates the bytes per output row.

```text
Sort  (cost=23567.91..23692.91 rows=50000 width=246)
      (actual rows=50000.00 loops=1)
  Sort Key: note
  Sort Method: external merge  Disk: 12680kB
  Buffers: shared hit=1725, temp read=6321 written=6641
  ->  Seq Scan on access_lab  (cost=0.00..2225.00 rows=50000 width=246)
                            (actual rows=50000.00 loops=1)
        Buffers: shared hit=1725
```

The indented scan is the child. It supplies 50,000 rows to its parent sort, which returns those rows in note order. Both estimates match the observed output, so an underestimated result is not the cause here. Each node ran once. The parent's 1,725 shared hits include the child's work; adding them would count the same accesses twice.

`external merge` and the temporary blocks expose the spill. At `32MB`, the same query used quicksort in about 14.4 MB of memory. This establishes that a larger local allowance removed this operation's spill.

It does not justify setting every connection to 32 MB. `work_mem` applies to individual operations. A query can contain several sorts and hashes, several sessions can run together, and parallel workers can add allowances. Hash operations also use `hash_mem_multiplier`.

Ten concurrent queries with two 64 MiB operations each already represent about 1.25 GiB of possible working state, before the server’s other memory. Not every operation necessarily reaches its allowance simultaneously, but a global change must be evaluated against that concurrency. First try a query-local change or reduce unnecessary rows/width, then measure the resulting resource budget.

An index providing a required order can avoid a sort, but only if its remaining fetch and filtering work is worthwhile. A `LIMIT 10` above a full sort can still consume the whole input before the first result. A limit above a matching ordered scan can stop early, yet may inspect many rejected entries if another condition is not supported by that index.

Change the operation allowance and concurrent report count below. The native sort observations stay beside the aggregate budget, so removing one spill can be compared with the memory that simultaneous work may need.

## Verify the repair at the request boundary

Keep the original query’s semantics: tenant restriction, duplicate handling, null behaviour and full ordering. A faster query that silently drops a tenant boundary or changes how ties page is a different result.

Then replay the important variations. Test small and large tenants, common and rare values, fresh and older data, and prepared execution in the application’s actual pool mode. Compare enough runs to distinguish a route change from cache noise. Restore forced diagnostic settings afterwards.

If the request remains slow while its executor plan is cheap, look outside the plan. Pool waiting occurs before the backend receives the statement. A lock wait needs activity and blocker evidence. Returning 45,000 wide rows costs transmission and consumption work. [Operating and diagnosing PostgreSQL](/review/relational/rl120/) follows those boundaries.

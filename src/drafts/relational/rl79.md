A constraint makes a rule part of the database's write contract. An import script, an administrator's SQL and the application all face the same rule. If a booking must reference a real session, the database can reject a missing session even when a writer bypasses the booking form.

The useful question is which fact the rule concerns. A positive capacity belongs to one row. An existing session requires a reference. “Only this tenant may read this row” is an access decision. “The total number of accepted bookings must stay within capacity” concerns several concurrent changes. Giving these rules the same application-side check does not give them the same guarantee.

Here tenant `t4` owns customer `42`, session `s7` with capacity two and booking `b17`. IDs are local to a tenant. PostgreSQL supplies the executable examples; engine differences that alter enforcement appear after the mechanism.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Reject invalid rows at their home

```sql
CREATE TABLE customers (
  tenant_id text NOT NULL, customer_id integer NOT NULL,
  name text NOT NULL,
  PRIMARY KEY (tenant_id, customer_id)
);
CREATE TABLE sessions (
  tenant_id text NOT NULL, session_id text NOT NULL,
  capacity integer NOT NULL CHECK (capacity > 0),
  PRIMARY KEY (tenant_id, session_id)
);
CREATE TABLE bookings (
  tenant_id text NOT NULL, booking_id text NOT NULL,
  customer_id integer NOT NULL, session_id text NOT NULL,
  seats integer NOT NULL CHECK (seats > 0),
  status text NOT NULL CHECK (status IN ('confirmed','cancelled')),
  PRIMARY KEY (tenant_id, booking_id),
  FOREIGN KEY (tenant_id, customer_id) REFERENCES customers,
  FOREIGN KEY (tenant_id, session_id) REFERENCES sessions
);
INSERT INTO customers VALUES ('t4',42,'Ada'), ('t5',42,'Another Ada');
INSERT INTO sessions VALUES ('t4','s7',2), ('t5','s8',2);
INSERT INTO bookings VALUES ('t4','b17',42,'s7',1,'confirmed');
```

`NOT NULL` requires a value. `CHECK` limits the values and combinations allowed in one row. The primary key requires a unique, non-NULL identity. A foreign key requires each referenced combination to exist. These rules compose: none replaces the others.

A second writer tries these statements independently:

```sql
INSERT INTO bookings VALUES ('t4','b18',42,'s7',0,'confirmed');
INSERT INTO bookings VALUES ('t4','b18',42,'s7',NULL,'confirmed');
INSERT INTO bookings VALUES ('t4','b17',42,'s7',1,'confirmed');
```

The first fails its positive-seat check, the second its not-null constraint, and the third its primary key. None adds a booking. A `CHECK (seats > 0)` alone would accept NULL because its result is unknown; not-null closes that gap.

In a transaction, PostgreSQL reports the failed statement and leaves the transaction failed until rollback, or rollback to a savepoint. The application must handle the error rather than continuing as if only that row had vanished. Name constraints explicitly in production schemas when their identity helps the application translate a particular failure into a useful response.

## Carry ownership through the reference

Tenant `t5` owns session `s8`; tenant `t4` does not. Try to attach a `t4` booking to it:

```sql
INSERT INTO bookings VALUES ('t4','b18',42,'s8',1,'confirmed');
```

PostgreSQL rejects the foreign key: `(t4,s8)` is absent. It does not substitute `(t5,s8)`, even though the local session ID exists somewhere.

<div data-relational-component="relational-design-tools/Constraints" data-number="1"></div>

Two separate foreign keys, one for `tenant_id` and another for a globally unique `session_id`, would only prove that each exists. They would not prove that the session belongs to that tenant. Even with globally unique IDs, a unique `(tenant_id, session_id)` target and a composite reference can enforce this relationship explicitly.

Nullable composite references need care. Under the usual `MATCH SIMPLE` rule, any NULL referencing column exempts the row from the match. Keep required reference columns non-NULL. When an optional composite relationship must be entirely absent or entirely present, PostgreSQL's `MATCH FULL` rejects a partially NULL combination. Use a row check or an equivalent supported mechanism in other engines.

A reference also determines what deletion means. Default `NO ACTION` refuses a parent deletion that leaves a reference at its check time. `CASCADE` deletes dependent rows; it is suitable only when their lifetime belongs to the parent. An order retaining an agreed purchase is usually a reason to restrict customer deletion or detach personal details, not to cascade financial history accidentally. [History, correction and deletion](/review/relational/rl80/) follows that choice.

## Uniqueness needs the business condition

Suppose one customer may hold only one confirmed booking for a session, but may have cancelled attempts. A unique key on all three identity columns would also reject the historical attempts. PostgreSQL can enforce the narrower rule:

```sql
CREATE UNIQUE INDEX one_confirmed_booking
ON bookings (tenant_id, customer_id, session_id)
WHERE status = 'confirmed';
```

A second confirmed row for Ada and `s7` now fails, including when two writers race. A cancelled row is allowed. MySQL does not offer PostgreSQL-style partial indexes; a design using an appropriate generated value or a separate active-booking table needs its own NULL and uniqueness analysis. SQLite supports partial indexes, and SQL Server has filtered indexes.

Uniqueness also uses the column's equality rules. Optional values and case-insensitive identity need an explicit contract, as [Values, missing data and equality](/review/relational/rl78/) shows. A rule that works only because today's inputs happen to differ is not enforced.

## Timing changes what intermediate states are allowed

Most constraints are checked at statement time. Sometimes a transaction needs a temporary reference cycle: create two rows that refer to one another, then commit them together. A PostgreSQL foreign key declared `DEFERRABLE INITIALLY DEFERRED` can wait until commit, when both must exist. The external guarantee is still a valid committed state.

Deferral is not a way to ignore invalid data. Commit can fail, and the application must wait for that outcome before confirming success. PostgreSQL `CHECK` constraints are not deferrable. Product support and timing differ; SQLite supports deferred foreign keys, while MySQL InnoDB checks foreign keys immediately. On SQLite, enable and verify `PRAGMA foreign_keys = ON` for each connection before beginning a transaction; declaring a reference does not by itself establish that the connection is enforcing it.

Adding a constraint to an existing table must confront old rows. PostgreSQL can add a foreign key or check as `NOT VALID`: new changes face the rule, but old rows have not yet been proved valid. Repair the old violations, then `VALIDATE CONSTRAINT`. Until validation succeeds, do not describe the whole table as satisfying the rule. [Live schema evolution](/review/relational/rl100/) owns the rollout and completeness work.

## Capacity is a rule about a shared total

The current schema permits these two bookings for different customers: one seat and two seats. Each is positive; each references `s7`; neither repeats an active customer's identity. Together they exceed its capacity of two.

The second writer can demonstrate this without violating any existing constraint:

```sql
INSERT INTO customers VALUES ('t4',43,'Ben');
INSERT INTO bookings VALUES ('t4','b19',43,'s7',2,'confirmed');
SELECT s.capacity, sum(b.seats) AS reserved
FROM sessions s JOIN bookings b USING (tenant_id, session_id)
WHERE s.tenant_id = 't4' AND s.session_id = 's7'
GROUP BY s.capacity;
```

```text
capacity | reserved
2        | 3
```

A row check on `bookings` cannot maintain the sum over other booking rows. Hiding a query inside a check function does not make it a continuously enforced constraint. A trigger that simply reads the current total has the same race: two writers can both see one seat free before either inserts.

The rule needs an authority all competing changes meet. One option stores a remaining-seat counter on the session and atomically decrements it only when enough remain, in the same transaction as the booking. Another locks the session row before counting bookings; every operation that can change the total must take that lock. Serializable execution can reject a conflicting history and requires retries. [Transactions and isolation](/review/relational/rl90/) and [Locks, deadlocks and contention](/review/relational/rl91/) teach those protocols.

This distinction also finishes a tenant boundary. Composite keys prevent cross-tenant references, but do not stop a caller from selecting every tenant's rows. Privileges, trusted tenant context and, where suitable, row-level security enforce who can act. The database owner, privileged roles and policy bypasses need deliberate handling. Access policy and structural integrity protect different questions, so keep both.

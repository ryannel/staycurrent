A slow application request can be waiting for a connection before PostgreSQL sees it, waiting for another transaction inside the server, sorting to temporary storage or waiting for a commit’s durability boundary. These delays need different evidence and different interventions.

PostgreSQL exposes the server side through activity, wait events, locks, statistics and logs. The first task is to connect a delayed application request to its backend and work out which boundary owns the time. A query plan alone cannot include time spent in an application pool.

We will diagnose a blocked workshop order update, a spilling sort and a group of simultaneous connections. The [native core lab](/review/relational/evidence/rl110-native.py) executes the cases on PostgreSQL 18.6, with named client sessions and an operator connection.

## Establish the request’s timeline

Record when the application received the request, began waiting for its pool, acquired a connection, sent the statement and received its result or error. Keep a request identity such as tenant `t4`’s `r81`, without treating an order’s local ID as globally unique.

Set `application_name` usefully for the service or task. In a controlled investigation, `SELECT pg_backend_pid()` identifies the session handling a request. A pool can reuse that backend for another request later, so correlate timestamps and transaction scope too.

In PostgreSQL, start with:

```sql
SELECT pid, usename, application_name, state,
       xact_start, query_start, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blockers, left(query,160) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid();
```

Use an operator role with appropriate monitoring access. Ordinary roles cannot inspect every other session’s details. Query text may contain business data; choose logging and retention accordingly.

`active` means a statement is in progress, not necessarily using CPU. It can be waiting. `idle in transaction` means the backend is waiting for its client while a transaction remains open, potentially retaining locks and a snapshot. `idle` outside a transaction is a different state.

A wait event is a sampled location, not a complete history. A short-lived event can be missed, and the absence of a reported wait does not establish which CPU operation dominates. Collect a short bounded series while correlating the request’s timing.

## Diagnose a blocker before acting

Client A starts a transaction, updates `t4/o81` and remains open. Client B tries to update the same order. The lab names them `blocker` and `waiter`.

```sql
-- A
BEGIN;
UPDATE workshop.orders SET status = 'held'
WHERE tenant_id = 't4' AND order_id = 'o81';
-- Keep this transaction open.
```

```sql
-- B
UPDATE workshop.orders SET status = 'refunded'
WHERE tenant_id = 't4' AND order_id = 'o81';
-- Waits for A.
```

The operator sees B active with a `Lock` wait on `transactionid`, and `pg_blocking_pids` identifies A. A may be waiting for the client or sleeping in this controlled lab. B is waiting for A’s transaction outcome, not for a new index or more working memory.

<div data-relational-component="relational-product-tools/Blocker" data-number="1"></div>

The lab cancels B’s current statement:

```sql
SELECT pg_cancel_backend(pid)
FROM pg_stat_activity WHERE application_name = 'waiter';
```

B receives `canceling statement due to user request`; A continues and later rolls back. No refund was accepted by B. Cancellation relieved the waiting request without deciding A’s business transaction for it.

Cancellation targets the current statement. In an explicit transaction an error normally leaves that transaction aborted until rollback, so the client must clean up before returning the connection to a pool. Cancelling an idle transaction does not force its owner to end it. `pg_terminate_backend` closes a session and rolls back its open transaction, with a larger application consequence.

Before terminating A, establish whether its caller can safely retry and whether any external effect has already happened. A database rollback cannot undo an already sent email or payment. A statement waiting at `SyncRep` may already be locally committed, so interrupting it requires uncertain-outcome reconciliation rather than assuming rollback.

A recurring idle transaction needs a caller fix or an appropriate timeout, not an operator who repeatedly kills symptoms. A long legitimate transaction may need a different work boundary. [Vacuum and transaction age](/review/relational/rl111/) explains the retention consequence beyond this blocked row.

## Distinguish execution from memory pressure

The [plan investigation’s full sort](/review/relational/rl113/#a-spill-is-execution-evidence) is the diagnostic example here. Its 50,000-row activity table has a wide hash-based note. With a transaction-local `work_mem='64kB'`, the sort used external merge and about 12.7 MB of temporary disk space. At 32 MB it used quicksort in memory. The linked section supplies the runnable query and captured tree.

The meaningful evidence is the sort method and temporary block work, not just a faster second run. Increasing the local allowance changed where that intermediate state lived. A warm cache or different concurrent load could also change elapsed time without changing the cause.

Before raising memory globally, inspect the actual plan and rows. Reducing unused output columns or rows can reduce the sort’s input. An appropriate order index can sometimes avoid it. If the application needs every row in that order, a spill may be an acceptable resource trade rather than a defect.

`work_mem` belongs to operations, with additional considerations for hashes and parallel workers. It is not one memory cap for a backend. A setting that repairs one isolated sort can produce memory exhaustion under many simultaneous plans.

Use transaction-local settings for a justified large report when the workload permits, and verify it under the concurrency budget. [Reading and repairing plans](/review/relational/rl113/) follows the estimates and prepared-plan conditions that can make the operation unnecessarily large in the first place.

The allowance is paid by each active operation, not once per backend. The same report can fit by itself and exceed the service’s budget when many copies run. Change both inputs and inspect their product.

## Count connections and active work separately

The lab’s server has `max_connections=20`. It opens six named clients sleeping concurrently; with the operator, `pg_stat_activity` shows seven client backends. All six consume connection slots even though none is doing useful CPU work during its sleep.

The harness cancels one of those statements, records its client error and lets the other five finish. Their connections close, and the named-session count returns to zero. This demonstrates an actual bounded intervention and released sessions; the lab does not claim to have exhausted the configured connection limit.

```sql
SELECT state, wait_event_type, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state, wait_event_type;
SHOW max_connections;
```

Many idle backends, many active CPU-bound queries and many blocked active queries are different capacity problems. More connection slots do not add processor, memory or storage throughput. Allowing more simultaneously expensive work can make each request slower and increase timeouts and retries.

An application pool caps work per instance. Its total includes every replica, background worker pool and migration client. Forty application instances with twenty connections each can offer 800 sessions, before operator and recovery access. Keep admission and queueing bounded at the application boundary, with enough room for operational control under pressure.

If acquisition time rises while PostgreSQL has spare capacity, inspect pool limits, leaked checkouts and long application work performed while holding a connection. If the server is saturated, increasing every pool simply moves more requests into the saturated system. Lower admitted concurrency or shed/retry work according to the request’s semantics, then measure completed throughput and latency.

## Pool modes change session assumptions

Session pooling keeps a client associated with a backend for its connection. Transaction pooling can give the next transaction a different backend. A session-level tenant setting, temporary table, advisory lock, named prepared statement or other retained state may then be absent or belong to a different logical caller unless the pool explicitly supports and resets it.

A safe design makes a transaction’s required context local to that transaction and ensures every statement in the transaction stays on the same backend. `SET LOCAL` ends with the transaction; plain `SET` does not. Still verify the pool and driver’s exact prepared-statement and reset behaviour rather than assuming all transaction poolers are interchangeable.

No external pooler ran in this lab. This is a deployment contract to test with the chosen pool mode, especially for [row-policy tenant context](/review/relational/rl121/). A direct `psql` session cannot establish the behaviour of a separately configured pooling service.

## Use statistics as interval evidence

`pg_stat_statements`, when installed and preloaded as required, groups statement work so an operator can find high total cost and changes across calls. It is useful for prioritising a workload, but an average can hide one large tenant’s tail. Combine grouped statistics with representative parameter and request evidence.

For storage and maintenance, compare interval changes in `pg_stat_io`, `pg_stat_wal`, `pg_stat_checkpointer` and table statistics. A counter since startup is not a current rate. Check reset times, the monitoring transaction’s snapshot/cache behaviour and whether collection settings enable the timing you need.

A rise in temporary work suggests spills; WAL or checkpoint pressure suggests another path; dead-version and age evidence points towards maintenance. Wait events such as `WalSync`, `WalWrite` or `SyncRep` identify different commit boundaries. Do not turn every lock-looking wait into a row-contention diagnosis: lightweight coordination around WAL can reflect storage cost.

Logs supply events statistics may miss: errors, deadlocks, slow statements, temporary files, autovacuum durations and checkpoint completion. Enable targeted evidence with an operating budget. Excessive logging can add work and sensitive data without clarifying the incident.

After acting, verify the intended outcome. The blocked client should receive a known error, the leaked connection count should fall, or the sort should stop spilling under a safe local budget. Then check whether the application’s complete request improved. An intervention is useful when the observed mechanism predicts its result and its side effect is acceptable.

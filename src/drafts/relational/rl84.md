A write has a contract beyond its new values. It must identify the right rows, state what must still be true, and tell the caller whether the change happened. An import adds another question: what should a repeated or older record do to information already stored?

SQL can evaluate a precondition and make its change in one statement. That closes the gap between an application reading a value and later writing a decision based on it. Constraints still enforce the resulting row; transaction boundaries decide which related changes commit together.

These examples use tenant `t4`, session `s7` with capacity two, and booking `b17`. PostgreSQL provides the native mutation syntax. The write contracts also apply to other engines, although their upsert and result APIs differ.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Put a precondition on the change

```sql
CREATE TABLE sessions (
  tenant_id text, session_id text,
  capacity integer NOT NULL CHECK (capacity > 0),
  remaining integer NOT NULL CHECK (remaining >= 0 AND remaining <= capacity),
  PRIMARY KEY (tenant_id, session_id)
);
INSERT INTO sessions VALUES ('t4','s7',2,2);
UPDATE sessions SET remaining = remaining - 1
WHERE tenant_id = 't4' AND session_id = 's7' AND remaining >= 1
RETURNING session_id, remaining;
```

```text
session_id | remaining
s7         | 1
```

The predicate and decrement form one database operation. The application must inspect the result: zero returned rows means no qualifying session existed at the point of the write. It does not distinguish a missing session from insufficient remaining capacity unless a separate authorised read resolves that distinction.

Repeat the statement and it returns zero remaining. A third attempt returns no row and changes nothing. At PostgreSQL's default Read Committed isolation, writers updating this same row serialize through its row lock; the later update rechecks its condition against the updated row. At Repeatable Read or Serializable, a competing update can instead produce a serialization failure that requires retrying the transaction. [Transactions and isolation](/review/relational/rl90/) develops the full concurrent history.

The counter must commit with the booking. If the booking fails, roll back the decrement. A cancellation must release seats exactly once, and every write path must maintain the counter. Otherwise its `CHECK` protects a number that has stopped representing the bookings.

For ordinary edits, put the expected revision in the predicate:

```sql
CREATE TABLE bookings (
  tenant_id text, booking_id text, status text NOT NULL,
  revision integer NOT NULL CHECK (revision > 0),
  PRIMARY KEY (tenant_id, booking_id)
);
INSERT INTO bookings VALUES ('t4','b17','confirmed',7);
UPDATE bookings SET status = 'cancelled', revision = revision + 1
WHERE tenant_id = 't4' AND booking_id = 'b17' AND revision = 7
RETURNING booking_id, status, revision;
```

This returns `b17, cancelled, 8`. Repeating the edit with expected revision seven returns no row. The caller must reload and resolve the conflict instead of overwriting a newer edit. A statement that sets a column to its existing value may still count as an affected row; driver row counts are not a portable proof that a business value changed.

## An upsert chooses a conflict contract

An upsert attempts an insert and defines what to do when a unique identity already exists. Its conflict key is therefore a business decision. `(tenant_id, booking_id)` identifies this booking; a customer's name does not.

For an immutable request record, “insert or keep the original” can be right. For a replicated booking revision, unconditional replacement is dangerous: a delayed revision six must not replace the locally corrected revision eight.

```sql
INSERT INTO bookings AS current (tenant_id, booking_id, status, revision)
VALUES ('t4','b17','confirmed',6)
ON CONFLICT (tenant_id, booking_id) DO UPDATE
SET status = EXCLUDED.status, revision = EXCLUDED.revision
WHERE EXCLUDED.revision > current.revision
RETURNING booking_id, status, revision;
```

There is no returned row. The older input lost the comparison. Revision nine would replace eight. Equal revision with different payload needs a declared response too: reject and investigate it, or prove that the source's version protocol makes that combination impossible. Silently ignoring it can hide corruption.

`DO NOTHING` is not the same as successful application of this input. It says a conflict prevented insertion. If the caller needs the existing result, retrieve it under the appropriate concurrency protocol. If it needs replay safety for a request with uncertain commit, preserve stable request `r81` and the result it owns; [Retries when a commit reply is missing](/review/relational/rl93/) owns that protocol.

PostgreSQL can target a particular unique key. MySQL's `ON DUPLICATE KEY UPDATE` reacts to a unique-key conflict and needs care when several unique keys can identify different rows. SQLite has its own `ON CONFLICT` rules. SQLite `INSERT OR REPLACE` can delete the conflicting row and insert a replacement, with reference and trigger consequences; it is not an ordinary update.

## Stage raw input before publishing it

A batch contains six source rows: a new booking, two versions of an existing booking, an invalid status, an equal-version disagreement and an exact duplicate. Preserve source identity and raw values so a rejected record remains explainable.

```sql
CREATE TABLE import_raw (
  source_row integer PRIMARY KEY, tenant_id text,
  booking_id text, status text, revision_text text
);
INSERT INTO import_raw VALUES
 (1,'t4','b18','confirmed','1'),
 (2,'t4','b17','confirmed','6'),
 (3,'t4','b17','cancelled','9'),
 (4,'t4','b19','unknown','oops'),
 (5,'t4','b17','confirmed','9'),
 (6,'t4','b18','confirmed','1');
```

Bulk transfer such as PostgreSQL `COPY` can load this staging table efficiently. If fields are loaded directly into constrained typed destination columns, one malformed value can abort the load before the service has classified all rejects. A raw stage makes parsing and reporting separate from publication. Bound field sizes and batch volume as well; a text stage is not a licence for unlimited input.

Classify before casting. Here a valid revision is one to nine decimal digits and must be positive; that bound also makes an integer cast safe.

```sql
CREATE VIEW import_valid AS
SELECT source_row, tenant_id, booking_id, status,
       CASE WHEN revision_text ~ '^[0-9]{1,9}$'
            THEN revision_text::integer END AS revision
FROM import_raw
WHERE tenant_id = 't4' AND booking_id IS NOT NULL
  AND status IN ('confirmed','cancelled')
  AND revision_text ~ '^[0-9]{1,9}$'
  AND CASE WHEN revision_text ~ '^[0-9]{1,9}$'
           THEN revision_text::integer > 0 ELSE false END;
```

Row four is rejected. Rows three and five disagree at revision nine. A “last row wins” rule would make file order decide whether a cancellation survives. Quarantine that key/version conflict instead. Rows one and six are exact duplicates and can collapse without changing meaning.

PostgreSQL rejects an `ON CONFLICT DO UPDATE` statement that attempts to affect the same destination row twice, so deduplication is also necessary for a well-defined bulk statement.

## Reconcile the batch, including the rows it did not change

For this fixture, row four is invalid, rows three and five conflict, row six repeats row one, row two is stale, and row one inserts `b18`. The destination ends with `b17` cancelled at revision eight and `b18` confirmed at revision one. No corrected row is overwritten.

Record those six dispositions against a durable batch identity. The counts must reconcile: one applied, one stale, one duplicate, two contradictory and one malformed equals six input rows. A count of “one row changed” alone cannot explain what happened to the other five.

The script classifies outcomes while no other writer changes the destination. A precomputed “applied” label can become stale before the write, even inside one Read Committed transaction. With concurrent writers, apply the conditional upsert first and use its `RETURNING` rows to identify applied candidates.

In PostgreSQL, `ON CONFLICT DO UPDATE` locks a conflicting destination row even when its `WHERE` prevents the update. Keep that transaction open, read the unchanged candidates' destination rows, and classify them by the locked revision and payload. Record the resulting dispositions before releasing those locks at commit. Retry the whole transaction if concurrency produces a retryable failure.

Publish the actual destination changes and the batch's completed outcome together when they belong in the same database transaction. If the process crashes before commit, rerun the same staged batch. Version-conditional application leaves the final destination state unchanged on replay; distinguish “already applied by this batch” from an unrelated equal-version record using the batch ledger and payload comparison.

For a large live import, use bounded transactions and a durable cursor over source rows. A final completion check still has to account for every source record, including rejected keys. This page owns ingestion's write contract; [Live schema changes and backfills](/review/relational/rl100/) develops completeness while application writes continue.

Finally, set-based updates need the same discipline as imports. An `UPDATE ... FROM` with multiple source matches for one target has no useful business contract unless the source is reduced to one intended value. Preview the candidate identities, constrain the join, and verify the returned identities and post-state. The safe question is always what made this row eligible, what won its conflict, and what the caller can conclude from the reply.

A commit reply tells the caller that a transaction completed. Losing the reply does not tell it the opposite. The database may have committed before the connection broke, or the connection may have disappeared before commit took effect.

Both histories look like a failed request to the application. Treating that failure as permission to create a new purchase can charge or book twice. Treating it as proof that nothing happened can tell a customer their accepted order failed.

The repair is an application protocol: identify the intended operation, retain its meaning and result, and recover that same operation after uncertainty. Our workshop request r81 asks tenant t4 to create order o81 for customer 42 at an agreed total of 4,000 cents. The price is part of the intent; a retry does not silently replace it with today's catalogue price.

## Three states need three responses

A database error can describe a confirmed rejected attempt. PostgreSQL's serialization failure `40001` and deadlock `40P01` tell us that attempt cannot commit. End its failed transaction, then repeat the complete decision with fresh reads when the error is retryable.

A slow statement is different. It may still be waiting, executing or finishing. Sending another request adds a contender; the first request has not become a failed transaction merely because the caller's deadline expired. Cancellation itself can race with completion.

A broken connection after COMMIT may have been sent leaves an **unknown outcome**. Discard the broken connection and recover by operation identity. Do not convert that branch into a confirmed abort by guessing.

The application should track the point at which it sends commit and preserve the error's transaction semantics. Error codes are more reliable than translated message strings. Driver helpers can manage cleanup, but only if their contract makes rejected attempts and uncertain commits distinguishable.

## Lose the actual reply

Our PostgreSQL 18.6 experiment put a small protocol proxy between a native client and its disposable server. It forwarded commands and replies normally until the server produced `CommandComplete` for COMMIT. The proxy discarded that message and closed the connection.

The client had inserted o81 and r81 in one transaction. It then sent COMMIT and received `Connection terminated unexpectedly`. A separate authoritative connection found the completed purchase before we attempted any retry.

The proxy knows this particular transaction committed because it intercepted the server's completion. The application does not possess that evidence. The experiment demonstrates why its branch must handle uncertainty, even when the database is healthy.

## Retain the identity and the intent

A useful operation key survives every layer that may retry. The browser keeps r81 with its pending purchase; repeated HTTP requests carry it. A durable background task keeps the same identity across process restarts. Generating a new key whenever an HTTP request arrives defeats deduplication between those requests.

Scope the identity to its authenticated owner. Tenant t9's r81 must not recover tenant t4's order. A key is not an access token: authorisation still checks that the caller can obtain that tenant's result.

```sql
CREATE TABLE request (
  tenant text, id text,
  payload jsonb NOT NULL,
  result jsonb NOT NULL,
  PRIMARY KEY (tenant, id)
);
CREATE TABLE purchase (
  tenant text, id text,
  request_id text NOT NULL,
  customer integer NOT NULL,
  total_cents integer NOT NULL,
  PRIMARY KEY (tenant, id),
  UNIQUE (tenant, request_id)
);
```

The payload has a defined representation: session, customer, quantity, agreed price, currency and any other field that changes the operation. This small fixture uses a one-seat request and one currency, so its stored JSON explicitly contains session, customer and total. A real cart needs every line and a defined comparison, including ordering rules and numeric units. JSON formatting alone should not decide equality.

Keep a completed response or enough immutable facts to reconstruct it. Do not later recalculate the agreed price from a mutable catalogue. Reusing r81 with total 5,000 is a conflicting intent, even when it names the same customer and session.

## Claim before creating effects

On one borrowed connection, the handler opens Read Committed and tries to claim r81:

```sql
INSERT INTO request (tenant, id, payload, result)
VALUES ($1, $2, $3::jsonb, '{}'::jsonb)
ON CONFLICT (tenant, id) DO NOTHING
RETURNING id;
```

A returned row means this attempt owns a provisional claim. It may now reserve the seat, check the result, insert its purchase and store the response, all in that same transaction. If any required step fails, it rolls back the claim too.

An empty result means another attempt owns or completed that identity. The handler skips every business effect and reads the stored record in a subsequent statement on the same authoritative database. In PostgreSQL Read Committed, that fresh statement can see a conflicting claimant that committed while the INSERT waited.

```python
# Application protocol; SQL values are bound parameters.
async def record_or_recover(tenant, request_id, intent):
    tx = await begin_read_committed()
    try:
        if await claim(tx, tenant, request_id, intent):
            if not await reserve_one_seat(tx, tenant, intent.session):
                await tx.rollback()
                return unavailable()
            order = await insert_order(tx, tenant, request_id, intent)
            answer = accepted(order)
            await store_result(tx, tenant, request_id, answer)
            await tx.commit()  # An uncertain exception enters recovery.
            return answer

        stored = await lookup_on_same_authority(tx, tenant, request_id)
        await tx.rollback()  # This attempt created no business changes.
        if stored.intent != intent:
            raise ConflictingRequestIdentity()
        return stored.result
    except KnownRejectedAttempt:
        await cleanup(tx)
        raise
    except UnknownCommitOutcome:
        await discard_connection(tx)
        return pending(tenant, request_id)
```

The empty provisional result is never committed as a completed claim. Keep that invariant in one handler or a controlled database API. If callers can commit a claim and crash before completing its purchase, the design needs explicit pending-owner recovery, expiry and resolution states; the atomic protocol above avoids creating that extra durable state.

A retry whose claim waits on the original transaction is useful coordination. If the first attempt commits, the retry recovers it. If the first rolls back, the retry can claim the identity and perform the operation. An early empty lookup by itself cannot settle which future will occur.

## Complete the recovery branch

Our native replay used the stored JSON intent and result. Replaying r81 with customer 42, session s7 and total 4,000 returned `{"order":"o81","status":"accepted"}`. The purchase count stayed 1. Replaying the same key with total 5,000 ran the application's rejection branch before any new effect.

Recover on authoritative state. A lagging replica can report absence after the primary committed. If the authoritative database is unavailable, preserve r81 as pending and return an answer that admits the unresolved state. An attempt budget expiring is not evidence of rejection.

Retain the key for the whole retry contract. Deleting o81 and its deduplication record while a caller can still retry r81 makes that old request look fresh again. A long-lived tombstone or compact retained result may be appropriate after detailed order data expires. Define an explicit expiry response when retries beyond the retention period are refused.

Failover and restore can remove acknowledged deduplication history along with orders. That is a recovery contract, not something a unique index on the new history can infer. [Backup and reconciliation](/review/relational/rl96/) follows a later valid order lost by an earlier restore target, then reapplies its retained external identity once.

## Bound retries without changing the meaning

After a known retryable rejection, repeat the entire transaction, including the logic that selected its writes. Keep the operation key and agreed intent, but reread mutable capacity and authorisation. The answer may now be unavailable. Retrying is another evaluation, not a promise to force the original answer through.

Use a total deadline and attempt limit. Release the failed transaction and connection before sleeping. Jitter reduces the chance that every contender restarts together; bounded exponential backoff reduces repeated pressure. When conflict persists, investigate the hot resource or long transaction instead of expanding the loop indefinitely.

A payment provider is another authority. The database's r81 record cannot stop a second charge unless the provider recognises its own stable identity or supports an equivalent lookup contract. Record and reconcile the provider operation, and use an [outbox](/review/relational/rl94/) for durable delivery intent. “Exactly once” needs a named effect and an authority that enforces it.

## Port the protocol, then verify its SQL

The shared principle is a stable identity protected by one authoritative uniqueness decision, with effects and result committed atomically. PostgreSQL's `ON CONFLICT` spelling is one implementation.

InnoDB uses its locking and duplicate-key rules; a locking or fresh current read may be needed after a consistent snapshot began earlier. SQL Server needs its own transaction and unique-key error handling; a generic MERGE is not an automatic substitute for this complete protocol. SQLite serialises writers, but callers still need stable identity across HTTP retries and must handle busy or stale-snapshot failures. None of those differences removes uncertainty after a lost commit reply.

A connection gives an application a session with the database. It is not a unit of useful capacity. Hundreds of connections can be idle, while a handful of active transactions exhaust CPU, storage throughput or one contested booking row.

A connection pool reuses sessions and limits how many requests enter the database at once. Its limit places a queue somewhere: inside the application, at the pool, or among active database transactions. Capacity planning decides where that queue belongs, how large it may grow and how much work the service can safely admit.

Our workshop's request r81 reserves one seat in tenant t4's session s7. We will first count ordinary concurrency, then deliberately make every request contend on one record. More connections help the first workload only while resources can use them; they cannot split the second record's serial decision.

## Count occupied time, not just query time

In a stable system, average concurrency is arrival rate multiplied by average time spent in the measured part of the system. This is Little's law. The boundaries matter.

Suppose the application completes 200 requests a second, and each occupies a borrowed connection for 50 ms. The average occupied concurrency is `200 × 0.050 = 10`. If application work between SQL statements keeps that connection for another 150 ms, average occupancy becomes 40 even when the SQL itself did not slow down.

Measure connection checkout, queue wait, statement execution, lock waiting and commit separately. A large end-to-end latency can come from any of them. Do not increase the pool because a graph labelled “database time” includes waiting to borrow a connection.

The formula assumes a stable observation interval. During overload, arrivals can exceed completions and the queue grows. A closed-loop test whose clients wait before issuing another request can hide that growth by reducing offered load as latency rises. Record offered rate, accepted rate, rejected rate and completions.

## Budget every application instance together

A pool of 20 on one application process becomes 400 when autoscaling creates twenty processes. Workers, migrations, monitoring, administrative access and rolling-deployment overlap add more sessions. A per-process setting is only one share of the server budget.

Reserve connections and compute for diagnosing and recovering the service. If ordinary traffic consumes every slot, an operator may be unable to connect to stop the cause. Reserve work capacity too: a free administrative session does little if storage is full or every CPU is exhausted.

A pool should have a bounded pending queue, an acquisition deadline and a policy for overload. Reject or defer work that cannot finish within its useful deadline. Letting thousands of expired requests sit waiting converts a transient slowdown into sustained useless work.

Transaction/session features affect multiplexing. Temporary tables, prepared statements, advisory locks, tenant context and transaction state can bind an operation to a session. A proxy's transaction pooling changes which state survives between operations. Verify its reset and compatibility contract before treating its client limit as interchangeable with server connections.

## More clients can make the same bottleneck slower

We ran a deliberately serial PostgreSQL 18.6 workload. Every transaction updated the same row, slept for 10 ms while holding its lock, then committed. Each client issued five transactions. The sleep is an explicit experimental device, representing time spent while a shared resource remains held.

```sql
BEGIN;
UPDATE capacity_hot SET v = v + 1 WHERE id = 1;
SELECT pg_sleep(0.01);
COMMIT;
```

The extra clients did not raise the useful rate materially. They waited behind the same lock and widened latency. This tiny run establishes the serial mechanism, not a typical PostgreSQL throughput or percentile. The exact observations and run conditions are retained with the script.

Removing the 10 ms hold, shortening the transaction or changing the resource design can improve the ceiling. Adding nodes cannot make two incompatible updates to that one capacity counter independent. Sharding can spread many sessions across resources; it does not divide one invariant automatically.

A pool that keeps twelve contenders active here spends sessions on waiting. A smaller admitted set can preserve similar throughput while keeping the queue visible and bounded in the application, where expired work can be removed before it takes database resources.

## Admission needs a whole-request deadline

Consider a deterministic model with six simultaneous requests and two slots. Each admitted request takes 50 ms. Two finish at 50 ms, two at 100 and two at 150. The last pair waited 100 ms before starting.

If six active contenders instead each take 150 ms because of shared-resource pressure, all six finish at 150 ms and none wins a 120 ms budget. Those service times are model assumptions, not engine measurements. The point is to vary both admitted concurrency and the service time it causes, rather than assume a larger pool preserves each request's earlier speed.

A timeout must reach the work. After a confirmed statement cancellation, end the failed transaction. If a commit's outcome is uncertain, recover its stable identity instead of launching a new purchase. Retries need their own admission budget: three layers each retrying three times can multiply a small failure into many database attempts.

## Capacity includes retained bytes and recovery work

An application can have enough query capacity and still fail because history consumes the remaining disk. Replication slots, a failed archive, long snapshots and large backfills all retain or generate bytes beyond current business rows.

Suppose log generation is 20 MB/s, the required consumer is stopped and 60 GB of space is usable for its backlog. With no other growth, the runway is `60,000 / 20 = 3,000 seconds`, about 50 minutes. Index creation, temporary spills and the database's own safety margins shorten it. This is a budget from stated rates, not an exact exhaustion clock.

Catch-up requires spare rate. If a replica applies 25 MB/s while the primary continues generating 20 MB/s, it closes backlog at only 5 MB/s. A 60 GB backlog would take roughly 3.3 hours under those fixed assumptions. A recovery design sized only for the normal 20 MB/s can never catch up while traffic continues.

Memory has the same shared-budget problem. The buffer cache is not the whole server. Sorts, hashes, parallel query workers, connection overhead and maintenance use additional memory, often per operation rather than per connection. A pool that enables more concurrent large sorts can turn a safe setting into spills or memory pressure.

Plan for the reduced system too. A failover target may have a cold cache, fewer replicas or slower storage. A rebalance copies data while normal requests continue. The service's safe admitted rate during that interval can be lower than its healthy peak.

## Find the useful concurrency experimentally

Use production-shaped data and a representative mix of read, write, report and background work. Increase offered rate and active concurrency separately. Plot throughput, queue depth, latency distributions, CPU, storage latency, log rate, lock waits and memory use over the same interval.

The useful knee is where more active work stops buying the required throughput or starts violating the latency/error budget. Choose an operating point with margin, then test a failed replica, a checkpoint, a backfill or a restart. One average query timing cannot establish that point.

In PostgreSQL, server sessions carry per-backend resources and `max_connections` is an admission ceiling, not a throughput goal. InnoDB also has a bounded server connection model with engine-specific worker and memory costs. SQL Server's workers and memory grants can limit active work separately from session count. SQLite's embedded connections still share one writer per database; adding writer connections usually adds contention. The pool budget must follow the deployed engine's resource model.

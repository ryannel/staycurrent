PostgreSQL permissions determine who may connect, find objects and perform operations. Row security can additionally restrict which rows an allowed operation may see or change. A privileged function introduces another boundary: it can act with its owner’s rights rather than the caller’s.

These layers compose. A correct row policy is irrelevant if an application owns the table and bypasses it. A carefully restricted table can still be exposed through a function that resolves an attacker’s object under privileged authority.

We will use two orders with the same local ID, `t4/o81` at 20 and `t5/o81` at 90. Tenant identity must remain attached to every permitted row. The [native core lab](/review/relational/evidence/rl110-native.py) runs the permitted and denied requests through real PostgreSQL 18.6 roles.

## Ownership is an operational authority

The lab separates the owner from login roles:

```sql
CREATE ROLE migrator NOLOGIN;
CREATE ROLE app LOGIN;
CREATE ROLE tenant4 LOGIN;
CREATE ROLE elevated LOGIN BYPASSRLS;
CREATE SCHEMA secure AUTHORIZATION migrator;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

`migrator` owns the application schema and tables. Deployment authority can deliberately assume that role. `app` receives only runtime rights. The `elevated` role exists to make a bypass condition visible in the experiment; it is not a sensible normal application role.

Ownership gives control over the object, including changing its definition and access. Granting the application ownership is therefore much broader than granting it `SELECT` or `UPDATE`. A `NOLOGIN` owner still has authority; membership permitting another role to assume it must be controlled too.

The fixture creates the table as `migrator`, then grants the needed layers:

```sql
SET ROLE migrator;
CREATE TABLE secure.orders (
  tenant_id text, order_id text, agreed_price numeric,
  PRIMARY KEY (tenant_id, order_id)
);
INSERT INTO secure.orders VALUES ('t4','o81',20),('t5','o81',90);
GRANT USAGE ON SCHEMA secure TO app,tenant4,elevated;
GRANT SELECT,INSERT,UPDATE ON secure.orders TO app,tenant4,elevated;
RESET ROLE;
```

Schema `USAGE` allows names inside it to be resolved. Table privileges allow the named operations. Database connection privileges and authentication govern entry to the database. One does not imply the others.

If inserts use a separate sequence, check sequence privileges as well. If future migrations create new objects, existing table grants do not automatically cover them. `ALTER DEFAULT PRIVILEGES FOR ROLE migrator ...` changes defaults for objects that role subsequently creates; it is not a retroactive grant or a blanket default for every creator in the schema.

## Test with the real runtime role

The lab opens fresh clients authenticated as `app`, rather than sending every test through its superuser connection. It attempts:

```sql
DELETE FROM secure.orders;
ALTER TABLE secure.orders DISABLE ROW LEVEL SECURITY;
```

Both are denied: the application has no delete privilege and does not own the table. A successful test as the owner would have taught the wrong runtime boundary.

Keep denial tests alongside successful operations. Verify the application can perform the intended request, cannot perform the excluded request and cannot acquire a role that makes the exclusion irrelevant. `SET ROLE` is useful for controlled inspection, but a fresh login also tests authentication and inherited/session configuration.

The lab uses local trust authentication so all roles can be exercised without storing credentials. A deployed system needs appropriate authentication, network and credential management in addition to these database object rights.

## A row policy needs a trustworthy tenant source

The fixture enables row security and creates an application-context policy:

```sql
ALTER TABLE secure.orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_boundary ON secure.orders TO app
USING (tenant_id = current_setting('workshop.tenant', true))
WITH CHECK (tenant_id = current_setting('workshop.tenant', true));
```

`USING` controls which existing rows the role may access under this policy. `WITH CHECK` controls the permitted new row state for inserts or updates. Granting `UPDATE` alone does not allow a row to be moved to another tenant when the check rejects that new state.

Through `app`, with `workshop.tenant='t4'`, a query returns only `t4/o81/20`. Inserting `t5/evil/1` is rejected with `new row violates row-level security policy`. With no recognised tenant value, this equality does not accept rows.

But a normal custom setting is not authenticated identity. The same role can set `workshop.tenant='t5'` and read the t5 order. The lab executes that variation. This policy is suitable only when a trusted application chooses the setting from authenticated request context and arbitrary SQL under that role is outside the tenant’s authority. Giving an untrusted caller the `app` credential defeats that assumption.

For an independently authenticated tenant role, the fixture uses a policy that does not trust caller-controlled context:

```sql
CREATE POLICY tenant4_fixed ON secure.orders TO tenant4
USING (tenant_id = 't4') WITH CHECK (tenant_id = 't4');
```

The `tenant4` login still reads only `t4/o81` after setting the custom value to `t5`. Its attempt to insert a t5 row is denied. This is a different deployment contract, with a credential/role per tenant and the corresponding administration cost.

An application using a pool should set transaction-local context and keep all dependent statements in that transaction. Session context that leaks to the next caller creates a cross-request problem. Transaction pooling may also switch backends between transactions. Test the actual pool, driver and reset behaviour; this lab uses direct sessions.

Policies also combine. Multiple permissive policies can broaden the accepted set, while restrictive policies add conditions under their rules. Review the effective policy set after migrations, not just the one named `tenant_boundary`.

## Owners and bypass roles change the result

As the table owner, `migrator` initially reads both rows despite row security. The native test then forces owner participation:

```sql
SET ROLE migrator;
SELECT count(*) FROM secure.orders;
-- 2
ALTER TABLE secure.orders FORCE ROW LEVEL SECURITY;
SELECT count(*) FROM secure.orders;
-- 0
RESET ROLE;
```

The owner has no applicable accepting policy in this fixture, so forcing row security leaves it no visible rows. A superuser and the `elevated` login with `BYPASSRLS` still read both rows. `FORCE` does not turn row security into a boundary against every privileged server actor.

Keep ownership and bypass capability out of routine application credentials. Also inspect membership and privileged code that might grant equivalent access. A table policy does not constrain all operations identically; for example, table-wide operations and referential-integrity checks have their own semantics. Use the manual’s exact policy scope when deciding what a tenant can infer or change.

RLS is a useful database-enforced condition for permitted callers. It is not a substitute for restricting deployment authority, protecting the server and deciding which role is trusted to supply tenant identity.

## SECURITY DEFINER resolves names with authority

A `SECURITY DEFINER` function executes with its owner’s privileges. That can expose a narrow authorised operation without granting the caller direct access to its underlying tables. It can also turn unqualified object lookup into an attack path.

The lab creates `secure.config` and both functions as `migrator`. The configuration table contains `trusted`. An unsafe function uses `SET search_path=secure` and selects from unqualified `config`. The caller creates a temporary table also named `config`, containing `attacker`, and permits the owner to read it.

For relation lookup, the temporary schema can be searched before the named schemas when it is not explicitly placed. The unsafe function returns `attacker`. The table in the trusted schema still exists; the privileged function resolved a different object.

The safe version fixes the lookup path and puts temporary objects last:

```sql
BEGIN;
SET LOCAL ROLE migrator;
CREATE FUNCTION secure.safe() RETURNS text
LANGUAGE plpgsql SECURITY DEFINER
SET search_path = pg_catalog, secure, pg_temp
AS $$
DECLARE result text;
BEGIN
  SELECT label INTO result FROM config LIMIT 1;
  RETURN result;
END
$$;
REVOKE ALL ON FUNCTION secure.safe() FROM PUBLIC;
GRANT EXECUTE ON FUNCTION secure.safe() TO app;
COMMIT;
```

In the same caller session with its temporary shadow, the safe function returns `trusted`. The native result is `attacker | trusted` for unsafe and safe together.

The trusted schema must itself exclude untrusted object creation. Merely naming a writable schema in `search_path` does not make its contents safe. Schema-qualify sensitive objects, fix the execution environment, validate arguments and avoid unsafe dynamic SQL. Secure function execution rights in the same transaction as creation so no unintended public execution window opens.

A privileged function is still privileged code. An owner that bypasses row security can make the function bypass it too. Review its intended row boundary and exposed result, not just its function-level grant.

## Keep prevention and evidence separate

Grants and policies prevent particular operations. Activity views, statement logs and auditing facilities record selected evidence. A log of tenant reads does not stop an overprivileged role reading another tenant, and a denial test does not prove that every historical action was logged.

Choose access records from the actual investigation and retention needs, including who can modify or erase them. Test login, permitted operation, denied operation, ownership/bypass variations and the privileged-code path after material role or schema changes. Those executed requests expose assumptions that a list of grants alone can miss.

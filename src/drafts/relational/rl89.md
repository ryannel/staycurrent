Table partitioning divides one logical table into physical pieces according to a key. A session table might keep October's sessions in one partition and November's in another. Queries still address the parent table; the engine routes inserts and combines relevant partitions for reads.

Two jobs can justify the split. A date predicate can let a query skip unrelated partitions, and a retention operation can detach an old period as a unit. Neither benefit follows merely from the table being large. A lookup without a useful partition-key condition may search every piece, while uniqueness and references become harder to enforce across the boundary.

The examples partition workshop sessions by their start date inside one PostgreSQL database. This is not sharding: all partitions remain under the same database's transaction and write authority. [Sharding and distributed SQL](/review/relational/rl105/) owns distributing that authority.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Choose a boundary that serves the workload

Suppose most operational screens ask for sessions in a date range, and old sessions can be archived by whole calendar month. A range partition fits both jobs. If most lookups know only a session ID, monthly partitions offer less read benefit and create more places to probe.

```sql
CREATE TABLE sessions (
  tenant_id text NOT NULL, session_id text NOT NULL,
  starts_on date NOT NULL, capacity integer NOT NULL CHECK (capacity > 0),
  PRIMARY KEY (tenant_id, starts_on, session_id)
) PARTITION BY RANGE (starts_on);
CREATE TABLE sessions_oct PARTITION OF sessions
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE sessions_nov PARTITION OF sessions
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
INSERT INTO sessions VALUES
 ('t4','s7','2026-10-19',2), ('t4','s8','2026-11-02',12);
SELECT tableoid::regclass AS partition, session_id, starts_on
FROM sessions ORDER BY starts_on;
```

```text
partition    | session_id | starts_on
sessions_oct | s7         | 2026-10-19
sessions_nov | s8         | 2026-11-02
```

The range includes its lower bound and excludes its upper bound. Exactly midnight at the next boundary belongs to the next partition. Date-only `starts_on` makes the example simple; partitioning instants requires deliberate timezone boundaries, as [Values, missing data and equality](/review/relational/rl78/) explains.

Partition count is a consequence of the chosen granularity. Daily partitions make daily removal precise but create about thirty times as many child tables and indexes as monthly partitions. That adds planning, catalogue and maintenance work. Choose the coarsest boundary that earns the required pruning and lifecycle behaviour.

## Pruning skips pieces; an index searches inside them

```sql
EXPLAIN (COSTS OFF)
SELECT session_id FROM sessions
WHERE tenant_id = 't4'
  AND starts_on >= date '2026-10-01' AND starts_on < date '2026-11-01';
```

The plan names only `sessions_oct`. PostgreSQL proves that November cannot contain a matching date and omits it. This is partition pruning. A small fixture may still use a sequential scan inside October; pruning and index access are separate decisions.

Now remove the date:

```sql
EXPLAIN (COSTS OFF)
SELECT session_id FROM sessions
WHERE tenant_id = 't4' AND session_id = 's7';
```

Both partitions appear under an `Append`. Each can contain that tenant and session ID because the query supplies no partition boundary. With 120 monthly partitions, a rare lookup may need 120 local index probes or scans.

PostgreSQL can also prune during execution when parameter values become available. Not every expression permits that proof. Prefer a direct half-open predicate on the partition key and inspect the actual plan with representative parameters. An index on a different column does not itself tell the parent which partitions can be skipped.

Within a surviving partition, choose an index from the query workload. The parent index declaration creates corresponding child indexes in PostgreSQL; it is not one global B-tree over all dates. [Indexes and access paths](/review/relational/rl86/) explains why a selective index may still lose to a scan when much of one partition matches.

## Partitioning changes the uniqueness promise

The primary key above includes `starts_on`. PostgreSQL requires a partitioned table's primary or unique constraint to include all partition-key columns, subject to its documented restrictions. Local indexes can then prove uniqueness without a cross-partition index.

That key permits two rows with the same tenant and session ID on different dates. If the business says `s7` identifies exactly one session within `t4`, this is too weak. Adding the date merely to satisfy the engine must not silently redefine session identity.

One option is an unpartitioned session-identity table keyed by `(tenant_id, session_id)` and a partitioned table of dated occurrences keyed by identity plus date. Another is to partition a large history or attendance table while keeping the smaller current session table unpartitioned. A separate identity registry must be maintained transactionally; a row check or application convention alone cannot provide global uniqueness.

References inherit the cost. A booking referencing the partitioned primary key must carry the date as well as tenant and session ID. Rescheduling can then update the key and its dependants, and a retention detach may conflict with references. Decide whether the date is truly part of the referenced business identity before accepting that design.

MySQL partitioning has its own unique-key restrictions. In MySQL 8.4, partitioned InnoDB tables cannot contain foreign keys or be referenced by them. SQL Server supports different partitioned-index arrangements, including nonaligned indexes with their own maintenance tradeoffs. SQLite has no native equivalent of this PostgreSQL parent/child facility. Do not transfer a partitioning design based only on shared SQL syntax.

## Make the next partition before the boundary arrives

An insert outside all ranges fails unless a default partition exists:

```sql
INSERT INTO sessions VALUES ('t4','s9','2026-12-02',6);
```

The failure is explicit: no partition is found for the row. An operational process should create upcoming partitions before traffic reaches their dates and alert when the expected coverage is missing.

A default partition can keep ingestion available for unexpected dates, but it turns a clear error into a backlog that must be inspected and moved. Before attaching December, PostgreSQL must establish that the default partition contains no December rows. A default full of misplaced rows can make that work slow or fail the attach. Treat it as an exception queue with ownership, not permanent invisible storage.

Updates can move a row when its partition key changes. In PostgreSQL this can become a delete from the former partition and an insert into the destination; it has locking and concurrency consequences. A mutable start date may therefore be an awkward physical boundary for heavily rescheduled sessions. An immutable ingestion date serves a different lifecycle and must not be substituted unless it answers the intended retention question.

## Attach data with its boundary already proved

An archive or bulk-loading process can prepare a standalone December table, validate its range and then attach it:

```sql
CREATE TABLE sessions_dec (LIKE sessions INCLUDING DEFAULTS INCLUDING CONSTRAINTS);
ALTER TABLE sessions_dec ADD CONSTRAINT december_bounds
CHECK (starts_on >= date '2026-12-01' AND starts_on < date '2027-01-01');
INSERT INTO sessions_dec VALUES ('t4','s9','2026-12-02',6);
ALTER TABLE sessions ATTACH PARTITION sessions_dec
FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');
```

A matching validated check can avoid scanning that child to prove the partition bound. The attach still takes locks and must satisfy index and constraint requirements. A default partition may need separate validation against the new range. Plan the lock window and transaction behaviour for the actual engine; “attach” does not mean free or nonblocking.

After attachment, query through the parent to verify routing, count the prepared rows and inspect the required child indexes. Reconcile the prepared source before making the partition visible if it came from a bulk import. [Updates, upserts and bulk imports](/review/relational/rl84/) covers rejected rows and conflict contracts.

## Detachment changes visibility before it erases data

```sql
ALTER TABLE sessions DETACH PARTITION sessions_oct;
SELECT session_id FROM sessions ORDER BY session_id;
SELECT session_id FROM sessions_oct ORDER BY session_id;
```

The parent now returns `s8, s9`; the detached table still returns `s7`. Detaching removes a range from ordinary parent queries without physically erasing its rows. It can be a useful first stage of archival: verify the archive, update dependent read paths, then drop the old table when retention allows it.

PostgreSQL offers `DETACH PARTITION ... CONCURRENTLY` with different locking and transaction restrictions; interruptions can require finalisation. Use it only after checking the operation's conditions, including default partitions and references. The ordinary detach above is the executed teaching case, not a zero-downtime deployment recipe.

Dropping a whole partition avoids row-by-row deletion of its contents and associated index entries, but it does not eliminate locks, reference checks, backup copies or downstream data. A legal hold on one session can also prevent treating the month as one disposable unit. The physical boundary must fit the real lifecycle, including exceptions.

[History, correction and deletion](/review/relational/rl80/) defines what retained and removed data mean, while [Live schema changes and backfills](/review/relational/rl100/) develops changes under active traffic. Partition when a visible pruning or lifecycle saving justifies the new routing and enforcement obligations, and verify each benefit separately.

A PostgreSQL physical standby reconstructs the primary’s storage history from WAL. It can provide another recoverable copy and serve read-only queries while continuing to replay changes. Promotion ends recovery and lets that copy accept writes.

Those are separate capabilities. Receiving a commit does not mean a standby query can see it. Promoting a standby does not stop the old primary accepting writes. A streaming connection also does not retain a safe earlier state before a bad deletion.

We will follow workshop orders `o81` through `o84` across two independent PostgreSQL 18.6 servers. The [native replication lab](/review/relational/evidence/rl110-native.py) uses ports 56810 and 56811, separate data directories and actual WAL streaming. They share one machine, so this tests mechanisms and procedure rather than machine-level availability.

## Start from a physical copy

The primary owns a logged table:

```sql
CREATE TABLE physical_orders (
  tenant text, order_id text, PRIMARY KEY (tenant, order_id)
);
INSERT INTO physical_orders VALUES ('t4','o81');
SELECT * FROM pg_create_physical_replication_slot('physical_lab', true);
```

A physical slot retains WAL from its recorded restart position so a disconnected standby can catch up when it returns. The lab takes a base backup and writes standby configuration:

```sh
pg_basebackup -h "$PRIMARY_SOCKET" -p 56810 -U lab \
  -D "$STANDBY_DATA" -X stream -R -S physical_lab -c fast
```

`-R` creates the standby signal and connection settings. The fixture explicitly sets its primary connection to application name `standby_lab`, because the later synchronous policy names that standby. A setting written in `postgresql.auto.conf` can override `postgresql.conf`; inspect the effective configuration rather than assuming the last file you edited wins.

A production replication role should have the needed replication rights and an appropriate authenticated connection rule. The lab’s local trust/superuser connection is only an isolated convenience. A physical replication stream can expose the cluster’s data, so it is a privileged access path.

Physical replication follows the cluster’s storage format and history. It is not a way to select only tenant `t4` or rename a destination table. Keep primary and standby on compatible major versions, architecture and extension binaries. [Logical replication](/review/relational/rl118/) has a different row-level contract when selection or a migration is required.

## Receive, flush and replay are different progress

Once the standby has `o81`, pause its replay and insert `o82` on the primary:

```sql
-- Standby
SELECT pg_wal_replay_pause();
SELECT pg_get_wal_replay_pause_state();
-- paused
```

```sql
-- Primary, after the pause is confirmed
INSERT INTO physical_orders VALUES ('t4','o82');
SELECT application_name, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;
```

The primary’s first sample showed `sent_lsn` ahead of replay; its remote write and flush reports had not advanced yet. The following standby sample showed `pg_last_wal_receive_lsn()` ahead of replay. That function reports WAL received and synced locally. Querying the standby still returned only `o81`: its receiver continued while its recovery process was paused.

```sql
-- Standby
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();
SELECT * FROM physical_orders ORDER BY order_id;
-- t4 | o81
```

Resume with `pg_wal_replay_resume()` and wait for a fresh read to count two orders. A long-lived standby snapshot can still retain its earlier view, so a read-your-writes test also needs a fresh appropriate transaction.

Byte gaps between positions locate backlog. A time-lag field can be null or uninformative on an idle system; it is not a promise that every request is that many seconds stale. To require a particular write on a chosen replica, carry a position known to cover its commit, compare that replica’s replay progress within the same history, then read from a fresh snapshot or route to the writer. Account for failover and timeline changes in that protocol.

## Choose what the commit waits for

Streaming is asynchronous by default. A primary can acknowledge an order before the standby has received it. Losing the primary then promoting the standby can lose acknowledged work that never reached that candidate.

Synchronous replication extends the acknowledgement boundary to designated standbys. It adds remote work and communication to commit latency, and can reduce write availability when the required recipients are unavailable.

<table><caption>Boundaries with a configured eligible synchronous standby</caption><thead><tr><th>synchronous_commit</th><th>Required remote progress</th><th>Remaining distinction</th></tr></thead><tbody><tr><td>remote_write</td><td>Written to the standby operating system</td><td>Not necessarily persistent after its OS crash</td></tr><tr><td>on</td><td>Flushed durably on the standby</td><td>Standby queries may still wait for replay</td></tr><tr><td>remote_apply</td><td>Replayed on the standby</td><td>Existing old snapshots and other replicas can still be stale</td></tr><tr><td>local</td><td>No remote acknowledgement required</td><td>Only the local durability boundary is awaited</td></tr></tbody></table>

With no synchronous standby configured, `on` does not create a remote copy. Applications can also change their transaction’s setting. The actual guarantee is the effective setting plus the configured membership and the storage failure domains.

The lab configures one required named recipient:

```sql
ALTER SYSTEM SET synchronous_standby_names = 'FIRST 1 (standby_lab)';
SELECT pg_reload_conf();
```

It stops the standby, then sends the insert of `o83` from another client. That client waits, and `pg_stat_activity` reports `wait_event='SyncRep'`. Restarting the standby lets it receive the required WAL and releases the acknowledgement. The standby then reads three orders.

A waiting or interrupted commit is not evidence of a rolled-back order. Local commit may already have occurred while the caller waits for remote acknowledgement. Cancellation and lost connections need request-identity reconciliation, not automatic submission under a new identity.

`FIRST` chooses a priority-based set; `ANY` defines a quorum-style requirement. Decide which failure domains the set must span and how membership changes are controlled. Making an unavailable standby optional restores availability by changing the loss contract, not by repairing the missing copy.

## Slots trade rebuild risk for retention

While the standby was stopped, the lab’s `physical_lab` slot was inactive and its retained-WAL distance increased. Query this boundary on the primary:

```sql
SELECT slot_name, active, restart_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS retained_bytes
FROM pg_replication_slots;
```

Retention lets a returning standby catch up. It also consumes source storage. A forgotten slot can retain enough WAL to fill the volume needed by the live writer. `max_slot_wal_keep_size` can bound retention at a checkpoint, but crossing the bound can invalidate the consumer’s ability to catch up.

Without a slot, sufficient `wal_keep_size` or a retrievable archive may cover an outage. Otherwise required WAL may have been recycled and the standby needs a new base backup. Neither an existing slot name nor a successful TCP connection proves that the required history is available.

Physical standby feedback raises another budget. It can keep the primary from cleaning versions still needed by standby queries, reducing recovery conflicts while increasing primary bloat. That row-history horizon differs from the slot’s WAL position; inspect both when diagnosing growth.

## Fence the old writer, then promote

The lab catches the standby up through `o83`, stops the old primary and only then promotes:

```sh
pg_ctl -D "$OLD_PRIMARY_DATA" -m fast -w stop
pg_ctl -D "$STANDBY_DATA" -w promote
```

Stopping the old server is the lab’s explicit fence. Promotion supplies no command that makes another still-running machine stop writing. In production the fence may be power, storage access, network/application authority or an orchestrator’s verified exclusive control. A failed health check or an expired timeout alone does not prove the old server lost write authority.

The promoted server reports `pg_is_in_recovery() = false` and accepts `o84`. A connection to its port reads `o81`, `o82`, `o83` and `o84`. The fixture checkpoints and inspects the new timeline. Only that promoted copy remains the writer during the test.

The application still needs routing. Drain or invalidate old writer connections and direct new transactions to the selected endpoint. Reconnecting to the old host address would not discover the replacement automatically. Validate accepted request IDs and caller retry behaviour before reopening normal traffic.

The old primary’s data directory belongs to its earlier branch. Do not simply restart it as another writer or assume it can stream from the new one without repair. A fresh base backup is the straightforward rejoin; `pg_rewind` can be appropriate when its prerequisites and required history are satisfied. Its use needs its own tested procedure and post-rejoin acceptance.

The harness later stops the promoted lab server before restarting the original for a separate logical-replication investigation. That is a new isolated exercise, not a production rollback or a claim that divergent writers can safely alternate.

## Replication does not preserve an earlier mistake-free state

A physical standby faithfully replays a committed bad delete. A synchronous acknowledgement can make that bad delete especially well replicated. For recovery from logical damage, retain tested backups and archived history with a suitable recovery target.

The operating decision is therefore a set of concrete boundaries: what acknowledgement survives which failure, which replica has replayed the required work, who can fence the former writer, and how a diverged server returns. A successful promotion proves only one step of that procedure.

A database transaction can commit an order and the intention to send its confirmation. It cannot usually commit an email provider's action in that same atomic decision. An **outbox** preserves the intention as a database row so a worker can deliver it after the order commits.

A database-backed job uses a similar durable row for work such as generating a workshop document or reconciling a payment. A worker claims it, performs the work and records completion. Crashes and lost replies can happen between any two steps.

These patterns move slow or unreliable work out of a request without forgetting it. Their harder question is what happens when two workers both believe they may act, especially when an expired worker returns.

## Outbox: commit the fact and its delivery intent

Tenant t4's request r81 creates order o81 for customer 42. The order records its historical agreed price. In the same transaction, the application inserts outbox row j81 containing an event identity and the facts needed to send a confirmation. The local fixture uses these definitions; the reservation protocol is the capacity check from [transactions and isolation](/review/relational/rl90/).

```sql
CREATE TABLE purchase (
  tenant text, id text, request_id text NOT NULL,
  customer integer, total_cents integer,
  PRIMARY KEY (tenant, id), UNIQUE (tenant, request_id)
);
CREATE TABLE outbox (
  tenant text, id text, request_id text, payload jsonb,
  PRIMARY KEY (tenant, id)
);
```

```sql
BEGIN;
-- Reserve the seat and check success before these inserts.
INSERT INTO purchase (tenant, id, request_id, customer, total_cents)
VALUES ('t4', 'o81', 'r81', 42, 4000);
INSERT INTO outbox (tenant, id, request_id, payload)
VALUES ('t4', 'j81', 'r81', '{"order":"o81"}');
COMMIT;
```

The IDs and JSON are literal fixture values; application calls bind parameters. The transaction boundary is the important part. Rolling back removes both records. Committing preserves both. Our native drill performed each branch and inspected the resulting rows.

Sending before the transaction would allow a confirmation for an order that never commits. Sending after commit without a durable row leaves a crash window: the API can die before sending, with no durable instruction to try again.

The outbox closes the “forgot to send” gap. It does not close the “sent but did not record completion” gap. Marking complete before sending would reverse the failure: a crash would lose the effect instead. Where the recipient cannot join the transaction, preserve replay-safe identity at that recipient or accept and handle duplicate effects.

The payload is a deliberate choice. Store the confirmation's agreed facts if later edits must not change its meaning. Store an entity reference when processing should use current state, then define what happens if that entity changes or disappears. An outbox row that says only “look something up” does not preserve an earlier historical price.

## Relay restart and duplicate effects

A relay polls committed rows, delivers them and records progress. It can also use a change-data-capture stream, but the delivery contract is still about the durable event and the recipient's acknowledgement.

For a consumer that changes its own relational database, store `(consumer, tenant, event_id)` in a unique inbox table in the same transaction as its business effect. A repeated j81 finds that identity and returns the stored result. Rolling back the effect rolls back its inbox claim too. This is the same [operation-identity protocol](/review/relational/rl93/) used for uncertain commits.

For an external provider, send its supported idempotency key and recover its result after uncertainty. If it offers no duplicate-suppression contract, distinguish business tolerance from a guarantee. A repeated informational notification might be acceptable; a repeated payment usually is not. A stable local outbox ID cannot by itself change the provider's authority.

Ordering needs an equally precise scope. Two events for o81 may require an order version, with the consumer refusing or buffering version 3 until version 2 is resolved. Parallel workers can finish in the opposite order to their claim order. `ORDER BY created_at` in a polling query is not a global delivery-order guarantee. Unrelated orders often need no common order at all.

## Jobs: claim briefly, work outside the transaction

A job claim changes a row from eligible work to owned work. It should commit quickly, before the worker performs slow I/O. Keeping a database transaction and row lock open while generating a document ties scarce connections and locks to the slowest dependency.

A claim commonly stores a lease deadline and an increasing ownership generation, also called an epoch. Here is a small PostgreSQL job table:

```sql
CREATE TABLE job (
  tenant text, id text,
  epoch bigint NOT NULL DEFAULT 0,
  lease_until timestamptz,
  status text NOT NULL DEFAULT 'ready',
  PRIMARY KEY (tenant, id)
);
```

A batch claim can find eligible rows with `FOR UPDATE SKIP LOCKED`, update their leases and generations, return them, then commit. This avoids workers waiting on the same currently claimed rows. The selected index should narrow unfinished eligible work; completed history need not make every poll scan the whole table.

```sql
WITH candidate AS (
  SELECT tenant, id FROM job
  WHERE status = 'ready'
     OR (status = 'running' AND lease_until < clock_timestamp())
  ORDER BY tenant, id
  FOR UPDATE SKIP LOCKED
  LIMIT 10
)
UPDATE job j
SET status = 'running', epoch = j.epoch + 1,
    lease_until = clock_timestamp() + interval '1 minute'
FROM candidate c
WHERE (j.tenant, j.id) = (c.tenant, c.id)
RETURNING j.*;
```

The native drill executes this batch pattern too. With j82 locked by one connection, another worker claims j83; after release, its next batch claims j82. The epoch history below separately uses one named job so ownership changes stay easy to inspect. The lease clock belongs to the authority, not each worker's local wall clock. A worker carries the returned epoch into renewals, completion and effect requests. Updates with an older epoch must change no row.

Leases limit how long a dead worker can strand work. They do not guarantee that the worker stops executing at expiry. A paused process can wake after the database has leased its job to somebody else.

## An expired worker can still reach the effect

Worker A claims j81 at epoch 1, then pauses. Its lease expires. Worker B claims the job at epoch 2. A resumes with its earlier payload and token.

Checking the job row only when marking completion is too late. A can already have overwritten a document or sent another charge. Even checking immediately before the network call leaves a gap in which ownership can change. The authority performing the effect must reject stale authority at the point it accepts that effect.

<div data-relational-component="relational-operation-tools/Lease" data-number="2"></div>

We made the effect authority a separate native database operation. It checked the current unexpired epoch while locking the job row and inserted into an effect table whose primary key was `(tenant, job)`. The check and effect shared one transaction, so another claim could not change authority between them.

```sql
WITH authorised AS (
  SELECT tenant, id, epoch FROM job
  WHERE tenant = $1 AND id = $2 AND epoch = $3
    AND lease_until > clock_timestamp()
  FOR UPDATE
)
INSERT INTO effect (tenant, job, epoch, body)
SELECT tenant, id, epoch, $4 FROM authorised
ON CONFLICT (tenant, job) DO NOTHING
RETURNING *;
```

A's epoch-1 call returned no row. B's epoch-2 call inserted one confirmation effect. Repeating B's request inserted nothing. The final authority table contained one row at epoch 2. These outcomes were observed through separate PostgreSQL connections.

For a real remote resource, the resource must supply equivalent conditional acceptance, or all writes must pass through a gateway that does. Some systems accept an increasing fencing token and remember the highest accepted token; that prevents an older token from acting after a newer token has reached them. If exclusion must begin the instant a lease changes, their acceptance must also be tied to the current authority, as the SQL operation is here. A highest-seen token alone does not know about a newer lease it has never seen.

Choose the guarantee the resource can enforce. If a provider supports only duplicate identity, make the effect immutable for that identity. If it supports no conditional authority, do not claim that a lease excludes stale effects. Redesign the resource update, serialise it through an enforcing authority, or reconcile the remaining risk explicitly.

## Finish, retry or park the work

Completion should be conditional on tenant, job and epoch. A worker that loses its lease must not mark another worker's claim finished. A zero-row completion asks the worker to recover the effect's result and current ownership; it is not permission to act again with a new identity.

Retry transient failures with a next-attempt time and bounded exponential backoff. Record attempts, last error category and elapsed age. A permanently invalid payload needs repair rather than an endless retry. A parked or dead-letter job should retain its identity, intent and diagnostic history so an operator can reconcile or replay it safely.

Watch oldest unfinished age and service rate alongside queue length. A thousand short document jobs may be healthy; one stuck paid order may not be. Polling and workers also compete with the foreground database. Bound claim batch size and worker concurrency; keep enough capacity to renew leases and recover when a dependency returns.

A database queue suits modest work whose facts already live there and whose guarantees fit these operations. A dedicated queue can offer delivery scheduling and throughput facilities, but it does not remove recipient deduplication or stale-effect authority. Moving bytes to another product is not a substitute for completing the failure protocol.

## Adapt the claim to the engine

PostgreSQL and InnoDB offer locking reads with SKIP LOCKED, with different isolation and range-lock behaviour. SQL Server's READPAST-based patterns need its locking and isolation restrictions, including page-lock and versioning interactions; do not copy the PostgreSQL CTE as portable SQL. SQLite's single writer can claim work atomically, but many pollers still contend on one write boundary. The authority requirements for leases and duplicate effects remain the same.

An aggregate summarises several rows into one value. A window function calculates across related rows while keeping those rows in the result. The difference decides whether a daily report has one row per day or one row per order with a daily total alongside it.

Both operations need an explicit grain and an explicit set of contributing rows. Ordering adds another decision: two orders can share a timestamp, so “up to this order” may mean something different from “up to this timestamp”. A default that works until the first tie is a fragile running total.

These examples use four orders for workshop tenant `t4`. The order totals are already at order grain, so independent line and payment joins cannot inflate them. [Joins and the meaning of a result row](/review/relational/rl81/) shows why that preparation matters.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Grouping changes the row meaning

```sql
CREATE TABLE orders (
  tenant_id text NOT NULL, order_id text NOT NULL,
  customer_id integer NOT NULL, placed_at timestamptz NOT NULL,
  total numeric(10,2) NOT NULL, status text NOT NULL,
  PRIMARY KEY (tenant_id, order_id)
);
INSERT INTO orders VALUES
 ('t4','o81',42,'2026-10-19 09:00+00',40,'paid'),
 ('t4','o82',42,'2026-10-19 09:00+00',20,'pending'),
 ('t4','o83',43,'2026-10-19 10:00+00',30,'paid'),
 ('t4','o84',43,'2026-10-20 09:00+00',10,'paid');
SELECT (placed_at AT TIME ZONE 'UTC')::date AS day,
       count(*) AS orders, sum(total) AS order_value
FROM orders WHERE tenant_id = 't4'
GROUP BY (placed_at AT TIME ZONE 'UTC')::date
ORDER BY day;
```

```text
day        | orders | order_value
2026-10-19 | 3      | 90.00
2026-10-20 | 1      | 10.00
```

This report sums order value, including pending `o82`. The paid-only report below asks a narrower question.

`GROUP BY` collects equal grouping values. Every output expression must then describe the group: a grouping key, an aggregate, or an expression the engine can prove is determined by the keys. An arbitrary `order_id` has no answer for the first group, which contains three orders.

The chosen timezone is part of the report contract. A UTC day is not always the customer's local business day. Define that boundary before grouping, using [Values, missing data and equality](/review/relational/rl78/) for the time representation.

`WHERE` removes input rows before grouping. `HAVING` removes completed groups. To find customers whose total purchases exceed €50, group all their orders and use `HAVING sum(total) > 50`. Filtering `WHERE total > 50` first would find no rows in this dataset, because no individual order exceeds €50.

## Counts and averages have denominators

```sql
SELECT customer_id,
       count(*) AS all_orders,
       count(*) FILTER (WHERE status = 'paid') AS paid_orders,
       sum(total) FILTER (WHERE status = 'paid') AS paid_total
FROM orders WHERE tenant_id = 't4'
GROUP BY customer_id ORDER BY customer_id;
```

```text
customer_id | all_orders | paid_orders | paid_total
42          | 2          | 1           | 40.00
43          | 2          | 2           | 40.00
```

PostgreSQL and SQLite support aggregate `FILTER`. A broadly supported alternative is `sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END)`. Be deliberate about the `ELSE`: `count(CASE ... ELSE 0 END)` counts the zeroes too, since zero is non-NULL.

`count(*)` counts input rows. `count(value)` counts only non-NULL values. `avg(value)` divides by the count of known values, not all rows. If missing amounts mean an incomplete report, substituting zero disguises that uncertainty rather than resolving it.

An aggregate over no rows still returns one row when there is no `GROUP BY`: `count(*)` is zero and `sum(total)` is NULL. With `GROUP BY`, no input means no groups and therefore no output rows. A left join from a calendar can create the missing dates; count a non-NULL order key rather than `count(*)`, which would count the calendar's preserved row.

An average of averages usually loses the correct denominator. A day with one €100 order and a day with nine €10 orders have daily averages of €100 and €10; their mean is €55, but the ten-order average is €19. Carry sum and count through intermediate summaries, then divide total sum by total count. The same principle applies to weighted prices: `sum(quantity * price) / sum(quantity)`, with a deliberate zero-denominator case.

## A window keeps individual orders

```sql
SELECT order_id, customer_id, total,
       sum(total) OVER (PARTITION BY tenant_id, customer_id) AS customer_total
FROM orders WHERE tenant_id = 't4'
ORDER BY order_id;
```

```text
order_id | customer_id | total | customer_total
o81      | 42          | 40.00 | 60.00
o82      | 42          | 20.00 | 60.00
o83      | 43          | 30.00 | 40.00
o84      | 43          | 10.00 | 40.00
```

The result still has four order rows. `PARTITION BY` selects the rows related to each current row for this calculation. It does not physically partition the table. Include tenant identity unless a deliberately cross-tenant report is intended.

Window functions operate after filtering and grouping. A `WHERE status = 'paid'` would remove pending `o82` from both the output and the customer total. To calculate over all orders but show only selected ones, calculate the window in a subquery and filter outside it.

## Tied timestamps change the default frame

Add ordering to a window and the calculation can become cumulative. In PostgreSQL the default ordered frame includes rows through the current row's last peer: rows whose window ordering values are equal. The first two orders share 09:00.

```sql
SELECT order_id, total,
       sum(total) OVER (ORDER BY placed_at) AS through_timestamp,
       sum(total) OVER (
         ORDER BY placed_at, order_id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS through_order
FROM orders WHERE tenant_id = 't4'
ORDER BY placed_at, order_id;
```

```text
order_id | total | through_timestamp | through_order
o81      | 40.00 | 60.00             | 40.00
o82      | 20.00 | 60.00             | 60.00
o83      | 30.00 | 90.00             | 90.00
o84      | 10.00 | 100.00            | 100.00
```

Both timestamp peers receive €60. That is correct for “all orders through this timestamp”. The explicit `ROWS` frame plus unique tie-breaker gives one cumulative step per order. `ROWS` alone without the tie-breaker would allow either tied order first, so its individual totals would remain unstable.

A frame of `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` includes the previous order and this one. A time-based `RANGE` frame answers a different question, such as the preceding hour, and its allowed bounds depend on the engine and order type. Spell out what the metric means before choosing the frame.

`last_value(total)` is another default-frame trap. With an ordered frame ending at the current peers, it returns the last value in that frame, not necessarily the last order in the partition. To ask for the whole partition's last value, specify a frame ending at `UNBOUNDED FOLLOWING` with a deterministic ordering.

## Rankings need a tie policy

To rank orders by amount, `row_number()` assigns a distinct sequence number, `rank()` gives tied amounts the same rank and leaves gaps, and `dense_rank()` gives ties the same rank without gaps. On amounts €40, €30, €20 and €10 the distinction is invisible. Change €20 to €30 and the ranks become 1, 2, 2, 4, while dense ranks become 1, 2, 2, 3.

“Largest order per customer” can therefore mean one row or all equal-largest rows. For exactly one, use `row_number() OVER (PARTITION BY tenant_id, customer_id ORDER BY total DESC, order_id)` and filter `rn = 1` in an outer query. This dataset returns `o81` and `o83`. For all top ties, use `rank()` ordered by amount alone. Adding the ID to that ranking would break the tie and change the question.

`lag(total)` and `lead(total)` read neighbouring rows in a window order; they can compare successive bookings without a self-join. The first row has no predecessor, so a NULL result is meaningful. A top-level `ORDER BY` still controls presentation: a window's order controls calculation and does not promise the output will arrive that way.

A deterministic order is also the foundation of [Pagination and consistent exports](/review/relational/rl83/). It makes each page boundary expressible, while a snapshot decides which rows the whole traversal is allowed to see.

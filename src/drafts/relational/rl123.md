CockroachDB presents SQL tables while storing their contents as ordered key-value entries distributed across machines. A client can connect to one node and ask for a row whose data lives elsewhere. The connected node plans the SQL and routes the work; owning the client connection does not mean owning the row.

The useful unit of placement is a **range**, a contiguous interval of keys. Each range has replicas on several nodes. Its replication protocol keeps their accepted changes consistent, and a lease identifies the replica normally responsible for coordinating current access. To explain a request, we need to follow those boundaries rather than draw one database box per server.

We will load a small event table, split its primary-key space, and compare its secondary index with the underlying rows. The table is deliberately small enough to inspect. Its manual splits expose placement; they are not evidence that this workload needed a distributed database.

## A SQL row contributes ordered keys

Consider the table used in the native run:

```sql
CREATE TABLE workshop.events (
  id INT PRIMARY KEY,
  tenant STRING,
  created INT,
  value INT
);
CREATE INDEX events_by_tenant
  ON workshop.events (tenant, created);
```

The primary index stores rows in primary-key order. A conceptual key for event 2500 is `events / primary / 2500`. The real encoding includes identifiers and encoding details; this notation shows the ordering without pretending to be a byte dump.

The secondary index supplies another ordering: tenant first, then creation value, then the information needed to identify the primary row. That lets a query find a tenant’s recent events together even though its primary rows are scattered among other tenants’ events.

Ask for `value` using the first secondary index and the engine must retrieve it from the primary row. Adding `STORING (value)` can keep that returned value with the secondary entry. That saves another access path while adding maintained bytes and write work. [CockroachDB query work and hot ranges](/review/relational/rl126/) measures that change.

A SQL update can therefore write keys in several places. Updating `tenant` changes the secondary entry as well as the row. A multi-row transaction can touch several ranges. Replicating each range’s writes is one problem; accepting all the transaction’s changes together is another. [Transactions and retries](/review/relational/rl124/) follows the latter.

## Split the key space, then inspect ownership

Load the worksheet’s 10,000 events, or reproduce its insert:

```sql
INSERT INTO workshop.events
SELECT x, 't' || (x % 10)::STRING, x, x % 71
FROM generate_series(1, 10000) AS g(x);

ALTER TABLE workshop.events
SPLIT AT VALUES (2500), (5000), (7500);

SHOW RANGES FROM TABLE workshop.events WITH DETAILS;
```

The split request introduces primary-key boundaries at 2500, 5000 and 7500. It does not promise one range per node. A table’s secondary index has its own key spans; a range can cover more than one logical object when their key intervals allow it. Inspect the returned boundaries rather than count table rows and assume a placement.

The range output identifies range IDs, key bounds, replicas and the leaseholder. One row in the native output was:

```text
start_key     end_key       range_id  lease_holder  voting_replicas
…/1/2500      …/1/5000      81        1             {1}
```

The boundaries include the start and exclude the end, so event 2501 belongs to range 81; event 5000 belongs to the next interval. The `1` before the event key identifies the primary index in this abbreviated output. This early observation still had only one voting replica on these ranges: starting three processes did not mean replication had converged. It locates the keys, but does not yet establish tolerance of a node loss.

Range IDs are observations about this cluster, not stable application identifiers. Repeat the inspection through another SQL gateway. You are looking at the same distributed data, although the client entered elsewhere. Before testing failure, wait for the intended replica count and placement, as the [regional drill](/review/relational/rl127/) does.

Automatic splitting and rebalancing operate on these intervals as data and load change. Our explicit small split is a controlled teaching variation. A deployed cluster’s thresholds, load, capacity and placement constraints determine when useful movement occurs.

Range metadata can become stale after a split or lease transfer. Internal requests can refresh that information and retry routing without asking the application to understand a range ID. Do not infer that all SQL transactions are automatically safe to replay: internal routing retries and a client retry of a transaction are different boundaries.

Historical reads can sometimes use nearby replicas rather than the current leaseholder. Their safe timestamp is part of the read contract, not permission to return whatever local bytes happen to exist. [Isolation and follower reads](/review/relational/rl125/) tests that distinction.

## Replicas protect one range’s history

CockroachDB uses Raft to replicate a range’s state. With three voting replicas, a majority of two can accept progress; one surviving isolated replica cannot keep accepting conflicting changes independently. Replicas are copies of the same key interval, not extra partitions of its contents.

Losing one node can therefore leave the range available if a voting majority remains and the cluster can establish the required authority. Losing a majority stops progress for that range. A healthy SQL gateway elsewhere cannot manufacture the missing votes. System metadata and other ranges needed by the request also have to remain usable.

A leaseholder coordinates current access; a Raft leader leads replication. In 25.4, the default leader-lease mechanism normally puts both roles on the same replica, except briefly during transfers. Their jobs still differ, and neither role owns the whole database: another range can have its authority on another node.

Our three processes share a laptop. Stopping one demonstrates independent process failure and routing recovery. It does not show survival of that laptop, its drive or its power supply. The regional worksheet later uses labelled groups of local processes to test placement rules and controlled group loss; it still cannot measure a real regional network.

## Why sequential writes can remain hot

The split created several historical intervals, but every newly increasing `id` lands at the high end. Old ranges can become quiet while the newest interval takes most inserts. More nodes and many range IDs do not prove useful write distribution.

A hash-sharded index or a different key can spread that access. The cost appears on the read side: a range scan that was contiguous may now need several spans and a merge. A single shared capacity row is stricter still. Every booking that decrements that same row must agree on its next value, whichever node accepts the connection.

Choose the key from the workload. Inspect which spans receive writes, which nodes hold their leases, and how a proposed spread changes the queries. The useful diagnosis is “this operation concentrates on this key interval”, not simply “the cluster needs another node”.

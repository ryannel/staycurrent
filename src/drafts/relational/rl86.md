<p>An <strong>index</strong> lets a database find rows by their value without reading the whole table. Ask a database for customer 42’s orders with no index, and it reads every row in the table to find them. With an index on <code>customer_id</code>, it looks up 42 and goes straight to the matching rows.</p>
  <p>It works like the index at the back of a book. The terms are sorted, so you can find one quickly, and each term lists the pages it appears on. A B-tree index keeps values from one or more columns in sorted order, with entries that lead to their stored rows. The <strong>B-tree</strong> is the ordinary kind in PostgreSQL, MySQL’s InnoDB, SQLite and SQL Server, and it is this article’s subject.</p>
  <p>Indexes speed up queries that filter on a column (<code>WHERE customer_id = 42</code>), ask for a range (<code>BETWEEN 20 AND 34</code>) or sort (<code>ORDER BY placed_at</code>). They also enforce uniqueness and speed up joins on a key. In return, each index takes space, and inserts and many updates have to change it as well.</p>
  <p>Databases store a table in fixed-size blocks called <strong>pages</strong>: normally 8 kB in PostgreSQL and 16 kB in InnoDB; these are configurable defaults. Each page holds many rows, and the database reads a whole page even when it needs only one row from it. Page access is therefore a useful first measure of query work, alongside the entries examined and rows processed. A page may already be cached, so visiting it does not necessarily require a disk read.</p>
  <p>An index helps when it lets the database read fewer pages than a scan of the whole table would. For a narrow B-tree lookup, the query’s conditions and sort order should line up with the index’s leading columns, and few enough rows should match. The database’s planner judges both from its estimates and may decide a full scan is cheaper, so an index that exists isn’t always used.</p>
  <p>Count page accesses and examined entries to compare candidates, then check the chosen route in the query plan.</p>

  <p>The workshop collection uses tenant-scoped identities. This retained access-path model deliberately uses a separate, single-tenant orders dataset so every row and page count stays comparable to its original measurements. In a shared service, the customer-history key begins with <code>tenant_id</code>, followed by <code>customer_id</code>, date and the tie-breaker. Filtering customer 42 without that tenant would be a correctness error before it became an access-path question.</p>

  <section id="scan">
   <h2>Sequential scan</h2>
   <p>A <strong>sequential scan</strong>, also called a full table scan, reads every page of a table in order and tests each row against the query’s conditions. In PostgreSQL a table’s pages make up its <strong>heap</strong>, so called because its rows sit in no particular order. <a href="/review/relational/rl92/#a-row-lives-inside-a-page">Row versions, storage and cleanup</a> looks inside one.</p>
   <p>The figures in this article use an invented table of 36 orders, six to a page, so every row stays visible. Most figures also show, under their counters, the same measurement on <strong>the 60,000-order table</strong>, taken in PostgreSQL 18. It holds one order a minute from 1 January 2026, placed by 1,000 customers in turn, so each customer’s 60 orders are spread through the table, while consecutive customers share pages.</p>
   <p>Figure 1 scans the invented table for customer 42. Watch the counters: only four rows match.</p>

<div data-relational-component="indexes/ScanFigure" data-number="1"></div>

   <p>The scan read 6 pages and checked 36 rows to return 4. Its cost follows the size of the table, not the size of the answer. On the 60,000-order table, the same lookup read all 1,725 pages to return 60 rows.</p>
   <p>That count comes from <code>EXPLAIN (ANALYZE, BUFFERS)</code>, which runs a query and reports the route PostgreSQL took and the pages each step read. The section on <a href="#check">checking an index with EXPLAIN</a> shows how to read its output.</p>
  </section>

  <section id="entries">
   <h2>Index entries and row locations</h2>
   <p>An <strong>index entry</strong> pairs a key with a row location. The <strong>key</strong> is the indexed column’s value. The <strong>row location</strong> is whatever the database needs to find the row again, and it depends on how the table is stored. The ordinary row tables compared here use two broad layouts.</p>

   <h3 id="heap">Tables stored as a heap</h3>
   <p>Rows in a heap aren’t moved to keep an order, so an index entry can point straight at a row’s page and position. In PostgreSQL that location is a <strong>TID</strong>, short for tuple identifier; a tuple is PostgreSQL’s word for a stored row. A TID is a page number plus an item number on that page, and PostgreSQL shows it as the hidden column <code>ctid</code>. Order 3, the third row on page 0, has TID (0,3).</p>
   <p>Figure 2 builds an index on <code>customer_id</code>. Customer 42’s rows are on four different pages. Watch where their entries go.</p>

<div data-relational-component="indexes/BuildFigure" data-number="2"></div>

   <p>After sorting, customer 42’s entries sit side by side. Finding them means finding the first 42 and reading forward until the key changes. The table itself is not reordered: the index holds the order, and the TIDs lead back to the rows.</p>
   <p>On the 60,000-order table, an index on <code>customer_id</code> cut the lookup from 1,725 pages to 62. It read 2 index pages to find the 60 entries, then the 60 table pages they point to, because customer 42’s orders sit on 60 different pages.</p>

   <h3 id="key-order">Clustered tables</h3>
   <p>The other design keeps rows in the leaf pages of a B-tree, ordered by a <strong>clustering key</strong>. MySQL’s InnoDB uses the primary key for this when one is declared, and calls the table the <strong>clustered index</strong>. SQLite normally uses its integer <code>rowid</code>; <code>WITHOUT ROWID</code> tables use their declared primary key. SQL Server can cluster by a chosen index key, which need not be the primary key. Its primary-key constraint creates a clustered index by default when none already exists. The B-tree section below explains the shared structure.</p>
   <p>A row in a clustered table moves when its page fills up and divides in two, so it has no fixed page and position to point at. Each entry in another index carries the clustering key instead. Finding a row through such an index then takes two searches: one in the index, then one in the table for the key the entry carries. The section on <a href="#clustered">searching a clustered table</a> follows both, once the B-tree has been explained.</p>
  </section>

  <section id="btree">
   <h2>B-tree</h2>
   <p>So far, nothing says how a search finds the first 42. A <strong>B-tree</strong> is a tree of index pages that lets a search jump there instead of reading the entries from the start. The sorted entries live on <strong>leaf pages</strong>. Above them, <strong>branch pages</strong> hold one key for each page below, marking where that page’s range begins; PostgreSQL’s documentation calls them internal pages. The single page at the top is the <strong>root</strong>.</p>
   <p>Figure 3 draws the invented index as a B-tree on its side, with the root on the left. Pick a customer and count the index pages the search reads.</p>

<div data-relational-component="indexes/DescentFigure" data-number="3"></div>

   <p>Every search in this tree reads three index pages, whatever the key: root, branch and leaf. That count is the tree’s <strong>depth</strong>, and it grows very slowly. A real leaf page holds hundreds of entries, so each extra level multiplies the rows the tree can reach by hundreds. The 60,000-order table’s customer index has only two levels, a root and its leaf pages, which is why its lookup read 2 index pages.</p>
   <p>To see how slowly depth grows, the table below indexes a single integer column in three separate tables of 100,000, 1 million and 10 million rows.</p>
   <div class="table-scroll" role="region" tabindex="0" aria-labelledby="depth-caption"><table><caption id="depth-caption">B-tree depth for an index on one integer column, measured in PostgreSQL 18</caption><thead><tr><th>Rows</th><th>Levels</th><th>Index pages</th></tr></thead><tbody><tr><td>100,000</td><td>2</td><td>276</td></tr><tr><td>1,000,000</td><td>3</td><td>2,745</td></tr><tr><td>10,000,000</td><td>3</td><td>27,422</td></tr></tbody></table></div>
   <p>A freshly built leaf page held 367 integer entries, and going from 1 million rows to 10 million added no level. A lookup for one key among the 10 million read 4 pages: 3 in the index and 1 in the table. A larger page can hold more entries, but entry width, page overhead and fill also differ between engines. PostgreSQL’s measured depths do not establish InnoDB’s depth for the same row count.</p>
  </section>

  <section id="range">
   <h2>Range scans</h2>
   <p>A <strong>range scan</strong> descends to the first entry at or above a lower bound, then reads entries in order until it passes the upper bound. B-trees serve <code>&lt;</code>, <code>&lt;=</code>, <code>=</code>, <code>&gt;=</code>, <code>&gt;</code>, <code>BETWEEN</code>, <code>IN</code> and <code>IS NULL</code> this way.</p>
   <p>Figure 4 runs a range scan for customers 20 to 34. Watch how many times the search descends, and what it does at the end of a leaf page.</p>

<div data-relational-component="indexes/RangeFigure" data-number="4"></div>

   <p>The search descended once, to the first 20. At the end of each leaf page it followed the link to the next, and it stopped at 42, the first key past the range. The entries came out in key order, so the <code>ORDER BY</code> needed no extra work.</p>
   <p>The links let PostgreSQL and InnoDB step from one leaf page to the next without going back up the tree, so a range scan descends only once.</p>
   <p>On the 60,000-order table, customers 40 to 45 have 360 orders, and the index search read 3 pages to collect them: the root and two leaf pages. PostgreSQL then sorted the 360 rows again. It had fetched them with a <strong>bitmap heap scan</strong>, which collects the matching row locations from the index and reads the table pages in page order, so the rows lose the index order. The section on <a href="#selectivity">selectivity</a> returns to it.</p>
  </section>

  <section id="clustered">

   <p>With the B-tree in hand, a clustered table is easy to picture: its rows sit on the leaf pages, in clustering-key order. A lookup by that key is one descent, like the searches above. Rows with neighbouring keys share pages, so a range of keys reads few pages. In a heap, rows land wherever there is room, so the key says nothing about the page.</p>

  <section id="selectivity">
   <h2>Selectivity and the planner’s choice of scan</h2>
   <p><strong>Selectivity</strong> is the fraction of a table’s rows that a condition matches. A condition matching 60 rows out of 60,000 is very selective; one matching half the table is not. The <strong>planner</strong>, the part of the database that chooses how to run a query, estimates selectivity from statistics that a command such as <code>ANALYZE</code> collects. Then it picks one of three routes:</p>
   <ul>
    <li>An <strong>index scan</strong> follows each entry to its row, in index order.</li>
    <li>A <strong>bitmap heap scan</strong> collects the matching TIDs from the index, sorts them by page, then reads each table page once. It saves repeat visits but returns rows in page order, not index order. MySQL’s Multi-Range Read does the same job, sorting row lookups before it makes them; its plan says <code>Using MRR</code>.</li>
    <li>A <strong>sequential scan</strong> ignores the index and reads every page.</li>
   </ul>
   <p>Figure 6 widens a range one customer at a time. Watch how quickly the matching rows spread across the pages. Then switch the table order to “By customer” and step through again.</p>

<div data-relational-component="indexes/SelectivityFigure" data-number="6"></div>

   <p>With the rows scattered, every page held a match by the third step, when 8 rows (22% of the table) matched. From there the index can only add work. A bitmap heap scan reads all six pages anyway, and an index scan reads some of them more than once.</p>
   <p>Stored by customer, the same rows filled one page before reaching the next, and the matches reached every page only at 89% of the table. Where the matching rows sit matters as much as how many there are.</p>
   <p>The 60,000-order table is laid out like the “By customer” order: one customer’s rows are spread out, but consecutive customers share pages, about 35 to a page. PostgreSQL chose a bitmap heap scan up to <code>customer_id &lt;= 500</code>, half the table, reading 922 of the 1,725 pages, and a sequential scan from 550. On a copy with the rows shuffled, the same bitmap scan read every page, yet the planner switched at the same point. Its estimate treats the matches as spread at random, so it can’t see the difference. When the choice matters, compare the pages each plan actually read.</p>
   <p>The order of reads matters too. A sequential scan reads pages one after another, which storage serves quickly, while index lookups jump around, so planners price a jumping read higher. PostgreSQL makes that price two settings, <code>seq_page_cost</code> and <code>random_page_cost</code>, which you can change.</p>
   <p>Selectivity belongs to the value, not the column. Four in five of the 60,000 orders are paid and the rest pending. With an index on <code>status</code>, a query for the paid orders was still a sequential scan of all 1,725 pages. The pending orders used the index.</p>
   <p>Their layout helped: they arrived in blocks of 1,000 consecutive orders, so the fifth of the table they make up sits on 365 pages. Scattered, a fifth of the rows would have touched nearly every page.</p>
   <p>The planner knows this only through its statistics, so a skewed value or an out-of-date count can send it the wrong way. <a href="/review/relational/rl87/#make-the-statistics-miss-new-data">Query execution and bad plans</a> follows the work caused by a wrong estimate.</p>
  </section>

  <section id="composite">
   <h2>Composite (multicolumn) indexes</h2>
   <p>A <strong>composite index</strong> has more than one key column. Its entries sort by the first column, then by the second among entries that tie on the first, and so on. The column order decides which entries sit together.</p>
   <p>The rest of this article often returns to one query on the 60,000-order table. The <strong>history query</strong> asks for customer 42’s ten newest orders since 1 February:</p>
   <p><strong>The history query: customer 42’s ten newest orders since 1 February</strong></p>
<pre><code class="language-sql">SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
  AND placed_at &gt;= timestamptz &#x27;2026-02-01 00:00:00+00&#x27;
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;</code></pre>
   <p>Figure 7 asks a small version of it: customer 42’s two newest orders since 10 January. Switch between the three indexes and count the entries each one reads.</p>

<div data-relational-component="indexes/CompositeFigure" data-number="7"></div>

   <p>With <code>customer_id</code> alone, the index found customer 42’s four orders but knew nothing about their dates, so every row was fetched, checked and sorted. With <code>(customer_id, placed_at DESC)</code>, the entries were already newest first, and the scan stopped after two. With the date first, every customer’s entries were interleaved by date, and the scan read 16 to find two.</p>
   <p>An index on <code>(a, b)</code> helps a query that filters on <code>a</code>, or on <code>a</code> and <code>b</code>, because entries with the same <code>a</code> sit together. It generally doesn’t help a query on <code>b</code> alone, because the matching <code>b</code> values are spread through every <code>a</code>.</p>
   <p>More precisely, equality conditions on the leading columns, plus a range condition on the next one, limit how much of the index is read. So put the columns compared with <code>=</code> first, then the column used for the range or the sort.</p>
   <p>When the leading column has no condition, PostgreSQL 18 can still search the index once for each distinct value of that column. This is a <strong>skip scan</strong>, and MySQL and SQLite have narrower versions of it. It is especially useful when the leading column has few distinct values. With many values, repeated searches can cost more than a scan; verify the chosen route on the workload before relying on it.</p>
   <p>The history query read these pages with each index in place:</p>
   <div class="table-scroll" role="region" tabindex="0" aria-labelledby="history-caption"><table><caption id="history-caption">The history query on the 60,000-order table with each index in place</caption><thead><tr><th>Index</th><th>Plan</th><th>Pages read</th></tr></thead><tbody>
    <tr><td>None</td><td>Sequential scan, then sort</td><td>1,725</td></tr>
    <tr><td><code>(customer_id)</code></td><td>Bitmap heap scan: 60 rows fetched, 45 rejected, then sort</td><td>62</td></tr>
    <tr><td><code>(placed_at DESC, customer_id)</code></td><td>Index scan through about 11,000 entries, then a partial sort</td><td>54</td></tr>
    <tr><td><code>(customer_id, placed_at DESC, order_id DESC)</code></td><td>Index scan, stops after 10 rows, no sort</td><td>13</td></tr>
   </tbody></table></div>
   <p>Pages dominate the work, but page counts alone can mislead. The reversed index’s 54 pages look cheap beside the customer index’s 62, yet it read about 11,000 entries, every customer’s newest first, to find ten rows. When page counts are close, compare the entries or rows read with the rows returned. Reading 11,000 to return 10 says the index doesn’t fit the query.</p>
   <p>The composite index read 13 pages: 3 index pages, one per level, and 10 table pages, one per row. Its entries are wider than the customer index’s, so its tree has three levels. The <code>order_id DESC</code> column breaks ties between orders placed in the same instant, as the query’s <code>ORDER BY</code> does.</p>

   <h3 id="fates">What an index does with each condition</h3>
   <p>The history query’s two conditions both decided where the scan started and stopped. A paid-only version adds a third:</p>
   <p><strong>Customer 42’s ten newest paid orders</strong></p>
<pre><code class="language-sql">SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
  AND placed_at &gt;= timestamptz &#x27;2026-02-01 00:00:00+00&#x27;
  AND status = &#x27;paid&#x27;
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;</code></pre>
   <p>With an index that lacks <code>status</code> (the covering index of the next section), PostgreSQL fetched 12 rows and threw away 2 pending ones to return 10. Its plan listed <code>status</code> under <code>Filter</code>. For a customer whose recent orders were mostly pending, it would read much further.</p>
   <p>That <code>Filter</code> line is one of three things a condition can do, and the plan tells you which:</p>
   <ul>
    <li><strong>It narrows the scan.</strong> Equality on the leading key columns, plus one range on the next, decides where in the index the scan starts and stops. In the history query, <code>customer_id = 42</code> and the date since 1 February did this.</li>
    <li><strong>It is checked inside the index.</strong> A condition on a later key column is tested against each entry the scan reads. It saves table visits for the entries it rejects. In an ordinary range scan it does not narrow the interval; PostgreSQL 18 may also use skip scans to jump over parts of that interval.</li>
    <li><strong>It is checked at the table.</strong> A condition on a column the index lacks can be tested only after the row is fetched, so every rejected row costs a table visit. This is where <code>status</code> was.</li>
   </ul>
   <p>Adding <code>status</code> as the last key column moves its check into the index, as <a href="#status-last">the end of the next section</a> measures. Putting <code>status</code> before <code>placed_at</code> would narrow the scan as well, but it splits each customer’s history by status, so it suits only queries that always name a status.</p>
   <p>PostgreSQL lists the first two under <code>Index Cond</code> and the third under <code>Filter</code>. MySQL calls the second <em>index condition pushdown</em> and reports it as <code>Using index condition</code>. SQL Server lists the first under <code>Seek Predicates</code> and the others under <code>Predicate</code>.</p>
   <p>For an ordinary column index, compare the indexed column with a compatible value. Expression indexes can support a matching expression, and some casts preserve index use. Expressions such as <code>lower(email) = ...</code> or <code>customer_id + 0 = 42</code> usually give no search bound on an ordinary index of the underlying column. The engine may scan entries or table rows and evaluate the expression for each candidate. The measured cases here used full table scans. The <a href="/review/relational/evidence/rl86-experiment.sql">runnable experiment</a> includes these bare-column cases.</p>

   <h3 id="order">Indexes and ORDER BY</h3>
   <p>The history query needed no sort step, because its index entries came out in the order it asked for. So an index can answer an <code>ORDER BY</code> as well as a <code>WHERE</code>.</p>
   <p>The rule is the composite one: the columns the query fixes with <code>=</code> come first, and the columns it sorts by follow in the index’s order. An index can be read backwards as well as forwards, so reading customer 42’s entries from the end serves <code>ORDER BY placed_at DESC</code> from an index declared ascending.</p>
   <p>Four things decide whether the match works:</p>
   <ul>
    <li><strong>Direction in a composite key.</strong> A whole index can be read forwards or backwards, but a mixed request needs a matching index. With an index on <code>(customer_id, placed_at)</code>, <code>ORDER BY customer_id, placed_at DESC</code> was not served, and PostgreSQL added an Incremental Sort. An index declared <code>(customer_id, placed_at DESC)</code> serves it.</li>
    <li><strong>Where NULLs sort.</strong> PostgreSQL puts NULLs last in ascending order and first in descending order, and an index stores them the same way. On a nullable column such as a <code>shipped_at</code> date, <code>ORDER BY shipped_at DESC NULLS LAST</code> needs a matching index order, such as <code>(shipped_at DESC NULLS LAST)</code>, or the reverse scan of <code>(shipped_at ASC NULLS FIRST)</code>. Otherwise PostgreSQL must sort.</li>
    <li><strong>Collation.</strong> Text sorts by a collation, a set of rules for ordering strings, and an index serves only an <code>ORDER BY</code> in its own collation. In a database using <code>en_US.UTF-8</code>, <code>ORDER BY email LIMIT 10</code> used the index and <code>ORDER BY email COLLATE "C" LIMIT 10</code> sorted. The two orders really differ: <code>"C"</code> puts every capital letter first, so <code>'Zoe'</code> comes before <code>'adam'</code>, while <code>en_US</code> puts <code>'adam'</code> first.</li>
    <li><strong><code>LIMIT</code>.</strong> An index scan that needs table columns can fetch a row at a time across much of the heap. A sequential scan and sort can then be cheaper; a covering path or a different physical layout can change the choice. Without a <code>LIMIT</code>, <code>ORDER BY customer_id, placed_at</code> was planned as a sequential scan and a sort. The index pays when the query stops early, as the history query does after ten rows.</li>
   </ul>
   <p>The other engines follow the same rules with their own defaults. SQLite reports a mixed-direction order it can’t serve as <code>USE TEMP B-TREE FOR LAST TERM OF ORDER BY</code>. MySQL can declare <code>DESC</code> key parts for a mixed order, and it puts NULLs first in ascending order, the opposite of PostgreSQL.</p>
   <p>Keep the <code>ORDER BY</code> in the SQL, because the index only makes it cheap. The index supplies a possible route; the query still defines its required result order.</p>

   <h3 id="combining">Combining indexes</h3>
   <p>A query with conditions on two columns doesn’t need one composite index for them. PostgreSQL can search two indexes, turn each result into a bitmap of row locations and combine the bitmaps: <code>BitmapAnd</code> when both conditions must hold, <code>BitmapOr</code> when either may.</p>
   <p>On the 60,000-order table, with separate indexes on <code>customer_id</code> and <code>status</code>, customer 42’s pending orders came from a <code>BitmapAnd</code>. It read 2 pages of the customer index and 12 of the status index, collecting all 12,000 pending entries only to narrow 60 rows down to 12. A composite index on both columns would have gone straight to the 12.</p>
   <p>In the other direction, <code>customer_id = 42 OR order_id = 7</code> became a <code>BitmapOr</code> over two indexes, which no single composite index could serve.</p>
   <p>The planner adds a second index only when reading it looks cheaper than the table visits it saves. For <code>order_id = 7 AND status = 'pending'</code>, the primary key led to one row in 3 pages, so the plan checked <code>status</code> on that row and left the status index alone.</p>
   <p>Choose by how the conditions combine. Conditions joined by <code>AND</code> that appear together in most queries belong in one composite index. Conditions joined by <code>OR</code>, or columns filtered in many different combinations, are better served by separate indexes the planner can combine.</p>
   <p>MySQL calls combining <em>index merge</em>, and its plan says <code>Using intersect</code>, <code>Using union</code> or <code>Using sort_union</code> in <code>Extra</code>. SQLite normally uses one index for each table in a query, so on SQLite conditions joined by <code>AND</code> want the composite index. Its exception is a condition joined by <code>OR</code>, where it can search each branch with its own index (<code>MULTI-INDEX OR</code> in the plan).</p>
  </section>

  <section id="covering">
   <h2>Covering indexes and index-only scans</h2>
   <p>An <strong>index-only scan</strong> answers a query from the index without visiting the table. For ordinary column access, the index must hold the values the query needs. An index holding them is a <strong>covering index</strong> for that query. Partial predicates and expression indexes can sometimes prove a condition or supply its value without storing every underlying column.</p>
   <p>The history query returns <code>total</code>, which the composite index lacks, so each of its ten rows needs a table visit. PostgreSQL’s <code>INCLUDE</code> clause adds columns to every entry as stored values that are not part of the sort, as in <code>(customer_id, placed_at DESC, order_id DESC) INCLUDE (total)</code>.</p>
   <p>Holding the columns is not always enough. When PostgreSQL updates or deletes a row, it keeps the old version while a transaction that began earlier might still need it. So an index entry may lead to a row version the current transaction can’t see, and the entry alone can’t say which.</p>
   <p>PostgreSQL therefore checks the table unless a bit in its <strong>visibility map</strong> says every row on that page is visible to every transaction. <code>VACUUM</code>, its cleanup of old row versions, sets the bit, and any change to the page clears it.</p>
   <p>Figure 8 runs a small version of the history query against one leaf page of that index. Include <code>total</code>, then change the state of the table, and watch the heap fetches beside each page’s bit.</p>

<div data-relational-component="indexes/CoveringFigure" data-number="8" data-update="true" data-scale="true"></div>

   <p>With <code>total</code> included but no bits set, the scan still visited both rows’ pages. After <code>VACUUM</code> it answered from the index alone. Then one update to order 19, which belongs to another customer, cleared page 3’s bit, and the scan went back to the table for order 21 on that page. Each <code>Heap Fetches</code> is one such visit.</p>
   <p>On the 60,000-order table, adding <code>total</code> took the history query from 13 pages to 4 once <code>VACUUM</code> had run. It also grew the index from 2.3 to 2.9 MiB, and changing <code>total</code> now changes the index too. A covering index pays for a frequent query on a table that changes slowly, where most pages stay all-visible between vacuums.</p>
   <p>The other engines cover a query in the same way but differ in how you add a column and in when they still visit the table. In SQL Server, a noncovering index path can show a <code>Key Lookup</code> into a clustered table, or a <code>RID Lookup</code> into a heap:</p>
   <div class="table-scroll" role="region" tabindex="0" aria-labelledby="covering-caption"><table><caption id="covering-caption">Covering indexes in four engines</caption><thead><tr><th>Question</th><th>PostgreSQL</th><th>MySQL (InnoDB)</th><th>SQLite</th><th>SQL Server</th></tr></thead><tbody>

   </tbody></table></div>
   <p id="status-last">Covering also changes what a condition costs. With the covering index, the paid-only query from <a href="#fates">What an index does with each condition</a> fetched 12 rows to return 10 and read 15 pages. Adding <code>status</code> as the last key column made it an index-only scan of 5 pages:</p>
   <p><strong>Status as the last key column</strong></p>
<pre><code class="language-sql">CREATE INDEX index_orders_cover_status
ON index_orders (customer_id, placed_at DESC, order_id DESC, status)
INCLUDE (total);</code></pre>
   <p>Most of that drop came from skipping the table, not from the check itself. The scan still read the same entries as before, pending ones included; <code>status</code> decided only which of them to return.</p>

  <section id="kinds">
   <h2>Partial, expression and unique indexes</h2>
   <h3 id="partial">Partial indexes</h3>
   <p>A <strong>partial index</strong> holds entries only for rows that match its own <code>WHERE</code> clause. A fifth of the 60,000 orders are pending:</p>
   <p><strong>Index only the pending orders</strong></p>
<pre><code class="language-sql">CREATE INDEX index_orders_pending
ON index_orders (placed_at)
WHERE status = &#x27;pending&#x27;;</code></pre>
   <p>This index is 35 pages, against 166 for a full index on <code>placed_at</code>, and inserts of paid orders skip it. A query for the ten newest pending orders read it backwards and touched 4 pages. The planner uses a partial index only when the query’s own conditions imply the index’s <code>WHERE</code> clause.</p>
   <p>Two patterns come up often. When unprocessed work is a small slice of a large table, indexing only the waiting rows avoids an entry for every finished row. Its size still follows the active backlog and index upkeep.</p>
   <p>Soft deletion is the other. A unique partial index such as <code>CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL</code> refuses a second live user with the same address, but a deleted user’s address can be used again. <a href="/review/relational/rl79/#uniqueness-needs-the-business-condition">Constraints and tenant boundaries</a> applies uniqueness to the intended population; <a href="/review/relational/rl80/">History, correction and deletion</a> follows what deletion means for retained facts.</p>

   <h3 id="expression">Expression indexes</h3>
   <p>An <strong>expression index</strong> indexes the result of an expression instead of a column. A report of one day’s orders can’t use an index on <code>placed_at</code> through <code>placed_at::date</code>, and that cast can’t be indexed either. Its result depends on the session’s time zone, so one stored moment could give two different dates, and the index could not hold a single value for it. A fixed time zone makes it indexable:</p>
   <p><strong>Index each order’s date in UTC</strong></p>
<pre><code class="language-sql">CREATE INDEX index_orders_day
ON index_orders (((placed_at AT TIME ZONE &#x27;UTC&#x27;)::date));</code></pre>
   <p>A query that repeats the expression exactly, <code>(placed_at AT TIME ZONE 'UTC')::date = date '2026-02-01'</code>, used the index and touched 47 pages to count 1,440 orders. The same question written as <code>placed_at::date = date '2026-02-01'</code> read all 1,725 pages. The planner matches the expression as written, in SQLite as in PostgreSQL, so even <code>x+y</code> and <code>y+x</code> count as different expressions.</p>

   <h3 id="unique">Unique indexes, foreign keys and joins</h3>
   <p>A <strong>unique index</strong> also refuses a second entry with the same key. That is why a unique constraint is built on an index: checking for an existing copy of a key is a search in the index. PostgreSQL creates one for every primary key and <code>UNIQUE</code> constraint, so <code>index_orders_pkey</code> is one. An index on <code>(customer_id, placed_at)</code> declared <code>UNIQUE</code> would refuse two orders for one customer in the same instant.</p>
   <p>NULL is the exception, and the engines disagree about it. PostgreSQL, MySQL and SQLite treat NULLs as distinct from each other, so any number of rows can have a NULL key; PostgreSQL 15 and later accept <code>NULLS NOT DISTINCT</code> to allow only one. SQL Server allows only one NULL in a unique index, so an optional column such as a second email address needs a filtered unique index, <code>WHERE email IS NOT NULL</code>, to allow the rest.</p>
   <p>A foreign key’s referencing column wants an index of its own. If <code>customer_id</code> referenced a customers table, deleting a customer would have to find that customer’s orders, and without an index that is a scan of the whole orders table. InnoDB creates that index for you; PostgreSQL, SQL Server and SQLite don’t. The referencing index makes that lookup affordable; the referenced unique key establishes which parent may be named.</p>
   <p>The same index serves joins. Joining orders to customers, a nested-loop join takes each customer and looks up that customer’s orders through the index on <code>orders.customer_id</code>. Hash and merge joins process sets rather than repeat one lookup per outer row; filtering or ordered index access can still reduce their inputs, and an enclosing limit can sometimes stop them early. <a href="/review/relational/rl87/#read-the-plan-as-rows-flowing-towards-the-result">Query execution and bad plans</a> explains the join methods.</p>

   <p>The engines differ in which of these variants they offer, and in two defaults that change a design:</p>

  <section id="writes">
   <h2>Write cost and upkeep</h2>
   <p>Each index is another copy of some of the table’s data. Inserts add index entries, while the cost of an update depends on which indexed values change and how the engine stores row versions. Figure 9 follows one insert and one update through a PostgreSQL table with up to four indexes: the primary key, <code>customer_id</code>, <code>(customer_id, placed_at DESC)</code> and <code>total</code>. Change the number of indexes and count the pages the insert writes, then switch the statement to UPDATE.</p>

<div data-relational-component="indexes/WriteFigure" data-number="9"></div>

   <p>With four indexes, the insert wrote 8 pages, four of them because a full index page had to divide in two. With only the primary key, it wrote 2.</p>
   <p>PostgreSQL also records every change in its <strong>write-ahead log</strong>, which it replays after a crash; InnoDB’s redo log does the same job. On the 60,000-order table, inserting 10,000 orders wrote 3.3 MB of write-ahead log with only the primary key, and 6.7 MB with all four indexes.</p>
   <p>The update wrote 1 page until an index held <code>total</code>, then 5. While no index contained the changed column, PostgreSQL wrote the new row version beside the old one on the same page, with a pointer from old to new. The index entries still lead to the old version, and through it to the new one, so no index had to change.</p>
   <p>PostgreSQL calls this a <strong>heap-only tuple (HOT) update</strong>. It works only when the new version fits on the same page, which a table fill factor below 100 makes more likely, as <a href="/review/relational/rl110/#hot-preserves-the-existing-index-route">PostgreSQL processes, pages and row versions</a> demonstrates. A non-HOT update adds a new entry to each of these B-tree indexes, including those on unchanged columns. Summarising indexes such as BRIN have different maintenance rules and do not by themselves prevent HOT.</p>
   <p>InnoDB updates the row in place in the clustered index and leaves a secondary index alone unless one of its columns changed. Then it marks the old record deleted and inserts a new one.</p>

   <h3 id="splits">Page splits</h3>
   <p>When the leaf page where an entry belongs is full, the page <strong>splits</strong>: half its entries move to a new page, and the branch page above gains a pointer to it. A split can travel upwards when the branch page is full too, and a split of the root adds a level to the tree. Where new keys land decides how often this happens.</p>
   <p>Figure 10 inserts the same 75 keys into two indexes, once in order, as an auto-increment key arrives, and once shuffled, as random UUIDs arrive. Watch the bottom row.</p>

<div data-relational-component="indexes/SplitsFigure" data-number="10"></div>

   <p>Keys in order always land on the last page. When it fills, the next key starts a new page and the full one is left alone, so every page ends nearly full.</p>
   <p>Random keys land all over the index. Each full page they hit splits into two half-full pages, which fill again only as later keys happen to land on them. The same keys end up on more pages, and every scan of the index reads more of them.</p>
   <p>PostgreSQL leaves pages 90% full when keys arrive in order. On the 60,000-order table, its primary key took 166 pages with the keys inserted in order and about 225 with the same keys at random.</p>
   <p>That 90% is the index’s <strong>fill factor</strong>. You can lower it with <code>WITH (fillfactor = 70)</code> on <code>CREATE INDEX</code>, to leave more room on each page for keys that land in the middle. SQL Server’s <code>FILLFACTOR</code> and InnoDB’s <code>innodb_fill_factor</code> apply only when an index is built or rebuilt. Microsoft advises keeping the default except for an index that splits heavily under random keys, and a lower fill factor makes every scan read more pages.</p>

   <h3 id="key-choice">Choosing a clustering key</h3>
   <p>A clustering key does three jobs at once. InnoDB uses the declared primary key for these jobs; SQL Server can use a different clustered-index key. It orders the table, it is the row locator stored in every other index, and it decides where new rows land. A choice that suits one job can hurt another, so check all three.</p>
   <ul>
    <li><strong>Width.</strong> Every secondary index entry carries the key, so a 4-byte or 8-byte integer adds that much to each of them. A UUID has 16 bytes of value data in a native or binary representation; its usual text form has 36 characters before encoding and storage overhead. Composite keys carry several values. Wider row locators can therefore enlarge every secondary index, although overlapping key columns and engine encoding affect the exact bytes.</li>
    <li><strong>Insert pattern.</strong> An increasing integer puts new rows at the right edge of the tree. Time-ordered identifiers such as UUIDv7 usually concentrate writes near that edge, although independent generators and clock differences can reorder arrivals. PostgreSQL 18 provides <code>uuidv7()</code>. A random UUID puts each row on an arbitrary page, so inserts split table pages across the whole table, as Figure 10 showed for an index.</li>
    <li><strong>Stability.</strong> A key that never changes keeps secondary indexes still. Changing it moves the row and rewrites its entry in every secondary index, so a value people edit, such as an email address, makes a poor key.</li>
   </ul>
   <p>Some systems need identifiers that can’t be guessed, or that several clients generate. One option is a short integer clustering key, with a public identifier in a unique secondary index. Compare the extra index with the width and write pattern it saves. In a heap table such as PostgreSQL’s, the primary key is one index among several, so the primary key’s width and randomness directly affect that index; other indexes still pay for any primary-key columns they explicitly include or reference.</p>

   <h3 id="deleted-rows">Deleted rows and index bloat</h3>
   <p>An index grows when rows arrive and does not reliably shrink when they leave. Figure 11 deletes two-thirds of the rows behind the primary key index in two ways: scattered through the table, or as one block of the oldest orders. Watch the pages in the file.</p>

<div data-relational-component="indexes/DeletedFigure" data-number="11"></div>

   <p>Deleting scattered rows thinned every page and emptied none. After <code>VACUUM</code> removed the dead entries, all six pages were still in use, each a third full. A page holding a third of its entries is still a whole page to read, cache and back up.</p>
   <p>Deleting the oldest rows emptied whole pages instead. PostgreSQL takes an empty page out of the tree and reuses it later, but the file kept its size. Only <code>REINDEX</code>, which builds the index again from the surviving rows, made it smaller. An index carrying that much empty space is called <strong>bloated</strong>.</p>
   <p>On the 60,000-order table, deleting two rows in three left the primary key at 166 pages after <code>VACUUM</code>, and <code>REINDEX</code> brought it to 57. PostgreSQL removes a B-tree page only when every entry on it is gone, and it never merges two partly full pages.</p>
   <p>Later inserts refill gaps only where their keys land. New orders, with the highest IDs, fill the last pages, while the gaps in the older ones stay.</p>
   <p>InnoDB tries to merge a page with a neighbour when a delete leaves it less than half full (<code>MERGE_THRESHOLD</code>, default 50). That holds sparseness down but does not remove it.</p>
   <p>A bloated index costs more pages for every range scan and more memory for the same hot entries. The PostgreSQL live-change investigation shows how to <a href="/review/relational/rl119/#measure-an-index-before-rebuilding-it">measure the bloat</a> and <a href="/review/relational/rl119/#rebuild-within-a-resource-and-recovery-budget">decide whether a concurrent rebuild earns its cost</a>.</p>

   <h3 id="upkeep">Building, finding and dropping indexes</h3>
   <p>Loading a lot of data into a new or empty table goes faster without its indexes, which would otherwise be updated row by row. PostgreSQL’s documentation advises loading first and creating the indexes afterwards: the build sorts every entry at once and fills each page in turn, and InnoDB builds a new index the same way. Run <code>ANALYZE</code> after the load, so the planner sees the new rows.</p>
   <p>On a live table a build can hold up writes until it finishes. <a href="/review/relational/rl119/#a-failed-concurrent-index-can-remain">PostgreSQL schema changes under load</a> executes a concurrent build and repairs an invalid leftover. Other engines have different online-operation limits.</p>
   <p>An index that no query reads still costs every write, so the list of indexes needs pruning as well as growing. To find indexes worth removing, look for ones no query has read since the usage counters were last reset, ones made redundant by a wider index (an index on <code>(a)</code> beside one on <code>(a, b)</code>), and invalid leftovers from failed builds. <a href="/review/relational/rl119/#remove-an-index-only-after-accounting-for-its-duties">PostgreSQL index removal</a> checks the observation interval, constraints, replicas and replacement before the drop.</p>

  <section id="check">
   <h2>Checking an index with EXPLAIN</h2>
   <p>Databases can show the plan they chose for a query: <code>EXPLAIN</code> in PostgreSQL and MySQL, <code>EXPLAIN QUERY PLAN</code> in SQLite, the estimated or actual execution plan in SQL Server. The details below are PostgreSQL’s. The engine-specific names identify the route; <a href="/review/relational/rl113/">Reading and repairing PostgreSQL plans</a> develops the native PostgreSQL evidence.</p>
   <p>In PostgreSQL, <code>EXPLAIN (ANALYZE, BUFFERS)</code> also runs the query and reports what each step did and how many pages it touched. Here <code>ANALYZE</code> means run and measure; the separate <code>ANALYZE</code> command collects the planner’s statistics. Since PostgreSQL 18, <code>ANALYZE</code> reports pages without <code>BUFFERS</code>, but older versions need it.</p>
   <p><strong>Run the history query and report its plan</strong></p>
<pre><code class="language-sql">EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, placed_at, total
FROM index_orders
WHERE customer_id = 42
  AND placed_at &gt;= timestamptz &#x27;2026-02-01 00:00:00+00&#x27;
ORDER BY placed_at DESC, order_id DESC
LIMIT 10;</code></pre>
   <p>With the covering index in place and the table vacuumed, the important part of the plan looks like this. Costs, timings and a few details are left out, and long lines are wrapped.</p>
   <pre class="plan"><code>Limit (actual rows=10.00 loops=1)
  Buffers: local hit=4
  -&gt;  Index Only Scan using index_orders_cover on index_orders
        (actual rows=10.00 loops=1)
        Index Cond: ((customer_id = 42) AND
          (placed_at &gt;= &#x27;2026-02-01 00:00:00+00&#x27;))
        Heap Fetches: 0
        Buffers: local hit=4</code></pre>
   <p>Read it from the most indented line outwards. The index-only scan produces rows in order, and <code>Limit</code> stops asking for more after ten. Four parts of a plan tell you what an index did:</p>
   <ul>
    <li><strong>The node type.</strong> <code>Seq Scan</code>, <code>Index Scan</code>, <code>Index Only Scan</code> or <code>Bitmap Heap Scan</code> names the route.</li>
    <li><strong><code>Index Cond</code> against <code>Filter</code>.</strong> Conditions under <code>Index Cond</code> were checked against index entries: the leading ones narrowed the scan, and the rest were tested entry by entry, as <a href="#fates">What an index does with each condition</a> described. In a plain <code>Index Scan</code>, a <code>Filter</code> is checked after fetching the row, so rejected rows cost table visits. An <code>Index Only Scan</code> can also filter values supplied by its index; read the node type before equating a filter with heap work.</li>
    <li><strong><code>Heap Fetches</code>.</strong> In an index-only scan, the rows that still needed a table visit.</li>
    <li><strong><code>Buffers</code>.</strong> <code>shared hit</code> counts accesses satisfied by PostgreSQL’s shared cache; <code>read</code> counts pages brought into it, possibly from the operating system’s cache. Repeated visits count again, so these totals are neither distinct pages nor physical disk operations. The 60,000-order table is a temporary table, which lasts only as long as the session that made it, so its pages appear under <code>local</code> instead.</li>
   </ul>
   <p>For this small selective lookup, the composite path costs roughly the tree descent plus one table visit per returned row. A covering path can avoid those table visits when visibility permits. Other workloads may legitimately read many rows per page or revisit pages. A condition can appear under <code>Index Cond</code> while the scan reads the whole index, so trust the page count over the plan’s wording.</p>
   <p>Of the four engines, PostgreSQL and SQL Server report pages: SQL Server through <code>SET STATISTICS IO</code>, as logical reads. MySQL and SQLite let you check the route but not this arithmetic.</p>
  </section>

  <section id="design">
   <h2>Designing an index for a query</h2>
   <p>Choosing an index starts from a query, and it can be done in a fixed order. The worked case is the history query, customer 42’s ten newest orders since 1 February, which reached 13 pages once the index was shaped for it.</p>
   <ol>
    <li><strong>Sort the query’s columns into roles.</strong> Equality conditions, the range or sort, and the columns the query only returns.</li>
    <li><strong>Build the key from the roles in that order.</strong> Equality columns first, then the range or sort column, then a tie-breaker if the order needs one.</li>
    <li><strong>Ask whether the equality columns narrow the table.</strong> Together they should cut it to a small fraction. If they don’t, the index will lead to much of the table anyway, as the <a href="#selectivity">selectivity</a> section showed.</li>
    <li><strong>Add returned columns only if the query earns it.</strong> Covering columns pay for a frequent query on a table that changes slowly.</li>
    <li><strong>Create it on production-shaped data and read the plan.</strong> The conditions meant to narrow the scan should appear under <code>Index Cond</code>, the sort step should be gone, and the pages read should drop, as in the plan of the previous section.</li>
    <li><strong>Count what it costs.</strong> Check which existing indexes it makes redundant, as <a href="#upkeep">Building, finding and dropping indexes</a> describes, and what it adds to every write.</li>
   </ol>
   <div class="table-scroll" role="region" tabindex="0" aria-labelledby="design-caption"><table><caption id="design-caption">Where each part of the history query goes in the index key</caption><thead><tr><th>The query says</th><th>Role</th><th>In the index</th></tr></thead><tbody>
    <tr><td><code>customer_id = 42</code></td><td>Equality</td><td>First key column</td></tr>
    <tr><td><code>placed_at &gt;= ...</code> and <code>ORDER BY placed_at DESC</code></td><td>Range and sort on one column</td><td>Second key column, <code>DESC</code> to match</td></tr>
    <tr><td><code>ORDER BY ... order_id DESC</code></td><td>Tie-breaker</td><td>Third key column</td></tr>
    <tr><td><code>LIMIT 10</code></td><td>Early stop</td><td>Nothing, but it is why the sort order pays</td></tr>
    <tr><td><code>SELECT ... total</code></td><td>Returned only</td><td><code>INCLUDE (total)</code>, if the query is frequent enough</td></tr>
    <tr><td><code>status = 'paid'</code> (the paid-only variant)</td><td>Equality, optional</td><td>After the sort columns, to check it inside the index; before them only if every query supplies it</td></tr>
   </tbody></table></div>
   <p>A condition on a column with one fixed value changes step 2. A dashboard of the ten newest pending orders has <code>status = 'pending'</code> as its only equality, and a fifth of the table is pending. Rather than lead with <code>status</code>, index <code>placed_at</code> alone with <code>WHERE status = 'pending'</code>. That is the partial index from earlier, which holds only the rows the query wants and was read in 4 pages.</p>
   <p>For the history query, the composite index removes the avoidable filtering and sort, leaving 13 page accesses. Use that as the measured endpoint for this case. For another workload, stop when the remaining work is acceptable and a further index would cost more than it saves; some filtering or sorting may be the cheaper choice.</p>
   <p>A further index that saves one more page on a query that runs rarely is not worth its write cost. Before adding one, ask whether an index you already have can be widened instead. The history query’s composite index can replace the plain <code>customer_id</code> index, because an index on <code>(a, b)</code> can also serve the leading <code>a</code> lookup. Check uniqueness, width, collation and workload before treating the narrower index as redundant. Then every write pays for one index instead of two.</p>
   <h3 id="workload">Designing for several queries</h3>
   <p>A real table serves several queries, so design the set of indexes together rather than one per query. Suppose the orders table answers four: the history query; a customer’s order list, newest first with no date bound; the foreign-key check when a customer is deleted; and the pending dashboard. The composite index <code>(customer_id, placed_at DESC, order_id DESC)</code> serves the first three, because each fixes <code>customer_id</code> and needs at most the columns that follow it, in that order. The partial index on pending orders serves the fourth. Two indexes answer four queries, where one index per query would have made four, and Figure 9 showed what each extra index adds to every insert.</p>
   <p>Queries that join tables, page through results or combine many optional conditions follow the same steps with a few more rules. <a href="/review/relational/rl81/">Joins and the meaning of a result row</a> establishes the join’s intended answer; <a href="/review/relational/rl83/">Pagination and consistent exports</a> supplies the continuation contract. For a plan that ignores an expected index, follow <a href="/review/relational/rl87/">Query execution and bad plans</a> into the relevant native branch.</p>
  </section>

  <section id="types">
   <h2>Other index types</h2>
   <p>A B-tree serves any value with one sort order. Some questions have no such order, and each engine offers other index types for them. In PostgreSQL, <code>USING</code> chooses one: <code>CREATE INDEX ON products USING gin (tags)</code>.</p>
   <ul>
    <li><strong>Words inside text, or a substring.</strong> A full-text index lists every row containing each word: GIN in PostgreSQL, <code>FULLTEXT</code> in InnoDB, the FTS5 module in SQLite. PostgreSQL’s <code>pg_trgm</code> extension indexes substrings for <code>LIKE '%mug%'</code>. See the optional published <a href="/learn/databases/relational/postgresql/full-text-search/">full-text search investigation</a>.</li>
    <li><strong>Values that hold many keys.</strong> Arrays and JSON documents, searched by containment such as <code>tags @&gt; ARRAY['gift']</code>, want GIN in PostgreSQL. See <a href="/review/relational/rl112/#gin-extracts-keys-from-a-value">GIN indexes</a> and <a href="/review/relational/rl114/">PostgreSQL JSON and structured alternatives</a>.</li>
    <li><strong>Overlap and distance.</strong> Booking ranges, geometry and network addresses want GiST or SP-GiST in PostgreSQL, spatial R-trees in InnoDB and the R*Tree module in SQLite.</li>
    <li><strong>Nearest neighbours among embeddings.</strong> PostgreSQL’s pgvector extension adds HNSW and IVFFlat indexes. See the optional published <a href="/learn/databases/relational/postgresql/vector-search/">vector-search investigation</a>.</li>
    <li><strong>Very large tables in time order.</strong> A BRIN index records only the smallest and largest value in each range of table pages, so it stays tiny on an append-only log. See <a href="/review/relational/rl112/#brin-excludes-physical-page-ranges">BRIN indexes</a>.</li>
    <li><strong>Reports over most of a table.</strong> A column store can reduce the bytes read when a report scans a few columns across most rows. A covering index can also help some such queries; see <a href="/learn/databases/column-stores/">Column stores</a>.</li>
   </ul>
   <p>The access method must fit the operator. A B-tree orders whole keys; an inverted index records each contained key separately. With tags, one session contributes several postings:
</p>
<figure class="relational-figure"><div class="state-grid"><div><strong>Session values</strong><p>s7: wood, beginner</p><p>s8: wood, advanced</p><p>s9: metal, beginner</p></div><div><strong>Inverted entries</strong><p>wood → s7, s8</p><p>beginner → s7, s9</p></div><div><strong>Contains both</strong><p>intersect the two lists</p><p>→ s7</p></div></div><figcaption>Figure 12. Several contained values produce several index entries. Intersecting their postings finds the session with both tags; ordering whole arrays is a different access problem.</figcaption></figure>
<p>That arrangement makes containment cheap but gives each insert more keys to maintain. An update that changes many tags can create much more index work than changing one scalar B-tree key. Some methods return candidates that need rechecking against the stored row. In PostgreSQL a GIN plan commonly uses a bitmap scan; its operator class decides which containment or search questions the entries answer. <a href="/review/relational/rl112/">PostgreSQL index methods and operators</a> owns that product-specific choice.</p>
<p>A coarse-range index makes the opposite trade. Rather than keep an entry per value, PostgreSQL BRIN stores a summary for a range of table pages. Suppose pages 0–15 contain only October dates and pages 16–31 only November dates. An October query can skip the November range from its minimum and maximum, but must still inspect candidate pages in the October range. If October and November rows are shuffled through both ranges, both summaries span both months and neither range can be skipped. The index stays small while its saving disappears.</p>
<p>The native supplement builds a GIN tag index and a BRIN date index on ordered data. Their queries return 1,666 two-tag matches and 1,440 rows for one day, respectively. The plans retain recheck conditions: the summaries or postings narrow candidates rather than replacing the SQL predicate. The <a href="/review/relational/evidence/rl86-alternatives.sql">runnable supplement</a> labels the diagnostic setting that forces the candidate access route for inspection. Partial predicates and expression keys are additional design choices only where the selected access method and operators support them.</p>

A backup is useful when it can restore a service to an acceptable state. A successful copy job is only one dependency. Recovery may also need a continuous log chain, credentials, encryption keys, schema code, enough temporary storage and people who can run the procedure while the primary system is unavailable.

A restore also chooses a history. Stopping before an accidental deletion removes that deletion and every later transaction, including useful work. The database can become internally consistent while disagreeing with customers, payment providers and messages already sent.

We will restore tenant t4's order o81, deliberately lose a later valid order o82 at the same time, and reconcile o82 once using its retained request r82. The native drill runs on disposable PostgreSQL 18.6 clusters. External acceptance is an explicit fixture supplied to reconciliation; no payment service was called.

## Decide what recovery must achieve

Start with two quantities. The **recovery point objective**, RPO, limits acceptable missing history. The **recovery time objective**, RTO, limits time until an acceptable service returns. Neither is proved by the interval between backup jobs.

If a nightly backup is all you retain, a failure can lose most of a day's accepted work. Frequent log archiving can narrow that gap, but only if the archive is complete and available. A ten-minute file restore can still miss an hour-long reconciliation and validation step in the service's RTO.

A useful recovery contract names which failures it covers. A replica may handle a failed host, yet copy an accidental DELETE immediately. A backup in the same account and permission boundary may be deletable by the same compromised operator. Encryption can protect a stolen copy while making it unusable without a separately recoverable key.

## Logical copies and physical copies recover differently

A **logical backup** records database objects and data in a form that can be recreated through the database interface. It can be useful for selective recovery and migration. Restoring it rebuilds tables and indexes, and cluster-wide roles or external dependencies may need separate handling.

A **physical backup** copies an engine's stored representation. It can restore a large database efficiently and, with the required logs, support point-in-time recovery. Its compatibility and recovery rules belong to that engine and version. An ordinary file copy of an active data directory is not automatically a valid physical backup.

In PostgreSQL, a base backup taken through the backup protocol includes the information needed to make its changing files consistent through WAL replay. A logical `pg_dump` is not a base for that replay. In MySQL, an InnoDB physical backup and binary-log recovery have their own coordination rules. SQL Server's full/differential/log chain depends on the recovery model and intact chain. SQLite provides an online backup API; copying a database while ignoring a live WAL can omit committed state.

Choose the restore path before choosing the copy schedule. A portable logical export, a local fast recovery copy and an isolated retained backup can serve different recovery jobs.

## A base and a continuous log chain

A base backup supplies pages from an earlier point. Logs describe how to advance them. The archive must cover every required position from the base's start through the recovery target. One missing segment can break the path even if hundreds of later segments are present.

The archive's retention policy must keep logs needed by the oldest retained usable base. Deleting an old base may free its dependency chain only after checking every other backup and recovery obligation. Incremental copies add dependency edges too; a missing parent can invalidate a later incremental.

Store manifests and check copies for damage. PostgreSQL's `pg_verifybackup` can verify a backup against its manifest; that is valuable but does not replace starting the restored system and exercising its application. A good manifest cannot supply a lost encryption key or a later archive segment.

## Choose a target before the mistake

Our fixture starts with o81, request r81, agreed total 4,000 cents. We take a native physical base backup and create a named restore point. Then a bad transaction deletes o81. A later good transaction inserts o82, request r82, total 6,000 cents.

The target should be supported by transaction evidence, not an approximate wall-clock guess while the service keeps changing. A named restore point is convenient for this controlled rehearsal. During a real incident, determine the offending transaction and target boundary, and preserve the damaged history for comparison before altering it.

Recovery replays the log in order. It cannot skip one bad business transaction and automatically keep all later transactions while promising the same consistent state. Later work may depend on the bad change. Selective reconstruction is a separate, application-aware operation.

## Restore into an isolated destination

The rehearsal copies the verified base into a new data directory. It configures PostgreSQL's archive restore command, target name and pause action, then starts that destination on another private socket port. The original remains available for comparison.

```text
restore_command = 'cp <isolated-archive>/%f %p'
recovery_target_name = 'before_bad_delete'
recovery_target_action = 'pause'
```

These are the meaningful settings from a script that substitutes its own unique temporary directory. They are not instructions to overwrite a production data directory. The [complete runnable rehearsal](/review/relational/evidence/rl90-104-native.mjs) creates and removes its disposable clusters.

The restored server reported recovery paused. Its order table contained o81 and no o82. We inspected it while it was still read-only, then promoted the checked destination to a new writable history.

The script also starts a second copy of the base with an empty archive. That copy cannot reach the requested restore point. Its startup and recovery log are retained in [the evidence](/review/relational/evidence/rl96-native-observed.json). This failure is intentional: a valid base is not evidence that the selected target is reachable.

For a real rehearsal, use the backup account's recovery credentials and independently retrieved keys, with production-like network and storage constraints. A privileged administrator quietly supplying a key from a healthy primary can hide the dependency the drill should test.

## Reconcile later valid work

Before letting ordinary callers resume, list what the earlier target removed. Useful evidence can include an independently retained request journal, payment-provider operation IDs, signed customer confirmations, downstream events and the preserved damaged database. These sources have different authority: a browser's unverified price proposal is not proof of an accepted payment.

For o82, our reconciliation input retains tenant t4, request r82, order o82 and agreed total 6,000. On the restored writable copy, the first import returns o82. Repeating it returns no new row because `(tenant, request)` is unique.

```sql
INSERT INTO recover_order (tenant, id, request, total_cents)
VALUES ('t4', 'o82', 'r82', 6000)
ON CONFLICT (tenant, request) DO NOTHING
RETURNING *;
-- First run: o82. Repeated run: no row.
```

An existing identity must also match the full recovered intent. Do not silently treat `ON CONFLICT DO NOTHING` as proof that a different stored amount is equivalent. Read and compare the retained facts, then either return the existing result or quarantine a conflict for resolution. The example's repeated rows are identical by construction.

A workshop booking needs another check beyond importing its order. Did capacity remain reserved in the chosen history? Is there room to restore this promise? If several valid later requests exceed the surviving capacity, the recovery process needs an explicit priority, rescheduling or refund decision. Manufacturing extra seats would preserve row counts while breaking the service's rule.

External effects need their own recovery too. Do not charge r82 again merely because its local payment row disappeared. Recover the provider's earlier operation, record its result locally and use stable identity for any genuinely missing effect. Outbox rows removed by the target may need reconstruction; outbox effects already delivered must remain safe to replay.

Our final native query showed both o81/r81/4000 and o82/r82/6000, and a second reconciliation made no duplicate. This completes the later-work branch for the fixture. A live service must validate its own inventory, money, tenant and notification invariants before reopening.

## Accept the service, not just the server

A restore acceptance test should establish that the intended target was reached, required objects and keys exist, critical queries return expected facts and runtime roles can operate. Check constraints and indexes, sequence state where relevant, external references and the recovered identity ledger. Keep writes controlled until authority is settled; two writable histories create a [failover and fencing problem](/review/relational/rl98/).

Measure elapsed time from loss detection through these checks and reconciliation. Record the missing accepted work as the observed RPO, and time until the defined usable service as the observed RTO. A drill that stops at “database ready to accept connections” has only measured database startup.

Recovery changes normal traffic too. Cold caches, replay catch-up and reconciling workers compete with returning requests. Reopen gradually with an admission budget, observe the result and retain the old evidence until the new history is accepted.

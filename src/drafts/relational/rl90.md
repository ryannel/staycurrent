A transaction groups database work into one decision. Its changes become committed together, or they are discarded together. This lets an application record a booking and reserve its seat without leaving one behind when the other fails.

Other requests can still run while that transaction is open. They may read earlier values, wait for a conflicting writer, or make decisions that cause an attempt to be rejected. **Isolation** determines which of those overlapping histories the database allows.

The useful question is therefore more precise than “is this transactional?” A workshop session, s7, has capacity 2. Tenant t4 already has booking b17 for customer 42. Two more requests arrive. Each must either create one booking with its seat reservation, or leave both unchanged. Across all requests, confirmed bookings must never exceed capacity.

## What commit makes atomic

We will use these small PostgreSQL tables. The tenant is part of each identity: another tenant's s7 is a different session.

```sql
CREATE TABLE seat (
  tenant text, session text,
  capacity integer NOT NULL,
  reserved integer NOT NULL,
  PRIMARY KEY (tenant, session),
  CHECK (reserved BETWEEN 0 AND capacity)
);
CREATE TABLE booking (
  tenant text, id text, session text,
  PRIMARY KEY (tenant, id)
);
INSERT INTO seat VALUES ('t4', 's7', 2, 1);
INSERT INTO booking VALUES ('t4', 'b17', 's7');
```

The counter records how many seats have been reserved. In this small example, every booking consumes one seat. Keeping the counter and the booking list aligned is the application's transaction protocol; the CHECK constrains the counter alone.

A booking handler opens a transaction, reserves capacity, checks the result, inserts a booking and commits. If the reservation finds no capacity, it rolls back. If the insert fails, it rolls back the reservation too. A new caller should see either the earlier committed state or the completed booking, rather than an intermediate state used by the handler.

```sql
BEGIN;
UPDATE seat
SET reserved = reserved + 1
WHERE tenant = 't4' AND session = 's7'
  AND reserved < capacity
RETURNING reserved;
-- Continue only if this returned one row.
INSERT INTO booking VALUES ('t4', 'b18', 's7');
COMMIT;
```

These are separate statements sent by a handler that branches on the UPDATE result. Running the whole listing blindly would insert b18 even when no seat was reserved. At PostgreSQL's default Read Committed level, the first reservation returns 2. A contender waits if necessary, tests the updated counter and returns no row once it is full.

The transaction does not include a confirmation email sent through another service. Sending it before commit can announce a booking that rolls back; sending it afterwards can fail after the booking is durable. Record the intention alongside the booking, then deliver it through an [outbox](/review/relational/rl94/).

A rollback also does not undo everything a program has done. Files, network calls and values already shown to a person remain outside it. Some database objects have special rules too: PostgreSQL sequence increments are not rolled back. Gaps in generated IDs do not imply missing committed bookings.

## A read followed by a write can lose a decision

Suppose the handler instead reads `reserved`, calculates the next value in application memory, then writes that absolute number. Both callers can read 1 and calculate 2.

<div data-relational-component="relational-operation-tools/Isolation" data-number="1"></div>

B's update has lost A's increment. Transactions made each booking internally atomic, but did not make the earlier application calculation current. Our PostgreSQL 18.6 run ended with `reserved = 2`, `capacity = 2` and three booking rows. The CHECK passed because it never counted bookings.

Putting the calculation into the guarded UPDATE makes the conflicting decisions meet on the same record. The database increments the value it is authorised to change, rather than a value the application read earlier. The successful reservation and its booking must still commit together, and cancellation must use the inverse protocol.

This protection solves a rule that fits one counter. It does not prove that an arbitrary subquery inside an UPDATE is protected. A predicate depending on other rows creates a different history.

## Snapshots describe a moment

A **snapshot** tells a reader which committed row versions belong in its view. It is visibility information, rather than a copied database. Retaining older versions lets a report read an earlier state while writers continue.

At PostgreSQL Read Committed, an ordinary SELECT takes a new snapshot at the start of each statement. An ordinary SELECT has no `FOR UPDATE` or `FOR SHARE` clause. If A counts one booking, B inserts b18 and commits, then A counts again, A sees two. We observed 1 followed by 2 inside one transaction.

That change in the answer is a **phantom**: a newly committed row now satisfies the same predicate. When a row already read changes its value between reads, the corresponding phenomenon is a nonrepeatable read. An engine exposing another transaction's unfinished changes would additionally allow dirty reads; PostgreSQL does not expose them at any of its isolation levels.

A transaction snapshot lets a report keep one view across several queries. Under PostgreSQL Repeatable Read, a snapshot is established by the first query or data-changing statement. A second ordinary count keeps the earlier answer even after b18 commits. A new transaction sees b18. The stable report has not stopped the booking.

The transaction sees its own changes too. Inserting b18 and then counting inside that transaction includes b18, even though other sessions cannot yet see it. “One snapshot” does not mean that the transaction cannot observe its own work.

Locking reads and writes need separate attention. At Read Committed, a PostgreSQL guarded UPDATE can wait for a concurrent writer and then recheck its predicate against that writer's committed row. At Repeatable Read, trying to change a target row updated since the snapshot can instead reject the transaction. An ordinary-read snapshot is not a promise about every command.

## A stable view can still oversell

Remove the counter from the booking decision. Each request counts bookings for s7, compares that count with capacity 2, then inserts its own distinct booking. Both can read one booking through stable snapshots. A writes b18; B writes b19. Neither tries to overwrite the other's row.

This is **write skew**. Each transaction made a locally valid decision from related facts, then their different writes jointly broke the rule. Inserting into a predicate is one form of it. Updating two different “instructor available” flags after checking the other flag produces the same shape.

Our native run used independent Repeatable Read sessions. Both counted 1, both inserted, and both commits succeeded. A unique booking ID did not help: b18 and b19 were intentionally different identities.

One repair is the guarded counter protocol above. Another is to give all session writers a shared existing row to lock, then count bookings in a subsequent Read Committed statement while holding that lock. That read occurs after the previous holder has finished. Every booking and cancellation path must honour the protocol. [Locks and deadlocks](/review/relational/rl91/) follows its waiting cost and the absent-row trap.

## Serializable protects the complete decision

**Serializable** requires the committed effect to be compatible with some order in which the transactions ran one at a time. It need not literally run them one at a time.

For the count-and-insert decision, neither serial order permits three bookings. If A finishes first, B counts two and declines. If B finishes first, A declines. An implementation must prevent both overlapping attempts from committing that three-booking outcome when the relevant decisions participate in the guarantee.

We repeated the same native schedule with both transactions Serializable. Both counts returned 1 and both inserts initially succeeded. A committed; B's COMMIT failed with SQLSTATE `40001`. The final rows were b17 and b18. The earlier INSERT result was provisional until commit.

PostgreSQL obtains this protection by tracking read/write dependencies and rejecting unsafe executions. Its predicate locks record dependencies; they do not make writers wait like ordinary exclusive row locks. Other engines can protect a serializable predicate through blocking key-range locks. Both approaches charge for coordination: waiting, tracking, aborted work or some combination.

After a confirmed serialization rejection, discard that attempt and repeat the whole decision in a new transaction. B now counts two and inserts nothing. Retrying only its old INSERT would remove the check that made the serial execution safe. Bound retries by a deadline and attempt budget, with jittered backoff after releasing the failed transaction.

Serializable does not invent an omitted business rule. A transaction that never checks capacity can serially oversell. Nor does it place an external payment inside the database transaction. A missing commit reply is a different branch, covered in [retries and operation identity](/review/relational/rl93/).

## The same level name can change the prediction

The following differences matter before moving this design between engines. They are documented contrasts; the native schedules above ran on PostgreSQL 18.6.

<table><caption>Isolation choices for ordinary reads and competing booking decisions</caption><thead><tr><th>Engine</th><th>What to verify</th></tr></thead><tbody>
<tr><td>PostgreSQL 18</td><td>Read Committed uses statement snapshots; Repeatable Read uses a transaction snapshot and can still allow write skew. Serializable adds dependency checks and whole-attempt retries.</td></tr>
<tr><td>MySQL 8.4 InnoDB</td><td>Repeatable Read is the default. Ordinary consistent reads and locking reads use different rules. Range locking can protect gaps, depending on isolation and access path; do not translate a PostgreSQL empty locking SELECT mechanically.</td></tr>
<tr><td>SQLite</td><td>There is one writer at a time. WAL mode permits a reader's earlier snapshot alongside a writer. Upgrading a stale reader to a writer can fail with SQLITE_BUSY_SNAPSHOT; restart the transaction. There is no PostgreSQL-style FOR UPDATE protocol.</td></tr>
<tr><td>SQL Server</td><td>Locking Read Committed and READ_COMMITTED_SNAPSHOT are different operating contracts. SNAPSHOT provides a transaction view; SERIALIZABLE uses key-range protection. Database options, including Azure defaults, matter alongside the requested level.</td></tr>
</tbody></table>

Choose from the invariant outwards. A unique constraint protects one identity. An atomic conditional update protects a quantity on its target record. A lock protocol makes several dependent decisions take turns. Serializable protects correctly written participating decisions against nonserial histories. Test the awkward concurrent history for the engine and settings you will actually operate.

## Run the histories

The [native evidence script](/review/relational/evidence/rl90-104-native.mjs) creates disposable PostgreSQL clusters and independent connections, records commands and results, then removes its clusters. It uses the local `pg` driver path and PostgreSQL binary path recorded at its start; adjust those paths for your machine. [RL90's observations](/review/relational/evidence/rl90-native-observed.json) retain the actual version and outcomes.

For manual practice, use two connections to the fixture above. Reset bookings to b17 and reserved to 1 between trials, after both connections finish or roll back. For the write-skew trial, begin Repeatable Read on A and B, count bookings on both, insert b18 on A and b19 on B, then commit A and B. Repeat under Serializable, handling a rejection wherever it arrives. For the atomic trial, pause A after its successful UPDATE; send B's UPDATE before committing A. Observe B waiting, then returning no row.

The schedule controls interleaving; an uncontrolled load test may miss the bad history. A passing run does not prove every application path uses the same invariant.

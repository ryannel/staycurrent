A PostgreSQL schema change is a transaction with lock and compatibility requirements. A command can avoid rewriting rows and still wait for a table lock. An index build can allow writes and still fail with an unusable object left behind.

A live change therefore needs two connected plans. One controls its effect on current traffic. The other keeps old and new applications correct while their expected schema and data overlap. “The ALTER succeeded” does not establish that either plan is complete.

We will add a workshop order field under a held read, recover a failed concurrent unique index, then follow its longer operating lifecycle through measuring, rebuilding and removing indexes. Finally, we will backfill a second representation with a database-maintained equality rule. The [native core lab](/review/relational/evidence/rl110-native.py) and [index lifecycle supplement](/review/relational/evidence/rl119-lifecycle.py) run these cases on PostgreSQL 18.6.

## A short operation can wait a long time

Client A begins a transaction and reads the workshop order:

```sql
BEGIN;
SELECT * FROM workshop.orders;
-- Leave the transaction open.
```

That read takes an Access Share table lock retained through the transaction. Client B attempts a constant-default column addition:

```sql
SET lock_timeout = '150ms';
ALTER TABLE workshop.orders ADD COLUMN currency text DEFAULT 'SEK';
```

The lab’s ALTER fails with `canceling statement due to lock timeout`. The reader does not hold a row write lock, and adding this constant default does not require rewriting all existing rows in this version. The table-level lock requirement is enough to make it wait.

An Access Exclusive request can also affect sessions arriving behind it. A long-held old read, a waiting ALTER and newer queries can form a queue in which ordinary new requests wait too. Inspect the waiter and blockers; do not assume that the DDL consumes little CPU so it is harmless.

```sql
SELECT pid, application_name, state, wait_event_type, wait_event,
       pg_blocking_pids(pid), left(query,120)
FROM pg_stat_activity
WHERE datname = current_database();
```

A short `lock_timeout` bounds the attempt to acquire locks. `statement_timeout` bounds total statement duration. Choose them for the operation and traffic budget, then handle the failure as a retryable migration attempt after identifying the blocker. Repeatedly retrying an expensive operation at high frequency can itself cause load.

When A commits, repeating the ALTER succeeds. The existing `o81` reads with currency `SEK`. That default is appropriate only if historical orders were actually denominated in SEK. A fast technical operation cannot justify inventing a historical currency.

## Inspect rewrite and validation requirements

PostgreSQL can add a non-volatile default without rewriting every existing tuple, recording a missing value to supply for old rows. Other defaults, type conversions and alterations can require scans or rewrites. Their behaviour depends on the exact command, expression and installed version.

A rewrite needs disk, WAL and time, and it changes the locking consequences. Before applying one to production, rehearse the actual statement on a representative copy and inspect its lock and resource requirements. A generic label such as “online DDL” does not describe those costs.

Constraints offer a useful separation. A new check can be enforced for future writes before all existing rows are scanned:

```sql
ALTER TABLE workshop.orders
ADD CONSTRAINT currency_required CHECK (currency IS NOT NULL) NOT VALID;
ALTER TABLE workshop.orders VALIDATE CONSTRAINT currency_required;
```

`NOT VALID` skips the initial existing-row validation; it does not permit new writes to violate the check. Validation then proves the older rows satisfy it under the command’s documented concurrency rules. Its lock is weaker than the most disruptive table alterations, but it can still conflict with maintenance and other DDL.

Check constraints also accept SQL unknown, so `CHECK (code_text = code::text)` alone does not require non-null text. State requiredness explicitly when it belongs in the invariant. Avoid calling a constraint “validated” merely because an application batch found no missing rows once.

## A failed concurrent index can remain

Plain `CREATE INDEX` blocks writes while building the index. `CREATE INDEX CONCURRENTLY` uses multiple phases so reads and writes can continue, while paying for extra scanning, waiting and maintenance. It cannot run inside a transaction block, which matters when a migration framework automatically wraps every migration in `BEGIN`.

The lab creates a staging table for imported workshop codes with a deliberate duplicate:

```sql
CREATE TABLE change_lab (id integer PRIMARY KEY, code integer);
INSERT INTO change_lab VALUES (1,7),(2,7);
CREATE UNIQUE INDEX CONCURRENTLY change_code ON change_lab (code);
```

The build fails because code 7 occurs twice. Inspect its catalogue state:

```sql
SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index WHERE indexrelid = 'change_code'::regclass;
-- change_code | false | false
```

The index exists but is not usable as the intended valid access path. A new attempt under the same name would fail at the name, not repair it. The precise maintenance state depends on which phase failed: this early duplicate failure left both flags false. Some later invalid remnants remain ready for write maintenance and can still impose costs or uniqueness behaviour.

The executed repair is explicit:

```sql
DROP INDEX CONCURRENTLY change_code;
UPDATE change_lab SET code = 8 WHERE id = 2;
CREATE UNIQUE INDEX CONCURRENTLY change_code ON change_lab (code);
```

The final flags are both true. In a real repair, correcting a duplicate requires a business decision about the two records. Our staging fixture deliberately defines row 2’s intended code as 8.

Monitor a running build through `pg_stat_progress_create_index`, locks and activity. A concurrent build can wait for older transactions and snapshots. It needs room for its new structure and generates work for WAL and replicas. One table cannot host arbitrarily many concurrent builds without coordination. Failed `REINDEX CONCURRENTLY` has its own temporary-copy states; inspect which copy is valid before dropping anything.

## Measure an index before rebuilding it

An index that built successfully can become expensive years later. Deletes remove records from the current history, but their keys may leave every leaf page sparsely occupied. A large file can also contain emptied pages awaiting reuse. Those cases call for different decisions.

The [index lifecycle supplement](/review/relational/evidence/rl119-lifecycle.py) creates a separate disposable server. Its `lifecycle_orders` table has tenant-aware primary and request keys, a customer foreign key, timestamps, agreed prices, status and notes. Numeric ID 81 represents order `o81`: tenant `t4` accepted request `r81` at 20.00. Another tenant has its own 81 and r81 at 90.00. Those facts must survive every maintenance step.

The generated t4 workload contains 250,000 orders spread over 1,009 customers. This history index serves a customer's newest orders:

```sql
CREATE INDEX lifecycle_history
ON lifecycle_orders (tenant, customer, placed_at DESC, id DESC)
INCLUDE (price);
```

The experiment deletes t4 rows whose IDs are not divisible by ten, retaining o81 as well. Together with the other tenant, 25,002 rows survive. Their customer/date keys are scattered through the index's leaf pages. Vacuum removes dead entries, but cannot combine all those partly occupied leaves into fewer pages.

### Compare with the same keys freshly built

`pg_relation_size` gives an index's file size. Dividing by live rows gives a useful baseline only for comparable definitions and data. A wider key, different fillfactor, included payload or deduplication behaviour can legitimately change bytes per row.

The supplement copies the survivors into a separate table and builds the identical index. These are native PostgreSQL 18.6 observations:

The sparse index carries about 497 bytes per live row; its fresh counterpart carries about 50. The first has no emptied or deleted pages: the space is distributed inside 1,507 leaves still in the tree. Scanning, caching and physically copying those pages costs more than the compact representation needs.

Use `pgstatindex`, from the supplied `pgstattuple` extension, for this closer inspection:

```sql
SELECT index_size, tree_level, internal_pages, leaf_pages,
       empty_pages, deleted_pages, avg_leaf_density, leaf_fragmentation
FROM pgstatindex('lifecycle_history');
```

This scans the index and needs suitable privileges, normally `pg_stat_scan_tables` or an explicit grant. It consumes I/O and can displace useful cached pages. Its page-by-page result is not an instantaneous snapshot while writers run. Start with sizes and workload evidence, then inspect selected candidates within an operating budget.

Leaf fragmentation describes physical versus logical leaf order; density describes how much useful data the leaves hold. They are not interchangeable percentages. Nor is a low density an automatic rebuild threshold: leave room deliberately when the measured insertion pattern earns it, and compare against that intended fillfactor.

### Emptied pages can be useful capacity

A second native table keeps 250,000 increasing IDs. Deleting the oldest 225,000 empties whole key ranges. After vacuum, its primary-key file still occupies 5,627,904 bytes, but the surviving tree has 69 leaf pages at 89.13% density and 615 deleted pages.

Deleted pages cannot be recycled while an older scan might still reference them. The supplement allocates and finishes another transaction ID, then vacuums again so those pages become available for reuse. It inserts 225,000 later IDs. The refilled index occupies 5,636,096 bytes: only one 8 KiB page more than the original. It reused the emptied space rather than allocating another full index's worth.

The following small model from Indexes makes the two shapes visible. It deletes two-thirds of 36 orders, either scattered or as the oldest keys. Watch the difference after vacuum, before the final rebuild. Its scale and measurements are separate from the larger native fixture above.

The retention index had a compact active tree plus capacity its next insert cycle could reuse. ## Rebuild within a resource and recovery budget

A rebuild earns its cost when the measured excess matters and the expected workload will not promptly reuse it. Examples include a hot index no longer fitting its cache budget, costly broad scans or storage pressure. Rebuilding every week regardless of its state spends work even when the result is almost unchanged.

In this fixture the fresh baseline is about a tenth of the sparse history index. The supplement actually runs:

```sql
REINDEX INDEX CONCURRENTLY lifecycle_history;
```

PostgreSQL builds a new copy from the table, catches changes made while building, switches dependencies and retires the old copy. Reads and writes can continue, but the operation needs extra work and waits for relevant transactions. It does not make competing I/O or an old snapshot disappear.

Before starting, budget space for the existing index, the new copy, sort spill and accumulated WAL. Index size is only one part of that peak. `maintenance_work_mem` controls maintenance working memory; a sort that exceeds it can use temporary files. In this small lab the rebuild session deliberately uses 1 MB and its log records a temporary sort file. Give a real operation a measured allowance without assuming all server memory belongs to this build.

WAL is another output. The measured interval around this rebuild generated 1,352,336 bytes. That includes the concurrent callers' updates and progress records, so it is an interval budget, not a statement-level attribution to REINDEX alone. Full-page images, other traffic and changed settings can alter the volume.

Physical standbys must receive and replay that WAL; an archive or slot can retain it if its consumer falls behind. Reserve the corresponding disk and recovery headroom, and watch lag while the job runs. A logical subscriber has its own index definitions and schema-change procedure; it does not automatically perform this same rebuild. The supplement runs one server and does not measure replica replay capacity.

### Observe progress and caller outcomes

The native test holds an older Repeatable Read snapshot and concurrently sends 100 ordinary note updates, each followed by a committed progress record. Monitoring sees the rebuild in `waiting for old snapshots` while those callers continue committing. It completes after the older reader ends.

```sql
SELECT a.pid, a.application_name, a.wait_event_type, a.wait_event,
       p.phase, p.index_relid::regclass, pg_blocking_pids(a.pid)
FROM pg_stat_activity a
JOIN pg_stat_progress_create_index p USING (pid);
```

The observed progress establishes that these callers continued during this operation. It is not a promise of unchanged latency, unlimited concurrent DDL or progress under every lock schedule. Only one concurrent index build or rebuild can run on a table at a time, and its Share Update Exclusive locks conflict with other maintenance and schema changes.

The rebuilt history index occupies 1,261,568 bytes, with 152 leaves at 89.47% density. It need not exactly match the untouched fresh baseline: concurrent versions and subsequent writes change its state. Both `indisvalid` and `indisready` are true.

The application checks matter as well as the byte count. The customer's ten newest orders are identical before and after. Summing the agreed prices for customers 40–49 still returns 5,048.50 from 247 rows. The plan still uses `lifecycle_history`.

That range query recorded 19 shared-buffer accesses before rebuilding and eight immediately afterwards. Its heap-fetch count also changed from zero to 100 because callers had modified a page while an old snapshot existed. A following vacuum reduced it to one heap fetch and seven buffer accesses. These are execution observations with changing visibility, not a clean storage-speed benchmark. The physical baseline establishes the space saving; the results establish that the request's facts survived it.

For a structural check, the supplement also runs `amcheck`:

```sql
SELECT bt_index_check('lifecycle_history', heapallindexed => true);
```

It returns without error. This check takes read-level relation locks; the stronger parent-check function has different locking and standby restrictions. Checking heap coverage adds work. A passing check means the selected checks found no inconsistency, not that hardware, every future write or every application rule has been proved correct. If corruption prompted the rebuild, investigate its cause too.

### Recover the failed rebuild's copy

A timeout does not necessarily roll back every phase of a concurrent operation. To expose the later failure state, the supplement repeats the rebuild with an older snapshot held and a 700 ms statement timeout. It fails and leaves:

```text
index                          indisvalid  indisready
lifecycle_history              true        true
lifecycle_history_ccnew         false       true
```

The original remains the valid authority. The new copy is ignored for querying but is ready for write maintenance, unlike the earlier duplicate build's invalid/not-ready object. After the old reader ends, the supplement removes just that failed copy:

```sql
DROP INDEX CONCURRENTLY lifecycle_history_ccnew;
```

Then only the valid original remains. If the required repair has not yet been completed, resolve the wait or resource failure before retrying the rebuild. PostgreSQL can append a number to the suffix when names already exist. If an invalid leftover instead ends in `_ccold`, the new copy has taken over and the old copy could not be retired. Confirm which index is valid and owns constraint dependencies before removing the invalid remnant. Do not drop both names and erase the working access path.

Concurrent reindexing cannot run inside an explicit transaction block; the supplement executes and receives that rejection. Exclusion-constraint indexes and system catalog indexes do not support this concurrent route. A table or database command can skip unsupported indexes, so check what actually completed. Temporary-table reindexing is non-concurrent because other sessions cannot use that table. Use the installed version's restrictions when choosing a procedure.

## Remove an index only after accounting for its duties

A valid index with no observed reads still costs writes. In the supplement a note index occupies 33,210,368 bytes after the deletion workload, yet the defined application never searches notes. Its size and zero scan count make it a candidate, not permission to drop every index with the same zero.

Record an interval covering the relevant workload, along with the counters' reset boundary:

```sql
SELECT clock_timestamp(), stats_reset
FROM pg_stat_database WHERE datname = current_database();
SELECT indexrelid, indexrelname, idx_scan, last_idx_scan,
       pg_relation_size(indexrelid) AS bytes
FROM pg_stat_user_indexes
WHERE relname = 'lifecycle_orders';
```

Compare snapshots over a representative period, including rare reporting, retention, customer-deletion and recovery jobs. Read-serving replicas keep their own observations; check each relevant server. Statistics can be delayed or cached by a monitoring transaction. Explicit resets and events such as crash recovery can invalidate an interval. The database reset timestamp is not a complete audit of per-index counter resets. Record index OIDs as well as names, and account for individual resets, rebuilds and drop/recreate operations; a new object or a counter decrease needs a new observation interval. One scan count is not a row count or a direct measure of time saved.

The lab deliberately resets statistics in its private database, then exercises five defined requests and one EXPLAIN ANALYZE. Its replacement index records six scans; the note index records zero. This proves which paths that small workload exercised. It does not manufacture a representative production observation period in a few seconds.

### Uniqueness and foreign keys survive quiet periods

The primary-key and request-uniqueness indexes also recorded zero scans during that short request interval. They still reject duplicate identities. The test attempts:

```sql
DROP INDEX CONCURRENTLY lifecycle_orders_pkey;
-- Rejected: the primary-key constraint requires it.
```

Dropping the constraint instead would change the data contract. It is not the safe workaround for an unused-index cleanup. A unique index on `(tenant,id)` is not redundant with a non-unique index on `(tenant,id,placed_at)`, nor with a unique index on all three: the latter permits repeated `(tenant,id)` when the timestamp differs.

A foreign key's referencing side is different. PostgreSQL does not require an index there, so a drop can succeed while making parent deletes or key updates scan a large child table. Inspect `pg_constraint` in both directions and identify those duties explicitly. The database's willingness to drop an index does not prove its workload is dispensable.

The catalogue identifies those definitions and dependencies. In the supplement, this query lists the child/parent relationship that the replacement must still serve:

```sql
SELECT conname, conrelid::regclass AS child, confrelid::regclass AS parent,
       pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE contype = 'f'
  AND (conrelid = 'lifecycle_orders'::regclass
       OR confrelid = 'lifecycle_orders'::regclass);
```

Also join `pg_index.indexrelid` to `pg_constraint.conindid`, checking the constraint type: primary, unique and exclusion constraints own their indexes; a foreign-key row identifies its referenced index. Check `indisunique` independently, too: a standalone unique index still enforces a rule without a named UNIQUE constraint.

### A matching prefix is a candidate comparison

An existing index on `(tenant,customer)` may be replaceable by one beginning with those keys. Compare the full definitions through `pg_get_indexdef` and `pg_index`: uniqueness, access method, key versus INCLUDE columns, expressions, predicate, operator classes, collations, sort directions and null placement.

`(tenant,customer,placed_at DESC,id DESC)` supplies the customer prefix and newest-first order. An index with `placed_at` first does not provide that same compact customer interval. Mixed ascending/descending requirements cannot all be repaired by reading an entire index backwards. A partial index omitting unpaid orders cannot replace an all-orders lookup. Included columns can let the shorter index cover a request that a supposedly dominant index cannot.

Text indexes with different collations or operator classes can serve different comparisons despite sharing column names. Do not collapse them by comparing `indkey` alone. Conversely, a longer equivalent index can still be larger and more expensive to scan for a narrow query. Redundancy analysis identifies a possible removal; representative plans and write costs finish the decision. [Index methods and operators](/review/relational/rl112/) teaches those operator contracts.

### Build, verify, then drop

To cover status as well as the agreed price, the supplement creates a replacement beside the existing indexes:

```sql
CREATE INDEX CONCURRENTLY lifecycle_replacement
ON lifecycle_orders (tenant,customer,placed_at DESC,id DESC)
INCLUDE (price,status);
```

It verifies validity and the actual request plan before removing anything. The request uses an Index Only Scan on `lifecycle_replacement`, returns ten ordered records and records zero heap fetches after maintenance. The new index is 1,482,752 bytes, wider than the price-only history index; the extra coverage has a real size and update cost.

After checking the defined usage and catalogue duties, the lab drops the unused note index while separate readers and writers run, then removes the shorter customer index:

```sql
DROP INDEX CONCURRENTLY lifecycle_unused_note;
DROP INDEX CONCURRENTLY lifecycle_customer;
```

Each is a separate command outside a transaction block. Concurrent drop waits for conflicting transactions instead of taking the ordinary drop's disruptive table lock; it does not mean immediate completion. The native observations show caller commits while the drop is active. PostgreSQL permits one index per concurrent-drop command, disallows CASCADE and cannot use this route to remove a primary/unique constraint's index. Partitioned-index restrictions also need checking.

The exact history request still returns the same ten records after removal. A customer-existence lookup uses the replacement's leading prefix. Deleting referenced customer t4/42 is still rejected by the foreign key, and duplicate order/request inserts still fail. The original t4 order remains at 20.00; the other tenant's order remains at 90.00.

The price-only history index is retained. The small status-request interval is insufficient evidence that every cheaper price-only query should abandon it. Apply the same decision to it when the full workload justifies doing so.

PostgreSQL 18 has no built-in invisible-index switch for temporarily hiding this index from the planner while retaining an instant reversal. Nor is a global `enable_indexscan` change a trial of one particular index's removal. Preserve its exact CREATE definition, choose an observation and rollback window, and retain enough capacity to recreate it concurrently if a missed request needs it. A replacement left valid beside the old copy is a much cheaper rollback point than a completed drop.

The index set is now smaller without removing the order's identity or customer boundary. The same discipline applies to the data representation itself: new storage must coexist with old callers before an old contract can be removed.

## Expand before changing readers

Now the import service must carry a textual representation of `code`. Old clients still write integers; new clients can send both. The initial authoritative fact remains the integer, so a compatibility trigger derives the text for every writer:

```sql
ALTER TABLE change_lab ADD COLUMN code_text text;
CREATE FUNCTION fill_code() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.code_text := NEW.code::text;
  RETURN NEW;
END
$$;
CREATE TRIGGER compatibility
BEFORE INSERT OR UPDATE ON change_lab
FOR EACH ROW EXECUTE FUNCTION fill_code();
```

Installing the new column and write protocol must precede the backfill and reader change. A newly added nullable column alone creates no rule keeping copies equal.

The lab sends both caller forms:

```sql
-- Old client contract
INSERT INTO change_lab (id,code) VALUES (3,9);
-- New client contract during compatibility
INSERT INTO change_lab (id,code,code_text) VALUES (4,10,'10');
```

The trigger makes both copies agree. It also prevents a newer client’s inconsistent text from becoming a second authority; during this phase, the integer wins. That is a deliberate transitional contract, not a permanent licence to silently discard meaningful new input.

## Backfill in bounded transactions and prove completion

Select a bounded set of mismatches and lock those rows for the batch:

```sql
WITH batch AS (
  SELECT id FROM change_lab
  WHERE code_text IS DISTINCT FROM code::text
  ORDER BY id LIMIT 100
  FOR UPDATE SKIP LOCKED
)
UPDATE change_lab c SET code_text = c.code::text
FROM batch b WHERE c.id = b.id;
```

Commit each batch. `SKIP LOCKED` avoids waiting on currently busy rows, but those rows are skipped, not completed. A final zero-row batch can therefore mean “nothing currently claimable.” The completion proof must revisit the full predicate after concurrent writers are covered by the invariant.

This fixture requires a code. Although its staging column began nullable, the final check deliberately rejects null text, including the null produced by the trigger for a null integer. If missing codes are valid in the old contract, preserve that case in the invariant instead of adding requiredness during the backfill.

The lab checks for all disagreement, then installs and validates that rule:

```sql
SELECT count(*) FROM change_lab
WHERE code_text IS DISTINCT FROM code::text;
-- 0
ALTER TABLE change_lab ADD CONSTRAINT backfill_equal
CHECK (code_text IS NOT NULL AND code_text = code::text) NOT VALID;
ALTER TABLE change_lab VALIDATE CONSTRAINT backfill_equal;
```

A validated constraint plus the compatibility trigger makes equality persist while either client form continues. The harness then runs independent legacy and modern clients together, inserting codes 11 and 12 through their respective forms. Both commit, and the mismatch count remains zero. The batch cursor is only scheduling state; the predicate and maintained constraint define completeness.

On a large table, monitor batch latency, WAL growth, replica lag, dead versions and foreground query latency. Choose a restartable progress record and rate limits. A technically correct backfill can still exceed the operating budget if it updates the whole relation in one transaction.

## Contract only after the old contract ends

Readers can switch to `code_text` after it is populated and maintained. Dropping `code` or changing which field wins requires another coordinated phase. Verify that no old application, scheduled job, worker, report or rollback package still depends on it.

If text becomes authoritative, define the allowed new values before converting writes: text can represent cases an integer cannot. Keeping a trigger that casts everything back to integer may defeat the new feature. Once old writers are excluded, change or remove the compatibility mechanism, migrate the remaining dependent objects and eventually remove the old column.

This is why schema rollback is stage-dependent. Before switching readers, the new representation may be expendable. After accepting new values that the old application cannot represent, reopening that old application can lose information even if the old binary still starts.

The database can enforce the completed state, but it cannot discover which external application versions are still eligible to run. Keep that deployment authority explicit, and keep lock/rewrite evidence alongside the compatibility proof.

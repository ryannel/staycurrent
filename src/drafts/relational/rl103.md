A slow database request can be waiting to obtain a connection, executing an expensive plan, waiting for a lock, flushing a commit or waiting for a remote copy. Those causes can produce the same application timeout while requiring different interventions.

Incident diagnosis finds the boundary where time is accumulating, gathers enough evidence to explain it and changes one thing with a predicted result. The fastest useful observation often prevents a much more disruptive guess.

Our workshop's booking requests suddenly time out. Tenant t4's session s7 is small and normally cheap to update. Some unrelated reads still finish quickly. We will reveal a native wait chain, then follow the consequences of releasing it. PostgreSQL names the observed states; the investigation applies across engines, with product-specific tools gathered later.

## Begin with the request boundary

First establish the affected operation, time window and spread. Are all tenants slow, one hot session, only writes, or one report parameter? Compare accepted arrival rate, completions, errors and queue depth. A service that stopped completing work can show fewer database calls precisely because its application pool is full.

Separate request time into admission/pool wait, borrowed-connection time, statement time and commit time. If most delay is before the database receives a statement, a plan change may be irrelevant. If the database has the statement but reports a lock wait, higher CPU is not the first remedy.

Preserve a small evidence set before intervention: a representative request trace, current running and waiting work, the relevant blocking relationships, resource trends and recent changes. Prefer a bounded snapshot and interval deltas to dumping every query text, parameter or row. Diagnostics can expose customer data and create load of their own.

The workshop symptom points towards contention: one session is slow, while unrelated reads remain quick. We still need evidence. A coincident deployment can cause longer transactions, a changed plan or simply more arrivals; its timing alone does not choose among them.

## Follow the blocker, not the busiest label

In our native PostgreSQL 18.6 drill, connection A begins a transaction and sets s7's counter to 0, then waits for another application command. Connection B's UPDATE assigns 1 to the same counter and asks to return it. These diagnostic assignments expose lock ownership; the booking handler must still use its guarded reservation protocol. A monitoring connection captures:

`active` means B has an active statement, not that it is consuming CPU. A appears idle but owns the transaction preventing completion. Cancelling several visible waiters would leave the root cause alive.

The useful questions now concern A. Which application owns it? How old is the transaction? Has it sent an external payment? Is it legitimate long work, a forgotten transaction or a worker stuck on another dependency? Can its owner safely roll back? An administrative process ID is not yet a business decision.

PostgreSQL's `pg_blocking_pids` supplies a wait relationship without making the operator infer ownership from every low-level lock record. In another engine, use its equivalent wait and transaction metadata. Follow a chain to the root; a blocked blocker can hide the real owner several steps away.

## Cancellation is not transaction completion

We sent `pg_cancel_backend(A)` while A was idle in its transaction. The call returned true. B remained waiting.

<figure class="relational-figure">
<figcaption>Figure 2. A successful cancellation request did not release an idle transaction's locks. The native observation records the pending waiter and its later completion.</figcaption>
<div data-step><p><strong>1. A has no running statement</strong></p><p>Its earlier UPDATE finished. The transaction and row lock remain open.</p></div>
<div data-step><p><strong>2. Operator sends cancel</strong></p><p>The cancellation request is accepted. There is no running statement to interrupt; B is still unresolved.</p></div>
<div data-step><p><strong>3. A rolls back</strong></p><p>The transaction releases its lock. B completes and returns reserved = 1.</p></div>
</figure>

Cancelling a running statement can also leave an explicit transaction needing rollback before reuse. Terminating the session is a stronger action: it disconnects the application and causes its transaction to abort. In an undo-based engine, rollback of a huge transaction can itself be lengthy. Neither command should be interpreted as instant service recovery merely because the administrative request succeeded.

Choose the least disruptive action that addresses the owner. If A's application can roll back, ask that controlled path to finish. If it is abandoned and termination is justified, record the transaction and expected lost work before doing it. A commit possibly already sent creates an [uncertain-outcome recovery](/review/relational/rl93/) case; do not tell callers to create new purchase identities.

Our drill uses explicit rollback and shows B's successful result afterwards. It does not claim that terminating an arbitrary production transaction is safe.

## Stop a released queue becoming the next incident

The root lock can hide a second bottleneck. Hundreds of booking handlers may be queued behind it, while their callers have retried. Releasing the lock lets the surviving requests contend rapidly for capacity, CPU and commit throughput.

Before releasing a large queue, bound new admission and stop duplicate retry amplification. Remove expired work where it can still be cancelled safely. Preserve request identities for unresolved purchases. Then release the blocker and watch completions, active work and errors through the drain.

The [hot-row capacity exercise](/review/relational/rl102/) supplies a measured reason to keep this budget: adding contenders widened latency without improving the serial resource's throughput. A booking count returning “full” is a useful successful result during the drain; retrying that business refusal would only keep the queue busy.

## A changed plan needs different evidence

Now vary the symptom. Suppose all large-tenant order lists are slow, CPU rises and there is no root lock chain. An index recently removed or an estimate badly wrong can make a query examine far more rows than it returns.

Collect the statement shape and relevant parameter sizes, then compare estimated and actual rows, loops, scans, sorts and spill evidence. A nested loop doing a small lookup 100,000 times can dominate even if one loop is cheap. A selective-looking condition may match most of the largest tenant's rows. [Query execution and bad plans](/review/relational/rl87/) develops that reading.

Do not run an unbounded `EXPLAIN ANALYZE` on a costly production statement just to obtain a plan: it executes the statement, including writes. Use an estimated plan, a representative safe copy or a bounded controlled execution appropriate to the operation. A rollback still does the work and may have external trigger effects to consider.

Choose a candidate intervention tied to the prediction: restore a needed index, refresh demonstrably wrong statistics, remove repeated application queries or temporarily reduce a costly report. Compare the same workload and parameters afterwards. A warm-cache rerun by itself cannot establish that the change fixed the cause.

## Storage and replica symptoms can look like query slowness

If commit latency rises while execution remains cheap, inspect log flush latency, required synchronous replicas and storage queues. A stalled synchronous destination can delay commits without the primary's CPU being busy. Relaxing its acknowledgement policy may restore availability while changing the data-loss contract; that is a deliberate recovery decision.

If disk space is disappearing, distinguish current table growth, retained row versions, retained replication/archive logs, temporary files and an ongoing index or table copy. Repeatedly vacuuming a table cannot release log retained by a disconnected consumer. Deleting arbitrary log files can destroy recovery.

Retain enough space and connections to diagnose and recover. If a replica must be rebuilt after dropping a retention obligation, include the rebuild and reduced redundancy in the incident plan. [Capacity](/review/relational/rl102/) and [backup acceptance](/review/relational/rl96/) make those dependencies explicit.

## Verify recovery at the original boundary

After the intervention, test the original request, not only the administrative command. Did r81 complete once? Are capacity and order facts correct? Did the queue drain? Are newly admitted requests staying within latency and error budgets? Observe a full relevant interval, including background catch-up, before declaring stability.

Then repair the cause: transaction lifetime, missing rollback, admission, access path, retained-history ownership or an acknowledgement dependency. Set a signal that would distinguish the same failure earlier. An incident record should retain the prediction, evidence, action, result and any business reconciliation; a list of commands is insufficient.

[The native evidence](/review/relational/evidence/rl103-native-observed.json) and [disposable script](/review/relational/evidence/rl90-104-native.mjs) cover the lock chain, cancellation request and successful waiter completion. PostgreSQL operational commands are developed in [Operating and diagnosing PostgreSQL](/review/relational/rl120/). InnoDB's performance schema, SQL Server's dynamic management views and SQLite's busy/checkpoint behaviour expose different details; use the engine's meaning for each wait rather than translating a label by appearance.

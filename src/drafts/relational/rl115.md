PostgreSQL can acknowledge a committed order before its updated heap page reaches the table file. The order survives because another description of the change has reached durable storage first: the write-ahead log, or WAL. Recovery can use it to bring an older stored page forward.

A logged change is not necessarily a committed transaction. A page can contain an uncommitted version, and WAL can describe work that later rolls back. Recovering physical bytes and deciding which versions a query may see are separate tasks.

This article follows that distinction through a real immediate shutdown and restart of PostgreSQL 18.6. The [disposable lab](/review/relational/evidence/rl110-native.py) keeps its own data directory. It tests server-process crash recovery with local storage intact. It does not cut power or test a storage provider’s flush contract.

## What changes before COMMIT

A backend changes a copy of a heap page in shared buffers. The page becomes **dirty**, meaning its memory contents differ from the table file. It may also change index pages and other persistent structures.

PostgreSQL generates WAL records describing recovery operations. These are not saved application SQL statements. Re-executing arbitrary SQL at recovery could see different rows, function results or concurrent history. WAL instead supplies the storage-level information needed to reconstruct the recorded work.

A dirty page can reach its table file before its transaction commits. Conversely, a committed page can remain dirty in memory after the reply. Both orderings are permitted, provided PostgreSQL maintains its write-ahead rule and interprets transaction outcomes correctly.

The background writer helps make buffer slots reusable. The checkpointer writes pages so future recovery has a more recent starting boundary. A backend can also have to write a dirty victim before reusing its slot. Which process writes the page affects foreground latency, but none may bypass the required WAL ordering.

## Insertion, writing and flushing

An LSN is a position in the WAL byte stream. PostgreSQL exposes different progress boundaries:

```sql
SELECT pg_current_wal_insert_lsn() AS inserted,
       pg_current_wal_lsn() AS written,
       pg_current_wal_flush_lsn() AS flushed;
```

Insertion can be ahead while records remain in WAL buffers. Writing sends bytes to the operating system. Flushing completes the configured operation intended to make them persistent. On a busy server, other transactions can advance these positions immediately after your commit.

Two rules establish the local durability contract. Before a changed data page is persisted, its required WAL must be durable. Before a normally durable commit is acknowledged, its required WAL through the commit record must be durable. Commit need not flush every changed table and index page.

One flush can cover several transactions’ required positions. Each can then receive its reply. This is group commit: sharing a storage operation while retaining the per-transaction requirement. It explains why several concurrent clients can achieve more commits per second than a single client waiting for each flush before sending another.

WAL progress alone does not say whether an order committed. Nor does a local flush position prove that another server received or replayed it. [Physical replication](/review/relational/rl117/) adds those separate positions.

## Run a crash with a committed and unfinished change

The native drill creates a logged table and an unlogged scratch table, then checkpoints the initial state:

```sql
CREATE TABLE durable (id integer PRIMARY KEY, v integer);
INSERT INTO durable VALUES (1,20),(2,20);
CREATE UNLOGGED TABLE scratch (id integer);
INSERT INTO scratch VALUES (1);
CHECKPOINT;
```

Client A begins a transaction, changes row 2 to 99 and leaves it open. Client B changes row 1 to 22 and commits. The lab captures WAL positions, settings and checkpoint/WAL counters, then immediately stops only its own server:

```sh
pg_ctl -D "$OWNED_DATA_DIRECTORY" -m immediate -w stop
pg_ctl -D "$OWNED_DATA_DIRECTORY" -l "$OWNED_LOG" -w start
```

This is intentionally different from a clean shutdown, which writes a shutdown checkpoint. The pending client loses its connection. After restart the results are:

```text
id | v
1  | 22
2  | 20

scratch rows: 0
```

The committed logged change survives. The unfinished change is not visible. The unlogged table is empty, including the row whose insert had committed.

PostgreSQL can redo records for an unfinished transaction and leave its versions invisible. It does not need to restore every tuple byte to the pre-transaction image before opening the database. Cleanup later reclaims abandoned versions.

The lab also hashes the table file after the initial checkpoint and after both updates. The hashes match: those stored bytes still reflect the initial state. A separate flush-position check confirms that B’s committed update flushed WAL beyond A’s unfinished update. The experiment therefore separates three facts: an older table file, recoverable page changes for both transactions, and a committed outcome for only one. The expected visible result follows from all three.

## Checkpoints bound redo work

Stored pages can be at different stages of progress. A page LSN records the WAL progress reflected in that page. During ordinary page redo, PostgreSQL can compare it with the record’s end position and avoid reapplying an operation already present. Applicable full-page images follow their own restoration rules.

A checkpoint establishes a redo starting position and writes the pages needed to make recovery from that position safe. Its completion record comes later in the WAL. Recovery starts at the completed checkpoint’s redo position, not after its completion record. An incomplete checkpoint at the crash does not replace the last completed one.

The log makes this visible. Look for `database system was not properly shut down`, `redo starts at`, `redo done at`, an end-of-recovery checkpoint and finally `ready to accept connections`. Read the whole sequence. A message about an invalid record at the actual end of available WAL can mark its end; a missing required segment or premature end is a different failure.

```sql
SELECT num_timed, num_requested, buffers_written
FROM pg_stat_checkpointer;
SELECT wal_records, wal_fpi, wal_bytes FROM pg_stat_wal;
```

Use changes in counters over a known interval. Their reset times and a restart can break a rate calculation. PostgreSQL 18 separates checkpointer statistics from older versions’ background-writer reporting, so use the view definitions for the installed version.

More frequent checkpoints can reduce redo after a crash but repeatedly write hot pages. They also cause subsequent changes to pages to generate new full-page images. Fewer checkpoints can reduce that repeated work while increasing recovery exposure.

`checkpoint_timeout`, `max_wal_size` and checkpoint spreading influence the trade. `max_wal_size` is a soft checkpoint-related budget, not a hard ceiling on the WAL directory. A slow checkpoint, failed archiving or retained slot can leave more WAL than that setting suggests. Do not delete segment files by hand to enforce it.

A recovery-time target needs a measured redo rate for the intended environment. A warm laptop immediate restart may replay faster than a reboot with cold caches or a replacement server on different storage. Include detection, startup, end-of-recovery work, cache warming and application acceptance in the outage budget.

### Read the checkpoint and restart together

The executed drill’s forced checkpoint recorded these fields. Dates and process IDs are omitted; long lines are wrapped:

```text
checkpoint complete: wrote 114 buffers (2.8%), wrote 3 SLRU buffers;
write=0.015 s, sync=0.386 s, total=0.532 s;
distance=81541 kB; lsn=0/672E538, redo lsn=0/672E4A8
```

The buffer count describes checkpoint writes, not all writes since startup. `write` and `sync` distinguish writing work from synchronising files; the total can include other checkpoint work. The checkpoint record’s position and its redo starting boundary are different fields.

After the immediate shutdown, recovery reported `redo starts at 0/672E4A8`, matching that completed checkpoint’s redo boundary. It ended at `0/67306B0`, then wrote an end-of-recovery checkpoint before accepting connections. This tiny interval establishes the path; its rounded sub-second redo time is too small to supply a useful sustained replay-rate estimate.

### Choose spacing from a recovery budget

For a steady write workload, estimate how much WAL can accumulate after the last completed recovery boundary, then divide by a measured replay rate for the intended recovery environment. The rate and the amount both need realistic conditions; nominal storage bandwidth is not a redo rate.

The following retained model uses a workload writing 28 MiB of WAL a second and compares replay rates of 169 and 85 MiB a second. Those are explicit model inputs, not measurements from this small drill. Change `max_wal_size` and watch the largest replay interval grow. Then halve replay speed without changing the workload.

Leave operating margin and verify restart under load rather than choosing the largest size that just meets the model’s line.

## Full-page images and honest flushes

A power failure can interrupt a page write, leaving a page partly old and partly new. A narrow WAL record cannot necessarily repair such a torn page. With `full_page_writes=on`, PostgreSQL logs a full-page image when needed, ordinarily on the first modification after a checkpoint, so recovery has a complete page image to work from.

That is different from checksums. A checksum can detect some damage; detection does not itself provide a correct replacement. Neither mechanism replaces another surviving copy for a lost volume or arbitrary later corruption.

`fsync=on` asks PostgreSQL to enforce the persistence ordering through its supported flush operations. The guarantee still depends on the operating system, controller and device honouring them. The method is exposed by `wal_sync_method`; supported choices and their effectiveness differ across platforms.

A very fast flush can mean fast protected storage or an acknowledgement before volatile caches are safe. A process restart leaves the operating-system cache intact and cannot distinguish them. Hardware documentation and appropriate failure testing are needed for that boundary. `pg_test_fsync` measures supported methods; timing alone does not prove power-loss safety.

## Relax the acknowledgement deliberately

For a replayable counter, the application can choose asynchronous commit for one transaction:

```sql
BEGIN;
SET LOCAL synchronous_commit = off;
UPDATE replayable_counters SET value = value + 1 WHERE counter_id = 42;
COMMIT;
```

This is a configuration pattern; `replayable_counters` represents application data you have explicitly decided can lose recent work. PostgreSQL can acknowledge before the WAL flush. A crash may lose recently acknowledged transactions while recovery retains a consistent state. The default WAL-writer delay is 200 ms, and the documented maximum exposure under this policy is up to three times the configured delay.

The native immediate restart does not promise to demonstrate that loss on every run. Bytes already written may survive in the operating-system cache, and timing affects what was flushed. The changed guarantee comes from the documented acknowledgement policy.

Turning `fsync` off is a much broader change. It removes persistence-ordering protections and can permit unrecoverable corruption after an operating-system crash or power loss. It is not an equivalent faster setting for ordinary orders. Turning off full-page writes also changes torn-page protection.

Unlogged tables are narrower but still unsuitable for confirmed orders: their contents are reset after a crash and are not reproduced by physical WAL replication. Temporary tables have a session lifetime and another contract again.

Finally, durable WAL cannot deliver a lost reply. If `COMMIT` becomes durable and the connection drops before the caller receives success, request `r81` may already have created order `o81`. The caller needs a stable request identity and reconciliation, not a blind second order. Nor can crash recovery undo a validly committed bad deletion; that requires [restoring to an earlier target](/review/relational/rl116/).

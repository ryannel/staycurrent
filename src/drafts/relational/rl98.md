Failover moves service to another database server when the current primary cannot continue. Promotion gives the new server write authority. **Fencing** makes sure a previous writer can no longer exercise incompatible authority.

The difficult failure is a partition. A controller cannot reach the primary, while an application with an existing connection still can. Promoting a replica does not close that connection or make the old server aware of the decision. Two healthy processes can then accept conflicting purchases.

We will trace that case, then use an intentionally simple native fence: stop the disposable PostgreSQL primary and confirm it is stopped before promoting its standby. This validates a manual process fence, not an automatic production failover controller.

## Silence does not prove the primary is dead

Suppose primary A serves tenant t4's session s7. Replica B follows it. A controller polls A, and applications find A through a routing name.

A network failure cuts controller-to-A traffic. Some applications also lose A, but one application retains a working path and cached connection. The controller's timeout is real evidence that its path failed; it is not proof that A cannot still change s7.

Restarting a router, changing DNS or removing A from a pool directs future traffic. It does not revoke credentials, cached sockets, direct operator access or another network path. A useful fence addresses every route that can still authorise the effect.

Examples include a confirmed power/process fence, revocation of exclusive storage access, or a database protocol in which writes require a still-valid lease or current quorum. Each has assumptions. A controller's “fence requested” response is weaker than confirmation that old writes are rejected.

## Decide which history may survive

Authority and data completeness are separate decisions. A safe single writer can still be missing previously acknowledged transactions if its replication policy permitted that loss.

With asynchronous replication, A may commit r81 after B stops receiving. If A becomes unavailable, B cannot recover a log record it never obtained. Promoting it selects an earlier prefix. A synchronous durable acknowledgement can reduce that window for the required surviving replicas, but only while the configured contract actually holds.

Before promotion, identify the most advanced trustworthy candidate and the acceptable loss boundary. Different candidates can have different received and applied positions; promotion may replay received log first. Never infer “zero loss” just from “replica healthy”. [Replicas, lag and read routing](/review/relational/rl97/) develops those stages.

Preserve uncertain client identities. A caller whose commit reply disappeared needs recovery against the chosen history. If the system lost an acknowledged operation and its deduplication record, replay can look fresh. Independent request/payment evidence may be needed to reconcile it after authority is settled.

## The manual native fence

The drill starts two PostgreSQL 18.6 servers on private sockets and catches the standby up. It then stops the standby and commits a marker `old_primary_only` on A. That marker represents an acknowledged transaction beyond the available replica history.

A separate old client also opens a transaction and inserts `stale_uncommitted`, without committing. We stop A with immediate mode, wait for `pg_ctl` to confirm completion, then ask the cached client to commit. Its connection fails; it cannot authorise the write after the process fence.

Only after the fence is confirmed do we start and promote B. B accepts a marker `new_primary`. It does not contain `old_primary_only`, which it never received, or `stale_uncommitted`, which never committed.

The result is deliberately narrower than an automatic failover claim. In production, the controller must obtain equivalent evidence through the infrastructure it can still reach. If it cannot fence the old authority or otherwise prove exclusion, retaining availability by promoting anyway risks conflicting writers. A manual failover procedure needs an explicit stop condition for that case.

## A former primary cannot simply return as primary

A now has stored history B did not receive. B has begun a new writable history. Restarting A writable would restore the very authority conflict the fence removed.

First preserve evidence needed to reconcile useful transactions from A. Then rebuild or rewind it from the selected primary using the engine's supported procedure. Rewind changes physical history to match the new source; it is not a business merge of both sets of accepted orders.

In the native drill, PostgreSQL `pg_rewind` uses B as the source and writes standby recovery configuration for A. The cluster was initialised with the required page-change tracking support. After restart, A reports that it is in recovery and catches up to `new_primary`.

```text
old node: pg_is_in_recovery() → true
old node: INSERT ...         → 25006, read-only transaction
```

We verify that refusal instead of stopping at a successful rewind command. The rejoined server is a replica, with no current write authority. A later application route accidentally pointing at it receives an error rather than creating another writable history.

A rebuilt former primary may need new replication slots, changed connection settings and a repaired backup timeline chain. Retained slots on a node that will not resume can pin logs. Rejoin acceptance includes role, replication progress and current history, not merely process liveness.

## Clients must recover through the transition

Established sessions usually break during failover. Pools must discard broken connections and discover the current route. Transaction state cannot move with a socket reconnect. A confirmed aborted attempt can restart; an unknown commit uses its stable [operation identity](/review/relational/rl93/).

Routing also affects reads. A session that read its own purchase on A might hit a lagging B after a route change. If B was promoted from a history missing that purchase, waiting for ordinary replay cannot invent it. Freshness tokens need topology/history awareness; reconciliation needs independent evidence when acknowledged data was lost.

Reopening traffic should be a controlled step after the new authority is writable, critical facts are checked and the loss boundary is understood. Returning every request and retry at once can overwhelm a cold cache and a reduced replica set. Reserve capacity for recovery work and admit ordinary requests within that budget.

## Product authority comes from the deployment

PostgreSQL core supplies replication, promotion and rewind, but does not provide a complete automatic primary-failure controller and external fence. The controller and infrastructure are part of the guarantee.

MySQL Group Replication and SQL Server availability groups use their own group/cluster authority mechanisms, membership rules and failover modes. An asynchronous MySQL replica manually promoted behind a routing change does not acquire Group Replication's guarantees. A SQL Server forced failover differs from a synchronised failover and may lose data. Check edition, platform and cluster configuration.

Consensus-based distributed SQL places authority within replicated partition protocols, but those protocols still need quorum and membership safety. They do not permit both sides of an arbitrary partition to accept conflicting serializable writes. [Transactions across partitions](/review/relational/rl106/) separates replica agreement from a whole transaction's decision.

SQLite's embedded deployment has no built-in remote primary promotion service. A product that copies or remotely serves SQLite needs an explicit write-authority contract beyond the local file's locking.

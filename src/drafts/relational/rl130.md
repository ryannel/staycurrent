A CockroachDB schema change can require more than changing a catalogue entry. Adding a stored computed column must populate old rows as well as maintain new ones. Adding an index must build its entries, validate its rules and make the new access path available without leaving ordinary writers to maintain an incomplete structure.

The engine carries that work through schema versions and durable jobs. This keeps the table usable during supported changes, but does not make a change free or an incompatible application safe. Existing callers may still omit columns, use positional inserts or expect a constraint that the job has not successfully installed.

The native examples use **CockroachDB 25.4.17**, with 10,000 workshop events on a disposable secure cluster. We first add a derived value, then attempt a uniqueness rule the records cannot satisfy. Those two outcomes give the operator different next steps.

## Existing rows need the new representation

The fixture contains globally identified events with a tenant, creation key and integer value:

```sql
CREATE TABLE workshop.events (
  id INT PRIMARY KEY, tenant STRING, created INT, value INT
);
INSERT INTO workshop.events
SELECT x, 't' || (x % 10)::STRING, x, x % 71
FROM generate_series(1,10000) AS g(x);
```

Add a stored computed column:

```sql
ALTER TABLE workshop.events
ADD COLUMN doubled INT AS (value * 2) STORED;
SELECT count(*), sum(doubled - value * 2) FROM workshop.events;
```

```text
count | sum
10000 | 0
```

The column is stored, so old rows need the derived value physically represented. A new write must also follow that computation. A stored expression is different from an ordinary nullable column that the application promises to fill later: the engine owns this derived value.

The observed sum checks the fixture's arithmetic in aggregate. In a general migration, zero aggregate difference alone would not prove every row correct, since positive and negative differences can cancel and NULL inputs can vanish from a sum. Acceptance should check missing values and individual violations, as well as row count. Define the expected result before running the job.

## A job and a caller advance on different clocks

At a high level, the engine bridges old and new schema versions, backfills the new representation, then publishes the completed shape. Ordinary traffic must maintain a representation that remains valid through those transitions. This is how a new access path can become complete even while writes continue.

A migration tool must respect this execution model. CockroachDB does not give arbitrary batches of DDL in explicit transactions PostgreSQL's full transactional-schema guarantee. Prefer the selected release's supported single-statement change boundaries and inspect what the tool sends. An application transaction containing business writes should not accidentally become the wrapper for a long schema job.

The resource cost matters as much as the state machine. A backfill scans old data and writes new state, adding disk, replication, CPU and memory demand. A table and its replacement representation can coexist until cleanup, so size for overlap. “Online” means ordinary operation can continue through supported transitions; it does not promise unchanged latency on a cluster already near capacity.

## Read the job that belongs to the change

After the stored-column statement, the native run queried the jobs:

```sql
SELECT job_id, job_type, status, description
FROM [SHOW JOBS]
WHERE job_type LIKE '%SCHEMA%'
ORDER BY created DESC LIMIT 8;
```

Its output included both `NEW SCHEMA CHANGE — succeeded` for adding `doubled` and `SCHEMA CHANGE GC — running` for associated cleanup. Other rows belonged to earlier index builds. A running cleanup row did not mean that the new column was still unavailable.

Match the description and job identity to the requested change. Capture the ID when starting a change or retrieve it by the known object and statement, then keep it in the deployment record. A list of the latest eight jobs is convenient for this isolated fixture but can lose the relevant job on a busy shared cluster.

Read status, error and progress in context. A job that is retrying a transient infrastructure failure calls for different action from one that has failed a data-validation rule. A stalled-looking progress fraction also needs an observation interval and resource evidence; it is not itself proof of a dead worker.

## Pause a real build while old callers work

A second fixture makes the job long enough to observe. The recorded run creates 200,000 rows with a repeated 200-character payload, then starts `CREATE INDEX online_payload ON workshop.schema_live(payload)` on a separate client. The later repeatable worksheet uses a smaller row-count parameter to bound runtime; the observations below belong to the recorded 200,000-row run.

The population statements run first; the index statement then runs on a separate connection so the worksheet can observe and interrupt it:

```sql
CREATE TABLE workshop.schema_live (id INT PRIMARY KEY, payload STRING);
INSERT INTO workshop.schema_live
SELECT x, repeat('x',200) FROM generate_series(1,200000) AS g(x);
CREATE INDEX online_payload ON workshop.schema_live(payload);
```

While the job reports `running`, another caller selects row 1 and changes its payload to `changed`. Both statements succeed. The administrator then sends:

```sql
PAUSE JOB 1220076726156165121;
```

That is the actual observed job ID; a rerun must obtain its own from `SHOW JOBS`. The command returns `PAUSE JOBS 1`, but the next observation says `pause-requested`. An immediate resume is rejected:

```text
job with state pause-requested cannot be resumed
```

The request and the completed transition are different states. The client that originally submitted `CREATE INDEX` also receives an error saying its job was paused before completion. That does not mean the table vanished or that no resumable work remains.

The old caller continues to use the table: it inserts row 200001 with payload `new` and reads `changed` from row 1. The operator waits until `SHOW JOBS` reports `paused`, then sends a separate `RESUME JOB` for that same ID. This later command succeeds. Subsequent observations progress through `running` to `succeeded`.

Finally, a new caller explicitly uses the published index:

```sql
SELECT id FROM workshop.schema_live@online_payload
WHERE payload = 'changed';
SELECT count(*) FROM workshop.schema_live;
```

```text
id:    1
count: 200001
```

The new index finds the value changed during its build, while the table count includes the row inserted during the interruption. Those checks tie the job state to caller behaviour. A successful pause command alone would not have proved either property.

The resulting decision is concrete: wait for the requested state before issuing the next state-dependent control, resume the existing job rather than launching a duplicate index build, then verify the published access path and the writes accepted during the interval. The observation establishes concurrent functional behaviour for these callers; it is not a sustained-load latency result.

## A unique-index failure changes the release decision

The fixture repeats `value = x % 71`, so many events have value zero. This attempted rule is impossible:

```sql
CREATE UNIQUE INDEX duplicate_values ON workshop.events(value);
```

```text
ERROR: failed to ingest index entries during backfill:
       duplicate key value violates unique constraint "duplicate_values"
SQLSTATE: 23505
DETAIL: Key (value)=(0) already exists.
```

The failure is not an instruction to retry unchanged. First decide whether uniqueness on `value` was ever the intended business rule. Here it was deliberately wrong: the value is a repeated measurement, while `id` identifies the event. Deleting all repeated measurements to satisfy the mistaken index would corrupt the application model.

The next native observation ran `SHOW INDEX FROM workshop.events` and inspected job errors. It showed the primary and previously successful secondary indexes, but no public `duplicate_values` index. The corresponding schema-change job was `failed`; a separate schema GC job was still running. The table and its existing access paths remained usable.

That completes the operational choice. Preserve the existing application behaviour, abandon the incorrect rule, and follow cleanup rather than release code that assumes the unique index exists. For a valid rule with dirty historical data, classify and repair the duplicates under a protocol that prevents new ones, then create the rule again and verify its success. A failed build's object name is not proof of a usable access path.

## Keep both application versions compatible

Suppose an old client writes `INSERT INTO events VALUES (...)` with four positional values. Adding a generated column or changing the visible shape can invalidate its assumptions. An explicit insert column list expresses what the old client actually owns, and lets a generated column remain the engine's responsibility.

Read shape matters too. A `SELECT *` consumer that decodes by position may fail after a new column appears, even though the database change completed normally. Prepared statements, generated ORM mappings and migration checks can each cache assumptions. Test real old and new client statements against the transition, not only a final schema dump.

For a change that needs application-maintained data, use an expand/backfill/switch/contract sequence. Keep old readers and writers supported until the new representation is complete and the new version is accepted. [Live schema changes and backfills](/review/relational/rl100/) owns the general completeness proof; the native job supplies one part of it, not the whole application rollout.

## Pause, cancel or repair from the actual state

When a supported schema job is paused, retain its job identity and know which application shape remains available. Resume it after fixing the capacity or competing-work cause. Cancelling a job can require reversal and later garbage collection; cancellation is a request to the job system, not an instant restoration of all free space.

Not every job supports every control at every stage. Inspect the pinned release's `PAUSE JOB`, `RESUME JOB` and `CANCEL JOB` rules, then check the resulting job and object state. Do not kill arbitrary processes or delete files to erase a schema change. Jobs are durable precisely so another process can continue their work after an ordinary node interruption.

If the job succeeds but the application fails, hold the next release and identify the incompatible statement. Dropping the new column immediately can make matters worse for the newly deployed readers. If the job fails because records violate an invariant, preserve the error and offending identity before deciding whether the records or the rule are wrong.

The stored-column, duplicate-index and concurrent pause/resume cases above were executed. They establish these state transitions and caller outcomes, while latency under sustained production traffic remains unmeasured. [Operating and securing a CockroachDB cluster](/review/relational/rl128/) provides the node and resource evidence; [Upgrading a CockroachDB cluster](/review/relational/rl131/) owns the different boundary between binary versions and cluster finalisation.

An index is useful because it keeps information that lets a query avoid unrelated data. PostgreSQL offers different index methods because different questions need different information. Ordered keys serve a date interval. Extracted array elements identify rows containing a tag. Bounds over a group of pages can rule out the whole group without identifying a single matching row inside it.

Choosing a method therefore begins with the operator in the query. “Index this JSON column” leaves out whether the application tests key existence, document containment or a numeric range. Each asks the index to prove something different.

We will use generated workshop activity to compare those proofs, their remaining heap work and their cost when records change. The [native lab](/review/relational/evidence/rl110-native.py), in `core` mode, runs the examples on PostgreSQL 18.6. Its `access_lab` table contains 50,000 rows with ID `n`, timestamp `2026-01-01 + n seconds`, a tenant, tags, an integer range and a wide note. Tenant `t4` owns 45,000 rows; each of 100 other tenants owns 50.

## B-tree preserves an order

A B-tree arranges keys in an order and uses upper pages to find a leaf interval. An index on `(tenant, id)` puts one tenant’s entries together, ordered by ID within that tenant. For a tenant-scoped recent list, that geometry provides a starting point and a stopping point:

```sql
CREATE INDEX access_cover ON access_lab (tenant, id) INCLUDE (created_at);
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM access_lab
WHERE tenant = 't5' ORDER BY id LIMIT 10;
```

The first ten IDs for `t5` are 45100, 45200 and so on through 46000. The query fixes the leading key and reads forward until ten rows have been produced. It does not need a separate sort. `INCLUDE` stores the timestamp for returning it, without making it part of the key order.

For a real order table, include tenant identity in the search and the complete requested order, such as `(tenant_id, customer_id, placed_at DESC, order_id DESC)`. The order ID breaks ties between equal timestamps. An index does not make an omitted `ORDER BY` into a contractual result order.

An equality on a later key can sometimes use PostgreSQL 18’s skip scan, making repeated searches for a small number of distinct leading values. It is a costed choice; it does not make every column ordering equally useful. If the leading key has many values, repeated seeks may be worse than scanning another structure.

### Covering still needs visibility

The index holds every selected field, but an ordinary entry does not contain enough information to establish tuple visibility. PostgreSQL can skip the heap check only when the page’s all-visible bit supplies that assurance.

```sql
VACUUM access_lab;
-- Repeat the SELECT with EXPLAIN (ANALYZE, BUFFERS).
-- Index Only Scan ... Heap Fetches: 0
UPDATE access_lab SET note = 'changed' WHERE id = 45100;
-- Repeat again: Index Only Scan ... Heap Fetches: 1
```

The update did not change any value returned by the query. It cleared the page’s visibility shortcut, so the next index-only scan checked a tuple in the heap. The node’s name identifies the available route; `Heap Fetches` records how much heap work this execution still needed.

A covering column also costs space and maintenance. Changing an included value can prevent HOT updates, even though it is not a search key. A frequently edited column can therefore increase write work while the table’s frequent page changes reduce the read benefit. ## GIN extracts keys from a value

Our fixture gives every row the tag `web`. Rows divisible by 100 also have `audit`; rows divisible by 250 also have `urgent`. A GIN index extracts these elements and keeps references to the rows containing each one.

```sql
CREATE INDEX access_tags ON access_lab USING gin (tags);
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM access_lab WHERE tags @> ARRAY['audit','urgent'];
```

There are 500 audit rows and 200 urgent rows. Both tags occur at multiples of 500, giving 100 answers. The containment operator `@>` requires both elements; array overlap `&&` would accept either and produce 600 distinct rows.

<div data-relational-component="relational-product-tools/Gin" data-number="2"></div>

Our plan used `Bitmap Index Scan on access_tags`, then a `Bitmap Heap Scan` returning 100 rows. A bitmap collects candidate locations before visiting heap pages. Its heap order is useful for locality but does not preserve an application sort order.

`Recheck Cond` states the predicate available for checking candidates. Its presence alone does not count false matches. Inspect `Rows Removed by Index Recheck` and exact/lossy heap blocks. Some operator classes have intrinsically approximate candidates; a bitmap can also become lossy when it retains page-level information instead of exact tuple locations. These are distinct reasons for further checking.

GIN creates work from each extracted key. A changing document may contribute many keys, unlike one integer B-tree entry. With fast update, new entries may accumulate in a pending list before merging into the main index. Reads must account for it too. Measure sustained writes and cleanup behaviour, not just a freshly built index over static records.

## GiST supports the type’s search relationships

A workshop reservation often asks whether time intervals overlap. Treating each interval as one B-tree scalar does not by itself provide the spatial relationship needed to skip unrelated ranges. GiST supplies a framework whose operator class defines useful bounding and consistency operations for the indexed type.

Our fixture uses integer ranges to keep the endpoint arithmetic visible. Row `n` covers `[n,n+2)`: the lower endpoint is included and the upper endpoint excluded.

```sql
CREATE INDEX access_slot ON access_lab USING gist (slot);
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM access_lab WHERE slot && int4range(700,705,'[)');
```

Rows 699–704 match: `[699,701)` intersects the requested interval, while `[698,700)` ends just as it begins. Row 705 begins at the excluded upper endpoint. The observed bitmap plan returned six rows from one exact heap block.

For actual bookings use the appropriate timestamp range and make the time-zone and boundary policy explicit. A GiST index can speed overlap searches. An exclusion constraint can additionally forbid selected conflicting rows. The constraint must express the real invariant: a blanket “no overlap” rule is wrong for session `s7` with capacity two. Searching candidates and enforcing capacity are separate jobs.

GiST can support different relationships for different types, including distance with suitable operator classes. Do not infer the supported operators, exactness or index-only ability from the name alone. Spatial types supplied by an extension also depend on that extension’s installation and provider support.

## BRIN excludes physical page ranges

BRIN retains much less information. With a min/max timestamp operator class, it records bounds for each range of heap pages. If the requested minute lies outside those bounds, none of the range can match. If it lies inside, PostgreSQL must inspect the pages.

```sql
CREATE INDEX access_time ON access_lab USING brin (created_at)
WITH (pages_per_range = 4);
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM access_lab
WHERE created_at >= timestamp '2026-01-01 00:30'
  AND created_at <  timestamp '2026-01-01 00:31';
```

The result is 60: seconds 1800 through 1859. Rows arrived in timestamp order, so nearby pages have narrow bounds. Our native run visited eight lossy heap blocks and rejected 172 candidate rows during recheck.

Now copy exactly the same records in a deterministic permutation and build the same BRIN index:

```sql
CREATE TABLE scattered AS
SELECT * FROM access_lab ORDER BY (id * 7919) % 50000;
CREATE INDEX scattered_time ON scattered USING brin (created_at)
WITH (pages_per_range = 4);
ANALYZE scattered;
```

Run the same minute query against `scattered`. It still returns 60. Our server still chose a BRIN bitmap route, but now visited 1,724 lossy heap blocks and rejected 49,936 rows. The matching plan label hid an enormous difference in the work left after the index.

<div data-relational-component="relational-product-tools/Brin" data-number="3"></div>

Smaller `pages_per_range` keeps more summaries and can narrow bounds. It cannot restore order when almost every small range contains widely separated times. Late arrivals can widen summaries in an otherwise ordered table. BRIN does not cluster data or create partitions.

New ranges also need summarisation. Vacuum, explicit summarisation functions and the optional autosummarize setting provide maintenance paths. An unsummarised range cannot safely be excluded. Monitor both the summary coverage and the fraction of heap pages actually skipped.

## Operator classes complete the definition

An access method needs the rules for the type. An **operator class** specifies the supported comparisons or extraction behaviour. Defaults usually work for ordinary scalar B-trees, but choosing another class can change which query the index serves.

For JSONB, `jsonb_ops` supports key existence as well as containment. `jsonb_path_ops` supports containment and JSON-path matching but not the `?` key-existence operator. For text under a language collation, `text_pattern_ops` can support character-based prefix matching without providing the same ordering as the language’s ordinary range comparisons.

The indexed expression must also be the expression searched. A GIN on `payload` does not automatically serve `payload->>'level' = 'advanced'`. A B-tree on that extracted text, or a whole-document containment predicate supported by the GIN, is a different design. [JSON and structured alternatives](/review/relational/rl114/) measures both.

Partial indexes add a predicate boundary. A paid-only index can serve a query whose conditions imply that boundary; it cannot answer requests for unpaid rows. Parameterised generic plans may be unable to establish the required implication. Expression inputs and predicates also count when assessing update maintenance and HOT eligibility.

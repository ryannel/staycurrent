A CockroachDB query has two maps. Its SQL plan connects scans, joins and sorts. Its key-value requests connect that work to the ranges and replicas holding the data. A query can use an index and still fetch every result a second time from another part of the key space.

Those requests matter even when the answer is small. Ten secondary-index entries can identify ten rows whose returned values require another batch of lookups. If the ranges are remote, the dependency adds network work. If they are local, it still adds decoding, memory and coordination inside the server.

We will follow a ten-row query, then consider the harder case where many writes converge on one advancing key boundary. The native examples use CockroachDB **25.4.17**, running as TLS-enabled processes on one macOS ARM64 host. Node locality labels are useful for observing placement, but these timings do not measure geographical latency.

## Follow the index entries to the missing value

The workshop event fixture has 10,000 rows. Event `id` is globally unique in this isolated dataset; its tenant column scopes the query, rather than supplying tenant-local event identity.

```sql
CREATE TABLE workshop.events (
  id INT PRIMARY KEY, tenant STRING, created INT, value INT
);
INSERT INTO workshop.events
SELECT x, 't' || (x % 10)::STRING, x, x % 71
FROM generate_series(1,10000) AS g(x);
CREATE INDEX events_by_tenant ON workshop.events(tenant,created);
```

Tenant `t4` has 1,000 events, every tenth event in insertion order. The query wants the latest ten values:

```sql
EXPLAIN ANALYZE
SELECT value FROM workshop.events@events_by_tenant
WHERE tenant = 't4'
ORDER BY created DESC LIMIT 10;
```

The `@events_by_tenant` suffix forces this index for the experiment. It lets us compare access paths deliberately; it is not evidence that permanently forcing an index is the right production remedy.

The secondary index contains the tenant, creation key and implicit primary-key identity. It can find the ten newest matching entries by scanning backwards, but `value` is not there. An **index join** fetches the missing column through the primary index.

```text
index join: events@events_pkey
  actual rows: 10
  KV rows decoded: 10
  KV gRPC calls: 1
└─ reverse scan: events@events_by_tenant
     actual rows: 10
     KV rows decoded: 10
     KV gRPC calls: 1
     span: tenant t4; limit 10

Whole query: 20 KV rows decoded; 2 KV gRPC calls
```

This is the recorded plan with timings and incidental fields removed. It does not perform twenty separate network round trips: the engine batches work. The important dependency is that the primary keys must first be found before the missing values can be fetched.

[CockroachDB keys, ranges and replication](/review/relational/rl123/) explains why primary and secondary indexes occupy separate key spans. The generic [Indexes and access paths](/review/relational/rl86/) explains their ordering; here the additional question is where the resulting work runs.

## Store the returned value in the access path

A covering index supplies all columns needed by this query:

```sql
CREATE INDEX events_cover
ON workshop.events(tenant,created DESC) STORING(value);
EXPLAIN ANALYZE
SELECT value FROM workshop.events@events_cover
WHERE tenant = 't4'
ORDER BY created DESC LIMIT 10;
```

```text
scan: events@events_cover
  actual rows: 10
  KV rows decoded: 10
  KV gRPC calls: 1
  span: tenant t4; limit 10

Whole query: 10 KV rows decoded; 1 KV gRPC call
```

The index join is gone. `STORING(value)` keeps the value with each index entry without making it another ordering key. The native run reduced reported maximum memory from 70 KiB to 20 KiB. One execution also became faster, but a single warm loopback run is not a latency benchmark. The stronger evidence is the removed lookup operator and its ten decoded KV rows.

The cost moves to writes and storage. An insert now stores the value twice, in the primary representation and in this secondary index. A value update must maintain that extra copy. Building the index also reads existing data and writes a new access structure; [CockroachDB schema jobs under load](/review/relational/rl130/) follows that job. Keep the index when the workload's saved lookups justify its maintenance, rather than making every index cover every possible response.

## Local SQL does not mean local storage

`distribution: local` in the plan describes SQL execution placement. It does not prove that every KV request stayed on the SQL gateway. Read the operator's `sql nodes`, `kv nodes` and `regions` as well.

In the fresh 25.4.17 run, both operators used SQL node `n1` and KV node `n1`, in the labelled `eu` locality. The retained upgrade-run experiment used SQL node `n1` and KV node `n2`, with labels `eu, us`, while still reporting local SQL distribution. Both also reported zero DistSQL network messages. Neither fact excludes SQL-to-KV RPCs: those are counted separately.

This distinction prevents two wrong diagnoses. Zero SQL exchange traffic does not prove zero remote storage work. Conversely, a plan spanning two labels on one laptop does not establish an intercontinental latency cost. Inspect placement and measure the intended network separately.

For larger queries, distributed operators can scan several spans and exchange rows for joins, aggregates or a final sort. Count the rows before the exchange as well as the final answer. Filtering near a scan or grouping before a large exchange can reduce transfer, but only when the rewrite preserves the result grain. [Query execution and bad plans](/review/relational/rl87/) develops that correctness and estimation work.

## An advancing key can keep one range busy

The event primary key increases from 1 towards 10,000. Splitting it at 2,500, 5,000 and 7,500 creates several primary-key ranges. That distributes the existing data, but the next insert still lands at the rightmost boundary. The next thousand inserts land there too.

A range has replicated copies, not independent writers for each copy. Moving its lease or splitting off an older part does not make an indivisible busy key accept independent concurrent updates. Spare nodes therefore do not imply spare capacity at this write boundary.

The same pattern can remain after changing the primary key to a random identifier. A secondary index beginning with an ever-increasing creation time still receives its newest entries at one edge. Inspect every index the write maintains, not just the primary key. Tenant-first indexing can distribute tenants while one unusually busy tenant continues to concentrate its own writes.

Use range and statement evidence together: which range has the load, which index span it represents, how much time is contention rather than CPU or storage, and whether requests are independently distributable. A single session counter that every booking decrements is a hot row even in a randomly distributed table. Preserving its capacity rule may require serialisation; random placement cannot remove that obligation.

## Scattering changes the ordered-read problem

A hash-sharded index places a computed shard prefix before a sequential key. Consecutive events can then belong to different buckets and, after suitable splitting and placement, different ranges. That gives the system independent spans to distribute.

The prefix also breaks one global chronological run. To find the newest ten events, a query without a known shard may have to inspect several bucket runs and combine their candidates. More buckets can spread writes further while increasing this read work.

The native variation makes that cost visible on the same event fixture. This query asks for the newest ten events across all tenants, so its comparison indexes begin with `created` rather than the tenant-scoped prefix used earlier:

```sql
CREATE INDEX events_ordered
ON workshop.events(created) STORING(value);
EXPLAIN ANALYZE
SELECT created, value FROM workshop.events@events_ordered
ORDER BY created DESC LIMIT 10;

CREATE INDEX events_sharded ON workshop.events(created)
USING HASH WITH BUCKET_COUNT = 4 STORING(value);
EXPLAIN ANALYZE
SELECT created, value FROM workshop.events@events_sharded
ORDER BY created DESC LIMIT 10;
```

The ordered path used one reverse scan. The sharded plan read ten candidates from each of four bucket spans, combined streams and applied the final limit. It still returned ten rows. The second plan also reached KV work on another labelled node; that placement is an observation, not an intrinsic four-bucket requirement.

This is a real read regression for the stated work counters. The lab does not measure a compensating write-throughput improvement, so it cannot conclude that the trade pays. Keep the ordered index if that is the work the application needs and no measured write bottleneck justifies scattering it.

Choose the shard count from a measured workload, including the ordered reads it must still serve. An exact lookup that supplies the hashed inputs has a different cost from an unbounded date scan. Compare one change at a time, use the same request mix and concurrency, and retain p95 latency, retries, KV work and range-load evidence. The native counters establish a covering lookup saving and the extra ordered-read work after sharding; they do not establish a write-throughput gain.

Locality is another independent lever. A covering index can eliminate the primary lookup while its remaining range is still far from the caller. [CockroachDB table locality and region survival](/review/relational/rl127/) places that range according to the workload and the failure contract. The useful repair names the cause it changes: fewer lookups, smaller scans, less contention or a nearer authority.

PostgreSQL stores a table as pages containing versions of records. An index helps a query find a candidate version, and transaction information decides whether the query may see it. A connection can therefore read a current order while an older report reads an earlier version from the same table.

That separation explains several practical surprises. Updating one small field can create work in every index. A page already in memory can still contain a version a reader must ignore. A table can grow while its count of current orders stays unchanged.

We will follow tenant `t4`’s order `o81`. Customer `42` booked workshop session `s7`, whose capacity is two. Request `r81` identifies the accepted request. Its agreed price of 20.00 is a historical fact; the updates here change an operational note. PostgreSQL 18.6 supplies the observations below.

## An isolated server and two clients

A PostgreSQL server owns a data directory. Clients connect to it; they do not open its table files. In the conventional server, each connection has a backend process. A transaction belongs to that connection until `COMMIT` or `ROLLBACK`. A pool can lend the connection to another request afterwards; returning it with an open transaction can let the next caller inherit unfinished work.

The [native lab script](/review/relational/evidence/rl110-native.py) creates its own data directories under a unique temporary directory, uses ports 56810–56815, and stops every server it creates. It requires Python 3 and the pinned PostgreSQL binaries under `/opt/homebrew/bin`. Run a selected investigation or the complete branch:

```sh
python3 rl110-native.py core
python3 rl110-native.py recovery
python3 rl110-native.py replication
python3 rl110-native.py migration
python3 rl110-native.py all
```

The complete run includes intentional errors and an immediate shutdown. Use these commands on a disposable local machine. The script never starts or stops the default PostgreSQL service. Its JSON evidence records SQL, replies, errors and server logs; successful runs remove their temporary clusters. Failed runs stop their servers and retain their directories for diagnosis.

For manual exploration, this is the same kind of server initialisation. Set `PG_BIN` to your PostgreSQL 18.6 binary directory; check the version before proceeding. The temporary socket directory makes the connection address explicit.

Local trust authentication lets local clients claim any database role. It makes a private disposable lab convenient; it is not a production access configuration. Open a second terminal with the same `LAB_ROOT` value and the same `psql` command for client B. `SELECT pg_backend_pid();` will return different backend IDs. Both clients see the same database once their transactions commit.

This compact schema retains tenant identity in every relationship:

```sql

  tenant_id text, customer_id integer, name text,
  PRIMARY KEY (tenant_id, customer_id)
);
CREATE TABLE workshop.sessions (
  tenant_id text, session_id text, capacity integer CHECK (capacity >= 0),
  PRIMARY KEY (tenant_id, session_id)

  tenant_id text, order_id text, request_id text,
  customer_id integer, session_id text,
  agreed_price numeric(10,2), status text, note text,
  PRIMARY KEY (tenant_id, order_id),
  UNIQUE (tenant_id, request_id),
  FOREIGN KEY (tenant_id, customer_id) REFERENCES workshop.customers,
  FOREIGN KEY (tenant_id, session_id) REFERENCES workshop.sessions
```

The disabled table autovacuum and low fillfactor keep the tiny physical example observable. ## From a key to tuple bytes

A query names a logical record:

```sql
SELECT customer_id, agreed_price, note
FROM workshop.orders
WHERE tenant_id = 't4' AND order_id = 'o81';
-- 42 | 20.00 | original
```

PostgreSQL parses the command, resolves names and types, and plans a way to obtain the answer. A primary-key lookup on a large table commonly uses its B-tree; this one-row fixture may correctly choose a sequential scan. `EXPLAIN (ANALYZE, BUFFERS)` shows which route it actually chose.

A B-tree entry holds a key and a tuple location. PostgreSQL normally uses 8 KiB heap pages. A location such as `(0,1)` names page zero and item one on that page. The item is a small pointer to the tuple bytes. Bytes can move within the page during compaction while the item number stays in place.

```sql
SELECT ctid, xmin, xmax, note FROM workshop.orders;
-- (0,1) | creator transaction | 0 | original
```

`ctid` describes this physical version’s location. It changes after updates and some maintenance, and the location can later be reused. It cannot replace `(tenant_id, order_id)` as an application identity.

A tuple header carries transaction information before the user columns. `xmin` identifies the creator. `xmax` participates in replacement and locking information; a nonzero value is not by itself proof of a committed deletion. Snapshots, transaction outcomes and header flags must be interpreted together.

## Shared pages and private work

Backends access ordinary index and heap pages through **shared buffers**, PostgreSQL’s shared page cache. Finding a page there avoids another read into that cache. Otherwise PostgreSQL asks its storage layer for the page, which may already be in the operating system’s cache.

Consequently, `shared hit=3` describes three buffer accesses, not three distinct disk reads. `shared read=3` says PostgreSQL brought pages into its own buffers, not that the physical drive necessarily served them. Repeated warm executions answer a different performance question from the first request after a reboot.

Backends share the page cache, locks and transaction coordination. They also have private execution state. A sort’s working memory is separate from shared buffers. Adding connections adds possible concurrent operations and memory demand; it does not give each connection its own independent database.

Background processes work alongside them. The background writer helps prepare reusable buffers, the checkpointer advances the recovery boundary, the WAL writer writes log data, and autovacuum workers maintain versions. A request does not travel through these as successive services.

Wide values add another storage boundary. A tuple cannot span heap pages. PostgreSQL’s TOAST machinery can compress large variable-width values and store them in another relation. A small heap tuple can then hold a pointer to a large note. Selecting just the price need not fetch the note; `SELECT *` may have to fetch and transmit it. Leaving an external value unchanged can reuse it, whereas constructing a changed JSON value can require new storage, as [the JSON investigation](/review/relational/rl114/) shows.

## Which page leaves the buffer pool

A report can read far more pages than the cache holds. If every newly read page displaced a recently used application page, a one-time report could evict the workshop service’s whole working set. The next small order lookup would then pay to bring its pages back.

PostgreSQL uses a clock sweep rather than maintaining a strict least-recently-used list. A buffer has a bounded usage count. Reuse can raise it; a clock hand looking for a victim reduces positive counts and takes an unpinned buffer it finds at zero. Pages used repeatedly can survive more passes than a page read once, but a sufficiently long stream of misses still wears their counts down.

For selected bulk paths PostgreSQL uses a small ring of buffers. The bulk operation tries to reuse that set as it advances, limiting how much unrelated cache it displaces. The access strategy matters: a large sequential scan can receive this protection while an index path reading many pages can place broader pressure on the ordinary replacement policy.

The figure puts eight slots around a small model service. S1–S4 are its repeatedly used pages; R pages are a report’s one-time reads. Start with the plain least-recently-used policy, then choose clock sweep and clock plus ring. Watch which service pages remain when the report finishes.

`pg_buffercache`, when installed with appropriate privileges, can inspect cached relations and usage counts. Its summary functions can be cheaper than scanning every buffer entry. Treat a snapshot cautiously: counts fall when replacement is needed, so an old unused page can keep a high count in an otherwise quiet pool. Compare changes across the workload you are diagnosing.

More shared buffers can help a working set fit, but it does not fix a query that needlessly reads most of the table. A plan change can also change the cache cost paid by other requests. Keep buffer policy in the explanation when a reporting query and small transactional queries compete.

## One row, two visible histories

In client A, begin a report and establish its snapshot:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT note FROM workshop.orders;
-- original
```

Leave A open. Client B changes the note and commits:

```sql
UPDATE workshop.orders SET note = 'amended'
WHERE tenant_id = 't4' AND order_id = 'o81';
SELECT ctid, note FROM workshop.orders;
-- (0,2) | amended
```

A’s next ordinary `SELECT note` still returns `original`; B sees `amended`. Repeatable Read keeps the snapshot established by A’s first ordinary statement. Under Read Committed, a later ordinary statement takes a fresh snapshot and can see the committed change. An ordinary old reader can read the retained version without waiting for B’s row update.

The old tuple has not become the new tuple. B wrote a replacement at another item and recorded that its transaction replaced the earlier version. The report excludes that replacement from its visible history even after B commits. A newer snapshot includes it.

## HOT preserves the existing index route

Our first update changed no indexed column, and the replacement fitted on the same page. PostgreSQL marked the old tuple `HEAP_HOT_UPDATED` and the replacement `HEAP_ONLY_TUPLE`. This is a **heap-only tuple**, or HOT, update.

The existing index entry can keep pointing to the chain’s first item. The native B-tree inspection still shows its reference to `(0,1)` after this HOT update. A reader follows the chain on that page and selects its visible version. Once no snapshot needs an earlier payload, pruning can remove its bytes and leave a redirect at the original item. The index still reaches the surviving version.

The lab inspects these states with `pageinspect`:

```sql
CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid,
       heap_tuple_infomask_flags(t_infomask, t_infomask2)
FROM heap_page_items(get_raw_page('workshop.orders', 0));
```

These privileged functions bypass ordinary row visibility. They are inspection tools for the disposable server, not application queries.

Now add an index on the field being edited:

```sql
CREATE INDEX orders_note ON workshop.orders (note);
UPDATE workshop.orders SET note = 'indexed'
WHERE tenant_id = 't4' AND order_id = 'o81';
```

The replacement at item three lacks `HEAP_ONLY_TUPLE`. Changing an indexed value prevents the shortcut. The new version needs index entries, including in indexes whose own key did not change, because their old entries identify an earlier physical version.

`INCLUDE` columns, expression inputs and partial-index predicates can also change eligibility. The condition concerns every relevant index, not just the index the last query used. Summarising indexes are the exception: PostgreSQL 18’s BRIN summaries can be maintained while an update remains HOT.

Page room is the other condition. A lower table fillfactor leaves space during insertion and can help eligible replacements stay beside their predecessors. It also means more heap pages for the same live rows. It cannot rescue an update that changes a non-summarising indexed value. Compare changes in `n_tup_upd` and `n_tup_hot_upd` over the workload before treating fillfactor as a remedy.

A successful update has now created a physical version, maintained its access paths and made it visible according to transaction rules. Its survival across a crash is a separate question, followed in [WAL, checkpoints and durability](/review/relational/rl115/).

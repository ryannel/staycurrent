A database value has rules for arithmetic, ordering and equality. Those rules affect more than presentation. They decide whether a price rounds, whether two account names can share a key and whether an unpaid order appears in a report.

Choose a type by the question the value must answer. An instant and a local appointment time can display the same clock face while meaning different things. An absent payment and a payment of zero are also different facts. SQL keeps these distinctions only when the representation does.

The examples follow workshop order `o81` in tenant `t4`. A `SELECT` evaluates expressions and returns columns; `WHERE` retains only rows for which its predicate is true. That last rule becomes important when a value is missing.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/review/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Money has a unit and a rounding rule

The service agreed on two seats at €20 each. An exact decimal type such as PostgreSQL `numeric(10,2)` represents the two decimal places directly. A binary floating-point value approximates most decimal fractions. That approximation is useful for measurements but makes exact decimal equality a poor contract.

```sql
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric AS decimal_equal,
       0.1::double precision + 0.2::double precision
         = 0.3::double precision AS float_equal,
       1.005::numeric(10,2) AS rounded;
```

```text
decimal_equal | float_equal | rounded
t            | f           | 1.01
```

The declared scale also rounds input. It does not prove that an upstream calculation used the right rounding rule. Decide whether taxes round per line or per invoice, and where a fractional-cent allocation goes. Three equal shares of €10 cannot all be €3.33: one must carry the remaining cent. Store enough information to reproduce the agreement, rather than recomputing it under tomorrow's rules.

An integer number of minor units is another exact representation: `2000` cents. It needs a currency and a scale contract. A bare integer `2000` must not sometimes mean cents and sometimes euros, and currencies do not all have two decimal places. Use a sufficiently wide integer, check overflow in multiplication, and avoid adding unlike currencies without an explicit conversion.

SQLite is a useful contrast. Declaring `DECIMAL(10,2)` gives a column numeric affinity; it does not install PostgreSQL's exact decimal arithmetic or enforce that scale. An integer minor-unit convention or a deliberately chosen decimal implementation is needed when exactness matters. The same type name across engines need not give the same value model.

## An instant is different from a local time

A workshop starts at a local wall-clock time in Stockholm. On 25 October 2026, clocks repeat the hour beginning at 02:00. These are two distinct instants:

```sql
SET TIME ZONE 'UTC';
SELECT timestamptz '2026-10-25 02:30:00+02' AS first_instant,
       timestamptz '2026-10-25 02:30:00+01' AS second_instant,
       timestamptz '2026-10-25 02:30:00+01'
         - timestamptz '2026-10-25 02:30:00+02' AS elapsed;
```

```text
first_instant          | second_instant         | elapsed
2026-10-25 00:30:00+00  | 2026-10-25 01:30:00+00  | 01:00:00
```

PostgreSQL `timestamptz` stores an instant, not the original zone name. The session's zone controls its display. Preserve `Europe/Stockholm` separately when future scheduling or the original locality matters. A `timestamp without time zone` stores local date and time fields; it cannot distinguish those two occurrences by itself.

For a future recurring session, store the intended local rule and zone, then define a policy for missing and repeated local times. “Every Sunday at 02:30 Stockholm time” is not the same schedule as “every 168 hours”. Time-zone rule updates can change future conversions; they must not silently redefine a past agreement.

Use half-open ranges for adjacent reporting days: `placed_at >= start AND placed_at < next_start`. The last representable microsecond is unnecessary, and a local day's UTC boundaries need not be 24 hours apart. SQLite and MySQL use different date/time representations and conversion facilities; do not transfer PostgreSQL literal syntax or timezone behaviour without checking the destination engine.

## Text equality is a business decision

PostgreSQL's ordinary deterministic comparison distinguishes `'Ada'` from `'ada'`. A `lower(name)` comparison deliberately changes that rule. SQLite's built-in `NOCASE` comparison folds ASCII letters, which does not make it a complete Unicode case-insensitive comparison.

```sql
SELECT 'Ada' COLLATE "C" = 'ada' COLLATE "C" AS exact,
       lower('Ada') = lower('ada') AS folded;
SELECT v FROM (VALUES ('Zoe'),('adam')) AS names(v)
ORDER BY v COLLATE "C";
```

```text
exact | folded
f     | t

v
Zoe
adam
```

A collation defines comparison rules. It may order by linguistic conventions rather than byte values, and some collations treat case or accents as insignificant. The unique constraint and the login lookup must use a compatible equality rule, or the application may accept two accounts it later cannot distinguish. Unicode normalisation is another decision: visually similar text may have different code-point sequences.

Keep the original display value if users need it, and define a canonical identity value deliberately. Do not casually lowercase the entire world of identifiers: filesystem paths, externally assigned IDs and the local part of an email address have contracts of their own. [Indexes and access paths](/review/relational/rl86/) explains why a comparison's expression and collation must also fit its index.

## NULL produces an unknown comparison

`NULL` marks a missing value. It does not say why the value is missing. A payment time may be unknown, inapplicable or not yet recorded; if the application must distinguish those states, give them explicit representation.

Comparing a missing value with `=` gives an unknown result, written as `NULL`, even when both operands are missing. Use `IS NULL` to test missingness. PostgreSQL's `IS NOT DISTINCT FROM` supplies equality in which two NULLs compare equal.

```sql
SELECT NULL = NULL AS ordinary_equal,
       NULL IS NULL AS is_missing,
       NULL IS NOT DISTINCT FROM NULL AS same_including_missing;
```

```text
ordinary_equal | is_missing | same_including_missing
NULL           | t          | t
```

<table><caption>Three-valued predicates for a missing payment time</caption><thead><tr><th>Expression</th><th>Result</th><th>Survives WHERE?</th></tr></thead><tbody><tr><td>paid_at IS NULL</td><td>true</td><td>yes</td></tr><tr><td>paid_at = a timestamp</td><td>unknown</td><td>no</td></tr><tr><td>NOT (paid_at = a timestamp)</td><td>unknown</td><td>no</td></tr><tr><td>false AND unknown</td><td>false</td><td>no</td></tr><tr><td>true OR unknown</td><td>true</td><td>yes</td></tr></tbody></table>

Unknown is not false, even though `WHERE` rejects both. `CHECK (amount > 0)` accepts unknown in PostgreSQL, so add `NOT NULL` when missing amounts are forbidden. Conversely, replacing every NULL with zero can turn missing revenue into known zero revenue. `COALESCE` chooses the first non-NULL value; use it only when that substitution matches the question.

Aggregates usually ignore NULL inputs. `count(*)` counts rows; `count(amount)` counts known amounts. `sum(amount)` over no rows is NULL, not zero. Outer joins introduce NULLs for the missing side even when the source column is `NOT NULL`.

## One missing payment ID changes NOT IN

Create two orders and one payment record whose order is not yet identified:

```sql
CREATE TABLE orders (tenant_id text, order_id text);
CREATE TABLE payments (tenant_id text, order_id text);
INSERT INTO orders VALUES ('t4','o81'), ('t4','o82');
INSERT INTO payments VALUES ('t4','o81'), ('t4',NULL);
SELECT order_id FROM orders
WHERE tenant_id = 't4'
  AND order_id NOT IN (
    SELECT order_id FROM payments WHERE tenant_id = 't4'
  );
```

The result has **zero rows**. For `o82`, SQL evaluates “not equal to `o81` and not equal to NULL”. That is true AND unknown, hence unknown. The unpaid order disappears.

Ask for the absence of a matching payment instead:

```sql
SELECT o.order_id FROM orders o
WHERE o.tenant_id = 't4'
  AND NOT EXISTS (
    SELECT 1 FROM payments p
    WHERE p.tenant_id = o.tenant_id AND p.order_id = o.order_id
  )
ORDER BY o.order_id;
```

```text
order_id
o82
```

This is a different, explicit question: no payment row has this tenant and order ID. Filtering NULLs out of the subquery would also repair this particular `NOT IN`, provided the outer ID is non-NULL. An empty subquery is another useful variation: `NOT IN` then accepts every order, whereas a subquery containing only NULL accepts none of these non-NULL IDs. Test missingness where it enters the data, before optimising the query that later encounters it.

A lock reserves permission to use a database resource in a particular way. A writer may hold an exclusive lock while changing a row; a second writer needing that resource waits until the first transaction finishes. The resource can also be a key range, a table or an application-defined name.

That waiting is often what makes a booking correct. It is also why a fast UPDATE can take seconds during an incident. To use locks well, identify the rule they protect, the resource every competing decision reaches and how long each holder keeps it.

Tenant t4's workshop session s7 has capacity 2 and one booking, b17. All bookings consume one seat. PostgreSQL is the native worked example; the last section gathers differences that change a protocol in other engines.

## An atomic update already takes a lock

Suppose `seat` contains `(tenant='t4', session='s7', capacity=2, reserved=1)`, with `(tenant, session)` as its primary key and a CHECK requiring reserved to stay between zero and capacity. The first caller runs:

```sql
BEGIN;
UPDATE seat
SET reserved = reserved + 1
WHERE tenant = 't4' AND session = 's7'
  AND reserved < capacity
RETURNING reserved;
-- 2
-- Insert the booking here, after checking the result.
```

The UPDATE locks its target. A separate `SELECT FOR UPDATE` is unnecessary when this single predicate and update express the entire capacity decision. The transaction keeps its write lock until commit or rollback, including the time the application spends between statements.

Send the same UPDATE from another connection before the first commits. It waits. At PostgreSQL Read Committed, once the first transaction commits, the contender rechecks the updated target and returns no row. After a rollback, it can instead reserve the seat. A zero-row result is a successful statement saying that this attempt reserved nothing.

Locking is paid for in time. Sending an email or waiting for a person inside A's transaction extends B's wait. Shorten the transaction by preparing independent work beforehand and recording external work as [durable intent](/review/relational/rl94/).

## Lock the record that represents the rule

Some booking decisions need several statements. A session may have separate booking rows and no maintained counter. Writers can take turns by locking the session's existing control row, then counting bookings in a later statement.

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT capacity FROM seat
WHERE tenant = 't4' AND session = 's7'
FOR UPDATE;

SELECT count(*) FROM booking
WHERE tenant = 't4' AND session = 's7';
-- Handler inserts its distinct booking only if count < capacity.
COMMIT;
```

A caller that waited for the control row gets a fresh snapshot for that subsequent count. If A inserts the second booking before releasing its lock, B's later count sees two and declines. Reading the dependent facts before acquiring the lock would keep a stale application decision alive through the wait.

Every writer of that rule must participate. A cancellation that changes the session's state, a bulk importer and a support tool can bypass an application lock convention. Centralise the operation, restrict direct write privileges, or choose a database-enforced constraint when one can express the rule. Serializable execution is another option for a correctly written predicate decision; [transactions and isolation](/review/relational/rl90/) explains its aborts.

The control row becomes a point of serialisation. That is reasonable for a capacity-2 session. Giving every session the same global control row would make unrelated workshops wait on each other.

## A missing row leaves nothing to lock

The tempting duplicate-booking protocol is “look up b20 FOR UPDATE, and insert it if absent”. In PostgreSQL, that empty result does not reserve the missing identity.

For one booking identity, put a primary key or unique constraint on `(tenant, id)` and handle that specific conflict. A prior lookup can improve a user interface, but it cannot replace the constraint.

For a quantity over many distinct bookings, that unique key is insufficient. b18 and b19 have different identities, so both satisfy uniqueness while overselling s7. Use an existing session row, an atomic counter or a serializable predicate decision. Where the rule is “one booking per numbered seat”, a unique `(tenant, session, seat_number)` expresses the finite resource directly; include a seat-range check and a session relationship so invented seat numbers cannot create capacity.

Range-locking engines can cover gaps, but that does not turn any empty SELECT into a portable mutex. The searched index, predicate and isolation level decide the protected range.

## Inspect the wait graph

A slow statement may be doing little work. Our second connection waited on the first transaction, while that first connection was idle, waiting for its application to send another command.

<table><caption>Native observation while B's UPDATE was blocked; process IDs vary by run</caption><thead><tr><th>Connection</th><th>State</th><th>Wait</th><th>Blocks on</th></tr></thead><tbody>
<tr><td>A</td><td>idle in transaction</td><td>Client / ClientRead</td><td>Nobody</td></tr>
<tr><td>B</td><td>active</td><td>Lock / transactionid</td><td>A's process ID</td></tr>
</tbody></table>

The word `active` does not say B is using CPU. PostgreSQL's wait category supplies the missing distinction. Its `pg_blocking_pids(pid)` function identifies blocking sessions; a row wait commonly appears as waiting on the owning transaction's completion. Follow the chain to its root before choosing an intervention.

A root blocker can itself be waiting on an external API or an abandoned application connection. Cancelling its current statement will not necessarily end its transaction. An idle transaction has no running statement to cancel. Terminating a session causes rollback and disconnects its application, so understand that transaction's work before choosing it. [Diagnosing an incident](/review/relational/rl103/) follows this decision through recovery.

Use separate budgets for lock acquisition, total statement execution and the whole application request. After a lock timeout or confirmed cancellation, clean up the transaction before returning the connection to a pool. A request deadline alone does not establish that the database stopped.

## Opposite lock order creates a cycle

Now the booking includes sessions s7 and s8, perhaps two workshop modules bought together. A updates s7 first. B updates s8 first. Then each asks for the other's resource.

<div data-relational-component="relational-operation-tools/Locks" data-number="3"></div>

Waiting longer cannot finish this history. It is a **deadlock**. Our native run deliberately created the cycle. PostgreSQL rejected A with `40P01`; B's pending update then completed. Another schedule can choose another victim. The aborted attempt cannot commit its earlier changes.

Acquire shared resources in a consistent order. For these two sessions, all handlers can lock `(t4, s7)` before `(t4, s8)`. B then waits at s7 before taking s8, leaving A free to finish. Include tenant and table in the order where the operation reaches several kinds of resource. A convention that sorts sessions while another path first locks an order row can still form a larger cycle.

```sql
SELECT tenant, session, reserved, capacity FROM seat
WHERE tenant = 't4' AND session IN ('s7', 's8')
ORDER BY tenant, session
FOR UPDATE;
```

This is PostgreSQL's ordered locking query for the fixture. While holding those locks, the handler checks and changes both resources, inserts its business rows and commits. The order needs to be shared by every relevant path, including cancellation and background work.

Always retain deadlock handling. Constraints, triggers, maintenance and other tables can add dependencies. After a confirmed deadlock rejection, roll back and retry the whole operation with fresh decisions under a bounded budget. Do not repeat an external effect performed during the failed attempt; move it to durable work with stable identity.

## Less waiting can change which work is selected

`NOWAIT` asks for immediate failure instead of waiting on a conflicting lock. That can make a request's refusal explicit, but it does not make its decision safe to skip. “Busy” and “sold out” are different answers.

`SKIP LOCKED` omits rows that cannot immediately be locked. It is useful when several workers can take different available jobs. It is unsuitable for a report of all bookings or a count used to admit another customer: omitted locked rows still exist and may matter. A queue also needs starvation handling when the same old job is repeatedly unavailable.

Neither option shortens the lock held by the first transaction. Removing unnecessary work from that transaction often helps more than changing every caller's wait policy.

## Engine differences that change the protocol

<table><caption>Lock scope and waiting across four engines</caption><thead><tr><th>Engine</th><th>Consequence for this design</th></tr></thead><tbody>
<tr><td>PostgreSQL 18</td><td>FOR UPDATE protects rows retrieved, not an absent key. Serializable predicate tracking rejects unsafe histories rather than blocking all inserts into a read predicate.</td></tr>
<tr><td>InnoDB, MySQL 8.4</td><td>Locking index scans can take record and gap/next-key locks. Repeatable Read and Read Committed differ in gap protection; an unselective scan can lock much more than the business key suggests.</td></tr>
<tr><td>SQL Server</td><td>Locks can cover keys, ranges, pages and tables. SERIALIZABLE protects key ranges; lock escalation can broaden contention. Read-committed versioning does not remove write conflicts.</td></tr>
<tr><td>SQLite</td><td>One database writer is the coordination boundary. BEGIN IMMEDIATE obtains write authority early or fails busy; there are no row locks to distribute among workshop sessions.</td></tr>
</tbody></table>

The rule is the same question in each engine: can two callers reach conflicting decisions without encountering the same enforced authority? The answer comes from actual lock scope and transaction behaviour, rather than the presence of the word “lock” in the SQL.

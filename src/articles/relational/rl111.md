An update leaves PostgreSQL with a new row version and an old version that some reader may still need. Vacuum is the maintenance that makes this arrangement sustainable. It removes versions that are no longer needed, cleans their index entries, records reusable space and maintains visibility information.

It also protects old records from transaction-ID ageing. A static table needs that protection even when it has no dead rows. Disk growth and transaction age therefore belong in the same investigation, but they are different measurements.

We will hold a workshop report open, delete half a table, and watch a vacuum that completes without removing those versions. Then we will release the report and prove that new rows reuse the reclaimed room. The native PostgreSQL 18.6 run uses the [isolated lab](/learn/databases/relational/postgresql/architecture/#an-isolated-server-and-two-clients), with separate clients A and B.

## A completed vacuum can leave dead versions

The fixture is a staging table with 10,000 rows. Its primary key is only a lab identity; actual workshop relationships retain their tenant keys. The text makes the heap large enough to inspect page reuse.

```sql
CREATE EXTENSION pgstattuple;
CREATE TABLE vacuum_lab (id integer PRIMARY KEY, note text)
WITH (autovacuum_enabled = false);
INSERT INTO vacuum_lab
SELECT n, repeat('x',180) FROM generate_series(1,10000) n;
VACUUM vacuum_lab;
```

Autovacuum is disabled for this one table so the manual schedule remains visible. Vacuum must run outside an explicit transaction block.

Client A establishes a stable report snapshot:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM vacuum_lab;
-- 10000
```

Leave it open. Client B deletes every even ID and vacuums:

```sql
DELETE FROM vacuum_lab WHERE id % 2 = 0;
VACUUM (VERBOSE) vacuum_lab;
```

B now counts 5,000 current rows. A still counts 10,000. Removing the deleted payloads would make A’s answer impossible, so PostgreSQL retains them. Our vacuum reported:

```text
tuples: 0 removed, 10000 remain,
        5000 are dead but not yet removable
```

“Dead” here describes the obsolete versions from the current history. “Not yet removable” says another permitted view can still use them. A recent vacuum timestamp proves that maintenance ran; it does not prove that every obsolete version became removable.

## Find the holder before increasing effort

While A remains open, inspect its session from an operator connection:

```sql
SELECT pid, application_name, state, xact_start,
       backend_xmin, age(backend_xmin), wait_event_type, wait_event
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;
```

The lab’s report had a non-null `backend_xmin`. In a manual pause between commands it will often be `idle in transaction`, waiting for the client while retaining its snapshot. A client-read wait does not mean the database has finished all responsibility for that session.

Transaction duration and transaction-ID age answer different questions. Duration is time on a clock. Age counts how much transaction-ID activity has passed the retained boundary. A quiet overnight report and a shorter report during heavy write traffic can have very different ages.

The oldest row deserves investigation, not automatic termination. Find the owning request and whether it can commit, roll back or be retried. A forgotten transaction usually needs an application fix. A deliberate long report may need a bounded transaction or a separate reporting arrangement. `idle_in_transaction_session_timeout` can limit abandoned sessions, but the application must handle the resulting disconnect and retry safely.

Sessions are only one source of retention. Inspect prepared transactions and replication slots too:

```sql
SELECT gid, prepared, owner, age(transaction) FROM pg_prepared_xacts;
SELECT slot_name, slot_type, active, xmin, catalog_xmin, restart_lsn
FROM pg_replication_slots;
```

`xmin` and `catalog_xmin` are row-history horizons; `restart_lsn` is a WAL-retention position. A slot can create a serious WAL-space problem without explaining dead tuples in this particular application table. Physical standby feedback can preserve versions for queries on another machine. Establish which horizon is relevant before dropping a slot or cancelling a report.

Dropping a slot can force a subscriber or standby to be rebuilt. Resolving a prepared transaction requires knowing whether the coordinator decided commit or rollback. These interventions change recovery or correctness obligations; they are not interchangeable ways to make an age number smaller.

## Reuse is different from shrinking

Commit A, then repeat B’s vacuum:

```sql
VACUUM (VERBOSE) vacuum_lab;
SELECT pg_relation_size('vacuum_lab') AS bytes,
       tuple_count, dead_tuple_count, free_space
FROM pgstattuple('vacuum_lab');
```

The second vacuum removed 5,000 tuples. Our heap still occupied 2,220,032 bytes, or 271 pages. `pgstattuple` now reported zero dead tuples and 1,094,072 bytes of free space. Before the report ended, its scan had found 5,000 dead tuples and only 13,528 free bytes.

That free space is useful. Insert 5,000 replacements with different keys:

```sql
INSERT INTO vacuum_lab
SELECT n, repeat('y',180) FROM generate_series(10001,15000) n;
SELECT pg_relation_size('vacuum_lab');
-- 2220032
```

The table returned to 10,000 current rows without growing. The file size alone would have missed both the cleanup and its benefit.

Ordinary vacuum can sometimes truncate empty pages at the end of the heap, subject to obtaining the needed lock. Scattered gaps inside the file do not meet that condition. `VACUUM FULL` instead rewrites a compact copy and takes an Access Exclusive lock, blocking reads and writes. It also needs space for the new copy and rebuilds indexes. A table that will refill tomorrow may pay that entire cost only to grow again.

For a separate rewrite test, the lab deletes the 5,000 replacement rows, runs ordinary vacuum and confirms that the heap remains 2,220,032 bytes. It then starts a new ordinary read transaction. `VACUUM FULL` with a 150 ms lock timeout fails while that reader holds its transaction open. After the reader finishes, the rewrite succeeds and the 5,000 survivors occupy 1,114,112 bytes. This smaller file was bought with a blocking rewrite; it did not come from making ordinary vacuum more aggressive.

`pgstattuple` scans the relation and needs suitable privileges. Use its exact inspection deliberately on a large table. Routine views such as `pg_stat_user_tables` offer cheaper estimated counts, which should not be mistaken for an exact inventory of reclaimable bytes.

## Visibility and freezing have separate jobs

Vacuum maintains two visibility-map bits per heap page. **All-visible** allows an index-only scan to trust visibility without fetching the heap tuple. **All-frozen** says that page does not contain transaction-ID work needing future freezing. A page can be all-visible without being all-frozen.

An update clears the relevant shortcut. A later vacuum can restore it after the versions qualify. This is why a covering index may show `Heap Fetches: 0` after vacuum and require heap checks again after one update, even to another row on the same page. [Native index methods](/learn/databases/relational/postgresql/indexes/) measures that change.

Transaction IDs in tuple headers have a finite 32-bit space. PostgreSQL compares them in a circular ordering. A creator left untreated for too much subsequent transaction activity could eventually appear to be in the future. **Freezing** records that a sufficiently old committed creator is permanently old.

Modern PostgreSQL records this in flags and can retain the original numerical `xmin`. Looking for every frozen tuple to acquire the number 2 would miss the state. After the refill, before the rewrite test, the lab ran `VACUUM (FREEZE, VERBOSE) vacuum_lab`. It froze 10,000 tuples and set 271 pages all-frozen. It made the mechanism observable; it is not a prescription to freeze every production table manually.

Track age at both relation and database boundaries, including TOAST relations:

```sql
SELECT c.oid::regclass AS relation,
       greatest(age(c.relfrozenxid), age(t.relfrozenxid)) AS xid_age,
       greatest(mxid_age(c.relminmxid), mxid_age(t.relminmxid)) AS mxid_age
FROM pg_class c
LEFT JOIN pg_class t ON t.oid = c.reltoastrelid
WHERE c.relkind IN ('r','m');
SELECT datname, age(datfrozenxid) FROM pg_database;
```

Multixact IDs describe some multiple-locker states and have their own age safety requirements. A low dead-tuple estimate does not discharge either ageing obligation.

## Make autovacuum keep up

Once eligible work can be removed, ask whether maintenance processes it fast enough. Compare counter changes across an interval: updates, deletes, HOT updates, autovacuum runs, dead-tuple estimates and relation sizes. Inspect running work in `pg_stat_progress_vacuum` and duration/I/O evidence in vacuum logs.

Percentage-based triggers allow more accumulated changes on a large table. A lower table-specific scale factor can start smaller passes sooner. Cost limits and delays change how aggressively a worker competes for resources; available worker capacity and the time each run takes determine whether the queue grows. Earlier starts cannot fix a snapshot boundary that remains pinned, and greater effort can make foreground latency worse.

In PostgreSQL 18, insert-triggered vacuuming and age-driven maintenance also matter. Do not reduce the investigation to “updates since last vacuum.” A mostly inserted or static table still needs visibility and freeze work. Anti-wraparound maintenance can be invoked even when ordinary autovacuum is disabled for a table.

Treat wraparound warnings as an incident. Resolve the actual blockers and follow the pinned version’s recovery guidance; do not keep cancelling the protective worker or attempt a table rewrite as a shortcut. The manual’s emergency procedure differs from this small illustrative `FREEZE` experiment.

A useful maintenance outcome is a steady working size, bounded age and foreground work within its budget. The next measurement should establish which of those failed, then show that the chosen intervention repaired it.

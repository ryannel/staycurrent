A CockroachDB backup is an independently retained recovery source. Replication keeps serving after some failures, but it also copies a committed deletion. A backup lets recovery choose a state from before that deletion, provided the necessary data, metadata, history and access still exist.

Choosing that state does not finish recovery. A restore can complete successfully while the service lacks its SQL identity or an order accepted after the selected point. Acceptance must test both the restored facts and what the application can do with them.

This rehearsal uses CockroachDB **25.4.17**, workshop tenant `t4`, customer `42` and session `s7`. It executes real full, incremental and historical restores into a separately initialised cluster on the same host. Its shared temporary `nodelocal` directory makes the experiment inspectable. A recovery copy for machine loss must also survive the source machine and its storage.

## Define the state the service must recover

The fresh source starts with order `r80` for €20 and two remaining places in `s7`. This is a smaller fixture than the earlier transaction worksheet: it does not contain `concurrent-A` or the large event table. Its orders are keyed by `(tenant, request)` and its session by `(tenant, session)`, with a check that remaining capacity cannot be negative.

We will admit `r82` for €22 and decrement capacity in the same mutation. Recovering that order without its capacity change could sell its place again. Recovering only the capacity change would leave a consumed place without its accepted request. The recovery target must keep those facts together.

A table backup suits a bounded recovery question only if its dependencies are accounted for. A database backup captures a broader application boundary; full-cluster recovery has another scope, including system objects and identities. Select the scope that restores the promised service. The [worksheet bundle and setup](/learn/databases/relational/cockroachdb/keys-and-ranges/) supplies the disposable environment used here.

## A full backup establishes a base

The source starts a backup collection:

```sql
BACKUP DATABASE workshop
INTO 'nodelocal://1/independent-backup'
WITH revision_history;
```

```text
status    | fraction_completed | rows
succeeded | 1                  | 2
```

The two rows are the initial order and session. Record the job identity, location, source scope and completion time beside the application's recovery markers. Success establishes that the backup completed; it does not establish that the credentials available after a disaster can restore it.

`nodelocal://1/...` names storage associated with a particular node's external-I/O directory. A surviving database node does not automatically make that path reachable. Use a supported destination whose storage, credentials and encryption keys survive the intended loss, and test them from the destination environment.

Keep backup access separate from routine application permissions. A role able to delete every backup can destroy recovery even while its SQL grants look narrow. Retention, immutability and key recovery depend on the selected storage and identity design as well as the backup statement.

## An incremental preserves the accepted booking

The worksheet saves `cluster_logical_timestamp()` before accepting `r82`. It then couples capacity and the order:

```sql
WITH admitted AS (
  UPDATE workshop.sessions
  SET remaining = remaining - 1
  WHERE tenant = 't4' AND session = 's7' AND remaining > 0
  RETURNING tenant
)
INSERT INTO workshop.orders
SELECT tenant, 'r82', 42, 22.00 FROM admitted
RETURNING request;
```

The statement returns `r82`. The update supplied a row, so the insert created the order in the same atomic statement. With no remaining place, it would supply no row and create no order. This new request now has two corresponding facts: its order at €22 and capacity reduced from two to one.

The next backup adds those changes to the collection:

```sql
BACKUP DATABASE workshop
INTO LATEST IN 'nodelocal://1/independent-backup'
WITH revision_history;
```

The recorded incremental succeeds with a row counter of two. Recovery still needs the earlier base and required intervening layers. Keeping only the smallest file mentioning `r82` does not make an independent full backup. Preserve the chain's data and manifests under one tested retention policy.

`LATEST` selects a collection subdirectory; it does not define the business recovery point. Inspect the contents and intervals with the pinned release's `SHOW BACKUP` surface. A schedule also needs evidence after creation: alert on failed or missing runs and track the newest restorable point's age, not only when a backup process last started.

## Choose a point inside the retained history

Ordinary backup layers preserve their supported snapshot endpoints. `revision_history` retains historical versions for the backed-up interval so a restore can select an eligible intermediate timestamp. It does not create versions older than the source retained or make an arbitrary timestamp valid.

Our saved timestamp is `1792409298341886000.0000000000`, just before `r82`. A rerun must capture its own value and preserve it outside the source's eventual loss. A CockroachDB logical timestamp and an application wall clock are different representations; do not guess the target by truncating a display time.

The worksheet now deliberately deletes `r82` without returning its place. The live state has only `r80`, while capacity remains one. Replication faithfully copies that mistake.

## Restore away from the live authority

The destination has a fresh store and cluster identity. It shares the source's host, temporary external-file directory and lab certificate authority. This tests destination dependencies without demonstrating independent-host disaster survival.

On that destination, restore the completed collection under a new name:

```sql
RESTORE DATABASE workshop
FROM LATEST IN 'nodelocal://1/independent-backup'
WITH new_db_name = 'valid_latest';
SELECT request, amount FROM valid_latest.orders ORDER BY request;
SELECT remaining FROM valid_latest.sessions;
```

```text
request | amount
r80     | 20.00
r82     | 22.00

remaining
1
```

The latest backup predates the deletion and includes the incremental. It recovers the two intended identities, their agreed amounts and the consumed place. Equal counts or totals alone would not detect swapped identities or compensating errors.

For this deletion, the latest backup is the useful recovery candidate. The next variation asks for an older history while the service still owes later accepted work. Restore the same chain at the saved earlier timestamp:

```sql
RESTORE DATABASE workshop
FROM LATEST IN 'nodelocal://1/independent-backup'
AS OF SYSTEM TIME '1792409298341886000.0000000000'
WITH new_db_name = 'valid_earlier';
```

The job also succeeds, but `valid_earlier` contains only `r80` at €20 and two remaining places. It is consistent about its selected time. It cannot become today's authority while the service still owes `r82` its booking. A valid timestamp and a completed job do not settle which later work the service must preserve.

## Reconcile the order and capacity once

The rehearsal knows that `r82` was accepted from the successful request and its observation record, retained outside the disposable cluster. A real recovery needs surviving evidence too: an independently retained acceptance journal or receipt, intact later history, or a downstream authority whose contract establishes the result. A log showing only that a request was sent does not prove it committed.

Preserve the original identity and intent with that evidence. If an outcome remains unknown, use the request's reconciliation protocol rather than inventing an accepted order. Restoring older database bytes cannot reconstruct acceptance evidence that was lost with the source.

The native replay connects with `valid_earlier` as its current database. It first tries to claim the original request identity:

```sql
BEGIN;
INSERT INTO orders VALUES ('t4', 'r82', 42, 22.00)
ON CONFLICT (tenant, request) DO NOTHING
RETURNING request;
```

This returns `r82`. Because this attempt inserted the order, the caller conditionally decrements capacity in the same transaction:

```sql
UPDATE sessions SET remaining = remaining - 1
WHERE tenant = 't4' AND session = 's7' AND remaining > 0
RETURNING remaining;
```

The update returns one and the caller commits. If it returned no row, the caller would roll back the newly inserted order and resolve the inconsistency. These are application branches, not a listing to send unconditionally.

The worksheet repeats the attempt. This time the insert returns no row. The caller reads `r82`, verifies customer 42 and amount 22.00, and commits without another decrement. Both attempts finish with `r80`, `r82` and one remaining place. A conflicting repeated request must be rejected rather than treated as proof that the requested work already happened.

The [transaction retry protocol](/learn/databases/relational/cockroachdb/transactions/) still applies to a rejected attempt, and an uncertain commit requires reconciling this same identity. A real replay must account for every dependent fact and external effect. This fixture tests the order/capacity pair and matching repeated identity.

## A successful restore can still lack its caller

Before the later booking, the worksheet also restored the initial full backup as database `restored`. That tiny restore took about 1.02 seconds. Its rows were `r80` at €20 and capacity two. `SHOW GRANTS ON restored.sessions` listed `admin` and `root`, with no ordinary `booking_app` read grant.

A fresh connection as `booking_app` failed with `28P01`: that user did not exist on the destination. Creating it and granting database/schema access got past connection setup, but its query still returned `42501` for missing table `SELECT` permission. Starting from the missing-user state, the complete repair gives this read-only caller its intended access:

```sql
CREATE USER booking_app;
GRANT CONNECT ON DATABASE restored TO booking_app;
GRANT USAGE ON SCHEMA restored.public TO booking_app;
GRANT SELECT ON restored.orders, restored.sessions TO booking_app;
```

A new authenticated connection can now read the expected order and capacity. UPDATE remains denied with `42501`. A separate administrator attempt to set capacity to −1 returns `23514`, showing that the restored check constraint still enforces its rule.

These results establish more than a root query of rows. They do not make a database backup carry every user's identity and privileges: that scope differs from full-cluster recovery. A real service must also check ownership, policies and external credentials. Use the application's ordinary identity for acceptance, as [Operating and securing a CockroachDB cluster](/learn/databases/relational/cockroachdb/operations/) teaches.

## Missing dependencies need repair

The larger native worksheet also tries `nodelocal://1/not-a-backup`. RESTORE fails with `58P01` because the path lacks completed latest-backup metadata. Repeating that job cannot produce a missing collection. Establish the correct URI, storage and chain first.

Other missing dependencies can be a referenced parent table, destination user, encryption key or earlier incremental layer. Skipping foreign keys can produce a restored object with a weaker contract; it needs a plan to restore and validate the missing rule.

Measure restore and application acceptance at the intended scale, with space for restored data and background work. The tiny functional run's 1.02 seconds is not a production recovery-time objective. Keep supported cross-version restore rules with the procedure; a newer backup is not automatically an older binary's downgrade path.

## Reopen after accounting for later work

Keep the former writer fenced while deciding whether to use the restored copy. List valid requests accepted after the chosen point and reconcile those that must survive. In this example, the latest incremental preserves `r82` and its consumed place; the earlier target requires both to be replayed once.

External effects need the same accounting. A restored pending payment or email job can repeat an effect that survived the database loss. Stable effect identities and downstream reconciliation belong in the plan, as [Outboxes and database-backed jobs](/learn/databases/relational/outboxes-and-jobs/) explains. Reopen only when records, identities, effects and write authority meet the selected recovery contract.

A durable commit promises that a change will still exist after a crash. That promise is expensive if every changed table and index page must reach storage before the reply. A transaction can touch many scattered pages, and each page can contain work from several transactions.

A **write-ahead log** makes the promise cheaper. The engine records enough information to reconstruct a change, appends it to a log and makes that log durable before acknowledging the commit. Data pages can follow later. After a crash, recovery repeats the logged work that those pages are missing.

We will change a workshop catalogue price from 20.00 to 22.00. Orders such as tenant t4's o81 retain their own agreed price; this update changes the current catalogue only. PostgreSQL supplies the running model and the native restart test. The log and rollback designs of the other engines differ in consequential ways.

## Dirty pages disappear with memory

The database changes a page in its memory cache, the **buffer pool**. A page that differs from its stored copy is **dirty**. If the engine replied to COMMIT while the only copy of 22.00 remained in memory, a crash could erase an acknowledged purchase or price change.

Writing every changed page before replying would avoid that loss, but one small transaction can change a table page and several index pages. Those writes land in different places. A page can also be only partly written when power fails, leaving an invalid mixture of old and new contents.

The important boundary is between volatile state and state that survives the stated failure. A write accepted by an operating-system cache may survive a database process crash while disappearing in an operating-system crash. “Written” needs a destination and a failure domain.

## Log first, pages later

With logging, the engine appends an update record and a commit record. It writes and flushes the log through that commit before acknowledging success. The data page can still contain 20.00: the durable log is enough to rebuild 22.00.

<div data-relational-component="storage/StepFigure" data-scene="wal-commit" data-number="2" data-title="The price change with a write-ahead log" data-alt="A transaction changes the memory page, records the change in log buffers, flushes the log and replies before writing the table page." data-caption="Figure 2. PostgreSQL's modelled write path. The update record is shown waiting until commit; background or pressure-driven writes can send it sooner."></div>

Log positions increase as records are appended. PostgreSQL and InnoDB call them **log sequence numbers**, or LSNs. A changed page records its progress too. Recovery can compare page progress with the log to avoid applying a change twice.

The **write-ahead rule** also applies before an uncommitted dirty page reaches its data file: the log describing that page's changes must already be durable. Otherwise the stored page could contain a change that recovery has no means to finish or undo. Commit acknowledgement and page-write ordering are separate uses of the log.

Writing an uncommitted page does not commit its transaction. Recovery may need to hide or undo unfinished changes. PostgreSQL's visibility machinery keeps versions from uncommitted transactions invisible; InnoDB redoes physical changes and then uses undo to roll unfinished work back. Physical presence in a file and committed visibility are different facts.

## The acknowledgement can be lost after durability

Crash at three points: before the commit record is durable, after it is durable but before the caller receives the reply, and after the reply. The second case is easy to overlook.

Durable log can preserve the transaction even when the caller never heard its completion. These are model histories; the native test below covers process interruption."></div>

The caller sees a dropped connection both when the transaction vanished and when it survived. Durability cannot solve the caller's missing knowledge. [Retries when a commit reply is missing](/learn/databases/relational/conflicts-and-retries/) uses a stable request identity to recover the answer without performing the purchase twice.

The log also faithfully preserves a mistaken committed DELETE. Recovery is not an editor of business history. Undoing that mistake needs a copy from before it and a chosen replay target, taught in [backup and reconciliation](/learn/databases/relational/backup-and-restore/).

## One flush can acknowledge several transactions

A flush asks the storage stack to make writes survive the promised failure. It is often slower than appending a few bytes to memory. A single client committing one row and awaiting every reply is limited by that flush latency.

Concurrent clients can share a flush. If their commit records are all included in one durable prefix of the log, that flush makes them all durable. This is **group commit**. Batching several application changes into one transaction can also reduce flushes, provided the larger transaction still has a sensible atomic boundary and lock lifetime.

<div data-relational-component="storage/StepFigure" data-scene="group-commit" data-number="4" data-title="Several commits sharing one durable flush" data-alt="Groups of clients place commit records into successive flushes. Client count and flush time can be changed." data-caption="Figure 4. An explicit scheduling model, not a throughput benchmark. Vary clients and flush latency to see why commit latency and total commit rate are different quantities."></div>

More clients do not remove the storage latency from each request. They can raise throughput while making individual commits wait for more work. Beyond the useful concurrency, extra active transactions add queueing and resource pressure. [Connections and capacity](/learn/databases/relational/connections-and-capacity/) makes that budget explicit.

SQLite has one writer, so it does not combine independently concurrent writer transactions in this way. Application batching still matters.

## Checkpoints bound what restart must replay

A **checkpoint** records a recovery position backed by sufficiently advanced data files. Once earlier logged changes no longer need replay for crash recovery, that part of the log can be recycled, unless a backup or replication consumer still needs it.

Checkpoint work trades foreground write cost against restart work. Frequent checkpoints write dirty pages sooner and can write a repeatedly changed page many times. Long intervals reduce that work but can leave more log to replay after a crash. PostgreSQL writes checkpoints in rounds; InnoDB and SQL Server advance recovery progress through their own flushing mechanisms.

Restart also needs valid pages. A small redo record cannot reliably repair a page torn by an interrupted write. PostgreSQL normally logs a full-page image on the first change after a checkpoint. InnoDB uses doublewrite protection for page writes. Checksums detect some damage but do not themselves reconstruct a good copy. Keep torn-write safeguards and recovery-copy mechanisms distinct.

A recovery-time estimate must include detection, restart, replay, unfinished-transaction handling and cache warm-up. Dividing log bytes by a measured replay rate estimates only one part, and that rate depends on record mix and whether files remain in an operating-system cache.

## What the native restart actually showed

Our disposable PostgreSQL 18.6 server used `fsync = on` and `synchronous_commit = on`. We committed a row named `acknowledged`, stopped the server with `pg_ctl stop -m immediate`, then restarted it.

```text
database system was not properly shut down; automatic recovery in progress
redo starts at ...
redo done at ...
checkpoint starting: end-of-recovery immediate wait
database system is ready to accept connections
```

The row remained present. [The observation file](/learn/databases/relational/evidence/rl95-native-observed.json) contains the actual LSNs and log lines; [the script](/learn/databases/relational/evidence/rl90-104-native.mjs) runs and cleans up the cluster.

This is an abrupt database-process restart. The operating system and drive remained running. It demonstrates recovery on the native server, but cannot prove how the drive behaves during power loss. Storage must honour its flush contract for that wider promise to hold.

## Choose the durability domain

<table><caption>Settings and designs that change what a commit reply promises</caption><thead><tr><th>Engine</th><th>Consequence</th></tr></thead><tbody>
<tr><td>PostgreSQL</td><td>With normal durable settings, commit waits for local WAL flush. synchronous_commit = off can acknowledge before that flush while preserving crash consistency; recently acknowledged changes can disappear. fsync = off removes a broader ordering safeguard and can allow corruption.</td></tr>
<tr><td>InnoDB, MySQL 8.4</td><td>Redo durability depends on innodb_flush_log_at_trx_commit. Replication and point-in-time recovery also depend on the separate binary log and sync_binlog. A local redo promise alone does not establish the surviving binary-log history.</td></tr>
<tr><td>SQL Server</td><td>Fully durable transactions wait for log persistence. Delayed durability permits earlier acknowledgement and possible loss; it is a database/transaction contract to choose explicitly.</td></tr>
<tr><td>SQLite</td><td>The rollback journal preserves original pages before replacing them; WAL mode appends changed page frames instead. WAL with synchronous = NORMAL can remain consistent while losing recent commits after a wider crash.</td></tr>
</tbody></table>

Weaker acknowledgement can suit reconstructible counters or events retained upstream. For an order already confirmed to a customer, losing the last moments requires a business recovery path, not merely a consistency check. Define what can be lost and how it will be rebuilt before changing the setting.

Even full local durability covers only the storage that holds the log. A lost disk needs another copy. A replica adds a separate failure domain only according to what acknowledgement waits for; receipt, flush and apply are different stages. [Replicas and read routing](/learn/databases/relational/replicas-and-read-routing/) follows those stages.

**Sharding** divides ownership of data across separate write resources. One owner might hold tenant t4's orders while another holds tenant t9's. A request must find the owner of each required record, and a rule spanning owners needs coordination between them.

A distributed SQL database incorporates that routing and coordination into a SQL system. An application-sharded service performs more of those jobs itself. Both choices can spread data and write work; neither makes placement or transaction boundaries irrelevant.

Before distributing the workshop service, identify the limit. A larger single server, a better access path, less repeated application work or read replicas can solve different bottlenecks with fewer moving parts. We will route one purchase through two layouts, then make one session hot enough to expose what extra nodes cannot divide.

## Partitioning and replication answer different questions

A replica is another copy of a history. It can serve some reads or survive some failures, but it still applies that history's writes. Sharding gives different subsets different owners so their work can use different resources.

Table partitioning can divide one table into smaller local pieces without creating independent write servers. PostgreSQL monthly partitions on one server can improve retention operations and prune irrelevant months; they still share its compute, log and transaction machinery. [Table partitioning and lifecycle](/learn/databases/relational/partitioning/) owns that local choice.

A sharded system also stores routing metadata, replication progress, transaction state and often several index representations. Its operating cost is more than the sum of table bytes divided by node count.

## Choose a key from the important transaction

This routing model starts a separate fixture in which b17 does not yet exist.

Request r81 buys a seat in tenant t4's session s7. It checks and increments capacity, creates booking b17 and records order o81 with an agreed price for customer 42. For this illustration, those are three writes: seat, booking and order. Real lines, indexes and identity records add work too.

A **partition key** determines where a record belongs. A routing directory or deterministic rule maps that key to its current owner. Include the tenant in every local identity and authorise it before routing. A caller's arbitrary tenant string is not permission to use that owner's data.

In the first layout, the directory says t4 belongs to A and t9 to B. Related t4 records share A. This is **colocation**: placement keeps common operations together.

The logical SQL relationships did not change. Their placement changed one local transaction into a three-owner decision. A native distributed database may execute that transaction correctly, but still pays for routing, network exchanges and commit coordination. An application-sharded service needs an explicit supported transaction or workflow protocol.

Tenant colocation is a good candidate when most important work is tenant-local. It is not a universal rule: a single huge tenant may need several partitions, and a product's table/index encoding can affect whether similarly prefixed keys actually share ranges. Verify the implementation's colocation facilities rather than assuming equal column names imply equal placement.

## Indexes distribute work too

An index is another ordered representation of data. In a distributed engine, its entries can live in partitions different from the primary records. A global lookup can therefore be cheap to find but expensive to maintain transactionally.

Suppose a support tool receives request r81 without a tenant. Tenant-local indexes cannot identify its owner directly. One option is an authoritative directory at G mapping globally scoped r81 to `(t4, o81)`. Reading the order touches G, then A.

If request identities are only unique within a tenant, the support interface should require that tenant or use a separate globally unique reference. A random identifier can make accidental collisions unlikely; it does not enforce a global business namespace across independent unique indexes.

The same issue appears with a globally unique booking code. A local unique index on each shard can accept the code once per shard. Enforce it at one owner, use an engine's coordinated global uniqueness facility, or change the business rule to tenant-local uniqueness. A scatter SELECT followed by uncoordinated inserts remains a race.

Secondary indexes can also turn a local insert into multi-partition work. Count them when modelling a transaction's network path. An apparently well-colocated primary key is not enough if every write updates a remote global index.

## Ranges, hashes and the largest tenant

Range partitioning preserves neighbouring keys, making scans and locality useful. An increasing key can also put every new insert into the last active range. Hashing spreads many distinct keys, but destroys some useful neighbourhood and can make range queries scatter.

Hashing tenant IDs distributes many tenants; it does not split t4. Hashing each order can split t4's inserts, but a customer-order query or session transaction may now reach many owners. A compound key can preserve an operational grouping, such as tenant and session, while distributing different sessions.

Test skew in work as well as bytes. A thousand quiet tenants can occupy more storage than one tenant whose popular workshop produces most writes. Moving the hot tenant to a dedicated shard can isolate neighbours; subdividing it requires a key that divides its actual independent work.

For s7's capacity 2, two seat identities can make claims independently unique. They do not allow three seats, and a caller must not create arbitrary seat numbers. For large quotas, preallocated rights can trade some immediate global flexibility for local progress. The allocation protocol must preserve the total and recover stranded rights; this is a changed invariant design, not an automatic effect of sharding.

The [native hot-row exercise](/learn/databases/relational/connections-and-capacity/) shows the original serial limit directly: more contenders increased waits without materially raising throughput.

## Global queries need a result contract

A tenant-specific query can route to its owner. A global report may send partial aggregation to all owners and combine the results. For a global newest twenty orders, each owner can supply candidates under the same total ordering, then a coordinator merges them. Slow or unavailable owners affect completeness.

The time meaning matters as well. A total from A at one moment and B at another is not automatically a consistent snapshot. A cross-shard transfer can be counted twice or omitted if its sides are read across different cuts. [Time, snapshots and distributed reads](/learn/databases/relational/distributed-reads/) teaches the shared read boundary.

If the application accepts a lagged analytical copy, define its refresh and completeness contract. Moving reports off the transactional cluster can be useful without changing transactional placement, but adds another copy to maintain. Avoid turning every global report into a strong multi-partition transaction when its reader does not need that guarantee.

## What the implementation takes on

Application sharding can preserve a simple local engine per owner, but the service owns routing changes, global identity, cross-shard operations, migrations and recovery. Citus extends PostgreSQL with distribution and colocation facilities whose supported query and transaction forms matter. CockroachDB maps SQL data and indexes into replicated ranges and supplies cross-range transactions. Spanner combines distributed placement, replicated storage and its own transaction/time machinery.

A standard PostgreSQL primary with physical replicas, MySQL InnoDB replica setup, SQL Server availability group or embedded SQLite database does not become a horizontally partitioned SQL transaction service merely because it has copies. Extensions and hosted products can supply broader facilities; state which component owns the guarantee.

The decision to distribute is defensible when representative work exceeds a credible single-owner design, the chosen key spreads that work, and the resulting coordination and operating costs fit the service. Include failover, backup, schema change and rebalancing in that test, rather than testing only a healthy scatter-free read.

## Inspect and vary the routing model

[The executable model](/learn/databases/relational/evidence/rl105-109-models.mjs) calculates the two layouts above and the directory path. [RL105's history](/learn/databases/relational/evidence/rl105-model-observed.json) lists every routed record. It does not run an engine or measure a network.

Change the owner function from tenant to `(tenant, session)` and list which rows each common operation needs. Which query becomes cheaper, and which loses locality? Add a global uniqueness entry and count the additional authority. These variations reveal placement costs before a real cluster benchmark.

[CockroachDB keys, ranges and replication](/learn/databases/relational/cockroachdb/keys-and-ranges/) provides a concrete implementation; [transactions across partitions](/learn/databases/relational/distributed-transactions/) follows the atomic decision once two owners are unavoidable.

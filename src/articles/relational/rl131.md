A major CockroachDB upgrade changes two versions. Each node starts a new executable, while the cluster initially retains its older logical version. That interval lets supported old and new binaries coexist. Finalisation then enables the new cluster version and its migrations, closing the path back to the former major version.

Those are separate milestones. Seeing the new binary on every node does not prove that the upgrade has finished. Seeing an application query succeed once during mixed versions does not prove that every client, job and schema assumption is compatible.

This article follows an actual three-node TLS rehearsal from **25.3.7 to 25.4.17** on macOS ARM64. It preserves one workshop session and a request-keyed order through a prefinalisation return, then deliberately tries the old binary after finalisation. It is evidence for this transition and dataset, not a recommendation to deploy these versions or a test of independent regional failure.

## Keep a supported return available before replacing binaries

The starting cluster had three nodes running 25.3.7. The native record pinned both executable builds and checked the logical version:

```sql
SHOW CLUSTER SETTING version;
```

```text
version
25.3
```

Before restarting a node on the target version, the rehearsal disabled automatic major-version finalisation:

```sql
SET CLUSTER SETTING cluster.preserve_downgrade_option = '25.3';
```

The setting preserves the older logical compatibility boundary while the binary transition is evaluated. It does not guarantee that any arbitrary source and target versions can coexist. Check the exact release's supported path, required source patches and release notes first. This rehearsal uses the next major version and records the actual source and target patches.

A return plan also needs a healthy cluster. Confirm replication and capacity before taking one node out, ensure application connections can reach surviving nodes, and preserve a tested recovery copy outside the installation being changed. A rolling procedure temporarily removes one node's resources; if that pushes the others into overload, an otherwise valid upgrade can still break the service.

## Replace one node and prove what changed

The worksheet stopped node 1, restarted its existing store with the 25.4.17 binary, and waited for it to answer. It then used node status rather than inferring cluster state from the CLI's own version:

```text
node | binary
1    | v25.4.17
2    | v25.3.7
3    | v25.3.7
```

A 25.4.17 CLI can talk to a cluster containing old servers. Its version string identifies the client executable; per-node status identifies the servers. `SHOW CLUSTER SETTING version` identifies the logical compatibility state. Keep all three distinct during a rolling change.

The application probe read session `s7`, whose remaining capacity was two, then inserted request `upgrade-r1` for tenant `t4`, customer `42`, amount €20. The insert committed while the cluster used mixed binaries.

This probe proves that particular read and write survived the mixed-version stage. A real acceptance workload should also cover transaction retries, prepared queries, privileges, background jobs and the schema features the service actually uses. Keep new-version-only behaviour out of application traffic while return remains a requirement.

## Test the return before relying on it

The worksheet stopped node 1 again and restarted its same store with 25.3.7. The connection reported the old server version, and querying the request identity returned:

```text
request
upgrade-r1
```

The application write was preserved. This matters because a binary return is useful only if it preserves the accepted work, not merely if a process starts.

The rehearsal then restarted node 1 on 25.4.17 and upgraded nodes 2 and 3 one at a time. After each restart, the node had to rejoin and the application query had to return. Node status eventually showed all three target binaries. The logical version still returned `25.3`, because the preservation setting remained active.

Pause here for the acceptance decision. A schema or client problem discovered at this point can still use the documented return procedure for this supported pair. A problem that requires restoring an older backup has a different data-loss and reconciliation contract, even before finalisation. [CockroachDB backup and recovery](/learn/databases/relational/cockroachdb/backup-and-restore/) follows that boundary.

## Finalisation is work, not a version-label edit

Only after those checks did the rehearsal release the preservation setting:

```sql
SET CLUSTER SETTING cluster.preserve_downgrade_option = '';
```

The setting command returned before the logical upgrade finished. Repeated observations first showed `25.3`, then intermediate values such as `25.3-upgrading-to-25.4-step-008`, then `25.4`. Those intermediate strings are observations of this build's internal progress, not stable application interfaces.

```sql
SHOW CLUSTER SETTING version;
SELECT count(*) FROM workshop.orders;
```

```text
version: 25.4
orders:  2
```

The two orders were the initial `r80` and the accepted mixed-version request. The logical version and data probe together established completion for the rehearsal. They did not make the earlier backup, credentials or rollback instructions automatically compatible with future changes.

A separate deliberately small-memory run started nodes with `--max-sql-memory=64MiB`. Finalisation stalled at step 008. Its retained log names the failing internal job and reports:

```text
failed to ingest index entries during backfill:
not enough memory available to create a BulkAdder
HINT: Try setting a higher --max-sql-memory.
```

The full excerpt records a request for 33,554,432 bytes with 33,646,592 already allocated and no bytes remaining in that budget. The next full rehearsal used 256 MiB of SQL memory per node and reached the final stable version. That repair addresses the observed capacity failure; it is not a production minimum-memory recommendation.

This is why finalisation needs resource and job evidence alongside version polls. The workshop's small foreground query could succeed while internal schema work could not obtain its buffer. Waiting longer without changing that budget would not explain or repair the recorded rejection.

Do not respond to a slow finalisation by assuming the old binary remains safe. Compatibility changes can already have begun before the final stable version string appears. Follow the pinned release's documented gate and recovery procedure; an intermediate state is not a user-defined rollback window.

## The old binary cannot read the finalised store

After the cluster reached `25.4`, the worksheet stopped node 1 and deliberately tried its former 25.3.7 executable against the same store. It exited with code 2. The recorded storage error included:

```text
pebble: database "…/node1" written in unknown format major version 26
```

That is a storage-format number, not the CockroachDB release number. The old executable did not understand the store's newer representation. Changing the filename of the executable, retrying the start or restoring the preservation setting cannot teach it the missing format.

The worksheet returned the node to the target executable and rejoined it. In a real post-finalisation incident, prefer a supported forward repair when it preserves accepted work. If recovery requires a pre-upgrade backup, restore into a compatible isolated environment, account for every later accepted request and effect, and decide which can be reconciled before returning authority. Do not treat “use the old cluster again” as an empty deployment switch once it lacks new writes.

## Keep the upgrade decision tied to evidence

A useful upgrade record names the executable on every node, the logical cluster version, preservation setting, relevant job state, application results and the recovery copy tested. It should also identify the last supported return point and what accepted work exists after it.

[Operating and securing a CockroachDB cluster](/learn/databases/relational/cockroachdb/operations/) owns steady membership and identity. [CockroachDB schema jobs under load](/learn/databases/relational/cockroachdb/schema-changes/) explains a failed DDL job. Neither substitutes for this upgrade's binary/logical gate: the decisive result is the same store accepting the old executable before the gate and rejecting it afterwards.

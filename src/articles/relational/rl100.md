A schema is an agreement between stored facts and their callers. Changing it while a service runs means changing that agreement while old application servers, workers and reports can still be using it. A quick rename can break them even when the database finishes in milliseconds.

A live migration therefore has two moving populations: existing rows and continuing writers. A backfill transforms the earlier population; a compatibility rule keeps new changes correct. Finishing either population alone is not completion.

We will rename an order's agreed amount from `price_cents` to `amount_cents`, preserving its meaning and integer units. Tenant t4's order o81 stays priced at 4,000 cents. The migration must not substitute today's catalogue price. PostgreSQL is the native example; the sequence is general, while DDL locks and online operations are engine-specific.

## Expand before changing callers

A direct rename removes the name release A still reads and writes. Instead add the nullable new column, then establish an explicit source of truth. During this first stage, `price_cents` remains authoritative. New readers can fall back to it while historical rows remain uncopied.

A database trigger can maintain the one-way copy for old writers, including scripts that the application deployment does not control. Another design can use an application API with verified complete coverage. Uncoordinated dual writes from two sources are not a rule: decide which value wins when a caller supplies conflicting amounts.

The native fixture uses numeric row IDs 10 and 20 so a late ID 5 makes cursor behaviour visible. Those are local fixture IDs; o81 remains the business example.

```sql
CREATE TABLE migration_order (
  tenant text, id integer,
  price_cents integer NOT NULL,
  amount_cents integer,
  PRIMARY KEY (tenant, id)
);
INSERT INTO migration_order VALUES
  ('t4', 10, 4000, NULL), ('t4', 20, 6000, NULL);
```

## A tiny ALTER can become a large wait

Adding a nullable column without a rewriting expression can be cheap once it obtains its schema lock. Obtaining that lock is another matter. A long transaction may keep a table lock even after its SELECT finishes.

In our PostgreSQL 18.6 drill, A opened a transaction and read `migration_order`. B tried to add a nullable `note` column with `lock_timeout = '100ms'`. It failed with `55P03`, lock timeout. After A rolled back, the same addition succeeded.

Bound lock acquisition and statement duration separately, with budgets chosen for the service. On timeout, roll back the failed transaction, inspect the blocker and retry with a limit and delay. Repeated immediate retries can repeatedly recreate the lock queue. Increasing a timeout does not remove the blocker.

Separate stages into committed operations when their lock behaviour requires it. Adding a constraint with a lighter later validation scan loses much of that benefit if the initial stronger lock is kept inside one transaction through the entire scan. Concurrent index builds have their own transaction and failure-cleanup rules.

A three-row trial says little about a table rewrite's duration, log volume or replica lag. Determine whether the exact subcommand and expression rewrite data in the selected engine and release, then test on a representative copy.

## Copy bounded batches from the current target row

A backfill should restart after interruption without redoing completed work or overwriting a newer value. One PostgreSQL pattern selects a bounded candidate set, then repeats the eligibility test in the UPDATE:

```sql
WITH batch AS (
  SELECT tenant, id FROM migration_order
  WHERE amount_cents IS NULL
  ORDER BY tenant, id
  LIMIT 100
  FOR UPDATE SKIP LOCKED
)
UPDATE migration_order o
SET amount_cents = o.price_cents
FROM batch b
WHERE (o.tenant, o.id) = (b.tenant, b.id)
  AND o.amount_cents IS NULL
RETURNING o.tenant, o.id;
```

Read the amount from the row being changed. A worker that reads 4,000 into application memory, waits while an old writer changes the amount to 4,500, then unconditionally stores its remembered 4,000 has manufactured disagreement. A null guard and a maintained writer invariant prevent that stale overwrite in the appropriate transaction protocol.

`SKIP LOCKED` is useful for distributing independent eligible work, but an empty or short batch can leave eligible rows locked by other workers. This query locks candidates as it selects them; those locks then protect them through the UPDATE. The number returned proves only what this batch changed. In the native drill, an eligible row held by another connection made the displayed batch return empty. After that connection released its lock, the next batch returned the row and copied it.

Commit each batch before recording its durable progress. Tune batch size by transaction time and resource use, rather than row count alone: wide rows and indexed changes can write very different amounts of log. Pause or reduce workers when foreground latency, replica lag, cleanup backlog or disk pressure grows.

## The last key is not a completeness proof

A key cursor avoids repeatedly scanning already processed rows. It must not become the definition of correctness. An imported row can arrive with a smaller ID, or a writer can make an earlier row eligible again.

Our native drill copies IDs 10 and 20, then inserts ID 5 with a missing new amount. A continuation query requiring `id > 20` returns no row. A whole-table comparison finds ID 5.

The repair has two parts. First establish that all continuing writes preserve the new representation. Then repair and verify the old population. Otherwise a zero count is merely a moment in which the next uncovered writer has not yet run.

For this drill, a BEFORE INSERT OR UPDATE trigger sets `NEW.amount_cents := NEW.price_cents`. Its unconditional direction is deliberate: old remains authoritative, and no new-only writer is enabled yet. Installing the rule takes the engine's DDL coordination; previously running work must be considered at that boundary.

After installing it, we sweep all disagreements. An old writer changes ID 10 to 4,500 and inserts ID 3 at 8,000. The trigger maintains both representations. The global check returns zero:

```sql
SELECT count(*) AS mismatch
FROM migration_order
WHERE amount_cents IS DISTINCT FROM price_cents;
-- 0
```

`IS DISTINCT FROM` includes a missing new value; `<>` alone would evaluate to unknown for NULL and miss it. Equality matters too: non-null 4,000 is wrong when the authoritative value is 4,500.

## Turn the completion condition into an enforced rule

PostgreSQL can add a CHECK as `NOT VALID`, enforcing it for future changes while deferring the scan of existing rows. Validate in a separate stage:

```sql
ALTER TABLE migration_order
ADD CONSTRAINT amount_matches
CHECK (amount_cents IS NOT NULL AND amount_cents = price_cents)
NOT VALID;
-- Commit this short stage, with bounded lock wait.

ALTER TABLE migration_order
VALIDATE CONSTRAINT amount_matches;
```

The native run's validation succeeded, and the catalogue reported `convalidated = true`. That supplies a maintained completion condition rather than a writer's optimistic counter. A check requiring only non-null would prove presence but not the correct copy.

This equality constraint belongs to the old-authoritative compatibility phase. Before allowing new-only writes, change the rules deliberately: require the new column, retire the old-authoritative trigger and either maintain reverse compatibility or declare that old readers are no longer valid. Leaving the earlier trigger enabled would overwrite a new-only update with the old amount.

## Cross the rollback boundary deliberately

Deploy new readers everywhere before enabling writes that omit the old representation. Include exporters, support scripts and delayed jobs in “everywhere”. An unused old column is not evidence that nobody still reads it.

If rollback to A is required, every new write must keep A's expected representation current. If C is allowed to write only new values while old stays stale or NULL, rolling application binaries back to A is no longer safe. Restoring old readers would first need a controlled reverse backfill and compatible write rule.

Remove the old column, trigger and helper objects only after the old interface is retired and the rollback contract permits contraction. Unexpected dependencies deserve investigation; `CASCADE` can hide a missed report by deleting it. Retain migration evidence, accepted counts and the reconciliation method for longer than the deployment's immediate rollback window.

## DDL portability changes the operation

InnoDB distinguishes INSTANT, INPLACE and COPY operations, with metadata locks and concurrency restrictions even for “online” work. Ask for an explicit supported algorithm/lock contract when silent fallback would violate the budget.

SQL Server's online index operations and resumability depend on the operation, edition and version, and still require locking phases. SQLite implements a limited set of direct ALTER operations; other changes require its documented table-rebuild procedure and single-writer coordination. PostgreSQL's NOT VALID and concurrent-build syntax cannot be assumed on either.

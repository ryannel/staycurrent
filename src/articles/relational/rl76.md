A **relational database** stores data in tables. Each row describes one thing, such as a customer or a booking, and each column holds one part of it, such as the customer’s name. Rows in different tables refer to one another through values they share. A booking can carry a customer’s identifier, and a query can use that identifier to find the customer’s name.

The tables give us several ways to ask about the same data. We can list a customer’s bookings, count the bookings for a session, or find sessions with places left. We don’t need to store a separate copy of the data for each question. Most relational databases use **SQL**, a language for asking those questions and changing the stored rows.

They also let us group changes in a **transaction**. Accepting a purchase might consume a place and create an order. Both changes should happen, or neither should. Transactions make relational databases useful for bookings, orders, accounts and other applications where several facts have to agree.

The examples follow one workshop service. Ada has booked a repair class, and two places remain. We’ll read her booking, accept another purchase, then change where the service runs: first on one device, then behind several application servers, then across regions. The tables can stay much the same while the database we choose changes.

## Tables, keys and joins

The service keeps customers, sessions and bookings in three tables. A **tenant** is one workshop organiser using the service; this organiser is `t4`. Ada is customer 42, and her booking is `b17` for session `s7`. Each card below shows one row from its table; the labels are its columns.

The booking stores 42 rather than Ada’s name. If Ada changes her name, one customer row changes, and every booking still points to her. Copying her name into every booking would leave us with several rows to update and the possibility of two different names for one customer.

The pair `(tenant, customer)` is a **key**: values that identify one customer row. Customer 42 in another tenant could be someone else, so 42 alone isn’t enough. The sessions table has its own key, `(tenant, session)`.

A **foreign key** is a rule requiring a reference to match an existing row. A foreign key from the booking’s `(tenant, customer)` to the customers table would reject a booking for a customer who doesn’t exist. The database checks the rule whoever sends the write, including a maintenance script.

To show Ada’s booking, the application sends this SQL query. Follow the matches from the middle card in Figure 1 to the two outside it:

```sql
SELECT c.name, s.title
FROM bookings AS b
JOIN customers AS c
  ON c.tenant = b.tenant AND c.customer = b.customer
JOIN sessions AS s
  ON s.tenant = b.tenant AND s.session = b.session
WHERE b.tenant = 't4' AND b.booking = 'b17';
```

| name | title |
| --- | --- |
| Ada | Repair basics |

The query starts from booking `b17`. Each `JOIN` adds the row whose values match its `ON` condition. The first finds Ada; the second finds Repair basics. `SELECT` chooses the two columns to return, and `WHERE` chooses the booking. The letters `b`, `c` and `s` are short names for the tables.

Combining rows this way is a **join**. It produces a result for this query; it doesn’t store another copy of Ada’s name in her booking. [Joins and the meaning of a result row](/learn/databases/relational/query-results/) follows what happens when more than one row matches.

Some copies do belong in the stored data. An order should keep the price the customer agreed to pay, even after the workshop’s current price changes. That amount describes the purchase, so it belongs on the order. [Relations, keys and normalisation](/learn/databases/relational/modelling/) develops how to decide which facts belong together.

## Transactions

The next purchase consumes one of the two remaining places and creates an order for request `r81`. Follow just those two writes. If the application reduces the places from two to one, then crashes before it inserts the order, a place has disappeared with no purchase to explain it. Reversing the writes leaves an order that consumed no place.

Put both writes in one transaction. `BEGIN` starts it. `COMMIT` makes its changes permanent; `ROLLBACK` discards them. If the application loses its connection before it commits, the unfinished changes are discarded too.

Compare the stored facts before and after. Then choose *Roll back* to see the other ending. This starts again from the original state; a rollback cannot undo a transaction that has already committed.

Committing kept one place and an order for request `r81`. Rolling back left two places and no order. Now commit after only one statement. The place is consumed with no order, just as before: a transaction keeps together the writes we give it, so the application must include both before it commits.

There is another problem when customers buy at the same time. Two requests could both read “one place left” and each sell it. The purchase must check for a place as part of taking it. This SQL shows the shape of that operation:

```sql
BEGIN;
UPDATE sessions
SET remaining = remaining - 1
WHERE tenant = 't4' AND session = 's7' AND remaining > 0;
-- Continue only if exactly one row changed.
INSERT INTO orders (tenant, request, customer, amount)
VALUES ('t4', 'r81', 42, 20.00);
COMMIT;
```

The `UPDATE` changes a row only while `remaining > 0`. The application reads the number of rows it changed. If that is zero, it sends `ROLLBACK` and reports that no place was available. Only after a successful update does it insert the order and send `COMMIT`. The comment is an instruction to the application; SQL doesn’t branch there by itself.

Start with one place and two buyers. At PostgreSQL’s default isolation level, the first buyer’s `UPDATE` changes one to zero and holds a lock on the session row until its transaction ends. The second buyer’s `UPDATE` waits for that lock. When the first buyer commits, PostgreSQL checks the second buyer’s condition against the changed row: zero is not greater than zero. No row changes, so the application rolls back that purchase without inserting an order.

Other engines and isolation settings may instead return an error requiring the competing transaction to retry. Checking and taking the place must remain one protected operation; after the first purchase commits, a retry has no place left to take.

This is one small rule over one session row. Rules involving several rows need more care about what simultaneous transactions can see and change. That protection is called **isolation**, and [Transactions and isolation](/learn/databases/relational/transaction-boundaries/) develops it.

A connection lost during `COMMIT` leaves the application unsure whether the purchase succeeded, so `r81` must remain the same request identity when it retries. A unique key on `(tenant, request)` helps prevent a second order; [Handling conflicts and uncertain outcomes](/learn/databases/relational/conflicts-and-retries/) gives the complete retry procedure.

An email can’t be rolled back with a database row. [Outboxes and database-backed jobs](/learn/databases/relational/outboxes-and-jobs/) shows how to record the work to send in the transaction and send it afterwards.

## Embedded databases and database servers

So far, the application has sent SQL without saying where the database runs. Suppose the organiser first uses a desktop application, on one laptop, and needs it to work without a network connection.

**SQLite** runs inside the application process and reads a local database file. There is no database server to start or connect to. The application can use tables, joins and transactions while the laptop is offline. It still needs a way to back up that file and recover from a lost laptop.

Now put the application on a website. Customers’ browsers send requests to an application server, and that server sends the SQL. SQLite can still work here: the application server owns the local file, and browsers never open it directly.

SQLite allows one writer at a time per database file. If each purchase finishes quickly, writers can take turns. If purchases arrive faster than they finish, they queue, and customers wait. The number of web visitors alone doesn’t tell us which case we have; the duration and overlap of the writes do.

The service grows to several application servers, each needing the same bookings. A **database server**, such as PostgreSQL, MySQL with InnoDB, or SQL Server, is a natural next design. Each application server connects to it and sends SQL. The database server owns the files and coordinates the connections, including competing purchases of the last place. Sharing a SQLite file directly between machines over a network filesystem introduces different locking and reliability problems.

| Design | Where SQL runs | What coordinates writes |
| --- | --- | --- |
| Desktop app with SQLite | Inside the desktop app | SQLite, one writer at a time for its file |
| One application server with SQLite | Inside the application server | SQLite, one writer at a time for its file |
| Several application servers using PostgreSQL, MySQL or SQL Server | In the database server | The database server, across its client connections |

A server adds work: connections, access controls, upgrades, monitoring and backups. A **managed database** transfers some of that work to a provider. Exactly which work depends on the service. A provider may take backups for us, but we still need to know whether a restore brings back a working booking application. The schema, transactions and expensive queries remain ours to design.

## Distributed SQL and regional failures

Several application servers can share one database service in one region. The next requirement changes that design: the workshop must keep accepting purchases even when an entire region is unavailable, without losing confirmed orders.

Now the database needs copies outside the failed region and a way to agree which purchases count. A distributed SQL system such as **CockroachDB** can coordinate transactions across machines and keep replicas of the data. Its placement and failure settings must match the outage we intend it to survive. A conventional server with replicas is another design to examine; a second copy by itself doesn’t establish how failover works or which confirmed writes survive.

Agreement takes communication. If copies in different regions must acknowledge a purchase before it commits, that purchase waits for messages between those regions. Putting each customer near a server doesn’t remove the wait to agree over the last place in the same session.

The new requirement has therefore bought failure survival at a cost in latency, money and operating work. Measure purchases both with every region healthy and with one unavailable. [Sharding and distributed SQL](/learn/databases/relational/partitioning-and-sharding/) follows the data placement and transaction choices; [Replication and failover](/learn/databases/relational/replicas-and-failover/) follows what happens to confirmed writes.

## Choosing an implementation

The workshop has now produced three different starting choices. One offline device points towards SQLite. Several application servers sharing bookings point towards a database server. Continued writes through a regional outage require a design that demonstrates that survival.

Within the server choice, PostgreSQL, MySQL/InnoDB and SQL Server can all be candidates. Start with the one the team can already operate, then look for a requirement it cannot meet. For this comparison, the versions are PostgreSQL 18, MySQL 8.4 and SQL Server 2025. SQL Server’s edition and the terms of a hosted service affect the facilities and limits available.

Turn the requirements into a small trial. The table is a worksheet for the workshop service: fill in the quantities and limits before running it.

| Requirement | What to try | What would fail the choice |
| --- | --- | --- |
| Never sell more places than remain | Start with two places and send overlapping purchases | Three accepted orders, a lost place or a retry that creates another order |
| Serve the expected busy period | Set the expected purchases per second, largest organiser and response-time limit; run the real queries and background work together | A growing write queue, unacceptable response times or a bill above the budget |
| Show data fresh enough for its use | State how old an organiser’s report may be; keep the capacity decision on a path that checks current availability | A report older than its limit, or a stale capacity read used to accept a purchase |
| Keep working through the required failure | State the allowed outage and confirmed-order loss, then interrupt the specified process, machine or region | Recovery takes too long, or loses orders the requirement promised to keep |
| Run this application | Use its actual driver, SQL, migrations and retry code | An unsupported operation or an error the application mishandles |
| Recover and move the data | Restore into a separate destination, sign in as the application, read the bookings and make a purchase; test the export path too | Missing records, permissions or dependencies, or no workable way to leave the service |

Run the booking query from earlier as part of that trial, but don’t stop when it returns Ada. Different databases accept different SQL, offer different extensions and handle concurrency differently. A familiar connection protocol doesn’t prove that the application’s queries and transactions behave the same way.

Other kinds of database deserve the same test. A document store can suit an application that usually reads and changes one self-contained document. Here the remaining places are shared by many purchases, so we still have to show how those purchases avoid overselling. A search service may find classes by relevance, while the booking database remains responsible for deciding whether a place was sold.

If the candidates meet the requirements at an acceptable cost, the team’s experience is a sound reason to choose among them. Record what would change that decision: more overlapping writers, a platform dependency, a recovery limit or the new requirement to survive a region. Those are reasons to revisit a database choice that can be tested.

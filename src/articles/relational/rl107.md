A distributed read needs two answers: which moment should it describe, and which replicas can safely answer for that moment? Nearby data can be old. Independently current answers from several partitions can also describe different moments.

A **consistent snapshot** provides one coherent cut through committed history. It can deliberately describe the past. **Freshness** says how that cut relates to the request and completed work. A read can satisfy one property while failing the other.

We will follow tenant t4's session s7 and order o81 across partitions. The integer timestamps below are invented ordered labels, shared by the model. They are not PostgreSQL LSNs, clock milliseconds or measured product timestamps.

## Reading each partition's latest value can mix histories

At timestamp 10, partition P has one reserved seat in capacity-2 session s7. Partition Q has no o81. Request r81 commits a transaction at timestamp 20 that increments the count to 2 and creates o81. The two changes have one outcome.

Suppose a nearby P replica can safely serve through timestamp 25, while the chosen Q replica can safely serve only through 15. Reading each one's latest value returns reserved = 2 and no o81. That pair is neither the before nor the after state of the purchase.

The read must select a common timestamp and obtain each required record as of that timestamp. Atomic commit decides whether r81 belongs to that cut; multiversion storage supplies the earlier versions. A transaction still in an unresolved state may require status lookup, waiting or recovery before the read can determine its visible effect.

A global sum or join has the same need. Adding subtotals from independent snapshots does not create a common one. The issue is easiest to see with two records, but does not disappear when the results contain millions of rows.

## A safe read frontier is a promise about the past

A replica needs more than a local clock saying 25. It must have applied the required data and know that no unresolved or future write can later change the answer at the selected timestamp.

Call that completed boundary the replica's **safe read frontier** in this model. The term is descriptive; products name and implement such boundaries differently. P's frontier is 25 and Q's is 15. A common snapshot at 15 can use both. A snapshot at 25 must wait for Q, route elsewhere or fail within its budget.

Taking the minimum of arbitrary “last message seen” timestamps would not establish that promise. A backdated write or an unresolved earlier transaction could still alter the answer. The engine's protocol must close that possibility and ensure the chosen replica has applied the associated progress.

The chosen past must also remain retained. Garbage collection can remove versions older than a configured history window. A historical query outside that window fails or needs a backup; a read timestamp is not a permanent archive. Long historical transactions can also interact with retention and cleanup budgets.

## A consistent old count cannot approve a new booking

The report at 15 is correct: one seat was reserved then. After r81 fills the session, a new caller can still read that old count from a nearby historical replica. Reusing it as current permission to insert b19 would make three bookings in capacity 2 if the write protocol performs no current invariant check.

The problem is not that the report was internally inconsistent. Its time contract was wrong for the decision. A report can tolerate “as of a little earlier”; an admission decision must coordinate with competing current reservations.

Use an atomic conditional reservation on current authority or a correctly isolated transaction that reads and changes the relevant invariant. The write can refuse after the UI optimistically displayed availability. That refusal is an ordinary business outcome. [Transactions and isolation](/learn/databases/relational/transaction-boundaries/) shows the guarded update and write-skew alternatives.

A stale display followed by a current guarded write is often a useful design. An unconditional write based on the display's earlier count is a different design. Keep the distinction in the handler rather than assuming a strong-looking historical SELECT makes every later action safe.

## Logical order and physical time are different tools

A logical counter can order events without claiming a UTC time. Physical clocks estimate real time but can disagree across machines. A timestamp scheme can combine both, using messages to carry causal progress while preserving a physical-time component.

CockroachDB uses hybrid logical timestamps together with transaction coordination and clock-offset assumptions. Its historical follower reads rely on closed timestamps and applied replication progress: a range promises not to introduce new writes at or below the closed boundary, and a follower must have applied the corresponding replicated state. Merely synchronising host clocks would not supply that promise.

A timestamp can order transactions even when its wall-time component is not an exact measurement of when a person acted. Conversely, two close physical timestamps do not prove one operation observed the other's result. Follow the product's ordering and visibility contract rather than treating every timestamp column as a causal guarantee.

Application-maintained `updated_at` values are especially weak for this job. They may be supplied by clients, have coarse resolution, change outside commit order or omit updates. They can serve a business purpose without constituting a database-wide safe snapshot frontier.

## Spanner's bounded-clock approach

Spanner supplies a useful contrast. Its TrueTime interface exposes an interval containing current absolute time, under the service's clock infrastructure and uncertainty bounds. Its serializable transaction contract provides external consistency: the serial order respects externally observed ordering of completed transactions.

A simplified commit-wait sketch shows how a bounded interval can help. Suppose the current interval is `[99, 103]`, in abstract units. Choose a commit timestamp at least 103. Before acknowledging, wait until the earliest possible current time is greater than that timestamp. Once it reaches 104, the acknowledgement can no longer precede the chosen timestamp in real time.

The interval and its maintained bound matter. Replacing it with an ordinary host timestamp plus an assumed small error would remove the premise. The mechanism also does not replace replication or atomic commit. It helps select and acknowledge timestamps with a real-time ordering property while those other protocols settle the transaction.

Do not turn this example into a claim that every distributed SQL system uses specialised clocks or waits this way. CockroachDB's hybrid logical clocks, uncertainty handling and closed timestamps form a different design. An application-sharded set of PostgreSQL or InnoDB servers has no automatic shared timestamp authority just because every host runs time synchronisation.

## Choose the read contract at the interface

A useful contract names the result's moment and failure behaviour. “Current” may mean a strong read that includes work completed before the operation begins, under the product's guarantee. “Read my purchase” may use causal/session progress. “As of T” selects one historical cut. “No more than Δ old” requests bounded staleness.

A network or replica outage can make the strongest available contract slower or temporarily unavailable. A caller may choose to accept an older display, but changing the contract should be explicit. A fallback that quietly turns a current booking decision into a historical one can destroy correctness while improving the latency graph.

PostgreSQL and SQL Server local snapshots supply coherent views within their supported database scope. InnoDB consistent reads have their own transaction/snapshot rules. SQLite WAL readers see a local earlier view. None of these facts alone establishes a common cut across independently managed servers. The distributed implementation must own that additional coordination.

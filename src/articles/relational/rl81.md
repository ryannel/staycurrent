A query combines stored facts into the answer an application needs. An order receipt might need an order, its customer and its lines. A session list might need every session, including those nobody has booked. SQL can express both, but the meaning of one output row must come from the question.

That meaning is the result's **grain**. One receipt row can mean one order line. One dashboard row can mean one session. If a join silently changes that grain, a later total can be wrong even though every expression is valid SQL.

We will follow workshop order `o81` in tenant `t4`. It has two lines and eventually two payment records. Keeping those small records visible makes the multiplication countable.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/learn/databases/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Read one table first

```sql
CREATE TABLE lines (
  tenant_id text, order_id text, line_no integer,
  description text, quantity integer, agreed_price numeric(10,2),
  PRIMARY KEY (tenant_id, order_id, line_no)
);
CREATE TABLE orders (
  tenant_id text, order_id text, customer_id integer,
  PRIMARY KEY (tenant_id, order_id)
);
CREATE TABLE customers (
  tenant_id text, customer_id integer, name text,
  PRIMARY KEY (tenant_id, customer_id)
);
INSERT INTO customers VALUES ('t4',42,'Ada'), ('t5',42,'Ben');
INSERT INTO orders VALUES ('t4','o81',42), ('t4','o82',42);
INSERT INTO lines VALUES
 ('t4','o81',1,'Workshop seat',2,20),
 ('t4','o81',2,'Workbook',1,5);
SELECT line_no, description, quantity * agreed_price AS amount
FROM lines
WHERE tenant_id = 't4' AND order_id = 'o81'
ORDER BY line_no;
```

```text
line_no | description   | amount
1       | Workshop seat | 40.00
2       | Workbook      | 5.00
```

`FROM` names the input, `WHERE` chooses rows, and `SELECT` chooses and computes columns. `ORDER BY` supplies the result's order. The stored price is the amount agreed on this line; the current catalogue price has no role in this receipt.

SQL normally retains duplicate result rows. Selecting just `order_id` from these two lines yields `o81` twice. Those rows are not an error: two inputs produced them. Whether the application needs both is a question about the result grain.

## A join produces one row per matching pair

```sql
SELECT l.line_no, c.name, l.quantity * l.agreed_price AS amount
FROM lines l
JOIN orders o USING (tenant_id, order_id)
JOIN customers c
  ON c.tenant_id = o.tenant_id AND c.customer_id = o.customer_id
WHERE l.tenant_id = 't4' AND l.order_id = 'o81'
ORDER BY l.line_no;
```

```text
line_no | name | amount
1       | Ada  | 40.00
2       | Ada  | 5.00
```

Each line matches one order, then that order matches one customer. The customer key proves the second join cannot multiply a line. If the query matched customers on `customer_id` alone, both tenants' customer `42` would match and each line would appear twice, once with Ada and once with Ben.

A foreign key proves existence only when enforced, while a unique key proves at most one match. A many-to-one join preserves the left side's row count only when every left row actually finds that one match. An inner join drops rows with no match. Even a correctly declared nullable reference can therefore drop rows.

Avoid `NATURAL JOIN` in maintained application SQL: it automatically joins every identically named column, so adding a column can change the query's meaning. `USING` explicitly names shared key columns. `ON` handles different names and more general conditions.

## Two independent children multiply each other

```sql
CREATE TABLE payments (
  tenant_id text, payment_id text, order_id text, amount numeric(10,2),
  PRIMARY KEY (tenant_id, payment_id)
);
INSERT INTO payments VALUES ('t4','p1','o81',20);
```

Joining lines to payments on the order currently produces two pairs. Add a second payment:

```sql
INSERT INTO payments VALUES ('t4','p2','o81',25);
SELECT l.line_no, p.payment_id, l.quantity * l.agreed_price AS line_amount
FROM lines l JOIN payments p USING (tenant_id, order_id)
WHERE l.tenant_id = 't4' AND l.order_id = 'o81'
ORDER BY l.line_no, p.payment_id;
```

```text
line_no | payment_id | line_amount
1       | p1         | 40.00
1       | p2         | 40.00
2       | p1         | 5.00
2       | p2         | 5.00
```

<div data-relational-component="relational-design-tools/JoinPairs" data-number="1"></div>

The result grain is line/payment pair, not line and not order. `SUM(DISTINCT line_amount)` is not a general repair: two legitimate €20 lines would collapse to one. `SELECT DISTINCT` after an aggregation is too late; the repeated values already contributed.

Bring each independent child to the required grain before combining them:

```sql
WITH purchased AS (
  SELECT tenant_id, order_id, sum(quantity * agreed_price) AS total
  FROM lines GROUP BY tenant_id, order_id
), paid AS (
  SELECT tenant_id, order_id, sum(amount) AS total
  FROM payments GROUP BY tenant_id, order_id
)
SELECT o.order_id, COALESCE(l.total,0) AS purchased,
       COALESCE(p.total,0) AS paid
FROM orders o
LEFT JOIN purchased l USING (tenant_id, order_id)
LEFT JOIN paid p USING (tenant_id, order_id)
WHERE o.tenant_id = 't4'
ORDER BY o.order_id;
```

```text
order_id | purchased | paid
o81      | 45.00     | 45.00
o82      | 0         | 0
```

Each summary has at most one row per order, so their join cannot multiply orders. `COALESCE` deliberately interprets no lines or payments as zero here. [Aggregates, windows and ordered results](/learn/databases/relational/aggregates-and-windows/) develops grouping and empty inputs.

## An outer join preserves missing matches

Sessions `s7` and `s8` exist; only `s7` has booking `b17`. The dashboard should list both, showing confirmed bookings if present.

```sql
CREATE TABLE sessions (tenant_id text, session_id text);
CREATE TABLE bookings (tenant_id text, booking_id text, session_id text, status text);
INSERT INTO sessions VALUES ('t4','s7'), ('t4','s8');
INSERT INTO bookings VALUES ('t4','b17','s7','confirmed');
SELECT s.session_id, b.booking_id
FROM sessions s
LEFT JOIN bookings b
  ON b.tenant_id = s.tenant_id AND b.session_id = s.session_id
 AND b.status = 'confirmed'
WHERE s.tenant_id = 't4'
ORDER BY s.session_id;
```

```text
session_id | booking_id
s7         | b17
s8         | NULL
```

Figure 2 adds a cancelled booking for `s8`. Move the confirmed predicate, then remove that booking and compare the result. The stored bookings stay visible while the constructed rows change.

<div data-relational-component="relational-design-tools/OuterJoin" data-number="2"></div>

A left join first finds qualifying pairs. For each left row with none, it produces one row with NULLs on the right. Moving `b.status = 'confirmed'` into `WHERE` filters those constructed rows afterwards. The NULL comparison is unknown, so `s8` disappears.

Adding `OR b.booking_id IS NULL` to that `WHERE` is still not equivalent in general. If `s8` has a cancelled booking, the join found a match, so it never constructs the NULL row. The cancelled row then fails the filter. Put a condition defining an eligible match in `ON`; put a condition deciding which completed output rows to keep in `WHERE`.

## Ask about existence without creating pairs

If the application only wants orders with payments, no payment values need to join the output:

```sql
SELECT o.order_id FROM orders o
WHERE o.tenant_id = 't4' AND EXISTS (
  SELECT 1 FROM payments p
  WHERE p.tenant_id = o.tenant_id AND p.order_id = o.order_id
)
ORDER BY o.order_id;
```

This returns `o81` once, however many matching payments exist. `NOT EXISTS` with the same correlated conditions returns `o82`: no match exists. The selected `1` is irrelevant; existence asks only whether the subquery has a row.

A left join followed by `WHERE p.payment_id IS NULL` can express the same anti-join when the tested right-side key cannot be NULL in a real match. Testing a nullable payment attribute instead could misclassify an existing payment. `NOT IN` is also sensitive to NULL inside its subquery; [Values, missing data and equality](/learn/databases/relational/values/) executes that failure.

`UNION ALL` appends result rows, including repeats. `UNION` removes duplicates across the selected columns. Use the latter when the question is about distinct values, not as a general cure for an unexplained join. `INTERSECT` and `EXCEPT` express common and excluded values; support for their `ALL` variants differs by engine.

Before tuning a query, check a zero-match case, a single match and a second independent child. State the grain before and after each join, and verify it against the keys. A plan can make the wrong answer arrive faster; it cannot tell you what the result was meant to mean.

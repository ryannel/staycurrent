Pagination divides an ordered query result into manageable pieces. A person browsing recent workshop orders needs the first piece quickly. An export worker needs pieces small enough to write without holding the whole result in memory. Both need a continuation rule; they may need very different rules about changes between pieces.

An order-history screen can show a list that changes as new orders arrive. An accounts export may need every row to describe the same database snapshot. A correct cursor solves the position problem. It does not, by itself, freeze the data.

These examples use tenant `t4` and pages of two orders so the boundaries stay visible. All times are UTC and non-NULL. The PostgreSQL snapshot experiment uses two real connections.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/learn/databases/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## A page boundary needs a total order

```sql
CREATE TABLE orders (
  tenant_id text NOT NULL, order_id text NOT NULL,
  placed_at timestamptz NOT NULL, total numeric(10,2) NOT NULL,
  PRIMARY KEY (tenant_id, order_id)
);
INSERT INTO orders VALUES
 ('t4','o81','2026-10-19 09:00+00',40),
 ('t4','o82','2026-10-19 10:00+00',20),
 ('t4','o83','2026-10-19 12:00+00',30),
 ('t4','o84','2026-10-19 12:00+00',10),
 ('t4','o85','2026-10-19 12:00+00',50);
SELECT order_id, placed_at FROM orders
WHERE tenant_id = 't4'
ORDER BY placed_at DESC, order_id DESC LIMIT 2;
```

```text
order_id | placed_at
o85      | 2026-10-19 12:00:00+00
o84      | 2026-10-19 12:00:00+00
```

Three orders share noon. Ordering only by `placed_at` would leave their relative positions unspecified. Using a unique tie-breaker gives a total order within the tenant: every two rows have a definite relative position. A more precise timestamp would not guarantee uniqueness.

The IDs are stable labels here, not clocks or commit sequence numbers. Keep `ORDER BY` in every page query even when an index happens to return that order today.

## Offset counts positions in the current result

The next page can skip two rows:

```sql
SELECT order_id FROM orders WHERE tenant_id = 't4'
ORDER BY placed_at DESC, order_id DESC OFFSET 2 LIMIT 2;
```

With unchanged data this gives `o83, o82`. Now a second connection inserts `o86` at 13:00 and commits between page requests. The sequence becomes `o86, o85, o84, o83, o82, o81`. Offset two now returns `o84, o83`: the previous page's `o84` appears again. Deleting a row before the boundary can instead skip an unseen row.

Offset also makes the engine compute and discard earlier rows. A deep numbered page can therefore cost much more than an early one. For a small administrative list, or a fixed snapshot where direct page numbers are useful, that may be acceptable. It is a trade rather than inherently wrong SQL.

## A keyset cursor remembers values

Remember the last row's ordered values instead of its former position. After `(12:00, o84)`, descending order continues at pairs strictly smaller than that pair:

```sql
SELECT order_id, placed_at FROM orders
WHERE tenant_id = 't4'
  AND (placed_at, order_id)
      < (timestamptz '2026-10-19 12:00+00', 'o84')
ORDER BY placed_at DESC, order_id DESC LIMIT 2;
```

This returns `o83, o82`, with or without the new `o86`. It includes the remaining noon tie because its ID is smaller. A timestamp-only cursor using `placed_at < noon` would skip `o83`.

The supporting index is `(tenant_id, placed_at DESC, order_id DESC)`. It lets the scan seek to this tenant and boundary, then stop after a small result. [Indexes and access paths](/learn/databases/relational/indexes/) explains the order. Page parent orders before joining their lines, or `LIMIT 2` may select two lines of one order rather than two orders.

For a previous page, take the first visible row, seek to greater pairs, read in ascending order with the limit, then reverse the returned rows for display. Mixed directions need a different predicate. For `ORDER BY placed_at DESC, order_id ASC`, continuing after `(t,id)` means `placed_at < t OR (placed_at = t AND order_id > id)`, with parentheses beneath tenant and other filters. A simple tuple `<` would apply the wrong ID direction.

Nullable sort keys complicate comparisons because tuple comparisons involving NULL can be unknown. Either use required sort values, or encode the NULL region explicitly with the same placement as `ORDER BY ... NULLS FIRST/LAST`. Test entering and leaving that region.

A cursor is part of the query contract. Include an encoding version, sort values and identity, and bind it to the filter, sort direction and tenant. Validate it rather than interpolating its contents into SQL. Signing an opaque cursor can prevent alteration, but it does not replace permission checks. Request one extra row to learn whether a next page exists, then return the normal page and construct its cursor from the last returned row.

## A changing sort key can cross the boundary

After page one, another writer changes unseen `o82` from 10:00 to 14:00. It moves ahead of `(12:00,o84)`, so the next keyset page does not include it. An already-seen order moving behind the boundary can be returned twice. Deletes can remove unseen rows, and new rows behind the cursor can appear during the traversal.

An immutable placement time prevents this particular movement but does not freeze every selected value or filter. A pending-order list can lose rows when they become paid. A maximum ID or captured end time is not automatically a snapshot either: an older transaction can commit a row with an earlier assigned ID or timestamp after the boundary was captured.

For a live list, specify the intended behaviour and offer refresh from the beginning. For a fixed export, decide whether the promise is fixed membership, fixed values, or both.

## One snapshot gives the export fixed values

In PostgreSQL, an ordinary query at Read Committed sees a snapshot for that statement. Separate statements can see different committed states even inside one transaction. Repeatable Read lets ordinary reads in the transaction retain the same snapshot.

On export connection A, begin and perform the first read:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT order_id, total FROM orders
WHERE tenant_id = 't4' ORDER BY order_id LIMIT 2;
```

Now connection B commits a price correction and a new order. A's later reads still see the original order values and no new order. A fresh connection sees the correction and insert. The [two-connection record](/learn/databases/relational/evidence/rl83-native.txt) includes B's statements and both sets of results. The snapshot is established by A's first snapshot-taking statement, not merely by saying `BEGIN`.

Keep A's connection and transaction until the export completes. A database cursor can fetch successive chunks of one result:

```sql
DECLARE export_orders NO SCROLL CURSOR FOR
  SELECT order_id, total FROM orders
  WHERE tenant_id = 't4' ORDER BY placed_at, order_id;
FETCH FORWARD 2 FROM export_orders;
FETCH FORWARD 2 FROM export_orders;
CLOSE export_orders;
COMMIT;
```

`FETCH` sizes control delivery, not how much work the plan must do before producing its first row. A full sort may still retain substantial state. A non-holdable cursor closes when its transaction ends; returning its connection to a pool early breaks the export's lifetime. [SQL at the application boundary](/learn/databases/relational/application-sql/) follows that ownership.

Long snapshots have costs. PostgreSQL must retain row versions they might still read; other engines retain undo or version-store state. A slow destination can therefore make a database export costly long after the query first answered. Bound duration, monitor retained history and cancel abandoned exports. [Row versions, storage and cleanup](/learn/databases/relational/storage/) explains the mechanism.

## Materialise when restart matters

A snapshot held by one connection does not survive losing that connection. For a restartable job, materialise the export under a durable export ID. Capturing just order IDs fixes membership but later reads can see changed values or missing rows. Capturing the required columns fixes both membership and values, at the cost of another retained copy.

Create the capture in one statement or suitable snapshot transaction, then mark it complete only after the capture commits. Assign a deterministic export sequence. The writer records its last durably written sequence and resumes after it. If a destination write and progress update cannot commit together, use destination chunk identities that make replay safe, or tolerate and detect repeats.

Delete the materialisation only under its retention contract, after completion or expiry, and check tenant access to the export itself. The right continuation mechanism follows the promise: fresh navigation can use a keyset boundary; a consistent export needs a snapshot or an explicit durable capture as well.

A database connection acts with an identity and a set of permissions. If the application connects as an owner or administrator, a bad query can exercise that same authority. **Least privilege** gives each caller the operations and data it needs, then tests that it cannot cross the intended boundary.

Several boundaries are involved. Authentication establishes who connected. Transport protection keeps the exchange private and authenticates its peer. Object privileges allow operations on tables, columns or procedures. Row policies can restrict records inside a permitted operation. Application authorisation still decides whether this user's request should cause that operation.

Our workshop stores an o81 for tenant t4 and a different o81 for tenant t9. A tenant's key must never identify the other tenant's row by accident. We will give a runtime role narrow authority, test refusals through a separate native connection and expose a policy that can be bypassed by the wrong trust assumption.

## Separate the jobs before writing grants

The runtime application needs to read and record permitted orders. A migration process needs to change structure. A backup process needs the data and metadata required for recovery. An incident operator may need observation or exceptional intervention. Giving every one of them the database owner's credentials erases those distinctions.

Roles can collect permissions while separate login identities receive membership. Examine inherited permissions, default grants, public access and the ability to assume another role. A modest direct grant list does not restrict an account that can become the owner.

Ownership is especially consequential: owners can often alter an object's grants or policies. Keep the runtime role from owning its tables or inheriting the migration identity. Test against a fresh connection authenticated as runtime, rather than silently retaining an administrator's original session authority.

## Grant the statement the application really sends

A shipping worker may need order ID and status, yet no email or agreed amount. Column privileges or a deliberately secured view can expose that narrower interface. Reading a predicate column or returning a value can need read authority beyond the verb at the start of an UPDATE.

Use explicit field lists. A future sensitive column should not automatically become part of a worker's `SELECT *`. Also inspect schema-level creation rights, executable functions and accessible views; object names do not themselves establish a security boundary.

The native drill uses a schema `protected`, an owner role `migrator` and a separately authenticated `runtime` login. The owner creates:

```sql
CREATE TABLE protected.orders (
  tenant text, id text, total_cents integer,
  PRIMARY KEY (tenant, id)
);
INSERT INTO protected.orders VALUES
  ('t4', 'o81', 4000), ('t9', 'o81', 9000);
```

Runtime receives schema USAGE and SELECT, INSERT and UPDATE on that table. It receives no ownership, TRUNCATE, ALTER or membership in migrator. Those grants still cover both tenants until a row boundary is added.

## Tenant identity must come from a trusted authority

A query should carry both tenant and local identity:

```sql
SELECT id, total_cents FROM protected.orders
WHERE tenant = $1 AND id = $2;
```

The application must derive `$1` from authenticated, authorised context, not accept an arbitrary tenant parameter as permission. The composite primary key prevents one tenant's reference from accidentally naming another tenant's local o81, but does not decide which tenants a caller may read.

A row policy can provide a second boundary. For the drill, a PostgreSQL policy compares `tenant` with a transaction-local session setting. Existing-row access uses `USING`; new row values use `WITH CHECK`.

```sql
ALTER TABLE protected.orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_policy ON protected.orders TO runtime
USING (tenant = current_setting('app.tenant', true))
WITH CHECK (tenant = current_setting('app.tenant', true));
```

This policy demonstrates enforcement against an incorrect query under a correctly established t4 context. It does **not** prove isolation from a malicious caller who can set `app.tenant` arbitrarily. A shared runtime credential with arbitrary SQL can change that setting to t9. The context-setting authority is part of the design.

A tenant-specific database identity with a fixed policy, or a controlled procedure that verifies identity and chooses context, can establish a different boundary. Its ownership, role switching and executable permissions still need inspection. Do not allow the untrusted caller to invoke a privileged helper with any tenant they choose.

With a pool, establish context inside every transaction and clear/reset session state before reuse. A stale t4 setting borrowed by a t9 request can expose the wrong rows without any SQL injection. Transaction-local scope is useful, but only if every operation actually runs within that transaction on the expected connection.

## Test both permitted and denied work

On the separate runtime connection, the drill begins a transaction and sets the local tenant to t4. A broad SELECT returns only t4/o81/4000. An INSERT for t9 is rejected with SQLSTATE `42501` by row security. That failed transaction is then rolled back.

The same authenticated identity tries structural and privilege operations outside the failed block:

An administrator's separate query returns both tenants. PostgreSQL superusers and BYPASSRLS roles bypass row policies; table owners normally bypass them too unless the applicable force rule is used. Running the application under such a role would defeat the intended ordinary-row test.

Row policies also do not apply to every kind of operation. The denied TRUNCATE privilege matters precisely because filtering SELECT rows is not a general prohibition on destructive table operations. Constraint checks and errors can disclose facts even about rows a caller cannot select. Treat error responses and schema metadata as part of the exposed interface.

Repeat denied tests after migrations and role changes. An accidental broad grant, a new owner path or a permissive additional policy can widen the result. Test connection identity, not merely the text of the policy definition.

## Privileged code changes the authority of a call

A procedure or function may execute with rights different from its caller. That can offer a narrow business API, such as “book this session after checking the caller”, without granting direct table writes. It can also turn attacker-controlled names, paths or SQL into owner-level work.

Review who can execute the code, which identity it runs as, how it resolves object names and whether it accepts unrestricted SQL or tenant identifiers. Use safe parameter binding for values, deliberately qualified objects and the engine's security guidance for search paths and execution context. A view or function is an interface whose authority must be designed, not a shortcut around privilege review.

PostgreSQL's exact SECURITY DEFINER, owner and policy interactions belong in [roles, policies and privileged code](/learn/databases/relational/postgresql/access-control/). SQL Server has its own execution-context and ownership-chain rules. InnoDB/MySQL views and stored programs likewise have definer/invoker contracts. Similar names should not hide a change in whose privileges execute the operation.

## Connection and backup protection complete the boundary

A grant does not secure the connection. Restrict reachable endpoints, authenticate peers and use the deployment's supported verified encryption. Encryption without checking the server identity can protect traffic to an impostor. Store credentials outside source and ordinary logs, and avoid using an administrator secret in runtime diagnostics.

Rotate credentials through an overlap the service can operate: provision the replacement, make the application obtain it, replace pooled sessions, verify new connections, then revoke the old identity or secret. Existing authenticated sessions may need explicit retirement; changing a stored password does not universally end them. Test the engine/proxy contract and preserve an operator recovery path.

Backups contain the protected facts too. Their object storage, encryption keys, export destinations and restore credentials need an equally deliberate access model. Encryption at rest does not prevent a permitted SQL reader from exporting plaintext. A secret redacted in one query log may still appear in traces, error reports or backup files.

Keep useful audit evidence for privileged changes, role grants and exceptional data access, with access and retention controls of its own. Record enough to investigate who exercised authority without copying unnecessary sensitive payloads into the audit stream.

## Different engines place the boundary differently

PostgreSQL and SQL Server offer row security with different policy and bypass rules. MySQL 8.4 roles and grants do not provide the same native table-policy facility as PostgreSQL RLS; controlled views/procedures or application enforcement need explicit design. SQLite normally runs inside the application's process: file access, process trust and application authorisation carry much of the boundary, with its authorizer interface available for controlled SQL use. It has no separate built-in server login role system to copy these grants into.

[The native script](/learn/databases/relational/evidence/rl90-104-native.mjs) tests permission enforcement through a separately authenticated local runtime connection, using isolated trust authentication in a disposable cluster. [The observations](/learn/databases/relational/evidence/rl104-native-observed.json) record denials. The drill does not test passwords, TLS, network reachability, credential rotation or a hostile context-setting application; those require the actual deployment's connection and trust configuration.

Changing a PostgreSQL installation means moving more than table rows. The replacement needs compatible binaries and extensions, the expected collation and type behaviour, correct privileges and generators, and an application that still accepts and retrieves its facts.

The transfer also has an authority boundary. Once the replacement accepts a new order, reopening an older source without reconciliation loses that accepted work. A successful server start or `pg_upgrade` completion does not decide when that boundary is safe to cross.

We will choose among the native routes, then execute a bounded dump/restore migration of workshop orders with an extension, identity sequence and constraints. The dump/restore uses PostgreSQL 18.6 on both sides. A separate copy-mode `pg_upgrade` rehearsal moves PostgreSQL 17.6 to 18.6, then tests the application contract. The [dump/restore lab](/learn/databases/relational/evidence/rl110-native.py), in `migration` mode, records the first route. The [major-upgrade worksheet](/learn/databases/relational/evidence/lab/postgresql_major.py) records the separate 17.6→18.6 rehearsal.

## Choose the route from the permitted outage

A minor release ordinarily retains the major version’s storage compatibility. Its procedure normally replaces binaries and restarts the server, with release-note-specific instructions and extension/package compatibility still checked. Do not use that assumption to start a major version against an old major’s data directory.

A major upgrade can take several routes:

The data size and throughput of a rehearsal determine the likely outage. “Logical” is not automatically slow or fast enough; indexes, validation, storage, parallelism and external dependencies change the work.

Physical streaming is not the general major-upgrade bridge: it follows the major version’s storage/WAL contract. A logical migration can cross supported version combinations, but its source/target feature and type compatibility must be tested. [Logical replication](/learn/databases/relational/postgresql/logical-replication/) demonstrates why its subscriber is not automatically a complete replacement.

## Inventory the installation before the rehearsal

Record source and target server/client versions, locale/collation providers, encoding, extension versions and native libraries. The binaries for an extension need to exist on the target before its database objects can work there. A hosted service can restrict extensions or privileges even when its PostgreSQL major number matches a local server.

```sql
SELECT version();
SELECT extname, extversion FROM pg_extension ORDER BY extname;
SELECT datname, datcollate, datctype, datcollversion
FROM pg_database WHERE datname = current_database();
```

Also inventory roles, ownership, grants, tablespaces, scheduled jobs, foreign connections, large objects and application assumptions. `pg_dump` of one database does not recreate all cluster roles or every external service. Save globals with an appropriate procedure and review how they should map onto the destination’s operating model.

Keep the actual client/ORM/driver tests and representative queries in the acceptance plan. An extension can load while a changed operator or application assumption still breaks a request. An object can restore while its owner or runtime permissions are wrong.

Collation deserves its own test. A changed operating-system or ICU collation implementation can change ordering and invalidate assumptions behind indexes, uniqueness and pagination. Follow the documented rebuild and refresh procedure when versions differ. Refreshing a recorded version alone does not rebuild an index into the new order.

## The bounded migration has a known starting state

The native source database contains two tenant `t4` orders and the `btree_gist` extension:

```sql
CREATE EXTENSION btree_gist;
CREATE TABLE orders (
  tenant text, order_id text, request_id text,
  price numeric(10,2) CHECK (price >= 0),
  seq bigint GENERATED BY DEFAULT AS IDENTITY,
  PRIMARY KEY (tenant, order_id), UNIQUE (tenant, request_id)
);
INSERT INTO orders (tenant,order_id,request_id,price)
VALUES ('t4','o81','r81',20), ('t4','o82','r82',25);
```

Their agreed total is 45.00. The prices are copied historical facts, not recomputed from a current workshop price. The tenant-aware request uniqueness must survive the move.

The fixture creates a normal application login, then sets the source database’s connection limit to zero and attempts a fresh connection as that role. The server denies it because the database is not accepting further normal connections. The maintenance superuser can still perform the dump.

This is a bounded lab fence with no pre-existing application sessions. A production connection limit or `REVOKE CONNECT` alone does not stop sessions already connected, nor all privileged maintenance writers. Drain transactions, exclude background jobs and verify the actual source write authority before taking the final snapshot. Retain controlled maintenance access so the operator can finish the procedure.

## Export and restore with errors made visible

The harness takes a custom-format dump and restores into a separately initialised server on port 56815:

```sh
pg_dump -h "$SOURCE_SOCKET" -p 56810 -U lab \
  -d migration_source -Fc -f "$DUMP"
pg_restore -h "$TARGET_SOCKET" -p 56815 -U lab \
  -d migration_target --exit-on-error "$DUMP"
```

`--exit-on-error` makes an object failure stop this rehearsal rather than leaving a partially restored database unnoticed. The destination database and its available extension files already exist under the lab’s controlled setup.

A larger restore may deliberately use parallel jobs or staged index/constraint construction. Preserve the ordering and validation guarantees those choices need, and record which errors are permitted. Treating an error-filled transcript as a successful restore because most rows arrived leaves acceptance undefined.

The restored extension is present, the two orders retain their facts, and the identity sequence reports that its earlier values have been used. The next default-generated value is 3. This differs from native logical row replication, where the sequence state was not advanced by replicated explicit row values.

## Acceptance tests exercise the contract

The lab reads both restored orders, checks extension and collation metadata, inserts `o83/r83` at 30 and verifies the generated sequence value and aggregate:

```text
next generated seq: 3
orders: 3
total agreed price: 75.00
```

It then attempts another order under request `r81`. The restored unique constraint rejects it. A negative price is also rejected by the restored check constraint. Those are meaningful acceptance tests: the target still enforces identity and price invariants, rather than merely storing the original positive rows.

The original source remains at two orders. This makes the later rollback problem visible. `o83` is valid work accepted only on the new target. Routing back to the source would discard that acceptance unless it is explicitly reconciled.

This fixture does not test a full application, credentials under a hosted provider, changed ICU behaviour or an optional third-party extension. Its concrete acceptance proves the bounded native route and these schema contracts. Add the actual clients, queries, external effects and target-specific permissions before using the procedure for a service.

## Rehearse a major version with pg_upgrade

`pg_upgrade` needs both the old and new binary installations and compatible extension libraries, plus prepared old/new clusters. Run its checks against the exact versions and options planned for the outage. A generic dry-run command against invented directories establishes nothing about compatibility.

Copy, clone and link modes change time, space and rollback resources. Hard-link mode shares files between the old and new clusters. Once the new server writes them, the old copy is not an independent rollback image. Preserve the required independent backup/snapshot and follow the tool’s exact restrictions before starting either installation.

The tool checks a set of binary and catalogue compatibility requirements; it cannot prove every application semantic or extension upgrade script correct. Rehearse extension upgrades and generated post-upgrade actions, ensure appropriate statistics, then run the same application acceptance on the new installation.

The [major-upgrade worksheet](/learn/databases/relational/evidence/lab/postgresql_major.py) uses PostgreSQL 17.6 compiled from the official source and the installed PostgreSQL 18.6. It initialises both clusters with UTF-8, libc C locale and checksums enabled, then stops the source. The new installation’s `pg_upgrade --check` reports that the clusters are compatible; the copy-mode upgrade completes.

On 18.6, the two original orders still total 45.00. A normal application role inserts `r83` at 30.00, receives identity value 3 and reads a total of 75.00. Duplicate request `r81` and a negative price remain rejected. An `ANALYZE` refreshes this small database’s statistics before acceptance.

The retained 17.6 files can still start because copy mode left them independent. An isolated maintenance read finds only `r81` and `r82`, totalling 45.00. The files survived, but the old history is already missing `r83`. Reopening that source to application traffic would therefore lose accepted work. Both disposable servers are stopped and removed after the inspection.

This second rehearsal has no optional extensions, non-default tablespaces or changed collation implementation. The dump/restore tests `btree_gist`; the major upgrade does not. Compatibility of the real extension inventory and actual client workload still needs its own rehearsal. Neither test establishes the outage for a production data set.

## A short logical cutover still needs a fence

For a logical route, copy/synchronise while the source remains the writer. Deploy compatible destination schema first, monitor table readiness and lag, and keep destination application writes excluded. A healthy row count alone does not prove every final transaction arrived.

At cutover, fence source writes and establish a final source position or marker covering accepted work. Wait for the destination to apply that boundary through the required tables. Coordinate any separate streams and non-replicated objects. Repair sequences and validate rows, roles, extensions and client behaviour before routing writes.

If validation fails before the target accepts writes, reopening a still-current fenced source may be straightforward. After the first target-only acceptance, rollback needs a deliberate reverse transfer or reconciliation with its own identity/conflict rules. Forward replication does not create that reverse path automatically.

Keep the writer decision singular throughout. Update routing, invalidate stale pools, exclude old jobs and ensure the former writer cannot accept late transactions. The external fencing responsibility is the same one exposed by [physical promotion](/learn/databases/relational/postgresql/replication/).

A successful migration leaves an accepted target and a bounded plan for the old resources. Keep the former writer fenced until it is retired or deliberately reconfigured for another role. Retain backups and reconciliation evidence for the agreed recovery window; a successful binary upgrade is not a reason to erase them.

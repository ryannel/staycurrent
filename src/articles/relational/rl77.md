A relational schema divides stored facts into tables and connects them through keys. A customer can change their name without changing their bookings. A workshop session can move to another room without rewriting every customer who attends it. The schema decides which facts have one home and which combinations are allowed to exist.

Start with the meaning of one row. In this workshop service, a customer belongs to a tenant, a session is one scheduled workshop, and a booking connects a customer to a session. Tenant `t4` has customer `42`, session `s7` and booking `b17`. Another tenant may use the same local identifiers. The pair `(tenant_id, customer_id)` identifies a customer; `42` alone does not.

This article builds those relationships, then follows an order whose agreed price must survive a catalogue change. The SQL examples use PostgreSQL, but the design questions apply equally to server databases and embedded SQLite.

Run this page’s SQL in a [fresh disposable PostgreSQL database](/learn/databases/relational/evidence/relational-fixtures.md). The workshop identifiers recur, but each article supplies its own table shapes.

## Give each table one row meaning

A first design might put the customer and session details on every booking:

<table><caption>Two bookings before separating their facts</caption><thead><tr><th>Tenant</th><th>Booking</th><th>Customer</th><th>Name</th><th>Session</th><th>Room</th><th>Capacity</th></tr></thead><tbody><tr><td>t4</td><td>b17</td><td>42</td><td>Ada</td><td>s7</td><td>North</td><td>2</td></tr><tr><td>t4</td><td>b18</td><td>43</td><td>Ben</td><td>s7</td><td>North</td><td>2</td></tr></tbody></table>

Move `s7` to the South room by updating only `b17`. The database now says that one session occupies two rooms. Nothing about either booking row reveals which room is correct.

Here is the contradictory state as an executable change:

```sql
CREATE TABLE booking_flat (booking_id text, session_id text, room text);
INSERT INTO booking_flat VALUES ('b17','s7','North'),('b18','s7','North');
UPDATE booking_flat SET room = 'South' WHERE booking_id = 'b17';
SELECT * FROM booking_flat ORDER BY booking_id;
```

```text
booking_id | session_id | room
b17        | s7         | South
b18        | s7         | North
```

There are two more problems before anyone makes that mistake. A session cannot be stored until somebody books it, because its only home is a booking row. Deleting its last booking deletes its room and capacity too. These are update, insertion and deletion anomalies: independent facts have been made to share one lifetime.

Separate the facts that change independently:

<div data-relational-component="relational-design-tools/Facts" data-number="1"></div>

A customer may have many bookings, and a session may have many bookings. Each booking has exactly one of each. This is a many-to-many relationship represented by a table of its own. Its row can also hold facts about that relationship: when Ada booked, whether she cancelled and which attendance option she chose.

The relationship's identity needs a decision. If one customer can book a session only once, `(tenant_id, customer_id, session_id)` can be a candidate key: a minimal combination that uniquely identifies a booking. If cancelling and rebooking creates another booking, that combination no longer identifies every historical row. A separate booking ID can identify the occurrence, with another rule governing which occurrences may be active together.

## Keys express identity and allowed references

A primary key is the candidate key chosen as a table's principal identifier. Other candidate keys remain important and can be enforced with `UNIQUE`. An arbitrary generated ID does not remove the need to prevent duplicate business identities.

Here is a small schema. The tenant column participates in every local identity and every reference.

```sql
CREATE TABLE customers (
  tenant_id text NOT NULL,
  customer_id integer NOT NULL,
  name text NOT NULL,
  PRIMARY KEY (tenant_id, customer_id)
);
CREATE TABLE sessions (
  tenant_id text NOT NULL,
  session_id text NOT NULL,
  room text NOT NULL,
  capacity integer NOT NULL CHECK (capacity > 0),
  PRIMARY KEY (tenant_id, session_id)
);
CREATE TABLE bookings (
  tenant_id text NOT NULL,
  booking_id text NOT NULL,
  customer_id integer NOT NULL,
  session_id text NOT NULL,
  PRIMARY KEY (tenant_id, booking_id),
  UNIQUE (tenant_id, customer_id, session_id),
  FOREIGN KEY (tenant_id, customer_id)
    REFERENCES customers (tenant_id, customer_id),
  FOREIGN KEY (tenant_id, session_id)
    REFERENCES sessions (tenant_id, session_id)
);
INSERT INTO customers VALUES ('t4',42,'Ada'), ('t4',43,'Ben');
INSERT INTO sessions VALUES ('t4','s7','North',2);
INSERT INTO bookings VALUES ('t4','b17',42,'s7'), ('t4','b18',43,'s7');
UPDATE sessions SET room = 'South'
WHERE tenant_id = 't4' AND session_id = 's7';
SELECT b.booking_id, c.name, s.room
FROM bookings b
JOIN customers c USING (tenant_id, customer_id)
JOIN sessions s USING (tenant_id, session_id)
ORDER BY b.booking_id;
```

```text
booking_id | name | room
b17        | Ada  | South
b18        | Ben  | South
```

The `FOREIGN KEY` requires the referenced customer or session to exist. It also requires the same tenant on both sides. A globally unique booking ID can be convenient for URLs, but it would not make a reference to customer `42` tenant-safe. [Constraints and tenant boundaries](/learn/databases/relational/constraints/) follows what each rule enforces.

A natural key comes from the domain, such as a room code. A surrogate key is assigned for identity, such as a generated integer or UUID. Prefer a stable value for references. An email address may identify an account today and change tomorrow; making it the primary key spreads that edit to every reference. A surrogate key plus an appropriately scoped unique email rule often separates the two jobs better. Whether two email strings count as equal is itself a design decision, covered in [Values, missing data and equality](/learn/databases/relational/values/).

## Dependencies explain normalisation

The reason the room belongs in `sessions` is a dependency: given a tenant and session ID, the business rules determine one room. Write that as `(tenant_id, session_id) → room`. It does not follow from seeing two equal values in a sample. It follows from what a session means.

In the first table, the booking key determined the session key, which determined the room. The room was therefore stored repeatedly for a reason unrelated to the booking's identity. Normalisation uses dependencies like these to find facts with the wrong home.

First normal form asks for values in the declared domains rather than a list packed into one field. A comma-separated `customer_ids` value makes membership, references and individual changes difficult. A booking row per customer/session relationship makes those operations ordinary queries. This does not forbid every array or JSON value: an opaque document can be one value when its internals are not independently referenced or constrained.

Second normal form removes facts that depend on only part of a composite candidate key. In an order-line table keyed by `(tenant_id, order_id, line_no)`, the order's customer belongs to the order, not every line. Third normal form also removes dependencies through non-key facts: a room's street address belongs to the room if rooms have stable identities and independent addresses. These names describe progressively stronger checks on the same question: what determines this fact?

For an awkward schema, inspect all candidate keys, not just the chosen primary key. Boyce–Codd normal form strengthens the rule: whenever some columns determine a value outside that set, those columns must be a superkey, a combination that identifies a row. Decomposition still needs care: joining the pieces must reproduce the original allowed facts without inventing combinations, and important constraints should remain enforceable. A mechanical split by column count guarantees neither.

## An agreed price is a different fact

Tenant `t4` sells a workshop seat for €20. Order `o81` bought two seats at that price. The next week the catalogue price becomes €22. Rejoining the old order to today's price must not turn the agreement into €44.

```sql
CREATE TABLE products (
  tenant_id text, product_id text,
  current_price numeric(10,2) NOT NULL,
  PRIMARY KEY (tenant_id, product_id)
);
CREATE TABLE orders (
  tenant_id text, order_id text, customer_id integer NOT NULL,
  PRIMARY KEY (tenant_id, order_id),
  FOREIGN KEY (tenant_id, customer_id)
    REFERENCES customers (tenant_id, customer_id)
);
CREATE TABLE order_lines (
  tenant_id text, order_id text, line_no integer,
  product_id text NOT NULL, quantity integer NOT NULL CHECK (quantity > 0),
  agreed_unit_price numeric(10,2) NOT NULL CHECK (agreed_unit_price >= 0),
  PRIMARY KEY (tenant_id, order_id, line_no),
  FOREIGN KEY (tenant_id, order_id) REFERENCES orders,
  FOREIGN KEY (tenant_id, product_id) REFERENCES products
);
INSERT INTO products VALUES ('t4','seat',20);
INSERT INTO orders VALUES ('t4','o81',42);
INSERT INTO order_lines VALUES ('t4','o81',1,'seat',2,20);
UPDATE products SET current_price = 22
WHERE tenant_id = 't4' AND product_id = 'seat';
SELECT quantity * agreed_unit_price AS agreed_total
FROM order_lines WHERE tenant_id = 't4' AND order_id = 'o81';
```

```text
agreed_total
40.00
```

`current_price` is determined by the product now. `agreed_unit_price` is determined by this order line's agreement. They happened to be equal when the order was placed, but they are different facts. Keeping the agreed price is history, not a cached copy that should follow catalogue updates. If the displayed product name must also remain exactly as agreed, store that agreed description too.

A cached order total is a different kind of duplication: it is derived from the lines. It earns its place only if readers need the saving and writers can maintain it. Name the authoritative inputs, update the copy in the same transaction where possible, and retain a reconciliation query that recomputes it. A deliberate copy without an owner or repair path eventually becomes another contradictory room.
